# C-6 — Error handling: `Result`, `?`, восстановление ошибок

Атомарное задание блока C (Rust, параллельный трек). Одна глава — одно задание.
**Пройдено:** главы 1–8. **Эта:** глава 9. Дальше по карте — гл.10 (traits/generics/lifetimes).

Тема: обработка ошибок (error handling) в Rust — `panic!` против восстановимых (recoverable) ошибок, тип `Result<T, E>`, оператор `?` для проброса (propagation), кастомный enum-ошибок, восстановление (recovery) вместо падения.

## Что написать

Мини-парсер спецификации портов — в домене будущего сканера (тема блока накапливается).
На вход строка вида `"80,443,8000-8003,foo,70000,,22"`, на выход — список валидных портов + список ошибок по «плохим» токенам. Программа **не падает** на плохом токене, а пропускает его и продолжает (это и есть «восстановление ошибок»).

Проект: `cargo new port_parser` в `rust/`. Код в `rust/port_parser/src/main.rs`.

### Поведение
Разбить строку по запятой. Каждый токен — либо одиночный порт `"443"`, либо диапазон `"8000-8003"`.
- Одиночный: распарсить в `u16`, провалидировать (0 — невалидный порт).
- Диапазон: распарсить оба конца, проверить `start <= end`, развернуть в набор портов.
- Плохой токен (не число / пустой / вне диапазона / `start > end`) → **не паника**, а ошибка в список; идём дальше.

В конце напечатать: сколько портов собрано, сами порты, и отдельно — список ошибок с указанием токена.

Для тестового входа `"80,443,8000-8003,foo,70000,,22"` ожидаемо: валидны `80, 443, 8000, 8001, 8002, 8003, 22`; ошибки на `foo` (не число), `70000` (вне u16), `""` (пусто).

## Что должно быть задействовано (чек по главе 9)

1. **Кастомный enum-ошибок** `ParseError` с несколькими вариантами (варианты с данными — гл.6). `#[derive(Debug)]`.
2. **`Result<T, E>`** как возвращаемый тип функций-парсеров.
3. **Оператор `?`** — проброс ошибки вверх минимум в одном месте (при парсинге обоих концов диапазона: ошибка первого конца сразу прекращает разбор токена).
4. **`match`** по `Result` — для восстановления: в цикле по токенам `Ok` → добавить порты, `Err` → положить в список ошибок и **continue**.
5. **`.parse::<u16>()`** — он сам возвращает `Result`; превратить его ошибку в свою через `.map_err(|_| ParseError::…)?` (простое замыкание — как `unwrap_or_else` в guessing game, это ещё не гл.13).
6. **`panic!` / `expect` осознанно** — добавь ровно одно место, где паника уместна (например `expect` на инварианте, который ты гарантируешь сам), и в конспекте объясни, почему там паника, а не `Result`.

## Механика (словами, без кода)

- **`?` работает так:** `выражение?` — если `Ok(v)`, достаёт `v` и продолжает; если `Err(e)`, немедленно делает `return Err(e)` из текущей функции. Поэтому `?` можно писать только в функции, которая сама возвращает `Result` (или `Option`). Тип ошибки должен совпадать с типом `Err` функции — отсюда `.map_err(...)` перед `?`, чтобы привести `ParseIntError` к твоему `ParseError`.
- **Проброс vs восстановление** — это два уровня. Низкоуровневые функции (`parse_single`, `parse_token`) **пробрасывают** через `?` — они не решают, что делать с ошибкой. Верхний уровень (`parse_spec`) **решает**: ловит `Err` через `match` и восстанавливается (пропуск токена). Это стандартный рисунок: `?` тащит ошибку вверх до места, где есть контекст для решения.
- **Разворот диапазона** без итераторных адаптеров (гл.13): обычный `for p in start..=end { … }` и `push` в `Vec`. `start..=end` — inclusive range, ты его видел.
- **`.parse()` и тип:** `tok.parse::<u16>()` — turbofish задаёт целевой тип. `u16` сам отсекает `> 65535` (не влезает → `Err`), но `0` он примет — значит проверку на `0` (невалидный порт) делаешь руками.

## Security-фокус (§4)

Тема низкоуровневая косвенно, но связь с безопасностью прямая:
- **Парсинг недоверенного ввода (untrusted input) не должен паниковать.** `panic!` на плохом токене = отказ в обслуживании (DoS): один кривой порт роняет весь сканер. Модель «`Result` + восстановление» — это и есть защита: плохой вход деградирует gracefully, а не валит процесс. Это ровно тот контраст, который проверяет глава 9.
- В отличие от C здесь нет UB / выхода за границы буфера при парсинге — Rust не даст. Но логическая уязвимость (DoS через панику) полностью на тебе: `unwrap` на пользовательском вводе — типичная дыра.
- Диапазон `70000` в C легко даёт integer overflow при укладке в `uint16_t` (тихое усечение → 4464). В Rust `.parse::<u16>()` вернёт `Err` — сравни это поведение в конспекте.
