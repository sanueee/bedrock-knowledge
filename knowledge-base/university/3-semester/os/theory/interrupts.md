# Прерывания / Interrupts (x86, Pintos)

## Что это

Прерывание (interrupt) — это сигнал, по которому процессор приостанавливает текущий код, выполняет функцию-обработчик (interrupt handler) и возвращается ровно в то место, где остановился. Прерванный код этого «не замечает».

Альтернатива прерываниям — опрос (polling): программа сама постоянно спрашивает устройство «есть что-нибудь?». Аналогия: опрос — каждые 5 секунд подходить к двери проверять, не пришёл ли кто-то; прерывание — дверной звонок. Опрос тратит процессорное время впустую, а редкий опрос пропускает события.

---

## Ключевые термины (English)

- **interrupt** — асинхронный или синхронный сигнал процессору прервать текущий поток выполнения
- **interrupt handler** — функция, которая вызывается при прерывании
- **interrupt vector** — номер прерывания 0–255, индекс в IDT
- **IDT (Interrupt Descriptor Table)** — таблица из 256 записей «номер вектора → адрес обработчика», её формат задан процессором
- **IDTR** — регистр процессора с адресом IDT
- **PIC (Programmable Interrupt Controller)** — микросхема 8259, собирает линии IRQ от устройств и передаёт их процессору
- **IRQ (Interrupt Request)** — физическая линия запроса прерывания от устройства
- **EOI (End Of Interrupt)** — подтверждение контроллеру PIC, что прерывание обработано
- **external interrupt** — внешнее (аппаратное) прерывание от устройства, асинхронное
- **exception / fault** — внутреннее прерывание, вызванное текущей инструкцией, синхронное
- **software interrupt** — программное прерывание, инструкция `int N` (в т.ч. syscall)
- **IF (Interrupt Flag)** — бит EFLAGS: 1 — внешние прерывания разрешены, 0 — запрещены
- **interrupt gate / trap gate** — тип записи IDT: interrupt gate сбрасывает IF при входе, trap gate — нет
- **DPL (Descriptor Privilege Level)** — минимальный уровень привилегий, с которого можно вызвать вектор через `int N`
- **interrupt context** — состояние «сейчас выполняется обработчик внешнего прерывания»
- **critical section** — участок кода, который нельзя прерывать посередине
- **polling** — опрос устройства в цикле вместо ожидания прерывания
- **preemptive multitasking** — вытесняющая многозадачность: ОС сама отбирает процессор у потока

---

## Как работает (x86)

1. **Проверка после каждой инструкции.** Закончив инструкцию, процессор смотрит: пришёл ли сигнал прерывания и установлен ли флаг IF.
2. **Номер вектора.** У каждого прерывания есть номер 0–255 — «какой звонок прозвенел».
3. **Поиск в IDT.** Процессор берёт запись `IDT[вектор]` (адрес таблицы — в регистре IDTR). В Pintos таблица — `static uint64_t idt[INTR_CNT]` в `threads/interrupt.c:28`.
4. **Сохранение состояния.** Процессор сам кладёт в стек `EFLAGS`, `CS`, `EIP` (адрес возврата) и прыгает на обработчик. Если запись — interrupt gate, IF сбрасывается автоматически.
5. **Обработчик.** Выполняется код ОС.
6. **Возврат.** Инструкция `iret` достаёт из стека `EIP`, `CS`, `EFLAGS` — прерванный код продолжает работу с той же инструкции и с тем же IF.

```
  код потока:  инструкция 1
               инструкция 2   ← пришло прерывание
               ─────────────────────────────────────────┐
                                    обработчик          │
               ◄────────────────── iret ────────────────┘
               инструкция 3   (поток продолжает как ни в чём не бывало)
```

### Путь прерывания в Pintos

```
устройство ─ IRQ ─> PIC 8259 ─> CPU ─> IDT[vec] ─> intrNN_stub  (threads/intr-stubs.S)
                                                      push код ошибки (0 или настоящий)
                                                      push номер вектора
                                                      jmp intr_entry
                                                           │
                                   intr_entry: pushl ds/es/fs/gs, pushal
                                   → на стеке лежит struct intr_frame
                                   call intr_handler(frame)
                                                           │
                                   intr_handler (threads/interrupt.c:346)
                                   handler = intr_handlers[frame->vec_no]
                                   handler(frame)
                                   если внешнее: EOI в PIC, возможно thread_yield
                                                           │
                                   intr_exit: popal, pop сегменты, iret
```

Все 256 заглушек генерирует макрос `STUB(NUMBER, TYPE)` в `intr-stubs.S`. Для векторов, где процессор сам кладёт код ошибки (page fault и др.), `TYPE = REAL`, иначе `zero` — кладётся фиктивный 0, чтобы `struct intr_frame` всегда имела одинаковую раскладку.

## Виды прерываний

### 1. Внешние (аппаратные) — external interrupts

Источник — устройство вне процессора. **Асинхронные**: приходят в любой момент, между любыми двумя инструкциями. Устройства подключены к PIC 8259.

По умолчанию BIOS отображает IRQ0–7 на векторы `0x08–0x0F`, но векторы `0x00–0x1F` заняты исключениями процессора. Поэтому `pic_init` (`threads/interrupt.c:238`) переназначает (remap) линии:

```c
outb (PIC0_DATA, 0x20); /* ICW2: line IR0...7 -> irq 0x20...0x27. */
```

В Pintos внешние прерывания — векторы `0x20–0x2F`, регистрируются через `intr_register_ext`:

| Вектор | IRQ | Устройство | Где регистрируется |
|---|---|---|---|
| `0x20` | 0 | таймер 8254 | `devices/timer.c:39` |
| `0x21` | 1 | клавиатура | `devices/kbd.c:33` |
| `0x24` | 4 | последовательный порт | `devices/serial.c:90` |
| `0x2E`, `0x2F` | 14, 15 | IDE-диски | `devices/ide.c:142` |

### 2. Исключения — exceptions

Вызывает **сама текущая инструкция**. **Синхронные**: та же инструкция с теми же данными вызовет исключение снова.

- `0` — `#DE` деление на ноль
- `14` — `#PF` page fault, обращение к несуществующей или запрещённой странице
- регистрируются в `userprog/exception.c` через `intr_register_int`

### 3. Программные — software interrupts

Программа вызывает их **намеренно** инструкцией `int N`. Главный пример — системный вызов (syscall):

```c
intr_register_int (0x30, 3, INTR_ON, syscall_handler, "syscall");   // userprog/syscall.c:12
```

Второй аргумент `3` — DPL: вызывать `int 0x30` можно даже из пользовательского режима (ring 3).

## Включение и выключение прерываний

Флагом IF управляют инструкции процессора `cli` (clear, запретить) и `sti` (set, разрешить). В Pintos они обёрнуты (`threads/interrupt.c`):

```c
enum intr_level intr_disable (void);               // cli, возвращает прежнее состояние
enum intr_level intr_enable (void);                // sti
enum intr_level intr_set_level (enum intr_level);  // вернуть сохранённое
enum intr_level intr_get_level (void);             // INTR_ON / INTR_OFF
```

Шаблон критической секции:

```c
enum intr_level old_level = intr_disable ();
/* ... сюда не ворвётся ни один внешний обработчик ... */
intr_set_level (old_level);
```

**Почему `intr_set_level(old_level)`, а не `intr_enable()`:** если код вызван там, где прерывания уже были выключены (например, из другой критической секции), безусловный `intr_enable()` включил бы их раньше времени и сломал бы внешнюю секцию. Сохранение и восстановление делает секции вкладываемыми.

**Зачем выключать.** Внешнее прерывание может прийти между любыми двумя инструкциями. Если обработчик меняет те же данные, что и основной код, получается состояние гонки (race condition). Пример — `timer_ticks()` в [[pintos-timer-ticks]]: 64-битный счётчик на 32-битном x86 читается двумя инструкциями.

`cli` блокирует **только внешние** прерывания. Исключения и `int 0x30` происходят всё равно — их вызывает сам код.

## Контекст прерывания — чего нельзя в обработчике

Обработчик внешнего прерывания прерывает **случайный** поток в **случайный** момент. Правила Pintos (комментарий `threads/interrupt.c:39`):

- **Выполняется с выключенными прерываниями.** Для внешних векторов в IDT ставится interrupt gate (`register_handler`, `threads/interrupt.c:170`: `INTR_OFF` → `make_intr_gate`). Внешние обработчики не вкладываются друг в друга.
- **Спать нельзя.** Никаких `sema_down`, `lock_acquire`, `timer_sleep`, `thread_block`. Обработчик — не поток, который можно усыпить: он выполняется «поверх» чужого потока на его стеке.
- **Работать быстро.** Пока он работает, остальные внешние прерывания ждут, а таймерные могут потеряться.
- **Переключать поток напрямую нельзя** — `thread_yield` начинается с `ASSERT (!intr_context ())`. Вместо этого `intr_yield_on_return()` ставит флаг, и переключение происходит после завершения обработчика (подробно — [[pintos-preemption]]).
- Проверка «я в обработчике?» — `intr_context()`.

Аналогия из Linux: те же ограничения у signal handler — в нём можно вызывать только async-signal-safe функции ([[async-signal-safe]]). Сигнал — программный аналог аппаратного прерывания ([[signals-linux]]).

## Пример: регистрация и обработчик таймера

```c
/* devices/timer.c */
void
timer_init (void) 
{
  pit_configure_channel (0, 2, TIMER_FREQ);
  intr_register_ext (0x20, timer_interrupt, "8254 Timer");
}

static void
timer_interrupt (struct intr_frame *args UNUSED)
{
  ticks++;
  thread_tick ();
}
```

```c
/* threads/interrupt.c:346 — общий диспетчер, фрагмент для внешних прерываний */
external = frame->vec_no >= 0x20 && frame->vec_no < 0x30;
if (external) 
  {
    ASSERT (intr_get_level () == INTR_OFF);
    ASSERT (!intr_context ());
    in_external_intr = true;
    yield_on_return = false;
  }

handler = intr_handlers[frame->vec_no];
if (handler != NULL)
  handler (frame);
...
if (external) 
  {
    in_external_intr = false;
    pic_end_of_interrupt (frame->vec_no);   // EOI, иначе PIC не пришлёт следующее
    if (yield_on_return) 
      thread_yield (); 
  }
```

## Зачем ОС прерывание таймера

Поток выполняет `while (1) {}`. Без прерываний он никогда не отдаст процессор — управление к ядру просто не вернётся. Прерывание таймера **каждые 10 мс насильно** передаёт управление ядру даже от зациклившегося потока. Ядро решает, не пора ли переключить поток. Это и есть вытесняющая многозадачность (preemptive multitasking). Без таймера возможна только кооперативная (cooperative) — потоки отдают процессор добровольно.

## Подводные камни

- **Разорванное чтение (torn read) многословных данных.** Обработчик меняет `int64_t`, основной код читает его двумя инструкциями → значение из старой младшей и новой старшей половины. Лечится выключением прерываний на время чтения.
- **Забытый EOI.** Без `pic_end_of_interrupt` PIC больше не пришлёт прерывание этой линии (и ниже по приоритету) — устройство «замолкает».
- **Сон в обработчике.** Блокировка в interrupt context ломает систему: блокируется не обработчик, а случайный прерванный поток, с выключенными прерываниями — вплоть до зависания.
- **`intr_enable()` вместо восстановления уровня** ломает вложенные критические секции.
- **Долгая работа с выключенными прерываниями.** PIC хранит только один ожидающий запрос на линию: пока прерывания выключены дольше тика, лишние тики теряются и часы ОС отстают.
- **Ложные прерывания (spurious interrupts).** Векторы `0x27` и `0x2F` могут прийти без причины из-за аппаратной гонки — `intr_handler` их явно игнорирует.

### Безопасность

- **DPL — граница привилегий.** Только вектор `0x30` и исключения `#BP`, `#OF`, `#BR` (`userprog/exception.c:36`) имеют DPL 3. Если пользовательская программа выполнит `int 0x20` (DPL 0), процессор сгенерирует General Protection fault вместо вызова обработчика таймера. Ошибка в DPL открыла бы пользователю вызов ядерных обработчиков с поддельным `intr_frame`.
- **`intr_frame` — недоверенные данные в syscall.** Регистры и указатель стека в кадре syscall заданы пользователем. Любой указатель оттуда перед разыменованием нужно проверять (ниже `PHYS_BASE`, отображён в таблице страниц) — иначе ядро читает/пишет по адресу, который выбрал атакующий.
- **Гонки обработчик ↔ основной код** — это классическое неопределённое состояние данных, а не UB языка C, но последствия такие же непредсказуемые: порча списков (`ready_list`, список спящих) → use-after-free или бесконечные циклы в ядре.
