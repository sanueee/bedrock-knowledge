# Калибровка таймера и короткие задержки / timer_calibrate & loops_per_tick (Pintos)

## Что это

`timer_calibrate` при загрузке один раз измеряет, сколько итераций пустого цикла `busy_wait` помещается в один тик таймера, и записывает результат в `loops_per_tick` (`devices/timer.c:25`). По этому числу `real_time_delay` отмеряет задержки короче тика (микро- и наносекунды), которые через `ticks` отмерить невозможно.

```
ticks          — «линейка» с делениями по 10 мс: точная, но грубая
loops_per_tick — «нониус»: делит одно деление линейки на сотни тысяч частей
```

Зачем: устройствам нужны паузы в микросекунды — контроллеру IDE после сброса ~10 мкс (`devices/ide.c:194`), контроллеру клавиатуры 2 мкс между опросами (`devices/shutdown.c:73`). Ждать ради этого тик (в 1000 раз дольше) расточительно, а с выключенными прерываниями — невозможно.

---

## Ключевые термины (English)

- **calibration** — калибровка: измерение скорости цикла относительно эталона времени
- **busy wait / delay loop** — пустой цикл фиксированной длины для задержки
- **loops per tick** — число итераций цикла за один тик таймера
- **BogoMIPS** — аналог в Linux: калибровка задержечного цикла при загрузке
- **optimization barrier** — конструкция, запрещающая компилятору оптимизировать через неё
- **`volatile`** — квалификатор C: значение может измениться вне видимости компилятора
- **inlining** — встраивание тела функции в место вызова
- **code alignment** — выравнивание машинного кода в памяти, влияет на скорость
- **binary search** — двоичный поиск
- **exponential search** — поиск удвоением до выхода за границу, затем уточнение
- **integer truncation** — отбрасывание дробной части при целочисленном делении
- **integer overflow** — выход результата за диапазон типа

## Как работает

### 1. Один и тот же цикл для калибровки и задержек

```c
/* devices/timer.c:204 */
static void NO_INLINE
busy_wait (int64_t loops) 
{
  while (loops-- > 0)
    barrier ();
}
```

`busy_wait` вызывают **и** калибровка (`too_many_loops`), **и** каждая задержка (`real_time_delay`). Это принципиально: `loops_per_tick` означает «итераций **именно этого** цикла за тик». Другой машинный код дал бы другую скорость — число стало бы бессмысленным.

**`NO_INLINE`** (`lib/debug.h:9`) = `__attribute__ ((noinline))`. Без него компилятор мог бы встроить цикл в разные места по-разному, с разным выравниванием и разной скоростью.

**`barrier()`** (`threads/synch.h:49`):

```c
#define barrier() asm volatile ("" : : : "memory")
```

Пустая ассемблерная вставка, которая сообщает компилятору «здесь может измениться любая память». Нужна по двум причинам:

1. Без неё тело цикла пустое → компилятор с `-O` **выбросит цикл**, задержка станет нулевой.
2. В `too_many_loops` — `while (ticks == start) barrier ();`. `ticks` не объявлена `volatile`, внутри цикла её никто не пишет → компилятор вправе прочитать её **один раз** в регистр → вечный цикл. Про прерывание, меняющее `ticks` «из ниоткуда», компилятор не знает. `barrier()` заставляет перечитывать память на каждой итерации.

### 2. `too_many_loops` — одно измерение

```c
/* devices/timer.c:180 */
static bool
too_many_loops (unsigned loops) 
{
  /* Wait for a timer tick. */
  int64_t start = ticks;
  while (ticks == start)
    barrier ();

  /* Run LOOPS loops. */
  start = ticks;
  busy_wait (loops);

  /* If the tick count changed, we iterated too long. */
  barrier ();
  return start != ticks;
}
```

1. Дождаться смены `ticks` — замер стартует ровно на **границе** тика.
2. Запомнить `ticks`, выполнить `loops` итераций.
3. `ticks` изменился → итераций больше, чем помещается в тик → `true`.

`ticks` читается напрямую, без выключения прерываний: нужно только «изменилось или нет».

### 3. `timer_calibrate` — поиск числа

```c
/* devices/timer.c:44 */
void
timer_calibrate (void) 
{
  unsigned high_bit, test_bit;

  ASSERT (intr_get_level () == INTR_ON);
  printf ("Calibrating timer...  ");

  /* Approximate loops_per_tick as the largest power-of-two
     still less than one timer tick. */
  loops_per_tick = 1u << 10;
  while (!too_many_loops (loops_per_tick << 1)) 
    {
      loops_per_tick <<= 1;
      ASSERT (loops_per_tick != 0);
    }

  /* Refine the next 8 bits of loops_per_tick. */
  high_bit = loops_per_tick;
  for (test_bit = high_bit >> 1; test_bit != high_bit >> 10; test_bit >>= 1)
    if (!too_many_loops (high_bit | test_bit))
      loops_per_tick |= test_bit;

  printf ("%'"PRIu64" loops/s.\n", (uint64_t) loops_per_tick * TIMER_FREQ);
}
```

**`ASSERT (INTR_ON)`** — без прерываний `ticks` не растёт, `too_many_loops` зависнет в ожидании тика.

**Шаг 1 — грубая оценка степенью двойки.** Старт с `2^10 = 1024`, удвоение, пока удвоенное ещё помещается в тик. Итог — **наибольшая степень двойки `2^k`, которая помещается в тик**. `ASSERT (loops_per_tick != 0)` ловит переполнение `unsigned` (сдвиг `1u << 31 << 1` = 0).

Пример: реально помещается ~300 000 → результат `2^18 = 262 144`, т.к. `2^19 = 524 288` уже не помещается.

**Шаг 2 — уточнение младших битов.** Истинное значение между `2^k` и `2^(k+1)`. Цикл перебирает биты `high_bit>>1`, `>>2`, …, `>>9` (условие `!= high_bit >> 10` — значит **9 битов**, хотя комментарий говорит «8»). Для каждого проверяет, помещается ли `high_bit | test_bit`, и если да — добавляет бит в результат. Работа с битами маской и сдвигом — см. [[bitwise-flags]].

**Шаг 3 — вывод** итераций в секунду: `loops_per_tick × TIMER_FREQ`. Это строка `Calibrating timer...  N loops/s.` при загрузке. Число зависит от машины и эмулятора, поэтому калибровка делается при каждом запуске.

### 4. Особенность шага 2: результат завышается

Проверяется `high_bit | test_bit`, а **не** `loops_per_tick | test_bit` — найденные ранее биты в проверку не входят. Каждая проверка независима: «старший бит + один этот бит». Если бит подошёл, все младшие тоже подойдут (их сумма со старшим ещё меньше) → выставятся **все** младшие биты после первого подошедшего. Это не настоящий двоичный поиск.

Пример, `h = 2^18`, реально ≈ 1.14·h (`h + x` = `high_bit | test_bit`, биты не пересекаются):

| Проверка | Значение | Помещается? | `loops_per_tick` |
|---|---|---|---|
| `h + h/2` | 1.5·h | нет | h |
| `h + h/4` | 1.25·h | нет | h |
| `h + h/8` | 1.125·h | да | + h/8 |
| `h + h/16` | 1.0625·h | да | + h/16 |
| … | … | да | + … |
| `h + h/512` | ≈1.002·h | да | + h/512 |

Итог ≈ `h + h/4 − h/512` ≈ **1.248·h** при реальных 1.14·h. Худший случай — реальное 1.5·h → результат ≈ 2·h, **+33 %**. Честный двоичный поиск получился бы с `loops_per_tick | test_bit`.

### 5. Место калибровки в загрузке

```
init.c:  intr_init → timer_init → thread_start (intr_enable) → timer_calibrate
                                                  │
                         ticks начал расти  ◄─────┘
                                                  │
    too_many_loops(N):  дождаться смены ticks ────┤  ticks — эталон времени
                        busy_wait(N)              │
                        ticks изменился?  ────────┘
                                │
          поиск максимального N, при котором ticks НЕ успевает измениться
                                ▼
                  loops_per_tick ≈ итераций busy_wait за 1/TIMER_FREQ с
```

`ticks` — **эталон**, по которому один раз «поверяется» цикл. После калибровки задержки работают **без** `ticks` и даже без прерываний.

### 6. `real_time_delay` — время в итерации

```c
/* devices/timer.c:240 */
static void
real_time_delay (int64_t num, int32_t denom)
{
  /* Scale the numerator and denominator down by 1000 to avoid
     the possibility of overflow. */
  ASSERT (denom % 1000 == 0);
  busy_wait (loops_per_tick * num / 1000 * TIMER_FREQ / (denom / 1000)); 
}
```

Формула:

```
итераций в секунду = loops_per_tick × TIMER_FREQ
ждать секунд       = num / denom
итераций           = loops_per_tick × TIMER_FREQ × num / denom
```

| Функция | `num` | `denom` | `denom / 1000` |
|---|---|---|---|
| `timer_mdelay(ms)` | ms | 1 000 | 1 |
| `timer_udelay(us)` | us | 1 000 000 | 1 000 |
| `timer_ndelay(ns)` | ns | 1 000 000 000 | 1 000 000 |

Кроме `*delay`-функций, `real_time_delay` вызывается из `real_time_sleep`, когда интервал меньше тика ([[pintos-timer-sleep]]).

**Порядок операций** — слева направо: `((loops_per_tick * num) / 1000) * TIMER_FREQ / (denom / 1000)`.

- Сначала делить (`num / denom`) — почти всегда 0: `10 / 1000000 = 0`, задержки нет (integer truncation).
- Сначала всё перемножить — `loops_per_tick * num * TIMER_FREQ` при больших `num` рискует переполнить `int64_t`.
- Поэтому числитель и знаменатель одинаково уменьшены в 1000 раз (дробь не меняется), умножения чередуются с делениями. Потеря от раннего `/ 1000` — доли итерации.
- `loops_per_tick` — `unsigned` (32 бита), `num` — `int64_t` → умножение сразу 64-битное.
- `ASSERT (denom % 1000 == 0)` — `denom / 1000` делится нацело.

## Пример расчёта

`loops_per_tick = 400 000` (40 000 000 loops/s, 40 итераций на микросекунду).

**`timer_udelay (10)`** — 10 мкс:

```
400 000 × 10          = 4 000 000
          / 1000      = 4 000
          × 100       = 400 000
          / 1000      = 400 итераций      (40 итераций/мкс × 10 мкс ✓)
```

**`timer_mdelay (5)`** — 5 мс:

```
400 000 × 5           = 2 000 000
          / 1000      = 2 000
          × 100       = 200 000
          / 1         = 200 000 итераций  (половина тика = 5 мс ✓)
```

## Точность

Задержки гарантируют **«не меньше, примерно столько»**:

1. **Завышение при калибровке** — до ~+33 % (см. п. 4). Для железа безопасно: ждать дольше можно, меньше нельзя.
2. **Прерывания во время задержки.** Время обработчика тика (и других потоков, если квант кончился) добавляется к задержке.
3. **Эмулятор.** В QEMU скорость цикла зависит от загрузки хоста и «гуляет» между калибровкой и использованием. Bochs детерминирован.
4. **`TIMER_FREQ`.** Чем чаще тик, тем меньше итераций в тике и грубее калибровка.
5. **Потеря тиков.** Задержка дольше тика с выключенными прерываниями → PIC помнит один IRQ0 → часы ОС отстают. Для ≥ 1 тика при включённых прерываниях — `timer_sleep` (так делает `real_time_sleep`).

## Подводные камни

- **Цикл без `barrier()`** — компилятор удаляет пустой цикл: задержка 0, калибровка уходит в бесконечность (`loops_per_tick` удваивается до переполнения → `ASSERT`).
- **Чтение `ticks` без барьера** в цикле ожидания — компилятор кэширует значение в регистре → вечный цикл.
- **Вызов калибровки до `intr_enable()`** — зависание в `too_many_loops`.
- **Свой задержечный цикл вместо `busy_wait`** — `loops_per_tick` к нему неприменим.
- **Путаница комментария и кода**: «Refine the next 8 bits», а уточняется 9.
- **`denom`, не кратный 1000**, — `ASSERT`; напрямую `real_time_delay` с произвольным знаменателем не вызывать.

### Безопасность

- **Integer overflow в `real_time_delay`.** `loops_per_tick * num` — `int64_t`, знаковое переполнение — **UB** в C (не просто «обернётся»). При `loops_per_tick ≈ 4·10^6` переполнение наступает при `num ≈ 2.3·10^12`: `timer_ndelay` на ~38 минут. Для ядерного кода — ограничивать аргумент до умножения, если он может прийти извне (аналогично арифметике указателей: UB возникает при вычислении, а не при использовании — см. [[pointer-arithmetic-ub]]).
- **Отрицательный аргумент.** `busy_wait` с отрицательным `loops` просто не выполнит ни одной итерации (`loops-- > 0`), UB нет — но задержка молча станет нулевой, и устройство получит команду раньше, чем готово.
- **Завышение `loops_per_tick` — безопасное направление**, занижение — нет: слишком короткая пауза после сброса контроллера приводит к чтению/записи в неготовое устройство и порче данных на диске.
- **Timing side-channel.** Измерение скорости цикла — ровно тот приём, которым атакующий оценивает время выполнения чужого кода. В реальных ОС стабильные высокоточные часы доступны пользователю только с оглядкой на Spectre-подобные атаки.
