# Splay-дерево

> Код: `knowledge-base/university/2-semester/ds/practice/splay/splay.c` (splay + insert + search написаны руками целиком). Самонастраивающийся
> BST **без хранимого баланса**: каждое обращение поднимает узел в корень. Гарантия —
> **амортизированная** O(log n).

## 1. Определение
BST без инварианта баланса. При любом обращении (search/insert/delete) узел поднимается в корень операцией **splay** (серия поворотов). Нет ни height, ни balance factor.

## 2. Узел — проще AVL
```c
typedef struct Node { int key; struct Node *left, *right; } Node;  // НЕТ height
```

## 3. splay — три случая (x — цель, p — родитель, g — дед)
- **zig** — p уже корень → один поворот, x встаёт корнем.
- **zig-zig** — x и p в ОДНУ сторону (прямая палка) → повернуть **деда первым, потом родителя** (два поворота одного направления).
- **zig-zag** — x и p в РАЗНЫЕ стороны (излом) → повернуть **родителя первым, потом деда** (как AVL-LR/RL).

## 4. Правило перецепки: «куда указывал повёрнутый узел — туда и результат»
`rotate(Y)` возвращает новую вершину поддерева Y. Присваивать результат надо тому указателю, что указывал на Y:
- повернул **весь** `root` → `root = rotate(root)` или `return rotate(root)`;
- повернул **дочерний** `root->left` → `root->left = rotate(root->left)`. Частый баг: `root->left = rotate_right(root)` — повернул целое, сунул в детский слот → root и ребёнок указывают друг на друга = ЦИКЛ.

Реализация веток (левая; правая — зеркало left↔right, rotate_right↔rotate_left):
```c
// zig:      return rotate_right(root);
// zig-zig:  root->left->left  = splay(root->left->left,  key);
//           root = rotate_right(root);  return rotate_right(root);   // дед, потом родитель (он теперь root)
// zig-zag:  root->left->right = splay(root->left->right, key);
//           root->left = rotate_left(root->left);  return rotate_right(root);  // родитель, потом дед
```
Опознание случая — сравнением `key` с `root->left->key` (== zig / < zig-zig / > zig-zag), не охотой за `==key`. NULL-проверки перед спуском в внука обязательны.

## 5. Как глубокий узел доходит до корня (рекурсия)
splay спускается **шагами по 2 уровня** (zig-zig/zig-zag смотрят на ребёнка и внука, рекурсят во внука). Прыжок веры: рекурсивный вызов на поддереве внука **уже** вернул цель на свою вершину; повороты текущего кадра поднимают её ещё на 2 уровня. Узел на глубине 4 → корень за 2 шага zig-zig (4→2→0).

## 6. Операции
- **search(key):** `root = splay(root, key)`; найдено ⇔ `root->key == key`. Перестраивает дерево **даже на чтении** (минус: не read-only, нужна блокировка для конкурентного чтения). Промах тоже двигает дерево (всплывает ближайший).
- **insert(key):** splay по key; дубликат (root->key==key) — no-op; иначе **разрез (split)**: новый узел — корень, старый корень и его «дальнее» поддерево уходят на одну сторону, ближнее поддерево корня — на другую. Работает чисто, т.к. после splay между key и корнем нет ключей.
  ```
  key < root->key:  new->left = root->left;  new->right = root;        root->left  = NULL;
  key > root->key:  new->right = root->right; new->left  = root;       root->right = NULL;
  ```
- **delete(key):** splay key в корень; удалить корень → join левого L и правого R: splay max у L (у него не будет правого ребёнка) → подвесить R справа. (в коде не писали)

## 7. Сложность — амортизированная
```
одна операция (worst):    O(n)        ← может выродиться на одном запросе
амортизированно/операцию: O(log n)
серия m операций:         O(m log n)
```
**Метод потенциала:** Φ = Σ rank(x), rank = log₂(size поддерева). Access lemma: амортизир. стоимость splay ≤ 3·(rank(root) − rank(x)) + 1 = O(log n). Интуиция: дорогой splay (длинный путь) обязан **сложить дерево** = уронить Φ → накопленный «банк» оплачивает дорогую операцию. Та же амортизация, что в [[dynamic-array]] (дорогой realloc оплачен дешёвыми push), только банк — это форма дерева.

## splay vs «протаскивание к корню» (rotate-to-root) — экзаменационный вопрос
Оба двигают узел в корень. Разница **целиком в zig-zig**:
- **zig** — у обоих одинаково (один поворот).
- **zig-zag** — у обоих **ИДЕНТИЧНО** (родитель→дед). Тут splay не отличается от протаскивания.
- **zig-zig** — splay: **дед→родитель** (складывает прямую ветку вдвое, path-halving → амортизир. O(log n)); протаскивание: родитель→дед (по уровню за раз, цепь не складывается → worst-case O(n) на операцию).

Демонстрация (левая цепочка 4→3→2→1, достаём 1):
```
splay(1):  высота 3 → 2   (дерево сложилось)        rotate-to-root(1):  высота осталась 3
   1                                                    1
    \                                                    \
     3                                                    4
    / \                                                  /
   2   4                                                3
                                                       /
                                                      2
```
Серия достаний глубокого: splay → O(m log n); протаскивание → O(m·n). Весь выигрыш splay над наивным протаскиванием — из обработки zig-zig (дед первым).

## Плюсы / минусы
**+** простой узел (нет height); подстраивается под паттерн доступа (90/10, кэш-эффект LRU); move-to-root бесплатно. **−** гарантия только амортизированная (одна операция O(n) — плохо для real-time); перестраивает на чтении (нет конкурентного read без блокировки, плохая cache-locality); на равномерно-случайном доступе проигрывает AVL/RB по константам.

## Где применяется
Кэши, аллокаторы памяти, сетевые таблицы с временно́й локальностью. **Экзаменационный канон:** «подсчёт десятичных чисел → splay», «вещественные → АВЛ/splay». Родня move-to-front (MTF) в сжатии.
