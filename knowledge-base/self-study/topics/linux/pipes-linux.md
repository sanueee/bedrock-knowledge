# pipes — межпроцессный канал данных / Pipes

## Что это

Pipe — однонаправленный буфер в памяти ядра (kernel buffer) с двумя файловыми дескрипторами: один конец пишет (write end), другой читает (read end). Не имеет имени в файловой системе и существует только пока хотя бы один процесс держит fd на него.

---

## Ключевые термины (English)

- **pipe** — межпроцессный канал данных, односторонний буфер в ядре
- **read end** — fd[0], дескриптор для чтения из pipe
- **write end** — fd[1], дескриптор для записи в pipe
- **EOF (end-of-file)** — на pipe приходит когда **все** write-ends закрыты
- **broken pipe** — попытка write() в pipe у которого нет read-ends → SIGPIPE и/или `EPIPE`
- **dup2** — клонирование дескриптора (используется для перенаправления stdin/stdout в pipe)
- **named pipe / FIFO** — pipe имеющий имя в FS (`mkfifo`), переживает перезапуск процесса

---

## Как работает

```
pipe(fd) создаёт:
  fd[0] — read end
  fd[1] — write end

Процесс A           ядро (буфер ~64KB)         Процесс B
write(fd[1]) ──→  [ h e l l o \n ]  ──→  read(fd[0])
```

1. `pipe(fd)` — вызывать **до** `fork()`, иначе процессы получат разные несвязанные трубы.
2. После `fork()` оба процесса наследуют **обе копии** обоих концов — у каждого процесса по своему `fd[0]` и `fd[1]`. Дескрипторы дублируются.
3. Каждый закрывает ненужный конец — иначе EOF никогда не придёт (см. ниже про счётчик).
4. Пишущий: `write(fd[1], buf, strlen(buf))` — `strlen`, не `sizeof`. Строка обычно короче буфера, лишний `sizeof` отправит мусор.
5. Читающий: цикл `while ((n = read(fd[0], buf, sizeof(buf) - 1)) > 0)`, потом `buf[n] = '\0'` для нуль-терминатора.
6. EOF на read: возвращается `0`, не `-1`. `-1` это ошибка.

---

## EOF и счётчик write-ends — главное правило

В ядре на каждый pipe ведутся **счётчики открытых дескрипторов** обоих типов:
- `nrwriters` — сколько процессов сейчас держат открытый write end
- `nrreaders` — сколько процессов держат открытый read end

`read()` на pipe ведёт себя так:

| `nrwriters` | данные в буфере | `read()` возвращает |
|---|---|---|
| > 0 | есть | количество прочитанных байт |
| > 0 | пусто | **блокируется** (ждёт write или закрытия) |
| **= 0** | есть | оставшиеся байты |
| **= 0** | пусто | **0 (EOF)** |

Это значит: **EOF приходит только когда ВСЕ копии write-end закрыты**, не одна из. После `fork()` write-end дублирован — у ребёнка своя копия, у родителя своя. Если ребёнок умер (или сделал `close(fd[1])`), но родитель **держит свою копию открытой** — `nrwriters > 0`, EOF не приходит, `read()` зависает навсегда.

**Практический урок**: после `fork()` каждая сторона **немедленно** закрывает ненужный конец:

```c
pipe(fd);
if (fork() == 0) {
    close(fd[0]);              // ребёнок не читает — закрыть read-end
    write(fd[1], "hello", 5);
    exit(0);                   // exit() закрывает оставшийся fd[1]
} else {
    close(fd[1]);              // ← ВАЖНО: родитель не пишет — закрыть write-end
    char buf[256]; ssize_t n;
    while ((n = read(fd[0], buf, sizeof(buf)-1)) > 0) { ... }
    // когда ребёнок умрёт и закроет свой fd[1], а родитель уже закрыл свой —
    // nrwriters = 0 → следующий read возвращает 0 (EOF)
    close(fd[0]);
    waitpid(...);
}
```

Без `close(fd[1])` у родителя — read-цикл повиснет навсегда после первого `read("hello")`. Прервёшь только Ctrl+C.

В реальных пайплайнах типа `cmd1 | cmd2 | cmd3` забытый `close` ломает всё: команды не получают EOF, пайплайн зависает.

## Самоблокировка одного процесса — порядок close → wait

Сценарий из разбора musl `pclose.c` (см. [[musl-popen]]).

Сетап:
- P — родитель.
- C — ребёнок созданный через `popen("./consumer", "w")`. P пишет в pipe, C читает stdin в цикле.

P должен сделать **два действия в правильном порядке**:

| Порядок | Что происходит |
|---------|---------------|
| `close(wfd)` → `waitpid(C)` | wfd освобождается → C получает EOF → C завершается → waitpid возвращается. OK. |
| `waitpid(C)` → `close(wfd)` | **self-deadlock** |

### Почему обратный порядок ломает всё — пошагово

1. P-waiter уходит в `waitpid` и засыпает в ядре.
2. P-writer всё ещё "должен" сделать `close`, но не может — поток заморожен в `waitpid`.
3. У C `read()` блокирует в ожидании EOF.
4. EOF не наступает: `nrwriters > 0`, потому что P-writer держит wfd.
5. C никогда не завершается.
6. P-waiter ждёт C вечно.

Это **не deadlock между двумя процессами**. Это **один тред, две роли (writer + waiter), неправильный порядок** — он застрял на первой роли и никогда не дойдёт до второй.

### Класс паттернов

Где встречается тот же принцип "порядок завершения двух ресурсов важен, потому что один блокирует освобождение другого":

- `shutdown(SHUT_WR)` перед `close(socket)` (FIN handshake)
- `fflush` перед `fclose`
- `pthread_cancel` + `pthread_join`
- В Rust — порядок Drop у RAII-объектов

---

## Кто кого блокирует — wait и read

Часто путают. На самом деле:

| Сисколл | Блокирует **кого** | До чего |
|---------|--------------------|--------|
| `wait4(pid, ...)` | вызывающий процесс (родитель) | пока ребёнок не завершится |
| `read(rfd, ...)` на pipe | вызывающий процесс | пока в буфер не придут данные **или** `nrwriters` не упадёт до 0 |

`wait4` **ничего не делает с ребёнком**. Ребёнок не знает что родитель его ждёт. Ребёнок продолжает выполняться независимо.

`read()` на pipe принимает решение "ждать дальше или вернуть EOF" глядя в ядро на `nrwriters` той самой `struct file`. EOF — это **сигнал от ядра**, не "когда писатель решит".

## fd inheritance — расширенные сценарии

Базовый случай "родитель забыл закрыть write-end → read у читателя висит" уже разобран выше. Есть более тонкие сценарии связанные с **многократным fork**.

Сетап:
- P создал pipe `[rfd, wfd]`, форкнул C1.
- C1 наследовал копию fd-таблицы P **на момент fork**.

Теперь P делает **второй fork** → появляется C2. C2 тоже наследует копию fd-таблицы P. Что попадёт к C2 — зависит от того, что P успел закрыть до второго fork.

### Сценарий A — чисто

P закрыл `wfd` **до** второго fork. C2 не унаследовал write-end. C1 завершается → его wfd закрывается ядром. `nrwriters → 0`. P получает EOF. ✓

### Сценарий B — P забыл закрыть wfd перед вторым fork

C2 получил копию wfd. Дальше:
1. C1 заканчивает работу → его wfd закрыт автоматически.
2. P закрывает свой wfd (запоздало).
3. **C2 всё ещё держит wfd.** `nrwriters = 1`.
4. P вызывает `read(rfd)` → виснет до тех пор, пока C2 либо явно не закроет fd, либо не завершится.

### Сценарий C — C2 это долгоживущий процесс

C2 = `vim`, или daemon, или шелл который ждёт ввода. Он понятия не имеет про твой pipe. Read у P не закончится **никогда**. Plus у C2 в fd-таблице висит мусор — fd leak.

### Сценарий D — C2 это sandbox / менее доверенный процесс

C2 унаследовал write-end pipe который P считал приватным каналом с C1. C2 может **писать** в pipe → P получит данные и подумает что они от C1. Нарушение confidentiality канала. В sandbox-контексте — потенциальный escape vector (вектор побега). Это материал для threat model на этапе 3.

### Сценарий E — забыли про exec

C2 после fork делает `execve("/usr/bin/vim", ...)`. После exec **адресное пространство C2 заменяется**, но **fd-таблица переживает exec** (она часть `task_struct`, а не адресного пространства). Если pipe-fd не имеет флага `FD_CLOEXEC`, vim его унаследует и будет тупо держать.

### Три защитные техники

| Техника | Что делает | Где применить |
|---------|-----------|--------------|
| Ранний `close` ненужного конца | Не дать fd попасть к следующему fork-у | Сразу после `pipe()` или сразу после `fork()` |
| `O_CLOEXEC` на pipe-fd | Ядро само закрывает fd при `execve` | `pipe2(fd, O_CLOEXEC)` вместо `pipe(fd)` |
| `posix_spawn_file_actions_addclose` | Атомарное закрытие чужих fd у нового ребёнка | При использовании `posix_spawn` (как в musl popen) |

## SIGPIPE — обратное направление

Симметричный случай: `write()` в pipe у которого `nrreaders = 0` (все прочитавшие закрыли свой конец).

```c
write(fd[1], buf, n);   // нет read-ends → ядро шлёт SIGPIPE процессу
```

Default действие SIGPIPE — terminate. Это и значит "broken pipe". Если игнорировать (`signal(SIGPIPE, SIG_IGN)` или `sigaction`), `write()` вернёт `-1` с `errno = EPIPE`.

В сетевых программах часто игнорируют SIGPIPE и проверяют `errno == EPIPE` — потому что иначе попытка отправить данные в закрытый сокет убивает процесс целиком.

## char * vs char[] — разница в read()

```c
char *buf;                        // указатель, 8 байт на стеке, мусор внутри
read(fd[0], buf, sizeof(buf)-1);  // НЕ работает: буфер не выделен → segfault
                                  // sizeof(buf) = 8 (размер указателя), не размер данных
```

```c
char buf[256];                    // массив, 256 байт на стеке
read(fd[0], buf, sizeof(buf)-1);  // OK: 256 байт памяти, sizeof = 256
```

Принципиальные различия:

| | `char *buf;` | `char buf[256];` |
|---|---|---|
| Что это | переменная-указатель | массив |
| Размер на стеке | 8 (адрес) | 256 |
| `sizeof(buf)` | 8 | 256 |
| Выделена ли память для данных | **нет** (значение указателя — мусор) | да |
| Можно ли писать в `buf[i]` | UB (мусорный адрес) | OK |

`sizeof()` корректно работает на массивах **только в той области видимости где они объявлены**. Передал массив в функцию — параметр распадается в указатель → `sizeof` = размер указателя:

```c
void f(char arr[256]) {
    sizeof(arr);   // 8, не 256! arr — указатель внутри функции
}
```

Это типичная ловушка C, на которой регулярно ловятся даже опытные. Если функция должна знать размер — передавать его явным аргументом: `void f(char *arr, size_t len)`.

## Подводные камни

| Ошибка | Последствие |
|--------|-------------|
| `pipe()` после `fork()` | Процессы не связаны, данные не передаются |
| Не закрыть write-end у читателя | `read()` блокируется навсегда, EOF не приходит |
| `char *buf;` вместо `char buf[256];` | Запись по мусорному адресу, segfault |
| `sizeof(buf)` на `char *` | Размер указателя (8), не размер данных |
| `write(fd[1], buf, sizeof(buf))` | Отправляется мусор после нуля строки — нужен `strlen` |
| `read()` без `buf[n] = '\0'` | `printf("%s", buf)` читает мусор за пределами строки |
| `buf[n] = '\0'` когда `n == sizeof(buf)` | Запись за границу массива (нужно `sizeof - 1` в `read`) |
| `pipe()` без проверки возврата | Может упасть при достижении лимита fds, не заметишь |
| `write()` без обработки SIGPIPE | Процесс убивается дефолтным действием при закрытом read-end |
