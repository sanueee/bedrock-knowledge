# Copy-on-write при fork / Copy-on-write (COW)

## Что это

Оптимизация ядра: при `fork()` память **не копируется** побайтно. Вместо этого page tables ребёнка указывают на **те же** физические страницы что у родителя, все страницы помечены **read-only**. Физическое копирование происходит лениво — только когда кто-то пишет в страницу.

Без COW `fork` процесса с 4 GB RSS был бы 4 GB memcpy. С COW — микросекунды независимо от размера памяти. Это то что делает связку `fork`+`execve` жизнеспособной.

## Ключевые термины (English)

- **virtual memory** — виртуальная память, абстракция над физической
- **virtual address** — адрес который видит процесс
- **physical address** — адрес реальной RAM
- **page** — страница, минимальная единица мапирования (обычно 4 KB)
- **page table** — таблица перевода виртуальных адресов в физические
- **PTE (page table entry)** — одна запись page table, описывает одну страницу
- **MMU (memory management unit)** — блок CPU делающий перевод адресов по page tables
- **page fault** — исключение CPU когда нет валидной PTE или нарушены права
- **TLB (translation lookaside buffer)** — кэш page tables внутри CPU
- **RSS (resident set size)** — сколько страниц процесса реально в RAM
- **COW (copy-on-write)** — техника отложенного копирования по записи

## Виртуальная память — фундамент

Каждый процесс видит свои виртуальные адреса (от 0 до 2^48 на x86-64). Ядро через **page tables** мапит виртуальные страницы (4 KB) в физические. Перевод делает **MMU** в CPU, кэшируя в **TLB**.

Каждая PTE содержит:
- Физический адрес страницы.
- Биты прав: **read / write / execute / user-accessible**.
- Биты состояния: present, dirty, accessed.
- На x86-64 — несколько software-битов, доступных ядру для своих меток (например — "это COW-страница").

Когда CPU выполняет инструкцию записи в виртуальный адрес:
1. MMU ищет PTE.
2. Если **write-бит = 0** — генерирует **page fault** (исключение).
3. CPU прыгает в обработчик page fault в ядре.
4. Ядро решает: это легитимная COW-страница или реальная ошибка прав (`SIGSEGV`).

## Механика COW при fork — пошагово

**До fork:**
```
P process:
  virt 0x1000 → PTE { phys 0xA000, rw=1 }
  virt 0x2000 → PTE { phys 0xB000, rw=1 }
```

**После fork (без COW было бы 2 страницы памяти скопированы):**

С COW ядро делает три вещи:
1. Аллоцирует ребёнку **новые** page tables.
2. **Копирует содержимое** page tables родителя в дочерние (только PTE, не сами страницы).
3. Помечает все writable-страницы (в обоих процессах!) как **read-only + COW**.

```
P process (после fork):
  virt 0x1000 → PTE { phys 0xA000, rw=0, cow=1 }   ← было rw=1, стало rw=0
  virt 0x2000 → PTE { phys 0xB000, rw=0, cow=1 }

C process (только что создан):
  virt 0x1000 → PTE { phys 0xA000, rw=0, cow=1 }   ← те же физ. адреса!
  virt 0x2000 → PTE { phys 0xB000, rw=0, cow=1 }
```

Оба процесса видят одну и ту же физическую RAM. Пока оба только **читают** — это OK.

**Что происходит когда P пишет в `0x1000`:**

1. CPU выполняет `mov [0x1000], rax`.
2. MMU видит PTE с `rw=0` → **page fault**.
3. Ядро в обработчике видит флаг `cow=1` → это не SIGSEGV, это COW-trap.
4. Ядро:
   - Аллоцирует **новую** физическую страницу `0xC000`.
   - Копирует содержимое `0xA000` → `0xC000` (вот теперь memcpy на 4 KB).
   - Меняет PTE родителя: `virt 0x1000 → PTE { phys 0xC000, rw=1, cow=0 }`.
   - У ребёнка PTE остаётся как есть (всё ещё `0xA000`, всё ещё `rw=0+cow=1`).
   - Декрементит refcount страницы `0xA000` (если бы был ещё один процесс с COW на `0xA000`, страница не освободилась бы).
5. Если теперь у `0xA000` остался ровно один владелец (C) и нет других COW-копий — ядро **снимает с C COW-флаг**: `rw=1, cow=0`. C может писать без page fault.
6. CPU возвращается в user space, инструкция записи retry-ится — на этот раз `0xC000` имеет `rw=1`, запись проходит.

Итог: реально скопирована **одна** страница (`0xA000` → `0xC000`), не вся память процесса.

## Почему fork+execve дёшев

`execve` сразу сбрасывает всю старую память — мапит новый бинарь, новый стек, новую кучу. Те страницы которые ребёнок успел "тронуть" до execve и тем самым форсировал копирование — выкидываются.

Если между `fork` и `execve` нет другого кода — реально копируется **ноль** страниц (плюс одна-две stack-страницы для самого вызова). Это идиоматический паттерн в Unix.

## Чего стоит остерегаться

- **Stack copy неочевиден**: ребёнок сразу пишет в stack (хотя бы возвращаемый адрес из fork). Это **первая** страница которая всегда COW'ится — незаметно.
- **glibc atfork-handlers** могут писать в кучу → принудительно COW-ят кучные страницы. Это одна из причин почему `posix_spawn` / `_Fork` предпочтительнее когда сразу `execve` (см. [[async-signal-safe]]).
- **`vfork()`** — старая оптимизация: ребёнок и родитель **разделяют** адресное пространство, родитель приостановлен до `execve`/`_exit`. Очень опасно (любая запись ребёнка ломает родителя), но даёт нулевое копирование даже page tables. Сейчас почти не нужен — COW делает обычный `fork` достаточно дешёвым.
- **fork big-memory процесса всё равно недёшев**: само копирование page tables и пометка всех PTE как RO — O(N) от размера памяти. Для процесса с 100 GB RSS fork может занять секунды (страдает Redis при `BGSAVE`).
- **TLB shootdown**: пометка страниц как RO требует инвалидации TLB на всех CPU. Это межпроцессорные прерывания — тоже не бесплатно.
- **COW работает не только для fork**: `mmap(MAP_PRIVATE)` файла тоже использует COW. Изменения в private mapping видны только этому процессу, на диск не пишутся.

## Где это видно снаружи

- `/proc/PID/smaps` — поле `Private_Dirty` показывает страницы которые процесс уже модифицировал (его собственные после COW). `Shared_Clean` — страницы которые он делит с другими (ещё не COW'нуты).
- После `fork` `RSS` родителя и ребёнка в `ps` будет показывать одинаковое число — но это **виртуальный** счёт. Реальная физическая память не удвоилась.

## Связь с reading-01

В `_Fork.c` musl делает ровно то же что обычный `fork` — но без atfork-handlers. COW работает идентично, просто пользовательские callback'и не запускаются. Async-signal-safe это требование к **коду**, COW это механика **памяти** — независимые вещи, но обе важны для понимания почему `_Fork` существует отдельно. См. [[async-signal-safe]].
