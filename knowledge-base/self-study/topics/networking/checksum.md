# Internet checksum / one's complement sum (RFC 1071)

## Что это
Контрольная сумма для обнаружения ошибок (error detection) в IP/TCP/UDP/ICMP заголовках: 16-битная one's complement sum по данным. Не исправляет ошибки — только ловит битые пакеты, которые затем отбрасываются. Дизайн заточен под дешёвый расчёт (только сложение) и инкрементальный пересчёт на каждом хопе.

## Ключевые термины (English)
- **error detection** — обнаружение (не коррекция) искажений при передаче.
- **one's complement (обратный код)** — представление, где перенос не теряется, а заворачивается назад (end-around carry); есть два нуля: `0x0000` и `0xFFFF`.
- **end-around carry** — перенос за 16-й бит прибавляется обратно к младшим 16 битам.
- **pseudo-header** — 12 байт из IP-контекста (src/dst IP, proto, TCP length), участвуют в TCP-checksum, но не отправляются.
- **misdelivery** — доставка сегмента не тому хосту; pseudo-header защищает от неё.
- **strict aliasing** — правило C: доступ к памяти через несовместимые типы указателей = UB.
- **alignment** — требование выровненного адреса для типа (`uint16_t` кратен 2 на ARM/MIPS).

## Как работает

### Алгоритм (RFC 1071), один и тот же для IP/TCP/ICMP
1. Разбить данные на 16-битные слова, суммировать в широкий аккумулятор `uint32_t` (чтобы переносы копились в старших битах, а не терялись).
2. **End-around carry в цикле:** `sum = (sum & 0xFFFF) + (sum >> 16)`, повторять пока `sum >> 16 != 0`. Именно `while`, а не `if`: прибавление переноса может породить новый (напр. `sum = 0x1FFFF → 0xFFFF + 1 = 0x10000` → второй перенос).
3. Инверсия: `checksum = ~sum` по младшим 16 битам.

Инвариант расчёта: поле `check` в заголовке во время суммирования = **0**. Результат `~sum` кладётся в это поле.

### Почему верификация даёт ноль (главное место)
Пусть `D` — сумма всех содержательных полей заголовка (адреса, TTL, порты — всё, кроме поля checksum).

- **Отправитель** считает по заголовку, где поле checksum = 0. Ноль в сумму ничего не вносит → `S = D`. Кладёт в поле `~S = ~D`.
- **Получатель** суммирует те же поля (`D`) **плюс** поле checksum, которое теперь = `~D`. Итого `D + ~D`.
- `D + ~D` = все единицы = `0xFFFF` (в каждом бите ровно один операнд даёт 1, ни одного переноса). Инверсия → `0x0000`.

Ключ, где легко запутаться: обнуление поля у отправителя делает `S` равным «сумме без поля». Поэтому поле checksum у получателя не «лишнее слагаемое, которого не было» — оно встаёт **ровно на место того нуля**, но уже со значением `~D`, и замыкает сумму до всех единиц. Если по дороге бит побился, `D' ≠ D`, а поле всё ещё старое `~D` → `D' + ~D ≠ 0xFFFF` → не ноль → пакет битый.

### Byte order independence (RFC 1071 §2)
Внутри цикла суммирования `ntohs` **не нужен**: one's complement sum обладает свойством — посчитаешь по байт-свопнутым словам, получишь байт-свопнутый результат, но это тот же checksum. Пока и считаешь, и записываешь консистентно (и отправитель, и получатель гоняют один алгоритм), конкретный порядок байт внутри слова не важен. Тот же вывод, что с gateway на [[interface-enumeration]]: host-order слово = network-байты на LE → класть как есть.

**Но:** при **построении** полей заголовка (`tot_len`, порты, `tcp_len` в pseudo-header) byte order важен — их надо класть в network order через `htons`/`htonl`, потому что эти байты реально едут по проводу. Byte order independence — про сам цикл суммы, не про формирование полей.

### Pseudo-header (только TCP/UDP)
TCP checksum суммирует не только TCP-заголовок, а спереди приклеивает 12 байт из IP-уровня:
```
+--------+--------+--------+--------+
|          Source IP (4)            |
+--------+--------+--------+--------+
|        Destination IP (4)         |
+--------+--------+--------+--------+
|  zero  | proto  |   TCP length    |   proto=6 (IPPROTO_TCP), TCP length = длина TCP-заголовка+данных
+--------+--------+--------+--------+
```
Смысл: привязать L4-checksum к L3-адресам → защита от misdelivery. Если сегмент доставлен не тому хосту, получатель реконструирует pseudo-header из **своего** IP-заголовка (там его `Destination IP`), отправитель считал с другим адресом → расхождение в 1 байте → сумма не сходится → отброс. Pseudo-header **не отправляется** — обе стороны строят его локально из своих IP-заголовков. `tcp_len` берётся из IP-контекста (в TCP-заголовке поля длины нет).

## Пример
Разбиение буфера длины 3 `[0xAB, 0xCD, 0xEF]` → слова `0xABCD` и `0xEF00` (хвостовой байт в старшую половину, padding нулём справа). Сборка слова из байт вручную:
```c
uint16_t word = (buf[i] << 8) | buf[i + 1];   // читаем через uint8_t*, слово строим сами
```
Нечётная длина — хвост отдельной веткой после цикла:
```c
while (len > 1) { sum += (buf[i] << 8) | buf[i+1]; i += 2; len -= 2; }
if (len == 1)  sum += buf[i] << 8;              // padding нулём, buf[i+1] НЕ читать
```

## Подводные камни
- **OOB-read на нечётной длине:** `for (i=0; i<len; i+=2) sum += (buf[i]<<8)|buf[i+1];` читает `buf[len]` за границей на последней итерации. Хвостовой байт — отдельной веткой (тот же класс промахов, что `strlen(NULL)` на B-13, `%s` по recv на B-15; см. [[feedback-tedious-security-code]]).
- **Каст `(uint16_t*)buf` — два независимых UB:** (1) **alignment** — невыровненный адрес → SIGBUS на ARM/MIPS (на x86 «прокатит»); (2) **strict aliasing** — компилятор считает, что `uint16_t*` и `uint8_t*` не пересекаются, и на `-O2` переставляет/выкидывает обращения. Правильно: `(buf[i]<<8)|buf[i+1]` или `memcpy(&word, buf+i, 2)`. `uint8_t*`/`char*` легально алиасят всё, обратно — нет.
- **Забыть pseudo-header** — посчитать TCP checksum только по TCP-заголовку. Не сойдётся у получателя.
- **`if` вместо `while` при свёртке carry** — второй перенос (`0x1FFFF`) не обработается.
- **Не обнулить поле `check` перед расчётом** — сумма посчитается по мусору в поле, инвариант верификации сломается.
- **Byte order на записи результата в поле `check` (пойман на B-18).** Byte-order independence из RFC 1071 работает, только если чтение и запись консистентны. Если функция читает слова **принудительно big-endian** (`(*data<<8)|*(data+1)`), она и возвращает «BE-значение». Записать его в поле обычным присваиванием `uint16_t` (`hdr->check = compute(...)`) на little-endian машине = положить байты в host order → checksum на проводе перевёрнута. Фикс: `hdr->check = htons(compute(...))`. Ключ: свёртка суммы byte-order-независима (one's complement коммутирует с byteswap — расчёт самосогласован и даёт верное BE-значение), но **граница функции**, где BE-значение уходит в host-order память, — та точка, где свап вылезает. Проверка: прогнать эталонный заголовок (пример из Wikipedia, правильный checksum на проводе = `b8 61`), сравнить байты в памяти с эталоном — не только self-verify через ту же функцию.
- **Sentinel-коллизия при возврате адреса (пойман на B-18, не про checksum, про error handling рядом).** Функция `int valid_addr(const char *ip, uint32_t *out)` не может вернуть адрес через `return` и кодировать ошибку тем же `uint32_t`: IPv4-адрес занимает **весь** диапазон `2^32` (`0xFFFFFFFF` = broadcast, валиден) → под код ошибки нет свободного значения. Разделять: статус через `return` (`0`/`-1`), данные через out-параметр — как это делает сам `inet_pton` (`1`/`0`/`-1` + адрес в переданный указатель). `inet_pton` возвращает `0` на невалидной строке, `-1` только на неизвестном address family → проверять `<= 0` / `!= 1`, не `== -1`.
