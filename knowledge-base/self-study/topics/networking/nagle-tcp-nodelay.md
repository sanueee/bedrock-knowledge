# Алгоритм Нагла / Nagle's algorithm + TCP_NODELAY

## Что это

Алгоритм оптимизации TCP (RFC 896, 1984), который **накапливает мелкие исходящие данные в send buffer** до получения ACK на предыдущий неподтверждённый сегмент или заполнения MSS. `TCP_NODELAY=1` его выключает.

## Ключевые термины (English)

- **Nagle's algorithm** — отправлять только если есть unacked данные или buffer >= MSS.
- **MSS (Maximum Segment Size)** — максимальный размер TCP-сегмента, обычно ~1460 байт на Ethernet.
- **ACK piggybacking** — отправка ACK вместе с ответными данными в одном сегменте.
- **delayed ACK** — ядро на стороне получателя задерживает ACK на ~40 мс надеясь объединить с ответом. Парная оптимизация.
- **TCP_NODELAY** — socket option (`IPPROTO_TCP`), выключает Нагла на конкретном сокете.
- **TCP_CORK** (Linux only) — обратная крайность: не отправлять вообще ничего, пока приложение не разрешит. Для batch.

## Зачем придумали

Сценарий 1984 года: telnet-сессия. Пользователь жмёт "a" — приложение шлёт 1 байт. TCP-заголовок 20 байт + IP 20 байт = **40 байт overhead на 1 байт полезных**. Эффективность <3%. Жмёт "abcd" быстро — 4 пакета по 41 байт.

Нагл говорит: "не отправляй маленький сегмент, пока есть unacked. Накапливай." Получишь ACK — отправь всё что накопилось одним сегментом. Bulk-передача мелких записей собирается в большие сегменты.

## Как работает (правило)

При отправке смотрим:
1. Есть **unacked** segment в полёте? И размер новых данных < MSS?
2. Если **да** — копим в send buffer, не отправляем.
3. Если **нет** (нет в полёте ИЛИ накопили ≥ MSS) — отправляем сразу.

## Когда становится "смертью латентности"

Протокол **запрос-ответ** (HTTP API, Redis, RPC):

```
client: GET key\r\n      (10 байт)
client: ждёт ответа...
```

Без Нагла — 0 мс на отправку. С Нагла — ядро думает "вдруг ещё допишут" и ждёт:
- пока не накопится MSS (никогда — больше не будет данных),
- пока не придёт ACK на предыдущее (а его не придёт — только что начали),
- пока не сработает таймер ~40 мс.

В худшем случае **+40 мс на каждую команду**. Для Redis (отвечает за микросекунды) — катастрофа: in-memory БД, но сеть добавит +200×.

Плюс **delayed ACK** на стороне получателя — он тоже ждёт 40 мс. Если оба включены, ждут друг друга. Эту патологию знают как **"Nagle + delayed ACK = деадлок задержки до 500 мс"**.

## Правило выбора

- **Bulk-передача** (файлы, потоковая запись логов, `scp`, FTP DATA) — Нагл **полезен**, оставь как есть.
- **Запрос-ответ, малые сообщения** (Redis, HTTP API, JSON-RPC) — `TCP_NODELAY=1`.
- **Batch у тебя в коде** (формируешь полный пакет, потом одним `write` шлёшь) — Нагл не мешает, но лучше явно `TCP_CORK` на время сборки + uncork.

## Пример (из Redis anet.c)

```c
static int anetSetTcpNoDelay(char *err, int fd, int val) {
    if (setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &val, sizeof(val)) == -1) {
        anetSetError(err, "setsockopt TCP_NODELAY: %s", strerror(errno));
        return ANET_ERR;
    }
    return ANET_OK;
}
```

Redis включает `TCP_NODELAY` на принятых сокетах — он request-response in-memory БД, латентность критична.

## Подводные камни

- **Нельзя выключить delayed ACK портабельно.** `TCP_QUICKACK` есть только на Linux и сбрасывается после первого пакета — нужно ставить заново. Поэтому борются обычно с Нагла, а не с delayed ACK.
- **Не лечит "слишком много мелких write()".** Если ты сам делаешь 100 раз `write(fd, byte, 1)` — это 100 системных вызовов, оверхед уже на твоей стороне. `TCP_NODELAY` не поможет. Сначала собирай в свой буфер.
- **Включается на каждом сокете отдельно.** В Redis — на каждом accepted fd. Это идиома.
