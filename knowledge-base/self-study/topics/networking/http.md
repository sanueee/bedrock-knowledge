# HTTP/1.1 basics — устройство протокола и работа с ним из C / HTTP basics

## Что это

HTTP/1.1 — текстовый протокол «запрос-ответ» (request-response) поверх обычного TCP-потока. **Нет ни одного http-сисколла**: используешь те же `send`/`recv`, что в любом TCP-клиенте. Весь «HTTP» живёт не в ядре, а в твоём коде разбора строк — это ключевая мысль. `send`/`recv` — тупые трубы, смысл в байты вкладываешь ты.

## Ключевые термины (English)

- **request line** — первая строка запроса: `METHOD path HTTP/version` (`GET /index.html HTTP/1.1`).
- **status line** — первая строка ответа: `HTTP/version code reason` (`HTTP/1.1 200 OK`).
- **header field** — строка `Name: value`, оканчивается `\r\n`. Имена **case-insensitive**.
- **CRLF** — `\r\n` (carriage return 0x0D + line feed 0x0A); разделитель строк в HTTP. Требуется именно `\r\n`, не голый `\n`.
- **header/body separator** — `\r\n\r\n` (две подряд CRLF); граница «заголовки кончились, дальше тело».
- **entity body** — тело сообщения после separator.
- **framing** — определение границ сообщения в байтовом потоке: где кончается тело.
- **Content-Length** — заголовок с точной длиной тела в байтах (десятичное число).
- **Transfer-Encoding: chunked** — тело кусками, каждый со своим hex-размером; терминатор — чанк размера 0.
- **keep-alive** — поведение HTTP/1.1 по умолчанию: соединение не закрывается после ответа (переиспользуется).
- **name-based virtual hosting** — много сайтов на одном IP; какой нужен — говорит заголовок `Host:`.

## Как работает

### Один обмен

```
C (client)                          S (server)
   |  --- request  (текст) --->  send()  |
   |  <--- response (текст) ---  recv()  |
```

Один запрос → один ответ, оба — простой текст, разбитый на строки через CRLF.

### Анатомия запроса (что отправляешь)

```
GET /index.html HTTP/1.1\r\n     ← request line: METHOD path HTTP/version
Host: example.com\r\n            ┐
User-Agent: httpget/0.1\r\n      │ headers
Connection: close\r\n            ┘
\r\n                             ← пустая строка = конец заголовков (ОБЯЗАТЕЛЬНА)
[тело — у GET его нет]
```

- **`path` — только путь** (`/index.html`), не полный URL. Хост идёт отдельно в `Host:`.
- **`Host:` обязателен в HTTP/1.1.** TCP-connect знает только IP; на одном IP много сайтов (name-based virtual hosting) — `Host:` говорит серверу, какой из них нужен. Без него — `400 Bad Request`.
- **Пустая строка обязательна.** Без финального `\r\n` (то есть без `\r\n\r\n` в конце) сервер думает, что заголовки ещё не закончились, и **виснет в ожидании** — `recv` у клиента заблокируется.
- **`GET`** — дай ресурс с телом; **`HEAD`** — дай только заголовки, без тела (удобно для banner grab).

### Анатомия ответа (что приходит)

```
HTTP/1.1 200 OK\r\n              ← status line
Server: nginx\r\n               ┐
Content-Length: 1256\r\n        │ headers
Content-Type: text/html\r\n     ┘
\r\n                            ← separator
<!doctype html>...              ← body, 1256 байт
```

Status line: `code` (int, `200`) + `reason` (`OK`). Дальше заголовки, потом `\r\n\r\n`, потом тело.

### Проблема framing — сердце протокола (и задания)

TCP — это **байтовый поток (byte stream) без границ сообщений** (в отличие от UDP-датаграмм, где `recvfrom` вернул ровно одно сообщение — см. [[udp-sockets]]). `recv` возвращает «сколько байт сейчас лежало в буфере ядра», а **не** «одно HTTP-сообщение». Ответ на 1256 байт может прийти за 1 вызов `recv` или за три по 500/500/256 — клиент этим не управляет.

Значит нужен способ понять, что тело кончилось. HTTP даёт три:

| Способ | Как узнаёшь конец тела | Когда |
|---|---|---|
| **Content-Length: N** | тело = ровно N байт после `\r\n\r\n` | сервер знает размер заранее (файл) |
| **Transfer-Encoding: chunked** | куски со своим размером; конец — чанк 0 | сервер генерирует на лету, размер неизвестен |
| **Connection: close** | тело = всё до закрытия сокета; `recv`→0 = конец | HTTP/1.0 или явный `Connection: close` |

**Зачем `Connection: close` в запросе:** просишь сервер закрыть соединение после ответа. Тогда работает простое правило `recv вернул 0 → ответ целиком в буфере`, и разбор длины можно делать потом. Без него (keep-alive по умолчанию) сервер соединение не рвёт → цикл `while (recv > 0)` **зависает навсегда** (буфер ядра пуст, ждёт данных, которых не будет). Тогда пришлось бы считать байты: читать до `len(заголовки до \r\n\r\n) + Content-Length`.

### Chunked-декодирование

Нужен, когда сервер начинает слать тело, не досчитав общий размер (стриминг, динамика). Формат на проводе:

```
1a\r\n                          ← размер чанка в HEX (0x1a = 26), потом \r\n
<26 байт данных>\r\n            ← данные, потом закрывающий \r\n
4\r\n
data\r\n
0\r\n                           ← чанк размера 0 = конец тела
\r\n
```

Алгоритм (курсор `p` на начале тела, после `\r\n\r\n`):

```
1. size = strtol(p, &end, 16)   // размер в HEX
2. if (size == 0) конец, выход
3. p = end + 2                  // перешагнуть \r\n после размера
4. вывести size байт с p через %.*s
5. p += size + 2                // данные + закрывающий \r\n
6. goto 1
```

## Пример

Сборка запроса (`snprintf`) и цикл чтения — как в `self-practice/networking/http-basics/httpget.c` (B-11):

```c
char req[1024];
int n = snprintf(req, sizeof req,
    "GET %s HTTP/1.1\r\n"
    "Host: %s\r\n"
    "Connection: close\r\n"
    "\r\n",                     // ← пустая строка
    path, host);
// проверить n > 0 && n < (int)sizeof req — иначе запрос обрезался

// отправка: send в цикле, пока не отправлено n байт (send может отдать меньше)

// приём: Connection: close → читаем до нуля
char buf[65536];
size_t total = 0;
ssize_t k;
while ((k = recv(fd, buf + total, sizeof buf - total, 0)) > 0)
    total += k;                 // копим весь ответ

// разбор: граница заголовки/тело
char *sep = memmem(buf, total, "\r\n\r\n", 4);
// заголовки = [buf .. sep), тело = sep + 4
```

Связь протокол ↔ функция:

| Часть протокола | Функция | Тонкость |
|---|---|---|
| собрать request | `snprintf` | возвращает длину для `send`; проверять на обрезание |
| отправить | `send` в цикле | может отдать меньше запрошенного |
| принять поток | `recv` в цикле | возвращает **ровно** прочитанное, не «ожидаемое» |
| граница заголовки/тело | `memmem`/`strstr` по `"\r\n\r\n"` | separator из двух CRLF |
| имя заголовка | `strncasecmp` | имена case-insensitive по RFC |
| код статуса / hex-размер | `strtol` (основание 10 / 16) | `end` даёт курсор после числа |
| печать тела | `printf("%.*s", len, p)` | сетевые данные не NUL-terminated |

## Подводные камни

- **Забыл финальную пустую строку** (`\r\n\r\n` в запросе) → сервер ждёт продолжения заголовков, `recv` виснет. Самая частая ошибка.
- **Голый `\n` вместо `\r\n`** → сервер может не распарсить. Всегда `\r\n`.
- **keep-alive vs `while (recv > 0)`** → без `Connection: close` цикл до нуля зависает навсегда. Либо шли `Connection: close`, либо останавливайся по `Content-Length`.
- **Security §4 — `%s` по сетевым данным = OOB-read.** Тело/заголовки не NUL-terminated; печатать только `%.*s` с явной длиной.
- **Security §4 — доверие `Content-Length`/hex-размеру.** Заявленный размер может увести курсор `p + size` за пределы реально прочитанного буфера → out-of-bounds read. Сравнивай с фактически полученными байтами (`total`).
- **Security §4 — `strtol` на мусоре** вернёт 0 → примешь за «конец chunked-тела». Проверяй `end != p` (реально ли сдвинулись).
- **Буфер приёма фиксированного размера** переполнится на большом ответе — либо ограничивай `sizeof buf - total` в `recv` (как в примере), либо расти динамически.
- **`AF_INET` захардкожен в `socket()`** — если резолвил с `AF_UNSPEC`, бери семейство из `res->ai_family`, иначе рассинхрон резолва и сокета.
