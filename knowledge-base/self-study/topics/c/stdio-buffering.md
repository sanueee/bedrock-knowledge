# Буферизация потоков stdio / stdio buffering

## Что это

`stdio` (`printf`/`fprintf`/`fputs`) не пишет в файловый дескриптор сразу — копит данные в **буфере (buffer)** в user space и сбрасывает (**flush**) их пачкой. Это ускоряет вывод (меньше syscall'ов `write`), но **меняет видимый порядок строк**, если писать в `stdout` и `stderr` вперемешку.

## Ключевые термины (English)

- **buffering** — накопление данных перед записью, чтобы делать меньше syscall'ов
- **flush** — принудительный сброс буфера в нижележащий fd (`fflush`)
- **line-buffered** — flush на каждом `\n` (режим stdout при выводе в терминал)
- **fully buffered** (block-buffered) — flush только когда буфер полон или при `exit` (режим stdout при выводе в pipe/файл)
- **unbuffered** — flush сразу, без накопления (режим stderr всегда)
- **interleaving** — переплетение строк из разных потоков из-за разных режимов буферизации

## Как работает

Три режима, и для `stdout` режим **зависит от того, куда он направлен**:

| Поток | Терминал (tty) | Pipe / файл / capture |
|-------|----------------|------------------------|
| `stdout` | line-buffered (flush на `\n`) | **fully buffered** (flush на `exit` или заполнении) |
| `stderr` | unbuffered | unbuffered (всегда) |

`stderr` **никогда** не буферизуется — диагностика должна появляться немедленно, даже если программа сейчас упадёт. `stdout` оптимизируется под пропускную способность: в терминале человек смотрит построчно (line-buffered), а в pipe важна скорость (fully buffered).

## Пример (из task-b05 host_probe)

Запуск с захватом вывода (`example.com 80`, баннер не приходит → таймаут):

```
server didn't send banner (timeout)     ← stderr (unbuffered, печатается сразу)
connected: 172.66.147.243:80            ← stdout (fully buffered, лежит в буфере до exit)
```

В коде `connected:` (stdout) идёт **раньше** `timeout` (stderr), но в выводе — позже. Причина: вывод перенаправлен (pipe), поэтому `stdout` стал **fully buffered** — строка `connected:\n` копилась в буфере и сбросилась только на `exit`, а `stderr` напечатался мгновенно.

В обычном терминале (tty) того же бага не было бы: `stdout` там line-buffered, `connected:\n` сбросился бы сразу на `\n`, порядок верный. То есть **переплетение — артефакт перенаправления, не код**.

Контрпример из той же программы: `github.com 22` дал `connected:` и `banner:` в правильном порядке — обе строки в одном `stdout`, между собой stdio их не переставляет.

## Подводные камни

- **Порядок stdout↔stderr не гарантирован** при перенаправлении. Если он важен (лог, где диагностика должна стоять на своём месте) — `fflush(stdout)` перед записью в `stderr`, либо писать оба сообщения в один поток.
- **Потеря вывода при краше**: если программа упала (segfault, `abort`) с непустым fully-buffered `stdout` — буфер не сбросится, последние `printf` **не появятся**. Отладочный `printf` «до падения» может не напечататься именно поэтому. Лечится `fflush` или печатью в `stderr`.
- **`_exit`/`_Exit` не сбрасывают буферы** (в отличие от `exit`/возврата из `main`). После `fork` в child обычно `_exit`, чтобы не сбросить унаследованный буфер родителя дважды.
- Управление режимом: `setvbuf(stream, NULL, _IONBF/_IOLBF/_IOFBF, size)` — задать режим явно.
- Не путать с буферами **ядра** (TCP send/recv buffer, page cache) — это отдельный слой; stdio-буфер живёт в user space поверх fd.
