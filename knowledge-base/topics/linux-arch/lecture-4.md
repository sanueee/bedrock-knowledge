# Лекция 4. Дерево каталогов, файловые системы и типы файлов

---

## 1. Базовые понятия: носители и файловые системы

**Внешний носитель (накопитель)** — физическое или логическое устройство хранения данных: HDD, SSD, USB-флэш, CD-ROM, сетевое хранилище. С точки зрения ядра это источник сырых блоков данных.

**Файловая система (FS)** — структура данных, записанная поверх накопителя и определяющая, как данные упорядочены, адресованы и защищены. Без файловой системы диск — просто набор байт без смысла. Примеры: FAT32, NTFS, ext4, XFS, ISO 9660 (оптические диски), ZFS.

---

## 2. Единое дерево каталогов vs буквы дисков

В **Windows** каждый накопитель или раздел получает букву (`C:`, `D:`, `E:`). Чтобы открыть файл на другом диске, нужно явно сменить «диск».

В **Linux (Unix)** существует **единое иерархическое дерево каталогов** с одним корнем — `/`. Все накопители, сетевые ресурсы и виртуальные источники данных встраиваются в это дерево в произвольных точках. Пользователь работает с единым пространством имён, не думая о том, на каком физическом устройстве лежит файл.

```
/                       ← корень, всегда один
├── home/               ← может быть на отдельном диске
│   └── user/
├── var/                ← может быть на отдельном разделе
│   └── log/
├── mnt/usb/            ← USB-флэш, смонтированный сюда
└── proc/               ← псевдофайловая система ядра
```

## 3. Типы файловых систем

### Локальные FS

Расположены на накопителях внутри машины или непосредственно подключённых к ней.

**Семейство UFS (Unix File System)** — общее название для файловых систем с POSIX-семантикой:
- **ext2** — классика Linux, нет журналирования.
- **ext3** — ext2 + журнал (journaling) для восстановления после сбоя.
- **ext4** — современный стандарт: журналирование, поддержка файлов до 16 ТБ, экстенты вместо блоковых указателей, delayed allocation.
- **XFS** — высокопроизводительная, хорошо работает с большими файлами и высоким параллелизмом (используется в RHEL по умолчанию).
- **Btrfs** — современная FS с copy-on-write, снапшотами и встроенным RAID.

Общие свойства UFS-семейства: inode-based (метаданные отделены от данных), поддержка прав доступа POSIX, жёстких и символических ссылок.

### Сетевые FS

Позволяют монтировать файловые системы с удалённых серверов в локальное дерево каталогов, делая удалённые файлы неотличимыми от локальных.

| Протокол | Описание |
|----------|----------|
| **NFS** (Network File System) | Стандарт Unix/Linux. Сервер экспортирует каталог; клиент монтирует его. |
| **SMB/CIFS** (smbfs/cifs) | Протокол Windows. Linux-клиент через `mount.cifs` может монтировать шары Windows/Samba. |

### Псевдофайловые системы

Виртуальные (воображаемые) FS, которые **не хранят данные на диске**. При обращении к файлу ядро генерирует его содержимое «на лету». Они встраиваются в дерево каталогов как обычные FS.

| Псевдо-FS | Точка монтирования | Назначение |
|-----------|-------------------|-----------|
| **procfs** | `/proc` | Информация о процессах и состоянии ядра |
| **sysfs** | `/sys` | Информация об устройствах и шинах |
| **devtmpfs** | `/dev` | Файлы устройств |
| **tmpfs** | `/tmp`, `/run` | RAM-диск: данные живут только до перезагрузки |
| **debugfs** | `/sys/kernel/debug` | Отладочная информация ядра |

## 4. Монтирование файловых систем

**Монтирование** — операция присоединения файловой системы к **точке монтирования** — существующему каталогу в дереве. После монтирования содержимое FS становится видно через этот каталог.

При загрузке первой монтируется **корневая FS (`/`)** — это обязательное условие. Всё остальное монтируется поверх неё.

### Команда mount

```bash
mount                           # показать все смонтированные FS
mount /dev/sdb1 /mnt/usb       # смонтировать раздел в /mnt/usb
mount -t nfs server:/export /mnt/share  # смонтировать NFS
umount /mnt/usb                 # отмонтировать
```

Постоянные точки монтирования описываются в **`/etc/fstab`** — они монтируются автоматически при загрузке:

```
# устройство    точка         тип   опции          dump pass
/dev/sda1       /             ext4  errors=remount-ro 0  1
/dev/sda2       /home         ext4  defaults           0  2
/dev/sda3       none          swap  sw                 0  0
```

### Стратегия разбивки на разделы для серверов

Разделение на несколько FS позволяет оптимизировать **производительность** и **надёжность** независимо для каждой части дерева:

| Каталог | Характер данных | Приоритет |
|---------|-----------------|-----------|
| `/` | Системные файлы, конфиги | Надёжность + производительность |
| `/home` | Данные пользователей | Надёжность (не потерять чужие данные) |
| `/var` | Логи, базы данных, почта | Производительность (много мелких записей) |
| `/tmp` | Временные файлы | Производительность, можно tmpfs |
| `/boot` | Ядро и загрузчик | Отдельно, чтобы гарантировать доступ |

Например, `/var/log` заполняется логами быстро — если он на отдельном разделе, переполнение не убьёт корневую FS и не нарушит работу системы.

## 5. Адресация файлов: абсолютные и относительные пути

Поскольку дерево каталогов — структура с одним корнем, путь от корня до любого объекта **единственен и уникален**.

### Абсолютное путевое имя

Отсчитывается от корня дерева. **Всегда начинается с `/`**.

```
/home/user/documents/report.pdf
/etc/nginx/nginx.conf
/proc/1/cmdline
```

Первый `/` — это имя корневого каталога (пустая строка до первого слеша). Каждый `/` внутри пути — разделитель компонентов.

### Относительное путевое имя

Отсчитывается от **текущего рабочего каталога** (CWD — Current Working Directory). **Не начинается с `/`**.

```bash
# Если CWD = /home/user
documents/report.pdf        # = /home/user/documents/report.pdf
../guest/file.txt           # = /home/guest/file.txt
```

### Специальные символы

| Символ | Значение |
|--------|----------|
| `.` | Текущий рабочий каталог |
| `..` | Родительский каталог |
| `~` | Домашний каталог текущего пользователя (`$HOME`) |

Комбинации допустимы в любом месте пути:

```bash
cd /var/log/../run    # эквивалентно cd /var/run
ls ./scripts/../bin   # можно, хотя и избыточно
```

## 6. Псевдофайловые системы /proc и /sys

### /proc — состояние ядра и процессов

Каждый живой процесс имеет свой каталог `/proc/<PID>/`:

```
/proc/1234/
├── cmdline     ← командная строка запуска
├── status      ← состояние процесса (имя, PID, PPID, память, UID...)
├── maps        ← карта виртуальной памяти
├── fd/         ← символические ссылки на открытые файловые дескрипторы
├── exe         ← символическая ссылка на исполняемый файл
└── cwd         ← символическая ссылка на текущий каталог процесса
```

Глобальная информация о системе:

| Файл | Содержимое |
|------|-----------|
| `/proc/meminfo` | Использование оперативной памяти |
| `/proc/cpuinfo` | Характеристики процессора (модель, частота, флаги) |
| `/proc/modules` | Загруженные модули ядра |
| `/proc/mounts` | Текущие точки монтирования |
| `/proc/net/dev` | Статистика сетевых интерфейсов |
| `/proc/uptime` | Время работы системы |

Команда `ps` читает именно эти файлы, как и `free`, `top`, `lsmod`. Это можно увидеть через `strace`:

```bash
strace ps 2>&1 | grep open
# openat(AT_FDCWD, "/proc/1/stat", ...)
# openat(AT_FDCWD, "/proc/1/status", ...)
# ...
```

Команда `free` под капотом открывает `/proc/meminfo` системным вызовом `open()` и читает его через `read()`. Весь вывод `free` — это разобранный текст из одного псевдофайла.

### /sys — устройства и шины

`sysfs` экспортирует иерархию устройств такой, какой её видит ядро:

```
/sys/bus/pci/devices/     ← устройства на PCI-шине
/sys/bus/usb/devices/     ← USB-устройства
/sys/class/net/           ← сетевые интерфейсы
/sys/block/               ← блочные устройства
```

Утилиты `lspci` и `lsusb` читают псевдофайлы из `/sys` для получения информации об устройствах. `lspci -v` детально показывает параметры каждого PCI-устройства. Для расшифровки числовых кодов производителей и устройств используется база данных `/usr/share/misc/pci.ids` (или `/usr/share/hwdata/pci.ids`).

Другие псевдофайловые системы:
- **`/dev`** (devtmpfs) — файлы устройств, создаются ядром автоматически.
- **`/run`** (tmpfs) — PID-файлы, сокеты сервисов, живут только до перезагрузки.
- **`/sys/kernel/debug`** (debugfs) — расширенная отладочная информация для разработчиков ядра.

## 7. Трассировка файловых системных вызовов

`strace` позволяет увидеть, какие системные вызовы делает программа для работы с файлами. Это наглядно раскрывает принцип «всё есть файл»:

```bash
strace cat /proc/meminfo
# openat(AT_FDCWD, "/proc/meminfo", O_RDONLY) = 3
# fstat(3, {st_mode=S_IFREG|0444, st_size=0, ...}) = 0
# read(3, "MemTotal:       ...", 131072) = 1234
# write(1, "MemTotal:       ...", 1234) = 1234
# close(3) = 0
```

`ltrace` показывает вызовы библиотечных функций (уровень libc), тогда как `strace` — системные вызовы (уровень ядра). Разница: `printf` — библиотечная функция, `write` — системный вызов, который `printf` в итоге вызывает.

## 8. Структура хранения данных: inode и Regular File

### Блоковое чтение

Все накопители (HDD, SSD) работают блоками. Исторический стандарт — **512 байт**. Современные диски часто используют 4096-байтные физические секторы, но для совместимости эмулируют 512-байтные логические.

**Файл** — это поименованная последовательность байт, хранящаяся в виде цепочки блоков на диске.

### inode — метаданные файла

Каждый файл в UFS-системе описывается структурой **inode** (index node — «узел индекса»). inode — это «данные о данных»: он содержит всё о файле, **кроме его имени**.

Поля inode:

| Поле | Описание |
|------|----------|
| **Тип файла** | Обычный, каталог, симлинк, устройство, pipe, сокет |
| **Права доступа** | `rwxrwxrwx` (владелец, группа, остальные) |
| **UID / GID** | Числовые идентификаторы владельца и группы |
| **Размер** | В байтах |
| **atime** | Время последнего доступа (access) |
| **mtime** | Время последней модификации данных (modify) |
| **ctime** | Время последнего изменения метаданных (change) |
| **Счётчик ссылок** | Сколько имён указывает на этот inode |
| **Указатели на блоки** | Адреса дисковых блоков с данными файла |

Просмотреть inode:

```bash
stat /etc/passwd
# File: /etc/passwd
# Size: 2847      Blocks: 8      IO Block: 4096   regular file
# Inode: 394205   Links: 1
# Access: (0644/-rw-r--r--)  Uid: (0/root)   Gid: (0/root)
# Access: 2026-04-24 10:00:00
# Modify: 2026-04-20 12:00:00
# Change: 2026-04-20 12:00:00
```

## 9. Каталог — второй тип файла

**Каталог** — специальный файл, содержащий таблицу вида:

```
имя файла  →  номер inode
```

Это принципиально: **имя файла хранится не в inode, а в каталоге**. inode хранит только данные и метаданные, но не знает собственного имени.

Пример содержимого каталога (схематично):

```
.        → 12345   (сам каталог)
..       → 12000   (родительский каталог)
passwd   → 394205
shadow   → 394206
hosts    → 401100
```

Служебные записи `.` и `..` присутствуют **в каждом каталоге** без исключения:
- `.` — ссылка на сам каталог (inode текущего каталога).
- `..` — ссылка на родительский каталог. В корне `/` запись `..` ссылается на сам `/` (нет родителя выше).

## 10. Жёсткие ссылки (Hard Links)

Поскольку имя хранится в каталоге, а не в inode, **одному inode может соответствовать несколько имён** — в одном или разных каталогах. Каждое такое имя называется **жёсткой ссылкой (hard link)**.

```bash
ln /home/user/photo.jpg /home/user/backup/photo.jpg
```

Оба имени указывают на один и тот же inode — один и тот же набор данных на диске.

**Счётчик ссылок** в inode отслеживает, сколько имён ссылается на него. Файл **физически удаляется** только тогда, когда:
1. Счётчик ссылок падает до 0, **и**
2. Ни один процесс не держит файл открытым (файловый дескриптор — тоже ссылка).

```bash
ln file hardlink   # счётчик: 1 → 2
rm file            # счётчик: 2 → 1, данные не удалены
rm hardlink        # счётчик: 1 → 0, данные удаляются
```

**Ограничения hard links:**
- Нельзя создать жёсткую ссылку на каталог (во избежание циклов в дереве).
- Нельзя создать жёсткую ссылку через границу файловой системы (inode-номера уникальны только внутри одной FS).

## 11. Символические ссылки (Symbolic Links)

**Символическая ссылка (symlink, soft link)** — специальный файл, содержащий строку-путь к другому файлу или каталогу. Это аналог «ярлыка» в Windows.

```bash
ln -s /usr/bin/python3 /usr/local/bin/python
ls -l /usr/local/bin/python
# lrwxrwxrwx 1 root root 16 ... python -> /usr/bin/python3
```

**Ключевые отличия от hard link:**

| Свойство | Hard Link | Symbolic Link |
|----------|-----------|---------------|
| Тип файла | То же что оригинал | Отдельный тип `l` |
| Хранит | Номер inode | Строку-путь |
| Пересечение FS | Нет | Да |
| Ссылка на каталог | Нет | Да |
| Поведение при удалении оригинала | Данные живы | «Битая» ссылка |

**Практический пример — медиатека с тегами:**

Есть коллекция музыки. Физически файлы хранятся в одном месте, но мы хотим классифицировать их по нескольким признакам (жанр, год, исполнитель) без дублирования:

```
music/
├── files/          ← реальные файлы
│   └── song.mp3
├── by_genre/
│   └── rock/ → ../../files/song.mp3   (symlink)
└── by_year/
    └── 2024/ → ../../files/song.mp3   (symlink)
```

Одна песня — несколько «тегов» через символические ссылки. Удалить «тег» — удалить только ссылку, файл остаётся.

## 12. Файлы устройств (/dev)

Файловая система `/dev` (devtmpfs) содержит **специальные файлы устройств**. Они не хранят данных — операции `read()`/`write()` на них перенаправляются ядром в соответствующий **драйвер устройства**.

Каждый файл устройства идентифицируется двумя числами:
- **Major** — номер драйвера (тип устройства).
- **Minor** — номер конкретного экземпляра устройства.

```bash
ls -l /dev/sda /dev/tty0
# brw-rw---- 1 root disk  8, 0 ... /dev/sda
# crw--w---- 1 root tty   4, 0 ... /dev/tty0
# ^                        ^  ^
# тип (b=block, c=char)  Maj Min
```

### Символьные устройства (type=c, character devices)

Обмен происходит **побайтово**, без буферизации в блоки. Данные читаются и записываются последовательно.

Примеры:
- `/dev/tty`, `/dev/pts/*` — терминалы.
- `/dev/input/event0` — клавиатура (поток событий нажатий).
- `/dev/input/mice` — мышь (поток координат и кликов).
- `/dev/null` — «чёрная дыра»: всё записанное теряется, при чтении — EOF.
- `/dev/urandom` — источник псевдослучайных байт.

Чтение сырого потока с клавиатуры:
```bash
sudo cat /dev/input/event0   # бинарный поток событий
```

### Блочные устройства (type=b, block devices)

Обмен происходит **блоками**. Ядро кэширует блоки в page cache. Используются для дисков и накопителей.

Примеры:
- `/dev/sda` — первый SATA/SCSI/SSD диск целиком.
- `/dev/sda1` — первый раздел этого диска.
- `/dev/nvme0n1` — NVMe-диск.

Работа с блочным устройством напрямую:
```bash
sudo hexdump -C /dev/sda | less   # просмотр сырых байт диска (MBR, таблица разделов...)
sudo fdisk -l /dev/sda            # показать таблицу разделов
```

## 13. Именованные каналы — Pipe (FIFO)

**Именованный канал (named pipe, FIFO)** — специальный файл для **однонаправленной** передачи данных между процессами (IPC — Inter-Process Communication).

- Работает по принципу очереди: **FIFO** (First In, First Out).
- Данные хранятся в буфере памяти ядра — на диске их нет.
- **Simplex**: один конец пишет (`write`), другой читает (`read`), в обратную сторону нельзя.

```bash
mkfifo /tmp/mypipe          # создать именованный канал (type=p)
ls -l /tmp/mypipe
# prw-r--r-- 1 user group 0 ... /tmp/mypipe

# В одном терминале:
echo "hello" > /tmp/mypipe   # пишем (блокируется до появления читателя)
# В другом терминале:
cat /tmp/mypipe               # читаем
```

Безымянные каналы (неименованные, `|` в командной строке) работают аналогично, но существуют только пока живы оба процесса.

## 14. Сокеты — Socket (type=s)

**Сокет** — специальный файл для **двунаправленного** межпроцессного взаимодействия.

- **Duplex**: оба конца могут одновременно и читать, и писать.
- **Multiplexing**: к одному сокету могут подключаться несколько клиентов.
- Данные также хранятся в буфере памяти ядра.

**Unix domain socket** (локальный сокет) — сокет в виде файла в `/dev` или `/run`, используемый для IPC на одной машине (быстрее, чем TCP-сокет на `localhost`).

Классический пример — **syslogd** (демон журналирования):

```bash
stat /dev/log
# File: /dev/log
# File type: socket

sudo lsof /dev/log
# syslogd ... /dev/log   ← демон слушает сокет
# rsyslogd ... /dev/log  ← другие процессы пишут в него
```

Все программы, вызывающие `syslog()`, пишут в `/dev/log`. syslogd читает из него и раскладывает сообщения по файлам в `/var/log/`.

## 15. Сводная таблица типов файлов

| Символ | Тип | Создаётся | Назначение |
|--------|-----|-----------|-----------|
| `-` | Regular file | `touch`, `echo >`, редактором | Хранение данных |
| `d` | Directory | `mkdir` | Таблица «имя → inode» |
| `l` | Symbolic link | `ln -s` | Ссылка-путь на другой объект |
| `b` | Block device | ядром в `/dev` | Блочный накопитель (диск) |
| `c` | Char device | ядром в `/dev` | Символьное устройство (клавиатура, tty) |
| `p` | Named pipe | `mkfifo` | Однонаправленный IPC-канал |
| `s` | Socket | программой через `bind()` | Двунаправленный IPC |

Тип файла — это поле в **inode**. Команда `stat` покажет его явно, `ls -l` — первым символом в строке прав.
