# DNS-протокол вручную / DNS wire format

## Что это

DNS (Domain Name System) — распределённая база «имя → запись». На wire-уровне это бинарный протокол «один вопрос → один ответ» поверх UDP:53. Собираешь запрос по байтам, шлёшь на recursive resolver (рекурсивный резолвер, напр. 8.8.8.8), парсишь ответ. Всё, что за тебя прятал `getaddrinfo` (B-4), здесь делается руками.

## Ключевые термины (English)

- **stub resolver** — программа-клиент, умеет только сформировать вопрос и разобрать ответ.
- **recursive resolver** — сервер (8.8.8.8), который сам обходит иерархию root → TLD → authoritative и возвращает готовый ответ.
- **RD (recursion desired)** — флаг «сделай рекурсию за меня». `RD=0` → сервер вернёт referral (отсылку) или REFUSED, а не пустоту.
- **RR (resource record)** — запись в ответе: NAME, TYPE, CLASS, TTL, RDLENGTH, RDATA.
- **QNAME / labels** — имя в формате length-prefixed меток, без точек.
- **name compression** — переиспользование повторяющегося имени через 2-байтовый указатель (`0xC0`-маркер).
- **NXDOMAIN** — `RCODE=3`, имени не существует.
- **NODATA** — `RCODE=0` при `ANCOUNT=0`: имя есть, но записей запрошенного типа нет.
- **TC (truncated)** — ответ не влез в UDP, переспросить по TCP.

## Как работает

### 1. Экосистема и транспорт

- **S** (stub, твоя программа) шлёт один UDP-датаграмм на **R** (recursive, 8.8.8.8:53) с `RD=1`.
- R с `RD=1` сам обходит иерархию (root → `.com` → authoritative) — эта рекурсия на его стороне, S её не видит.
- R возвращает один UDP-датаграмм. S принимает через `recvfrom()` → `n` байт, работать ровно с `n`.
- UDP выбран ради одного round-trip без handshake; плата — нет гарантий доставки и лимит размера (при переполнении бит `TC` → fallback на TCP).

### 2. Формат сообщения — 5 секций (одинаков для запроса и ответа)

| Секция | Что внутри | В запросе | В ответе |
|--------|-----------|-----------|----------|
| Header | 12 байт, счётчики + флаги | есть | есть |
| Question | имя + тип + класс | 1 запись | эхо той же записи |
| Answer | найденные RR | пусто | N записей |
| Authority | authoritative-серверы | пусто | опционально (игнорируем) |
| Additional | доп. записи | пусто | опционально (игнорируем) |

### 3. Заголовок — 12 байт (шесть 16-битных полей, network byte order → htons/ntohs)

```
offset  поле       что это
0-1     ID         transaction ID (рандомизировать!)
2-3     Flags      битовое поле (ниже)
4-5     QDCOUNT    число вопросов
6-7     ANCOUNT    число ответов
8-9     NSCOUNT    записей в Authority
10-11   ARCOUNT    записей в Additional
```

Запрос: `ID`=random, `Flags`=`0x0100` (только RD), `QDCOUNT`=1, остальные счётчики=0.

**Поле Flags по битам:**

```
бит  15   14-11    10   9    8    7    6-4   3-0
     QR   Opcode   AA   TC   RD   RA   Z     RCODE
```

| Бит | Имя | Смысл | Запрос | Ответ |
|-----|-----|-------|--------|-------|
| QR | query/response | 0=запрос, 1=ответ | 0 | 1 |
| Opcode | тип операции | 0=стандартный | 0 | 0 |
| AA | authoritative answer | ответ от authoritative | — | инфо |
| TC | truncated | обрезан → TCP | 0 | проверить |
| RD | recursion desired | «сделай рекурсию» | 1 | эхо |
| RA | recursion available | R умеет рекурсию | — | обычно 1 |
| Z | reserved | нули | 0 | 0 |
| RCODE | response code | 0=OK,3=NXDOMAIN,5=REFUSED | 0 | проверить |

`0x0100` = `0000 0001 0000 0000` — единственный бит на позиции 8 (RD). Пример разбора ответа `Flags=0x8180` = `1000 0001 1000 0000`: QR=1 (бит15), RD=1 (бит8), RA=1 (бит7), RCODE=0 (младшие 4 бита) — нормальный успешный ответ.

### 4. Секция Question — кодирование имени в labels

Порядок: `QNAME` (переменная длина) → `QTYPE` (2 байта, A=1) → `QCLASS` (2 байта, IN=1).

`QNAME` — не строка. Цепочка меток: `[длина][байты]...`, завершается нулевым байтом. Точек в wire нет — они превращаются в границы меток.

```
example.com  →  07 example 03 com 00
dns.google.com  →  03 dns 06 google 03 com 00
```

Сборка: идёшь по hostname, `memchr(p,'.')` → длина метки = расстояние до точки → пишешь байт длины → `memcpy()` метку → за точку → повтор → в конце `00`. Точка не копируется.

Ограничения (не случайные): метка ≤ 63 байта (старшие 2 бита байта длины зарезервированы под указатель), всё имя ≤ 255 байт.

### 5. Answer — RR и name compression

Формат RR:
```
NAME     переменная (labels / указатель / гибрид)
TYPE     2 байта (A=1)
CLASS    2 байта (IN=1)
TTL      4 байта
RDLENGTH 2 байта
RDATA    RDLENGTH байт (для A = 4 байта IPv4)
```

**Компрессия имён.** Повторяющееся имя пишут раз, дальше — указатель. Байт со старшими битами `11` (маска `0xC0`) = указатель на 2 байта; младшие 14 бит = offset от начала сообщения (байт 0):
```
offset = ((byte0 & 0x3F) << 8) | byte1
```
Классика: NAME в Answer = `C0 0C` → offset 12 → конец заголовка → QNAME вопроса.

Имя всегда завершается **либо** нулевым байтом `00`, **либо** указателем (указатель терминирует имя). Возможен гибрид: `03 www C0 0C`.

**Для задачи B-12 — SKIP, не EXPAND.** Чтобы добраться до RDATA, `NAME` надо только пропустить:
```
1. читаешь байт, смотришь старшие 2 бита
2. 11 → указатель, +2 байта, NAME пройден
3. байт == 0 → терминатор, +1 байт, NAME пройден
4. иначе (00, L>0) → метка, +1+L байт, назад к 1
```
Следовать по указателю (раскручивать в строку) для A-записи не нужно.

## Пример (реальный разбор Answer из сессии)

Байты Answer-записи для `example.com`:
```
C0 0C  00 01  00 01  00 00 01 2C  00 04  5D B8 D8 22
```
- `C0 0C` — NAME: указатель на offset 12 (имя вопроса). NAME пройден.
- `00 01` — TYPE = 1 = A.
- `00 01` — CLASS = 1 = IN.
- `00 00 01 2C` — TTL = 0x12C = 300 сек.
- `00 04` — RDLENGTH = 4.
- `5D B8 D8 22` — RDATA: 93.184.216.34 (реальный IP example.com). Печать через `inet_ntop()`.

## Подводные камни

**Логика ответа:**
- Проверять `RCODE==0` **и** `ANCOUNT>0` — это разные гейты. `RCODE=0, ANCOUNT=0` = **NODATA** (имя есть, A-записи нет — только AAAA/MX и т.п.), это НЕ `NXDOMAIN` (`RCODE=3`, имени нет вообще). Без проверки `ANCOUNT>0` войдёшь в цикл парсинга несуществующей секции → полезешь в Authority как в Answer → мусор/OOB.
- В Answer могут быть записи не типа A (CNAME, AAAA) — проверять `TYPE==1`, иначе пропускать `RDLENGTH` байт.

**Security (горячая зона — untrusted parsing, [[feedback-tedious-security-code]]):**
- **Каждый доступ сверять с `end = buf + n`.** `recvfrom` вернул `n`; за `n` — мусор. Любой байт NAME/TYPE/TTL/RDATA — перед `end`.
- **`RDLENGTH` — untrusted длина** (как chunked-размер в B-11): проверять **до** чтения RDATA. Причём форма важна: `p + rdlength > end` при `rdlength` до 65535 **образует заграничный указатель — это UB само по себе**, до всякого разыменования (стандарт разрешает указатель только внутри массива и на one-past-the-end). Правильно сравнивать остаток: `rdlength > end - p` (`end - p` определено, оба указателя in-bounds). Иначе — и OOB-read, и UB на вычислении.
- **Compression pointer loop → DoS.** Если раскручиваешь имя по указателю, malformed-пакет может дать петлю A→B→A → бесконечный цикл. Guard: лимит прыжков ИЛИ требовать указатель строго назад (меньший offset). При режиме SKIP (не следуешь) — петля не грозит, но при EXPAND — обязательно.
- **Offset указателя — untrusted:** при следовании проверять `offset < n`.
- **ID рандомизировать.** Предсказуемый ID + известный source port → off-path атакующий подделывает ответ → cache poisoning. Random ID поднимает планку угадывания (16 бит ID + порт).
- **Byte order:** забыл `htons` на `QDCOUNT` → уедет как 256 → сервер не поймёт запрос.
- **Alignment / type punning:** каст `buf` на `struct` заголовка рискован (разыменование `uint16_t*` по невыровненному адресу = UB); в Answer поля вообще не выровнены. Безопаснее ручное извлечение байт (`buf[i]<<8 | buf[i+1]`) или `memcpy` в поле.

**Сравнение с getaddrinfo (B-4):** библиотека прятала сборку пакета, компрессию, `/etc/resolv.conf`, retry/timeout, TCP-fallback, выбор A/AAAA.
