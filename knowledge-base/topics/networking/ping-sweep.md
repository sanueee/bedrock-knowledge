# ICMP ping sweep / host discovery по подсети

## Что это

Ping sweep — обход подсети echo-запросами, чтобы получить список живых хостов (host discovery). От `ping` отличается не масштабом, а **структурой**: 254 запроса живут одновременно, отправка отвязана от приёма, тайм-аут один на всю фазу сбора.

## Ключевые термины (English)

- **ping sweep / host discovery** — перечисление живых хостов сети рассылкой probe-пакетов.
- **fan-out phase / collection phase** — фаза рассылки и фаза сбора; в этой модели они не пересекаются.
- **absolute deadline** — момент окончания сбора, вычисленный один раз от конца рассылки.
- **slot** — запись массива состояния, соответствующая одной цели; ключ доступа — `sequence` из ответа.
- **false negative** — живой хост, помеченный как молчащий; для сканера — самая дорогая ошибка.
- **rate limit** — искусственная пауза между отправками, растягивающая фазу рассылки.
- **kernel receive buffer (`SO_RCVBUF`)** — очередь принятых пакетов сокета; переполнение = молчаливая потеря.
- **skb truesize** — реальный объём памяти ядра на один пакет; учитывается против лимита буфера, а не размер полезной нагрузки.
- **software timestamping (`SO_TIMESTAMPNS`)** — метка времени приёма, проставленная ядром и переданная в ancillary data.
- **ancillary data / control message** — метаданные пакета, приходящие через `recvmsg` рядом с полезной нагрузкой.

## Как работает

**Почему синхронная схема не «медленнее», а неприменима.** В [[icmp-echo]] цикл был «отправил → подождал → напечатал → следующий», и состояние одного запроса помещалось в локальные переменные итерации, потому что живым был ровно один запрос. Для `/24` эта схема даёт 254 цели × 1 с тайм-аута на молчащий адрес = больше четырёх минут на сеть, где живых три хоста. Реальный sweep — две секунды. Разница не в оптимизации кода, а в том, что все запросы должны быть в воздухе одновременно.

**Три следствия, из которых состоит вся структура программы:**

1. **Состояние переезжает из переменных в массив.** «Ответил ли», «когда отправлено», «какой RTT», «какой TTL» — поля записи `struct target`, массив длиной в число целей (`calloc`, потому что `/22` — это 1022 записи, для стека многовато).
2. **Корреляция превращается в адресацию.** Вопрос уже не «мой это пакет или чужой», а «в какой слот его положить». `sequence`, положенный в запрос, даёт индекс за O(1) — но приходит он **из сети**.
3. **Дедлайн один на фазу сбора.** Вычисляется от момента окончания рассылки; `recvfrom` каждый раз получает **остаток** до него через `SO_RCVTIMEO`. Урок про перезапуск окна на каждом вызове (см. [[icmp-echo]]) здесь критичнее: за окно сбора приходят сотни пакетов.

**`sequence` как индекс — это индексирование массива числом, которое прислал удалённый хост.** Между `ntohs(icmp->un.echo.sequence)` и записью в слот обязаны стоять четыре проверки, и только первая про границы:

```
1. id совпадает со своим            — иначе это ответ чужому процессу
2. 1 <= seq <= count                — иначе out-of-bounds write; кто угодно пришлёт seq = 60000
3. src.sin_addr == адрес слота      — тот ли хост ответил, кем он себя считает
4. слот ещё не HOST_ALIVE           — дубль не должен второй раз попасть в статистику
```

Проверки 2 и 3 закрывают разные атаки: граница — от порчи памяти, сверка адреса — от подделки чужим хостом реплая за молчащую цель.

**Три состояния цели, а не два.** Молчание (`HOST_NO_REPLY`) и явный отказ (`HOST_UNREACHABLE`, пришёл ICMP Destination Unreachable) — разные результаты скана: первое читается как «фильтруется или нет хоста», второе — как «маршрутизатор подтвердил недостижимость». Сваливать их в «no response» значит терять информацию, которая у тебя уже есть. Внутри ICMP-ошибки лежит копия исходного IP-заголовка (снова `ihl*4`) и первые 8 байт исходного ICMP — то есть свои `id`/`sequence`, по которым ошибка привязывается к слоту.

**Откуда берутся unreachable в локальной сети.** На прогоне B-20 в docker-сети `/24` их оказалось 148 из 254 — и не от роутера, а от **собственного ядра**: ARP-запрос к несуществующему соседу не получает ответа, ядро генерирует локальный ICMP Destination Unreachable и доставляет его на raw-сокет. Отсюда неожиданная зависимость: при `timeout = 1000` мс их ноль, при `2000` мс — 148, потому что ARP-таймаут (около секунды) успевает истечь внутри окна сбора. Число «недостижимых» в такой сети — функция тайм-аута, а не свойство сети.

**Фаза рассылки и приёмный буфер ядра.** Пока идёт рассылка, сокет не читается, а ответы от быстрых хостов уже приходят и копятся в приёмном буфере. Ядро считает не полезную нагрузку, а `skb->truesize` — сотни байт–килобайт на 84-байтовый пакет, поэтому в дефолтные ~208 КБ (`net.core.rmem_default`) влезает порядка нескольких сотен ответов, а не тысяч. Переполнение = молчаливый дроп = false negative. Два независимых средства: rate limit (`nanosleep` порядка 1 мс между отправками — растягивает рассылку) и подъём `SO_RCVBUF` через `setsockopt`. Оба применимы одновременно.

**Потолок `SO_RCVBUF` и почему `CAP_NET_RAW` тут не помогает.** Ядро удваивает переданное значение (`SO_RCVBUF` учитывает накладные расходы) и обрезает его по `net.core.rmem_max`. Обойти лимит можно только `SO_RCVBUFFORCE`, который требует `CAP_NET_ADMIN` — а у sweep есть лишь `CAP_NET_RAW`. Практический вывод: запросить с запасом, прочитать фактическое значение через `getsockopt` и **предупредить**, если урезали. Проверка «получилось ли» — `actual < requested`: при успехе `actual` вернётся удвоенным, то есть заведомо больше запроса.

**RTT в фазовой модели измеряется неверно, и это невидимо при чтении кода.** Если `t_recv` берётся в момент, когда пользовательский код вычитал пакет, то в RTT попадает всё время, которое пакет лежал в буфере, ожидая конца рассылки. На прогоне B-20 sweep показал 330–348 мс там, где системный `ping` даёт 0.089 мс — расхождение в четыре тысячи раз. Арифметика сходится точно: `nanosleep(1 мс)` реально спит ~1.35 мс, 254 цели дают ~343 мс рассылки, и первая по порядку цель получает ровно эти 343 мс, одиннадцатая — 343 − 15. То есть измеряется «сколько осталось до конца рассылки», а не задержка сети.

Два честных решения:

| Способ | Что даёт | Цена |
|---|---|---|
| `SO_TIMESTAMPNS` + `recvmsg` | ядро ставит метку в момент приёма пакета; фазовая модель не меняется | разбор ancillary data (`CMSG_FIRSTHDR`/`CMSG_DATA`); метка на `CLOCK_REALTIME` → `t_send` тоже надо снимать `CLOCK_REALTIME`, иначе вычитание бессмысленно |
| перекрыть фазы | честный RTT без CMSG | сокет в non-blocking, приём вклинивается в цикл рассылки — переделка структуры, шаг к событийной модели |

Пока RTT нужен как «жив/не жив» — расхождение терпимо; как метрика задержки он в фазовой модели просто не работает.

**Аккумуляторы статистики.** `min` нельзя инициализировать нулём — условие `rtt < rtt_min` тогда не сработает ни разу; либо `DBL_MAX` из `<float.h>`, либо флаг «первый замер». Сумма и среднее — разные величины: копится `rtt_sum`, деление на `hosts_up` происходит в момент печати и только под проверкой `hosts_up > 0` (иначе `0/0` = NaN в отчёте). `probes_sent` инкрементируется после успешного `sendto`, а не в начале итерации. Инвариант отчёта, проверяемый глазами на каждом прогоне: `hosts_up + hosts_unreachable + no_response == probes_sent`.

**Число хостов в сети.** Для `/24` — 254: `broadcast - network - 1`. Для `/31` и `/32` формула даёт 0, и надо решить осознанно: RFC 3021 говорит, что в `/31` нет network/broadcast (оба адреса используемые), а `/32` — один хост. Отказ с внятной ошибкой — допустимое решение, «а я не подумал» — нет.

## Пример

Корреляция ответа со слотом — `sections/networking/ping-sweep/net.c`, функция `recv_packets`:

```c
uint16_t seq = ntohs(icmp->un.echo.sequence);
if (seq < 1 || seq > count)                             // граница: seq пришёл из сети
    continue;
if (src.sin_addr.s_addr != list[seq-1].addr.s_addr)     // тот ли хост ответил
    continue;
if (list[seq-1].status == HOST_ALIVE)                   // дубль не считаем дважды
    continue;
```

Подъём приёмного буфера с проверкой, что ядро не урезало запрос — `send_packets`:

```c
if (getsockopt(*fd, SOL_SOCKET, SO_RCVBUF, &rcvbuf_actual, &rcvbuf_len) == 0
    && rcvbuf_actual < rcvbuf)
    fprintf(stderr, "warning: SO_RCVBUF = %d, requested %d (capped by net.core.rmem_max);"
                    " some replies may be dropped\n", rcvbuf_actual, rcvbuf);
```

Прогон в docker-сети `172.28.0.0/24` (gateway, сам контейнер и два поднятых рядом):

```
172.28.0.1      ttl=64 time=343.698 ms
172.28.0.2      ttl=64 time=342.640 ms
172.28.0.11     ttl=64 time=331.258 ms
172.28.0.12     ttl=64 time=330.023 ms
--- sweep statistics ---
254 probes sent, 4 hosts up, 0 hosts unreachable, 250 no response
elapsed 1371 ms, rtt min/avg/max = 330.023/336.905/343.698 ms
```

Те же 330–343 мс против `ping`, работающего в этой же сети — иллюстрация ошибки измерения RTT, разобранной выше:

```
rtt min/avg/max/mdev = 0.041/0.089/0.121/0.034 ms
```

## Подводные камни

- **`sequence` из пакета как индекс без проверки границ** — прямой out-of-bounds write, управляемый кем угодно в сети. Проверка обязана стоять до любого обращения к массиву.
- **Дефолтный `SO_RCVBUF` на длинной рассылке** — теряются ответы уже отвеченных хостов; ошибка проявляется как «часть живых хостов не найдена» и не воспроизводится стабильно.
- **`SO_RCVBUF` выше `net.core.rmem_max` без `CAP_NET_ADMIN`** — молча урезается; без `getsockopt`-проверки программа думает, что защитилась.
- **RTT, замеренный в момент чтения из сокета,** в фазовой модели измеряет время до конца рассылки. Проверяется сравнением с системным `ping`, а не чтением кода.
- **`rtt_min = 0`** — «минимум» навсегда останется нулём. Аккумулятор с именем `rtt_avg`, в котором лежит сумма, прячет забытое деление.
- **Деление на `hosts_up == 0`** даёт NaN в отчёте на полностью молчащей сети — самый частый реальный сценарий скана.
- **`prefix` из аргументов без нижней границы** — `/8` это 16 миллионов целей; порог (в B-20 — `/22`) отсекает случайный запуск, который положит и сеть, и программу.
- **Адрес, не выровненный по сети** (`172.17.0.137/24`) должен нормализоваться маской, а не приниматься как есть.
- **`htonl` вместо `ntohl`** на входе арифметики работает (обе — одна и та же перестановка байт), поэтому ошибка не ловится тестом; ловится только чтением имени.
- **Хедер, не подключающий свои типы,** собирается лишь потому, что включён последним; включённый первым даёт `incompatible pointer type` в прототипе.
- **Docker Desktop на macOS не возвращает ICMP из контейнера в интернет** (выяснено на B-19) — все цели должны быть внутри docker-сети. Дефолтный bridge — `/16`, поэтому под тест порога `/22` нужна отдельная сеть: `docker network create --subnet 172.28.0.0/24`.
