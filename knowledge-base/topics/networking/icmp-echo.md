# ICMP echo через raw socket / ICMP echo request-reply

## Что это

ICMP echo — пара сообщений request/reply поверх IP, которой `ping` проверяет достижимость хоста и измеряет round-trip time (RTT). Пишется через raw socket (`SOCK_RAW`, `IPPROTO_ICMP`), потому что ICMP не имеет портов и не обслуживается обычными datagram-сокетами.

## Ключевые термины (English)

- **ICMP echo request / echo reply** — type 8 / type 0; reply возвращает identifier, sequence и payload запроса без изменений.
- **identifier / sequence number** — 16-битные поля корреляции внутри `un.echo`; отправитель кладёт свои, получатель обязан вернуть их эхом.
- **RTT (round-trip time)** — время туда-и-обратно, от `sendto` до приёма **своего** reply; включает обработку на удалённой стороне.
- **TTL (time to live)** — вопреки названию, счётчик хопов в IP-заголовке; каждый роутер декрементирует, на нуле пакет отбрасывается и шлётся ICMP Time Exceeded.
- **discriminated union** — union, активная ветка которого определяется полем **снаружи** него (в `struct icmphdr` — полем `type`).
- **absolute deadline** — фиксированный момент окончания ожидания; в отличие от per-call timeout не продлевается повторными вызовами.
- **out-parameter** — возврат данных через переданный указатель; статус — через `return`.
- **dangling pointer** — указатель на память, время жизни которой уже закончилось.

## Как работает

**Формат сообщения.** 8 байт заголовка (`type`, `code`, `checksum`, затем 4 байта union) + произвольный payload. Настоящий `ping` кладёт 56 байт payload, отсюда «64 bytes» в выводе — это 8 + 56, длина **ICMP-части**, а не всего принятого буфера.

**Union в `struct icmphdr`.** Три ветки делят одни и те же 4 байта, поэтому `sizeof(struct icmphdr) == 8` при любом сценарии. Какая ветка активна — сама память не сообщает; решает поле `type`, лежащее снаружи union:

| `type` | Активная ветка | Что в ней |
|---|---|---|
| 8 / 0 (`ICMP_ECHO` / `ICMP_ECHOREPLY`) | `un.echo` | `id`, `sequence` — поля корреляции |
| 5 (`ICMP_REDIRECT`) | `un.gateway` | IP нового шлюза |
| 3 + `code == ICMP_FRAG_NEEDED` | `un.frag.mtu` | MTU для Path MTU Discovery |
| 3 (общий случай), 11 (`ICMP_TIME_EXCEEDED`) | — | 4 байта unused; полезное лежит **после** заголовка |

Практическое правило: сначала прочитать `type`, только потом решать, какую ветку смотреть. `memset` под ноль обнуляет весь union разом, дальше пишется только своя ветка; `id`/`sequence` многобайтовые → `htons` при записи, `ntohs` при чтении.

**Checksum.** Тот же RFC 1071, что и в [[checksum]], но по **всему** ICMP-сообщению (заголовок + payload) и **без pseudo-header** — тот нужен TCP/UDP для привязки к L3-адресам, ICMP живёт прямо на IP. Функция `compute_checksum(const uint8_t*, size_t)` переносится из B-18 без единой правки — это и есть отдача от протокол-агностичного интерфейса. Инвариант прежний: поле `checksum` = 0 в момент расчёта, payload уже на месте.

**Центральная идея — raw socket отдаёт копию чужой почты.** Raw ICMP-сокет получает копию **каждого** ICMP-пакета, пришедшего на хост: ответы соседнему процессу, ICMP-ошибки от чужих соединений, чей-то `traceroute`. Отсюда два следствия, определяющих всю структуру кода:

1. **Нужна корреляция** — по `id` (кто отправитель, обычно `getpid() & 0xFFFF`) и `sequence` (какой именно запрос). Усечение до 16 бит делается **один раз**, при инициализации: если в пакет кладётся `(uint16_t)pid`, а сравнивается полный `pid_t`, при pid > 65535 совпадения не будет никогда.
2. **Чужой пакет — не ошибка и не тайм-аут.** Он не должен ни съедать итерацию, ни трогать `seq`, ни попадать в статистику. Это условие продолжения цикла ожидания, а не его завершения.

**`recvfrom` отдаёт пакет вместе с IP-заголовком.** Отступ до ICMP-части — `ip->ihl * 4`, а не `sizeof(struct iphdr)`: заголовок может нести options. Порядок проверок жёсткий — каждая стоит перед чтением, которое без неё станет OOB:

```
1. recv >= sizeof(struct iphdr)?           иначе даже ihl не прочитать
2. ip_len = ip->ihl * 4
3. ip_len >= 20 && recv >= ip_len + 8?     ihl пришёл из сети: 0 даст смещение 0, 15 уведёт за буфер
4. icmp = (struct icmphdr *)(answer + ip_len)
```

**Структура ожидания — три исхода, не два.** Цикл нужен вокруг `recvfrom`, а не вокруг всей итерации: отправка происходит один раз, приём — много раз в одном окне. Наружу уходят `REPLY_OK` / `REPLY_TIMEOUT` / `REPLY_ICMP_ERROR` (+ `REPLY_FATAL`); «чужой» наружу не возвращается вообще.

**Ловушка `SO_RCVTIMEO`.** Он отсчитывает свою секунду **заново на каждый вызов** `recvfrom`. Десять чужих пакетов подряд — и одна итерация ждёт десять секунд вместо одной. Лечится абсолютным дедлайном: `deadline = ts_to_ms(t_send) + окно`, перед каждым `recvfrom` пересчитать остаток и положить его в `SO_RCVTIMEO`; остаток ≤ 0 → тайм-аут. Окно ужимается, а не начинается заново.

**RTT и `CLOCK_MONOTONIC`.** `struct timespec` хранит две независимые части, складывать их напрямую нельзя — нужен общий знаменатель:

```
rtt_ms = (t_recv.tv_sec - t_send.tv_sec) * 1000.0
       + (t_recv.tv_nsec - t_send.tv_nsec) / 1000000.0
```

Разность наносекунд может быть отрицательной — формула сама компенсирует переход через секунду: `{5, 999000000}` → `{6, 1000000}` даёт `1000.0 + (−998.0) = 2.0 ms`. Делитель обязан быть `1000000.0` с точкой, иначе целочисленное деление обнулит всё меньше миллисекунды. Часы — только `CLOCK_MONOTONIC`: wall-clock может прыгнуть назад от NTP-корректировки прямо между отправкой и приёмом и дать отрицательный RTT.

**Момент замера.** RTT берётся **после** успешной корреляции, а не сразу после `recvfrom` — иначе засчитывается время до чужого пакета.

**TTL как источник информации.** В reply приходит TTL, с которым пакет дошёл. Типовые стартовые значения: 64 (Linux), 128 (Windows), 255 (сетевое оборудование) — отсюда `ttl=117` от 8.8.8.8 читается как 128 − 117 = 11 хопов, и отсюда же OS fingerprinting по TTL (продолжение линии B-13).

**Статистика инкрементируется в разных местах, не в одной точке.** `transmitted` — сразу после успешного `sendto`, независимо от исхода приёма (иначе при полном отсутствии ответов получится `0 transmitted` и деление на ноль вместо честных 100% loss). `received` и RTT-аккумуляторы — только после полной валидации. ICMP-ошибка — **не** «ответ получен»: хост подтвердил, что доставки не было, loss по этому `seq` остаётся.

**Печатать наблюдаемое, а не предполагаемое.** Адрес источника берётся из `struct sockaddr_in`, заполненного `recvfrom`, а не из адреса цели. Для echo reply они совпадут, но `Time to live exceeded` шлёт промежуточный роутер, а при резолве имени интересен конкретный ответивший IP. В B-20 (sweep по `/24`) это станет единственным способом понять, кто ответил.

**Привилегии.** `socket(AF_INET, SOCK_RAW, IPPROTO_ICMP)` требует `CAP_NET_RAW` (см. [[capabilities]]). Право проверяется один раз, в момент `socket()` — значит его можно сбросить сразу после открытия (`capng_clear` + `capng_apply`), и `sendto`/`recvfrom` на уже выданном fd продолжат работать. Подтверждено прогоном: от `nobody` без `setcap` — `EPERM`, с `setcap cap_net_raw+ep` — работает под обычным uid.

## Пример

Корреляция и выход из цикла ожидания — ядро `sections/networking/icmp-echo/ping.c`:

```c
if (icmp->type == ICMP_ECHOREPLY)
{
    if (ntohs(icmp->un.echo.id) != id || ntohs(icmp->un.echo.sequence) != seq)
        continue;                    // чужой ping — ждём дальше в том же окне
    struct timespec t_recv;
    clock_gettime(CLOCK_MONOTONIC, &t_recv);
    *rtt = (t_recv.tv_sec - t_send.tv_sec) * 1000.0 + (t_recv.tv_nsec - t_send.tv_nsec) / 1000000.0;
    *ttl = ip->ttl;
    *icmp_len = recv - ip_len;
    *src_addr = src.sin_addr;        // копируем ЗНАЧЕНИЯ, не указатели внутрь answer
    return REPLY_OK;
}
```

Проверка, что чужой трафик не ломает корреляцию (системный `ping` флудит 5 pkt/s по тому же адресу параллельно):

```
$ ping -i 0.2 -q 172.17.0.1 &  ;  ./ping 172.17.0.1 6
64 bytes from 172.17.0.1: icmp_seq=1 ttl=64 time=0.113583 ms
...
6 packets transmitted, 6 received, 0% packet loss
```

## Подводные камни

- **`&&` — не «адрес адреса», а GCC-оператор адреса метки** (label address, для computed goto). Чтобы получить `T**`, брать адрес надо у переменной типа `T*`: `&x` даёт `T*`, если `x` имеет тип `T`.
- **Присваивание параметру-указателю не видно вызывающему.** Параметр — локальная копия адреса; `ip = ...` внутри функции умирает на `return`, а `*ip_len = ...` идёт **по** адресу и пишет в память вызывающего. Отсюда развилка: копировать данные (`memcpy` в объект вызывающего) либо отдавать сам указатель через `T**`.
- **Указатели внутрь приёмного буфера нельзя выносить за время его жизни.** Если `answer` — локальный массив функции приёма, наружу отдаются скопированные значения (`ttl`, длина, адрес), иначе вызывающий получит dangling pointer на мёртвый стек.
- **Приоритет операторов в условии цикла.** `sent = sendto(...) != N` разбирается как `sent = (sendto(...) != N)` — в переменную ложится 0/1, не число байт. Аналогично `sent = sendto(...) && errno == EINTR`. Присваивание в условии требует явных скобок: `(sent = sendto(...)) < 0`.
- **Знаковость в сравнениях с `sizeof`.** `ssize_t recv >= sizeof(...)` конвертирует знаковый операнд в беззнаковый: `-1` становится огромным числом и проверка проходит. Ошибку syscall ловить как `< 0` **до** любых сравнений с размерами.
- **Стрелка стартового значения `min`.** Инициализация нулём делает `rtt_min` неотличимым от «ещё не заполнено»; надёжнее флаг или присвоение первым замером.
- **Деление на ноль в статистике** — `packet_loss` при `transmitted == 0`, `rtt_avg` при `received == 0`. И порядок скобок: доля потерь считается **до** умножения на 100 (`(1 - received/transmitted) * 100`, не `1 - ratio*100`).
- **Буферизация вывода.** `stdout` при перенаправлении становится полностью буферизованным, `stderr` — никогда; строки успеха и ошибок в логе разъезжаются по порядку. Лечится `setvbuf(stdout, NULL, _IOLBF, 0)`.
- **ICMP-ошибки требуют своей корреляции.** Внутри type 3/11 после 8 байт заголовка лежит копия исходного IP-заголовка (снова `ihl*4`) и первые 8 байт исходного ICMP — то есть твои `id`/`sequence`. Без сверки чужая ICMP-ошибка прервёт твоё ожидание.
- **Docker Desktop на macOS не возвращает ICMP из контейнера наружу.** Echo request'ы уходят с `eth0` (видно в `tcpdump`), ответов нет, при этом TCP и DNS работают. Тестировать на loopback, на docker-шлюзе (`172.17.0.1` — маршрутизируемый путь, не loopback) или на Linux-VM.
