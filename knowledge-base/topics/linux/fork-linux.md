# fork() — создание процессов в Linux

## Суть (своими словами)

`fork()` создаёт точную копию текущего процесса. После вызова существуют два независимых процесса с одинаковым кодом и данными, но разными PID. Оба продолжают выполнение с одной и той же строки — сразу после `fork()`.

---

## Как ядро создаёт копию

1. Ядро выделяет новую запись в таблице процессов — новый PID.
2. Копирует адресное пространство родителя (в реальности — через **copy-on-write**: физическая копия делается только когда один из процессов записывает в память).
3. Копирует открытые файловые дескрипторы, сигналы, окружение.
4. Возвращает управление обоим процессам.

---

## Возвращаемое значение — ключевое

```c
pid_t pid = fork();
```

| Где | Что вернул fork() | Значит |
|---|---|---|
| Родитель | PID дочернего (> 0) | "Я создал ребёнка с этим PID" |
| Дочерний | 0 | "Я — дочерний" |
| Ошибка | -1 | Лимит процессов, нет памяти |

Это единственный способ различить родителя и дочернего — по возврату `fork()`.

---

## Типичная структура кода

```c
pid_t pid = fork();

if (pid == -1) {
    perror("fork");
    exit(1);
}

if (pid == 0) {
    // === дочерний ===
    printf("child: pid=%d ppid=%d\n", getpid(), getppid());
    exit(0);
}

// === родитель ===
int status;
waitpid(pid, &status, 0);
printf("parent: child exited with code %d\n", WEXITSTATUS(status));
```

---

## Зомби и waitpid()

Когда дочерний завершается через `exit()`, он не исчезает сразу. Ядро оставляет запись с его exit code — ждёт пока родитель заберёт результат. Это состояние называется **зомби** (zombie, `Z` в `ps`).

`waitpid()` забирает этот результат и освобождает запись:

```c
// Ждать конкретного ребёнка
pid_t finished = waitpid(pid, &status, 0);

// Ждать любого ребёнка (кто первый завершится)
pid_t finished = waitpid(-1, &status, 0);
```

Если родитель завершится раньше дочернего — дочерний переходит к процессу `init` (PID 1). Это называется **orphan** (сирота). init всегда вызывает wait, поэтому зомби не остаются.

---

## Порядок выполнения после fork()

Планировщик ядра сам решает кому дать CPU — родителю или дочернему. Порядок вывода недетерминирован. Нельзя рассчитывать на то, что родитель или дочерний выполнится первым.

```
fork() → [родитель] [дочерний]  — оба готовы к выполнению
            ↓           ↓
         планировщик выбирает кого запустить
```

## Создание N дочерних процессов — почему два цикла

### Один цикл (неправильно для параллелизма)

```c
for (int i = 0; i < N; i++) {
    pid_t pid = fork();
    if (pid == 0) { /* работа */ exit(i); }
    waitpid(pid, &status, 0);  // ждём сразу
}
```

Временная линия:
```
spawn 0 → [child 0 работает] → child 0 умер → spawn 1 → [child 1 работает] → ...
```
Дети живут по одному. Следующий создаётся только после смерти предыдущего.

### Два цикла (правильно)

```c
pid_t pids[N];

// Фаза 1 — создаём всех детей
for (int i = 0; i < N; i++) {
    pids[i] = fork();
    if (pids[i] == -1) { perror("fork"); exit(1); }
    if (pids[i] == 0) {
        printf("[child %d] pid=%d ppid=%d\n", i, getpid(), getppid());
        exit(i);   // ОБЯЗАТЕЛЬНО — иначе дочерний продолжит цикл и сам начнёт форкать
    }
    // родитель: не ждём, идём форкать следующего
}

// Фаза 2 — собираем всех детей
for (int i = 0; i < N; i++) {
    int status;
    waitpid(pids[i], &status, 0);
    printf("[parent] child %d exited with code %d\n", pids[i], WEXITSTATUS(status));
}
```

Временная линия:
```
spawn 0
spawn 1    ← все трое существуют одновременно
spawn 2
         → waitpid 0
         → waitpid 1
         → waitpid 2
```

### Зачем это важно

Если каждый дочерний делает что-то долгое (сетевой запрос, чтение файла):
- Один цикл: 3с + 3с + 3с = **9 секунд**
- Два цикла: все трое параллельно = **~3 секунды**

В procfork дети моментально умирают — разница незаметна. Но структура та же что в реальных программах (веб-серверы, build-системы).

## Чтение status — только через макросы

`waitpid` записывает в `status` **bit-packed** структуру, где упакованы: код выхода, номер сигнала-убийцы, флаг "core dumped", флаг "stopped by signal". Прямое чтение как `int` — мусор.

| Макрос | Что проверяет / достаёт |
|---|---|
| `WIFEXITED(status)` | true если ребёнок завершился нормально через `exit()` |
| `WEXITSTATUS(status)` | код выхода (то что ребёнок передал в `exit(N)`); валиден только если `WIFEXITED == true` |
| `WIFSIGNALED(status)` | true если ребёнок убит сигналом |
| `WTERMSIG(status)` | номер сигнала-убийцы; валиден только если `WIFSIGNALED == true` |
| `WCOREDUMP(status)` | true если был сброшен core dump |
| `WIFSTOPPED(status)` | true если ребёнок остановлен (не завершён) — нужно `WUNTRACED` в `waitpid` |

```c
if (waitpid(pid, &status, 0) == -1) { perror("waitpid"); exit(1); }
if (WIFEXITED(status))
    printf("exit code = %d\n", WEXITSTATUS(status));
else if (WIFSIGNALED(status))
    printf("killed by signal %d\n", WTERMSIG(status));
```

## Частые ошибки

| Ошибка | Последствие |
|---|---|
| Нет `exit()` в дочернем | Дочерний продолжает цикл и сам форкает детей — форк-бомба |
| Нет `waitpid()` в родителе | Дочерние становятся зомби и держат PID до завершения родителя |
| Читать `wstatus` напрямую | Неверный exit code — нужен `WEXITSTATUS()` |
| `getppid()` вместо возврата `fork()` | Ловушка: `getppid()` это "**get parent** PID" — PID родителя текущего процесса (для `./a.out` это shell). Чтобы получить PID **только что созданного ребёнка** — только через возвращаемое значение `fork()` |
| Не проверять возврат `waitpid` | При ошибке (например `ECHILD` если ждёшь не своего ребёнка) `status` остаётся неинициализированным — читаешь мусор |
| `printf` без `\n` перед `sleep`/долгой операцией | stdout line-buffered на терминале → текст висит в буфере процесса до `\n` или `exit()`. Решение: либо `\n`, либо `fflush(stdout)`. На pipe/file даже `\n` не помогает (fully-buffered) — только `fflush` |
