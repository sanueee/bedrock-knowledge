# Системные вызовы / System calls

## Что это

Механизм через который user-space процесс просит ядро выполнить привилегированную операцию. **Не обычный вызов функции** — это смена режима процессора (CPU mode switch) с ring 3 (user) на ring 0 (kernel).

## Ключевые термины (English)

- **syscall** — system call, обращение к ядру из user space
- **user space** — режим CPU с ограниченными привилегиями, где живут процессы
- **kernel space** — режим CPU с полными привилегиями, где живёт ядро
- **ring 0 / ring 3** — уровни привилегий x86 CPU (0 = ядро, 3 = пользователь)
- **trap instruction** — машинная инструкция запускающая переход в kernel (`syscall` x86-64, `svc` ARM)
- **libc wrapper** — тонкая функция libc которая упаковывает аргументы и делает trap
- **errno** — глобальная переменная libc с кодом последней ошибки (не часть ядра)

## Как работает

1. Процесс в user space хочет ресурс который контролирует ядро (fd, память, сигнал).
2. libc-обёртка (например `read`) кладёт **номер сисколла** в `rax` и аргументы в `rdi, rsi, rdx, r10, r8, r9` (x86-64 ABI).
3. Выполняет инструкцию `syscall`. CPU:
   - Переключается в ring 0.
   - Прыгает в фиксированную точку входа ядра (`entry_SYSCALL_64`).
4. Ядро по номеру в `rax` находит обработчик в таблице сисколлов, вызывает его.
5. Обработчик выполняет работу (может спать, может потревожить hardware), кладёт результат в `rax`.
6. Возвращение через `sysret` — CPU обратно в ring 3, продолжение user-space кода.

Вся "обёртка" в libc — это ~5 ассемблерных инструкций. Реальная работа происходит за границей.

## Конвенция возврата: ядро vs libc

**Ядро возвращает отрицательный код ошибки** в `rax`:
- Успех — нормальное значение (например количество прочитанных байт).
- Ошибка — `-EINTR (-4)`, `-EPERM (-1)`, `-EAGAIN (-11)`, ... диапазон `-1` до `-4095`.

**glibc-конвенция** для user-facing функций:
- Если результат от `-1` до `-4095` — это ошибка.
- glibc кладёт `-result` в глобальную `errno`, возвращает `-1`.
- Поэтому в обычном коде ты пишешь `if (read(...) == -1) perror(...)`.

**musl-конвенция** для внутренних `__sys_*`:
- Возвращает отрицательный код напрямую (`-EINTR`).
- Не трогает `errno`.
- `errno` появляется только на user-facing границе (`read`, `write`).

Это видно в [[reading-01]]: `while ((r = __sys_wait4(...)) == -EINTR);` — сравнение с `-EINTR`, не `-1`.

## Пример из musl (reading-01)

```c
// pclose.c
while ((r = __sys_wait4(pid, &status, 0, 0)) == -EINTR);
```

`__sys_wait4` — это thin wrapper над сисколлом `wait4` (номер 61 на x86-64). Возвращает -EINTR напрямую, поэтому retry-loop проверяет именно это значение.

## Подводные камни

- **Сисколл может быть прерван сигналом** → возвращает `-EINTR`. Если signal handler без `SA_RESTART`, ядро **не** retry-ит автоматически. См. [[async-signal-safe]].
- **`errno` thread-local** в современных libc — но это libc-уровень, не ядерный. На уровне сисколла нет `errno`, есть только возвращаемое значение.
- **Количество сисколлов разное в разных архитектурах**. Номер `wait4` на x86-64 = 61, на ARM64 другой. Поэтому таблица в `<asm/unistd.h>` архитектурно-зависима.
- **vDSO** — некоторые "сисколлы" (`gettimeofday`, `clock_gettime`) ядро мапит в user space как обычный код, чтобы не делать trap. Это оптимизация — но программе это прозрачно.
