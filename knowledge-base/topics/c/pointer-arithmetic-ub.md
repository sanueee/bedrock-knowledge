# UB арифметики указателей + квалификаторы указателей / Pointer arithmetic UB & qualifiers

## Что это

Два «мылящих глаз» C-момента, всплывших на B-12 (`dnsquery.c`):
1. **Образование** указателя за пределы массива — undefined behavior (UB) **до всякого разыменования**.
2. Почему компилятор ругается на `char *` ↔ `const char *` / `char *` ↔ `uint8_t *`, если «в языке же есть неявные преобразования».

## Ключевые термины (English)

- **out-of-bounds pointer formation** — вычисление указателя за границей объекта; UB сам по себе.
- **one-past-the-end** — указатель ровно на элемент за последним: образовывать можно, разыменовывать нельзя.
- **qualifier conversion** — преобразование по `const`/`volatile`-квалификатору.
- **signedness mismatch** — разница знаковости (`char *` vs `unsigned char *`/`uint8_t *`).

## Как работает

### 1. UB не только на разыменовании

Распространённая ошибка mental model: «UB — это когда я *читаю* по битому указателю». На деле стандарт C (§6.5.6) разрешает арифметику указателя **только внутри** объекта-массива и **на one-past-the-end**:

```
[ answer[0] ... answer[n-1] ] answer+n
  └── читать можно (deref) ──┘  └─ образовать можно, читать НЕЛЬЗЯ
                                    answer+n+1 и дальше — UB уже на вычислении
```

Две отдельные границы:
- **разыменование `*p`** легально в `[base, base+size-1]`;
- **образование указателя** легально в `[base, base+size]` (шире на один — one-past-the-end).

`p + rdlength`, где `rdlength` — untrusted длина из сети (до 65535), а `p` внутри `answer[512]`, **образует** указатель далеко за концом → UB, даже если ты потом только сравниваешь его (`p + rdlength > end`) и не читаешь. Компилятор вправе предполагать, что UB не наступает, и «оптимизировать» проверку не так, как ты ждёшь.

**Правильно — сравнивать остаток, не образовывать заграничный указатель:**
```c
if (rdlength > (size_t)(end - p)) { /* malformed */ }
```
`end - p` определено: оба указателя in-bounds одного массива, разность даёт число оставшихся байт (`ptrdiff_t`). Дальше обычное целочисленное сравнение — никаких заграничных указателей.

Зачем стандарт так строг: на экзотических платформах (сегментная память, аппаратный bounds-check, provenance-tracking) даже вычисление невалидного адреса может дать trap или «отравить» указатель. Современные оптимизаторы используют это как гарантию.

### 2. Квалификаторы указателей — почему ругается

«Есть же неявные преобразования» — да, но они **однонаправленные по безопасности**:

| Из → в | Легально? | Почему |
|--------|-----------|--------|
| `char *` → `const char *` | ✅ да, неявно | добавить `const` безопасно: ты лишь *обещаешь* не менять |
| `const char *` → `char *` | ⚠️ warning/ошибка | снять `const` = потенциально нарушить обещание вызывающего |
| `char *` ↔ `uint8_t *` (`unsigned char *`) | ⚠️ разные типы | не про `const`, а про **знаковость**: `char`, `signed char`, `unsigned char` — три *разных* типа |

То есть если VS Code подсвечивает передачу `char *` в функцию, ждущую `const char *` — это **не** та ошибка (это как раз разрешено). Ругается обычно на:
- снятие `const` (передача `const char *` туда, где `char *`);
- знаковость (`char *` buffer против `uint8_t *` API, как при парсинге — там и брали `uint8_t[]`, чтобы `b<<8` не sign-extend'ился).

Практика для сетевого парсинга: буфер всегда `uint8_t *` (беззнаковый — байты не «отрицательные»), а функции, которые не мутируют вход, помечать `const` — тогда `char *`→`const` идёт молча, а компилятор ловит реальные нарушения.

## Пример (из B-12)

```c
// UB: p + rdlength образует заграничный указатель при untrusted rdlength
if (p + rdlength > end) { ... }          // ← неверно
if (rdlength > (size_t)(end - p)) { ... } // ← верно, сравниваем остаток

// skip_name: параметр не мутирует буфер → const; буфер беззнаковый
const uint8_t *skip_name(const uint8_t *p, const uint8_t *end);
```

## Подводные камни

- `p + n > end` с untrusted `n` — UB даже без разыменования. Всегда `n > end - p`.
- `end - p` определено, только если `p` и `end` в одном массиве (держи инвариант `p <= end`).
- `char` может быть signed → `buf[i] << 8` на байте ≥ 0x80 sign-extend'ится в мусор. Для парсинга — `uint8_t` буфер.
- Не «чинить» warning про `const` кастом `(char *)` — это глушит реальную диагностику.
