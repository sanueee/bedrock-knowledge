# Сон потока и Alarm Clock / timer_sleep & busy waiting (Pintos)

## Что это

`timer_sleep(ticks)` — функция, которая приостанавливает поток на заданное число тиков. В исходном Pintos она сделана через активное ожидание (busy waiting): поток в цикле отдаёт процессор и проверяет часы, оставаясь в очереди готовых. Задание Alarm Clock (проект 1) — переписать её так, чтобы спящий поток был заблокирован и не тратил процессор.

---

## Ключевые термины (English)

- **busy waiting** — активное ожидание: крутиться в цикле, проверяя условие, вместо блокировки
- **blocking** — блокировка: поток переводится в `THREAD_BLOCKED` и не выбирается планировщиком
- **wake-up time** — абсолютный тик, в который поток должен проснуться
- **sleep list** — список спящих потоков (в исходном Pintos его нет)
- **ordered insertion** — вставка в отсортированный список (`list_insert_ordered`)
- **lost wake-up** — потерянное пробуждение: сигнал «проснись» пришёл до того, как поток уснул
- **resolution** — разрешение таймера: минимальный измеримый интервал (1 тик = 10 мс)
- **real-time sleep** — сон в реальных единицах (мс/мкс/нс) с переводом в тики

## API таймера

```c
/* devices/timer.h */

/* 1. Узнать время */
int64_t timer_ticks (void);
int64_t timer_elapsed (int64_t);

/* 2. Уснуть, отдав процессор другим потокам */
void timer_sleep  (int64_t ticks);
void timer_msleep (int64_t milliseconds);
void timer_usleep (int64_t microseconds);
void timer_nsleep (int64_t nanoseconds);

/* 3. Активное ожидание — процессор НЕ отдаётся */
void timer_mdelay (int64_t milliseconds);
void timer_udelay (int64_t microseconds);
void timer_ndelay (int64_t nanoseconds);

/* 4. Статистика */
void timer_print_stats (void);
```

Группы 1, 2, 4 опираются на `ticks` ([[pintos-timer-ticks]]). Группа 3 и короткие вызовы группы 2 — на `loops_per_tick` ([[pintos-timer-calibrate]]).

## Как работает сейчас

```c
/* devices/timer.c:90 */
void
timer_sleep (int64_t ticks) 
{
  int64_t start = timer_ticks ();

  ASSERT (intr_get_level () == INTR_ON);
  while (timer_elapsed (start) < ticks) 
    thread_yield ();
}
```

Поток запоминает время старта и в цикле отдаёт процессор. Пока он в очереди, работают другие потоки, приходят прерывания, `ticks` растёт. Когда очередь дойдёт до спящего, он проверит часы; рано — снова `thread_yield`.

`ASSERT (INTR_ON)` — с выключенными прерываниями `ticks` не растёт, цикл был бы вечным.

### Почему это плохо

`thread_yield` кладёт поток в `ready_list` — **поток спит, но числится готовым**. Планировщик продолжает давать ему процессор, а поток тратит его на то, чтобы посмотреть на часы и уйти обратно.

Пример: 5 потоков вызвали `timer_sleep(100)`, больше работы нет.

```
ready_list: [T0, T1, T2, T3, T4, main]

T0: elapsed < 100 → yield → в конец
T1: elapsed < 100 → yield → в конец
...
main: ... → yield
T0: elapsed < 100 → yield            ← сотни тысяч раз за один тик
```

Последствия:

1. **Процессор загружен на 100 %** без полезной работы.
2. **Idle-поток никогда не запускается** — `ready_list` не пуст, `hlt` не вызывается. В статистике: `idle_ticks ≈ 0`, всё ушло в `kernel_ticks`.
3. **Единственный спящий поток** — `thread_yield` кладёт его в очередь и тут же достаёт (`cur == next`, переключения нет). Чистый холостой цикл.
4. **Ломаются приоритеты** (после Priority Scheduling): спящий высокоприоритетный поток постоянно выбирается первым и мешает реально занятым низкоприоритетным.

### Точность

Отсчёт идёт от тика, в котором был вызов, а вызов может случиться в любой момент внутри 10-мс интервала:

```
тик:      100            101            102            103
           │──────────────│──────────────│──────────────│
              ▲ вызов timer_sleep(2), start = 100
                                           ▲ проснётся не раньше тика 102
реально проспал:  от ~10 до ~20 мс (плюс ожидание в очереди)
```

Поэтому тест выравнивается на начало тика перед сном:

```c
/* tests/threads/alarm-priority.c:44 */
/* Busy-wait until the current time changes. */
int64_t start_time = timer_ticks ();
while (timer_elapsed (start_time) == 0)
  continue;

/* Now we know we're at the very beginning of a timer tick, so
   we can call timer_sleep() without worrying about races
   between checking the time and a timer interrupt. */
timer_sleep (wake_time - timer_ticks ());
```

## Alarm Clock: идея решения

Цель — **спящий поток не находится в `ready_list`**.

**В `timer_sleep`:**

1. Если `ticks <= 0` — сразу вернуться.
2. Вычислить **абсолютный** момент пробуждения `timer_ticks() + ticks`, сохранить в `struct thread`.
3. Выключить прерывания.
4. Добавить поток в список спящих (удобно — отсортированный по времени пробуждения).
5. `thread_block()` — статус `THREAD_BLOCKED`, планировщик забывает про поток.
6. Восстановить уровень прерываний.

**В `timer_interrupt`** — «будильник», вызывается каждый тик:

7. Пройти начало списка спящих: всем, у кого время пробуждения `<= ticks`, — удалить из списка и `thread_unblock()` (поток вернётся в `ready_list`).
8. На первом, кому рано, — остановиться (список отсортирован).

Пока все спят, `ready_list` пуст → работает idle → `hlt` → процессор действительно простаивает.

```
timer_sleep(50) в тик 1000              timer_interrupt, тик 1050
┌──────────────────────────┐            ┌──────────────────────────┐
│ wake = 1050              │            │ sleep_list: [T(1050),...] │
│ intr_disable             │            │ 1050 <= ticks → unblock   │
│ sleep_list += T (sorted) │            │ следующий > ticks → стоп  │
│ thread_block  ──────┐    │            └────────────┬─────────────┘
└─────────────────────┼────┘                         │
                      │  BLOCKED, не в ready_list    │ READY, в ready_list
                      └──────────── 50 тиков ────────┘
```

Решение не расписано кодом намеренно — это задание.

## Сон в реальных единицах: `msleep` / `usleep` / `nsleep`

Все три вызывают `real_time_sleep(num, denom)` — «спать `num/denom` секунд»:

```c
/* devices/timer.c:212 */
static void
real_time_sleep (int64_t num, int32_t denom) 
{
  int64_t ticks = num * TIMER_FREQ / denom;   // в тики, округление ВНИЗ

  ASSERT (intr_get_level () == INTR_ON);
  if (ticks > 0)
    timer_sleep (ticks);            // хотя бы один тик — нормальный сон
  else 
    real_time_delay (num, denom);   // меньше тика — активное ожидание по loops_per_tick
}
```

Реальные вызовы из драйвера диска:

| Вызов | Расчёт | Результат |
|---|---|---|
| `timer_msleep (150)` (`devices/ide.c:199`) | 150 · 100 / 1000 = **15 тиков** | `timer_sleep(15)` |
| `timer_msleep (10)` (`devices/ide.c:218`) | 10 · 100 / 1000 = **1 тик** | `timer_sleep(1)` |
| `timer_usleep (10)` (`devices/ide.c:194`) | 10 · 100 / 1 000 000 = **0 тиков** | `real_time_delay`, ~10 мкс |

Округление вниз: `timer_msleep(19)` = `timer_sleep(1)`.

## Задержки без сна: `mdelay` / `udelay` / `ndelay`

```c
/* devices/timer.c:144 */
void
timer_udelay (int64_t us) 
{
  real_time_delay (us, 1000 * 1000);
}
```

Никогда не зовут `timer_sleep` и не требуют прерываний. Нужны там, где спать нельзя: выключенные прерывания, обработчик, перезагрузка:

```c
/* devices/shutdown.c:68 — перезагрузка через контроллер клавиатуры */
for (i = 0; i < 0x10000; i++)
  {
    if ((inb (CONTROL_REG) & 0x02) == 0)
      break;
    timer_udelay (2);
  }
```

## Тесты alarm-*

| Тест | Что проверяет |
|---|---|
| `alarm-single` | 5 потоков спят по 1 разу, разная длительность — порядок пробуждения |
| `alarm-multiple` | то же, по 7 раз (`tests/threads/alarm-wait.c`) |
| `alarm-simultaneous` | несколько потоков просыпаются в **один и тот же** тик |
| `alarm-priority` | одновременно проснувшиеся запускаются в порядке приоритета |
| `alarm-zero` | `timer_sleep(0)` — сразу вернуться |
| `alarm-negative` | `timer_sleep(-100)` — не упасть |

`alarm-wait.c` проверяет инвариант: произведение «номер итерации × длительность» в порядке пробуждения не убывает.

## Подводные камни

- **Потерянное пробуждение (lost wake-up).** Если прерывание придёт между «добавил в список» и `thread_block`, обработчик разбудит ещё не уснувший поток: `thread_unblock` на `THREAD_RUNNING` → `ASSERT` падает, либо поток засыпает навсегда. Добавление и блокировку делать **с выключенными прерываниями**. `thread_block` сама это требует: `ASSERT (intr_get_level () == INTR_OFF)`.
- **Локи в `timer_interrupt`.** `lock_acquire`/`sema_down` в обработчике запрещены (он не может спать). Список спящих защищается выключением прерываний, не локом.
- **Долгий обработчик.** Проход по всему несортированному списку 100 раз в секунду с выключенными прерываниями — O(n) на тик. Отсортированный список + остановка на первом «рано» — O(k), где k — число просыпающихся.
- **Будить только одного.** Несколько потоков с одинаковым временем пробуждения — разбудить **всех** (`alarm-simultaneous`).
- **Относительное время в списке.** Хранить «сколько осталось спать» и уменьшать каждый тик — лишняя работа в обработчике. Хранить абсолютный тик.
- **`list_elem` занят.** `elem` в `struct thread` уже используется для `ready_list`/семафоров. Для списка спящих — либо отдельное поле `list_elem`, либо аккуратно учитывать, что заблокированный поток не лежит в `ready_list`.
- **`timer_sleep` с выключенными прерываниями** — нарушение `ASSERT (INTR_ON)`; вызывающий должен восстанавливать уровень.
- **Busy-wait дольше тика с выключенными прерываниями** (`mdelay`) — теряются тики.

### Безопасность

- **Знаковое переполнение.** `timer_ticks () + ticks` при огромном `ticks` (например, `INT64_MAX` из пользовательского аргумента будущего syscall) — UB в C; на практике время пробуждения станет отрицательным, и поток проснётся мгновенно или никогда. Ограничивать вход до сложения.
- **Busy waiting = DoS-примитив.** Исходная реализация позволяет любому числу спящих потоков занять процессор на 100 %. Корректная блокировка — не только производительность, но и изоляция.
- **Use-after-free в списке спящих.** Если поток завершится (`thread_exit`), оставшись в списке спящих, обработчик таймера обратится к освобождённой странице `struct thread`. Поток должен быть удалён из списка до уничтожения — в корректной реализации он в списке только пока заблокирован, а заблокированный поток не может выйти сам.
