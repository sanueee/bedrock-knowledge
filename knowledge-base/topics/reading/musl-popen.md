## Ключевые термины (English)

- **ofl** — open file list, глобальный связанный список (linked list) всех открытых stdio-FILE\* в процессе
- **mutex** — взаимная блокировка (mutual exclusion) для разделяемой структуры
- **fd inheritance** — наследование файловых дескрипторов ребёнком при `fork`
- **file actions** — структура с инструкциями для ребёнка в `posix_spawn` (close/dup2/open)
- **CLOEXEC (close-on-exec)** — флаг fd, заставляющий ядро автоматически закрывать fd при `execve`
- **EINTR (interrupted syscall)** — сисколл был прерван сигналом до завершения, нужен явный retry
- **SA_RESTART** — флаг `sigaction` который заставляет ядро автоматически перезапускать прерванные сисколлы
- **self-deadlock** — самоблокировка одного процесса из-за неправильного порядка освобождения ресурсов
- **refcount (reference count)** — счётчик ссылок на ресурс в ядре

## Архитектурный вывод 1 — три защитные техники против fd-наследования

При создании ребёнка через любую `fork`-семантику нужно контролировать **что именно унаследует ребёнок**. В popen.c видны все три классические техники одновременно:

| Техника | Что делает | Где в коде |
|---------|-----------|------------|
| Ранний `close` ненужного конца | Не дать fd попасть к ребёнку через fork | `posix_spawn_file_actions_adddup2` затем стандартный паттерн |
| `O_CLOEXEC` на pipe-fd | Ядро само закроет fd при успешном `execve` | `popen.c:27` — `pipe2(p, O_CLOEXEC)` |
| `addclose` в file_actions | Атомарное закрытие чужих fd у нового ребёнка через `posix_spawn` | `popen.c:37-39` — проход по ofl-списку |

### Сетап — почему addclose нужен

- P — родитель.
- C1 — первый popen-ребёнок (запущен `popen("cmd1", "w")`).
- C2 — второй popen-ребёнок (запущен `popen("cmd2", "w")`).

P держит два write-end pipe: `wfd1` (к C1) и `wfd2` (к C2). Без защиты при создании C2 он унаследует `wfd1`. Дальше:

1. P закрывает `wfd1` через `pclose(f1)`.
2. C1 ждёт EOF на своём read-end.
3. EOF не приходит — потому что **C2 держит wfd1**.
4. C1 не завершается. `pclose(f1)` виснет на `wait4`.

Решение musl: при создании каждого нового popen-ребёнка пройти по списку всех уже открытых popen-FILE и **сказать spawn'у явно**: "закрой эти fd у нового ребёнка до execve". Это делает строка:

```c
for (FILE *l = *__ofl_lock(); l; l=l->next)
    if (l->pipe_pid && posix_spawn_file_actions_addclose(&fa, l->fd))
        goto fail;
```

`l->pipe_pid != 0` — отличает popen-FILE от обычных fopen-FILE. Только pipe-fd нужно изолировать, не все stdio.

## Архитектурный вывод 2 — порядок fclose → wait4 в pclose

Сетап:
- P — родитель.
- C — ребёнок созданный `popen("./consumer", "w")`. P пишет в pipe, C читает stdin.

В `pclose.c` порядок такой:

```c
fclose(f);                                              // строка 9
while ((r=__sys_wait4(pid, &status, 0, 0)) == -EINTR);  // строка 10
```

**Сначала `fclose`, потом `wait4`. Поменять местами = self-deadlock.**

### Почему — пошагово при неправильном порядке (wait4 → fclose)

1. P-waiter уходит в `wait4` и засыпает в ядре.
2. P-writer всё ещё "должен" сделать `fclose`, но не может — поток заморожен в `wait4`.
3. У C `read()` блокирует в ожидании EOF.
4. EOF не наступает — refcount(wfd) в ядре = 1, потому что P-writer держит wfd.
5. C никогда не завершается.
6. P-waiter ждёт C вечно.

Это **не deadlock между двумя процессами**. Это **один тред, две роли (writer + waiter), неправильный порядок** — он застрял на первой роли и никогда не дойдёт до второй.

С правильным порядком (fclose → wait4):

1. `fclose(f)` синхронно за миллисекунду освобождает wfd. Refcount(wfd) → 0.
2. C получает EOF на следующем `read()`, выходит из цикла, делает `exit(0)`.
3. Только потом P-waiter уходит в `wait4`. Ребёнок уже завершён или вот-вот завершится.
4. `wait4` возвращается со статусом.

### Шире — где встречается этот паттерн

Порядок завершения двух ресурсов важен, когда один блокирует освобождение другого. Это всплывает в:

- socket close vs shutdown (FIN handshake)
- RAII destructors в Rust (порядок Drop)
- close файла после flush буфера
- pthread_join после pthread_cancel

Это **класс паттернов** — не разовая особенность popen.

## Архитектурный вывод 3 — EINTR retry вместо SA_RESTART

`__sys_wait4` — блокирующий сисколл. Если в P приходит сигнал с установленным handler'ом, ядро прерывает сисколл и возвращает `-EINTR`. Сисколл нужно повторить вручную.

Можно было бы поставить `SA_RESTART` на каждый signal handler — тогда ядро **само** перезапускает прерванные сисколлы. Но musl этого не делает:

> musl — библиотека. Она **не контролирует** какие флаги поставил пользователь на свои signal handlers. Может быть код, который намеренно ставит сигналы без SA_RESTART (чтобы `read()` от пользовательского ввода прерывался на Ctrl+C). Поэтому stdlib не полагается на флаги — она делает retry сама.

Это **defensive programming на уровне библиотеки**: не предполагать ничего о пользовательском коде, отрабатывать корректно при любых настройках.

Связь с [[signals-linux]]: `SA_RESTART` это контракт между пользователем и ядром. Внутри библиотечной функции этого контракта может и не быть.

## Архитектурный вывод 4 — открытый список stdio (ofl)

musl держит глобальный связанный список всех открытых через stdio FILE\* — это нужно чтобы `exit()` / `fflush(NULL)` могли пройтись по всем потокам и сбросить буферы.

```c
// src/stdio/ofl.c
static FILE *ofl_head;              // голова списка
static volatile int ofl_lock[1];    // futex-мьютекс защищающий список

FILE **__ofl_lock()
{
    LOCK(ofl_lock);                 // взять мьютекс
    return &ofl_head;               // вернуть указатель на голову
}
```

`__ofl_lock()` делает **две вещи в одном вызове**: захватывает мьютекс и возвращает указатель на голову. Парная `__ofl_unlock()` отпускает.

Этот же список используется в popen для прохода по всем уже открытых pipe-FILE (см. вывод 1).

Mutex нужен потому что список общий для всех тредов процесса — параллельные `fopen`/`fclose`/`popen` будут пытаться менять его одновременно. Это [[pthreads-linux]] mutual exclusion (взаимное исключение).

## Интересные приёмы

- **Возвращаемое значение `__sys_*` в musl** — отрицательное число с кодом ошибки (`-EINTR`, `-EPERM`), а не `-1`+глобальный errno как в glibc. Чище для library code, errno появляется только на user-facing границе.
- **Локирование + получение указателя в одной функции** (`__ofl_lock`) — стандартная защита от race condition: если бы пользователь сначала брал mutex, а потом сам читал указатель, можно было бы забыть взять mutex.
- **`pipe_pid != 0` как маркер** — поле в `FILE`, нулевое для обычных fopen, ненулевое для popen. Простой способ различать типы FILE без отдельного enum.
- **Кастомизируемый CLOEXEC через mode 'e'** — `popen.c:45-46`. Если в mode передан `'e'` — fd остаётся CLOEXEC (был установлен в pipe2). Иначе musl снимает флаг через `fcntl` для совместимости со старыми программами.
