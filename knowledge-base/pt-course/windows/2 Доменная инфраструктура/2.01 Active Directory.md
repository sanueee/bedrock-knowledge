# Active Directory

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 2: Доменная инфраструктура / Роли и сервисы Active Directory
>
> **Кейсы:** [3.10 DC](../../cases/windows/3.10%20DC.md), [3.11 IIS](../../cases/windows/3.11%20IIS.md), [3.12 AD CS](../../cases/windows/3.12%20AD%20CS.md)

В крупной компании с тысячами сотрудников администратору так или иначе приходится управлять доступом всех пользователей к компьютерам, принтерам и файлам. Новый сотрудник должен получить доступ ко всем нужным ресурсам автоматически, в первый же день работы, а смена пароля должна происходить на всех компьютерах одновременно. Все эти задачи решает одна технология - **Active Directory (AD)**. Это не просто "база данных пользователей" - это целая экосистема сервисов, которая является центральной нервной системой Windows-инфраструктуры в организациях по всему миру. **Active Directory Domain Services** (**AD DS**) - это служба, которая хранит информацию об объектах сети (пользователях, компьютерах, принтерах) и делает эти данные доступными для администрирования и аутентификации.

> **Аналогия:** крупную международную компанию можно представить так, что **Active Directory** - это единая база данных отдела кадров (кто работает), пропускная система (кто куда может заходить), внутренний телефонный справочник (где что находится) и служба безопасности (кто что делал) - всё в одном флаконе.

## Типы объектов Active Directory

**Active Directory** - это каталог объектов. Каждый объект представляет реальную сущность: человека, компьютер, принтер, политику. Понимание типов объектов и их атрибутов - основа работы с **AD**.

### Основные типы объектов

| Тип объекта | Что представляет | Ключевые атрибуты |
|---|---|---|
| User | Учётная запись человека | sAMAccountName , userPrincipalName , memberOf , passwordLastSet , lastLogon |
| Computer | Учётная запись компьютера в домене | dNSHostName , operatingSystem , lastLogon , servicePrincipalName |
| Group | Контейнер для пользователей, компьютеров и других групп | member , memberOf , groupType , groupScope |
| Organizational Unit (OU) | Контейнер для организации объектов внутри домена | linkedGroupPolicyObjects , managedBy |
| Group Policy Object (GPO) | Набор настроек, применяемых к пользователям и компьютерам | gPCFileSysPath (ссылка на SYSVOL ), versionNumber |
| Contact | Внешний контакт - не может входить в систему | mail , displayName , telephoneNumber |
| Shared Folder / Printer | Опубликованный в AD сетевой ресурс | uNCName , serverName |

Каждый объект в **AD** хранится как запись в базе **NTDS.DIT** и описывается набором атрибутов, определённых в схеме леса. Тип объекта (класс) задаётся атрибутом **objectClass**.

Просмотреть атрибуты любого объекта можно через **PowerShell** - для каждого типа объекта есть свой командлет:

| Задача | Команда |
|---|---|
| Атрибуты пользователя | Get-ADUser -Identity "username" -Properties * |
| Атрибуты компьютера | Get-ADComputer -Identity "PC01" -Properties operatingSystem, lastLogon |
| Все объекты в OU | Get-ADObject -SearchBase "OU=IT,DC=corp,DC=example,DC=com" -Filter * |

> Параметр **-Properties** позволяет командлентам возвращать набор выбранных атрибутов, а с звёздочкой ( ***** ) - весь набор, включая системные.

Среди всех типов объектов особого внимания заслуживают группы: именно через них строится вся модель разграничения доступа в домене, и именно в них чаще всего допускают ошибки при настройке.

### Группы: типы и области видимости

Группы - самый часто используемый и самый часто неправильно настраиваемый тип объекта. У групп есть два независимых параметра: **тип** и **область видимости**.

### Тип группы

| Тип | Назначение |
|---|---|
| Security | Используется для назначения прав доступа к ресурсам и применения политик. Это основной тип для администрирования. |
| Distribution | Используется только для почтовых рассылок (Exchange/Outlook). Нельзя использовать для назначения прав доступа. |

> **Частая ошибка:** создать **Distribution-группу** и пытаться дать ей права на папку. Windows проигнорирует такое назначение - только **Security-группы** учитываются при проверке доступа.

### Область видимости

Область видимости определяет, из каких доменов могут быть члены группы и где группа может быть использована для назначения прав.

| Область | Члены группы | Где можно назначить права | Типичное применение |
|---|---|---|---|
| Domain Local | Пользователи и группы из любого домена леса, а также внешних доменов | Только внутри своего домена | Назначение прав на локальные ресурсы: DL_FileServer_Read |
| Global | Только объекты из своего домена | В любом домене леса | Группировка пользователей по роли: G_Accountants |
| Universal | Объекты из любого домена леса | В любом домене леса | Группировка для многодоменных сред: U_AllManagers |

### Рекомендуемая модель: AGDLP

В корпоративных средах принята модель **AGDLP** (**A**ccounts → **G**lobal groups → **D**omain **L**ocal groups → **P**ermissions):

![](../../_images/a0546eb0f350.webp)

На первом шаге учётные записи пользователей (**Accounts**) объединяются в **Global-группы** по роли - например, все бухгалтеры попадают в **G_Accountants**. На втором шаге эта **Global-группа**, в свою очередь, добавляется как член в **Domain Local-группу**, привязанную к конкретному ресурсу, - **DL_Share_Finance_Read**. На третьем, финальном шаге права доступа к ресурсу назначаются именно **Domain Local-группе**, а не отдельным пользователям или **Global-группам** напрямую.

Такая цепочка позволяет легко управлять доступом: чтобы дать новому бухгалтеру доступ ко всем нужным папкам, достаточно добавить его в **G_Accountants** - права на все ресурсы применятся автоматически через вложенность групп.

### Управление группами через PowerShell

Практическая работа с моделью **AGDLP** начинается с создания **Global**-группы:

Дальнейшее управление группой сводится к паре типовых операций:

| Задача | Команда |
|---|---|
| Создание группы | New-ADGroup -Name "G_Accountants" -GroupScope Global -GroupCategory Security `
-Path "OU=Groups,DC=corp,DC=example,DC=com" |
| Добавить пользователя в группу | Add-ADGroupMember -Identity "G_Accountants" -Members "username1","username2" |
| Посмотреть вложенность групп пользователя | Get-ADUser "username" -Properties MemberOf | Select-Object -ExpandProperty MemberOf |

Модель **AGDLP** описывает, как права распределяются внутри одного домена. Но реальная инфраструктура редко ограничивается одним доменом - крупные организации строят целую иерархию из лесов, доменов и организационных подразделений, и именно эта иерархия определяет границы административного управления.

## Домен, Лес и OU: Три уровня иерархии Active Directory

Архитектура **AD DS** строится на трёх фундаментальных уровнях абстракции, которые позволяют гибко управлять даже самой сложной инфраструктурой. Каждый уровень решает свои задачи, имеет свои границы и свои механизмы безопасности.

> **Аналогия для понимания:** три уровня иерархии AD можно сравнить с устройством крупной международной корпорации.
> 
> 
> 
> **Forest** - это вся корпорация целиком, со своим уставом, правилами безопасности и общей стратегией. Это граница, за которую никто не может зайти без ведома владельца.
> 
> 
> 
> **Domain** - это отдельный региональный филиал (например, "Европа" или "Азия"). У каждого филиала свой директор, свои локальные правила найма, но все они подчиняются общей стратегии корпорации. Администратор из Европы по умолчанию не может уволить сотрудника в Азии.
> 
> 
> 
> **Organizational Unit (OU)** - это отдел внутри филиала ("Бухгалтерия", "IT"). Начальник отдела может сбросить пароль своему сотруднику, но не может уволить сотрудника из другого отдела.

### 1. Лес: Абсолютная граница безопасности

**Лес** - это самый верхний уровень иерархии **Active Directory**. Это граница безопасности, административного управления и доверия. Лес представляет собой совокупность всех доменов, у которых есть своя схема доверия между собой.

**Особенности леса:**

| Характеристика | Описание | Ключевой смысл |
|---|---|---|
| Единая схема (Schema) | В лесу существует одна схема - она определяет, какие типы объектов ("пользователь", "компьютер", "группа") и какие атрибуты (поля) у них могут быть | Изменение схемы (добавление нового атрибута для пользователя) коснётся всех доменов леса. Изменить схему может только член группы Schema Admins |
| Единая конфигурация (Configuration Partition) | Вся конфигурация леса (топология сайтов, список всех контроллеров доменов, список доверительных отношений) хранится в одной базе данных и реплицируется на все контроллеры доменов леса | Разные "топологии" для разных доменов внутри одного леса невозможны. Конфигурация едина |
| Автоматические доверительные отношения | Между доменами внутри одного леса по умолчанию автоматически создаются двусторонние транзитивные доверительные отношения | Пользователь из DomainA может получить доступ к ресурсу в DomainB (двусторонность). А через DomainB - в DomainC (транзитивность), без каких-либо дополнительных настроек |
| Единый глобальный каталог (Global Catalog, GC) | Глобальный каталог - это "справочник" по основным объектам всего леса. Не каждый контроллер домена обязан быть GC , но в каждом лесу хотя бы один DC должен быть GC | Пользователь из DomainA может найти пользователя из DomainB в адресной книге Outlook, потому что GC хранит основные атрибуты всех пользователей леса |

**Группы с правами на уровне леса:**

| Группа | Что может делать |
|---|---|
| Enterprise Admins | Единственная группа, которая имеет права на уровне всего леса. Может устанавливать новый домен, изменять схему, назначать администраторов доменов. Самый привилегированный доступ в инфраструктуре |
| Schema Admins | Может изменять схему леса (добавлять/изменять типы объектов и их атрибуты) |

> **Enterprise Admins** не подходит для повседневной работы администратора. Она должна использоваться **строго** для задач изменения самой **AD**-инфраструктуры (установка нового домена, миграция, изменение схемы). Иначе это эквивалентно тому, чтобы дать ключ от сейфа компании курьеру.

Несколько лесов имеют смысл в нескольких ситуациях. Организационная граница безопасности требуется, когда две дочерние компании не доверяют друг другу и их IT-отделы не должны иметь никакого административного доступа к инфраструктуре друг друга. Изоляция от экспериментов позволяет "сломать" тестовый лес, не боясь повлиять на продуктивный. Разная топология репликации нужна, если удалённый офис с плохим каналом связи требует отдельной настройки репликации.

Лес задаёт внешнюю границу безопасности, но внутри этой границы основная единица администрирования - уже не лес, а домен.

### 2. Домен: Единица административного управления

**Домен** - это логическая группа объектов (пользователей, компьютеров, групп), которую можно администрировать как единое целое. Домены существуют **внутри** леса. Лес может состоять из одного домена или из многих.

**Особенности домена:**

| Характеристика | Описание | Ключевой смысл |
|---|---|---|
| Административная изоляция | Администратор домена ( Domain Admins из DomainA ) не имеет прав по умолчанию в соседнем домене DomainB | Это позволяет передавать управление филиалом местному IT-отделу, не давая им влияния на головной офис |
| Политики уровня домена | Настройки, такие как политика паролей (сложность, срок действия, блокировка), применяются на уровне домена и действуют для всех объектов внутри него | В одном домене не может действовать требование к паролю "10 символов" для "бухгалтеров" и "5 символов" для "гарантийного отдела" одновременно. Политика одна на весь домен. Если нужны разные политики - используются Fine-Grained Password Policies (FGPP) , но это более сложный механизм |
| Автономность репликации | Репликация данных между контроллерами домена ( nTFRS или DFS-R ) настраивается на уровне домена | Скорость и топологию репликации можно настроить для DomainA независимо от того, как она настроена в DomainB - у каждого домена свои параметры сайтов и расписание репликации |
| Уникальный идентификатор (DNS-имя) | Каждый домен имеет уникальное DNS-имя (например, DomainA.com , DomainB.com ) | Компьютеры ищут контроллеры домена именно по этим DNS-именам |

**Группы с правами на уровне домена:**

| Группа | Что может делать |
|---|---|
| Domain Admins | Имеет полный административный контроль над всеми объектами в домене (пользователи, компьютеры, группы, OU). Может изменять политики домена. Автоматически входит в локальную группу Administrators на всех компьютерах домена. Не имеет прав по умолчанию в других доменах леса |
| Account Operators | Может создавать, удалять и изменять учётные записи пользователей и групп. Не имеет прав на управление группами Domain Admins и другими привилегированными группами |
| Server Operators | Может входить на серверы домена интерактивно, создавать/удалять общие ресурсы, выполнять резервное копирование, останавливать и запускать службы |
| Print Operators | Может управлять принтерами в домене (добавлять, удалять, настраивать) |
| Backup Operators | Может выполнять резервное копирование и восстановление файлов на контроллерах домена, обходя стандартные NTFS -разрешения |
| Administrators (локальная группа на каждом компьютере) | Даёт локальный административный доступ только к одному компьютеру. Не путать с Domain Admins . Группа Domain Admins автоматически входит в Administrators на всех компьютерах своего домена |

> **Пример:**
> Корпорация **example** имеет лес **example.com**. Внутри леса выделен домен **corp.example.com** для центрального офиса в США, администраторы которого управляют своими серверами и сотрудниками, и домен **emea.example.com** для европейского филиала. Администратор из **corp.example.com** не может по умолчанию зайти на контроллер домена **emea.example.com**, и наоборот.

Домен задаёт границу администрирования между филиалами, но внутри самого домена тоже нужна структура - именно эту задачу решает третий, самый гибкий уровень иерархии.

### 3. Organizational Unit (OU): Гибкий контейнер для политик и делегирования

**OU** - это самый гибкий и практичный инструмент для администрирования **внутри** домена. **OU** - это контейнер, который может содержать пользователей, группы, компьютеры и даже другие **OU**. **OU** не являются "мини-доменами" и не имеют своих политик паролей.

**Особенности OU:**

| Характеристика | Описание | Ключевой смысл |
|---|---|---|
| Делегирование прав (Delegation of Control) | OU - это основной инструмент, чтобы дать возможность, например, начальнику отдела сбрасывать пароли только своим сотрудникам, не давая ему прав на всю компанию | Часть административных задач "спускается" на уровень ниже, разгружая центральную службу поддержки |
| Применение групповых политик (Group Policy Objects, GPO) | Если нужно, чтобы для бухгалтеров работала одна политика (например, ограничения на установку ПО), а для программистов - другая, их помещают в разные OU , к которым "привязывают" свои GPO | Это позволяет точечно управлять настройками компьютеров и пользователей у разных отделов |
| Вложенность | OU могут содержать другие OU | Можно создать иерархию: Company\EMEA\Finance\Users и Company\EMEA\Finance\Computers |
| Не являются границей безопасности | Пользователь, имеющий права на чтение в одной OU , по умолчанию не имеет прав на чтение в соседней OU . Но: Администратор домена ( Domain Admins ) имеет права на все OU в домене | OU не защищают от компрометации учетной записи администратора домена |

**Практические примеры использования OU:**

| Сценарий | Действие | Результат |
|---|---|---|
| Сброс паролей для HR | Делегировать группе HR_Admins право "Сброс паролей" на OU HR_Users | Сотрудник HR может сбросить пароль новому сотруднику, но не может удалить его из AD или изменить права |
| Настройка экрана блокировки для маломощных компьютеров | Создать OU LowEndComputers , переместить туда старые ПК. Привязать GPO , которая отключает визуальные эффекты и устанавливает короткий таймаут блокировки | Пользователи на старых ПК работают быстрее, а на мощных - видят "красивую" Windows |
| Разные обои для разных отделов | Создать GPO на OU Sales (обои - логотип отдела продаж) и другую GPO на OU IT (обои - чёрный экран с текстом) | Пользователи в каждом отделе видят свои обои |

**Административные инструменты для работы с OU:**

Для создания, перемещения и настройки **OU**, пользователей и групп используется графический интерфейс **Active Directory Users and Computers** (**ADUC**, **dsa.msc**), который требует **Remote Server Administration Tools** (**RSAT**) на рабочей станции администратора. Для автоматизации тех же операций применяется **PowerShell**-модуль **ActiveDirectory**:

| Задача | Команда |
|---|---|
| Создать новую OU | New-ADOrganizationalUnit -Name "IT" -Path "DC=corp,DC=example,DC=com" |
| Переместить пользователя в OU | Move-ADObject -Identity "CN=username,CN=Users,DC=corp,DC=example,DC=com" -TargetPath "OU=IT,DC=corp,DC=example,DC=com" |
| Получить все GPO, привязанные к OU | Get-GPInheritance -Target "OU=IT,DC=corp,DC=example,DC=com" |

**Чего НЕЛЬЗЯ делать с OU:**

Политику паролей нельзя применить отдельно к **OU**, поскольку это настройка уровня домена, - если нужны разные политики паролей для разных групп, используются **Fine-Grained Password Policies**. Также не стоит рассматривать **OU** как "домен в миниатюре": **Domain Admins** всегда имеет права на все **OU** в домене.

### Взаимосвязь: Таблица сравнения

| Характеристика | Лес | Домен | OU |
|---|---|---|---|
| Граница чего | Безопасности, доверия, репликации схемы | Административной изоляции, политики паролей, репликации | Делегирования прав, применения GPO |
| Ключевые группы | Enterprise Admins , Schema Admins | Domain Admins | Нет встроенных . Создаются администратором |
| Транзитивные доверия между доменами | Автоматические между всеми доменами внутри леса | Только вручную между доменами разных лесов | Не применимо. Доверия существуют только между доменами |
| Политика паролей | Отсутствует, наследуется от политик доменов | Одна на весь домен (или FGPP ) | Нельзя применить отдельную политику паролей |
| Основной инструмент администратора | Active Directory Domains and Trusts ( domain.msc ) + PowerShell | Active Directory Users and Computers ( dsa.msc ) + PowerShell | Active Directory Users and Computers + Group Policy Management Console ( gpmc.msc ) |

### Пример иерархии в реальной компании

Собрать все три уровня в единую картину помогает пример условной корпорации **example**, которая владеет одним лесом из трёх доменов.

![](../../_images/46153d3e00e9.webp)

Читать эту схему нужно от корня к листьям. На верхнем уровне находится единственный лес **example.com** - общая граница безопасности и схемы для всей корпорации. Внутри леса выделены три домена: **corp.example.com** для головного офиса в США, а также **emea.example.com** и **asia.example.com** для европейского и азиатского филиалов - каждый со своей административной изоляцией и собственной политикой паролей. Внутри домена **corp.example.com** объекты дополнительно разложены по **OU**: серверы отделены от рабочих станций и учётных записей пользователей, а внутри каждой из этих веток есть более узкие **OU** под конкретные отделы, к которым привязаны свои **GPO** и делегированные права - например, сброс паролей для **IT_Users** или отдельные ограничения для компьютеров бухгалтерии.

Такая трёхуровневая структура - **лес, домен, OU** - вместе с объектами и группами, рассмотренными в начале статьи, формирует полную картину того, как устроена **Active Directory**. Понимание этих базовых элементов - объектов, их типов, групп и уровней иерархии - необходимая основа для дальнейшего изучения более сложных тем: групповых политик, механизмов аутентификации и репликации, к которым мы перейдём в следующих статьях.
