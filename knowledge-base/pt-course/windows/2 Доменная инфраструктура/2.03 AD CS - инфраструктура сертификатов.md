# AD CS - инфраструктура сертификатов

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 2: Доменная инфраструктура / Роли и сервисы Active Directory
>
> **Кейсы:** [3.10 DC](../../cases/windows/3.10%20DC.md), [3.11 IIS](../../cases/windows/3.11%20IIS.md), [3.12 AD CS](../../cases/windows/3.12%20AD%20CS.md)

**AD CS** - это служба развёртывания собственной **инфраструктуры открытых ключей** (**PKI**). Она выпускает, отзывает и обновляет цифровые сертификаты внутри организации.

## Зачем нужен AD CS

Сертификаты, которые выпускает **AD CS**, используются в самых разных сценариях: для **TLS/SSL**, для безопасного удалённого доступа через **VPN** с сертификатами, для шифрования файлов (**EFS**), для аутентификации по смарт-картам и для подписи кода. Такое разнообразие применений делает **AD CS** одним из самых часто встречающихся компонентов инфраструктуры - и одновременно источником потенциальных уязвимостей, если сертификаты настроены и выданы неправильно.

Центральную роль в том, какие сертификаты и кому будут выданы, играют шаблоны сертификатов - именно их настройка определяет, останется AD CS безопасным компонентом или превратится в путь для повышения привилегий в домене.

## Шаблоны сертификатов

**Certificate Templates** - это "формы", которые администратор заполняет один раз, а система потом штампует сертификаты по ним. Рассмотрим это на примере: в компании часть сотрудников работает удалённо и подключается к сети через **VPN**. Пароли для такого подключения - слабое звено: их можно подобрать или перехватить, поэтому принимается решение перейти на аутентификацию по сертификатам, которые выдаются на смарт-карты сотрудников. Именно эта задача и определяет, какие поля должны быть заполнены в шаблоне сертификата.

Поскольку сертификат нужен именно для входа в сеть, а не для подписи документов или шифрования почты, в **EKU** указываются только **Smart Card Logon** и **Client Authentication** - использование сертификата для других целей не предусмотрено. Имя владельца в сертификате должно совпадать с реальной учётной записью сотрудника в домене, поэтому **Subject Name** строится из данных **AD**, а не вводится самим заявителем - это исключает ситуацию, когда пользователь мог бы вписать себе произвольное имя. Доступ к **VPN** нужен не всем сотрудникам компании, а только тем, кто оформлен как удалённый работник, поэтому право на **Enroll** выдаётся не всем аутентифицированным пользователям домена, а конкретной группе безопасности "Удалённые сотрудники". Так как смарт-карты сотрудникам физически выдаёт ИТ-отдел, а не они получают сертификат самостоятельно за компьютером, в шаблоне включается требование **Authorized Signature** - заявку должен подтвердить сотрудник ИТ-отдела, обладающий ролью **Enrollment Agent**.

То, как настроен шаблон, напрямую отражается на полях уже выпущенного сертификата:

| Поле сертификата | Значение в примере с VPN |
|---|---|
| Subject | CN =Иванов Иван, OU =Удалённые сотрудники, DC =domain, DC =local |
| Subject Alternative Name (SAN) | Иванов Иван ( UPN : ivanov@domain.local ) - подставлено автоматически из AD |
| Enhanced Key Usage (EKU) | Smart Card Logon, Client Authentication |
| Issuer | CA компании ( Issuing CA ) |
| Public Key | RSA 2048 бит, сгенерирован на смарт-карте |
| Validity Period | 1 год (согласно сроку действия шаблона) |
| Template Name | VPN-SmartcardLogon (дубликат Smartcard Logon ) |

На примере видно, что настройка шаблона складывается из нескольких параметров - от них зависит, кто и как сможет получить сертификат:

| Параметр в шаблоне | Что определяет |
|---|---|
| EKU | Для чего можно использовать сертификат ( Client Authentication, Smart Card Logon, Code Signing и др.) |
| Subject Name | Как определяется имя владельца сертификата. Может быть "построено из AD " или "предоставлено заявителем (запросчик сам указывает SAN )" |
| Enrollment Rights | Кто имеет право запрашивать сертификаты по этому шаблону |
| Manager Approval | Требуется ли одобрение менеджера перед выдачей сертификата |
| Authorized Signatures | Требуется ли подпись уполномоченного лица ( Enrollment Agent ) |

Когда один или несколько из этих параметров настроены небезопасно, шаблон становится основой для целого семейства атак повышения привилегий.

## Семейство ESC-атак (Enterprise Subordinate CA)

Систематизированное семейство методов атак **Enterprise Subordinate CA** (**ESC**) было исследовано SpecterOps в 2021 году и позже дополнено. Суть - в неправильной конфигурации **AD CS**, которая позволяет повышать привилегии в домене.

### ESC1: Кража личности через указание произвольного SAN

Самая опасная и известная уязвимость семейства. Злоумышленник может получить сертификат на имя администратора домена.

Для эксплуатации должны совпасть четыре условия:

1. Шаблон разрешает аутентификацию (**EKU = Client Authentication, Smart Card Logon** или **Any Purpose**)
2. Заявитель может запрашивать сертификат без одобрения менеджера
3. Шаблон имеет флаг **CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT**, позволяющий заявителю самому указать **Subject Alternative Name** (**SAN**)
4. У злоумышленника есть права на запрос по этому шаблону

Атака выполняется одной командой - атакующий просто передаёт параметр **-upn** с именем администратора, и сервер выдаёт ему действующий сертификат, с которым можно пройти аутентификацию: `certipy req -u "user" -p "pass" -dc-ip "IP_DC" -target "CA_SERVER" -template "VULN_TEMPLATE" -upn "administrator@domain.local"`

Результат - получение **TGT** от имени администратора домена и полный контроль над доменом.

**ESC1** требует, чтобы шаблон разрешал заявителю указывать **SAN**. Следующая уязвимость встречается там, где шаблон вообще не ограничивает назначение сертификата.

### ESC2: Швейцарский нож (Any Purpose)

Шаблон имеет **EKU** "**Any Purpose**" или не определяет **EKU** вовсе, что эквивалентно "**Any Purpose**". Такой сертификат можно использовать для аутентификации, подписи кода, шифрования - для всего.

Атака заключается в том, чтобы запросить сертификат с шаблона, не требующего одобрения, а затем использовать полученный сертификат для аутентификации от имени пользователя.

**ESC1** и **ESC2** эксплуатируют один шаблон напрямую. **ESC3** устроен сложнее - он использует один сертификат, чтобы получить право выпускать другие.

### ESC3: Цепочка из двух сертификатов

Существует шаблон с **EKU** "**Certificate Request Agent**". Этот **EKU** позволяет использовать сертификат для запроса других сертификатов от имени другого пользователя.

Атака проходит в два шага: сначала атакующий получает сертификат **Enrollment Agent** по уязвимому шаблону с **EKU** "**Certificate Request Agent**", а затем, используя этот сертификат, запрашивает другой сертификат для аутентификации, указав в **SAN** имя администратора.

**ESC1-ESC3** эксплуатируют шаблоны, которые изначально настроены небезопасно. Но шаблон можно сделать уязвимым и постфактум, если у атакующего есть права его редактировать.

### ESC4: Уязвимый контроль доступа к шаблонам

Атакующий имеет права на запись в объект **Certificate Template** в **Active Directory**.

Атака сводится к изменению настроек существующего шаблона - например, добавлению флага **ENROLLEE_SUPPLIES_SUBJECT** или разрешению аутентификации. После модификации шаблон становится уязвимым для **ESC1**, и атакующий запрашивает сертификат администратора.

**ESC4** меняет права на конкретном шаблоне. Похожая логика применима и к другим объектам инфраструктуры **PKI** за пределами самих шаблонов.

### ESC5: Уязвимый контроль доступа к объектам PKI

Атакующий имеет права на запись в другие объекты инфраструктуры **PKI** - контейнеры **AD**, групповые политики, объекты сервера **CA**.

Атака заключается в изменении прав доступа к **CA**, включении флага **EDITF_ATTRIBUTESUBJECTALTNAME2** в настройках CA и отключении проверки политик. Результат - возможность запросить любой сертификат.

Флаг **EDITF_ATTRIBUTESUBJECTALTNAME2**, упомянутый в **ESC5**, заслуживает отдельного разбора - он достаточно опасен, чтобы стать самостоятельным вектором атаки.

### ESC6: EDITF_ATTRIBUTESUBJECTALTNAME2

Флаг **EDITF_ATTRIBUTESUBJECTALTNAME2** настройки **CA** отключён по умолчанию. Если он включён, **CA** позволяет заявителю указать произвольный **SAN** в любом запросе, даже если сам шаблон это не разрешает.

Атака работает даже против правильно настроенного шаблона (без **ENROLLEE_SUPPLIES_SUBJECT**): атакующий включает **SAN** в запрос **CSR**, и **CA** его принимает. Уязвим любой шаблон с **Client Authentication**.

**ESC5** и **ESC6** требуют прав на изменение настроек **CA**. Тот же результат достигается и без изменения флагов - если у атакующего есть привилегированная роль непосредственно на самом **CA**.

### ESC7: Уязвимый контроль доступа к CA

Атакующий имеет привилегированные роли на **CA**: **ManageCA** (управление конфигурацией) или **ManageCertificates** (управление и выдача сертификатов).

Роль **ManageCA** позволяет включить **ESC6** или **ESC11**, а затем получить сертификат администратора через открывшийся шаблон. Роль **ManageCertificates** даёт другой путь: отправить запрос на сертификат, который требует одобрения менеджера, а затем одобрить свой же запрос через эту же роль.

**ESC1-ESC7** требуют определённых прав внутри **AD** или на **CA**. Следующая атака работает иначе - она эксплуатирует не права, а протокол аутентификации веб-интерфейса регистрации.

### ESC8: NTLM Relay на HTTP

Интерфейсы веб-регистрации **AD CS** (например, **/certsrv/**) настроены на аутентификацию по **NTLM**.

Атака заключается в том, чтобы заставить привилегированного пользователя (администратора домена) открыть веб-страницу, которая отправляет **NTLM**-аутентификацию на подконтрольный атакующему сервер. Злоумышленник ретранслирует полученный **NTLM**-хеш к **CA** и получает сертификат администратора.

**ESC8** эксплуатирует протокол передачи учётных данных. Следующие две уязвимости, **ESC9** и **ESC10**, работают на уровне того, как контроллер домена сопоставляет сертификат с учётной записью.

### ESC9: No Security Extension

Версия шаблона - 1, самая старая. Такие шаблоны имеют флаг **CT_FLAG_NO_SECURITY_EXTENSION** и не добавляют в сертификат расширение с **SID** заявителя. Если на контроллерах домена включено слабое сопоставление (**StrongCertificateBindingEnforcement ≤ 1**), **KDC** доверяет полю **UPN** из сертификата вместо **SID**.

Атака проходит в четыре шага: атакующий временно меняет атрибут **userPrincipalName** своей учётной записи на **UPN** целевого администратора, затем запрашивает сертификат по шаблону версии 1 (**CA** автоматически подставит подменённый **UPN** в поле **SAN**), после этого возвращает свой **UPN** в исходное состояние и, наконец, использует полученный сертификат для аутентификации от имени администратора (**Pass-the-Certificate**).

**ESC9** эксплуатирует конкретно старую версию шаблона. **ESC10** работает шире - через общую настройку сопоставления сертификатов на контроллерах домена, независимо от версии шаблона.

### ESC10: Weak Certificate Mappings

На контроллерах домена ослаблены механизмы маппинга сертификатов. Это происходит, когда параметр **StrongCertificateBindingEnforcement** установлен в **0** или **1** (**Compatibility Mode**), а **CertificateMappingMethods** включает бит **UPN mapping** (**0x04**). В такой конфигурации **KDC** и **Schannel** доверяют полю **UPN** в сертификате вместо строгой проверки по **SID**. Параметр **StrongCertificateBindingEnforcement** = **2** (**Full Enforcement**) блокирует атаку.

Атака повторяет логику **ESC9,** но работает через любой подходящий шаблон: атакующий временно меняет атрибут **userPrincipalName** учётной записи, над которой у него есть контроль (**GenericWrite**), на **UPN** целевого привилегированного пользователя, затем запрашивает сертификат по любому шаблону, разрешающему аутентификацию (**Client Authentication**) - **CA** автоматически подставит подменённый **UPN** в поле **SAN** сертификата, - после этого возвращает **UPN** своей учётной записи в исходное состояние и, наконец, использует полученный сертификат для аутентификации от имени цели (**Pass-the-Certificate**) через **Kerberos PKINIT** или **LDAPS**.

**ESC9** и **ESC10** подделывают привязку сертификата к личности через **UPN**. **ESC11** действует на другом уровне - атакует сам протокол, по которому клиент обращается к **CA**.

### ESC11: Relayed NTLM to ICPR

Атака на **NTLM** на **DCOM**-интерфейс **CA**. Требует того же трюка с принуждением привилегированного пользователя к аутентификации, что и **ESC8**, но использует другой транспортный протокол - **ICPR** через **DCOM** вместо **HTTP**.

**ESC1-ESC11** так или иначе эксплуатируют настройки **AD**, шаблонов или протоколов. **ESC12** стоит особняком - это уязвимость конкретного аппаратного решения для хранения ключей **CA**.

### ESC12: YubiHSM Key Storage Provider

При использовании **YubiHSM 2** в качестве хранилища ключей **CA** пароль доступа к **HSM** сохраняется в открытом виде в реестре Windows. Злоумышленник с любым доступом к серверу **CA**, даже непривилегированным, может извлечь этот пароль и, имея физический доступ к такому же устройству **YubiHSM**, сгенерировать поддельные сертификаты от имени **CA**.

Атака проходит в три шага: получить доступ (**shell**) к серверу **CA**, прочитать значение **AuthKeysetPassword** из ветки реестра **HKEY_LOCAL_MACHINE\SOFTWARE\Yubico\YubiHSM\**, и, используя извлечённый пароль, выпустить произвольные сертификаты.

Последняя уязвимость семейства возвращается к настройкам **AD**, но эксплуатирует не сам шаблон, а связанную с ним политику выдачи.

### ESC13: Issuance Policy с привязкой к группе

Существует политика выдачи (**Issuance Policy**) с привязкой к группе **AD**, настроенная на шаблоне, где атакующий имеет права на запрос.

Атака заключается в запросе сертификата, в котором атакующий указывает **OID** этой политики. После выдачи и аутентификации с этим сертификатом система добавляет атакующего в соответствующую группу.

Диапазон **ESC1-ESC13** покрывает все компоненты инфраструктуры **AD CS** - от неправильно настроенных шаблонов до целых **CA**. Ошибки конфигурации **AD CS** - одна из самых опасных уязвимостей в современных доменах, так как злоумышленники получают доступ к сертификатам, которые система воспринимает как "абсолютно доверенные".

## Рекомендации по защите AD CS

Большая часть перечисленных атак закрывается одним и тем же набором организационных и технических мер:

| Мера | Зачем нужна |
|---|---|
| Отключить HTTP -эндпоинты AD CS | Использовать только HTTPS для процесса регистрации - закрывает NTLM Relay через HTTP ( ESC8 ) |
| Отключить NTLM на CA | Настроить IIS -приложения CA на принудительную аутентификацию Kerberos |
| Включить Extended Protection for Authentication ( EPA ) | Защита от NTLM Relay атак |
| Убрать флаг ENROLLEE_SUPPLIES_SUBJECT | Если флаг нельзя убрать - включить обязательное утверждение менеджера ( CA Certificate Manager Approval ) |
| Ограничить права на запрос | Выдавать права только необходимым группам, а не всем аутентифицированным пользователям |
| Мониторить события | Event ID 4886 ( Certificate Services received a certificate request ); проверять SAN -поля - признак ESC1 |

**AD CS** расширяет возможности инфраструктуры, но каждый неправильно настроенный шаблон или ослабленная проверка на **CA** потенциально превращается в путь к полному контролю над доменом - поэтому шаблоны сертификатов заслуживают такого же строгого аудита, как и права в самой **Active Directory**.
