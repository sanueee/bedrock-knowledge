# AD DS - сердце инфраструктуры

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 2: Доменная инфраструктура / Роли и сервисы Active Directory
>
> **Кейсы:** [3.10 DC](../../cases/windows/3.10%20DC.md), [3.11 IIS](../../cases/windows/3.11%20IIS.md), [3.12 AD CS](../../cases/windows/3.12%20AD%20CS.md)

**AD DS** - это "сердце" и основа всей инфраструктуры. Эта служба хранит каталог (имена, пароли, группы) и предоставляет службы аутентификации (**Kerberos KDC**) и авторизации. Именно с ней работают администраторы, создавая пользователей и настраивая **Group Policy.**

## Что делает AD DS

| Характеристика | Описание |
|---|---|
| Хранилище идентичностей | Содержит все объекты домена: пользователей, компьютеры, группы, OU |
| Служба аутентификации | Kerberos Key Distribution Center ( KDC ) - выдает билеты для доступа к ресурсам |
| Служба авторизации | Проверяет, имеет ли пользователь доступ к запрашиваемому ресурсу |
| Репликация | Мультимастер-репликация - изменения можно вносить на любом контроллере домена |

## Архитектура: ключевые компоненты

Прежде чем разбирать атаки - нужно понять, из чего состоит **AD DS** изнутри. Каждый компонент - это одновременно и критическая функция, и потенциальная точка входа для атакующего.

### NTDS.DIT

**NTDS.DIT** - это главный файл базы данных **Active Directory**. Физически он лежит на каждом контроллере домена по пути **%SystemRoot%\NTDS\ntds.dit**. Внутри - абсолютно всё: каждый пользователь, каждый компьютер, каждая группа, каждый атрибут, каждый хеш пароля.

База построена на движке **Extensible Storage Engine (ESE)**. **ESE** работает по принципу транзакционного журнала: прежде чем изменение попадёт в основной файл, оно записывается в журнал **EDB.LOG**. Это гарантирует целостность данных при внезапном отключении питания, но это же означает, что рядом с **ntds.dit** всегда лежат файлы журналов, которые тоже содержат чувствительные данные.

Файл заблокирован системой пока работает **AD DS** - напрямую скопировать его нельзя. Но есть обходные пути:

| Метод | Команда |
|---|---|
| Теневое копирование (VSS) | vssadmin create shadow /for=C: |
| ntdsutil | ntdsutil "activate instance ntds" "ifm" "create full C:\dump" quit quit |

> **Volume Shadow Copy Service (VSS)** - штатный компонент Windows, создающий теневую копию тома на уровне блочного устройства для целей резервного копирования и восстановления системы. Теневая копия - это снимок состояния диска на момент запуска, доступный для чтения даже пока исходные файлы заблокированы работающими процессами; именно поэтому через неё можно скопировать заблокированный **ntds.dit**, обратившись не к оригинальному файлу, а к его снимку.

Оба метода легитимны и используются для резервного копирования администратором домена. Именно поэтому они так популярны у атакующих - они не выглядят как атака.

После получения файла атакующий извлекает хеши паролей офлайн. Ни один антивирус на контроллере домена это не остановит - файл уже у атакующего на его машине.

> **Защита:** мониторить создание теневых копий (**Event ID 8222** в **System Log**), ограничить права на запуск **ntdsutil**, настроить алерт на любое обращение к директории **%SystemRoot%\NTDS** извне системных процессов через **Sysmon Event ID 11**.

**NTDS.DIT** хранит данные статически, но у **Active Directory** есть и динамическая часть - служба, которая на лету проверяет подлинность каждого пользователя и выдаёт ему билеты доступа.

### Kerberos KDC

**Key Distribution Center (KDC)** - служба, которая живёт на каждом контроллере домена и отвечает за выдачу билетов **Kerberos**.

**KDC** состоит из двух частей: **Authentication Service (AS)** принимает первичный запрос пользователя и выдаёт **TGT**, а **Ticket Granting Service (TGS)** принимает **TGT** и выдаёт сервисные билеты для доступа к конкретным ресурсам.

Всё это работает на одной служебной учётной записи - **KRBTGT**. Она создаётся автоматически при развёртывании домена, никогда не используется для интерактивного входа и имеет один критически важный атрибут: её хеш пароля шифрует все **TGT** в домене. Это означает, что тот, кто владеет хешем **KRBTGT** - владеет доменом целиком и бессрочно, пока пароль не сменят дважды.

**KDC** выдаёт билеты, но откуда компьютеры и пользователи берут сами настройки политик, которые к ним применяются? За это отвечает ещё один ключевой компонент - общая сетевая папка, реплицируемая на все контроллеры домена.

### SYSVOL

**SYSVOL** - общая сетевая папка, которая реплицируется на все контроллеры домена. Физически она находится по пути **%SystemRoot%\SYSVOL\sysvol&lt;domain_name>**. Внутри неё два типа содержимого:

1. Папка **Policies** с **GPO**, где каждая **GPO** хранит два компонента - объект в **NTDS.DIT** (настройки) и папку в **SYSVOL** (файлы скриптов, шаблоны)
2. Папка **Scripts** со скриптами входа в систему, которые выполняются при входе пользователя. Когда компьютер применяет политику, он читает настройки из **AD** и файлы из **SYSVOL.**

Репликация **SYSVOL** между **DC** исторически работала через **File Replication Service (FRS)**, который был заменён на **Distributed File System Replication (DFS-R)** начиная с Windows Server 2008 R2. Если в инфраструктуре остался **FRS** - это не только устаревший компонент, но и источник проблем с репликацией при сбоях сети.

Главная угроза **SYSVOL** - права на запись. Если обычный пользователь или скомпрометированная служба получит права на запись в папку **GPO** внутри **SYSVOL**, при следующем входе любого пользователя домена выполнится вредоносный скрипт с правами этого пользователя.

**NTDS.DIT**, **KDC** и **SYSVOL** хранят и выдают данные, но всё это взаимодействие происходит через единый протокол, с помощью которого любой клиент - легитимный или нет - обращается к каталогу.

### LDAP и Global Catalog

**Lightweight Directory Access Protocol (LDAP)** - основной протокол для работы с **Active Directory**. Через него происходит всё взаимодействие с каталогом: поиск объектов, аутентификация, изменение атрибутов. **LDAP** работает на порту **389** (без шифрования) и **636** (LDAPS - с TLS).

Каждый контроллер домена отвечает на **LDAP**-запросы, но только в рамках своего домена. Если нужно найти объект из другого домена леса - обычный **LDAP** не поможет. Здесь вступает в игру **Global Catalog**.

**Global Catalog (GC)** - это не отдельный сервер, а роль, которую может играть любой контроллер домена. **DC** с ролью **GC** хранит полную копию всех объектов своего домена и частичную копию объектов из всех остальных доменов леса. **GC** отвечает на запросы на порту **3268** (без шифрования) и **3269** (с TLS).

Зачем это нужно: когда пользователь из **corp.example.com** открывает адресную книгу Outlook и ищет коллегу из **emea.example.com** - его клиент не идёт напрямую в контроллер домена **emea**. Он обращается к **GC** и получает ответ мгновенно, потому что **GC** уже хранит основные атрибуты всех пользователей леса локально.

Атакующие могут воспользоваться протоколом и перечислить объекты домена, а через **GC** - всего леса целиком:

Перечисление пользователей домена: `Get-ADUser -Filter * -Server "dc01.corp.example.com" -Properties Department, Title | Select-Object Name, Department, Title`

> Тот же запрос, направленный на **Global Catalog**, вернёт данные уже по всему лесу, а не только по одному домену:

Перечисление пользователей всего леса через **GC** (порт **3268**): `Get-ADUser -Filter * -Server "gc.corp.example.com:3268" -Properties Department, Title | Select-Object Name, Department, Title`

На практике атакующие редко останавливаются на разведке: дальше в ход идут конкретные техники, которые эксплуатируют все рассмотренные ранее компоненты для получения полного контроля над доменом.

## Атаки на репликацию каталога

Один из самых прямых способов получить сразу все хеши в домене - не воровать их по одному, а запросить у контроллера домена легитимную репликацию.

### DCSync

**DCSync** - техника, при которой атакующий, обладая правами на репликацию каталога, обращается к контроллеру домена напрямую по протоколу репликации и получает те же данные, что обычно передаются между контроллерами домена, включая хеши паролей всех учётных записей. Для проведения атаки нужна учётная запись с правами на репликацию - обычно это **Domain Admins** или специально делегированные аккаунты. Атакующий использует протокол репликации контроллеров домена (**MS-DRSR**) и запрашивает у настоящего **DC** синхронизацию данных - в том числе хеши паролей.

С точки зрения контроллера домена это выглядит как обычный запрос репликации от другого **DC**. Никакого вредоносного кода на контроллере домена не запускается - всё происходит по сети, и в результате атакующий получает учётные данные всех пользователей домена без выполнения кода на самом контроллере и без прямого доступа к файлу **NTDS.DIT**, что делает технику практически невидимой для антивирусных решений.

> **Защита:** ограничить права **Replicating Directory Changes** - они не должны быть у обычных пользователей или сервисных аккаунтов. Мониторить **Event ID 4662** с **GUID** **{1131f6aa-9c07-11d1-f79f-00c04fc2dcd2}** - это признак **DCSync**.

**DCSync** читает данные через механизм репликации. Тот же механизм можно развернуть в обратную сторону - не забирать данные, а записывать их, выдав свою машину за полноценный контроллер домена.

### DCShadow

**DCShadow** - атака, зеркальная по отношению к **DCSync**: если **DCSync** использует протокол репликации каталога для чтения данных, то **DCShadow** тот же протокол использует для записи. С правами администратора можно зарегистрировать свою машину как новый контроллер домена в схеме **AD** и реплицировать изменения на настоящие **DC**. В отличие от **DCSync**, который только читает данные, **DCShadow** их записывает - создавая бэкдоры, меняя пароли, добавляя себя в привилегированные группы.

Атака особенно опасна тем, что изменения вносятся через легитимный механизм репликации. Стандартные журналы безопасности на DC не зафиксируют источник изменений корректно.

> **Защита:** ограничить права на создание объектов типа **server** в разделе **CN=Sites,CN=Configuration** - по умолчанию это могут делать только **Domain Admins** и **Enterprise Admins**, любое расширение этих прав должно быть явно обоснованным. Мониторить **Event ID 4662** на регистрацию новых объектов в этом разделе - любой незапланированный новый **DC** в инфраструктуре это немедленный красный флаг.

**DCSync** и **DCShadow** объединяет общий принцип: обе техники используют штатный механизм репликации **AD**, но применяют его в разных направлениях - на чтение и на запись. Обладая достаточными правами, атакующий получает доступ не только к данным каталога, но и к возможности их изменения от имени легитимного контроллера домена.
