# Групповые политики

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 2: Доменная инфраструктура / Групповые политики
>
> **Кейсы:** [3.13 GPO](../../cases/windows/3.13%20GPO.md)

**Group Policy Object (GPO)** - это механизм централизованного управления конфигурацией политик в среде **Active Directory (AD)**. Если **Local Policy Object (LPO)** работает на одном хосте, то **GPO** одним действием применяет настройки на тысячи машин в домене. Именно здесь администратор реально управляет безопасностью инфраструктуры, а не настраивает каждый компьютер вручную. Подробности в [**Group Policy overview**](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/hh831791%28v=ws.11%29) на Microsoft Learn.

> Если **LPO** - это устав одного гарнизона, то **GPO** - это приказ главнокомандующего, который одновременно меняет правила во всех крепостях на подконтрольной территории. Один приказ, тысячи исполнителей.

![](../../_images/963e12a225ab.webp)

## Как работает GPO: модель применения

Прежде чем трогать консоль, нужно понять логику. **GPO** применяются к объектам **Active Directory** - сайтам, доменам и подразделениям (**Organizational Unit**, **OU**). Порядок применения важен: чем ниже объект в иерархии, тем позже применяется его политика, и значит - тем выше приоритет.

**Порядок применения (LSDOU):**

1. **Local** - локальная политика компьютера (**secpol.msc**)
2. **Site** - политики, привязанные к сайту **AD**
3. **Domain** - политики, привязанные к домену
4. **OU** - политики подразделений (от родительского к дочернему)

![](../../_images/9e02df08881b.webp)

> **Важно:** При конфликте побеждает политика, применённая последней. То есть **GPO** на дочернем **OU** перекрывает **GPO** домена, а **GPO** домена перекрывает локальную политику. Исключение - флаг **Enforced**, который ломает это правило намеренно.

**Два типа настроек внутри GPO:**

- **Computer Configuration** - применяется к компьютеру при его загрузке, независимо от того, кто вошёл в систему
- **User Configuration** - применяется к пользователю при входе в систему, независимо от того, на каком компьютере

Для работы с **GPO** используется несколько штатных инструментов Windows - каждый со своей ролью: одни создают и редактируют политики, другие принудительно применяют их на клиентах, третьи помогают понять, какие политики реально сработали.

| Инструмент | Где запускается | Для чего |
|---|---|---|
| gpmc.msc | Контроллер домена / управляющий ПК | Создание, редактирование, привязка GPO |
| gpedit.msc | Любой ПК ( Pro / Enterprise ) | Редактирование только локальной политики |
| gpupdate /force | Cmd на целевом ПК | Принудительное применение всех политик (даже тех, что не изменились) |
| gpresult /h report.html | Cmd на целевом ПК | Полный HTML -отчёт о применённых политиках |

> **Важно:** **gpmc.msc** - основной инструмент администратора домена. Для его работы требуется установить компонент **Remote Server Administration Tools** на рабочей станции или использовать непосредственно контроллер домена.

## Создание и привязка GPO

Процесс состоит из двух независимых шагов: сначала политика создаётся, потом привязывается к нужному объекту **AD**. Это не одна операция - **GPO** существует отдельно от места своего применения, что позволяет привязать одну политику к нескольким **OU**.

**Создание GPO:**

1. Открыть **gpmc.msc**
2. В дереве найти **Group Policy Objects** -> правый клик -> **New**
3. Дать имя, отражающее назначение: **SEC-Workstations-PasswordPolicy**, а не **Policy1**
4. После создания - правый клик по **GPO** -> **Edit** -> настроить параметры

**Привязка GPO к OU:**

1. В **gpmc.msc** найти нужный **OU** в дереве
2. Правый клик по **OU** -> **Link an Existing GPO...**
3. Выбрать нужную политику из списка

> **Важно:** Хорошая практика именования - включать в название тип объекта (**SEC** - безопасность, **SW** - ПО), цель применения (**Workstations**, **Servers**, **Domain**) и суть настройки. Это спасёт через полгода, когда в домене будет 40 политик.

## Диагностика применения: gpresult

**gpresult** - первый инструмент, когда политика "не работает". Он показывает результирующий набор политик - то, что реально применилось на конкретном компьютере для конкретного пользователя с учётом всей иерархии и конфликтов.

| Для чего | Команда |
|---|---|
| Краткий вывод в консоль для текущего пользователя и компьютера | gpresult /r |
| Подробный HTML -отчёт для анализа | gpresult /h C:\report.html /f |
| Проверка политик для конкретного пользователя на удалённом компьютере | gpresult /s HOSTNAME /u DOMAIN\username /r |

**На что смотреть в выводе gpresult /r:**

- **Applied GPOs** - список политик, которые реально применились
- **Denied GPOs** - список политик, которые были пропущены (причина указана рядом)
- Причины отказа: **Empty** (в **GPO** нет настроек), **Disabled** (**GPO** отключён), **Security Filtering** (нет прав на чтение)

> **Важно:** Типичная ошибка - **GPO** привязан к **OU**, но не применяется. Причина почти всегда одна из трёх: неправильная фильтрация безопасности (объект не входит в группу применения), **GPO** отключён, или компьютер находится не в том **OU**.

## Фильтрация применения GPO

По умолчанию **GPO** применяется ко всем объектам в **OU**. Это можно ограничить двумя способами.

### 1. Security Filtering

Позволяет применять **GPO** только к определённым пользователям, компьютерам или группам.

1. В **gpmc.msc** выбрать **GPO**
2. Во вкладке **Scope** в секции **Security Filtering** по умолчанию стоит **Authenticated Users**
3. Удалить **Authenticated Users**, добавить нужную группу

> **Важно:** Если убрать **Authenticated Users** и не добавить ничего - **GPO** не применится ни к кому. Это частая причина "пропавших" политик.

### 2. WMI Filtering

Позволяет применять **GPO** только к компьютерам, соответствующим условию **WMI**-запроса (**WMI** разбирался ранее в курсе). Например, только к машинам с Windows 11 или только к ноутбукам.

Пример **WMI**-фильтра для применения политики только на Windows 11: `SELECT * FROM Win32_OperatingSystem WHERE Version LIKE "10.0.2%"`

**WMI**-фильтр создаётся в **gpmc.msc** -> **WMI Filters**, затем привязывается к **GPO** на вкладке **Scope**.

## Брандмауэр Windows в контексте домена

Основы работы брандмауэра Windows, платформа **Windows Filtering Platform (WFP)** и назначение трёх профилей (**Domain**, **Private**, **Public**) уже разбирались ранее в курсе. Здесь остановимся только на специфике его централизованной настройки через **GPO**.

Без **GPO** каждый пользователь или локальный администратор может изменить настройки брандмауэра на своей машине. С **GPO** правила применяются принудительно и не могут быть изменены обычным пользователем.

**Настройка брандмауэра через GPO:**

**Computer Configuration -> Policies -> Windows Settings -> Security Settings -> Windows Defender Firewall with Advanced Security**

Здесь можно централизованно:

- Включить брандмауэр для всех профилей (и запретить его отключение)
- Создать правила разрешения или блокировки для конкретных портов и приложений
- Настроить логирование отклонённых пакетов

> **Важно:** Настройки брандмауэра из **GPO** имеют приоритет над локальными настройками. Если администратор применил политику, запрещающую входящий **RDP** - пользователь не сможет его включить через **Control Panel**.

**Пример: централизованное включение брандмауэра.**

1. В **gpmc.msc** создать **GPO SEC-Firewall-Baseline**
2. Редактировать: **Computer Configuration -> Windows Settings -> Security Settings -> Windows Defender Firewall**
3. В свойствах каждого профиля: **Firewall state: On**, **Inbound connections: Block**, **Outbound connections: Allow**
4. Привязать к **OU** с рабочими станциями

> **Важно:** Не применяйте эту политику к **OU** с контроллерами домена без отдельной проработки правил. **DC** требуют открытых портов для репликации **AD**, **Kerberos**, **LDAP**, **DNS** и других служб - жёсткая блокировка входящих соединений нарушит работу всего домена.

## Кто может изменять GPO

**GPO** - мощный инструмент, и именно поэтому он становится целью атак. Компрометация **GPO** означает компрометацию всех машин, к которым он привязан. С точки зрения атакующего, **GPO** - это легитимный механизм выполнения кода на сотнях хостов сразу, который редко вызывает подозрения у защитников.

### Права по умолчанию

Понимание того, какие группы имеют доступ к **GPO**, - основа как защиты, так и атаки. Атакующий в первую очередь ищет именно эти группы при компрометации аккаунтов.

| Группа | Права на GPO | Комментарий |
|---|---|---|
| Domain Admins | Полный контроль | Могут создавать, редактировать, удалять любые GPO |
| Enterprise Admins | Полный контроль | Права распространяются на весь лес AD , не только домен |
| Group Policy Creator Owners | Создание GPO + полный контроль над своими GPO | Могут создавать GPO , но редактировать чужие - нет |
| SYSTEM | Полный контроль | Системная учётная запись, используется при применении политик |
| Authenticated Users | Чтение | Любой аутентифицированный пользователь домена может читать содержимое GPO |
| Domain Controllers | Чтение | DC читают GPO для применения на компьютерах |
| Creator Owner | Полный контроль над своими объектами | Тот, кто создал GPO , управляет им |

> **Важно:** **Authenticated Users** имеет право на чтение по умолчанию. Это значит, что любой пользователь домена - включая скомпрометированный аккаунт с минимальными правами - может прочитать содержимое всех **GPO** и скриптов в **System Volume (SYSVOL)**. Именно поэтому хранить пароли в **GPO**-скриптах категорически нельзя.

### Делегирование прав

**Делегирование прав** - это механизм **Active Directory**, позволяющий передать конкретному пользователю или группе часть административных полномочий над определённым объектом каталога, не выдавая при этом полных прав на весь домен. Идея - принцип минимальных привилегий: если команде **helpdesk** нужно только сбрасывать пароли пользователей в конкретном **OU**, ей не нужны права **Domain Admin** на весь домен. Ей делегируется только это конкретное право на конкретный **OU**.

Технически делегирование работает через **ACL** объекта **AD**. Администратор через мастер делегирования или прямое редактирование дескриптора безопасности добавляет в **ACL** новую запись с указанием: **кто** (учётная запись или группа), **какое право** (чтение, запись, специфичные операции) и **на какой объект** (**OU**, **GPO**, отдельная учётная запись). При обращении к объекту **AD** проверяет **ACL** так же, как файловая система проверяет доступ к файлам.

В **GPO** это реализовано следующим образом: Каждый **GPO** - это отдельный объект **AD** со своим собственным **ACL**. Права на **GPO** делегируются через **gpmc.msc** -> **GPO** -> вкладка **Delegation** и могут выдаваться отдельно от всех остальных прав в домене. Именно здесь чаще всего появляются избыточные права: администраторы делегируют команде **helpdesk** возможность управлять политиками рабочих станций - и не всегда точно понимают, к чему это приводит.

Типы прав, которые можно делегировать на **GPO**:

| Право | Что позволяет |
|---|---|
| Read | Только просмотр настроек GPO |
| Edit settings | Изменение параметров GPO (самое опасное при утечке) |
| Edit settings, delete, modify security | Полный контроль, включая изменение прав доступа к GPO |
| Read (from Security Filtering) | Определяет, применяется ли GPO к объекту |

В контексте атакующих механизм делегирования может быть использован для получения доступа к изменению политик. Классический сценарий в корпоративных сетях:

1. Администратор делегировал группе **IT-Helpdesk** право **Edit settings** на **GPO SEC-Workstations-Baseline**
2. Атакующий компрометирует любой аккаунт из группы **IT-Helpdesk** (фишинг, брутфорс)
3. Через этот аккаунт он редактирует **GPO** и добавляет вредоносное задание
4. Задание выполняется от **SYSTEM** на тех рабочих станциях, к которым применяется эта политика

![](../../_images/ae00dfd52c34.webp)

> **Важно:** Право **Edit settings** на **GPO** - это фактически право выполнять код от **SYSTEM** на всех машинах в области применения этой политики. Выдавать его нужно так же осторожно, как права локального администратора.

## Атаки на GPO

Если атакующий получил права **GenericWrite**, **GenericAll** или **GpoEditDeleteModifySecurity** на объект **GPO** - он может модифицировать политику. Это происходит, например, после компрометации аккаунта администратора **OU** или рядового пользователя, которому по ошибке выдали лишние права.

### GPO Abuse: добавление Scheduled Task

**GPO Abuse через Scheduled Task** (MITRE ATT&CK: [**T1484.001**](https://attack.mitre.org/techniques/T1484/001/), [**T1053.005**](https://attack.mitre.org/techniques/T1053/005/)). Самый тихий способ - добавить задание через **Computer Configuration -> Preferences -> Control Panel Settings -> Scheduled Tasks**. Задание выполнится с правами **SYSTEM** на всех машинах в области применения **GPO** при следующем обновлении политик (по умолчанию каждые 90 минут + случайный сдвиг до 30 минут).

Автоматизация через [**SharpGPOAbuse**](https://github.com/FSecureLABS/SharpGPOAbuse) - добавление немедленного задания, которое выполнит команду от **SYSTEM**: `SharpGPOAbuse.exe --AddComputerTask --TaskName "WindowsUpdate" --Author "NT AUTHORITY\SYSTEM" --Command "cmd.exe" --Arguments "/c net localgroup administrators attacker /add" --GPOName "Default Domain Policy"`

> **Важно:** Задание выглядит как легитимная системная задача. Имя можно замаскировать под **WindowsUpdate**, **DiskCleanup**, **TelemetryService** - и оно не вызовет подозрений при беглом просмотре.

### GPO Abuse: добавление скрипта запуска

**GPO Abuse через Startup Script** (MITRE ATT&CK: [**T1484.001**](https://attack.mitre.org/techniques/T1484/001/), [**T1037.003**](https://attack.mitre.org/techniques/T1037/003/)). Через **SharpGPOAbuse** можно добавить скрипт запуска, который помещается в **SYSVOL** и выполняется при загрузке компьютера от **SYSTEM**: `SharpGPOAbuse.exe --AddComputerScript --ScriptName "update.bat" --ScriptContents "net user backdoor P@ssw0rd /add && net localgroup administrators backdoor /add" --GPOName "SEC-Workstations-Baseline"`

В отличие от **Scheduled Task**, скрипт срабатывает только при перезагрузке машины - но зато не оставляет записи в планировщике заданий, что делает его чуть менее заметным.

### GPO Abuse: назначение User Rights

**GPO Abuse через User Rights Assignment** (MITRE ATT&CK: [**T1484.001**](https://attack.mitre.org/techniques/T1484/001/)). Через **GPO** можно добавить свою учётную запись в группы с системными привилегиями: `SharpGPOAbuse.exe --AddUserRights --UserRights "SeDebugPrivilege,SeImpersonatePrivilege" --UserAccount "attacker" --GPOName "Default Domain Policy"`

**SeDebugPrivilege** даёт доступ к памяти всех процессов, включая **LSASS** (разбирался ранее в курсе) - откуда можно вытащить хеши паролей. **SeImpersonatePrivilege** позволяет выполнять код от имени других пользователей и является ключом ко многим техникам повышения привилегий.

### GPP Password Attack (CVE-2014-1812)

**GPP Password Attack** (MITRE ATT&CK: [**T1552.006**](https://attack.mitre.org/techniques/T1552/006/)). До 2014 года администраторы могли хранить пароли прямо в **Group Policy Preferences (GPP)** - например, чтобы автоматически создавать локального администратора на всех машинах или подключать сетевые диски с учётными данными. Пароли шифровались алгоритмом **AES-256**, но Microsoft опубликовала ключ шифрования в открытой документации.

**Где хранились GPP-пароли.** Файлы **XML** с паролями лежат в **SYSVOL** и доступны на чтение любому аутентифицированному пользователю домена:

- **\\DOMAIN\SYSVOL\domain\Policies{GUID}\Machine\Preferences\Groups\Groups.xml**
- **\\DOMAIN\SYSVOL\domain\Policies{GUID}\User\Preferences\Drives\Drives.xml**
- **\\DOMAIN\SYSVOL\domain\Policies{GUID}\Machine\Preferences\Services\Services.xml**

Пароль в файле выглядит так: **&lt;Properties action="U" userName="Administrator" cpassword="VPe/o9YRyz2cksnYRbNeqg..." />**

![](../../_images/d92b65df258e.webp)

**Расшифровка.** Через утилиту **gpp-decrypt** из Kali Linux: `gpp-decrypt "VPe/o9YRyz2cksnYRbNeqg..."`

Автоматический поиск по всему домену через **CrackMapExec**: `crackmapexec smb DOMAIN_CONTROLLER -u user -p password -M gpp_password`

Изнутри домена через **PowerShell** и **PowerSploit**: `Get-GPPPassword`

> **Важно:** Уязвимость закрыта патчем [**MS14-025**](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2014/ms14-025) - новые пароли через **GPP** создать нельзя. Но в инфраструктурах, которые существуют с 2014 года и не прошли полный аудит, старые файлы с паролями до сих пор лежат в **SYSVOL**.

### SYSVOL как источник учётных данных

**Поиск учётных данных в SYSVOL** (MITRE ATT&CK: [**T1552.001**](https://attack.mitre.org/techniques/T1552/001/)). **SYSVOL** реплицируется на все контроллеры домена и читается всеми аутентифицированными пользователями. Это означает, что любой пользователь домена может просмотреть содержимое **GPO**-скриптов - и найти там пароли.

![](../../_images/80e7a487f4b1.webp)

Поиск потенциальных паролей в скриптах **GPO** через **findstr**:

| Для чего | Команда |
|---|---|
| Поиск в PowerShell -скриптах | findstr /si "password" \DOMAIN\SYSVOL\*.ps1 |
| Поиск в batch -файлах | findstr /si "password" \DOMAIN\SYSVOL\*.bat |
| Поиск в XML -файлах | findstr /si "password" \DOMAIN\SYSVOL\*.xml |
| Поиск в VBScript -файлах | findstr /si "password" \DOMAIN\SYSVOL\*.vbs |

Или рекурсивно через **PowerShell** с более широким набором ключевых слов:

```
Get-ChildItem -Path "\\DOMAIN\SYSVOL" -Recurse -Include *.ps1,*.bat,*.xml,*.vbs -ErrorAction SilentlyContinue |
    Select-String -Pattern "password|passwd|pwd|secret" |
    Select-Object Path, LineNumber, Line
```

Администраторы нередко хардкодят учётные данные прямо в скриптах, которые **GPO** применяет на машины. Типичные сценарии: подключение к базе данных, монтирование сетевых дисков, установка агентов мониторинга.

## Какие механизмы защиты работают на GPO

**Принцип минимальных прав на GPO** - в **gpmc.msc** -> **GPO** -> **Delegation** оставить только тех, кому реально нужно редактирование. Сужает поверхность атаки при компрометации учётных записей в домене.

**Аудит изменений объектов AD** - через **Default Domain Controllers Policy** -> **Audit Directory Service Changes: Success, Failure**. Фиксирует ключевые события изменений **GPO**:

- **Event ID 5136** - изменение объекта **AD**, в том числе **GPO**
- **Event ID 5137** - создание нового объекта **AD**
- **Event ID 5141** - удаление объекта **AD**
- **Event ID 4719** - изменение системной политики аудита
- **Event ID 4706** - создание нового доверия домена
- **Event ID 7045** - установка новой службы (может быть через **GPO**)

**Регулярный аудит SYSVOL** - запуск скрипта поиска паролей в **SYSVOL** по расписанию. Обнаруживает захардкоженные учётные данные в **GPO**-скриптах.

**Патч MS14-025 + аудит SYSVOL** - убедиться, что **KB2962486** установлен на всех **DC**; найти и очистить оставшиеся **cpassword** в **SYSVOL** командой: `findstr /si "cpassword" \DOMAIN\SYSVOL\*.xml`

**Уровни административных аккаунтов (Tier model)** - **Tier 0** (**DC**), **Tier 1** (серверы), **Tier 2** (рабочие станции). Разные аккаунты для каждого уровня. Компрометация **Tier 2** аккаунта не даёт доступа к **GPO** серверов.

**LAPS для локальных администраторов** - уникальные пароли для локальных админов на каждой машине. Ломает горизонтальное распространение через **GPO Abuse: User Rights**.

**Мониторинг создания и изменения GPO в SIEM** - алерты на **Event ID 5136** для критичных **GPO** (**Default Domain Policy**, **Default Domain Controllers Policy**) с уведомлением ответственного администратора.

## Практический чек-лист: базовая GPO-безопасность

Ниже - минимальный набор политик, который стоит реализовать в любой доменной инфраструктуре.

**GPO для рабочих станций (SEC-Workstations-Baseline):**

- **Computer Configuration -> Security Settings -> Account Policies** - политика паролей (аналогично **LPO**, но применяется через домен)
- Брандмауэр: все профили включены, входящие соединения блокируются по умолчанию
- **User Configuration -> Administrative Templates -> System -> Prevent access to registry editing tools** - запретить **regedit** обычным пользователям
- Отключить автозапуск (**AutoPlay**) для всех дисков

**GPO для защиты контроллеров домена (SEC-DomainControllers-Hardening):**

- Ограничить **Allow log on locally** только группой **Domain Admins**
- Включить расширенный аудит входов, изменений объектов **AD**, управления учётными записями
- Запретить установку программ пользователями

> **Важно:** Политика паролей домена (длина, сложность, срок действия) применяется только через **GPO**, привязанный к домену, а не к **OU**. Это фундаментальное ограничение **AD**: политика паролей для доменных учётных записей берётся только из **Default Domain Policy** или объектов **Fine-Grained Password Policy**. **GPO** на **OU** не влияет на пароли доменных аккаунтов.
