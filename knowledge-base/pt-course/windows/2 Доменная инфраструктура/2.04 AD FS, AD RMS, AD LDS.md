# AD FS, AD RMS, AD LDS

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 2: Доменная инфраструктура / Роли и сервисы Active Directory
>
> **Кейсы:** [3.10 DC](../../cases/windows/3.10%20DC.md), [3.11 IIS](../../cases/windows/3.11%20IIS.md), [3.12 AD CS](../../cases/windows/3.12%20AD%20CS.md)

## Active Directory Federation Services (AD FS)

**AD FS** - это служба федерации, которая обеспечивает единый вход (**Single Sign-On, SSO**) через веб-браузер для приложений за пределами корпоративной сети (федеративное доверие).

> **Single Sign-On (SSO)** - технология единой аутентификации, при которой пользователь один раз подтверждает свою личность и получает доступ ко всем связанным системам и приложениям без повторного ввода учётных данных.

**AD FS** решает несколько связанных задач. Она позволяет сотрудникам использовать единый корпоративный логин и пароль для доступа к Office 365, Salesforce, Dropbox и другим облачным сервисам, обеспечивает федеративное доверие с доверенными партнёрами (аутентификацию пользователей партнёра в корпоративной системе и наоборот), а также поддерживает основные протоколы федерации: **SAML, WS-Federation** и **OAuth**.

Такая функциональность обеспечивается несколькими компонентами, каждый из которых при неправильной настройке становится отдельной точкой отказа.

### Архитектура AD FS

![](../../_images/6e4b75756721.webp)

Схема показывает три звена, через которые проходит любой запрос на федеративную аутентификацию. Клиент из внешней сети обращается не напрямую к внутренней **Federation Service**, а к прокси-серверу **WAP**, размещённому в **DMZ** - именно эта граница отделяет корпоративную сеть от интернета. Прокси передаёт запрос внутрь, где **Federation Service** сверяет учётные данные пользователя с **Attribute Stores** и в случае успеха выпускает федеративный токен. Этот токен уходит уже не обратно во внутреннюю сеть, а во внешнее приложение-партнёр, которому пользователь изначально хотел войти.

| Компонент | Назначение | Риск |
|---|---|---|
| Federation Service | Основная служба, обрабатывающая запросы на аутентификацию через протоколы федерации ( SAML , WS-Fed ) | При компрометации - выдача федеративных токенов (неограниченный доступ к любому федеративному приложению) |
| Proxy Service (WAP) | Прокси-сервер в DMZ , который принимает входящие федеративные запросы из интернета и передает их внутренней AD FS | Прокси может быть скомпрометирован для ретрансляции вредоносных запросов |
| Attribute Stores | Источники атрибутов о пользователе ( AD DS, SQL Server, LDAP ) | Неправильная настройка может раскрыть атрибуты пользователей неавторизованным приложениям |

**AD FS** защищает процесс входа в систему, но не то, что происходит с данными после того, как пользователь получил к ним доступ. Именно эту задачу решает следующая служба.

## Active Directory Rights Management Services (AD RMS)

**AD RMS** - это служба защиты информации от несанкционированного доступа. **AD RMS** принудительно применяет политики использования к документам и электронным письмам (не копировать, не печатать, не пересылать). Это защищает конфиденциальные документы даже после их отправки по электронной почте.

Эта защита реализована через несколько взаимосвязанных серверных компонентов.

### Ключевые компоненты AD RMS

![](../../_images/d8e49ca60ce3.webp)

**Пример:** сотрудник компании отправляет партнёру защищённый документ по электронной почте. Когда партнёр открывает файл, приложение на его компьютере как **RMS-клиент** обращается к объекту **AD RMDS** в **AD**, чтобы узнать адрес действующего **Certification Server**. Получив этот адрес, приложение запрашивает у **Certification Server** сертификаты защиты и лицензию на использование документа. Сам **Certification Server** при этом обращается к **RMS Database**, где хранятся ключи и шаблоны политик, необходимые для выдачи лицензии, и к **Logging Database**, где фиксируется факт запроса. Только после получения лицензии содержимое документа расшифровывается и к нему применяются заданные политики использования - без неё содержимое остаётся зашифрованным, даже если письмо попадёт не по адресу.

| Компонент | Назначение | Риск |
|---|---|---|
| Certification Server | Выдает сертификаты защиты и лицензии использования для RMS -клиентов | При компрометации - выдача прав на архивированные документы для любых пользователей |
| RMS Database | Хранит ключи, шаблоны политик, логи использования | Утечка ключей расшифровки защищенных документов |
| Logging Database | Журнал запросов на сертификаты и лицензии | Отключение журналирования мешает выявлению атак, а утечка журналов раскрывает активность пользователей |
| AD RMDS (Service Connection Point) | Объект в AD , указывающий на серверы AD RMS | Неправильные права доступа позволяют перенаправить аудиторию на злонамеренный сервер AD RMS |

**AD RMS** защищает документы внутри домена. Но не каждому приложению вообще нужен полноценный домен - для более лёгких сценариев существует урезанная версия **AD DS**.

## Active Directory Lightweight Directory Services (AD LDS)

**AD LDS** (ранее известный как **ADAM - Active Directory Application Mode**) - это "облегченная версия" **AD DS**, которая предоставляет каталог-сервис для приложений, но запускается как обычная служба, а не как полноценный домен.

**AD LDS** используется в нескольких типовых сценариях. Он позволяет изолировать данные приложения от основной базы **AD DS** ради безопасности и производительности, даёт возможность разрабатывать и тестировать приложения без развёртывания полноценного домена, а также хранить данные в формате **LDAP** без необходимости быть контроллером домена.

Несмотря на облегчённую модель, у **AD LDS** есть собственная внутренняя структура, повторяющая логику **AD DS** в миниатюре.

### Архитектура AD LDS

![](../../_images/45efdd2a7287.webp)

Каждый **Instance** службы **AD LDS** внутри себя делится на три раздела. **Configuration Partition** хранит настройки самого экземпляра - от репликации до привязок к портам. **Schema Partition** описывает структуру данных, будь то копия схемы **AD** или собственная схема приложения. **Application Partition** содержит непосредственно пользовательские данные приложения и на практике оказывается основной целью атак, поскольку именно здесь находится ценная информация.

| Компонент | Назначение | Риск |
|---|---|---|
| Instance | Отдельный экземпляр службы AD LDS . На одном сервере можно запустить несколько экземпляров с разными портами и данными | Неправильная настройка сетевой изоляции или прав доступа |
| Configuration Partition | Содержит конфигурацию самого экземпляра (схему, репликацию, привязки) | Раскрывает информацию о структуре каталога, помогает атакующему составить карту |
| Schema Partition | Копия схемы AD или пользовательская схема приложения | Наличие в схеме конфиденциальных атрибутов - утечка в ответах LDAP |
| Application Partition | Пользовательские данные приложений - основной компонент AD LDS | Несанкционированный доступ к каталогу |

Рассмотренные роли - **AD DS, AD CS, AD FS, AD RMS** и **AD LDS** - решают разные задачи, но вместе формируют единую инфраструктуру **Active Directory**. Свести их особенности и уязвимости в одну общую картину помогает итоговое сравнение.

## Сравнительная таблица: Все роли Active Directory

![](../../_images/60fbb0e8909b.webp)

**AD DS** играет центральную роль, вокруг которой строятся остальные четыре. **AD CS** выпускает сертификаты, которые используются в том числе для защиты документов в **AD RMS**. **AD FS** опирается на учётные записи **AD DS**, но выносит аутентификацию за пределы корпоративной сети, обеспечивая единый вход в облачные и партнёрские приложения. **AD LDS**, в отличие от остальных, не расширяет **AD DS,** а предоставляет облегчённую копию его логики - **LDAP**-каталог для приложений, которым не нужен полноценный домен.

| Характеристика | AD DS | AD CS | AD FS | AD RMS | AD LDS |
|---|---|---|---|---|---|
| Основная функция | Каталог пользователей, аутентификация | Выпуск и управление сертификатами | Единый вход ( SSO ) для веб-приложений | Защита документов ( DRM ) изнутри | LDAP-каталог для приложений |
| Ключевой компонент | NTDS.DIT, SYSVOL, KDC | Certificate Templates, CA | Federation Service (proxy), Attribute Stores | Certification Server, Licensor Certificates, Rights Policy Templates | Instance, Application/Configuration/Schema Partition |
| Основные уязвимости | Golden/Silver Ticket, DCSync, Kerberoasting | ESC1-ESC13 (конфигурация шаблонов) | ADFSjacking, Open Redirect, NTLM Relay | Компрометация сервера, Pass-the-Certificate , атаки на шаблоны прав | Information Disclosure (анонимный LDAP ), Memory Consumption DoS |
| Основная угроза | Полный захват домена | Получение сертификата администратора | Кража федеративных токенов | Компрометация защищенных документов (дешифровка) | Утечка данных приложения без аутентификации |
| Главная рекомендация | Защищать KRBTGT , отключать неиспользуемые протоколы | Не использовать самоподписанные сертификаты в боевых системах, внедрить строгий контроль Enrollment | Регулярно обновлять, отключить NTLM, настроить Reply URL | Ограничить доступ к серверу, использовать HSM , защищать шаблоны | Отключить анонимный доступ, принудительно использовать LDAPS |
