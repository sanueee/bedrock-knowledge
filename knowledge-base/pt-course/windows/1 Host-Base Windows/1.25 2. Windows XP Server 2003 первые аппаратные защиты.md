# 2. Windows XP / Server 2003: первые аппаратные защиты

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Эволюция Windows NT

**Windows XP** - **NT 5.1**, **Server 2003** - **NT 5.2**. Внутренне это эволюция **Windows 2000**, но именно здесь Microsoft начала переносить безопасность из "настроек" в архитектуру памяти и ядра.

**Data Execution Prevention (DEP)** **DEP** запрещает исполнение кода из страниц памяти, которые предназначены для данных: стека, кучи, статических переменных. Аппаратная основа - бит **NX** (**No-eXecute)** у AMD и **XD** (**Execute Disable**) у Intel: процессор физически отказывается выполнять инструкции с таких страниц ([**DEP**](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/determine-hardware-dep-available)). До **DEP** классическая атака через переполнение буфера выглядела просто: записать **shellcode** в стек и передать туда управление. **DEP** сделал это невозможным - **shellcode** в стеке исполниться не может. Но **DEP** не убил класс атак, а поднял планку: атакующие перешли к **Return-Oriented Programming (ROP)** - технике, которая не размещает новый код, а собирает нужные действия из уже существующих фрагментов легитимного кода в памяти. **DEP** и **ROP** - это первый пример в истории Windows, когда защита породила новую более сложную технику атаки.

**Kernel Patch Protection (PatchGuard)** В 64-битных редакциях **XP** и **Server 2003** Microsoft ввела **PatchGuard** - механизм, который периодически проверяет целостность критических структур ядра: таблицы системных вызовов (**SSDT**), таблицы прерываний (**IDT**), код самого **ntoskrnl.exe**. При обнаружении модификации - немедленный **BSOD 0x109**. До **PatchGuard** руткиты и антивирусы одинаково использовали **SSDT**-хуки: перехватывали системные вызовы, подменяя адреса в таблице. **PatchGuard** закрыл этот подход для всех сразу. Антивирусные вендоры были недовольны - им пришлось переписывать продукты. Руткиты стали сложнее. Отсутствие **PatchGuard** в 32-битных системах - одна из причин, почему **x86** сегодня считается архитектурно слабым: на нём до сих пор возможны техники, которые на **x64** вызывают синий экран.

**Windows Driver Frameworks (WDF): KMDF и UMDF** Разработка драйверов на чистом **WDM** требовала от программиста вручную обрабатывать управление питанием, **PnP**-события, синхронизацию очередей **IRP** и десятки других деталей. Ошибка в любом из этих мест - потенциальный **BSOD** или уязвимость с повышением привилегий, потому что всё это работает в ядре. **KMDF** (**Kernel-Mode Driver Framework**) и **UMDF** (**User-Mode Driver Framework**) появились как фреймворки поверх **WDM**, которые берут рутину на себя ([**WDM vs WDF**](https://learn.microsoft.com/en-us/windows-hardware/drivers/wdf/differences-between-wdm-and-kmdf)). **UMDF** пошёл дальше: часть драйверов вообще переехала в пространство пользователя - если такой драйвер падает или содержит уязвимость, он не утягивает за собой ядро.
