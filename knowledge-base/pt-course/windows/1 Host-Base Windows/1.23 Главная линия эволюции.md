# Главная линия эволюции

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Эволюция Windows NT

Эволюция Windows NT показывает одну закономерность: каждая защита решала конкретную проблему своего времени - и одновременно создавала условия для следующей атаки. Понимать эту цепочку важно не для того, чтобы знать даты релизов, а чтобы понимать, почему Windows 11 устроена именно так, а не иначе - и чем она принципиально отличается от Windows XP.

Посмотрите на траекторию:

1. **2000–2003:** NT становится массовой корпоративной платформой. Главная задача - заставить это работать в реальных сетях
2. **Vista/2008:** безопасность перестаёт быть надстройкой и встраивается прямо в архитектуру: **UAC**, **MIC**, **ASLR**, **WDDM**, **BitLocker**, **Server Core**, **Hyper-V**
3. **7/2008 R2:** масштабирование и энергоэффективность - **processor groups**, **core parking**, улучшенный **scheduler**
4. **8/2012:** доверенная загрузка и изоляция приложений: **Secure Boot**, **ELAM**, **AppContainer**, **Client Hyper-V**
5. **10/2016:** гипервизор перестаёт быть только платформой для **VM** и становится механизмом безопасности: **VBS**, **Credential Guard**, **HVCI**, **контейнеры**, **WSL**
6. **11/2022+:** аппаратная безопасность превращается из опции в базовое требование
7. **Server 2025:** **Hyper-V**, **VBS** и **storage**/**network**-стек масштабируются под современные датацентры и **AI**/**VM**-нагрузки

Каждое поколение защит в Windows появлялось не по расписанию, а как прямой ответ на конкретную технику атаки. Это важно понимать, потому что та же логика продолжает работать сегодня.

**DEP** сделал невозможным размещение **shellcode** в стеке - атакующие ответили **ROP**: цепочками из фрагментов уже существующего легитимного кода.

**ASLR** убрал предсказуемость адресов - атакующие начали искать **information leak**: способы вытащить из процесса хотя бы один реальный адрес, чтобы вычислить остальные.

**PatchGuard** закрыл прямое патчирование ядра через SSDT-хуки - руткиты усложнились, стали работать глубже.

Обязательная **подпись драйверов** сделала загрузку произвольного кода в ядро дорогой - появился **BYOVD**: зачем получать подпись самому, если можно взять уже уязвимый подписанный драйвер и заставить его сделать грязную работу?

**HVCI** защитил целостность кода в ядре через гипервизор - **BYOVD** стал стандартным инструментом, потому что других вариантов почти не осталось.

Это не случайная последовательность. Это гонка: каждая защита закрывает один путь и вынуждает атаку искать следующий, более сложный. Понимать эту цепочку важнее, чем знать отдельные аббревиатуры - потому что следующий виток уже происходит, и он будет про гипервизор и **VBS enclaves**.
