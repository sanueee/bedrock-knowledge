# Брандмауэр Windows

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Сетевой стек Windows и удалённое управление
>
> **Кейсы:** [3.06 NFS](../../cases/windows/3.06%20NFS.md), [3.07 Сетевой стек](../../cases/windows/3.07%20Сетевой%20стек.md)

**Штатный брандмауэр Windows** - это не просто графическое приложение в панели управления, а инструмент защиты, глубоко интегрированный в сетевой стек через платформу **Windows Filtering Platform (WFP)**.

**WFP** - набор системных сервисов (включая службу **Base Filtering Engine (BFE)**) и **API**, работающих на разных уровнях абстракции ядра. В отличие от простых фаерволов, **WFP** позволяет инспектировать сетевой трафик на любом уровне стека - от физического формирования пакета до его финальной маршрутизации в приложение. Платформа использует концепцию слоёв фильтрации (например, **FWPM_LAYER_INBOUND_IPPACKET_V4**) и драйверов-выносок (callout drivers). Весь сетевой трафик проходит через **WFP**, которая может задерживать, модифицировать и сбрасывать пакеты до того, как они достигнут прикладного **ПО**.

> Архитектура **WFP** - это не ленивый охранник у входной двери здания. Это многоуровневая система умных турникетов, сканеров сетчатки и металлодетекторов на каждом этаже, в каждом коридоре и перед каждой дверью кабинета, которая постоянно проверяет право находиться в конкретной точке пространства.

## Сетевые профили и стратегия настройки правил

Служба **NLA** непрерывно анализирует сетевое окружение и автоматически переключает брандмауэр на один из трёх сетевых профилей. Каждый профиль определяет уровень доверия и свой набор правил.

| Профиль | Уровень доверия | Когда применяется | Поведение |
|---|---|---|---|
| Domain | Высокий | Машина обнаружила и аутентифицировалась на контроллере домена AD | Правила диктуются централизованно через Group Policy Object (GPO) |
| Private | Средний | Домашняя сеть или доверенная рабочая группа | Разрешён обмен файлами, обнаружение устройств, печать |
| Public | Низкий | Недоверенные сети (Wi-Fi в кафе, аэропорту) | Максимальная изоляция, блокировка входящих по умолчанию |

![](../../_images/b2b474e4baa6.webp)

> Сетевые профили - это уровни допуска на режимном объекте. Профиль **Public** - Вы случайный прохожий с улицы. Профиль **Private** - Вы рядовой сотрудник из соседнего отдела. Профиль **Domain** - Вы член высшего руководства с официальным пропуском во все внутренние помещения.

При проектировании защиты системный **специалист** должен соблюдать стратегию разделения правил брандмауэра. Три важнейшие категории подходов к фильтрации:

**Что делать обязательно.** Безусловная блокировка всех входящих подключений по умолчанию. Явное разрешение выдаётся только тому трафику и тем портам, которые критически необходимы. Любое открытое соединение должно быть осознанным и задокументированным. При конфликте правила запрета и правила разрешения блокировка имеет высший приоритет.

**Что делать желательно.** Включить логирование сброшенных пакетов (Dropped Packets) для всех активных профилей - это критично для диагностики и выявления сканирования портов. По умолчанию логи пишутся в **pfirewall.log** с лимитом 4 МБ. Это разумное значение для офисного хоста в спокойном режиме, но при активном сканировании портов или брутфорсе **pfirewall.log** заполняется за считанные минуты - и после этого старые записи затираются новыми. На практике это означает, что первые и самые ценные следы атаки исчезают раньше, чем у специалиста дойдут руки до их анализа. Увеличение лимита хотя бы до 20 МБ даёт запас времени на расследование до того, как ротация съест критичные данные. Также - ограничивать исходящий трафик для критичных узлов: серверу баз данных не нужен неограниченный доступ в интернет.

**На что можно не обращать внимания.** Десятки дефолтных правил от встроенных сервисов вроде Xbox Live, которые генерируются **ОС** даже в серверных сборках. Сотни динамических правил для изолированных приложений **Universal Windows Platform (UWP)**: пакеты **UWP** используют уникальные **SID** для контейнерной изоляции, на сервере они бесполезны.

## PowerShell для работы с брандмауэром

| Для чего | Команда |
|---|---|
| Проверка активных профилей и их состояние | Get-NetFirewallProfile | Select-Object Name, Enabled, DefaultInboundAction, DefaultOutboundAction |
| Включение логирование сброшенных пакетов и увеличения размера лога | Set-NetFirewallProfile -Profile Domain,Public,Private -LogAllowed True -LogBlocked True -LogMaxSizeKilobytes 20480 -LogFileName "%SystemRoot%\System32\LogFiles\Firewall\pfirewall.log" |
| Найти все включённые правила, разрешающие входящий трафик от Any | Get-NetFirewallRule -Direction Inbound -Action Allow -Enabled True | Get-NetFirewallAddressFilter | Where-Object { $\_.RemoteAddress -eq 'Any' } | Select-Object InstanceID |
| Блокировка опасных портов для NetBIOS и SMB вне локальной сети | New-NetFirewallRule -DisplayName "Block SMB from Internet" -Direction Inbound -Protocol TCP -LocalPort 445 -RemoteAddress Internet -Action Block |

Проверочный минимум по брандмауэру: профили активны, default action на входящий трафик - **Block**, логирование сброшенных пакетов включено хотя бы на 20 МБ, нет правил с **RemoteAddress = Any** на критичных портах. Эти четыре среза закрывают большую часть базовых проблем конфигурации.

Брандмауэр контролирует, что пускать в сеть и из сети. Но прежде чем стек дойдёт до фильтрации, имя узла из приложения нужно превратить в конкретный **IP**-адрес. Этим занимаются вспомогательные протоколы поверх **TCP/IP** - **LLMNR**, **NBNS**, **mDNS** и **WINS**.
