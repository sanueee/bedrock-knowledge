# Расширенное журналирование

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Расширенное журналирование
>
> **Кейсы:** [3.09 Расширенное журналирование](../../cases/windows/3.09%20Расширенное%20журналирование.md)

Стандартная политика аудита Windows - это компромисс между полнотой информации и производительностью. По умолчанию многие важные категории отключены или работают на уровне широких групп, без детализации. Для специалиста по безопасности этого недостаточно: чтобы видеть конкретные события - запуск процесса с полной командной строкой, изменение политики аудита, создание задач планировщика - нужно настраивать аудит на уровне подкатегорий. Microsoft называет это **расширенной политикой аудита** (**Advanced Audit Policy**). Подробности - в [**Advanced Audit Policy Configuration**](https://learn.microsoft.com/en-us/windows/security/threat-protection/auditing/advanced-security-audit-policy-settings) на Microsoft Learn.

> **Аналогия:** Стандартный аудит Windows - как заголовки новостей в утренней газете: знаешь, что что-то произошло, но без деталей. Расширенный аудит - полный репортаж: кто, когда, чем именно, в какой последовательности. Стандартный покажет "был неуспешный вход", расширенный добавит "из подкатегории Logon, тип входа 10 (RDP), с конкретного IP, по конкретной учётной записи".

### Базовый vs расширенный аудит

Стандартная политика аудита (**secpol.msc -> Local Policies -> Audit Policy**) работает на уровне **9 широких категорий**: вход в систему, доступ к объектам, изменения учётных записей и так далее. Включение категории целиком означает, что аудит начинает писать **все** события этой категории - и полезные, и мусорные.

Расширенная политика аудита (**secpol.msc -> Advanced Audit Policy Configuration**) разбивает эти 9 категорий на **58 подкатегорий**.

![](../../_images/549ba39f7e1e.webp)

Проверить текущие настройки расширенного аудита можно командой: `auditpol /get /category:*`

Команда выводит все 58 подкатегорий с текущим состоянием (Success, Failure, оба или No Auditing).

### Минимальный набор логирования

Минимальный набор подкатегорий для аудита:

| Подкатегория | Категория | Почему важно |
|---|---|---|
| Audit Process Creation | Detailed Tracking | Event ID 4688 - запуск любого процесса (разбирался в Базовом журналировании) |
| Audit Logon | Logon/Logoff | Event ID 4624 , 4625 - входы и неудачные попытки входа |
| Audit Special Logon | Logon/Logoff | Event ID 4672 - вход учётной записи с административными правами |
| Audit Security Group Management | Account Management | Event ID 4732 - добавление пользователя в локальную группу (например, Administrators ) |
| Audit User Account Management | Account Management | Event ID 4720 , 4726 - создание и удаление учётных записей |
| Audit Policy Change | Policy Change | Event ID 4719 - изменение политики аудита (критично - именно этим атакующие отключают логирование) |
| Audit Audit Policy Change | Policy Change | Event ID 4902 - изменения настроек расширенного аудита |
| Audit Other Object Access Events | Object Access | Event ID 4698 - создание задач планировщика (типичная техника закрепления) |
| Audit Security System Extension | System | Event ID 7045 - установка новой службы (используется PsExec и аналогичными инструментами) |

Включить нужную подкатегорию из командной строки:

| Для чего | Команда |
|---|---|
| Включить аудит создания процессов (успех + неудача) | auditpol /set /subcategory:"Process Creation" /success:enable /failure:enable |
| Включить аудит входов | auditpol /set /subcategory:"Logon" /success:enable /failure:enable |
| Включить аудит изменений в группах безопасности | auditpol /set /subcategory:"Security Group Management" /success:enable /failure:enable |
| Включить аудит изменения политик аудита | auditpol /set /subcategory:"Audit Policy Change" /success:enable /failure:enable |

В корпоративной среде эти настройки применяются через **GPO** на **Default Domain Policy** или специальную политику для серверов и рабочих станций.

### Включить запись командной строки в Event ID 4688

По умолчанию **Event ID 4688** фиксирует только **имя** запущенного процесса. Без командной строки в логе виден **powershell.exe**, но не видно, что именно через него выполнялось. Это критичный пробел: большинство атак, использующих **PowerShell**, отличаются именно содержимым команды (флаги **-ExecutionPolicy Bypass**, **-EncodedCommand** с **Base64**-нагрузкой и так далее).

Включить запись командной строки в **Event ID 4688** через **GPO**:

**Computer Configuration -> Administrative Templates -> System -> Audit Process Creation -> Include command line in process creation events -> Enabled**.

Или через реестр одной командой: `reg add "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System\Audit" /v ProcessCreationIncludeCmdLine_Enabled /t REG_DWORD /d 1 /f`

После включения **Event ID 4688** начинает содержать полную командную строку. Типичная запись после включения выглядит так:

```
Process Information:
    New Process Name: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
    Process Command Line: powershell.exe -ExecutionPolicy Bypass -enc SGVsbG8gV29ybGQ=
```

Без этой настройки **PowerShell**-атаки видны как "запустился **powershell.exe**" - что в нормальной системе происходит десятки раз в сутки и не вызывает никакого алерта.

Расширенные подкатегории аудита и командная строка в **Event ID 4688** - это первая половина задачи. Вторая - не потерять собранные события при компрометации хоста. Если атакующий получил права администратора, он первым делом попробует очистить журнал или подменить настройки аудита локально. Чтобы этого не произошло, события должны попадать на отдельный коллектор как можно раньше. Для этого Windows предлагает встроенный механизм - **Windows Event Forwarding (WEF)**.

### Централизованный сбор: Windows Event Forwarding (WEF)

**Windows Event Forwarding (WEF)** - встроенный механизм Windows для централизованного сбора событий с множества хостов на один выделенный коллектор. Без него картина безопасности фрагментирована: события входа живут на одной машине, запуск процессов - на рабочей станции, и атаку, затрагивающую несколько хостов, практически невозможно обнаружить вовремя.

> **Аналогия:** Без **WEF** в крепости каждый часовой ведёт свой журнал дежурства, и никто не сводит их вместе. **WEF** - это центральный журнал, куда каждый часовой автоматически отправляет копию своих записей. Командир видит полную картину, не обходя каждый пост вручную.

#### Архитектура WEF

В схеме **WEF** участвуют два компонента:

- **Event Source** - любой Windows-хост, с которого собираются события
- **Event Collector** - выделенный Windows-сервер, который принимает события и хранит их в журнале **Forwarded Events**

Передача происходит по протоколу **WS-Management** (**WinRM**) через порт **TCP 5985** (**HTTP**) или **TCP 5986** (**HTTPS**).

![](../../_images/2df2d784d224.webp)

Два режима работы **WEF**:

| Режим | Кто инициирует соединение | Когда использовать |
|---|---|---|
| Push (Source-initiated) | Источник сам подключается к коллектору | Основной режим. Масштабируется на тысячи хостов через GPO |
| Pull (Collector-initiated) | Коллектор сам опрашивает источники | Редко. Только для небольших инфраструктур или хостов вне домена |

## Настройка коллектора

Базовые шаги для настройки сервера, который будет принимать события:

| Для чего | Команда |
|---|---|
| Установить службу Windows Event Collector в автозапуск и запустить её | sc config wecsvc start=auto ; net start wecsvc |
| Настроить WinRM на коллекторе (быстрая инициализация) | winrm quickconfig -quiet |

Дополнительно нужно дать **WinRM** права на чтение журналов на источниках. Служба **WinRM** на источниках пересылает события от имени учётной записи **NETWORK SERVICE**. По умолчанию она не имеет доступа к журналу **Security**. Нужно добавить **NETWORK SERVICE** в локальную группу **Event Log Readers** на каждом источнике - через **GPO**:

**Computer Configuration -> Policies -> Windows Settings -> Security Settings -> Restricted Groups** - добавить **NETWORK SERVICE** в **Event Log Readers**.

### Настройка источников через GPO

Все источники в домене настраиваются одной политикой - **SEC-WEF-EventForwarding** - и применяются к нужным **OU**.

**Шаг 1.** Указать адрес коллектора:

**Computer Configuration -> Policies -> Administrative Templates -> Windows Components -> Event Forwarding -> Configure target Subscription Manager**

В поле адреса: `Server=http://COLLECTOR-HOSTNAME:5985/wsman/SubscriptionManager/WEC,Refresh=60`

**Шаг 2.** Включить **WinRM** на источниках. Нужны два **GPO**-параметра - один запускает службу, второй разрешает входящие подключения:

- **Computer Configuration -> Policies -> Windows Settings -> Security Settings -> System Services -> Windows Remote Management (WS-Management)** = **Automatic**.
- **Computer Configuration -> Policies -> Administrative Templates -> Windows Components -> Windows Remote Management (WinRM) -> WinRM Service -> Allow remote server management through WinRM** = **Enabled**.

Первый параметр гарантирует, что служба запущена. Второй - что она принимает входящие подключения от коллектора.

**Шаг 3.** Добавить **NETWORK SERVICE** в **Event Log Readers** на источниках (см. выше).

### Подписки: что именно собирать

Подписка - это правило на коллекторе, определяющее, с каких хостов, какие события и в каком режиме собирать. Подписки задаются в **XML** и применяются через **wecutil**.

Основные команды управления подписками:

| Для чего | Команда |
|---|---|
| Список всех подписок | wecutil es |
| Статус конкретной подписки | wecutil gs "DC-SecurityEvents" |
| Создать подписку из XML -файла | wecutil cs subscription.xml |
| Удалить подписку | wecutil ds "DC-SecurityEvents" |

Базовый набор подписок, которые имеет смысл создать в любой инфраструктуре.

**Подписка 1: Аутентификация и входы**:

```
<QueryList>
  <Query Id="0">
    <Select Path="Security">
      *[System[(EventID=4624 or EventID=4625 or EventID=4634 or
       EventID=4648 or EventID=4768 or EventID=4769 or
       EventID=4771 or EventID=4776)]]
    </Select>
  </Query>
</QueryList>

```

**Подписка 2: Управление учётными записями**:

```
<QueryList>
  <Query Id="0">
    <Select Path="Security">
      *[System[(EventID=4720 or EventID=4722 or EventID=4724 or
       EventID=4725 or EventID=4726 or EventID=4728 or
       EventID=4732 or EventID=4738 or EventID=4740)]]
    </Select>
  </Query>
</QueryList>

```

**Подписка 3: Запуск процессов** (требует включённого аудита **Process Creation** и командной строки):

```
<QueryList>
  <Query Id="0">
    <Select Path="Security">*[System[(EventID=4688)]]</Select>
  </Query>
</QueryList>

```

**Подписка 4: Изменения политик аудита** (критически важна для детекта попыток ослепить мониторинг):

```
<QueryList>
  <Query Id="0">
    <Select Path="Security">
      *[System[(EventID=4719 or EventID=4817 or EventID=1102)]]
    </Select>
  </Query>
</QueryList>

```

**Подписка 5: PowerShell Script Block Logging** (Event ID **4103**, **4104** разбирались в Базовом журналировании):

```
<QueryList>
  <Query Id="0">
    <Select Path="Microsoft-Windows-PowerShell/Operational">
      *[System[(EventID=4103 or EventID=4104)]]
    </Select>
  </Query>
</QueryList>
```

### Диагностика WEF

Когда что-то не работает, проверка идёт с двух сторон - на коллекторе и на источнике.

На коллекторе:

| Для чего | Команда |
|---|---|
| Список всех подписок | wecutil es |
| Статус конкретной подписки и количество событий | wecutil gr "ИМЯ_ПОДПИСКИ" |

На источнике:

| Для чего | Команда |
|---|---|
| Проверить, что служба WinRM работает | sc query winrm |
| Проверить связь с коллектором по WinRM | winrm id -remote:COLLECTOR-HOSTNAME |

Частые причины отсутствия событий:

| Симптом | Вероятная причина | Решение |
|---|---|---|
| Источник не появляется в подписке | GPO не применилась | gpupdate /force , проверить gpresult /r |
| Ошибка Access Denied | NETWORK SERVICE не в группе Event Log Readers | Добавить через GPO Restricted Groups |
| Задержка событий часами | Режим доставки MinBandwidth | Переключить на MinLatency |

#### Масштабирование

При размерах инфраструктуры от тысяч хостов один коллектор не справляется. Используются промежуточные коллекторы по типам хостов:

**Рабочие станции (500)-> Промежуточный коллектор 1** **Серверы (200) -> Промежуточный коллектор 2 -> Центральный SIEM** **Контроллеры домена -> Промежуточный коллектор 3**

### WEF и SIEM

**WEF** только собирает и хранит события в журнале **Forwarded Events** на коллекторе. Анализ, корреляция и обнаружение аномальной активности требуют отдельных средств защиты - например, **SIEM** (разбирался ранее в курсе). Типичная связка:

1. Источники пересылают события на **WEF**-коллектор
2. На коллекторе события накапливаются в журнале **Forwarded Events**
3. **SIEM** получает события с коллектора - способ зависит от конкретной системы: агент на коллекторе (**Winlogbeat**, **NXLog**), опрос через **WinRM**/**API** или **syslog**-пересылка
4. **SIEM** агрегирует события со всей инфраструктуры, строит дашборды и применяет правила обнаружения

#### Способы обхода WEF

**WEF** - инфраструктурный сервис, и атакующие давно научились его обходить. Основные техники и то, как их обнаруживать:

| Атака | Метод | Обнаружение |
|---|---|---|
| Остановка WinRM на источнике | net stop winrm | Event ID 7036 в System Log , алерт на исчезновение хоста из подписки |
| Очистка журнала до пересылки | wevtutil cl Security | Event ID 1102 (если успел переслаться), режим MinLatency |
| Переполнение журнала | Генерация шумовых событий | Мониторинг резкого всплеска событий одного типа за короткий промежуток времени, алерт в SIEM |

Расширенный аудит даёт нам нужные категории и **Event ID 4688** с командной строкой. Но и он работает поверх более низкоуровневой инфраструктуры - **Event Tracing for Windows (ETW)**. Понимание **ETW** нужно специалисту по двум причинам: на нём построены практически все инструменты мониторинга Windows (включая сам **Event Viewer**), и именно его атакующие используют для обхода журналирования.
