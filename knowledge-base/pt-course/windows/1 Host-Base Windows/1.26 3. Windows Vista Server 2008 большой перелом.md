# 3. Windows Vista / Server 2008: большой перелом

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Эволюция Windows NT

**Vista** часто вспоминают как спорную пользовательскую ОС. Для ядра и безопасности это один из самых важных релизов в истории Windows. Большинство механизмов, которые сегодня считаются базовыми, появились именно здесь.

**User Account Control (UAC)** До **Vista** типичный корпоративный пользователь работал с правами администратора постоянно - иначе половина приложений не запускалась. **UAC** изменил эту модель: пользователь может быть членом группы администраторов, но его обычные процессы запускаются с ограниченным токеном, а права повышаются только при явном подтверждении ([**UAC**](https://learn.microsoft.com/en-us/windows/win32/secauthz/user-account-control)). Важно понимать ограничения: **UAC** - **не граница безопасности**, Microsoft прямо это признаёт. Задача **UAC** не заблокировать атаку, а заставить атакующего сделать лишний заметный шаг, который можно залогировать. Обходов **UAC** задокументировано несколько десятков, и большинство из них работают без каких-либо предупреждений пользователю. **UAC** повышает стоимость атаки, но не делает её невозможной.

**Mandatory Integrity Control (MIC)** MIC добавил в модель безопасности Windows уровни целостности: **Low**, **Medium**, **High**, **System**. Каждый процесс и каждый объект (файл, ключ реестра, именованный канал) получает уровень. Правило простое: процесс не может **писать** в объект с более высоким уровнем целостности, даже если **DACL** формально разрешает доступ ([**MIC**](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)). Практический пример: **Internet Explorer** в **Vista** запускался на уровне **Low Integrity**. Даже если атакующий полностью скомпрометировал браузер через уязвимость, процесс не мог записать файл в папку пользователя или изменить ключи реестра - они имеют уровень **Medium**. Это та же идея, что лежит в основе современных браузерных **sandbox**. Связанный механизм - **UIPI** (**User Interface Privilege Isolation**): процесс с низкой целостностью не может отправлять оконные сообщения (**SendMessage**, **PostMessage**) процессам с более высокой целостностью, что закрывает класс атак через **UI**-автоматизацию.

**Session 0 Isolation** До **Vista** все процессы - и службы Windows, и интерактивные приложения пользователя - работали в одной сессии. Это позволяло вредоносному коду взаимодействовать со службами через общие объекты, окна и именованные каналы. **Vista** разделила их: службы ушли в **Session 0**, пользовательские сессии начинаются с **Session 1** и выше. Прямое взаимодействие между ними теперь требует явных межсессионных механизмов. Это закрыло целый класс атак, где вредоносный код через **GUI** получал доступ к привилегированным службам в той же сессии.

**Address Space Layout Randomization (ASLR)** **ASLR** рандомизирует адреса, по которым загружаются модули, стек и куча при каждом запуске процесса ([**ASLR**](https://learn.microsoft.com/sv-se/cpp/build/reference/dynamicbase-use-address-space-layout-randomization)). До **ASLR** адрес любой функции в **kernel32.dll** или **ntdll.dll** был одинаков на всех машинах с одной версией Windows - exploit мог жёстко прописывать адреса перехода. **ASLR** убирает эту предсказуемость. В связке с **DEP** это существенно усложняет эксплуатацию: чтобы обойти оба механизма, нужно либо найти модуль, скомпилированный без поддержки **ASLR**, либо получить утечку адреса из памяти процесса, либо строить **ROP**-цепочку вслепую. Каждый из этих путей сложнее и заметнее, чем атака на систему без этих защит.

**BitLocker** Шифрование целых томов, включая системный диск, с привязкой к TPM ([**BitLocker overview**](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/hh831713%28v%3Dws.11%29)). В отличие от **EFS**, который шифрует отдельные файлы и зависит от сессии пользователя, **BitLocker** шифрует всё - и расшифровка происходит только если цепочка загрузки не изменилась (это проверяет **TPM**). При правильной конфигурации - **TPM** + **PIN** - физический доступ к диску ничего не даёт: без **PIN** **TPM** не отдаст ключ. Важная деталь для ИБ: **BitLocker** без **PIN** (только **TPM**) автоматически расшифровывает диск при загрузке на оригинальном железе. Это защищает от кражи диска, но не защищает от атаки на спящую или выключенную машину с оригинальным ноутбуком (например, **cold boot** или **DMA**), так как ключи шифрования остаются в памяти или передаются по шине.

**Windows Display Driver Model (WDDM)** До **Vista** графические драйверы работали целиком в ядре - сбой драйвера означал синий экран. **WDDM** перенёс основную часть драйвера в пространство пользователя, оставив в ядре только минимально необходимое ([**WDDM**](https://learn.microsoft.com/sk-sk/windows-hardware/drivers/display/windows-vista-display-driver-model-design-guide)). С точки зрения безопасности: **GPU**-драйверы перестали быть прямым путём в ядро через эксплуатацию ошибок рендеринга. Сбой драйвера теперь восстанавливается без перезагрузки. **GPU**-драйверы по-прежнему остаются интересной целью для атак - но планка стала выше.

**Обязательная подпись kernel-mode драйверов на x64** Начиная с **Vista x64**, все драйверы в ядре обязаны иметь цифровую подпись, доверенную Microsoft. Неподписанный драйвер не загрузится - код ошибки 52. Это принципиально изменило ситуацию с руткитами: раньше достаточно было скомпилировать драйвер и загрузить. Теперь нужно либо получить подпись (что требует идентификации), либо эксплуатировать уязвимость в уже подписанном драйвере - техника **BYOVD** (**Bring Your Own Vulnerable Driver**), которая стала ответом атакующих на это требование.

**Server Core** **Windows Server 2008** принёс режим установки без графической оболочки: нет **Explorer**, нет **DWM**, нет большинства GUI-компонентов - только консоль, **PowerShell** и **WinRM** ([**Server Core 2008**](https://learn.microsoft.com/en-us/windows-server/administration/server-core/what-is-server-core-2008)). Меньше установленных компонентов - меньше уязвимостей, требующих патчинга. Меньше запущенных служб - меньше поверхность атаки.

**Hyper-V как тип-1 гипервизор** Ключевой момент, который важно понять правильно: **Hyper-V** - это не программа для запуска виртуальных машин, которая работает поверх Windows. Это **тип-1 гипервизор**: после его включения именно гипервизор загружается первым и оказывается ниже всего остального. Сама Windows - включая ядро NT - работает как управляющая виртуальная машина (**parent partition**) поверх гипервизора ([**Hyper-V**](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/overview)). Именно это объясняет, почему **VBS** и **Credential Guard** работают так, как работают: гипервизор стоит ниже ядра и может защищать области памяти, недоступные даже скомпрометированному ядру.
