# LLMNR / NBNS / mDNS / WINS

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Сетевой стек Windows и удалённое управление
>
> **Кейсы:** [3.06 NFS](../../cases/windows/3.06%20NFS.md), [3.07 Сетевой стек](../../cases/windows/3.07%20Сетевой%20стек.md)

Не вся работа сетевого стека Windows завязана на **DNS**. Когда обычный **DNS** недоступен или не дал ответа, Windows автоматически активирует семейство широковещательных протоколов разрешения имён - **LLMNR**, **NBNS**, **mDNS**, исторически также **WINS**. Каждый из них решает свою задачу и каждый имеет известные проблемы безопасности, разбираемые ниже.

Порты:

- **LLMNR**: UDP/TCP 5355
- **NBNS**: UDP 137
- **NetBIOS Datagram**: UDP 138
- **NetBIOS Session**: TCP 139
- **mDNS**: UDP 5353
- **WINS**: UDP 137
- **Репликация WINS**: TCP/UDP 42

## LLMNR

**Link-Local Multicast Name Resolution** (LLMNR) - механизм поиска имени в локальном сегменте, который включается, когда обычный **DNS** не дал ответа. Хост рассылает multicast-запрос на порт **UDP 5355** (**TCP** опционально), любой узел подсети может на этот запрос ответить - именно это и делает атакующий, подменяя имя несуществующим. Подробности протокола - в спецификации [**MS-LLMNRP**](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-llmnrp/eed7fe96-9013-4dec-b14f-5abf85545385) на Microsoft Learn.

## NBNS

**NetBIOS Name Service** (NBNS) - старый механизм разрешения **NetBIOS**-имён в **IPv4**-адреса, исторически тесно связанный с **NetBIOS over TCP/IP**. Работает на портах **UDP 137-138** и **TCP 139**, хранит соответствия "**NetBIOS**-имя -> **IPv4**". На современных хостах его обычно отключают, но многие домены оставляют включённым из соображений совместимости со старыми приложениями. Полное описание - в спецификации [**MS-NBTE**](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-nbte/d9422cdb-0a41-4c10-83e5-c790c537b488).

## mDNS

**Multicast DNS** (mDNS) - механизм для локального обнаружения устройств и сервисов в подсети. Чаще всего встречается в сценариях обнаружения сетевых принтеров, **Apple**-совместимых устройств и сервисов через **DNS-SD**. Работает через порт **UDP 5353** и multicast-адрес **224.0.0.251**. Microsoft отдельно отмечает, что [**Zero Trust DNS**](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/zero-trust-dns/considerations-zero-trust-dns) ломает традиционное обнаружение через **mDNS**.

## WINS

**Windows Internet Name Service** (WINS) - централизованная служба регистрации и разрешения **NetBIOS**-имён, разворачиваемая на отдельном **Windows Server**. Microsoft описывает [**WINS**](https://learn.microsoft.com/en-us/windows-server/networking/technologies/wins/wins-top) как устаревшую службу и рекомендует не разворачивать её в новых сетях, переходя на **DNS**. Сейчас **WINS** встречается главным образом в старых корпоративных средах с legacy-приложениями, которые требуют **NetBIOS**-имена.

## Файл hosts

Перед обращением к **DNS** или к multicast-протоколам типа **LLMNR** Windows проверяет статический файл **C:\Windows\System32\drivers\etc\hosts**. Если имя нашлось там - запрос дальше не идёт. Это исторический механизм с высоким приоритетом, который используется как при легитимной локальной настройке, так и для скрытного перенаправления трафика: к примеру, запись **192.168.1.100 mybank.com** в **hosts** мгновенно переводит пользователя на ложный сайт без всяких **DNS**-запросов.

У этих протоколов (за исключением WINS, использующего unicast) есть общие архитектурные слабости, которые делают их идеальной целью для атак типа спуфинг.

> **Спуфинг** - это класс атак, основанный на подмене источника или маскировке под доверенный узел (подмена IP-адреса, MAC-адреса, email или DNS-имени).
> 
> 
> 
> *В контексте локальных сетей* механика атаки проста: когда компьютер жертвы ищет какой-то ресурс и отправляет запрос в сеть, атакующий отвечает первым и говорит: "Этот ресурс — это я". Жертва верит и передает злоумышленнику свои данные для авторизации.

## Пример сценария атаки на LLMNR/NBNS/mDNS

**LLMNR/NBNS Poisoning** (MITRE ATT&CK: [**T1557.001**](https://attack.mitre.org/techniques/T1557/001/)).

Перехват **NTLM**-аутентификации жертвы через подмену ответа на широковещательный запрос разрешения имени.

Механизм атаки:

1. **Промах DNS**: Жертва пытается разрешить имя **\FILESERVER**, которое отсутствует в **DNS** (опечатка, забытый сервер, скан внутренней сети)
2. **Multicast-запрос**: Хост рассылает **LLMNR**/**NBNS** multicast-запрос в локальную подсеть
3. **Подмена**: Атакующий в той же подсети отправляет поддельный ответ со своим **IP** - быстрее, чем легитимный сервер успевает отказать
4. **Подключение**: Жертва открывает **SMB**-сессию к машине атакующего, что автоматически инициирует **NTLM**-аутентификацию
5. **Захват**: На руках у атакующего - **NetNTLMv2**-хэш жертвы. Дальнейшие действия - офлайн-взлом хэша или ретрансляция (**NTLM Relay**, разбирается в подразделе про **NTLM**)

Условие успеха атаки - присутствие атакующего в том же **L2**-сегменте, что и жертва. Никаких особых привилегий не требуется.

![](../../_images/d07149e51282.webp)

Поскольку этот вектор атаки эксплуатирует фундаментальные механизмы работы Windows в локальной сети, защита должна выстраиваться комплексно. Чтобы обезопасить инфраструктуру от класса атак LLMNR/NBNS Spoofing (и последующего NTLM Relay), необходимо внедрить следующие настройки:

- Отключить **LLMNR** через **GPO**
- Отключить **NetBIOS over TCP/IP** на всех адаптерах
- Включить **SMB Signing**
- Использовать локальные имена с суффиксом домена (например, **fileserver.corp.local**)
- Включить **Extended Protection for Authentication (EPA)** для **NTLM**

После того как имя превращается в адрес, на сцену выходит главный протокол файлового и службового обмена в Windows - **SMB**.
