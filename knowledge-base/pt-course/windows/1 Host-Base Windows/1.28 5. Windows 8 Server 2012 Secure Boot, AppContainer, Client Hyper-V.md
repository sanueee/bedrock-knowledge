# 5. Windows 8 / Server 2012: Secure Boot, AppContainer, Client Hyper-V

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Эволюция Windows NT

Релиз спорный по **UI**, но по безопасности и платформе - принципиальный шаг.

**Secure Boot (UEFI)** **Secure Boot** проверяет криптографические подписи всех компонентов цепочки загрузки до того, как они получат управление: загрузчик, драйверы загрузки, ядро ОС ([**Secure Boot**](https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/secure-boot)). Это прямой ответ на **буткиты** - класс вредоносных программ, которые загружаются раньше ОС и поэтому полностью невидимы для любого антивируса внутри системы: к моменту запуска антивируса вредоносный код уже контролирует загрузку. **Secure Boot** разрывает этот сценарий: компонент без доверенной подписи просто не получит управление. Важная деталь: **Secure Boot** защищает цепочку загрузки, но не защищает от атак после загрузки ОС - это зона других механизмов.

**Early Launch Anti-Malware (ELAM)** **ELAM** решает смежную задачу: он позволяет антивирусному драйверу стартовать **раньше** всех остальных сторонних boot-start драйверов ([**ELAM**](https://learn.microsoft.com/en-us/windows/win32/w8cookbook/secured-boot)). Логика простая: если антивирус запускается первым, он видит все последующие драйверы при их загрузке и может оценить их до того, как они получат управление. Без **ELAM** вредоносный boot-start драйвер мог загрузиться раньше антивируса и скрыть своё присутствие. **ELAM** - продолжение цепочки доверия **Secure Boot** уже внутри запущенной ОС.

**Measured Boot** фиксирует состояние каждого компонента цепочки загрузки в регистрах **TPM**. Измерения хранятся в специальном регистре - **Platform Configuration Registers** (**PCR**). Результат нельзя подделать: **TPM** аппаратно гарантирует, что значения PCR отражают реальную последовательность загрузки. **MDM**-системы и **attestation**-сервисы могут запросить у TPM подписанный отчёт о загрузке и убедиться удалённо, что на устройстве загрузилась именно та ОС, именно с теми параметрами, без модификаций. Это основа для соответствия требованиям устройства в **zero-trust** архитектурах: доступ к корпоративным ресурсам предоставляется только устройствам с подтверждённой доверенной загрузкой.

**AppContainer / LowBox** **AppContainer** - **sandbox**-модель для UWP-приложений, развивающая идеи **MIC** до логического предела. Процесс в **AppContainer** получает специально ограниченный токен, практически без привилегий, и может обращаться только к ресурсам, для которых явно объявлены **capabilities** - возможности вроде "доступ к интернету", "доступ к микрофону", "доступ к документам". Никакого доступа к файловой системе или реестру по умолчанию нет вообще. Если приложение в **AppContainer **скомпрометировано, атакующий оказывается в среде с минимальными правами, из которой выбраться без отдельной уязвимости в самом **sandbox**-механизме крайне сложно. Это та же модель изоляции, которую используют современные браузеры для вкладок.

**Client Hyper-V** пришёл на клиентские **Windows 8 Pro** и **Enterprise**. С точки зрения безопасности это важнее, чем кажется: гипервизор на клиентской машине открыл путь к **VBS** в **Windows 10**. Логика следующая: если гипервизор есть на каждой машине, можно использовать его не только для виртуальных машин, но и для изоляции чувствительных компонентов самой ОС.

**Hyper-V в Server 2012: сетевая изоляция и SR-IOV** **Server 2012** превратил **Hyper-V** в полноценную платформу для частного облака - и каждая новая возможность интересна с точки зрения изоляции([**Hyper-V 2012**](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-R2-and-2012/hh831410%28v%3Dws.11%29)).

- **VHDX** заменил старый формат виртуальных дисков: больший максимальный размер, устойчивость к повреждениям при сбое питания.
- **SR-IOV** (**Single Root I/O Virtualization**) даёт виртуальной машине прямой доступ к физическому сетевому адаптеру, минуя виртуальный коммутатор. Производительность растёт - но модель изоляции усложняется: **VM** теперь ближе к железу, чем в стандартной схеме, и трафик такой **VM** сложнее инспектировать средствами хоста.
- **Hyper-V Replica** - асинхронная репликация **VM** на другой хост. Практическое следствие для ИБ: реплика копирует полное состояние **VM**, включая содержимое памяти. Если основная **VM** скомпрометирована, реплика воспроизводит это состояние.
- **Virtual NUMA** позволяет **VM** видеть топологию памяти хоста. Важно для баз данных и нагрузок с высокими требованиями к задержкам доступа к памяти внутри **VM**.

**Resilient File System (ReFS) и Storage Spaces** **ReFS** - файловая система, разработанная для хранилищ с высокими требованиями к целостности. В отличие от NTFS, она умеет обнаруживать и исправлять тихую порчу данных на лету - актуально для серверов, где диск может незаметно возвращать неверные данные без ошибки чтения. **Storage Spaces** - программный RAID поверх обычных дисков, встроенный прямо в Windows: объединяет дешёвые диски в отказоустойчивые пулы без аппаратного контроллера. Для анализа дисков важно: **Storage Spaces** создаёт дополнительный уровень абстракции между ОС и физическим носителем, который нужно учитывать при работе с образами дисков.
