# Уязвимости инфраструктуры журналирования

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Расширенное журналирование
>
> **Кейсы:** [3.09 Расширенное журналирование](../../cases/windows/3.09%20Расширенное%20журналирование.md)

**Инфраструктура журналирования** не защищена от компрометации сама по себе. Атакующий с правами администратора располагает несколькими способами ослепить мониторинг: от грубой очистки журнала до тонкого патчинга функций **ETW** в памяти отдельного процесса. Дальше - конкретные техники и то, что специалист должен видеть в логах при каждой из них.

## Очистка стандартных журналов (Event ID 1102)

Самая прямолинейная техника - очистить журнал **Security** одной командой: `wevtutil cl Security`

Перед физическим стиранием всех записей служба **LSASS** успевает записать последнее **предсмертное событие** - **Event ID 1102** (разбирался в Базовом журналировании). Это **абсолютный красный флаг**: в здоровой корпоративной сети журналы никогда не очищаются вручную. Появление **Event ID 1102** вне технологического окна обслуживания - прямой сигнал к расследованию.

Защита от потери информации - заранее настроенный **WEF** в режиме **MinLatency**: к моменту, когда атакующий выполнит **wevtutil cl**, события уже будут на коллекторе.

## Изменение конфигурации Auditpol (Event ID 4719)

Более тонкая техника - не удалять старые события, а отключить запись новых: `auditpol /set /subcategory:"Process Creation" /success:disable /failure:disable`

Система продолжает работать, служба логов активна, **Event ID 4688** перестаёт генерироваться - и атакующий может спокойно запускать процессы без следов.

Само изменение политики аудита фиксируется как **Event ID 4719** (**Audit Policy Change**). Это сравнительно "тихое" событие, поэтому в инфраструктуре с **SIEM** на него обязательно настраивается отдельный алерт. Без такого алерта **Event ID 4719** теряется в общем потоке - и атака остаётся незамеченной.

## Выгрузка драйвера Sysmon

Если на хосте установлен **Sysmon**, атакующий может выгрузить его драйвер из памяти ядра: `fltMC.exe unload SysmonDrv`

Эффект - служба **Sysmon** в **services.msc** может по-прежнему светиться как работающая, но **телеметрия прекращается полностью**. Никакие **Event ID 1**, **3**, **8**, **10** больше не пишутся.

Детектирование требует мониторинга самого факта вызова **fltMC.exe** через **Event ID 4688** с командной строкой (поэтому важна настройка из подраздела про расширенный аудит) или через **Sysmon Event ID 1** на других хостах, если атакующий пытается выполнить ту же команду на нескольких машинах.

В качестве дополнительной меры защиты можно через **GPO** запретить выполнение **fltMC.exe** непривилегированным процессам или ограничить его выполнение списком конкретных учётных записей.

## Подмена конфигурации Sysmon (Event ID 16)

Если выгрузка драйвера слишком заметна, атакующий может действовать тоньше - подменить **XML**-конфигурацию **Sysmon** так, чтобы тот перестал фиксировать события от конкретного бинарника: `sysmon.exe -c blind_config.xml`

В новом конфиге - правило "игнорировать всё от **backdoor.exe**". Формально **Sysmon** работает, журнал заполняется - но событий от вредоносного процесса в нём нет.

Сам **Sysmon** при любом изменении конфигурации генерирует **Event ID 16** с хэшем нового **XML**-файла. Появление **Event ID 16** вне технологического окна обслуживания - такой же красный флаг, как и **Event ID 1102**.

Защита включает в себя:

- Алерт на **Event ID 16** в **SIEM**
- Контроль прав на каталог установки **Sysmon** - конфиг должен быть защищён от записи обычными пользователями
- Хранение эталонного хэша конфига и регулярное сравнение с реальным

## Патчинг EtwEventWrite в памяти процесса

> **Аналогия:** Патчинг **EtwEventWrite** в памяти процесса - это не отключить запись на пульте охраны (это сразу заметят), а перерезать провод от микрофона в конкретной комнате. На пульте по-прежнему всё горит зелёным, журнал событий заполняется штатно - но из этой комнаты больше не приходит ни звука. Конкретный процесс продолжает выполняться, **PowerShell**-команды отрабатывают - но в логах от них ни следа.

Самая распространённая техника обхода **ETW** в контексте конкретного процесса. Атакующий патчит функцию **EtwEventWrite** в **ntdll.dll** прямо в памяти целевого процесса, заменяя её первый байт инструкцией **RET** (немедленный возврат). После этого все вызовы **ETW** из этого процесса молча игнорируются - события не генерируются.

![](../../_images/3a10e0c9e400.webp)

### Как это работает изнутри

Функция **EtwEventWrite** живёт в **ntdll.dll** - библиотеке, которая загружается в адресное пространство **каждого** процесса. Её пролог в **x64** выглядит примерно так:

```
EtwEventWrite:
    4C 8B DC              mov r11, rsp           ; пролог функции
    49 89 5B 08           mov [r11+8], rbx
    49 89 6B 10           mov [r11+16], rbp
    ...                                          ; дальше логика записи события

```

Атакующий меняет первый байт на **0xC3** (инструкция **RET**):

```
EtwEventWrite (после патча):
    C3                    ret                    ; немедленный возврат
    49 89 5B 08           (мёртвый код - никогда не выполнится)
    ...

```

Теперь любой вызов **EtwEventWrite** из этого процесса немедленно возвращает управление без записи события. **PowerShell** продолжает работать - но **Script Block Logging** (**Event ID 4104**, разбирался в Базовом журналировании) молчит.

Что нужно атакующему для патча:

1. Найти адрес **EtwEventWrite** в памяти процесса
2. Снять защиту страницы памяти через **VirtualProtect** с флагом **PAGE_EXECUTE_READWRITE**
3. Записать **0xC3** по найденному адресу
4. Восстановить защиту страницы

**Важные детали:**

- Патч действует **только внутри текущего процесса**: **ntdll.dll** имеет отдельное отображение в адресном пространстве каждого процесса. Патч в **powershell.exe** не затрагивает **cmd.exe** или другие процессы
- Патч **не переживает перезапуск**: при следующем запуске процесса **ntdll.dll** загрузится заново с диска с оригинальным кодом
- Для патча **чужого процесса** атакующему нужен **WriteProcessMemory** + дополнительные привилегии - это уже инъекция, которая детектируется **Sysmon Event ID 10** (**ProcessAccess** к памяти чужого процесса)

## Отключение провайдера ETW через реестр

Некоторые провайдеры **ETW** можно отключить не патчингом кода в памяти, а простым изменением реестра. Самый известный пример - отключение **Script Block Logging** для **PowerShell**: `reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" /v EnableScriptBlockLogging /t REG_DWORD /d 0 /f`

После этого **Event ID 4104** перестаёт генерироваться - **PowerShell** работает, но финальный декодированный код в журнал не попадает. Это атака на хост, а не на процесс: затрагивает все будущие **PowerShell**-сессии до следующего изменения реестра.

Обнаружение:

- **Event ID 4719** (изменение политики аудита) - срабатывает при изменении настроек, входящих в политики аудита
- **Sysmon Event ID 13** - изменение значения в ключе реестра. Мониторинг веток, связанных с политиками **PowerShell** (**HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\***), даёт прямой алерт

## Остановка ETW-сессии

Атакующий с правами администратора может напрямую остановить именованную **ETW**-сессию - в том числе ту, через которую идут события **Security**: `logman stop "EventLog-Security" -ets`

Это приведёт к прекращению журналирования **Security**-событий **без очистки журнала** - **Event ID 1102 не генерируется**, что делает атаку менее заметной, чем прямая очистка журнала.

Обнаружение - **Event ID 1100** (служба **Event Log** остановлена, разбирался в Базовом журналировании) и мониторинг состояния критических **ETW**-сессий. Простейший скрипт проверки: `$sessions = logman query -ets if ($sessions -notmatch "EventLog-Security") { Write-Warning "КРИТИЧНО: ETW-сессия EventLog-Security не активна!" }`

Скрипт можно запускать раз в несколько минут через **Task Scheduler** и слать оповещение в **SIEM** при срабатывании.

Восемь техник выше - реальный арсенал атакующего против инфраструктуры журналирования. Все они срабатывают, потому что инфраструктура мониторинга по умолчанию настроена на сбор данных, но не на защиту самой себя. Ниже - сводный набор практических действий, которые превращают журналирование из пассивного источника событий в самозащищённую систему.

### Какие механизмы защиты работают на инфраструктуру журналирования

- **Централизация через WEF в режиме MinLatency** - события улетают на коллектор быстрее, чем атакующий успевает их стереть локально
- **Мониторинг Event ID 1102** (очистка журнала **Security**) - один из самых громких индикаторов компрометации
- **Мониторинг Event ID 1100** (остановка службы **Event Log**) - срабатывает при попытках остановить логирование без явной очистки журнала
- **Мониторинг Event ID 4719** (изменение политики аудита) - детектирует **auditpol /set** в руках атакующего
- **Мониторинг Event ID 16** (изменение конфигурации **Sysmon**) - срабатывает при подмене **XML**-конфига
- **Мониторинг состояния критичных ETW-сессий** - регулярная проверка наличия **EventLog-Security** и других ключевых сессий через **logman query -ets**
- **Алерт на исчезновение хоста из подписки WEF** - если хост перестал слать события на коллектор, это либо сетевая проблема, либо целенаправленное отключение **WinRM**
- **Защита Sysmon-конфига от записи** обычными пользователями и ограничение прав на каталог установки
- **Защита драйвера Sysmon от выгрузки** через политику **Group Policy** для запрета **fltMC.exe** непривилегированным процессам
- **Sysmon Event ID 10** (**ProcessAccess** к **lsass.exe** и другим критичным процессам) - детектирует попытки **WriteProcessMemory** для патчинга **EtwEventWrite** в чужом процессе

## Итог: что настроить в первую очередь

Из всего, что разобрано в статьях про расширенное журналирование, есть набор действий, которые в любой инфраструктуре нужно выполнять в первую очередь. Они закрывают наибольшую долю реальных техник атак при минимальных вложениях времени:

| Приоритет | Действие | Эффект |
|---|---|---|
| 1 | Включить аудит Process Creation + командную строку в Event ID 4688 | Видеть, что запускалось и с какими аргументами |
| 2 | Включить PowerShell Script Block Logging | Видеть все PowerShell -команды, включая декодированные Base64 -нагрузки |
| 3 | Настроить WEF на централизованный коллектор в режиме MinLatency | Не потерять логи при очистке на локальном хосте |
| 4 | Установить Sysmon с конфигом SwiftOnSecurity | Закрыть слепые зоны: сетевые подключения, инъекции в процессы, доступ к lsass.exe |
| 5 | Настроить алерты в SIEM на Event ID 1102 , 4719 , 1100 , 16 | Немедленно получать сведения о попытках ослепить мониторинг |
| 6 | Увеличить размер журнала Forwarded Events на коллекторе до 1 ГБ+ | Не терять события при высоком потоке |
| 7 | Мониторинг ETW -сессий и счётчика EventsLost | Обнаруживать атаки на инфраструктуру журналирования (остановка сессий, перегрузка буферов) |
| 8 | Включить Sysmon Event ID 10 на lsass.exe | Детект Pass-the-Hash и патчинга EtwEventWrite в чужом процессе |

Этот восьмипунктовый минимум применим в любой инфраструктуре - от standalone-сервера до домена в несколько тысяч хостов. Дальнейшая работа - подстройка правил **SIEM**, расширение **Sysmon**-конфига и интеграция с **EDR**-решениями - уже зависит от конкретной среды и выходит за рамки базового курса администрирования.
