# Реестр Windows

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Реестр Windows
>
> **Кейсы:** [3.05 Реестр](../../cases/windows/3.05%20Реестр.md)

После того как атакующий разобрался с файловой системой и получил исполнение в нужном контексте, ему остаётся **закрепиться** на хосте и желательно **повысить привилегии**. И первое, и второе он будет делать через реестр. Реестр - любимое место злоумышленника по трём причинам: здесь хранятся автозагрузка и пути исполняемых файлов, здесь конфигурация системы безопасности, и сюда атакующего почти всегда пускают - изменение пользовательской ветки реестра не требует прав администратора.

Эта статья - про то, как устроена главная конфигурационная база Windows и где в этой базе живут уязвимости, на которых строятся самые распространённые техники закрепления и повышения привилегий.

## Что такое реестр

Реестр Windows - это иерархическая бинарная база данных, в которой хранятся настройки системы, драйверов, служб и установленных программ. До эпохи Windows NT каждое приложение хранило свои настройки в отдельных текстовых файлах **.ini**, разбросанных по диску. Реестр объединил всё в одно централизованное хранилище с поддержкой прав доступа, журналирования и удалённого администрирования.

![](../../_images/979ee201dc74.webp)

Реестр организован как дерево. Терминология такая:

- **Куст** (**hive**) - корень дерева. Кустов всего пять, и про каждый нужно знать, где он физически лежит
- **Ключ** - "папка" в реестре. Может содержать подразделы и параметры
- **Подраздел** - ключ внутри другого ключа
- **Параметр** - "файл" в реестре. Имеет имя, тип и данные

Путь в реестре выглядит как файловый, с обратными слэшами: **HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Run**

Здесь **HKEY_LOCAL_MACHINE** - куст, остальное - вложенные ключи, последний из которых (**Run**) обычно содержит параметры.

**Типы параметров.** Каждый параметр реестра имеет тип, который определяет, как Windows интерпретирует его данные. Младший специалист обязан различать пять основных типов:

| Тип | Что хранит | Пример |
|---|---|---|
| REG_SZ | Строка | C:\Windows\System32\notepad.exe |
| REG_EXPAND_SZ | Строка с переменными окружения, разворачиваемая при чтении | %SystemRoot%\System32 |
| REG_DWORD | 32-битное число | 0x00000001 |
| REG_BINARY | Произвольная последовательность байтов | хеш пароля в SAM |
| REG_MULTI_SZ | Массив строк, разделённых нулевыми байтами | список зависимостей службы |

Самый часто встречающийся тип в контексте атак - **REG_DWORD** со значением **1** (включить функциональность) или **0** (выключить). На этом значении строится половина техник, разобранных ниже.

## Кусты и их физическое расположение

Пять кустов реестра существуют только во время работы системы. Реально на диске лежат файлы, которые ядро монтирует при загрузке и при входе пользователя. Чтобы понимать, что именно крадёт атакующий, копируя файл **NTUSER.DAT**, нужно знать соответствие.

| Куст | Что содержит | Физический файл |
|---|---|---|
| HKEY_LOCAL_MACHINE ( HKLM ) | Настройки всей системы | C:\Windows\System32\config\{SYSTEM, SOFTWARE, SECURITY, SAM} |
| HKEY_CURRENT_USER ( HKCU ) | Настройки текущего пользователя | C:\Users\NTUSER.DAT |
| HKEY_USERS ( HKU ) | Профили всех пользователей, у которых открыта сессия | NTUSER.DAT каждого пользователя |
| HKEY_CLASSES_ROOT ( HKCR ) | Объединение HKLM\Software\Classes и HKCU\Software\Classes | виртуальный, не имеет своего файла |
| HKEY_CURRENT_CONFIG ( HKCC ) | Текущий профиль оборудования | ссылка на ветку HKLM\SYSTEM |

Главные кусты, в которые попадает атакующий, - **HKLM** и **HKCU**. Физическое расположение их файлов нужно запомнить: при компрометации хоста злоумышленник часто не редактирует реестр через **regedit**, а просто копирует файлы кустов на свою машину для офлайн-анализа.

**HKLM: настройки всей системы.** **HKEY_LOCAL_MACHINE** - сердце системы. Здесь конфигурация драйверов и служб, список установленных программ, парольная политика, базы учётных записей. Изменения в **HKLM** требуют прав администратора. Внутри куста есть несколько ключевых подразделов:

- **HKLM\SYSTEM** - настройки ядра, драйверов и служб. Внутри лежит **CurrentControlSet\Services**, где для каждой службы прописаны параметры **ImagePath**, **Start**, **ObjectName** - всё то, что разбиралось в предыдущей статье
- **HKLM\SOFTWARE** - настройки установленных программ, общих для всех пользователей. Внутри отдельная ветка **WOW6432Node** для 32-битных программ
- **HKLM\SECURITY** - локальные политики безопасности. По умолчанию недоступен даже администратору, читается только из-под **SYSTEM**
- **HKLM\SAM** - **Security Account Manager**, база локальных учётных записей. Здесь хранятся хеши паролей. Тоже закрыт от чтения; именно эти файлы атакующий копирует для офлайн-извлечения хешей

**HKCU: профиль текущего пользователя.** **HKEY_CURRENT_USER** - не самостоятельный куст, а символическая ссылка на профиль текущего пользователя в **HKEY_USERS**. Физически это файл **NTUSER.DAT** в каталоге профиля. При входе пользователя процесс **userinit.exe** монтирует **NTUSER.DAT** в **HKEY_USERS&lt;SID>**, после чего **HKCU** начинает указывать туда.

Главное свойство **HKCU** с точки зрения безопасности: запись сюда **не требует** прав администратора. Любой процесс, работающий от имени пользователя, свободно меняет его собственный куст. Именно поэтому большинство пользовательских техник закрепления строятся через **HKCU**, а не через **HKLM**.

## Инструменты работы с реестром

Графический редактор - **regedit.exe**, запускается через **Win + R** → **regedit**. Перед любой ручной правкой выделяем изменяемый ключ, нажимаем **File** → **Export** и сохраняем **.reg**-файл. Если что-то сломается, двойной клик по этому файлу восстанавливает исходное состояние.

Консольная утилита - **reg.exe**. Базовые команды: `reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" reg add "HKCU\Software\Test" /v Param /t REG_SZ /d "Hello" /f reg delete "HKCU\Software\Test" /f`

Для скриптов и работы с объектами стандартный инструмент - **PowerShell** с провайдером **Registry**.

## Управление через PowerShell

В **PowerShell** ветки реестра подключены как файловая система: **HKLM:** и **HKCU:** - это полноценные пути, по которым работают те же командлеты, что и в обычном **FileSystem**-провайдере. Все команды этого раздела запускаются от имени администратора, иначе доступ к **HKLM** будет частично закрыт.

| Команда | Что делает |
|---|---|
| Get-ChildItem HKLM:\ | Перечисляет все подразделы корня HKLM . Работает с реестром идентично работе с папками: вместо файлов - ключи, вместо имён файлов - имена ключей |
| Get-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" | Читает все параметры указанного ключа. Возвращает объект, поля которого - имена параметров, значения - их данные. Первая команда при подозрении на закрепление через реестр |
| Get-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" -Name OneDrive | Возвращает один конкретный параметр из ключа Run . Удобно для целевой проверки |
| Set-ItemProperty -Path "HKCU:\Software\TestApp" -Name "LogLevel" -Value 2 -Type DWord | Создаёт или обновляет параметр. -Type DWord указывает тип REG_DWORD . Без явного типа PowerShell выберет тип по умолчанию, что может стать причиной тихих багов в скриптах |
| New-Item -Path "HKCU:\Software\TestApp" -Force | Создаёт несуществующий ключ. -Force перезаписывает существующее значение без запроса |
| New-ItemProperty -Path "HKCU:\Software\TestApp" -Name "Enabled" -Value 1 -PropertyType DWord -Force | Добавляет параметр в ключ |
| Remove-ItemProperty -Path "HKCU:\Software\TestApp" -Name "Enabled" | Удаляет параметр из ключа |
| Remove-Item -Path "HKCU:\Software\TestApp" -Recurse | Удаляет ключ целиком. -Recurse обязательна, если у ключа есть подразделы |
| Get-ChildItem "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run", "HKLM:...\RunOnce", "HKCU:...\Run", "HKCU:...\RunOnce" -ErrorAction SilentlyContinue | ForEach-Object { Get-ItemProperty $_.PSPath } | Сводный аудит четырёх классических веток автозагрузки. Имеет смысл запускать на каждом хосте при подозрении на компрометацию |
| Get-Acl "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" | Format-List | Показывает разрешения на ключ реестра в формате ACL . Если у непривилегированной группы есть право FullControl на ветку Run в HKLM - это уязвимость уровня хоста |

Команды выше покрывают основные операции с реестром через **PowerShell**: чтение, запись, удаление и аудит прав. Для регулярной проверки автозагрузки и **ACL** их удобно объединять в скрипт и запускать по расписанию.

## Уязвимости и атаки

Разобравшись с устройством реестра и инструментами работы с ним, перейдём к тому, как именно атакующий использует эти знания. Ниже - четыре техники, которые встречаются чаще всего.

[**Registry Run Keys (T1547.001)**](https://attack.mitre.org/techniques/T1547/001/). Самая массовая и самая старая техника закрепления через реестр. Четыре классические ветки, любая запись в которых исполняется при следующем входе пользователя:

| Путь | Когда срабатывает |
|---|---|
| HKLM\Software\Microsoft\Windows\CurrentVersion\Run | Каждый вход любого пользователя |
| HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce | Однократно, затем параметр удаляется |
| HKCU\Software\Microsoft\Windows\CurrentVersion\Run | Каждый вход текущего пользователя |
| HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce | Однократно, для текущего пользователя |

В каждом ключе любой параметр типа **REG_SZ** интерпретируется как команда: имя параметра произвольное, значение - путь к исполняемому файлу с возможными аргументами. Атакующему достаточно записать одну строку в **HKCU...\Run** - права администратора не нужны - и его код будет запускаться при каждом входе пользователя в систему. Файловая половина этой же техники - папки **Startup** в профиле пользователя и в **ProgramData** - разбиралась в Статье 5.

Защитное наблюдение: ветка **Run** в **HKLM** требует прав администратора на запись, поэтому всё, что появилось там вне регламентных обновлений, по умолчанию подозрительно. Ветка **Run** в **HKCU** доступна пользователю без повышения, поэтому туда смотрят в первую очередь при разборе пользовательской компрометации.

### AlwaysInstallElevated ([T1078](https://attack.mitre.org/techniques/T1078/) + [T1546](https://attack.mitre.org/techniques/T1546/))

Эта политика позволяет любому пользователю устанавливать **MSI**-пакеты с правами **NT AUTHORITY\SYSTEM**. Изначально она задумана для централизованной установки одобренного администратором софта в корпоративной среде, но при включении становится прямой дорогой к повышению привилегий.

Уязвимость существует, когда оба параметра ниже выставлены в **1**:

- **HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer\AlwaysInstallElevated = REG_DWORD 1**
- **HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer\AlwaysInstallElevated = REG_DWORD 1**

Атакующий проверяет их одной командой: `Get-ItemProperty "HKLM:\SOFTWARE\Policies\Microsoft\Windows\Installer", ` "HKCU:\SOFTWARE\Policies\Microsoft\Windows\Installer" -ErrorAction SilentlyContinue`

Если оба значения равны **1**, он генерирует **MSI**-пакет с полезной нагрузкой (например, через **msfvenom**) и запускает его обычной командой `msiexec /quiet /qn /i payload.msi`. Установщик отрабатывает от имени **SYSTEM**, полезная нагрузка получает системные привилегии. Перезагрузка не требуется, аудита установки **MSI**-пакета по умолчанию нет. Это одна из самых популярных мишеней утилит автоматического аудита привилегий (**WinPEAS**, **PowerUp**, **SharpUp**).

### Image File Execution Options - IFEO Debugger Hijack ([T1546.012](https://attack.mitre.org/techniques/T1546/012/))

Изначально **IFEO** - легитимный механизм, позволяющий разработчику автоматически подключать отладчик к выбранной программе при её запуске. Описывается параметром **Debugger** в ключе: **HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options&lt;executable>**

Когда Windows запускает процесс с именем **&lt;executable>**, ядро проверяет, есть ли для него **Debugger**, и если есть - запускает указанный путь, передавая ему имя исходной программы как аргумент. Атакующий злоупотребляет этими двумя способами.

Первый - **закрепление и повышение привилегий**. Прописывается **Debugger = C:\path\to\evil.exe** для часто запускаемой программы (например, **notepad.exe**). При следующем запуске блокнота вместо него запускается **evil.exe**. Знаменитый вариант - подмена для **utilman.exe** (Ease of Access на экране входа): на экране блокировки нажатие сочетания **Win + U** запускает **utilman**, который из-за IFEO превращается в **cmd.exe**, и атакующий получает **SYSTEM**-консоль ещё до входа пользователя.

Второй - **подавление защиты**. Атакующий регистрирует невалидный отладчик для **MsMpEng.exe**, **WinDefend** или агента **EDR**, и при попытке системы запустить процесс защиты тот падает с ошибкой. **MITRE** относит это к [**T1562 - Impair Defenses**](https://attack.mitre.org/versions/v16/techniques/T1562/001/).

### AppInit_DLLs ([T1546.010](https://attack.mitre.org/techniques/T1546/010/))

Параметр **AppInit_DLLs** в ключе: **HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows** содержит список **DLL**-файлов, которые загружаются в **каждый процесс**, использующий библиотеку **user32.dll**. В современной Windows это подавляющее большинство пользовательских процессов: проводник, браузер, офисный пакет, любая программа с окнами. Для активации также требуется выставить **LoadAppInit_DLLs = 1** в том же ключе. Для 32-битных процессов аналогичный ключ - **HKLM\SOFTWARE\Wow6432Node\Microsoft\Windows NT\CurrentVersion\Windows**.

Положив свою библиотеку в этот список, атакующий получает одновременно **закрепление** (DLL загрузится в каждый новый процесс при следующей загрузке системы) и **массовый инжект кода** в адресные пространства доверенных процессов. Это эффективно эквивалентно глобальному **Process Injection** силами самой Windows.

Хорошая новость: начиная с Windows 8 при **включённом Secure Boot** механизм **AppInit_DLLs** отключён по умолчанию на уровне ядра. **Microsoft** официально не рекомендует его использовать. Однако на хостах с устаревшими конфигурациями, унаследованными политиками или без **Secure Boot** в **UEFI** этот вектор по-прежнему работает.

## Защита и обнаружение

- **Контроль автозагрузки**. Регулярный аудит четырёх веток **Run/RunOnce** в **HKLM** и **HKCU**, а также папок **Startup** - базовая гигиена. Утилита **Autoruns** из пакета **Sysinternals** показывает все известные точки автозагрузки Windows в одном окне, включая ветки реестра, папки Startup, запланированные задачи и службы. Запускайте её на любом хосте с подозрительным поведением до запуска антивирусов
- **Отключение AlwaysInstallElevated**. На любой машине, где политика не используется намеренно, оба параметра в **HKLM** и **HKCU\SOFTWARE\Policies\Microsoft\Windows\Installer** должны быть либо равны **0**, либо отсутствовать. На уровне **GPO** настраивается через **Computer Configuration → Administrative Templates → Windows Components → Windows Installer** и зеркальный путь в **User Configuration**
- **Защита от IFEO**. Аудит ключа **Image File Execution Options** на наличие параметров **Debugger** для системных и защитных бинарников. Нормальные **Debugger** существуют только для отладочных сценариев и должны быть документированы. На хостах в продакшене этой ветки в норме нет, любое появление - инцидент
- **Отключение AppInit_DLLs**. Включите **Secure Boot** в **UEFI** - это автоматически блокирует механизм. Дополнительно проверяйте, что параметры **AppInit_DLLs** и **LoadAppInit_DLLs** в **HKLM...\Windows NT\CurrentVersion\Windows** (и в **Wow6432Node**) пусты или равны **0**
- **Мониторинг изменений реестра**. **Sysmon** **Event ID 12** (создание ключа), **Event ID 13** (изменение значения), **Event ID 14** (переименование ключа) с правильно настроенным фильтром - основа детектирования всех описанных атак. В Security-журнале аналогом служит **Event ID 4657** при включённом аудите объектов реестра через **NTFS ACL**. Детальная настройка Sysmon и пример конфигурации с фильтрами по веткам **Run**, **Image File Execution Options** и **Policies\Microsoft\Windows\Installer** разбираются в статье про журналирование
- **Бэкап перед правкой**. Любая ручная модификация **HKLM\SYSTEM\CurrentControlSet\Services**, **HKLM\SECURITY**, **HKLM\SAM** или критичных веток автозагрузки начинается с **File → Export** в **regedit** или с создания точки восстановления системы
