## MS-RPC

**MS-RPC** (Remote Procedure Call) - это базовая инфраструктура Windows, позволяющая программам вызывать функции на удалённых компьютерах так же легко, как если бы они работали локально. Подавляющее большинство штатных средств удалённого администрирования - удалённое управление службами через **services.msc**, постановка задач в Task Scheduler, удалённый реестр, удалённое управление принтерами - построены поверх **MS-RPC**. Чтобы понимать, как программы находят друг друга в сети без жёсткой привязки к конкретному порту, достаточно разобрать базовую механику подключения MS-RPC:

Каждый доступный для вызова сервис (RPC-интерфейс) имеет свой уникальный идентификатор - **UUID**. При запуске сервис динамически занимает свободный порт (обычно из диапазона 49152-65535/TCP) или именованный канал и регистрирует эту информацию у системной службы Endpoint Mapper. Когда клиент хочет подключиться, он сначала обращается к Endpoint Mapper на стандартный порт TCP 135 и спрашивает: "На каком порту сейчас работает сервис с таким-то UUID?". Получив ответ, клиент подключается уже напрямую к нужному сервису.

Такая двухступенчатая схема выбрана не случайно. Если бы каждая системная служба сидела на фиксированном заранее известном порту, любая новая служба требовала бы согласования с разработчиками межсетевых экранов и сетевыми администраторами. Вместо этого Microsoft закрепил единственный известный порт - TCP 135 - за справочной службой **Endpoint Mapper**, а всем остальным компонентам разрешил выбирать порты динамически. Программа просит "дай мне сервис с UUID X" и получает адрес, не заботясь о том, какой порт сегодня свободен. На практике это означает: для работы MS-RPC между хостами нужны как минимум открытый TCP 135 и весь динамический диапазон 49152-65535/TCP. Поэтому грамотная сегментация сети обычно полностью закрывает RPC между несвязанными сегментами.

## COM и DCOM

Если **MS-RPC** - это транспортный уровень, то **COM** (Component Object Model) - это то, что по нему работает. Это стандарт, позволяющий разным программам в Windows использовать готовые бинарные компоненты (например, функционал из DLL или EXE файлов - COM-серверов).

Каждый такой объект имеет свой глобальный уникальный идентификатор - **CLSID** (Class ID). Операционная система хранит полную карту всех зарегистрированных в системе компонентов и их **CLSID** в Реестре.

Классический пример работы **COM** - автоматизация Microsoft Office. Скрипт PowerShell может выполнить **New-Object -ComObject Word.Application**, и Windows сама найдёт **CLSID** этого объекта в реестре, запустит соответствующий EXE-файл и вернёт скрипту объект Word, у которого можно вызывать любые методы интерфейса (открыть документ, вставить таблицу, сохранить). С точки зрения программиста, объект Word ничем не отличается от локальной функции - и в этом ключевая идея COM: предоставить единый бинарный интерфейс для использования готовых компонентов из любого языка программирования, без знания их внутренней реализации. **DCOM** (Distributed COM) - это расширение технологии **COM** для работы по сети. Если классический **COM** позволяет компонентам общаться внутри одного компьютера, то **DCOM** позволяет делать то же самое между разными хостами, используя MS-RPC в качестве транспорта. Самый показательный пример **DCOM** - удалённое управление через **WMI**. Команда **Get-WmiObject -Class Win32_Process -ComputerName SERVER01** активирует на SERVER01 COM-объект WMI, который через **DCOM/MS-RPC** возвращает локальной машине список процессов. С точки зрения пользователя вызов выглядит как обращение к локальной службе, хотя реально работает по сети через TCP 135 и динамические RPC-порты целевого хоста. Microsoft выбрал такую архитектуру, чтобы расширение на сеть не требовало изобретать отдельный протокол удалённого администрирования. DCOM использует уже существующую инфраструктуру **COM** - **CLSID** в реестре, аутентификацию через **NTLM/Kerberos**, регистрацию в **Endpoint Mapper** - и просто добавляет сетевой транспорт. Именно поэтому большинство штатных средств удалённого администрирования Windows построены через эту связку **DCOM + MS-RPC**.

Microsoft описывает [**DCOM Remote Protocol**](https://learn.microsoft.com/en-us/openspecs/windows_protocols/MS-DCOM/86b9cf84-df2e-4f0b-ac22-1b957627e1ca) как расширение **COM** поверх сети, построенное на **MS-RPC**; **DCOM** использует возможности **RPC** для аутентификации, авторизации и контроля целостности сообщений.

- **COM** - модель компонентов
- **DCOM** - удалённый **COM**
- **RPC** - транспортная и процедурная основа, через которую **DCOM** реально общается по сети

**Примеры компонентов Windows, связанных с RPC/DCOM:**

- **RPCSS** / **RpcSs** - базовая служба **RPC runtime** и **Endpoint Mapper**. Без неё значительная часть Windows-компонентов не сможет взаимодействовать
- **DCOM Server Process Launcher** / **DcomLaunch** - отвечает за запуск **COM**/**DCOM**-серверов. Важен для удалённой активации **COM**-объектов
- **Service Control Manager Remote Protocol (SCMR)** - **RPC**-интерфейс для удалённого управления службами: создание, запуск, остановка, изменение конфигурации. См. [**MS-SCMR**](https://learn.microsoft.com/en-us/openspecs/windows_protocols/MS-SCMR/705b624a-13de-43cc-b8a2-99573da3635f)
- **Task Scheduler Remoting Protocol** - **RPC**-интерфейсы для удалённой регистрации, настройки и проверки задач. Microsoft указывает три интерфейса: **ATSvc**, **SASec**, **ITaskSchedulerService**: [**MS-TSCH**](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tsch/21e8e86e-ee5a-469d-917f-28a41f3c25a4)
- **Print Spooler** / **Print System Remote Protocol** - **RPC**-протокол управления печатью, очередями и драйверами. См. [**MS-RPRN**](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rprn/a7cceedb-3afc-45f0-82e1-af2b2cbf20e4)
- **Remote Registry Protocol** - **RPC**-протокол удалённого доступа к реестру. См. [**MS-RRP**](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rrp/54e59812-99b1-4b0e-8699-34dfed8271f1)
- **WMI через DCOM/RPC** - классический удалённый **WMI** использует **DCOM**/**RPC**. Это важно для разведки, администрирования и выполнения команд
- **Server Service** / **SRVSVC** - служба **Server** предоставляет файловый и принтерный шаринг, named pipes и **RPC**-поддержку поверх сети. Это связка **SMB** + **RPC**

С точки зрения атак:

- **RPC**/**DCOM** увеличивает поверхность атаки, потому что один обнаруженный сетевой endpoint может вести к множеству интерфейсов
- при наличии учётных данных **RPC** и **DCOM** используется для удалённого администрирования
- через **SCM** возможно удалённое создание/запуск службы
- отдельные **RPC**-интерфейсы исторически становились источником серьёзных уязвимостей (например, критическая уязвимость в сервере печати **CVE-2021-34527** / **PrintNightmare**)

Понятия выше дают каркас. Дальше - конкретные атаки, в которых атакующие используют этот каркас не по назначению.

## Атаки на MS-RPC/DCOM

**Remote Service Creation via SCMR** (MITRE ATT&CK: [**T1569.002**](https://attack.mitre.org/techniques/T1569/002/))

Удалённое создание и запуск службы через **Service Control Manager Remote Protocol (SCMR)**. Имея учётные данные локального администратора на целевом хосте, атакующий подключается к **RPC Endpoint Mapper**, находит интерфейс **SCMR**, регистрирует новую службу с путём к своему исполняемому файлу и запускает её - в результате его код выполняется с правами **SYSTEM**. Это классический механизм работы утилиты **PsExec** и большинства инструментов lateral movement.

**PrintNightmare** (**CVE-2021-34527**, **CVE-2021-1675**)

Уязвимость в **Print Spooler** позволяет любому аутентифицированному пользователю домена удалённо загрузить произвольную **DLL** в контекст службы печати, которая работает с правами **SYSTEM**.

Механизм атаки:

1. **Подключение**: Атакующий обращается к **RPC**-интерфейсу **Print Spooler** на целевом хосте
2. **Подмена драйвера**: Вызывает функцию **RpcAddPrinterDriverEx()**, передавая путь к "драйверу принтера", который на самом деле является вредоносной **DLL** на сетевой шаре атакующего
3. **Загрузка**: Служба **spoolsv.exe** скачивает указанную **DLL** и загружает её в своё адресное пространство без проверки подписи
4. **Захват**: Код **DLL** выполняется от **SYSTEM** на целевом хосте

Условие успеха - наличие активной службы **Print Spooler** на целевом сервере. На контроллерах домена и обычных серверах без принтеров эту службу необходимо отключать.

> **PrintNightmare** - это допуск к принтеру, который по ошибке оказался допуском к серверу. Любой пользователь домена мог "поставить новый драйвер принтера" - и Windows загружала этот "драйвер" с правами **SYSTEM**, потому что подсистема печати работает в этом контексте. Атакующий приходит как "пользователь, которому нужно напечатать", уходит как **SYSTEM**.

![](../../_images/72fa6abb2a56.webp)

**DCOM Lateral Movement** (MITRE ATT&CK: [**T1021.003**](https://attack.mitre.org/techniques/T1021/003/))

Использование легитимных **COM**-объектов (**MMC20.Application**, **ShellWindows**, **ShellBrowserWindow**, **Excel.Application**) для удалённого выполнения кода через **DCOM**. Атакующий с правами в группе **Distributed COM Users** на целевом хосте активирует один из этих объектов и через его методы (например, **ExecuteShellCommand** у **MMC20.Application**) запускает произвольную команду в контексте пользователя. Преимущество для атакующего - вызов выглядит как нормальная активность **dllhost.exe** или **mmc.exe**, что часто пропускается **EDR**.

**WMI Remote Execution via DCOM** (MITRE ATT&CK: [**T1047**](https://attack.mitre.org/techniques/T1047/))

Удалённое выполнение команд через метод **Win32_Process.Create()** интерфейса **WMI**, который транспортируется через **DCOM**. Подробно разбирается в подразделе про **WMI** ниже.

**RPC Endpoint Enumeration**

Разведка доступных **RPC**-интерфейсов через **Endpoint Mapper** на порту **135** для поиска уязвимых или нестандартных сервисов. Простая, но эффективная техника на этапе пред-атаки: список доступных интерфейсов часто выдаёт, какие службы запущены, есть ли потенциальный **PrintNightmare**, доступен ли **Remote Registry**.

## Какие механизмы защиты работают на MS-RPC/COM/DCOM

- **Отключение Print Spooler** на серверах, не являющихся принт-серверами - закрывает класс уязвимостей **PrintNightmare**
- **Сегментация сети по RPC-портам**: порты **135** и динамический диапазон **49152-65535** не должны быть доступны из недоверенных сегментов
- **Ограничение прав на активацию DCOM** через **dcomcnfg.exe** - снимает поверхность атаки **DCOM Lateral Movement**
- **Группа Distributed COM Users** - регулярный аудит членства, минимизация состава
- **LAPS** для локальных администраторов - блокирует **Remote Service Creation** через **SCMR** с украденным паролем
- **Установка патчей Windows в приоритете** - **MS-RPC** и **Print Spooler** исторически являются источниками критических уязвимостей
- **AppLocker** / **WDAC** - блокировка неавторизованных исполняемых файлов, в том числе подложенных через **SCMR**
- **Аудит создания служб** (**Event ID 7045**) - детектирует **Remote Service Creation** и установку драйверов через **Spooler**
