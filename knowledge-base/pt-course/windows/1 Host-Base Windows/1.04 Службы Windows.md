# Службы Windows

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Службы Windows
>
> **Кейсы:** [3.01 Настройка служб](../../cases/windows/3.01%20Настройка%20служб.md)

**Службы** - это основа фонового исполнения в Windows. Через них реализована значительная часть системной функциональности, а сами они обычно работают с повышенными правами. Это делает службы одновременно главным инструментом администратора и одной из главных целей атакующих, потому что компрометация службы под **LocalSystem** равна компрометации всего хоста.

С технической точки зрения **служба** - это процесс под управлением **Service Control Manager** (**SCM**), запускающийся в фоне, без интерактивного входа пользователя. Службы стартуют до того, как кто-либо вошёл в систему, и продолжают работать после выхода. Именно через них реализованы **Windows Update**, **Print Spooler**, **DHCP Client**, антивирус, агенты мониторинга.

> **Служба** - это охранник на проходной режимного объекта. Он заступает на смену задолго до того, как в офис придёт первый сотрудник, и продолжает работать после того, как все уйдут. Ему не нужен начальник за плечом, чтобы выполнять свою функцию, - задача описана инструкцией, а механика запуска заложена в график смен. Управляет всеми такими охранниками единый диспетчер - **Service Control Manager**.

**Session 0 isolation.** Сессии в **Windows** нумеруются, и одна из них - **Session 0** - особенная. Это изолированное пространство, в котором работают системные службы, без рабочего стола и без возможности показывать графические окна обычным пользователям. До **Windows Vista** службы и интерактивные пользователи делили одну сессию, и это позволяло провести атаку **Shatter Attack** - перехват сообщений через окно высоко привилегированного процесса. С тех пор **Session 0 isolation** закрывает этот класс атак на уровне архитектуры.

Для специалиста это означает простую вещь: если процесс находится в **Session 0**, он не может ничего показывать пользователю и не должен с пользователем взаимодействовать. Если в дереве процессов **Session 0** появилось что-то, выглядящее как пользовательское приложение, - это аномалия.

![](../../_images/7651fc121705.webp)

Конфигурация каждой службы хранится в реестре в ветке **HKLM\SYSTEM\CurrentControlSet\Services<имя>**. Ключевые параметры:

- **ImagePath** - полный путь к исполняемому файлу службы. Это то, что **SCM** запустит
- **Start** - режим запуска: **0** (Boot, для драйверов), **1** (System), **2** (Automatic), **3** (Manual), **4** (Disabled)
- **ObjectName** - учётная запись, от имени которой работает служба
- **Type** - тип службы (драйвер ядра, пользовательский процесс, общий хост)

**Учётные записи служб.** Каждая служба работает от имени какой-то учётной записи. Windows предоставляет четыре встроенных варианта - они описаны в документации Microsoft:

| Учётная запись | Привилегии | Сетевая идентичность | Когда применять |
|---|---|---|---|
| LocalSystem ( NT AUTHORITY\SYSTEM ) | Максимальные на хосте | Доменный аккаунт компьютера | Только если служба действительно требует системных прав |
| LocalService ( NT AUTHORITY\LocalService ) | Минимальные, как у обычного пользователя | Анонимные | Локальная работа без сети |
| NetworkService ( NT AUTHORITY\NetworkService ) | Минимальные локальные | Аккаунт компьютера | Локальная работа с сетевыми ресурсами |
| Virtual Service Account ( NT SERVICE<имя_службы> ) | Настраиваются индивидуально | Аккаунт компьютера | Современная замена выделенных доменных учёток |

**Virtual Service Accounts** - автоматически управляемые локальные учётные записи, появившиеся в Windows Server 2008 R2. Создаются вместе со службой, имеют имя **NT SERVICE<имя>**, не требуют пароля и в домене работают через учётную запись компьютера. Это рекомендуемый подход для новых служб, потому что снимает все проблемы с управлением паролями.

> **Учётные записи служб** - это разные должности у того же охранника. **LocalSystem** - начальник службы безопасности с мастер-ключом от всех помещений; пускать каждого охранника на такую должность означает, что любая компрометация на проходной равна компрометации всех помещений. **LocalService** и **NetworkService** - обычные дежурные с минимальным набором ключей. **Virtual Service Account** - именная карточка под конкретную задачу: открывает только те двери, которые нужны именно этой смене и именно этому охраннику. Принцип наименьших привилегий - правило "выдавать мастер-ключ только тому, кому он реально нужен по обязанностям".

На практике это означает простое правило: новая служба, если у неё нет очевидной нужды в максимальных правах, по умолчанию создаётся под **Virtual Service Account**. Это закрывает большую часть типовых сценариев и снимает проблемы с управлением паролями.

Главное правило безопасности служб - **принцип наименьших привилегий**. Служба, которой нужно читать один файл, не должна запускаться под **LocalSystem**. Компрометация процесса, работающего под **LocalSystem**, - это компрометация всего хоста. Кража или подмена токена такой службы - отдельный класс атак, известный как **Token Impersonation / Theft** (**T1134**); он подробно разбирается в модулях про атаки на учётные данные.

Для точечного делегирования прав на саму службу (кто может её запускать, останавливать, менять конфигурацию) используется **Security Descriptor Definition Language** (**SDDL**). Например, чтобы выдать конкретной группе право только на запуск и остановку службы (без права изменять конфигурацию или удалять её), применяется команда `sc.exe sdset <ServiceName> <SDDL-строка>`.

Точечная выдача прав вместо включения пользователя в **Administrators** - стандартный подход в зрелой администрируемой среде.

## PowerShell для работы со службами

PowerShell предоставляет полноценный набор командлетов для управления службами через провайдер **Web Services Management** (**WSMan**) и через прямое обращение к **SCM**. Команды ниже работают локально, без необходимости в **PowerShell Remoting** (**PSRemoting**) - удалённое управление и модуль **ActiveDirectory** разбираются в статье 3.2.2. Запускайте все команды этого раздела от имени администратора - без повышенных прав часть полей просто не отдастся.

Перечисляет все службы хоста с их текущим состоянием (**Running**, **Stopped**) и режимом запуска - самая базовая команда инспекции: `Get-Service`

Возвращает детали по конкретной службе. **-Name** принимает имя службы как идентификатор, **Select-Object** выбирает нужные поля: `Get-Service -Name Spooler | Select-Object Name, Status, StartType, DisplayName`

Возвращает существенно больше информации, чем **Get-Service**, через **Common Information Model** (**CIM**). Поле **PathName** содержит командную строку запуска (то самое, что лежит в реестровом **ImagePath**), **StartName** - учётную запись службы. Это основная команда для проверки служб на признаки атаки: путь без кавычек, путь в подозрительной директории, учётная запись с избыточными правами: `Get-CimInstance -ClassName Win32_Service -Filter "Name='Spooler'" | Select-Object Name, PathName, StartName, StartMode, State`

Следующий фильтр находит **все** службы, у которых **PathName** содержит пробел и при этом **не** заключён в кавычки. Это прямое детектирование уязвимости **Unquoted Service Path** на хосте: `Get-CimInstance -ClassName Win32_Service | Where-Object { $_.PathName -notmatch '^"' -and $_.PathName -match ' ' } | Select-Object Name, PathName, StartName`

Управление состоянием и режимом запуска службы. **Set-Service** меняет тип запуска, эквивалент **sc.exe config spooler start= disabled**:

```
Start-Service -Name Spooler
Stop-Service -Name Spooler
Set-Service -Name Spooler -StartupType Disabled
```

Это уже не PowerShell, а классическая утилита **sc.exe**, но **специалист** обязан знать её для проверки прав на саму службу. Команда возвращает **Security Descriptor Definition Language** (**SDDL**) - текстовое описание разрешений: кто имеет право запускать, останавливать, менять конфигурацию службы. Слабые разрешения на службе - это второй классический вектор атаки на службы: `sc.exe sdshow Spooler`

После этих команд у Вас на руках три проверочных среза по любой подозрительной службе: что она запускает (**PathName**), от кого работает (**StartName**) и кто имеет право её изменять (**SDDL** через **sc.exe sdshow**). Этого достаточно, чтобы за одну сессию пройти по списку служб хоста и составить картину рисков.

Команды выше дают возможность видеть и менять конфигурацию служб. Теперь о том, что именно злоумышленник пытается в этой конфигурации найти и эксплуатировать.

## Уязвимости и атаки

### Unquoted Service Path (T1574.009)

Когда **SCM** запускает службу, он берёт строку **ImagePath** и передаёт её **CreateProcess**. Если путь содержит пробелы и не заключён в кавычки, Windows пытается интерпретировать его последовательно, рассматривая каждый пробел как разделитель.

Допустим, **ImagePath** службы выглядит так: **C:\Program Files\Vendor App\Service\app.exe**. Без кавычек Windows последовательно попытается запустить:

- **C:\Program.exe**
- **C:\Program Files\Vendor.exe**
- **C:\Program Files\Vendor App\Service.exe**
- **C:\Program Files\Vendor App\Service\app.exe**

Если у атакующего есть права записи в **C:** (что нетипично) или в **C:\Program Files** (что бывает при кривой установке), он подкладывает свой файл **Program.exe** или **Vendor.exe**. **SCM** запускает этот файл - и атакующий получает выполнение кода в контексте службы. Если служба работает под **LocalSystem**, это мгновенное повышение до **SYSTEM**.

![](../../_images/8627a87ea0f2.webp)

> Представьте курьера, которому дали адрес без кавычек и знаков препинания: "ул Парковая дом 5 кв 12". Если курьер не знает, где кончается название улицы и начинается номер дома, он попытается доставить посылку сначала на "ул Парковая", потом на "ул Парковая дом", и только в крайнем случае дойдёт до правильного варианта. Если по любому из неверных адресов уже кто-то живёт - посылка достанется ему. **Windows** делает ровно то же самое с путями к исполняемым файлам без кавычек: пробует интерпретации последовательно, и первая, по которой найдётся файл, выигрывает.

Техника каталогизирована **MITRE** как **T1574.009**, **Hijack Execution Flow: Path Interception by Unquoted Path**.

### DLL Hijacking в контексте служб (T1574.001 / T1574.002)

Сам по себе **DLL Hijacking** - подмена динамической библиотеки (**Dynamic-Link Library**, **DLL**), которую программа подгружает по неполному пути; как техника он разбирался в статье 4. В контексте служб этот вектор особенно неприятен по двум причинам.

Во-первых, многие службы работают под **LocalSystem**. Подмена их **DLL** даёт **SYSTEM**-привилегии без всяких трюков с эскалацией.

Во-вторых, службы стартуют автоматически при загрузке системы. Атакующему достаточно один раз положить свою библиотеку в правильное место, и она будет подгружаться каждую загрузку - получается одновременно повышение привилегий и закрепление в системе.

Уязвимыми оказываются службы, которые ищут свои библиотеки по относительному пути или по **PATH**, не указывая полного пути. Если ни одна из родительских папок не защищена, атакующий ставит **DLL** с нужным именем в каталог службы или в директорию, перебираемую раньше системной.

![](../../_images/610f8b082112.webp)

### Process Injection (T1055)

**Process Injection** - не одна техника, а целое семейство методов, объединённое общей идеей: запустить свой код внутри чужого, доверенного процесса. Зачем это атакующему:

- Код атакующего работает в контексте процесса, которому доверяет антивирус и **Endpoint Detection and Response** (**EDR**).
- Сетевой трафик исходит от легитимного приложения, фильтры на хосте его пропускают.
- В списке процессов нет ничего нового: атакующий не запустил **evil.exe**, он "одолжил" чужой процесс.

> Злоумышленник не приходит в офис под своим именем - он находит сотрудника, у которого уже есть пропуск и которого все знают в лицо, и незаметно "внедряется" в его кабинет. Из этого кабинета он отправляет письма от имени хозяина, делает звонки от его лица, заходит в системы под его учёткой. Антивирус и системы мониторинга видят знакомого сотрудника на знакомом месте, делающего свою обычную работу, - тревогу не поднимают. **Process Injection** работает так же: чужой код запускается внутри легитимного процесса и пользуется его репутацией.

MITRE выделяет десяток подтехник; вот основные, которые **специалист** должен узнавать по названию:

| Подтехника | Что делает |
|---|---|
| T1055.001 DLL Injection | Помещает свою DLL в адресное пространство чужого процесса и заставляет его её загрузить |
| T1055.002 PE Injection ( Portable Executable ) | Записывает исполняемый код напрямую в память чужого процесса, без файла на диске |
| T1055.003 Thread Execution Hijacking | Захватывает существующий поток чужого процесса и перенаправляет его на свой код |
| T1055.004 Asynchronous Procedure Call (APC) Injection | Подсовывает свой код в очередь APC потока чужого процесса |
| T1055.012 Process Hollowing | Запускает легитимный процесс в приостановленном состоянии, "выдалбливает" его память, подменяет её своим кодом и продолжает выполнение |

> **Process Hollowing** - особая разновидность того же приёма: атакующий не внедряется к сотруднику, а перехватывает его на проходной до начала смены, забирает у него пропуск и форму, надевает их сам и идёт работать вместо него. Снаружи всё выглядит как обычный сотрудник на обычной должности, но внутри - совсем другой человек с другими целями.

Все техники используют системные **API**:

- **VirtualAllocEx** для выделения памяти в чужом процессе
- **WriteProcessMemory** для записи туда полезной нагрузки
- **CreateRemoteThread** или **NtCreateThreadEx** для запуска чужого потока

Детальный разбор каждой техники - материал атакующих модулей курса; здесь достаточно понимать сам класс угроз и то, что любой подозрительный вызов **VirtualAllocEx** в чужой процесс - это сигнал тревоги.

Классическая мишень **Process Injection** - процесс **lsass.exe**, в памяти которого хранятся хеши паролей, тикеты Kerberos и другие материалы аутентификации. Инструменты вроде **Mimikatz** именно через инжект и чтение памяти **lsass.exe** извлекают эти данные - это атака на учётные данные, известная как **OS Credential Dumping** (**T1003.001**). Защитный механизм против этого класса разбирается ниже в блоке защиты.

![](../../_images/5c1ea52d4d09.webp)

## Защита и обнаружение

- **Минимизация прав служб**. Любая новая служба должна запускаться под **Virtual Service Account** или **LocalService**, не под **LocalSystem**. Проверьте конфигурацию командой `Get-CimInstance Win32_Service | Select Name, StartName` - в результате не должно быть лишних строк с **LocalSystem**
- **Кавычки в путях служб**. Команда **PowerShell** из раздела выше выявляет уязвимые **Unquoted Service Path** за секунды. Исправляется командой `sc.exe config <ServiceName> binPath= "C:\полный\путь.exe" `или прямой правкой реестра
- **Аудит прав на службы**. Регулярно проверяйте **sc.exe sdshow** на критичных службах. В выводе **SDDL** не должно быть **(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;AU)** или подобного - это означает, что **Authenticated Users** имеют права на изменение конфигурации
- **Мониторинг создания служб**. **Event ID 7045** в журнале **System** (источник **Service Control Manager**) фиксирует установку каждой новой службы с указанием **ServiceName**, **ImagePath**, **ServiceType**, **StartType**, **AccountName**. Событие **7045** на хосте, на котором никто ничего не устанавливал, - повод поднимать инцидент. В журнале **Security** аналог - **Event ID 4697**, доступный при включённом аудите категории **System** через **Audit Security System Extension**. Обратите внимание на путь к исполняемому файлу: всё, что не лежит в **%windir%** или **Program Files**, по умолчанию считается подозрительным

![](../../_images/f18534d606ce.webp)
- **Контроль иерархии системных процессов**. Через **Sysmon** **Event ID 1** (создание процесса) и поле **ParentImage**. Любое отклонение от таблицы базовых системных процессов (статья 2.1) - индикатор: процесс с системным именем, но из пути вне **System32**, или с неправильным родителем
- **Защита LSA** (**Local Security Authority**). Включите **Protected Process Light** для **lsass.exe** через ключ реестра **HKLM\SYSTEM\CurrentControlSet\Control\Lsa\RunAsPPL = 1**. Это запрещает любому процессу читать память **lsass.exe**, даже из-под **SYSTEM**, и закрывает целый класс атак на учётные данные через **Process Injection**. После изменения ключа Вам потребуется перезагрузка хоста
- **Детектирование Process Injection**. Sysmon **Event ID 8** фиксирует **CreateRemoteThread** между процессами. Sysmon **Event ID 10** - доступ одного процесса к памяти другого. Любой нештатный доступ к памяти **lsass.exe** - это попытка кражи учётных данных. Детальная настройка Sysmon разбирается в статье про журналирование и аудит

У Вас в руках теперь четыре среза знаний о службах **Windows** - как они устроены (**SCM**, реестр, учётные записи), как ими управлять через **PowerShell** и **sc.exe**, какие три классических вектора атаки на них действуют (**Unquoted Service Path**, **DLL Hijacking**, **Process Injection**) и какие конкретные журналы и настройки закрывают эти векторы. К этим инструментам Вы будете возвращаться в каждой проверке хоста
