# Идентификация, аутентификация и авторизация

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows

После того как мы разобрали пользователей, группы и права доступа, следующий шаг - понять, как Windows вообще решает две базовые задачи: кто именно вошел в систему и что этому субъекту разрешено делать. Эти понятия часто смешивают, но в Windows они разделены довольно строго.

- **Идентификация** отвечает на вопрос: кто это?
- **Аутентификация** отвечает на вопрос: правда ли это он?
- **Авторизация** отвечает на вопрос: что ему разрешено после входа?

Для специалиста важна простая мысль: пароль сам по себе не даёт доступ к файлам, службам или реестру. Доступ появляется только после того, как Windows создаст токен, сопоставит его с объектом и проверит **ACL**, **привилегии**, **логин правила** и **политики** вроде **UAC**. Разберём, как этот путь устроен изнутри - от момента ввода пароля до появления доступа.

## Общее описание процесса проверки подлинности

Проверка подлинности Windows начинается не с файла и не с **ACL**, а с предъявления учётных данных. Источник может быть разным: **экран входа**, **RDP-клиент**, **служба**, **сетевое приложение**, **браузер**, **SMB-клиент**, **WinRM**, **WMI**, **IIS** или другой процесс. Но логика остаётся общей: Windows получает материал аутентификации, выбирает подходящий пакет или поставщик безопасности, проверяет секрет против доверенного источника и создаёт контекст безопасности.

![](../../_images/5c14082be61c.webp)

Весь этот процесс можно разбить на четыре контрольные точки - именно в них чаще всего возникают уязвимости и следы атак:

| Контрольная точка | Что происходит | Что важно для защиты |
|---|---|---|
| Сбор учётных данных | пользователь вводит пароль, PIN , смарт-карту или биометрию - секрет попадает в защищённый канал, недоступный обычным приложениям | защита экрана входа, Credential Providers , отсутствие фишингового UI |
| Выбор механизма | LSA выбирает протокол проверки: Kerberos в домене, NTLM как запасной вариант, Schannel для TLS - выбор зависит от среды и доступности KDC | минимизация NTLM , запрет устаревших протоколов, политика Negotiate |
| Проверка | секрет проверяется против хранилища: локальная база ( SAM ) для локальных учёток, контроллер домена ( KDC/AD ) для доменных | защита SAM / LSASS , контроллеров домена, PKI и secure channel |
| Создание security context | Windows создаёт logon session - объект, с которым будут сверяться все последующие запросы доступа к файлам, реестру и службам | аудит 4624/4625/4672, связь события входа с последующей активностью |

Каждая из этих точек реализуется по-разному в зависимости от того, как именно пользователь входит в систему.

## Основные сценарии входа

Windows использует несколько сценариев входа. Они похожи по цели, но отличаются тем, как пользователь предъявляет учётные данные, какой процесс участвует в проверке и где именно происходит проверка подлинности.

| Сценарий | Как выглядит | Где проверяется |
|---|---|---|
| Локальный интерактивный вход | пользователь вводит пароль/ PIN на консоли | SAM на локальном хосте или домен через Kerberos/Netlogon |
| Доменный интерактивный вход | пользователь входит на присоединенный к домену хост | KDC/Active Directory , при необходимости cached logon verifier |
| Разблокировка рабочей станции | пользователь возвращается к заблокированной сессии | локальная проверка с уже существующим контекстом |
| Удалённый интерактивный вход | RDP | целевой хост, NLA/CredSSP/Kerberos или NTLM |
| Сетевой вход | SMB , WinRM , RPC , IIS , WMI | SSPI , Kerberos/NTLM/Schannel/Digest |
| Запуск службы | SCM запускает службу под заданной учётной записью | LSA проверяет учётную запись службы |
| RunAs / явные учётные данные | пользователь указывает другой логин/пароль | LSA проверяет предоставленный секрет |
| Смарт-карта | пользователь предъявляет карту и PIN | Kerberos PKINIT , сертификат, KDC |
| Биометрия / Windows Hello | локальная биометрия или PIN открывает ключ | локальный провайдер + криптографический материал |
| Кэшированный вход | доменный пользователь входит без доступного DC | Локально сохранённый проверяющий объект ( verifier ) |

Рассмотрим подробнее каждый из них - начнём с самого очевидного: пользователь за консолью.

### Интерактивный вход

Интерактивный вход начинается, когда пользователь видит защищённый экран входа, выбирает плитку и вводит пароль. В современных Windows передачу учётных данных в стек безопасности выполняет архитектура **Credential Provider**. Это не механизм принятия решения: провайдеры передают и сериализуют данные в **LSA**, а решение принимают пакеты проверки подлинности.

![](../../_images/4ec4d96dc318.webp)

1. Пользователь нажимает **Ctrl+Alt+Del** или видит экран входа - это **Secure Attention Sequence (SAS)**. Сигнал перехватывает **Winlogon**: обычное приложение не может эмулировать эту комбинацию, что защищает от подмены экрана входа
2. **Winlogon** запускает **LogonUI.exe** - процесс, который отображает визуальный интерфейс экрана входа
3. **LogonUI** запрашивает у зарегистрированных **Credential Providers** доступные плитки входа: пароль, **PIN**, смарт-карта, биометрия
4. **Credential Provider** возвращает список доступных методов и отображает соответствующий **UI**
5. Пользователь вводит секрет - пароль, **PIN**, прикладывает палец или карту
6. **Credential Provider** сериализует введённые данные и передаёт их обратно в **LogonUI**
7. **LogonUI** отправляет сериализованные учётные данные в **LSASS/LSA** по защищённому локальному каналу
8. **LSA** выбирает подходящий пакет аутентификации: **MSV1_0** для локальных учёток, **Kerberos** для доменных
9. Пакет проверяет секрет против **SAM** (локально) или **KDC/AD** (домен) и применяет политику входа
10. **SAM** или **KDC** возвращает результат: успех или отказ
11. При успехе **LSA** создаёт **logon session** и формирует токен безопасности с **SID**, группами и привилегиями пользователя
12. **Winlogon** получает данные сессии и запускает пользовательское окружение - загружает профиль и оболочку (**explorer.exe**)

Для доменной учётной записи шаг 9 выполняется через **Kerberos** и **DC**. Если доменный контроллер недоступен, Windows может разрешить вход по кэшированным данным, если это допускается политикой. Это удобно для ноутбуков, но создаёт отдельный риск: пользователь может войти на устройство, используя старый секрет, пока локальный **verifier** не будет обновлён.

Иначе устроен сетевой вход - здесь экрана с паролем нет, а аутентификация происходит незаметно для пользователя.

### Сетевой вход

Сетевой вход - это аутентификация, при которой пользователь или процесс обращается к ресурсу на удалённой машине: общей папке по **SMB**, веб-приложению через **IIS**, управляющему интерфейсу через **WinRM** или **WMI**. В отличие от интерактивного входа, здесь нет экрана с паролем - аутентификация происходит в фоне, на уровне протокола. Приложение или служба использует уже существующий контекст безопасности или запрашивает дополнительные учётные данные. Для такого сценария важна **Security Support Provider Interface** (**SSPI**).

**SSPI** скрывает от приложения детали протокола. **SMB**, **WinRM**, **RPC**, **HTTP Negotiate** или другое приложение могут вызвать единый интерфейс, а Windows уже выберет **Kerberos**, **NTLM**, **Schannel** или другой **SSP**.

![](../../_images/2af3640040a9.webp)
1. Клиентское приложение вызывает **InitializeSecurityContext** - запрос к **Client SSPI** на начало аутентификации. Приложению не нужно знать какой протокол будет использован
2. **Client SSPI** формирует начальный токен аутентификации и возвращает его приложению
3. Клиентское приложение передаёт токен серверному приложению по уже существующему протоколу - например, **SMB**, **HTTP** или **RPC**
4. Серверное приложение передаёт полученный токен своему **Server SSPI** через вызов **AcceptSecurityContext**
5. **Server SSPI** обрабатывает токен через **LSA/SSP** и формирует ответный токен - **challenge/response**. Для **NTLM** это **challenge**, для **Kerberos** - ответ на **ticket**
6. Серверное приложение возвращает ответный токен клиенту
7. Клиент обрабатывает ответ через следующий вызов **InitializeSecurityContext** и отправляет новый токен серверу. Этот обмен может повторяться несколько раз - до успеха или отказа
8. После завершения обмена **LSA/SSP** на стороне сервера создаёт **security context** - установленный контекст безопасности для данного соединения
9. Сервер получает **security context** или **impersonation context**, после чего может действовать от имени клиента при обращении к ресурсам

**Impersonation** - механизм, при котором серверный процесс временно получает права клиента и действует от его имени при обращении к ресурсам. Для этого серверу требуется привилегия **SeImpersonatePrivilege**. Важно понимать, что контекст **impersonation** появляется именно как результат успешной сетевой аутентификации - после этого сервер может использовать полученный токен для всех последующих проверок доступа, включая файловую систему, от имени клиента.

Отдельный сценарий - службы: они входят в систему без участия пользователя и оставляют собственный след в журналах.

### Вход службы

Службы в Windows работают под выделенными учётными записями - **LocalSystem**, **LocalService**, **NetworkService** или доменной/локальной учётной записью. Каждая из них определяет набор прав и привилегий, с которыми служба взаимодействует с системой и сетью. Когда служба настроена на доменную или локальную учётную запись, **LSA** проверяет её учётные данные и создаёт **logon session** типа **5**.

В контексте аутентификации, служба получает собственный **logon-сценарий** и **собственную запись в журналах**, поэтому активность службы нельзя анализировать как обычный интерактивный вход пользователя.

Разобрав основные сценарии входа, перейдём к альтернативным факторам аутентификации - смарт-картам, сертификатам и биометрии. В отличие от пароля, они строятся не на знании секрета, а на владении физическим носителем или криптографическим ключом.

### Смарт-карты, сертификаты и биометрия

Смарт-карта в доменной среде использует **Kerberos** с расширением для открытых ключей. Вместо общего секрета, производного от пароля, пользователь доказывает владение приватным ключом на карте. Приватный ключ не должен покидать носитель.

**Биометрия** и **Windows Hello** не сводятся к "Windows хранит отпечаток вместо пароля". Идея в том, что локальный фактор разблокирует криптографический материал, а дальше аутентификация строится вокруг ключей и доверенного устройства. Если биометрический вход настроен только локально, для доступа к доменным ресурсам всё равно может потребоваться доменный **credential path**.

Все эти сценарии сходятся в одном месте - **LSA** и процессе **lsass.exe**, который стоит за каждой проверкой.

## LSA и LSASS

**Local Security Authority** (**LSA**) - защищённая подсистема Windows, которая проверяет вход пользователей на локальный компьютер, хранит и применяет локальную политику безопасности, управляет пакетами аутентификации и участвует в создании контекста безопасности. Исполняемый процесс, в котором живёт эта логика - **Local Security Authority Subsystem Service** (**LSASS**, **lsass.exe**).

**SAM** (**Security Account Manager**) - локальная база данных, в которой Windows хранит учётные записи и хэши паролей локальных пользователей. Именно против неё проверяются учётные данные при локальном входе. **SAM** живёт в реестре по пути **HKLM\SAM** и недоступна напрямую даже для администратора - только через **LSA**.

> **Аналогия:** **LSASS** - это привратник, **SAM** - журнал с записями о том, кому разрешён вход. Всё что связано с входом в систему проходит через привратника, который сверяется с журналом.

И именно поэтому **LSASS** является главной целью атакующих при **credential dumping** - в памяти **LSASS** хранятся **NTLM**-хэши, **Kerberos**-тикеты и другие секреты активных сессий.

**LSA** делает больше, чем просто "проверяет пароль":

Когда пользователь вводит пароль, LSA не просто сверяет его с базой. Она выбирает нужный протокол проверки, применяет политики входа, переводит имя пользователя в **SID**, формирует токен с группами и привилегиями, записывает событие в журнал безопасности и сохраняет материал для последующего сетевого доступа без повторного ввода пароля. Всё это происходит за один сеанс входа - ниже краткий справочник по каждой из этих функций.

| Функция LSA | Что это означает для специалиста |
|---|---|
| Login verification | интерактивные, сетевые и сервисные logon -сценарии проходят через LSA или связанные пакеты |
| Security policy | LSA знает локальные политики безопасности, права пользователя и часть параметров входа |
| Authentication package manager | LSA загружает и вызывает пакеты вроде MSV1_0 , Kerberos , Negotiate |
| SID/name translation | переводит имена в SID и обратно |
| Audit generation | участвует в создании событий безопасности, например входов и отказов |
| Security context | получает данные от пакета проверки и инициирует создание logon session |
| Credential material | хранит или использует секреты, необходимые для single sign-on и сетевого доступа |

В нормальной системе **lsass.exe** должен быть один. Он запускается из **C:\Windows\System32** и имеет родителя **wininit.exe**. Любой второй **lsass.exe**, неправильный путь или странный родитель - индикатор маскировки.

Чтобы понять, как LSA справляется с этой задачей, нужно знать, из каких компонентов она состоит.

## Архитектура проверки учётных данных

В процессе аутентификации участвуют несколько служб, библиотек и драйверов, организованных в слои. Каждый слой отвечает за свою часть цепочки и взаимодействует с соседними через чётко определённые интерфейсы.

**Пользовательский слой** - то, с чем взаимодействует пользователь напрямую. **Winlogon** перехватывает **SAS** и управляет сессией входа. **LogonUI** отображает экран входа и плитки. **Credential Provider** принимает введённые данные и передаёт их вниз по цепочке в сериализованном виде.

**Слой LSA** - ядро всей проверки. **lsasrv.dll** внутри **LSASS** получает данные от **Credential Provider** и выбирает нужный пакет аутентификации: **MSV1_0** для локальных учёток, **Kerberos** для доменных, **NTLM** как запасной вариант через **Negotiate**. Каждый пакет знает как именно проверить секрет - против **SAM** локально или через **Netlogon** к контроллеру домена. Дополнительные пакеты - **Schannel** для **TLS**, **Digest** для legacy-сценариев, **CredSSP** для делегирования при RDP.

**Сетевой слой** - для приложений, которым нужна аутентификация без прямого доступа к **LSA**. **secur32.dll** предоставляет интерфейс **SSPI**: приложение вызывает единый API, а Windows сама выбирает нужный протокол и завершает обмен токенами.

**Слой ядра** - **KSecDD** (**ksecdd.sys**) обеспечивает криптографическую поддержку и канал между пользовательским режимом и **LSA** для операций, требующих защиты на уровне ядра.

![](../../_images/c61a8626eca4.webp)

Ниже - справочник по каждому компоненту. Их важно узнавать по именам, так как именно они встречаются в логах и списках модулей. Например, **wdigest.dll**, активная на современной системе - сигнал того, что включена **legacy**-аутентификация, а в памяти могут храниться пароли в открытом виде.

| Компонент | Где живёт | Роль |
|---|---|---|
| Winlogon | winlogon.exe | управляет интерактивным входом, блокировкой, выходом, secure attention sequence |
| Logon UI | LogonUI.exe | отображает экран входа и плитки Credential Providers |
| Credential Provider | COM -компоненты в реестре | передаёт учётные данные пользователя ( PIN , пароль, смарт-карту, биометрию) в стек безопасности Windows |
| secur32.dll | user mode библиотека | пользовательский вход в SSPI и передача учётных данных в LSA |
| LSASS / LSA | lsass.exe | центр проверки входа, политики безопасности, пакеты, аудит, контекст безопасности |
| lsasrv.dll | внутри LSASS | служба LSA Server ; применяет политики и управляет пакетами безопасности |
| MSV1_0 | msv1_0.dll | Пакет аутентификации NTLM/MSV1_0 , локальная проверка и совместимость |
| Kerberos SSP/AP | kerberos.dll | доменная аутентификация Kerberos , TGT/TGS , smart card logon |
| Negotiate | lsasrv.dll | выбирает Kerberos по возможности, иначе NTLM |
| Schannel | schannel.dll | TLS/SSL и сертификатная аутентификация |
| Digest | wdigest.dll | legacy/web/LDAP digest -сценарии; если активен - пароли могут храниться в памяти в открытом виде |
| CredSSP | credssp.dll | делегирование учетных данных для RDP/Terminal Services и некоторых SSO -сценариев |
| Netlogon | netlogon.dll , служба Netlogon | Защищённый канал к DC , передача доменных проверок, поиск DC через DNS |
| SAM Server | samsrv.dll | локальная база пользователей и групп, локальные политики учётных записей |
| KSecDD | ksecdd.sys | kernel-mode security support provider , криптографическая поддержка и LPC в LSA |
| Credential Manager / Vault | профиль пользователя | сохранённые учетные данные для приложений и сайтов |

**Credential Providers** не являются механизмом принудительного применения политик. Они отвечают за передачу учётных данных в стек безопасности. Проверку и применение политики выполняют **LSA** и пакеты аутентификации. Поэтому новый **Credential Provider** в системе входа - чувствительное изменение, но сам факт его наличия ещё не означает, что он "решает", пустить пользователя или нет.

Приложения взаимодействуют с этой архитектурой не напрямую, а через единый интерфейс - **SSPI**.

## SSPI и Security Support Providers

Когда приложение - например, **SMB**-клиент, браузер или **WinRM** - обращается к удалённому ресурсу, ему нужно каким-то образом аутентифицировать пользователя на другом конце соединения. Реализовывать **Kerberos** или **NTLM** самостоятельно в каждом приложении было бы громоздко и небезопасно. Для этого Windows предоставляет единый программный интерфейс - **Security Support Provider Interface** (**SSPI**).

**SSPI** - это программный интерфейс, через который приложения получают аутентификацию, целостность сообщений и конфиденциальность без прямой реализации **Kerberos** или **NTLM**. Приложению не нужно знать детали протокола: оно вызывает **SSPI**, передаёт токены по своему каналу связи, а Windows завершает обмен через один из установленных провайдеров - **SSP**.

Для специалиста важно понимать не только что делает каждый **SSP**, но и **что происходит при fallback**. **Kerberos** требует доступного **KDC**, правильных **SPN** и синхронизированного времени. Если что-то из этого нарушено - **Negotiate** автоматически переключается на **NTLM**. Атакующие намеренно создают условия для такого **fallback**: если заставить клиента аутентифицироваться через **NTLM** вместо **Kerberos**, появляется возможность для **relay-атак**.

| SSP | Где используется | Что важно для безопасности |
|---|---|---|
| Kerberos | домен AD , SMB , LDAP , RPC , IIS , WinRM при доменной доступности | предпочтительный протокол; требует DNS , SPN , времени и доступного KDC |
| NTLM | legacy , workgroup , fallback , SMB/HTTP/RPC | challenge-response ; риск relay/pass-the-hash ; нужен контроль и аудит |
| Negotiate | IWA , SMB , WinRM , HTTP Negotiate | выбирает Kerberos если возможно; fallback на NTLM нужно понимать и контролировать |
| Schannel | TLS/SSL , сертификаты, web , EAP-TLS | зависит от PKI , цепочки доверия и политики сертификатов |
| Digest | legacy LDAP/web | исторический механизм; если активен - пересмотреть необходимость |
| CredSSP | RDP , некоторые сценарии делегирования | удобно для SSO , но при лишнем делегировании учетных данных, атакующий на сервере получает учетные данные клиента клиента |
| PKU2U / NegoExts | peer-to-peer и расширенные сценарии | встречается реже, но может участвовать в нестандартной аутентификации |

Отдельный случай - вход без доступного контроллера домена: здесь в игру вступают кэшированные учётные данные.

## Кэшированные учётные данные и Credential Manager

Представьте сотрудника с ноутбуком, который работает вне офиса - без доступа к корпоративной сети и контроллеру домена. При каждом входе Windows в обычном режиме должна обратиться к **DC** для проверки пароля. Если **DC** недоступен, вход был бы невозможен. Чтобы решить эту проблему, Windows использует механизм кэширования учётных данных.

Windows может использовать кэшированные данные для интерактивного входа доменного пользователя, когда контроллер домена недоступен. Это не даёт полноценного доступа к доменным ресурсам само по себе, но позволяет открыть рабочий стол и использовать локальный профиль.

Механизм выглядит так: при первом успешном доменном входе Windows сохраняет на диске специальный **verifier** - не сам пароль, а его производную, достаточную для локальной проверки. По умолчанию хранится **10** таких записей (настраивается политикой). Это удобно для ноутбуков сотрудников которые работают вне офиса. Для высокочувствительных систем - риск: если устройство украдено, атакующий офлайн может попытаться перебрать пароль против кэшированного **verifier**.

**Credential Manager** и **Windows Vault** хранят сохранённые пользователем учетные данные для приложений, сайтов и сетевых ресурсов. Это не то же самое, что **SAM** или **Kerberos TGT**, но для атакующего это ценный источник: сохранённые credentials могут автоматически подставляться при следующем доступе к ресурсу - без каких-либо запросов пользователю.

Команда **PowerShell**: `cmdkey /list`

Показывает сохранённые учетные данные текущего пользователя. В расследовании важно понимать: это список ссылок на сохранённые записи, а не безопасный аудит всех секретов в организации.

Количество кэшированных **logon**-записей регулируется политикой:

Команда **PowerShell**: `Get-ItemProperty "HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" ` -Name CachedLogonsCount`

Значение **0** полностью отключает кэширование - уместно для серверов и привилегированных рабочих станций.

Все описанные механизмы - потенциальные точки атаки, и Windows предоставляет несколько уровней защиты для каждого из них.

## Механизмы защиты цепочки аутентификации

Зная, как устроена цепочка входа, логично задаться вопросом: а что мешает злоумышленнику вмешаться в неё? Windows выстраивает несколько рубежей защиты - каждый закрывает свою точку уязвимости в процессе аутентификации.

### Secure Attention Sequence и защищённый рабочий стол

Первый рубеж - сам экран входа. Проблема в том, что любое приложение теоретически может нарисовать окно, похожее на экран входа, и перехватить введённый пароль. Windows решает это через защищённый рабочий стол и **Secure Attention Sequence** (**SAS**).

Для интерактивного входа Windows использует защищённый путь: **Winlogon**, **LogonUI** и безопасный рабочий стол. Идея в том, чтобы обычное пользовательское приложение не могло незаметно подменить экран входа и собрать пароль. Именно поэтому настройки **UAC** на защищённом рабочем столе важны не только для удобства, но и для защиты пути ввода учетных данных.

### LSA Protection / RunAsPPL

Экран входа защищён, но что защищает сам процесс **LSASS**, в памяти которого хранятся все активные секреты? По умолчанию - ничего. Любой процесс с правами администратора и **SeDebugPrivilege** может открыть дескриптор к **lsass.exe** и прочитать его память.

**LSA Protection** решает эту проблему, запуская **LSASS** как защищённый процесс (**Protected Process Light**). Это мешает непривилегированным и неподписанным компонентам читать память **LSASS** или внедрять код в процесс. Именно так работает **Mimikatz** в базовом режиме - с включённым **PPL** это становится значительно сложнее: даже администратор не может просто так прочитать память защищённого процесса.

Команды **PowerShell**:

- Проверка: `Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa' | Select-Object RunAsPPL, RunAsPPLBoot`
- Включение: `reg add HKLM\SYSTEM\CurrentControlSet\Control\Lsa /v RunAsPPL /t REG_DWORD /d 1 /f`

После включения нужна перезагрузка. На системах с **UEFI Lock** и **Secure Boot** отключение одной правкой реестра не должно снимать защиту.

### Credential Guard и LSAIso.exe

Даже с включённым **LSA Protection** администратор с нужными правами всё равно может получить доступ к памяти **LSASS**. Следующий уровень защиты - вынести наиболее чувствительные секреты за пределы досягаемости обычной операционной системы.

**Credential Guard** использует **Virtualization-Based Security** (**VBS**) для изоляции секретов. В старой модели часть секретов жила в памяти **lsass.exe** - **Mimikatz** читал их оттуда напрямую. При включённом **Credential Guard LSA** взаимодействует с изолированным процессом **LSAIso.exe**, где защищаются **NTLM-derived secrets**, **Kerberos TGT** и часть доменных учетных данных. Обычная ОС не должна иметь прямого доступа к этим данным - они находятся в **VTL1**, недоступном из **VTL0** даже для **SYSTEM**.

Практический эффект: **Mimikatz** на системе с **Credential Guard** не может извлечь **NTLM-хэши** из памяти **LSASS** стандартными методами. Атакующему нужно либо атаковать момент аутентификации (перехват в транзите), либо искать другие пути.

![](../../_images/dd704a36553a.webp)

Проверка состояния **VBS/Credential Guard** через **PowerShell**: `Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard | Select-Object VirtualizationBasedSecurityStatus, SecurityServicesConfigured, SecurityServicesRunning`

Ограничение важно: **Credential Guard** не защищает всё подряд. Он не заменяет защиту контроллеров домена, не делает безопасными слабые пароли, не защищает секреты которые приложение хранит вне механизмов Windows, и не отменяет риск фишинга или кражи токена после входа.

### Restricted Admin и Remote Credential Guard

Отдельная проблема возникает при удалённом администрировании. Когда администратор подключается к серверу по **RDP**, его учётные данные оказываются на удалённом хосте - и если сервер скомпрометирован, атакующий получает их вместе с остальным содержимым памяти **LSASS**. Windows предлагает два режима, которые решают эту проблему по-разному. Это означает: если сервер скомпрометирован, атакующий получает учетные данные всех администраторов которые к нему подключались.

**Restricted Admin** решает эту проблему иначе: подключение происходит без передачи учетных данных на целевой хост. Вместо этого сессия использует компьютерный контекст. Побочный эффект - из такой сессии нельзя аутентифицироваться на другие ресурсы от имени пользователя.

**Remote Credential Guard** идёт дальше: учетные данные остаются на клиентской машине, а на сервер передаются только **Kerberos-тикеты**. Это защищает от кражи учетных данных на сервере, но требует поддержки с обеих сторон.

Эти режимы полезны для администрирования недоверенных или потенциально скомпрометированных серверов. Администратор подключается к заражённому серверу в **Restricted Admin** режиме - даже если сервер полностью под контролем атакующего, учетные данные администратора не попадут в его руки.

Зная, как устроена защита, можно быстро проверить её состояние на конкретном хосте.

## Что проверять на хосте

Команды PowerShell:

- Критические процессы цепочки входа. **lsass.exe** и **winlogon.exe** должны быть из **C:\Windows\System32**: `Get-Process lsass, winlogon, LogonUI -ErrorAction SilentlyContinue | Select-Object Id, ProcessName, Path, StartTime`
- Путь и родителя **LSASS**. Нормальный родитель - **wininit.exe**. Любое отклонение - признак маскировки или инъекции: `Get-CimInstance Win32_Process -Filter "Name='lsass.exe'" | Select-Object ProcessId, ParentProcessId, ExecutablePath, CommandLine`
- Показывать зарегистрированных **Credential Providers**. Любой новый **GUID** должен быть связан с известным продуктом и задокументированным изменением: `Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Providers*' | Select-Object PSChildName`

Понимание нормального состояния системы помогает распознать отклонения - рассмотрим, как атакующие эксплуатируют механизмы аутентификации.

## Популярные атаки на локальную аутентификацию и авторизацию

Разобрав архитектуру и механизмы защиты, посмотрим на то, как атакующие эксплуатируют эти же механизмы. Большинство атак на аутентификацию не ломают криптографию - они злоупотребляют легитимными возможностями Windows: токенами, привилегиями и авто-повышением процессов.

### Token Theft и Impersonation (T1134.001 / T1134.002)

**MITRE ATT&CK**: [**T1134.001 - Token Impersonation/Theft**](https://attack.mitre.org/techniques/T1134/001/), [**T1134.002 - Create Process with Token**](https://attack.mitre.org/techniques/T1134/002/).

После успешного входа ценностью становится не только пароль, но и уже выданный токен. Токен - это объект ядра; он существует, пока жив связанный с ним процесс. Процесс с достаточными привилегиями может открыть дескриптор к токену другого процесса и воспользоваться им.

**Технический механизм кражи токена:**

![](../../_images/38d88e331929.webp)

Атакующий не знает пароля - он берёт уже выданный токен. Именно поэтому события **4624 Type 9 (NewCredentials)** в журнале **Security** сигнализируют о входе с **token impersonation**.

**SeImpersonatePrivilege и Potato-атаки.** Эта привилегия по умолчанию выдаётся сервисным аккаунтам: **IIS Application Pool**, **SQL Server**, **NETWORK SERVICE**, **LOCAL SERVICE**. Атакующий, скомпрометировавший веб-приложение или базу данных, получает именно такой аккаунт. **Potato-атаки** (**JuicyPotato**, **PrintSpoofer**, **GodPotato**) эксплуатируют эту привилегию:

![](../../_images/2c0a744cc88f.webp)

> Event ID **4672** с **SeImpersonatePrivilege** в неожиданном контексте - прямой сигнал.

**Быстрая проверка опасных привилегий в системе через PowerShell:**

- Найти процессы с **SeDebugPrivilege** или **SeImpersonatePrivilege**: `whoami /priv`
- Проверить сервисные аккаунты с опасными привилегиями: `Get-CimInstance Win32_Service | Where-Object { $_.StartName -match 'SYSTEM|NetworkService|LocalService' } | Select-Object Name, StartName, PathName | Sort-Object StartName`

Если токен уже есть, следующая цель - повысить его до **High integrity**, минуя диалог **UAC**.

### UAC Bypass (T1548.002)

**MITRE ATT&CK**: [**T1548.002 - Abuse Elevation Control Mechanism: Bypass User Account Control**](https://attack.mitre.org/techniques/T1548/002/).

Если пользователь состоит в **Administrators**, у него есть два токена: ограниченный (**Medium integrity**) для повседневной работы и полный (**High integrity**) для административных задач. **UAC** разделяет эти контексты. Атакующий, уже работающий под таким пользователем с ограниченным токеном, пытается получить высокий контекст без диалога подтверждения.

**Метод 1: eventvwr.exe через реестр**

**eventvwr.exe** - авто-повышаемый бинарник (**auto-elevated**, флаг **requestedExecutionLevel level="highestAvailable"** в манифесте). При запуске он автоматически получает **High integrity** без **UAC**-диалога. Но перед запуском **mmc.exe** с нужной оснасткой он ищет ассоциацию в реестре:

- **eventvwr.exe** при запуске читает: **HKCU\Software\Classes\MSCFile\shell\open\command**
- Нормально этой ветки нет → **eventvwr** берёт ассоциацию из **HKCR**
- Если атакующий создаёт её: `reg add "HKCU\Software\Classes\MSCFile\shell\open\command" /ve /d "cmd.exe /c whoami > C:\temp\out.txt" /f`
   
   - **eventvwr.exe** запускается с **High integrity**
   - читает **HKCU** (пользователь может писать туда без **UAC**)
   - запускает **cmd.exe** - и это уже **High integrity** процесс

Вся цепочка проходит без UAC-диалога, потому что **eventvwr.exe** сам по себе доверенный авто-повышаемый процесс. После использования нужно убрать ключ: `reg delete "HKCU\Software\Classes\MSCFile\shell\open\command" /f`

**Метод 2: fodhelper.exe**

**fodhelper.exe** (**Features on Demand helper**) тоже авто-повышаемый. Читает: **HKCU\Software\Classes\ms-settings\shell\open\command** **\DelegateExecute = ""**

Если создать эту ветку с нужной командой, **fodhelper.exe** её выполнит с **High integrity**.

**Метод 3: COM Elevation через Rundll32**

При уровне **UAC** ниже максимального некоторые **COM**-объекты можно активировать с повышением без диалога. Атакующий через **rundll32.exe** загружает специально сконструированную **DLL**, которая инициирует такую **COM**-активацию и выполняет действие в защищённой директории.

**Обнаружение UAC bypass:**

> Изменение ключей **HKCU\Software\Classes\MSCFile** и **HKCU\Software\Classes\ms-settings** отслеживается **Sysmon Event ID 13**.

Скрипты **PowerShell**:

- Проверить, есть ли следы UAC bypass через реестр: `$bypassKeys = @( "HKCU:\Software\Classes\MSCFile\shell\open\command", "HKCU:\Software\Classes\ms-settings\shell\open\command", "HKCU:\Software\Classes.hta\shell\open\command" ); foreach ($key in $bypassKeys) { if (Test-Path $key) { Write-Warning "Потенциальный UAC bypass key: $key" Get-ItemProperty $key -ErrorAction SilentlyContinue } }`
- Проверить текущий уровень UAC: `$uacValue = Get-ItemProperty "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System" -Name "ConsentPromptBehaviorAdmin" ; Write-Host "UAC ConsentPromptBehaviorAdmin = $($uacValue.ConsentPromptBehaviorAdmin)"`

> 0 - без запроса (опасно), 1 - запрос на безопасном рабочем столе, 2 - запрос с повышенными правами, 5 - запрос (стандартное значение).

Ещё более ранняя точка входа - сам экран входа: вредоносный **Credential Provider** перехватывает секрет до того, как он попадает в **LSA**.

### Credential Provider Abuse

Вредоносный или неправильно установленный **Credential Provider** может вмешиваться в процесс сбора учётных данных на экране входа. Это более редкий, но особенно опасный класс атак: компонент работает рядом с самым чувствительным местом пользовательского входа и выполняется ещё до завершения нормальной загрузки пользовательского окружения.

**Credential Providers** регистрируются в реестре по пути **HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Providers**. Легитимных провайдеров немного: **PasswordProvider**, **PINLogonProvider**, **WinBioCredentialProvider**. Любой неизвестный **GUID** в этой ветке требует расследования.

Проверить зарегистрированные **Credential Providers** через **PowerShell**: `Get-ChildItem 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Providers' | ForEach-Object { $name = (Get-ItemProperty $_.PSPath).'(default)'; [PSCustomObject]@{ GUID = $_.PSChildName; Name = $name } }`

Любой незнакомый **GUID** без связанного продукта - повод для расследования. Легитимный **Credential Provider** появляется только при установке продукта безопасности или **SSO**-решения, и это изменение должно быть задокументировано.
