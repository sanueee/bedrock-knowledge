# Пользователи, группы и права доступа

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Пользователи, группы и права доступа
>
> **Кейсы:** [3.03 Пользователи и группы](../../cases/windows/3.03%20Пользователи%20и%20группы.md)

**Пользователи и группы** - это субъекты безопасности, к которым Windows привязывает все права на ресурсы хоста. Понимание того, какие бывают учётные записи, как они устроены изнутри и через какие механизмы получают доступ к файлам, реестру и службам - базовое знание для администратора и для специалиста по информационной безопасности. Эта статья разбирает четыре уровня темы: типы учётных записей и локальные группы; формальную модель безопасности, через которую Windows принимает решение о доступе; детальные права на файлы через **NTFS** и сетевые ресурсы; и техники, через которые атакующие эксплуатируют неправильно настроенные права. Базовая структура токена и проверки доступа уже разобрана в статье 2.1 - здесь акцент на специфике учётных записей и на разграничении прав.

> Представьте корпоративное здание. У каждого сотрудника есть электронный пропуск - на нём записано, кто он (**SID**) и в какие отделы может заходить (группы). Внутри здания у каждой комнаты свой охранник (**NTFS ACL**) со списком: "Иванов может войти, Петров - нет". На главной проходной (сетевой доступ) сидит ещё один охранник (**Share permissions**). Чтобы попасть в комнату через сеть, нужно пройти оба - и проходной, и комнатный.

## Типы учётных записей

Прежде чем рассматривать права доступа к файлам и реестру, нужно разобраться с основным субъектом безопасности Windows - учётной записью пользователя. Windows различает несколько типов учётных записей, и от типа зависит, что пользователь может делать в системе.

**Обычные пользователи.** Стандартные учётные записи, создаваемые вручную для работы людей. Входят в группу **Users**, могут запускать установленные программы и читать файлы в своём профиле, но не могут устанавливать драйверы или изменять системные файлы. Создание через **PowerShell**:

```
New-LocalUser -Name "vasya" -FullName "Vasiliy Ivanov" -NoPassword
Add-LocalGroupMember -Group "Users" -Member "vasya"
```

**Встроенные учётные записи.** Windows создаёт их автоматически при установке. Их нельзя удалить стандартными средствами, но можно переименовать и отключить.

| Тип | Примеры | Права по умолчанию | Назначение |
|---|---|---|---|
| Встроенный администратор ( RID 500 ) | Administrator | Полный контроль над системой | Аварийное восстановление, первичная настройка |
| Обычный пользователь | Vasya , Petya | Стандартный доступ, нет прав на установку ПО | Повседневная работа |
| Встроенный гость ( RID 501 ) | Guest | Минимальные, по умолчанию отключён | Временный доступ без учётной записи |
| Сервисный аккаунт | svc_backup , svc_sql | Только то, что нужно службе | Запуск служб и приложений |
| Виртуальный/системный | SYSTEM , LOCAL SERVICE , NETWORK SERVICE | Зависит от типа ( SYSTEM - полный) | Внутренние процессы ОС |

**Важно.** Учётная запись **Administrator** (**RID 500**) отключена по умолчанию на современных версиях Windows. Рекомендуется оставить её отключённой и переименовать - это затруднит атаки на предсказуемое имя.

**Сервисные учётные записи.** Используются для запуска служб и приложений - баз данных, веб-серверов, агентов резервного копирования. Сервисный аккаунт не должен иметь прав интерактивного входа и должен получать только те привилегии, которые нужны конкретной службе (принцип наименьших привилегий). Создание: `New-LocalUser -Name "svc_backup" -NoPassword -PasswordNeverExpires`

Запретить интерактивный вход - через локальную политику безопасности.

**Системные учётные записи.** Не отображаются в списке пользователей, не имеют пароля. Используются внутри ОС для запуска системных процессов.

| Учётная запись | SID | Описание |
|---|---|---|
| SYSTEM | S-1-5-18 | Максимальные привилегии. От её имени работает ядро ОС и большинство системных служб |
| LOCAL SERVICE | S-1-5-19 | Ограниченные права. Для служб, которым не нужна сеть |
| NETWORK SERVICE | S-1-5-20 | Ограниченные права + сетевой доступ от имени компьютера |
| Everyone | S-1-1-0 | Все пользователи, включая гостей. Осторожно с назначением прав |
| Authenticated Users | S-1-5-11 | Все прошедшие аутентификацию (без гостей). Безопаснее Everyone |

**Важно.** **SYSTEM** - это не обычный пользователь, а специальный контекст безопасности ядра. Процессы, работающие от **SYSTEM**, имеют доступ к любому объекту на локальном компьютере. Именно поэтому захват привилегий **SYSTEM** является конечной целью большинства атак на повышение привилегий.

Кроме индивидуальных учётных записей, Windows использует группы. Они позволяют назначать права сразу набору пользователей, не настраивая каждого отдельно.

## Локальные группы по умолчанию

При установке Windows создаёт набор стандартных групп. Группы позволяют назначать права сразу нескольким пользователям, не настраивая каждого по отдельности.

| Группа | SID / RID | Что может |
|---|---|---|
| Administrators | S-1-5-32-544 ( RID 544 ) | Полный контроль над локальной системой |
| Users | S-1-5-32-545 ( RID 545 ) | Стандартные права, запуск большинства программ |
| Guests | S-1-5-32-546 ( RID 546 ) | Минимальные права, временный доступ |
| Remote Desktop Users | S-1-5-32-555 ( RID 555 ) | Подключение по RDP без прав администратора |
| Power Users | S-1-5-32-547 ( RID 547 ) | Устарела. Раньше - "почти админ", сейчас почти не используется |
| Backup Operators | S-1-5-32-551 ( RID 551 ) | Резервное копирование и восстановление файлов в обход ACL |

**Примечание.** Группа **Power Users** сохранена для совместимости со старым ПО. В современных системах её использование не рекомендуется.

## Управление через PowerShell

**PowerShell** предпочтительнее графических инструментов: позволяет автоматизировать задачи, работает одинаково на всех версиях Windows 10/11/Server и легко встраивается в скрипты.

| Команда | Что делает |
|---|---|
| Get-LocalUser | Список всех локальных пользователей |
| Get-LocalGroup | Список всех локальных групп |
| Get-LocalGroupMember Administrators | Члены группы Administrators |
| New-LocalUser -Name "svc_app" | Создать нового локального пользователя |
| Add-LocalGroupMember -Group "Administrators" -Member "svc_app" | Добавить пользователя в группу |
| Disable-LocalUser -Name "Guest" | Отключить учётную запись |
| Enable-LocalUser -Name "Admin2" | Включить учётную запись |
| Get-LocalUser | Select Name, Enabled, SID | Показать имя, статус и SID всех пользователей |

Команды выше управляют учётками и группами на хосте. Теперь о том, как Windows на уровне ядра принимает решение, кому что разрешено.

## Разграничение прав: Модель безопасности Windows

Модель безопасности Windows базируется на трёх китах: **Security Identifier (SID)**, **токен доступа** и **Access Control List (ACL)**.

**SID** - уникальный идентификатор, который Windows присваивает каждому пользователю, группе и даже компьютеру при их создании. Он никогда не меняется и не используется повторно. Выглядит он так:

**S-1-5-21-397955417-626881126-188441444-1001**

Где:

- **S** - префикс (Security)
- **1** - версия
- **5** - authority (NT Authority)
- **21-...** - уникальный идентификатор компьютера или домена
- **1001** - **Relative Identifier (RID)** - относительный идентификатор пользователя

![](../../_images/8a2fbdc23546.webp)

**Важно.** **SID** - это "паспорт" пользователя. Его нельзя подделать или изменить без специальных инструментов и прав **SYSTEM**. Именно по **SID**, а не по имени, Windows идентифицирует пользователя. Если Вы переименуете пользователя **Vasya** в **Petya**, его **SID** останется прежним - система по-прежнему знает, кто есть кто.

![](../../_images/7e945010f9da.webp)

**Токен доступа** - структура, которую Windows создаёт при входе пользователя в систему и прикрепляет к каждому запущенному им процессу. Подробно её устройство (**SID** пользователя, **SID** групп, список привилегий, уровень целостности, типы первичного и **impersonation**-токена) разобрано в статье 2.1. Для текущей темы достаточно ключевого свойства: всё, что процесс пытается сделать с защищаемым объектом, проверяется через сравнение токена и **ACL** объекта.

**ACL** уже введён в 2.1 как список разрешений на защищаемом объекте. Здесь важен его внутренний состав: **ACL** состоит из записей **Access Control Entry (ACE)**. Каждая **ACE** - это одно правило вида "такой-то **SID** имеет такие-то права" или "такому-то **SID** запрещено такое-то действие". Дальше по тексту мы будем работать именно с **ACE** - они тот строительный блок, из которого собирается любое разрешение на файл, ключ реестра или службу.

## NTFS ACL: Охрана на уровне файлов

**NTFS ACL** - это самый детальный уровень контроля доступа в Windows. Каждый файл и папка на томе **NTFS** имеет свой **ACL**, который хранится в атрибуте **$SECURITY_DESCRIPTOR** внутри **Master File Table (MFT)**.

**Базовые разрешения NTFS (как их видит пользователь)**

| Разрешение | Что означает |
|---|---|
| Полный доступ | Всё: чтение, запись, выполнение, удаление, смена прав, смена владельца |
| Изменение | Чтение, запись, выполнение, удаление - но не смена прав |
| Чтение и выполнение | Просмотр содержимого и запуск программ |
| Чтение | Только просмотр (нельзя запускать) |
| Запись | Создание и изменение файлов |

**Расширенные разрешения**

| Расширенное право | Что разрешает |
|---|---|
| Traverse folder / execute file | Позволяет пройти через папку (даже если нет права "Содержание папки") к вложенному объекту, если известен его полный путь. Для файлов - разрешает запуск исполняемых файлов (.exe, .dll) |
| List folder / read data | Для папки - позволяет видеть имена файлов и подпапок . Для файлов - разрешает открывать и читать содержимое |
| Read attributes | Разрешает читать стандартные атрибуты файла/папки: ReadOnly , Hidden , Archive , System |
| Read extended attributes | Разрешает читать расширенные атрибуты - редко используемая возможность, оставшаяся от OS/2 . Некоторые вредоносные программы могут использовать расширенные атрибуты для хранения данных |
| Create files / write data | Для папки - разрешает создавать новые файлы внутри. Для файлов - разрешает изменять содержимое (перезаписывать или дописывать в конец) |
| Create folders / append data | Для папки - разрешает создавать вложенные папки . Для файлов - разрешает только добавлять данные в конец файла (без изменения уже существующего содержимого) |
| Write attributes | Разрешает изменять стандартные атрибуты ( ReadOnly , Hidden ). Не даёт изменять атрибуты сжатия и шифрования - для них нужны права администратора |
| Write extended attributes | Разрешает изменять расширенные атрибуты |
| Delete subfolders and files | Разрешает удалять дочерние объекты внутри папки, даже если нет права "Удаление" на саму папку |
| Delete | Разрешает удалить сам объект (файл или папку) |
| Read permissions | Разрешает просматривать ACL объекта |
| Change permissions | Разрешает изменять ACL объекта (добавлять/удалять пользователей и группы, менять их права) |
| Take ownership | Разрешает стать владельцем объекта. Владелец всегда может изменить разрешения (даже если "Смена разрешений" запрещена) |

> Базовые разрешения - это готовые наборы инструментов из магазина: "набор плотника", "набор электрика", "набор слесаря". Расширенные разрешения - это отдельные инструменты: молоток, отвёртка, плоскогубцы. Готовый набор можно собрать самому из отдельных инструментов, но обычно проще взять готовый. К расширенным правам Вы спускаетесь только тогда, когда нужно настроить что-то очень тонкое, чего в готовых наборах нет.

**Правила комбинирования разрешений NTFS**

1. **Явный запрет важнее явного разрешения.** Если в **ACL** есть запись "Запретить Vasya Чтение" и "Разрешить Vasya Чтение" - победит запрет
2. **Разрешения накапливаются.** Если **Vasya** входит в группу A (разрешено чтение) и группу B (разрешена запись), то в сумме у **Vasya** будут и чтение, и запись
3. **Наследование.** По умолчанию папки передают свои разрешения дочерним файлам и папкам. Это можно отключить (разорвать наследование) для конкретного объекта

## Сетевые права: Охрана на входе в здание

Когда пользователь подключается к папке по сети (через **\server\share**), в игру вступают **сетевые права**. Это второй уровень фильтрации, который работает до того, как пользователь вообще получит доступ к **NTFS**.

**Уровни сетевых прав.**

| Разрешение | Что даёт |
|---|---|
| Read | Просмотр имён файлов и папок, чтение файлов |
| Change | Всё из Read + создание/удаление файлов и папок |
| Full Control | Всё из Change + смена прав на самом общем ресурсе |

**Ключевая особенность.** Сетевые права действуют только при удалённом доступе. Если пользователь зашёл на сервер локально (физически или через **RDP**), сетевые права не применяются - только **NTFS**.

> Сетевые права - это охранник на проходной завода. Он проверяет, есть ли у Вас пропуск вообще и в какую зону Вас пускать. Но даже если он пропустил Вас на территорию, охранник внутри цеха (**NTFS ACL**) может сказать: "Стоп, в эту лабораторию вход только для своих". При локальном входе на сервер (через консоль или **RDP**) проходной нет - сразу начинается охранник цеха.

## Конфликт NTFS и сетевых прав: Золотое правило

**Самое важное правило, которое нужно запомнить:** при доступе к файлу по сети конечные права пользователя - это **пересечение** из сетевых прав и прав **NTFS**.

Проще говоря: что запрещает один слой, другой не может разрешить.

**Таблица итоговых прав**

| Сетевые права | Права NTFS | Итоговый доступ |
|---|---|---|
| Read | Read | Read |
| Read | Full Control | Read ( NTFS разрешает больше, но сетевые права ограничивают) |
| Full Control | Read | Read (сетевые права разрешают всё, но NTFS даёт только чтение) |
| Full Control | Full Control | Full Control |
| Deny Read | Full Control | Deny (запрет на любом уровне убивает всё) |
| Full Control | Deny Read | Deny |

![](../../_images/a3886bbdf082.webp)

> Две двери, на каждой свой охранник. Пройти можно только если оба пропустили. Если первый разрешил **Full Control**, а второй разрешил только чтение - сможете только читать. Если первый разрешил, а второй прямо запретил - не пройдёте никак, запрет всегда сильнее разрешения. Это та же арифметика, по которой работает связка **Share** + **NTFS**.

Графический интерфейс прав в Windows - это удобная оболочка над более низкоуровневым форматом. Этот формат называется **SDDL**.

## SDDL: Язык описания безопасности

**Security Descriptor Definition Language (SDDL)** - это текстовый язык для описания дескрипторов безопасности. Это стандартизированный формат, который Windows использует внутри для хранения и передачи информации о правах доступа.

Когда Вы смотрите на вкладку **Security** в свойствах файла, Windows показывает Вам графическое представление **SDDL**. Но в реестре, в скриптах **PowerShell**, в результатах некоторых команд **SDDL** появляется в чистом текстовом виде.

**Формат строки SDDL.** Полная строка дескриптора безопасности выглядит так:

**O:owner_sid G:group_sid D:dacl_flags(ace1)(ace2)... S:sacl_flags(ace1)(ace2)...**

Где:

- **O:** - владелец объекта (Owner)
- **G:** - группа-владелец (Primary Group)
- **D:** - **DACL** (**Discretionary Access Control List** - кто что может)
- **S:** - **SACL** (**System Access Control List** - аудит)

**Формат ACE (одной записи внутри D: или S:).** Каждая **ACE** заключена в круглые скобки, поля разделены точкой с запятой: **(ace_type;ace_flags;rights;object_guid;inherit_object_guid;account_sid)**

| Поле | Что означает | Примеры |
|---|---|---|
| ace_type | Тип ACE : разрешить или запретить | A - Allow, D - Deny |
| ace_flags | Флаги наследования | CI - Container Inherit, OI - Object Inherit |
| rights | Какие права даёт/запрещает ACE | FA - File All, FR - File Read, GA - Generic All |
| object_guid | GUID объекта (для Active Directory ) | {ab721a53-1e2f-11d0-9819-00aa0040529b} - право смены пароля |
| inherit_object_guid | GUID наследуемого объекта | Редко используется |
| account_sid | SID пользователя или группы | S-1-5-21-...-1001 или SY ( SYSTEM ), BA (Built-in Administrators ) |

**Самые частые SID в сокращённой форме.** **SDDL** поддерживает сокращения для встроенных **SID**:

| Сокращение | SID | Описание |
|---|---|---|
| SY | S-1-5-18 | SYSTEM (локальная система) |
| BA | S-1-5-32-544 | Built-in Administrators |
| BU | S-1-5-32-545 | Built-in Users |
| BG | S-1-5-32-546 | Built-in Guests |
| AU | S-1-5-11 | Authenticated Users |
| WD | S-1-1-0 | Everyone |
| AN | S-1-5-7 | Anonymous |

**Сокращения для прав доступа**

| Сокращение | Расшифровка | Что даёт |
|---|---|---|
| FA | File All | Полный доступ к файлу |
| FR | File Read | Чтение файла |
| FW | File Write | Запись в файл |
| FX | File Execute | Выполнение файла |
| GA | Generic All | Все права (обобщённо) |
| GR | Generic Read | Чтение (обобщённо) |
| GW | Generic Write | Запись (обобщённо) |
| GX | Generic Execute | Выполнение (обобщённо) |
| KA | Key All | Полный доступ к ключу реестра |
| KR | Key Read | Чтение ключа реестра |

**Пример SDDL строки.** Разберём реальный пример: **O:SYG:SYD:(A;;FA;;;WD)**

| Часть | Значение | Расшифровка |
|---|---|---|
| O:SY | Owner = SYSTEM | Владелец - локальная система |
| G:SY | Group = SYSTEM | Группа - локальная система |
| D: | Начало DACL | Список разрешений |
| (A;;FA;;;WD) | ACE | Разрешение ( A = Allow), права FA (Full Access), SID = WD ( Everyone ) |

![](../../_images/1ae050c42037.webp)

На практике Вы редко будете писать **SDDL** вручную. Но **читать** его - полезный навык для анализа скриптов и конфигураций безопасности.

На практике **SDDL** встретится Вам в выводе **sc.exe sdshow** при проверке прав на службу, в свойствах ключей реестра (особенно в **HKLM\SYSTEM\CurrentControlSet\Services**), в результатах **PowerShell**-командлета **Get-Acl** и в **XML**-файлах политик безопасности. Уметь читать **SDDL** означает уметь быстро понимать, что разрешено и кому, без необходимости открывать **GUI** на каждом объекте.

## PowerShell для работы с ACL

Просмотреть **ACL** объекта: `Get-Acl "C:\SensitiveData" | Format-List`

Просмотреть каждую **ACE** в читаемом виде: `(Get-Acl "C:\SensitiveData").Access | Format-Table IdentityReference, FileSystemRights, AccessControlType, IsInherited -AutoSize`

Найти файлы с правами записи для широких групп (типичный вектор повышения привилегий): `Get-ChildItem "C:\Program Files" -Recurse -ErrorAction SilentlyContinue | ForEach-Object { $acl = Get-Acl $ .FullName -ErrorAction SilentlyContinue; if ($acl.Access | Where-Object { $.FileSystemRights -match 'Write|FullControl|Modify' -and $_.AccessControlType -eq 'Allow' -and $_.IdentityReference -match 'Everyone|Authenticated Users|BUILTIN\Users' }) { Write-Warning "Writable by low-priv users: $($_.FullName)" } }`

Просмотреть **ACL** ключа реестра: `Get-Acl "HKLM:\SYSTEM\CurrentControlSet\Services\SomeService" | Format-List`

Команды выше - инструменты администратора. Те же команды используют злоумышленники, чтобы искать неправильно настроенные права. Дальше - четыре классических вектора, на которых это основано.

## Эксплуатация необычных прав: как злоумышленники повышают привилегии

Понимание модели безопасности Windows - это не только про защиту, но и про то, как злоумышленники ищут слабые места. Есть несколько классических техник повышения привилегий, основанных на неправильной настройке прав доступа.

**1. RID Hijacking.** Атака, при которой путём подмены **RID** в **Security Account Manager (SAM)** можно превратить обычного локального пользователя в локального админа.

**Как работает:**

1. Злоумышленник сначала получает доступ уровня **SYSTEM** (например, через эксплойт или неправильно настроенную службу)
2. Создаёт скрытую учётную запись с низкими привилегиями (обычно с специальным символом в имени, чтобы она не отображалась в стандартных списках)
3. Затем модифицирует реестр (**HKLM\SAM**) и меняет **RID** этой учётной записи с обычного (например, 1001) на административный (500)
4. После перезагрузки или повторного входа Windows воспринимает эту учётную запись как встроенного администратора

**Почему это опасно.** Учётная запись не отображается в стандартных интерфейсах (нет в **net user**), но имеет полный доступ к системе

**Защита.** Ограничение доступа к реестру **HKLM\SAM** (только **SYSTEM**), использование **LSA Protection** (**RunAsPPL**), регулярный аудит необычных учётных записей

![](../../_images/a0b5b57e990b.webp)

**2. OOBE Breakout.** Во время первоначальной настройки Windows (**OOBE** - **Out-Of-Box Experience**) система создаёт временную учётную запись **defaultuser0** с правами администратора. Это необходимо для установки и настройки.

**Как работает эксплойт:**

1. На экране **OOBE** (выбор региона, создание пользователя) злоумышленник открывает экранную лупу (**Magnify.exe**)
2. Нажимает **Win + R** (Run), затем **Alt + Tab**, чтобы переключиться на скрытое окно Run
3. Вводит **cmd.exe** и нажимает **Ctrl + Shift + Enter** - это вызывает **UAC**-запрос
4. Принимает **UAC** - и получает командную строку с правами администратора от имени **defaultuser0**

**Защита.** В корпоративной среде - скрыть кнопку сброса в **Intune**, использовать **Autopilot** для полностью автоматизированной настройки.

**3. SeBackupPrivilege / SeRestorePrivilege.** Это привилегии, которые позволяют пользователю читать любые файлы (**SeBackup**) или записывать в любые места (**SeRestore**), **игнорируя NTFS ACL**. Они предназначены для программ резервного копирования, но если их случайно дать обычному пользователю - катастрофа.

**Эксплуатация** - чтение **SAM**-файла через утилиту **reg save**, игнорируя **ACL**: `reg save hklm\sam C:\temp\sam.bak`

**Как проверить привилегии пользователя: **`whoami /priv`

Если Вы видите **SeBackupPrivilege** в списке и напротив **Enabled** - пользователь может читать любой файл на диске, даже **C:\Windows\System32\config\SAM**.

> **SeBackupPrivilege** - это мастер-ключ уборщицы. Уборщица должна попадать во все кабинеты, чтобы делать свою работу, поэтому её ключ открывает любую дверь, минуя обычные пропуска. Если такой ключ попал не в те руки - вся обычная система пропусков перестаёт что-либо значить. Поэтому **SeBackupPrivilege** выдают только программам резервного копирования и тщательно следят, кому ещё она досталась.

**4. Weak Service Permissions.** Это классика повышения привилегий. Службы Windows часто запускаются от имени **SYSTEM**, но права на управление службой (запуск, остановку, изменение конфигурации) могут быть неправильно настроены. Каждая служба в Windows - это объект безопасности с собственным **Access Control List**.

**Что ищут злоумышленники:**

- Службу, у которой **SERVICE_CHANGE_CONFIG** разрешена для обычных пользователей
- Службу, у которой путь к исполняемому файлу (**ImagePath**) записывается обычным пользователем

**Эксплуатация** - изменить конфигурацию службы так, чтобы она запускала **cmd**:

```
sc config "ИмяСлужбы" binPath= "C:\Windows\System32\cmd.exe /c whoami > C:\temp\out.txt"
sc start "ИмяСлужбы"
```

**Защита:**

1. Регулярный аудит **ACL** служб через **PowerShell**
2. Удалить **BUILTIN\Users** из прав на изменение системных служб
3. Включить аудит событий изменения служб (**Event ID 4697**, **7040**, **7045**)
4. Использовать **Group Managed Service Account (gMSA)** для сервисных аккаунтов в домене
5. Соблюдать принцип наименьших привилегий (проверять **whoami /priv**)

У Вас в руках теперь четыре блока знаний о правах в **Windows**: какие бывают учётные записи и группы, как **Windows** формально проверяет доступ через **SID** + токен + **ACL**, как настраиваются права на файлы и сетевые ресурсы, и какие классические ошибки конфигурации превращаются в векторы повышения привилегий. К этим знаниям Вы будете возвращаться при каждом аудите хоста и при разборе подозрительной активности.
