# 4. Windows 7 / Server 2008 R2: масштабирование и Hyper-V v2

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Эволюция Windows NT

**Windows 7** исправила многие практические проблемы **Vista**. С точки зрения ядра это не революция, но некоторые изменения важны.

**Processor Groups** До Windows 7 планировщик мог работать максимум с 64 логическими процессорами - жёсткое архитектурное ограничение. На больших серверных машинах с несколькими многоядерными процессорами это стало реальной проблемой. **Processor groups** разбивают все доступные процессоры на группы по 64 и позволяют ОС и приложениям работать со всем пулом сразу ([**Processor Groups**](https://learn.microsoft.com/en-us/windows/win32/procthread/processor-groups)). Для разработчиков это означает следующее: многопоточный код, написанный без учёта **processor groups**, будет незаметно использовать только часть доступных ядер на больших серверах. Это особенно актуально при написании инструментов анализа и мониторинга.

**Core Parking и Timer Coalescing** Планировщик научился останавливать ядра **CPU**: при низкой нагрузке часть ядер переводится в состояние глубокого сна, а работа концентрируется на меньшем числе активных ([**Core Parking**](https://techcommunity.microsoft.com/blog/askperf/windows-7--windows-server-2008-r2-core-parking--intelligent-timer-tick--timer-co/374196/)). Параллельно ядро начало группировать **таймеры** - вместо того чтобы просыпаться на каждый таймер отдельно, процессор обрабатывает несколько сразу и снова засыпает. Для серверов это означает более эффективную работу под переменной нагрузкой.

**Удаление scheduler dispatcher lock** Внутри планировщика была глобальная блокировка - **dispatcher lock**, - которая сериализовала часть операций на многопроцессорных системах. Её удаление улучшило параллелизм: больше потоков могут одновременно взаимодействовать с планировщиком без ожидания. Для конечного пользователя незаметно, но важно для производительности SQL Server, баз данных и других нагрузок с высокой частотой переключения контекста.

**User-Mode Scheduling (UMS)** Механизм, позволяющий **runtime**-библиотекам управлять планированием пользовательских задач поверх **kernel threads** - без постоянных **syscalls** в ядро. Использовался нишево (в основном в высокопроизводительных серверных сценариях), но архитектурно интересен: это попытка вынести часть работы планировщика из ядра, уменьшив переключения контекста и нагрузку на ядро.

**Hyper-V Live Migration** **Server 2008 R2** принёс возможность переноса работающей **VM** между узлами без остановки ([**Live Migration**](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/live-migration-overview)). С точки зрения безопасности инфраструктуры это важно в двух направлениях: патчинг хост-систем теперь не требует остановки сервисов - **VM** мигрирует на соседний узел, хост патчится и перезагружается. Но **live migration** также означает, что состояние памяти **VM** - включая **ключи**, **хэши**, **credentials** в **RAM** - передаётся по сети между узлами, и безопасность этого канала становится отдельным вопросом.
