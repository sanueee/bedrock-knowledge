# Драйверы и взаимодействие с ядром

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Драйверы и взаимодействие с ядром
>
> **Кейсы:** [3.02 Драйвера](../../cases/windows/3.02%20Драйвера.md)

Windows - многоуровневая система, и каждый уровень имеет свои правила доступа к ресурсам. Чтобы понять, почему драйверы так важны с точки зрения безопасности, нужно сначала разобраться в том, как процессор разграничивает привилегии между обычными программами и системным кодом.

**Драйвер** - файл **.sys**, загружаемый в ядро Windows. Это не обычное приложение: его нельзя запустить двойным кликом, и работает он не сам по себе - это набор обработчиков, которые ядро вызывает при необходимости. С точки зрения безопасности драйвер - это **код с максимальными привилегиями в системе**: **ring 0**, прямой доступ к любой ячейке памяти и любому порту ввода-вывода. Уязвимость или вредоносный код в драйвере - немедленная компрометация всей системы без каких-либо ограничений песочницы.

Чтобы понять почему это так критично, разберёмся как процессор разграничивает привилегии.

## Кольца защиты процессора

Процессоры **Intel**/**AMD** реализуют аппаратную изоляцию через **кольца привилегий** (**Rings 0–3**). Windows использует два из них:

![](../../_images/00f5865fddda.webp)

### User Mode (Ring 3)

Все пользовательские приложения работают здесь. Ключевые ограничения:

- **Нет прямого доступа к железу** - только через системные вызовы
- **Изолированное виртуальное адресное пространство** - процесс не может читать память другого процесса
- **Ошибка убивает только процесс** - остальная система продолжает работу

Именно поэтому падение браузера или игры не роняет всю Windows.

> Приложения в **User Mode** активно используют **Dynamic Link Library** (**DLL**) - файлы с готовым кодом, который подгружается во время работы. Вместо того чтобы каждая программа писала собственные функции работы с сетью или файлами, они все используют одни и те же системные **DLL:** **kernel32.dll**, **ntdll.dll**, **ws2_32.dll**. Это экономит память и упрощает разработку - но создаёт дополнительную поверхность атаки.

### Kernel Mode (Ring 0)

Ядро (**ntoskrnl.exe**), драйверы (**.sys**) и **HAL** работают здесь. Возможности:

- Прямой доступ к любой физической памяти
- Прямое управление любым устройством
- Изменение любых системных структур

**Цена привилегий:** ошибка в **Kernel Mode** не изолируется. У ОС нет механизма перехватить и ограничить её последствия. Результат - **BSOD**.

| Характеристика | User Mode (Ring 3) | Kernel Mode (Ring 0) |
|---|---|---|
| Что работает | Браузеры, офис, игры, скрипты | Ядро, драйверы ( .sys ), HAL |
| Доступ к железу | Только через syscalls | Прямой, неограниченный |
| Доступ к памяти | Только своё адресное пространство | Вся физическая память |
| Последствия ошибки | Падает только процесс | BSOD , остановка системы |
| Последствия компрометации | Доступ к данным одного пользователя | Полный контроль над системой |
| Пример ошибки | Access Violation → процесс убит | PAGE_FAULT_IN_NONPAGED_AREA → BSOD |

> **Для атакующего:** получить выполнение кода в **Ring 0** - конечная цель. Из **Ring 0** можно отключить антивирус, скрыть процессы, перехватить любые данные, установить буткит. Именно поэтому Microsoft так агрессивно защищает загрузку кода в ядро.

Разобравшись с уровнями привилегий, посмотрим на то какие именно драйверы существуют и какую роль каждый из них играет в системе.

## Типы драйверов

**Драйверы устройств** управляют конкретным железом: видеокартой, сетевой картой, USB-контроллером. Работают напрямую с регистрами устройства через **HAL**.

**Драйверы файловых систем** реализуют логику чтения/записи на диск: **NTFS**, **FAT32**, **exFAT**. Невидимы пользователю, но критически важны - любая операция с файлом проходит через них.

**Драйверы-фильтры** встраиваются в цепочку обработки запросов между приложением и устройством. Именно так работают антивирусы: фильтр-драйвер перехватывает запрос на открытие файла *до* того, как его прочитает приложение, сканирует содержимое и либо пропускает, либо блокирует.

![](../../_images/3f32d47c6a72.webp)

Эта же архитектура используется **Sysmon**, **EDR**-агентами и **DLP**-системами.

## Как драйвер попадает в систему

1. **Подключение устройства** - Windows получает от шины (**PCI**, **USB**) идентификатор устройства
2. **Поиск в Driver Store** - локальное хранилище **C:\Windows\System32\DriverStore\FileRepository**
   
   1. **Plug and Play** - если драйвер найден, установка происходит автоматически без перезагрузки
   2. **Windows Update / ручная установка** - если не нашелся в **Driver Store**
3. **Проверка подписи (DSE)** - происходит перед загрузкой драйвера в ядро
4. **Загрузка в Ring 0** - если подпись валидна драйвер загружается в адресное пространство ядра

Ключевой элемент в этой цепочке - шаг проверки подписи. Именно он отделяет легитимные драйверы от вредоносных. Разберём как он устроен и почему его можно обойти.

## DSE: Driver Signature Enforcement

**DSE** - механизм проверки цифровой подписи, встроенный в загрузчик ядра. Перед загрузкой **.sys** файла Windows проверяет:

1. Наличие подписи **Authenticode**
2. Цепочку доверия до корневого сертификата Microsoft
3. Целостность файла (хэш не изменился после подписания)

Неподписанный или изменённый драйвер получает отказ с ошибкой **Code 52**. На **x86**-системах **DSE** **отсутствует** - ядро физически не выполняет эту проверку.

Несмотря на это, злоумышленники располагают несколькими способами загрузить неподписанный код в ядро - каждый из них эксплуатирует своё слабое место в модели доверия.

### Методы обхода DSE

**1. Режим тестовой подписи**

Windows содержит встроенный механизм для разработчиков драйверов - режим тестовой подписи. В этом режиме система разрешает загрузку самоподписанных **.sys**-файлов, минуя проверку **DSE**. Это позволяет тестировать собственные драйверы без прохождения официальной процедуры подписания у Microsoft.

После включения на рабочем столе появляется водяной знак **Test Mode** - визуальный индикатор того, что защита подписи отключена. На производственных системах его наличие без обоснования является индикатором компрометации.

Включается командой в **cmd**: `bcdedit /set testsigning on`

**2. BYOVD: Bring Your Own Vulnerable Driver (T1068)**

**BYOVD** - самый распространённый современный метод компрометации ядра. Ключевая идея: атакующий не пытается обойти **DSE**, а использует тот факт, что Windows охотно загружает **легитимный, подписанный** драйвер, даже если в этом драйвере есть критическая уязвимость. Загружая уязвимую версию драйвера, атакующий получает доступ к **Ring 0** и может делать в ядре всё что угодно.

**MITRE ATT&CK:** [**T1068**](https://attack.mitre.org/techniques/T1068/) - Exploitation for Privilege Escalation, часто совмещается с [**T1562.001**](https://attack.mitre.org/techniques/T1562/001/) - Impair Defenses: Disable or Modify Tools.

**Почему BYOVD так эффективен:** **DSE** проверяет только наличие подписи, если она валидна, значит драйвер загружается. Список отзыва сертификатов (**DBX**) обновляется нерегулярно, поэтому уязвимые драйверы долго остаются в обороте. Большинство организаций не мониторят загрузку новых **.sys**-файлов в реальном времени - а значит атака проходит незамеченной.

**Техническая цепочка BYOVD:**

![](../../_images/b9611b8cdd93.webp)

На практике для BYOVD использовались драйверы таких продуктов как **MSI Afterburner** (**RTCore64.sys**), **GIGABYTE** (**gdrv.sys**), **Intel Network Adapter** (**iqvw64e.sys**) и даже античит **Genshin Impact** (**mhyprot2.sys**).

**Целевая задача BYOVD:** не только повышение до **Ring 0**, но прежде всего **убийство EDR-агентов** - после получения доступа к ядру атакующий может завершить любой защитный процесс, удалить его драйвер и лишить систему телеметрии.

**MITRE ATT&CK:** [**T1562.001**](https://attack.mitre.org/techniques/T1562/001/) - Impair Defenses: Disable or Modify Tools.

**Защита:** включить **HVCI** (**Memory Integrity)** - гипервизор будет проверять весь код ядра, и уязвимый драйвер не сможет модифицировать его структуры. Дополнительно - актуальный блок-лист уязвимых драйверов Microsoft (**WDAC Vulnerable Driver Blocklist**) обновляется через **Windows Update**.

**3. Эксплуатация уязвимостей ядра**

**CVE** в самом ядре Windows, позволяющие повысить привилегии до **Ring 0** без загрузки стороннего драйвера. Примеры: **CVE-2021-34527** (**PrintNightmare**), **CVE-2022-37969** (**Windows Common Log File System**), **CVE-2024-21338** (**Windows Kernel**- использовался группой Lazarus). В отличие от **BYOVD**, не требуют наличия уязвимого драйвера, но зависят от актуальности патчей на целевой системе.

Даже если атакующий загрузил вредоносный код в ядро, Windows имеет ещё один рубеж защиты - механизм, который периодически проверяет, не были ли изменены критические структуры ядра.

## PatchGuard (Kernel Patch Protection)

Когда атакующий получает доступ к **Ring 0**, первое что он захочет сделать - модифицировать структуры ядра: подменить обработчики системных вызовов, внедрить свой код в таблицу прерываний или изменить код самого ядра. Именно против этого направлен **PatchGuard**.

**PatchGuard** - механизм защиты ядра на **x64**-системах. При загрузке он снимает эталонные хэши критических структур ядра и периодически в случайные моменты времени перепроверяет их. Если текущее состояние структуры не совпадает с эталоном - значит кто-то её модифицировал, и Windows немедленно останавливает систему.

Проверяются:

- **System Service Descriptor Table** (**SSDT**) - таблица системных вызовов
- **Interrupt Descriptor Table** (**IDT**) - таблица прерываний
- **GDT/LDT** - таблицы дескрипторов сегментов
- Код и данные **ntoskrnl.exe**

При обнаружении модификации **PatchGuard** вызывает немедленный **BSOD** с кодом **0x109 CRITICAL_STRUCTURE_CORRUPTION**.

Мы разобрали как ядро и драйверы защищают себя от модификации. Но между ядром и физическим железом есть ещё один слой, без которого Windows не смогла бы работать на разном оборудовании - **HAL**.

## HAL: Hardware Abstraction Layer

**HAL** - это уровень аппаратных абстракций, встроенный переводчик между ядром Windows и физическим железом. Без него ядро было бы вынуждено знать особенности каждой материнской платы, каждого чипсета и каждой архитектуры - вместо этого оно отдаёт стандартизированные команды, а **HAL** переводит их в низкоуровневые инструкции, понятные конкретному железу.

В результате отпадает нужда переписывать ядро под каждое новое устройство. Прослойка **HAL** берёт на себя всю рутину аппаратной совместимости, позволяя ядру оставаться полностью независимым от железа.

Конкретно HAL отвечает за следующие аппаратные подсистемы:

- **Контроллеры прерываний** (**APIC**, **PIC**) - управляют тем, как устройства сигнализируют процессору о необходимости внимания
- **Таймеры высокого разрешения** (**HPET**, **TSC**) - обеспечивают точный отсчёт времени для ядра и планировщика задач
- **Контроллеры прямого доступа к памяти** (**DMA**) - позволяют устройствам читать и писать в оперативную память напрямую, не загружая процессор
- **Управление питанием** (**ACPI**) - регулирует переходы в спящий режим, гибернацию и энергопотребление

### BIOS и UEFI: уровень ниже драйверов

**Драйверы**, **ядро** и **HAL** - это уже территория запущенной Windows. Но до того как она вообще начнёт загружаться, работает прошивка материнской платы - **BIOS** или **UEFI**. Это первый код, который выполняется после нажатия кнопки питания: он инициализирует железо и передаёт управление загрузчику операционной системы. И это тоже поверхность атаки.

**BIOS** - устаревший стандарт прошивки, появившийся ещё в 1970-х. Работает в **16-битном** режиме процессора, ищет загрузчик в первом секторе диска (**MBR**), не видит диски больше **2 ТБ** и не имеет никакой защиты от подмены загрузчика.

**UEFI** - современная замена **BIOS**. Работает в **32/64-битном** режиме, имеет собственные драйверы файловых систем, поддерживает диски любого размера через **GPT** и содержит механизм **Secure Boot**.

**Secure Boot** - механизм проверки подписи загрузчика перед передачей ему управления. База доверенных ключей хранится в **NVRAM** материнской платы. Если загрузчик не подписан доверенным ключом - **UEFI** отказывает в загрузке.

**Значение для безопасности:** **Secure Boot** блокирует буткиты - вредоносное ПО, встраивающееся в цепочку загрузки до старта ОС. Без **Secure Boot** буткит загружается раньше Windows и становится невидимым для антивируса и **EDR**.

**Атаки на Secure Boot:**

- **BlackLotus** - первый публично задокументированный **UEFI**-буткит для **Windows 11**, обходящий **Secure Boot** через **CVE-2022-21894** (уязвимость в загрузчике Windows, который был в базе доверенных ключей). Патч - обновление базы отозванных ключей (**DBX**)
- **Подмена ключей через физический доступ** - сброс **Secure Boot** в **UEFI Setup** и загрузка собственного ключа

Проверить статус **Secure Boot**:

Команда **PowerShell**: `Confirm-SecureBootUEFI`

До этого момента мы говорили об атаках на уровне ядра. Но существует целый класс атак, которые работают в **User Mode** и при этом могут давать атакующему выполнение кода в контексте привилегированных процессов - **DLL Hijacking**.

## DLL Hijacking

**DLL Hijacking** - атака, при которой вредоносная **DLL** загружается вместо легитимной. Работает в **User Mode**, но последствия могут быть серьёзными: выполнение кода в контексте атакуемого процесса, включая привилегированные приложения.

Чтобы понять как это эксплуатируется, нужно знать в каком порядке Windows ищет **DLL** при их загрузке. Когда приложение вызывает **LoadLibrary("example.dll")**, Windows перебирает папки в фиксированном порядке и загружает первый найденный файл с нужным именем:

1. Уже загруженные **DLL** (**KnownDLLs** в реестре)
2. Директория, из которой запущено приложение
3. Системная директория (**C:\Windows\System32**)
4. Директория Windows (**C:\Windows**)
5. Текущая рабочая директория (**CWD**)
6. Папки из переменной **%PATH%**

Этот порядок актуален при включённом **Safe DLL Search Mode** (включён по умолчанию) - **CWD** находится ниже системных папок. При отключении **CWD** поднимается на 2-е место, что значительно расширяет поверхность атаки.

Именно этот порядок и эксплуатируется в разных сценариях атаки.

### Сценарий 1: Hijacking через директорию приложения

Приложение ищет **version.dll** и не находит её рядом с собой - грузит системную. Но если атакующий может записать файл в директорию приложения:

**C:\Program Files\VulnApp** **VulnApp.exe** ← легитимное приложение **version.dll** ← подброшена атакующим (загрузится вместо системной)

> Например, многие установщики и приложения ищут **DLL** в текущей директории до системной.

### Сценарий 2: Hijacking через PATH

Если в **PATH** есть папки с правами записи для пользователя - атакующий кладёт **DLL** туда:

![](../../_images/efa2de086ce1.webp)

### Сценарий 3: Phantom DLL Hijacking

Приложение пытается загрузить **DLL**, которой **вообще не существует** в системе. Если атакующий создаст файл с таким именем в одной из папок поиска - он будет загружен.

### Сценарий 4: DLL Side-Loading

Легитимное подписанное приложение загружает **DLL** по относительному пути без проверки подписи. Атакующий подкладывает **DLL** рядом с исполняемым файлом.

![](../../_images/a2142e29a674.webp)

Этот приём широко используется в целевых атаках: копируют легитимный **.exe** вместе со своей **DLL** в новую директорию.

### Защита от DLL Hijacking

| Мера | Описание |
|---|---|
| CWD не в начале PATH | Safe DLL Search Mode включён по умолчанию - не отключать |
| Права на директории приложений | Пользователи не должны иметь права записи в C:\Program Files |
| WDAC / AppLocker | Разрешить загрузку только подписанных DLL из доверенных путей |
| Process Monitor | Обнаружение попыток загрузки DLL из нестандартных мест |
| Sysmon Event ID 7 | Логирование всех загрузок DLL с хэшами и путями |
