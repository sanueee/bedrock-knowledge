# WMI

> [!info] Путь в курсе
> Глава 3: Windows-системы и их безопасность / Часть 1: Host-Base Windows / Сетевой стек Windows и удалённое управление
>
> **Кейсы:** [3.06 NFS](../../cases/windows/3.06%20NFS.md), [3.07 Сетевой стек](../../cases/windows/3.07%20Сетевой%20стек.md)

**Windows Management Instrumentation (WMI)** - инфраструктура управления и получения данных о Windows. Microsoft определяет [**WMI**](https://learn.microsoft.com/en-us/windows/win32/WmiSdk/wmi-start-page) как инфраструктуру для **management data and operations** в Windows. Подробнее - в [**About WMI**](https://learn.microsoft.com/en-us/windows/win32/wmisdk/about-wmi).

> **WMI** - это централизованная диспетчерская, в которой про каждый компьютер в сети известно всё: какие процессы запущены, какие учётные записи активны, какие диски подключены, какие службы работают. Любой клиент с правами может задать диспетчерской вопрос и получить ответ, не подходя к самому компьютеру. Те же ответы можно запрашивать в виде команд - "запусти X", "останови Y".

**WMI** использует модель **CIM** - **Common Information Model**. Через **WMI** можно работать с классами вроде:

- **Win32_Process**
- **Win32_Service**
- **Win32_OperatingSystem**
- **Win32_NetworkAdapterConfiguration**
- **Win32_LoggedOnUser**
- **Win32_StartupCommand**

Теоретически **WMI** удобно объяснять как три слоя:

- **WMI consumers** - клиенты: скрипты, **PowerShell**, **MMC**, **EDR**, админские инструменты
- **WMI service** / **repository** - посредник и хранилище метаданных
- **WMI providers** - компоненты, которые получают реальные данные от **ОС**, драйверов, служб, приложений

Основные возможности **WMI**:

- инвентаризация системы
- просмотр процессов и служб
- запуск процессов
- чтение событий
- управление настройками
- подписки на события

## Управление WMI через PowerShell

| Команда | Для чего |
|---|---|
| Базовый опрос системной информации | Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, LastBootUpTime |
| Опрос параметров компьютера | Get-CimInstance Win32_ComputerSystem | Select-Object Name, Domain, Manufacturer, TotalPhysicalMemory |
| Проверка WMI -фильтров событий (опасный вектор закрепления) | Get-WMIObject -Namespace root\subscription -Class __EventFilter |
| Проверка потребителей событий | Get-WMIObject -Namespace root\subscription -Class __EventConsumer |
| Проверка привязок фильтра к потребителю | Get-WMIObject -Namespace root\subscription -Class __FilterToConsumerBinding |
| Проверка прав namespace WMI для удалённого подключения | Get-WmiObject -Namespace root -Class __SystemSecurity | Invoke-WmiMethod -Name GetSecurityDescriptor |

## Атаки на WMI

**WMI Remote Execution** (MITRE ATT&CK: [**T1047**](https://attack.mitre.org/techniques/T1047/))

Удалённый запуск процесса на целевой машине через вызов метода **Win32_Process.Create()**. С точки зрения транспорта вызов идёт либо через **DCOM** (классический сценарий), либо через **WinRM/CIM** (современный). Преимущество для атакующего - запущенный процесс становится дочерним по отношению к **wmiprvse.exe**, что часто не вызывает алертов **EDR**, если правила не настроены на эту цепочку родителей.

**WMI Persistence** (MITRE ATT&CK: [**T1546.003**](https://attack.mitre.org/techniques/T1546/003/))

Создание постоянных **WMI Event Subscriptions** для скрытого автозапуска кода. Это один из самых популярных механизмов закрепления (persistence) в продвинутых атаках, потому что не оставляет следов в обычных местах (реестр **Run**, папка автозагрузки, службы) - его не видит ни **Autoruns** в дефолтной конфигурации, ни большинство сканеров.

Механизм атаки:

1. **EventFilter**: Атакующий регистрирует **WMI**-фильтр, который срабатывает на определённое событие системы (старт службы, вход пользователя, изменение нагрузки).
2. **EventConsumer**: Создаёт потребителя событий типа **CommandLineEventConsumer** или **ActiveScriptEventConsumer** с путём к своему коду.
3. **FilterToConsumerBinding**: Связывает фильтр и потребителя - теперь при наступлении события **WMI**-движок сам запустит указанный код.
4. **Триггер**: При первом же совпадении условия фильтра код выполняется в контексте **SYSTEM**.

Условие успеха - права администратора на этапе создания подписки. После создания подписка работает автономно и переживает перезагрузки.

**WMI Reconnaissance** (MITRE ATT&CK: [**T1047**](https://attack.mitre.org/techniques/T1047/))

Использование **WMI** для разведки целевой системы без загрузки сторонних инструментов. Все необходимые данные - список процессов, служб, локальных пользователей, установленных антивирусов, версии **ОС**, доменная принадлежность - доступны через стандартные **WMI**-классы и возвращаются обычными **CIM**-запросами. Запросы выглядят как легитимная активность администратора, и без специально настроенного аудита **WMI**-Activity (**Event ID 5857**, **5858**) обнаружить такое сканирование крайне сложно.

## Какие механизмы защиты работают на WMI

- **Регулярная инспекция WMI-подписок** через **PowerShell**-команды выше или утилиту **Autoruns** (**Sysinternals**, вкладка **WMI**) - единственный надёжный способ найти **WMI Persistence**
- **Ограничение прав на удалённый WMI** через консоль **wmimgmt.msc** - доступ только сервисным учётным записям мониторинга
- **WinRM вместо DCOM** для удалённого администрирования - лучше аудитится, проще ограничивается через **JEA**
- **Аудит WMI-Activity** через **Event ID 5857**, **5858**, **5859** - детектирование вызовов методов и создания подписок
- **Sysmon Event ID 19, 20, 21** - специализированные события для **WMI Persistence**, фиксируют создание **EventFilter**, **EventConsumer** и **FilterToConsumerBinding**
- **Отключение службы WMI** на хостах, где она не требуется (редкий случай, обычно невозможно из-за зависимостей)
- **EDR с правилами на дочерние процессы wmiprvse.exe** - детектирование **Remote Execution**

**SMB**, **RPC**, **WinRM**, **WMI** - всё это про неинтерактивное удалённое управление. Когда нужен интерактивный графический сеанс на удалённой машине, в дело вступает **RDP**
