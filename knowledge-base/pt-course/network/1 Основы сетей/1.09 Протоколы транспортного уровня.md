## Транспортный протокол TCP

> **Transmission Control Protocol (TCP)** - **транспортный протокол**, обеспечивающий надёжную передачу данных между устройствами.

Для того чтобы управлять TCP-соединением, протокол использует следующие флаги:

| Флаг | Роль |
|---|---|
| SYN | Синхронизация - первый флаг между двумя хостами, используется для установки соединения |
| ACK | Подтверждение полученного пакета |
| RST | Сброс - запрашивает разрыв соединения |
| FIN | Сообщает другой стороне, что все пакеты были отправлены |
| PSH | Используется, если необходимо немедленно передать данные из буфера |
| URG | Указатель важности: 0 - не используется, 1 - используется |

Теперь разберемся, как применяются эти флаги в процессе общения двух устройств. Разделим общение на **3** этапа: процесс инициализации сессии, обмен данными, завершение сессии. Чтобы установить соединение между двумя устройствами, они три раза обмениваются определенными сообщениями:

1. Клиент отправляет **SYN**
2. Сервер отвечает **SYN-ACK**
3. Клиент подтверждает соединение с помощью флага **ACK**

Такой процесс называется **трехсторонним рукопожатием**.

![](../../_images/cbba854e2eaf.webp)

Рассмотрим, как трехстороннее рукопожатие выглядит в трафике. Для этого воспользуемся фильтром, который покажет только пакеты, содержащие флаги SYN, SYN/ACK, ACK в рамках одной сессии (в нашем случае нулевой) - `tcp.stream == 0 && (tcp.flags == 0x002 || tcp.flags == 0x012 || tcp.flags == 0x010)`

![](../../_images/b9edec893e16.webp)

Мы видим, что соединение устанавливается между узлами **131.151.32.21** и **131.151.37.122**. Далее мы будем смотреть именно их взаимодействие. После установки соединения устройства могут передавать данные друг другу. Процесс передачи данных представлен следующей последовательностью:

1. Клиент отправляет данные с флагами **PSH** и **ACK**, указывая, что данные следует обработать немедленно
2. Сервер отвечает **ACK**
3. Сервер обрабатывает запрос и отправляет клиенту данные
4. Клиент подтверждает, что данные получены пакетом с флагом **ACK**

![](../../_images/93cfe903ead9.webp)

Теперь посмотрим, как узлы **131.151.32.21** и **131.151.37.122** обмениваются данными в трафике. Для этого изменим предыдущий фильтр так, чтобы показывать в нулевом потоке только пакеты PSH/ACK - `tcp.stream == 0 && tcp.flags == 0x018`

![](../../_images/0e7d881ea635.webp)

Можем увидеть, что узлы обмениваются данными почты (на что нам указывает **Microsoft Exchange** и **143** порт). Когда обмен данными будет закончен и необходимость поддерживать сессию отсутствует, начинается процесс завершения сессии. Этот процесс выглядит так:

1. Клиент запрашивает завершение сеанса, отправляя другой стороне пакет с флагами **FIN/ACK**
2. Сервер возвращает флаг **ACK** для подтверждения запроса
3. Сервер отправляет пакет с флагом **FIN/ACK**
4. Клиент подтверждает получение **FIN/ACK** от сервера и отправляет **ACK**

Не будем искать точное время, когда узлы закончили общаться. Сразу перейдём к просмотру процесса завершения сессии. Для этого найдём пакеты FIN/ACK и ACK - `tcp.stream == 0 && (tcp.flags.fin == 1 || tcp.flags == 0x010)`

![](../../_images/7191a9244b3d.webp)

Также нам необходимо отсортировать трафик по убыванию по столбцу **Start time**, так как именно самыми последними пакетами будут завершающие сессию. На этом участке трафика мы можем увидеть, что именно адрес **131.151.32.21** инициировал завершение соединения.

## Протокол UDP

> **User Datagram Protocol (UDP)** - протокол пользовательских датаграмм, который, в отличие от **протокола TCP**, не устанавливает стабильное соединение между устройствами. Данный протокол работает быстрее **TCP**, но из-за этого не гарантирует доставку данных и не контролирует порядок доставки пакетов.

Из-за высокой скорости и отсутствия этапа установки соединения UDP используется там, где важна минимальная задержка и допустима потеря части данных (к примеру, в онлайн-играх, видеостриминге и голосовой связи). Рассмотрим использование протокола UDP на примере DNS-трафика. Воспользуемся фильтром `udp.port == 53`.

![](../../_images/77a79320e740.webp)

Изучив поля протоколов UDP и DNS, можем увидеть, что в данном случае протокол UDP отвечает за быструю отправку лёгких пакетов стандартных запросов, без установки надежного соединения.

В виде таблицы подведём некоторый итог по двум протоколам транспортного уровня:

| TCP | UDP |
|---|---|
| Ориентирован на соединение | Без установки соединения |
| Подходит для приложений, требующих высокой надежности, где время передачи менее критично | Подходит для приложений, которым требуется быстрая и эффективная передача |
| Упорядоченные пакеты данных в указанном порядке | Пакеты могут приходить не по порядку; UDP их не упорядочивает |
| Размер заголовка составляет 20 байт | Размер заголовка составляет 8 байт |
| Гарантирует передачу пакетов | Нет гарантии передачи пакетов |
