# Протоколы межсетевого уровня

## IP

**Internet Protocol (IP)** – протокол сетевого уровня модели OSI, обеспечивающий адресацию и маршрутизацию пакетов между сетями. На передачу IP-пакетов влияет значение **MTU** сетевого интерфейса.

> **MTU (Maximum Transmission Unit)** – максимальный размер IP-пакета, который может быть передан через сетевой интерфейс без фрагментации. Для Ethernet обычно используется значение 1500 байт.

Если размер IPv4-пакета превышает MTU исходящего интерфейса, маршрутизатор может разделить его на несколько фрагментов. Однако в заголовке IPv4 может быть установлен флаг **DF (Don't Fragment)**, запрещающий фрагментацию. В таком случае маршрутизатор отбросит пакет и, как правило, отправит источнику ICMP-сообщение о необходимости фрагментации.

Предположим, что MTU исходящего интерфейса маршрутизатора равен 1500 байт. Чтобы найти IPv4-пакеты большего размера с установленным флагом DF, используем фильтр: `ip.flags.df == 1 && ip.len > 1500`

Такие пакеты не смогут пройти через этот интерфейс без уменьшения своего размера.

![](../../_images/d8a898e90546.webp)

Мы видим, что данный пакет имеет размер **7292 байта**. При поставленных нами условиях маршрутизатор отбросит этот пакет.

## ICMP

> **ICMP (Internet Control Message Protocol)** - это протокол **третьего уровня модели OSI**, который используется для диагностики проблем со связностью в сети. Говоря простым языком, **ICMP** используется для диагностики сети и позволяет определить, может ли пакет достичь узла назначения.

Рассмотрим на примере сетевого трафика, как выглядят протоколы ICMP версий 4 и 6, выставив фильтр **icmp || icmpv6**

![](../../_images/7fb526521d42.webp)

### Наиболее распространённые сообщения ICMPv4

Поле **Type** определяет назначение ICMP-сообщения, а поле **Code** уточняет причину его отправки.

| Type | Code | Сообщение | Назначение |
|---|---|---|---|
| 0 | 0 | Echo Reply | Ответ на эхо-запрос, например при выполнении ping |
| 3 | 0 | Network Unreachable | Сеть назначения недоступна |
| 3 | 1 | Host Unreachable | Узел назначения недоступен |
| 3 | 2 | Protocol Unreachable | Указанный протокол не поддерживается узлом |
| 3 | 3 | Port Unreachable | Порт назначения недоступен; часто встречается при работе с UDP |
| 3 | 4 | Fragmentation Needed and DF Set | Пакет превышает MTU, но его фрагментация запрещена |
| 3 | 13 | Communication Administratively Prohibited | Передача запрещена политикой безопасности, например межсетевым экраном |
| 5 | 1 | Redirect for Host | Маршрутизатор сообщает узлу более подходящий маршрут |
| 8 | 0 | Echo Request | Эхо-запрос, например отправленный утилитой ping |
| 11 | 0 | TTL Expired in Transit | Значение TTL закончилось при передаче; используется в работе traceroute |
| 11 | 1 | Fragment Reassembly Time Exceeded | Истекло время ожидания сборки фрагментов пакета |
| 12 | 0 | Parameter Problem | В заголовке IP-пакета обнаружена ошибка |

Ранее мы искали IPv4-пакеты, которые не смогут пройти через интерфейс с заданным MTU. Теперь найдём ICMP-сообщения, созданные маршрутизатором после отбрасывания таких пакетов. Для этого используем фильтр: `icmp.type == 3 && icmp.code == 4`

**Type 3** означает, что узел назначения недоступен, а **Code 4** уточняет причину: размер исходного пакета превысил MTU исходящего интерфейса, но установленный флаг **DF** запретил его фрагментацию.

![](../../_images/45cfe9598d7a.webp)

Разберем параметры этого пакета, чтобы понять, что произошло. Мы видим, что отправленный ICMP-пакет с **84.139.65.249** на **192.168.1.111** был отброшен с ошибкой **Destination unreachable**. Спускаемся ниже по телу протокола и видим, что к нашей ошибке есть пояснение (значение **Fragmentation needed**, а также MTU равняется 1492 байтам). Если взглянуть на флаг и размер тела IP-протокола, то становится ясно, что пакет не дошел до места назначения, так как его размер - **1500** байт и он не должен фрагментироваться, а MTU требует размера не более **1492** байт.

## IGMP

> **IGMP** (Internet Group Management Protocol) - протокол управления групповой передачей данных в сетях, основанных на **протоколе IP**.

IGMP используется маршрутизаторами и IP-узлами для организации сетевых устройств в группы. Этот протокол является частью спецификации групповой передачи пакетов в IP-сетях. Рассмотрим на практике, как выглядит трафик протокола IGMP с помощью фильтра `igmp`.

![](../../_images/45f4132bc365.webp)

В трафике есть следующие типы сообщений протокола:

1. **Membership Query, general** - запрос от маршрутизатора, который проверяет, есть ли в сети устройства, состоящие в multicast-группах
2. **Membership Report** - ответ от устройства, которое сообщает, что оно состоит в определенной multicast-группе.
3. **Membership Report / Join group 224.0.0.251 for any sources** - устройство сообщает, что хочет вступить в multicast-группу **224.0.0.251**

Разберем важные поля из тела запроса (**Membership Query, general**), отправленного от маршрутизатора **192.168.2.1**. Для этого выберем его и откроем тело протокола

![](../../_images/4216c4d94ded.webp)

В теле выделим такие поля, как **Type**, **Multicast Address**, **Max Resp Time** и **Checksum**. Именно они позволяют определить тип сообщения (**Membership Query**), multicast-группу (**0.0.0.0**), время ожидания ответа в секундах (**1**) и корректность переданных данных (**Checksum Status: Good**). Содержимое этого пакета говорит о том, что устройство с IP-адресом **192.168.2.1** отправляет общий запрос на адрес **224.0.0.1**, а значение Multicast Address (**0.0.0.0**) означает, что запрос относится ко всем multicast-группам, а не к одной конкретной группе.

## RIP

> **RIP (Routing Information Protocol)** - один из самых простых протоколов динамической маршрутизации, который применяется в небольших компьютерных сетях.

**RIP** позволяет маршрутизаторам обмениваться маршрутной информацией с соседними устройствами и автоматически обновлять таблицы маршрутизации. В качестве метрики RIP использует количество хопов (один прыжок пакета от одного устройства к другому): чем меньше хопов до сети, тем предпочтительнее маршрут. Для уменьшения лишнего трафика и предотвращения маршрутных петель в RIP применяются механизмы **Split Horizon** и **Poison Reverse**. В результате обмена маршрутной информацией маршрутизаторы постепенно приходят к **состоянию сходимости**, при котором все устройства имеют актуальные данные о доступных маршрутах.

> **Split Horizon** - метод, который экономит трафик и память, за счет того, что не отправляет данные о своих маршрутах тем узлам, с которых он получил эту информацию, так как данный узел уже обладает этой информацией.

> **Poison Reverse** - метод, при котором при обмене таблицами маршрутизации полученная запись помечается метрикой **16** (то есть как недоступная, так как у **RIP** максимальный допустимый маршрут составляет **15** хопов), и исключается из дальнейшей рассылки.

Рассмотрим, какими сообщениями общается протокол RIP в трафике. Выставим фильтр **rip**.

![](../../_images/251ee358f2d0.webp)

Мы видим, что присутствуют два типа сообщений:

1. **Request** - используется для запроса таблицы маршрутизации у соседних маршрутизаторов
2. **Response** - передает информацию о доступных маршрутах и их метриках

В ответах RIP метрика может быть равна **16**, что означает недостижимость маршрута, но такая метрика может быть и в запросе. В этом случае значение у такой метрики другое. Рассмотрим на примере такого запроса в трафике, выставив фильтр` rip.metric >= 16 && rip.command == 1`.

![](../../_images/e5dd2af2ebd4.webp)

В данном случае мы можем увидеть совокупность таких факторов: не указан следующий узел (**0.0.0.0**), не указана маска (**0.0.0.0**), не указана сеть (**Unspecified**), метрика равна **16**. Такой набор свидетельствует о том, что маршрутизатор отправляет на multicast-адрес запрос на отправку полной таблицы маршрутизации, а не о недостижимости какого-то маршрута.

## OSPF

> **OSPF (Open Shortest Path First)** - протокол **динамической маршрутизации**, который позволяет маршрутизаторам обмениваться информацией о топологии сети и автоматически рассчитывать маршруты до доступных сетей.

Для идентификации каждого маршрутизатора используется** Router ID** - 32-битное значение, записанное в формате IPv4-адреса. Полученная информация о топологии хранится в базе данных **LSDB (Link State Database)**, которая содержит сведения о маршрутизаторах, сетях, связях между ними и их метриках. На основе этой базы каждый маршрутизатор самостоятельно запускает **алгоритм Дейкстры**, рассчитывает кратчайшие пути и добавляет полученные маршруты в таблицу маршрутизации.

В отличие от** RIP**, **OSPF **выбирает маршрут не только по количеству промежуточных узлов. Каждому каналу назначается собственный вес, который в OSPF называется **стоимостью**. Разные каналы могут иметь разные значения стоимости в зависимости от их пропускной способности или настроек администратора. Стоимость можно задать вручную, однако в некоторых реализациях она рассчитывается по формуле: **Стоимость интерфейса = опорная пропускная способность / пропускная способность интерфейса**. **Опорная пропускная способность** - условное значение, с которым сравнивается скорость интерфейса, часто по умолчанию равное **100 Мбит/с**. Например, канал со скоростью **10 Мбит/с** получит стоимость **10**, а канал со скоростью **100 Мбит/с** - стоимость **1**. Стоимость всего маршрута складывается из **весов всех входящих в него каналов**, поэтому чем меньше итоговое значение, тем предпочтительнее маршрут.

![](../../_images/826a8c1dd3e0.webp)

Рассмотрим как **OSPF **выбирает кратчайший маршрут, опираясь на веса, а не количество хопов. На рисунке выше при использовании **RIP **трафик между **R1 **и **R2 **прошел бы напрямую, так как такой маршрут содержит меньше хопов. Однако прямой канал **R1-R2** имеет меньшую пропускную способность и, следовательно, больший вес. Путь через **R3 **состоит из двух более быстрых каналов, стоимость каждого из которых равна **1**, поэтому их суммарная стоимость составит **2**. Если стоимость прямого канала равна **10**, **OSPF **выберет маршрут **R1-R3-R2**, несмотря на наличие дополнительного промежуточного маршрутизатора.

Для **оптимизации **работы крупную **OSPF-сеть** можно разделить на **зоны**. Каждая зона имеет собственную **LSDB**, благодаря чему маршрутизаторам не требуется хранить подробную информацию обо всей автономной системе и выполнять перерасчет маршрутов для всех существующих узлов. Главной зоной является **магистральная **зона **Area 0**, которая обеспечивает передачу маршрутной информации между остальными зонами через пограничные маршрутизаторы **ABR (Area Border Router)**, которые используются для соиденения зон, будучи подключенными сразу к нескольким зонам и храня отдельную **LSDB **для каждой из них. Неправильное разделение сети на зоны может привести к использованию более длинного маршрута. Например, даже если Area 1 физически связана с Area 2, межзонный маршрут должен проходить через магистральную зону: `Area 1 → Area 0 → Area 2`

В общем** Ethernet-сегменте** с несколькими **OSPF-маршрутизаторами** выбираются **DR (Designated Router)** и **BDR (Backup Designated Router)**. Эти роли нужны для того, чтобы маршрутизаторам не приходилось устанавливать полный обмен маршрутной информацией с каждым устройством в сегменте. Остальные маршрутизаторы передают обновления DR и BDR, а DR распространяет их между всеми участниками сети, что уменьшает количество соединений и объем служебного трафика. BDR является **резервным **маршрутизатором и принимает роль DR, если тот становится недоступен. При этом DR не является главным маршрутизатором всей OSPF-сети: его роль действует только внутри конкретного сегмента, а каждый маршрутизатор продолжает хранить собственную **LSDB **и самостоятельно рассчитывать маршруты.

Посмотрим, каким образом общаются устройства внутри трафика протокола OSPF. Укажем фильтр `ospf`.

![](../../_images/515ae685c327.webp)

Мы видим 5 типов сообщений. Разберем, за что отвечает каждый из них:

1. **Hello** - используется для обнаружения соседних OSPF-маршрутизаторов и поддержания соседства между ними
2. **Database Description** - используется для краткого сравнения баз данных OSPF между соседними маршрутизаторами
3. **Link State Request** - используется для запроса недостающей или более новой информации о состоянии каналов
4. **Link State Update** - используется для передачи обновлений о состоянии каналов, маршрутах и изменениях в топологии
5. **Link State Acknowledgment** - используется для подтверждения получения обновлений OSPF

Теперь взглянем поближе на пакеты, отвечающие за передачу обновлений, используя фильтр `ospf.msg == 4`.

![](../../_images/e8aeb7eb655c.webp)

Что можно увидеть внутри тела протокола? Маршрутизатор **10.200.200.102** отправляет обновление в главную магистраль **0.0.0.0**, где сообщает свои новые 3 связи и их метрики. В связях он сообщает о том, есть ли в сети другие маршрутизаторы, тогда она будет **транзитной**, какой адрес у DR-роутера и него самого в этой сети, а также числовую метрику.
