## DHCP

> **Dynamic Host Configuration Protocol (DHCP)** - прикладной протокол, позволяющий устройствам автоматически получать **IP-адрес** и другие **сетевые параметры**.

![](../../_images/6de9e3f84da0.webp)

Процесс получения IP-адреса по DHCP называется **DORA** - это аббревиатура, описывающая четыре этапа взаимодействия клиента и сервера:

1. **Discover** - клиент отправляет широковещательный запрос в сеть, пытаясь найти DHCP-сервер
2. **Offer** - сервер отвечает и предлагает доступный IP-адрес
3. **Request** - клиент выбирает предложение и отправляет запрос на использование этого IP
4. **Acknowledge** - сервер подтверждает выдачу адреса и передаёт дополнительные параметры (например, шлюз и DNS)

![](../../_images/4965df71b61e.webp)

Рассмотрим на примере процесс выдачи IP-адреса. Для этого выставим фильтр **dhcp**.

![](../../_images/26eef9af6c60.webp)

На этом участке трафика мы видим процесс **DORA**. Посмотрев содержимое последнего подтверждающего пакета, можем увидеть, что клиенту был выдан адрес **192.168.0.10/24** на один час DHCP сервером **192.168.0.1**.

## DNS

> **Domain Name System (DNS)** - компьютерная распределенная система для получения информации о доменах (если коротко, то **система доменных имен**). Чаще всего используется для получения IP-адреса по имени хоста.

![](../../_images/e30a4bbf3675.webp)

Когда клиенту необходимо определить **IP-адрес** доменного имени, он отправляет запрос **рекурсивному **DNS-серверу, например DNS-серверу провайдера. Если нужной записи нет в кэше, сервер последовательно обращается к **корневому **DNS-серверу, серверу **домена верхнего уровня TLD** и **авторитетному **DNS-серверу **домена второго уровня SLD**. После получения ответа результат передается клиенту и временно сохраняется в кэше.

Спрашивая информацию у DNS-сервера, клиент может использовать такие виды запросов, как:

1. **Forward lookup** - прямой просмотр DNS обозначает, какой IP-адрес ассоциирован с запрашиваемым доменным именем
2. **Reverse lookup** - обратный просмотр DNS говорит, какое доменное имя ассоциировано с запрашиваемым IP

Дальше сервер будет искать информацию для ответа в определенных логических областях, которые называют зонами DNS, и бывают следующих типов:

1. **Primary DNS** - зона, где хранятся **все** записи домена
2. **Secondary DNS** - второстепенная зона DNS, служащая для резервирования основной зоны, записи там доступны **только для чтения**
3. **Stub DNS zone - зона-заглушка**. Информация в этой зоне позволяет вашему DNS напрямую связываться с DNS-сервером

**DNS **имеет иерархическую структуру, в которой доменное имя читается **справа налево**. Например, в адресе **www.123.ru** значение **.ru** является **TLD (Top-Level Domain)** - доменом верхнего уровня, **123** является **SLD (Second-Level Domain)** - доменом второго уровня, зарегистрированным внутри зоны **.ru**, а **www** обозначает конкретный узел или поддомен внутри **123.ru**. **Корневые **DNS-серверы хранят информацию о серверах доменов верхнего уровня и направляют запрос к DNS-серверам зоны **.ru**. **TLD **DNS-серверы, в свою очередь, сообщают адреса авторитетных DNS-серверов домена **123.ru**, на которых уже находятся записи его узлов, включая **www.123.ru**. После того как информация найдена, в ответ на запрос клиента сервер может вернуть одну из следующих записей, в зависимости от того, что спрашивал клиент:

1. **SOA (Start of Authority)** - начальная запись для зоны DNS, указывающая, на каком сервере хранится эталонная информация о домене и содержащая информацию лица, ответственного за данную зону, и время жизни записей DNS
2. **A/AAAA** - запись адреса. Связывает имя хоста с адресом протокола IPv4/IPv6
3. **NS (Name Server)** - указывает на DNS-сервер домена
4. **MX (Mail Exchange)** - почтовый обменник, указывающий на сервер (или несколько серверов) обмена почтой для данного домена
5. **TXT (Text)** - текстовая запись, используемая для хранения служебной информации о домене (к примеру, для подтверждения владения доменом)
6. **SRV (Server Selection)** - указывает на сервера для сервисов, например Active Directory
7. **PTR (Pointer)** - обратная DNS-запись. Она связывает IP-адрес с его каноническим именем

Чтобы посмотреть на практике, как выглядит DNS-трафик и какие DNS-серверы отправляют различные записи, воспользуемся фильтром `dns`.

![](../../_images/262d1afbb22e.webp)

Можно увидеть IP-адреса DNS-серверов и краткую информацию о том, что они отправляют. Однако если нам необходимо найти какой-то определенный тип записей, например **MX**, чтобы проанализировать, какие адреса отвечают за обработку почтовых писем в домене, нужно использовать фильтр **dns.mx.mail_exchange**

![](../../_images/d1a2f912c299.webp)

Мы можем увидеть, что DNS-сервер сообщил клиенту следующие почтовые серверы:

1. **preference 10, mx cluster5.us.messagelabs.com** - основной почтовый сервер с более высоким приоритетом
2. **preference 20, mx cluster5a.us.messagelabs.com** - резервный почтовый сервер с меньшим приоритетом

## Telnet и SSH

> **Telnet** - сетевой протокол для терминального управления удаленными устройствами и серверами. Для установки соединения использует порт **23**.

Данный протокол является плохим выбором для систем с точки зрения безопасности, так как он не шифрует данные, которые передаются по установленному каналу, а также не имеет системы аутентификации, что в совокупности подвергает передаваемые данные опасности. Чтобы убедиться в этом воспользуемся фильтром `telnet.data`.

![](../../_images/61b746e15cd8.webp)

На выделенном участке трафика в пакете под номером **22025** клиент получает форму заполнения пароля, а в следующем пакете, открыв тело протокола, мы можем увидеть переданный пароль в открытом виде (**L35jFNz0Z4Ao8X**). Такой подход к передаче данных крайне небезопасен.

> **Secure Shell (SSH)** - протокол для безопасного удаленного управления устройствами и передачи данных.

Через SSH можно выполнять операции в командной строке узла, который физически находится в другом месте. Протокол работает на 22-м порту по умолчанию. В отличие от Telnet, при обмене данными устройства устанавливают пару симметричных ключей, которыми в дальнейшем будут шифровать трафик, а чтобы эти ключи не были перехвачены, на этапе передачи используется асимметричное шифрование.

![](../../_images/af17920c0778.webp)

Сравним данные, передаваемые внутри SSH, с данными, которые передавались в открытом виде по протоколу Telnet. Для этого найдем пакеты, которые используют 22 порт и имеют длину больше 0 с помощью фильтра **tcp.port == 22 && tcp.len > 0**.

![](../../_images/797e9c2f703b.webp)

Можем увидеть, что теперь данные зашифрованы.

## HTTP и HTTPS

> **HTTP** - прикладной протокол передачи данных, изначально предназначенный для передачи веб-страниц, но сегодня используется для передачи любых данных. По умолчанию использует **80-й порт**.

Для взаимодействия устройств по этому протоколу были придуманы разные методы запросов, которыми может пользоваться клиент, чтобы получить требуемую информацию. Рассмотрим **два** основных метода:

1. **GET** - предназначен для получения ресурса с указанным URL. Получив запрос GET, сервер должен прочитать указанный ресурс и включить его код в состав ответа клиенту.
2. **POST** - передача данных на сервер. Однако, подобно методу GET, он может применяться по-разному и нередко используется для получения информации с сервера. URL, заданный в строке состояния, указывает на конкретный ресурс.

> **С полным списком методов мы познакомимся позже в другом разделе**.

После того как клиент отправил запрос некоторым методом, сервер должен ему сообщить об успешности или провале его действий. Для этого используются определенные типы ответов, которые называются **кодами состояний**. Рассмотрим **три** основных группы кодов состояний:

1. **2xx** - запрос клиента был успешно принят и обработан
2. **4xx** - запрос сформирован некорректно или не может быть выполнен по вине клиента. Ошибка может быть устранена на стороне клиента
3. **5xx** - сервер не смог выполнить корректно сформированный запрос по причинам, связанным с его внутренним состоянием или конфигурацией

> **С полным списком кодов состояний мы познакомимся позже в другом разделе**.

Теперь перейдём к изучению структуры стандартного GET-запроса в трафике. Для этого выставим фильтр `http.request.method == "GET"`

![](../../_images/b2ae7f12a378.webp)

Можем увидеть GET-запрос, в котором клиент **192.168.110.10** запрашивает главную страницу сайта **ip.webernetz.net**, используя метод **GET** и протокол **HTTP/1.1**, а также передает серверу информацию о браузере **Mozilla Firefox 26.0**, поддерживаемых типах контента, языках, методах сжатия и параметрах соединения **keep-alive**.

Сам протокол HTTP считается небезопасным, так как в нем отсутствует шифрование, а значит, если пользователь введет аутентификационные данные в форме регистрации, то в трафике сети злоумышленник сможет их обнаружить в открытом виде, а затем воспользоваться в своих целях. Именно из-за этого сейчас в основном используется протокол **HTTPS**. Это расширение протокола HTTP для поддержки шифрования в целях повышения безопасности. Данные передаются поверх криптографических протоколов TLS или SSL. Порт по умолчанию - 443.

В настоящее время в качестве криптографического протокола для HTTPS применяется именно **TLS (Transport Layer Security)**, так как его устаревшая версия **SSL (Secure Sockets Layer)** содержала критические уязвимости и была заменена. Чтобы защитить данные, TLS применяет следующие методы:

1. шифрование данных
2. проверка подлинности сервера
3. контроль целостности передаваемой информации

Важно отметить, что TLS использует гибкую систему шифрования, которая совмещает в себе асимметричное шифрование для обмена ключами и проверки подлинности, а также симметричное для защиты данных. Установка ключей и согласование параметров шифрования происходит в процессе **TLS-handshake**, который содержит следующие шаги:

1. клиент и сервер договариваются о способе шифрования
2. сервер отправляет свой сертификат
3. клиент проверяет его подлинность
4. устанавливаются ключи для шифрования

Только после выполнения данного процесса весь трафик между клиентом и сервером передается в зашифрованном виде. Теперь рассмотрим на практике, как выглядит такой зашифрованный трафик. В данном случае обычный фильтр `http` уже не поможет, потому что содержимое передается в зашифрованном виде. Нам понадобится фильтр `tls`.

![](../../_images/b2977b86ad1c.webp)

Используя такой фильтр, большинство пакетов будут иметь тип **Application Data**. Рассматривать их содержимое не имеет смысла, так как все передаваемые данные внутри зашифрованы. Однако мы можем посмотреть фрагменты трафика, где происходит то самое трехстороннее рукопожатие, с помощью фильтра `tls.handshake`.

![](../../_images/0338eae85c1a.webp)

В результате мы можем отслеживать состояние сессий, моменты установок ключей и проверок сертификатов, а также искать пакеты **Client Hello**, чтобы смотреть, кто инициировал подключение. Такой подход будет работать для HTTP/1 и HTTP/2, но не поможет при работе с **HTTP/3**.

> **HTTP/3** - современная версия **HTTP**, которая работает поверх транспортного протокола **QUIC** (который заменяет связку **TCP** и **TLS**, работает поверх **UDP**, обеспечивает встроенное шифрование и быстрое установление соединения).

Используя фильтр `quic`, мы будем видеть следующее:

![](../../_images/bc2b465da6f3.webp)

Мы можем видеть только служебные пакеты инициализации, то есть пакеты, которые содержат параметры, отвечающие за процесс установления соединения в **TLS-handshake** и данные в зашифрованном виде.

## FTP

> **File Transfer Protocol (FTP)** - классический протокол передачи файлов. Он работает поверх **TCP** и использует отдельный канал для команд и отдельный канал для передачи данных.

Главная проблема обычного FTP в том, что команды и учётные записи передаются в открытом виде. Рассмотрим на примере трафика, как можно воспользоваться передачей данных в открытом виде внутри протокола FTP. Для начала отфильтруем все пакеты только те, которые содержат поле имени пользователя - `ftp.request.command == "USER"`.

![](../../_images/8fddca4d7c22.webp)

Мы видим несколько запросов на подключение, выбираем первый попавшийся запрос, где имя пользователя не **anonymous**, в нашем случае это **ftp1119456-nureintest** (видим это в колонке **Info**), а затем открываем тела протоколов TCP и FTP:

1. В теле протокола TCP мы можем увидеть индекс потока (**280**)
2. В теле FTP мы видим имя пользователя (**ftp1119456-nureintest**)

Теперь выставим фильтр, который покажет все пакеты, содержащие поле пароля для учётной записи с логином ftp1119456-nureintest - `tcp.stream == 280 && ftp.request.command == "PASS"`.

![](../../_images/829281cdda96.webp)

Теперь, открыв тело протокола FTP, мы можем увидеть пароль, который вводил пользователь с именем **ftp1119456-nureintest** при авторизации - **98fDMjEHP6kV0D62WhK1**.

## NTP

> **Network Time Protocol (NTP)** - протокол прикладного уровня, предназначенный для синхронизации между устройствами в сети и работающий на **123-м UDP порту**.

Правильная работа данного протокола критична для работы сетевых сервисов и различных систем безопасности. Без корректного времени не будет ясной картины логов в сети, а некоторые протоколы аутентификации и шифрования будут работать неправильно. Для определения времени протокол использует иерархическую систему уровней (**stratum**):

1. **Stratum 0** - атомные часы, GPS
2. **Stratum 1** - сервера, подключённые к Stratum 0
3. **Stratum 2+** - обычные серверы и клиенты

Чем меньше номер такого уровня (**stratum**), тем точнее время. Теперь выставим фильтр `ntp.stratum`, который покажет, какой источник точного времени использует тот или иной узел.

![](../../_images/e4b8a22c257c.webp)

В данном пакете мы можем увидеть, что NTP-сервер **192.53.103.108** использует **Stratum 1**, а значит получает время от атомных часов или GPS. **Root Delay** отвечает за задержку времени от эталонного источника, а **Root Dispersion** - за то, какая погрешность может быть при передаче времени. В нашем случае задержки от источника у нас нет, а при передаче погрешность может составить **0,000153** секунды.

## SMTP/POP3/IMAP

Для работы с электронной почтой используются протоколы **SMTP (Simple Mail Transfer Protocol)**, **POP3 (Post Office Protocol)** и **IMAP (Internet Message Access Protocol)**. SMTP отвечает за отправку писем и используется как между клиентом и сервером, так и между почтовыми серверами. POP3 и IMAP, наоборот, применяются для получения почты. POP3 обычно загружает письма на устройство пользователя, тогда как IMAP позволяет работать с ними непосредственно на сервере и синхронизировать состояние между разными устройствами. На практике IMAP используется чаще, так как он лучше подходит для современных сценариев.

При использовании базовой аутентификации на почтовом сервере данные не шифруются, а только кодируются в **Base64**. Поэтому при отсутствии TLS их можно легко декодировать и привести к читаемому виду. Попробуем найти авторизационные данные с помощью фильтра `smtp.req.command == "AUTH"`.

![](../../_images/6daf20de98fc.webp)

В теле протокола можем увидеть поле **Username/Password** со значением **ADEyMzQ1Njc4QGFvbC5jb20AcGFzc3dk**. Попробуем декодировать эту Base64-строку с помощью любого декодера, к примеру, [**CyberChef**](https://gchq.github.io/CyberChef/#recipe=From_Base64%28'A-Za-z0-9%2B/%3D',true,false%29&input=QURFeU16UTFOamM0UUdGdmJDNWpiMjBBY0dGemMzZGs).

![](../../_images/5e632d64fc04.webp)

В результате мы получаем следующие учётные данные:

1. login - **12345678@aol.com**
2. password - **passwd**

## RDP

> **Remote Desktop Protocol (RDP)** - это протокол удалённого доступа к рабочему столу, позволяющий управлять компьютером по сети.

Пользователь получает полный графический интерфейс удалённой системы и может взаимодействовать с ней как с локальной. Внутри трафика этот протокол передает такой параметр, как **Routing Token/Cookie**.

> **Routing Token/Cookie** - параметр, который передаётся на раннем этапе согласования **RDP-сессии** и раскрывает имя пользователя или идентификатор подключения.

Само по себе это поле (**Routing Token/Cookie**) не является паролем или токеном доступа, но раскрывает имя пользователя, если в трафике отсутствует шифрование. Выставим фильтр **rdp.rt_cookie**, чтобы посмотреть на примере, как выглядит это поле.

![](../../_images/59d455094acc.webp)

Увидим, что на самом раннем этапе установки подключение RDP-сессии, вместе с основными данными в параметре **Routing Token/Cookie** передаётся значение **weberjoh-**, которое раскрывает имя пользователя. Хотя этого недостаточно для перехвата сессии, такая информация может дать злоумышленнику возможность перейти от полного перебора пары **логин/пароль** к атаке **password spraying**.

## SIP

> **Session Initiation Protocol (SIP)** - используется для установки, изменения и завершения мультимедийных сеансов, например **VoIP-звонков**.

Важно понимать, что SIP сам голос не передает. Он управляет звонком: кто кому звонит, когда вызов принят и когда сессия завершена. Сам медиапоток обычно передается по протоколу **RTP** или **SRTP**, которые мы рассмотрим позже. Сейчас же рассмотрим на практике как выглядит трафик SIP. Для этого выставим фильтр **sip**.

![](../../_images/9db5039a9d52.webp)

Мы можем увидеть разные типы сообщений, с помощью которых **SIP** управляет звонками. Так как в трафике представлены не все типы сообщений, поэтому разберём некоторые из них:

1. **INVITE** - начинает звонок или мультимедийную сессию
2. **ACK** - подтверждает успешное установление сессии
3. **BYE** - завершает уже установленную сессию
4. **CANCEL** - отменяет вызов до его принятия
5. **OPTIONS** - запрашивает возможности SIP-узла
6. **UPDATE** - изменяет параметры сессии до ее установления
7. **MESSAGE** - передает короткое текстовое сообщение через SIP

Самым интересным для нас будет сообщение типа **INVITE**, так как именно в нем содержатся параметры установки соединения и адреса. Чтобы рассмотреть детальнее содержимое пакета, выставим фильтр `sip.Method == "INVITE"`.

![](../../_images/89775687627b.webp)

В содержимом тела протокола мы можем увидеть такие данные, как:

1. **To** - вызываемый абонент (**+4960339285361**)
2. **From** - вызывающий абонент (**+31859027384**)
3. **Contact** - адрес, по которому можно связаться с инициатором (**sip:sgc_c217.0.21.65**)
4. **Allow** - список поддерживаемых SIP-методов (**REGISTER, REFER, NOTIFY, SUBSCRIBE, INFO, PRACK, UPDATE, INVITE, ACK, OPTIONS, CANCEL, BYE**)

Такие данные, а также множество других служебных параметров позволяют точно анализировать SIP-сессии: определять участников звонка, отслеживать этапы установления соединения и находить проблемы при передаче вызова.

## RTP/SRTP

> **Real-time Transport Protocol (RTP)** - это протокол передачи аудио и видео в реальном времени поверх **UDP**.

**RTP** переносит медиаданные и служебные поля, по которым можно отслеживать порядок пакетов, временные метки, тип полезной нагрузки и потери пакетов. В стандартной версии этот протокол не является защищённым и не шифрует медиаданные. Для защиты медиапотока используется **SRTP** (**Secure Real-time Transport Protocol**), который обеспечивает шифрование, проверку подлинности сообщений, контроль целостности и защиту от подмены RTP-данных. Рассмотрим, как выглядит **RTP-трафик** на практике и посмотрим на интересные поля в теле протокола. Установим фильтр **rtp**.

![](../../_images/f490c23bef86.webp)

В данном пакете мы видим RTP-поток от **84.146.135.221:7078** к **217.0.5.215:15020**, который был согласован через **SIP/SDP** в пакете **17965**. В RTP-пакете указан кодек **G.711 PCMA**, номер последовательности **1284**, временная метка **205440** и идентификатор источника **SSRC 0x6c889b66**, по которым можно анализировать медиапоток, порядок пакетов и возможные потери.

## BGP

> **BGP (Border Gateway Protocol)** - это протокол динамической маршрутизации, который используется для обмена маршрутами **между автономными системами** и описан в стандарте [**RFC4271**](https://datatracker.ietf.org/doc/html/rfc4271).

> **Автономная система** - это совокупность IP-сетей и маршрутизаторов, находящихся под единым административным управлением и использующих общую политику маршрутизации. Глобальный Интернет состоит из множества автономных систем, которые обмениваются маршрутной информацией между собой. Внутри автономной системы обычно используются внутренние протоколы маршрутизации, например **OSPF**, а обмен маршрутами между разными автономными системами выполняется с помощью BGP.

![](../../_images/94f0068b8585.webp)

На изображении выше **AS100** является транзитной автономной системой.

> **Транзитная автономная система** - автономная система, через которую передается трафик других автономных систем.

BGP работает поверх TCP, поэтому соединение между соседями надёжное. Когда маршрутизаторы устанавливают сессию, они сначала обмениваются сообщениями **OPEN**, а затем подтверждают соединение через **KEEPALIVE**, на протяжении всего соединения, раз в определенное время. После этого они начинают обмениваться маршрутами. Важно заметить, что BGP может опираться не только на технические параметры каналов при выборе метрики, но и на настроенную политику. А после того как маршруты все-таки выбраны, он будет делится ими только по определенным правилам, то есть отправлять только лучшие, не сообщать внутренним соседям маршруты, полученные от внутренних соседей другой автономной системы, а внешним соседям не сообщать маршруты, которые у них уже есть.

Рассмотрим сетевой трафик BGP, чтобы понять, как он себя ведет. Выставим фильтр `bgp`.

![](../../_images/fa4fbd4850ed.webp)

На данном участке можем увидеть процесс общения между двумя устройствами **192.168.255.1** и **192.168.255.14**. Общение начинается с обмена OPEN-пакетами, затем пакетами поддержки сессии и сообщениями о новых данных. Выберем сообщение от узла **192.168.255.1** с новыми данными, чтобы посмотреть, какая информация была передана.

![](../../_images/de0e3a958037.webp)

В теле сообщения нас интересуют тип сообщения, то есть **Update Message**, а также поля ниже. Рассмотрим, что они обозначают:

1. **NEXT_HOP** - следующим узлом для этого маршрута является 192.168.255.1
2. **LOCAL_PREF** - локальная метрика маршрута внутри AS равна 100
3. **AS_PATH** - пустое поле, что часто характерно для внутренних соседей
4. **ORIGIN**- источник маршрута неизвестен
5. **NLRI** - объявляется маршрут по умолчанию 0.0.0.0/0
