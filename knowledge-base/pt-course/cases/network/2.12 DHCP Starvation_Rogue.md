# Self-study Case 2.12 — DHCP Starvation_Rogue

> [!info] Путь в курсе
> Глава 2: Сети и сетевая безопасность / Часть 3. Кибератаки и защита от них / Атаки на L2

## Стенд / введение

Создадим виртуальную инфраструктуру в соответствии со схемой ниже:

![](../../_images/1155ae2cc0e4.webp)

Данная виртуальная инфраструктура состоит из следующих компонентов:

- **Debian-машина (Attacker)** - в качестве атакующей машины можно использовать любую ранее подготовленную виртуальную машину Debian. Она должна получать сетевой адрес динамически и быть подключена к MikroTik через адаптер типа **Internal Network** с именем **intnet**. В настройках адаптера необходимо установить для параметра **Promiscuous Mode** значение **Allow All**.
- **Debian-машина (Victim)** - использует динамический сетевой адрес и подключается к MikroTik через адаптер типа **Internal Network** с именем **intnet-debian**.
- **MikroTik** - выполняет функции маршрутизатора, NAT-шлюза и DHCP-сервера. В локальной сети ему назначен статический адрес **10.0.0.1/24**. Два адаптера типа **Internal Network** обеспечивают подключение виртуальных машин Attacker и Victim, а адаптер типа **Bridged Network** получает динамический адрес от маршрутизатора вашей домашней сети. Для адаптеров, подключённых к виртуальным машинам, необходимо установить для параметра **Promiscuous Mode** значение **Allow All**.

В качестве виртуальной машины (**Victim**) необходимо использовать подготовленный Positive Technologies OVA-образ с предустановленным программным обеспечением. Скачать его можно по [данной ссылке](https://storage.ptsecurity.com/seafhttp/f/11cea074671a4cfcb8ca/?op=view).

Для MikroTik также необходимо использовать подготовленный Positive Technologies OVA-образ, доступный по [данной ссылке](https://storage.ptsecurity.com/seafhttp/f/53c9a8db2ad14087a4c8/?op=view). При его импорте в VirtualBox в поле **MAC Address Policy** обязательно выберите значение **Include all network adapter MAC addresses**.

> Данные для аутентификации на виртуальной машине Victim не предоставляются, поскольку вход в неё для выполнения задания не требуется.

Уязвимость протокола **DHCP** связана с тем, что клиент обычно принимает сетевые параметры от первого DHCP-сервера, который ответил на его запрос. В обычной сети клиент не проверяет, является ли DHCP-сервер легитимным. Этим может воспользоваться атакующий, подключив к сети собственный DHCP-сервер.

> **DHCP Starvation** - атакующий отправляет большое количество **DHCP-запросов**, часто с разными **MAC-адресами**, чтобы занять весь пул адресов легитимного **DHCP-сервера**. После этого настоящий сервер больше не может выдавать адреса новым клиентам.

> **Rogue DHCP Server** - атакующий запускает собственный **DHCP-сервер** и начинает выдавать клиентам ложные сетевые параметры: **IP-адрес**, **шлюз**, **DNS-сервер**. Например, в качестве шлюза может быть указан адрес машины атакующего.

## Вопрос
*тип: open_answer, макс. баллов: 1, попыток: 3*

Необходимо провести совмещённую атаку DHCP Starvation + Rogue DHCP на Victim. Сначала требуется исчерпать пул адресов легитимного DHCP-сервера MikroTik, затем запустить поддельный DHCP-сервер и добиться получения Victim сетевых параметров от атакующего. После выполнения атаки необходимо найти флаг внутри сетевого трафика, исходящего с Victim. Пример: **osL4l0ug79lzEHouNXgS9QXoCHEj0E**

**DHCP Snooping** - основная технология защиты от Rogue DHCP. Она разделяет порты коммутатора на доверенные и недоверенные.

Роли портов:

1. **Trusted** - порты, за которыми находятся легитимные DHCP-серверы или uplink к ним.
2. **Untrusted** - клиентские порты. На недоверенных портах разрешаются DHCP-запросы от клиентов, но блокируются DHCP-ответы сервера, такие как **DHCP Offer** и **DHCP Ack**. Благодаря этому клиентское устройство может получить адрес, но не может выступать в роли DHCP-сервера.

**Port Security** - ограничивает количество MAC-адресов, которые могут находиться за одним портом. Например, если на порту должна быть только одна рабочая станция, коммутатор разрешает только 1 MAC-адрес. Если атакующий начинает генерировать DHCP-запросы от множества разных MAC-адресов, порт фиксирует нарушение и может заблокировать трафик или отключиться.

**MAC Address Verification** - дополнительная защита от обхода Port Security. Некоторые инструменты могут не менять внешний MAC-адрес Ethernet-кадра, а менять только поле **CHADDR** внутри DHCP-пакета. В таком случае для коммутатора трафик выглядит как идущий от одного устройства, но DHCP-сервер видит много разных клиентов. MAC Address Verification сверяет внешний MAC-адрес кадра с MAC-адресом внутри DHCP-пакета. Если они не совпадают, пакет отбрасывается.

**Client Isolation / Port Isolation** - ограничивает горизонтальное L2-общение между клиентами. Клиенты могут обращаться к шлюзу или серверу, но не могут напрямую взаимодействовать друг с другом. Это снижает риск прямого воздействия атакующего на соседние клиентские устройства.

Сначала необходимо включить DHCP Snooping и выдать роли портам. Воспользуемся следующими командами:

1. `/interface bridge set br dhcp-snooping=yes`
2. `/interface bridge port set [find interface=ether2] trusted=no`
3. `/interface bridge port set [find interface=ether3] trusted=no`

Теперь ограничим общение хостов по горизонтали.

1. `/interface bridge port set [find interface=ether2] horizon=1`
2. `/interface bridge port set [find interface=ether3] horizon=1`

Напишем скрипт, который будет имитировать функционал **Port Security**. Для этого создадим пустой скрипт командой `/system script add name=protect policy=read,write,test source=""`, затем откроем редактор `/system script edit protect source` и вставим следующее содержимое:

```
{
    :local bridgename "br"
    :local limit 1

    :foreach portname in={"ether2";"ether3"} do={

        :local cnt [/interface bridge host print count-only where bridge=$bridgename and on-interface=$portname and dynamic=yes and local=no]

        :if ($cnt > $limit) do={
            /log warning ("PORTSEC: violation on " . $portname . ", learned MAC count=" . $cnt . ", disabling port")
            /interface bridge port disable [find where bridge=$bridgename and interface=$portname]
        }
    }
}

```

Скрипт проходит по портам ether2 и ether3 в мосте br и считает количество динамически изученных MAC-адресов на каждом порту. Если на порту найдено больше 1 MAC-адреса, скрипт считает это нарушением, записывает предупреждение в лог и отключает этот порт в bridge. На изображении ниже показано, как должен выглядеть скрипт в терминале MikroTik.

![](../../_images/fead1d603e71.webp)

После сохранения содержимого укажем интервал автоматического запуска скрипта командой `/system scheduler add name=protect-scheduler interval=1s on-event=protect`

Для того чтобы убедится в правильном функционировании параметров безопасности, попытаемся еще раз выполнить атаку. Остановим службу **isc-dhcp-server**, затем одновременно запустим утилиты **ping** и **yersinia**, чтобы посмотреть, оборвет ли MikroTik соединение с нами, когда на интерфейсе станет больше 1 MAC-адреса.

![](../../_images/732caef6e325.webp)

На скриншоте видно, что после успешного прохождения трех ICMP-пакетов соединение обрывается, а адрес 10.0.0.1 становится недостижимым. В свою очередь, на самом MikroTik можно увидеть деактивированный интерфейс **ether2** и сообщение о срабатывании защиты, как показано на изображениях ниже.
