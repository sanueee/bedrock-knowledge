# Guided Case 2.10 — 3proxy

> [!info] Путь в курсе
> Глава 2: Сети и сетевая безопасность / Часть 2. Методы конфигурации сети / VPN и Proxy

## Стенд / введение

Создадим виртуальную инфраструктуру в соответствии со схемой ниже:

![](../../_images/b8d77daa9824.webp)

**Виртуальная инфраструктура состоит из:**

1. Debian-машины **External PC**, обязательно имеющей графический интерфейс, с адресом 10.0.0.2/24
2. Debian-машины **Proxy Server** с установленным 3proxy и адресом 10.0.0.1/24 в сети с External PC и адресом 192.168.2.2/24 в сети с MikroTik
3. Маршрутизатора **MikroTik** с адресом 192.168.2.1/24 в сети с Proxy Server и адресом 192.168.1.1/24 во внутренней локальной сети
4. Debian-машины **Internal Server** с адресом 192.168.1.10/24 и шлюзом 192.168.1.1

Для выполнения данного кейса необходимо скачать новый или клонировать ранее скачанный **OVA-образ** виртуальной Debian-машины, заготовленной Positive Technologies. В данном образе уже есть предустановленный набор программного обеспечения, а скачать его можно по [**данной ссылке**](https://storage.ptsecurity.com/seafhttp/f/b4275685f64849189a2a/?op=view). В качестве External PC необходимо использовать **OVA-образ** виртуальной Debian-машины с предустановленным **GNOME**, скачать его можно по [**данной ссылке**](https://storage.ptsecurity.com/seafhttp/f/205e9aa5d35a4871842e/?op=view)**.**

Для начала выдадим всем сетевым интерфейсам устройств адреса, которые соответствуют схеме, а также добавим статический маршрут на Proxy-сервер в сеть **192.168.1.0/24**, командой `sudo ip route add 192.168.1.0/24 via 192.168.2.1`.

Настроим Proxy-сервер. На виртуальной машине Debian предустановлена служба 3proxy, для настройки сервера. Чтобы регулировать логику работы необходимо отредактировать содержимое в файле **/etc/3proxy/3proxy.cfg**. Внесем следующие данные:

```
#daemon
nscache 65536
timeouts 1 5 30 60 180 1800 15 60

auth iponly
allow * 10.0.0.0/24 192.168.1.10 443 HTTPS

deny *
proxy -p3128 -i10.0.0.1 -e192.168.2.2
```

После сохранения настроек перезапускаем службу 3proxy и переходим к настройке внутреннего сервера. На внутреннем ресурсе нам необходимо поднять сервер nginx и сформировать ssl-сертификат, с помощью предустановленного пакета **openssl**.

Сначала добавим **PROXY TEST** в файл **index.html**. Теперь следующей командой создадим самоподписанный сертификат для функционирования https `sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout /etc/ssl/private/edtechlab.key -out /etc/ssl/certs/edtechlab.crt -subj "/CN=edtechlab.intern"`. Создадим конфиг **/etc/nginx/sites-available/edtechlab** и добавим в него следующие данные:

```
server {
    listen 443 ssl;
    server_name _;

    ssl_certificate /etc/ssl/certs/edtechlab.crt;
    ssl_certificate_key /etc/ssl/private/edtechlab.key;

    root /var/www/html;
    index index.html;
}

```

> **Самоподписанный сертификат** - это **SSL/TLS-сертификат**, который создан и подписан самим владельцем сервера, а не доверенным центром сертификации. Он позволяет использовать **HTTPS-шифрование**, но браузер может показывать предупреждение, так как не может автоматически проверить доверие к такому сертификату.

Создадим ссылку на этот файл в директории **/etc/nginx/sites-enabled/edtechlab** командой `sudo ln -s /etc/nginx/sites-available/edtechlab /etc/nginx/sites-enabled/edtechlab`, а затем перезагрузим службу nginx.

Перейдем на клиентскую машину и откроем браузер **Firefox**, а затем в настройках перейдем в меню Proxy (**Settings -> Network Settings -> Manual proxy configuration**).

![](../../_images/6e2a97627f58.webp)

Затем в настройках укажем следующие данные:

1. HTTP Proxy: 10.0.0.1; Port: 3128
2. HTTPS Proxy: 10.0.0.1; Port: 3128

![](../../_images/03fde8ade46f.webp)

Сохраняем настройки и в адресной строке вводим [**https://192.168.1.10**](https://192.168.1.10)

![](../../_images/bb7d5a8c9f24.webp)

Так как мы создавали **самоподписанный** сертификат, браузер не может проверить, поэтому выдает предупреждение. Соглашаемся с рисками, нажав кнопку **Accept the Risk and Continue**.

> Вне лабораторного окружения соглашаться с рисками, если вы не уверены в ресурсе не рекомендуется

![](../../_images/804ec50c4424.webp)

Мы можем видеть, что доступ к внутреннему ресурсу мы получили и видим надпись **PROXY TEST**. Теперь же проверим, работает ли разграничение доступа только по HTTPS, для этого в адресную строку введем измененную строку **http://192.168.1.10**

![](../../_images/c715eb3118f8.webp)

При попытке получить доступ по протоколу HTTP, ресурс недоступен, о чем нам сообщает ошибка **Access Denied**. В пояснение к ошибке написано более точно. Пояснение информирует нас о том, что контроль доступа запрещает нам обращаться к ресурсу.

## Вопрос
*тип: open_answer, макс. баллов: 1, попыток: 3*

Мы настроили подключение к внутреннему ресурсу через Proxy-сервер по протоколу HTTPS. После настройки необходимо скачать и запустить файл **checker_proxy **на **External PC **с помощью команды `sudo chmod +x ~/checkers/checker_proxy && sudo ~/checkers/checker_proxy`
