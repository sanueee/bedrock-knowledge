# Guided Case 2.7 — VLAN

## Стенд / введение

Создадим виртуальную инфраструктуру в соответствии со схемой ниже:

![](../../_images/d033f48fcad4.webp)

**Виртуальная инфраструктура состоит из:**

1. Первый коммутатор (**MikroTik1**) с адресом 192.168.1.1/24
2. Второй коммутатор (**MikroTik2**) с адресом 192.168.1.2/24
3. Третий коммутатор (**MikroTik3**) с адресом 192.168.1.3/24
4. Подсети 1, подключенной к MikroTik1
5. Подсети 2, подключенной к MikroTik2
6. Подсети 3, подключенной к MikroTik3

Для выполнения данного кейса необходимо скачать новый или клонировать ранее скачанный **OVA-образ** виртуальной Debian-машины, заготовленной Positive Technologies. В данном образе уже есть предустановленный набор программного обеспечения, а скачать его можно по [**данной ссылке**](https://storage.ptsecurity.com/seafhttp/f/b4275685f64849189a2a/?op=view)

> **Сетевой мост** - программная функция, объединяющая несколько сегментов локальной сети в **единую сеть**.
> 
> 
> 
> **Широковещательный шторм** - это состояние сети, при котором из-за петель или неконтролируемой рассылки широковещательных кадров происходит увеличение трафика, приводящее к перегрузке сети и отказу в обслуживании.
> 
> 
> 
> **Время сходимости** - это время, за которое сеть после изменения топологии пересчитывает дерево и восстанавливает корректную работу без петель.

#### Настройка широковещательного домена

Настроим сетевые интерфейсы и их адреса в соответствии со схемой и таблицей ниже:

|  | MikroTik1 | MikroTik2 | MikroTik3 | Subnet1 | Subnet2 | Subnet3 |
|---|---|---|---|---|---|---|
| MikroTik1 | - | intnet12 | intnet31 | intnetsub1 | - | - |
| MikroTik2 | intnet12 | - | intnet23 | - | intnetsub2 | - |
| MikroTik3 | intnet31 | intnet23 | - | - | - | intnetsub3 |

Затем на каждом коммутаторе создадим сетевые мосты и объединим в них все соответствующие кабели (в каждом по три штуки). А затем назначим каждому мосту IP-адрес.

MikroTik1:

1. `/interface bridge add name=br1 disabled=no protocol-mode=none` - создает сетевой мост br1
2. `/interface bridge port add bridge=br1 interface=ether1 `- добавляет ether1 в мост br1
3. `/interface bridge port add bridge=br1 interface=ether2` - добавляет ether2 в мост br1
4. `/interface bridge port add bridge=br1 interface=ether3` - добавляет ether3 в мост br1
5. `/ip address add address=192.168.1.1/24 interface=br1` - назначает IP-адрес мосту br1

MikroTik2:

1. `/interface bridge add name=br1 disabled=no protocol-mode=none`
2. `/interface bridge port add bridge=br1 interface=ether1`
3. `/interface bridge port add bridge=br1 interface=ether2`
4. `/interface bridge port add bridge=br1 interface=ether3`
5. `/ip address add address=192.168.1.2/24 interface=br1`

MikroTik3:

1. `/interface bridge add name=br1 disabled=no protocol-mode=none`
2. `/interface bridge port add bridge=br1 interface=ether1`
3. `/interface bridge port add bridge=br1 interface=ether2`
4. `/interface bridge port add bridge=br1 interface=ether3`
5. `/ip address add address=192.168.1.3/24 interface=br1`

Теперь спровоцируем шторм, применив команду `ping 192.168.1.3` с первого коммутатора на третий. Для того чтобы продемонстрировать нагрузку на сетевом мосте, включим мониторинг трафика командой `interface monitor-traffic br1` на MikroTik3 и MikroTik2, как показано далее.

![](../../_images/143cc6b23cb2.webp)

На скриншоте видно, что ICMP-пакеты на первом роутере иногда не доходят, вызывая ошибку **timeout**, а также скорость ответа растет со временем, от 3 мс до 27 мс. Наличие шторма подтверждает и мониторинг, показывая максимально 1472 пакетов в секунду, что для трех устройств явно многовато. Пока наша сеть не упала, отключим мост командой `/interface bridge disable br1`.

#### Локализация путем VLAN-сегментации

Для локализации шторма мы создадим два VLAN-сегмента (10 и 20), а также настроим access и trunk порты, чтобы локализовать шторм. Произведем необходимые настройки на коммутаторах.

Первый коммутатор:

1. `/interface bridge port set [find interface=ether3] pvid=10` - назначает ether3 VLAN ID 10
2. `/interface vlan add name=vlan10 interface=br1 vlan-id=10` - создает VLAN-интерфейс vlan10
3. `/ip address set [find interface=br1] interface=vlan10` - переносит IP-адрес с br1 на vlan10
4. `/interface bridge vlan add bridge=br1 vlan-ids=10 tagged=br1,ether1,ether2 untagged=ether3` - настраивает VLAN 10 с trunk- и access-портами
5. `/interface bridge vlan add bridge=br1 vlan-ids=20 tagged=br1,ether1,ether2` - разрешает VLAN 20 на trunk-портах
6. `/interface bridge enable br1` - включает мост br1
7. `/interface bridge set br1 vlan-filtering=yes` - включает фильтрацию VLAN на мосту

Второй коммутатор:

1. `/interface bridge port set [find interface=ether3] pvid=10`
2. `/interface vlan add name=vlan10 interface=br1 vlan-id=10`
3. `/ip address set [find interface=br1] interface=vlan10`
4. `/interface bridge vlan add bridge=br1 vlan-ids=10 tagged=br1,ether1,ether2 untagged=ether3`
5. `/interface bridge vlan add bridge=br1 vlan-ids=20 tagged=br1,ether1,ether2`
6. `/interface bridge enable br1`
7. `/interface bridge set br1 vlan-filtering=yes`

Третий коммутатор:

1. `/interface bridge port set [find interface=ether3] pvid=20`
2. `/interface vlan add name=vlan20 interface=br1 vlan-id=20`
3. `/ip address set [find interface=br1] interface=vlan20`
4. `/interface bridge vlan add bridge=br1 vlan-ids=10 tagged=br1,ether1,ether2`
5. `/interface bridge vlan add bridge=br1 vlan-ids=20 tagged=br1,ether1,ether2 untagged=ether3`
6. `/interface bridge enable br1`
7. `/interface bridge set br1 vlan-filtering=yes`

Аналогично применяем утилиту **ping** с MikroTik1 на MikroTik2, так как на третий коммутатор уже недоступен, ведь теперь он в другом VLAN-сегменте. Теперь на интерфейсах второго устройства (**ether1**) и третьего (**ether3**) одновременно запускаем мониторинг (`interface monitor-traffic <наименование интерфейса>`), как показано ниже.

![](../../_images/b53e6355ebae.webp)

Теперь ситуация внутри инфраструктуры изменилась. Можно отчетливо увидеть, что внутри сегмента 20 количество пакетов (параметр - **rx-packets-per-second**) снизилось, но все равно еще выше нормы, при этом на интерфейсе MikroTik3 этот параметр равен 0, так как его access порт не пропускает трафик.

#### Устранение шторма протоколом STP

На третьем этапе мы полностью излечим сеть от шторма, включив протокол STP. Для этого применим следующую команду на каждом устройстве.

1. MikroTik1 - `/interface bridge set br1 protocol-mode=stp`
2. MikroTik2 - `/interface bridge set br1 protocol-mode=stp`
3. MikroTik3 - `/interface bridge set br1 protocol-mode=stp`

Для того чтобы закрепить роль root-коммутатора строго за MikroTik3 командой `/interface bridge set br1 priority=0x1000`, а на остальных введем другую команду `/interface bridge set [find] priority=0x8000`. Затем запустим **ping** с первого на второй коммутатор, как делали прежде, а также включаем мониторинг br1 на остальных коммутаторах.

После применения настроек видно, что ошибка **timeout** полностью исчезла, а параметр **time** стал в пределах 2 миллисекунд. Количество пакетов в секунду со значения 1472 опустилось до 1.

#### Сравнение STP и RSTP

Для начала убедимся, что MikroTik3 является главным коммутатором (параметр - root-bridge), а также определим root-порты на устройствах (параметр - root-port), с помощью применения команды `interface bridge monitor br1`, как это сделано на изображении дальше.

![](../../_images/ef7eba5aafb8.webp)

Из скриншота видно, что третий коммутатор, как и задумывалось **root**, а на первом и втором root-портами являются интерфейсы **ether2**. Для того чтобы увидеть время схождение топологии, запустим **ping** с MikroTik1 на MikroTik2, параллельно выполнив перезагрузку **ether2** на MikroTik2, применив последовательно команды:

1. `interface disable ether2`
2. `interface enable ether2`

В момент перезагрузки утилита **ping** будет выдавать ошибки **timeout**, так как время перестроения топологии STP составляет 30–50 секунд. Соответственно, в этот промежуток времени часть пакетов будет теряться из-за отсутствия корректного маршрута передачи, что показано ниже.

![](../../_images/5f0d47e2286d.webp)

Можем увидеть, что при перезагрузке интерфейса **ether2** доступность узла упала, потому что в это время происходит перестроение топологии протоколом STP. Теперь выполним аналогичную перезагрузку интерфейса, но перед этим заменим протокол STP на RSTP следующими командами:

1. MikroTik1 - `/interface bridge set br1 protocol-mode=rstp`
2. MikroTik2 - `/interface bridge set br1 protocol-mode=rstp`
3. MikroTik3 - `/interface bridge set br1 protocol-mode=rstp`

![](../../_images/87be7edbb900.webp)

В случае с использованием RSTP, можем увидеть, что доступность не прерывалась, так как эта версия протокола связующего дерева перестраивает топологию быстрее.

#### Подготовка к проверке

В данном кейсе для проверки необходимо подключить Debian-машину в **Подсеть 3** и настроить ее сетевой интерфейс **enp0s3**, так чтобы был доступ до коммутатора **MikroTik3**. Какие настройки файла **/etc/network/interfaces** показано далее.

```
allow-hotplug enp0s3
iface enp0s3 inet static
	address 192.168.1.10
	netmask 255.255.255.0
	gateway 192.168.1.3

```

Затем на коммутаторе проверим работающие сервисы командой `ip service print`.

![](../../_images/14b2f4992183.webp)

Важно проверить отсутствие символа **X** перед сервисом **ssh**, если по каким-то причинам символ присутствует, то выполните команду `ip service enable ssh`. Затем выполним команду `ip service disable telnet`, чтобы отключить небезопасный протокол **telnet**. Итоговый список сервисов и их состояний должен выглядеть так:

![](../../_images/cef9fede39a5.webp)

Заключительным этапом установите пароль **pt-3dt3chl@b** для пользователя **admin** на коммутаторе с помощью команды `user set admin password=pt-3dt3chl@b`

## Вопрос
*тип: open_answer, макс. баллов: 1, попыток: 3*

Мы настроили сегментацию сети с помощью **VLAN**, а также использовали протоколы связующего дерева **STP/RSTP** для удаления петлей из топологии. После настройки сетевых конфигураций необходимо запустить **checker_vlan **на **Debian-машине **с помощью команды `sudo chmod +x ~/checkers/checker_vlan && sudo ~/checkers/checker_vlan`
