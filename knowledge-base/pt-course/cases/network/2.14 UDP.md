# Self-study Case 2.14 — UDP

## Стенд / введение

   - Сетевой шлюз - 192.168.1.1

Вторая сеть **192.168.2.0/24** состоит из:

1. Маршрутизатор **MikroTik** с интерфейсом **ether3**:

   - Маска - 255.255.255.0
2. **ServerScan** с интерфейсом **enp0s3**

Для выполнения данного кейса необходимо скачать **OVA-образ** виртуальной машины **ServerScan**, заготовленный Positive Technologies, скачать его можно по [**данной ссылке**](https://storage.ptsecurity.com/seafhttp/f/0eadf6eb044245698f39/?op=view). **ServerScan** уже настроен, требуется только подключить с правильными сетевыми параметрами

> У всех виртуальных машин должно быть по 1 сетевому адаптеру VirtualBox в режиме **Internal Network**

Сканирование внешней сети через UDP пакеты в реальной практике встречается редко, так как возникает проблема потери пакетов. Фаерволы часто настроены на DROP входящих UDP пакетов. Из-за подобных проблем сканирование UDP затягивается на часы, если между узлами есть множество промежуточных устройств.

Логика UDP-сканирования проста - отправляем на порт UDP пакет, если порт открыт, сервис может ответить своим UDP-пакетом (а может и промолчать). Если порт закрыт, операционная система цели обязана (по стандарту RFC) прислать ICMP Destination Unreachable, но он может быть поглащен фаерволом.

> **RFC** - серия документов, которые описывают технические спецификации, протоколы, стандарты и рекомендации, формирующие архитектуру сетей

При атаках используют следующие виды UDP сканирования:

1. Классическое сканирование портов - Nmap шлет пустые UDP-пакеты на указанные порты, для этого используется флаг **-sU**
2. Быстрый поиск UDP-сервисов через версии - nmap отправляет не пустой пакет, а специфический запрос для конкретного сервиса (например, запрос версии для DNS), используется флаг **-sV**
3. Использование UDP для обнаружения хоста - если ICMP-пинг запрещен, можно попробовать взаимодействовать с хостом через UDP, при помощи флага **-PU**

## Вопрос
*тип: open_answer, макс. баллов: 1, попыток: 3*

Какой **тип сервиса** определил nmap на сотом порту при сканирование UDP?

Ответ писать полностью, без пробелов.

> Подсказка: Смотрите на fingerprint, который выдает nmap на сотом порту.

В отличие от TCP, где закрытый порт просто не отвечает, стандарты UDP обязывают систему отправлять уведомление об ошибке. Поэтому эффективную стратегию можно построить двух принципах:

1. Жесткие лимиты - политика DROP вместо REJECT, в штатном режиме закрытый UDP-порт возвращает пакет ICMP Port Unreachable. Настройка брандмауэра в режим DROP заставляет систему уничтожать входящие запросы
2. Принудительное молчание - ограничение скорости ответов. Сетевой стек ядра Linux по умолчанию лимитирует генерацию сообщений об ошибках, искусственное ужесточение этих системных лимитов заставляет сканер увеличивать задержки

В реальности противник не будет знать, какой порт ему нужен и будет изначально рассматривать стандартные порты. Сканирование 200 портов уже заняло без малого 5 минут, при условии, что был выбран довольно быстрый режим сканирования **--max-rtt-timeout 50ms** - ограничивает время ожидания ответа на пакет до 50 миллисекунд и **-T4** - агрессивный шаблон скорости.

![](../../_images/6483c475db1f.webp)

Для защиты от быстрого сканирования портов настроим брандмауэр так, чтобы он возвращал уведомления о закрытых портах с жестко ограниченной скоростью, а все остальные подобные пакеты уничтожал. Для этого используем следующие флаги в iptables:

- **-A OUTPUT** - добавляем правило в цепочку исходящего трафика.
- **-p icmp --icmp-type port-unreachable** - фильтрует только ICMP-сообщения типа **порт недоступен**, которые генерируются при обращении к закрытым UDP-портам.
- **-m limit** - подключает модуль **limit** для контроля скорости передачи пакетов.
- **--limit 1/s** - устанавливает максимальную среднюю скорость пропускания - 1 пакет в секунду.
- **--limit-burst 1** - задает количество пакетов в буфере, в нашем случае 1 пакет.
- **-j ACCEPT / -j DROP** - либо разрешить прохождение пакета (**ACCEPT**), либо безвозвратно уничтожить его (**DROP**)

Получаем команду для ограничения скорости `sudo iptables -A OUTPUT -p icmp --icmp-type port-unreachable -m limit --limit 1/s --limit-burst 1 -j ACCEPT`

Остальной трафик мы просто отбрасываем `sudo iptables -A OUTPUT -p icmp --icmp-type port-unreachable -j DROP`

Просканируем повторно сервер и увидим, что Nmap начинает отображать активные службы на тех портах, где они фактически отсутствуют. Этот эффект обусловлен двумя факторами:

- Искажение обратной связи - правило ограничения скорости уничтожает легитимные исходящие пакеты ICMP Port Unreachable. Без этих уведомлений, Nmap не получает подтверждения того, что целевой порт закрыт. Согласно алгоритмам работы сканера, отсутствие ответа интерпретируется как потеря пакета в сети или блокировка файрволом, что автоматически переводит порт в неопределенный статус open|filtered.
- Фактор дефицита времени - при агрессивном сканировании с жестким ограничением тайм-аута (например, --max-rtt-timeout 50ms), Nmap работает в условиях дефицита времени. Сканер физически не успевает дождаться секундной паузы, когда лимит брандмауэра обнулится и сервер снова сможет легитимно подтвердить закрытие порта.
