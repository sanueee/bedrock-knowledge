## Стенд / введение

Создадим виртуальную инфраструктуру в соответствии с схемой ниже:

![](../../_images/bfa25f7aeffc.webp)

Первая сеть **192.168.1.0/24**, которая состоит из:

1. маршрутизатор **MikroTik** с интерфейсом **ether1**:
   
   - IP-адрес - 192.168.1.1
   - Маска - 255.255.255.0
2. **Debian-машина** с **GUI** и интерфейсом **enp0s3**. Установка виртуальной машины аналогична разделу **Установка Debian 12 **из Главы 1, только при создании требуется загрузить графический интерфейс
   
   - IP-адрес - 192.168.1.252
   - Маска - 255.255.255.0
   - Сетевой шлюз - 192.168.1.1

Вторая сеть **192.168.2.0/24** состоит из:

1. маршрутизатор **MikroTik** с интерфейсом **ether2**:
   
   - IP-адрес - 192.168.2.1
   - Маска - 255.255.255.0
2. **Victim3** с интерфейсом **enp0s3**:
   
   - IP-адрес - назначается по DHCP
   - Маска - назначается по DHCP
   - Сетевой шлюз - 192.168.2.1

Третья сеть **10.0.0.0/8** состоит из:

1. маршрутизатор **MikroTik** с интерфейсом **ether3**:
   
   - IP-адрес - 10.0.0.1
   - Маска - 255.0.0.0
2. **Suricata** с интерфейсом **enp0s3**:
   
   - IP-адрес - 10.255.255.254
   - Маска - 255.0.0.0
   - Сетевой шлюз - 10.0.0.1

В данном кейсе **Suricata** аналогична настроена и также используется как в предыдущем кейсе

Для выполнения данного кейса необходимо скачать **OVA-образ** виртуальной машины **Victim3**, заготовленный Positive Technologies, скачать его можно по [**данной ссылке**](https://storage.ptsecurity.com/seafhttp/f/181ed3e4a0ce46eb8943/?op=view). **Victim3** уже настроен, требуется только подключить с правильными сетевыми параметрами

> У виртуальных машин должно быть по 1 сетевому адаптеру VirtualBox в режиме **Internal Network**

## Вопрос
*тип: open_answer, макс. баллов: 1, попыток: 3*

Какое значение лежит в файле **readme** на сервере?

Посмотрим на логи в EveBox, которые появились в записях во время атаки.

![](../../_images/7c1a948df066.webp)

В EveBox сработало правило из открытого набора [PT Rules](https://rules.ptsecurity.com/):

```
alert http any any -> any any (msg: "ATTACK [PTsecurity] React Server Components RCE (CVE-2025-55182)"; flow: established, to_server; pcre: "/(?:next-action|rsc-action-id)/Hi"; http.content_type; content: "multipart/form-data|3b 20|"; content: "boundary|3d|"; distance: 0; http.request_body; content: "Content-Disposition|3a 20|"; content: "form-data|3b|"; distance: 0; content: "|22|status|22|"; distance: 0; pcre: "/\s*:\s*\x22resolved_model\x22/PR"; content: "Content-Disposition|3a 20|"; distance: 0; content: "form-data|3b|"; distance: 0; content: "|24 40|"; distance: 0; reference: url, www.wiz.io/blog/critical-vulnerability-in-react-cve-2025-55182; reference: cve, 2025-55182; reference: url, rules.ptsecurity.com; classtype: attempted-admin; sid: 10016007; rev: 1;)

```

Правило, которое зафиксировало атаку, ищет в HTTP-заголовках специфичные маркеры серверных экшенов next-action или rsc-action-id. Если данные заголовки найдены, запускается относительная цепочка проверок, которая подтверждает, что тип передаваемых данных соответствует веб-форме multipart/form-data, после этого происходит чтение тела запроса и проверка наличия параметра **status** со значением **resolved_model**. Финальным этапом выступает поиск комбинации байт **24 40**, которая отвечает за передачу ссылок на объекты в протоколе React Flight. Если вся последовательность заголовков и вредоносных параметров в теле формы строго совпала, Suricata генерирует предупреждение об атаке.

Откроем карточку инцидента и изучим его подробнее.

![](../../_images/28c9b0d2951c.webp)

Видим следующую информацию:

- **Timestamp** - 2026-06-11 06:28:07.445
- **Protocol** - TCP
- **Source** - 192.168.1.252, порт отправки: 39686
- **Destination** - 192.168.2.250, порт назначения: 3000
- **In interface** - dummy0
- **Signature** - ATTACK [PTsecurity] React Server Components RCE (CVE-2025-5182)
- **Category** - попытка получения прав администратора (Attempted Administrator Privilege Gain)
- **Severity** - 1, является наивысшим уровнем опасности
- **Action** - allowed, трафик был пропущен системой обнаружения вторжений, так как она работает в режиме мониторинга

Атакующий отправил на сервер 6 пакетов, передав 1254 байта данных. В ответ от сервера пришло 4 пакета объемом 280 байт. Малое количество пакетов указывает на то, что это был одиночный сетевой запрос. HTTP-метод - POST, атакующий отправлял вредоносную нагрузку в теле запроса, а не через адресную строку. Запрос был отправлен на корневой эндпоинт, инструментом атаки является библиотека **python-requests/2.32.3**.
