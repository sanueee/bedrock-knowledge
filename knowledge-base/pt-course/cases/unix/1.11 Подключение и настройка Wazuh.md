# Guided Case 1.11 — Подключение и настройка Wazuh

> [!info] Путь в курсе
> Глава 1: UNIX-системы и их безопасность / Часть 2: Устройство операционной системы Linux
>
> **Теория:** [2.01 Процесс загрузки и инициализации Linux](../../unix/2%20Устройство%20операционной%20системы%20Linux/2.01%20Процесс%20загрузки%20и%20инициализации%20Linux.md), [2.02 Ядро и userspace](../../unix/2%20Устройство%20операционной%20системы%20Linux/2.02%20Ядро%20и%20userspace.md)

## Стенд / введение

- Для выполнения данного кейса нам понадобятся 2 виртуальные машины. Создадим их путем **клонирования** базового образа **Debian-12-Gold**, который мы делали в статье **"Настройка Debian 12"** и переименуем в **Wazuh-Server** и **Wazuh-Agent** для удобства пользования
- У данных виртуальных машин должен быть **1** сетевой адаптер VirtualBox в режиме **NAT Network**
- Рекомендуемые мощности для виртуальных машин: **2vCPU**, **1GB RAM**
- Учётные данные от виртуальных машин остаются такими, какие вы назначали при установке образа

В этом разделе мы развернем SIEM-систему Wazuh. Наша цель - установить сервер и агент и настроить сбор событий безопасности (анализ логов и контроль целостности файлов), чтобы научиться централизованно фиксировать инциденты. Но для начала нам необходимо настроить проброс портов и статические IP-адреса.

Для доступа к виртуальным машинам с хост-машины настроим проброс портов в VirtualBox. Для этого откроем настройки сети в главном меню гипервизора: **File **-> **Tools** -> **Network**.

![](../../_images/cf38c9711459.webp)

В открытом меню находим секцию "NAT Networks", выбираем подсеть, которую конфигрурировали ранее. В нижнем меню находится секция "Port Forwarding"

![](../../_images/d4430bd2dc16.webp)

Добавим правила:

- Для Wazuh-Server:

| Name | Protocol | Host IP | Host Port | Guest IP | Guest Port |
|---|---|---|---|---|---|
| Wazuh-Server-SSH | TCP | 127.0.0.1 | 2225 | 192.168.250.10 | 22 |
| Wazuh-Web | TCP | 127.0.0.1 | 8443 | 192.168.250.10 | 443 |

- Для Wazuh-Agent:

| Name | Protocol | Host IP | Host Port | Guest IP | Guest Port |
|---|---|---|---|---|---|
| Wazuh-Agent-SSH | TCP | 127.0.0.1 | 2226 | 192.168.250.11 | 22 |

Далее настроим статические IP-адреса для обеих виртуальных машин. Поскольку машины были клонированы из одного образа, они получили одинаковые сетевые настройки. Для корректной работы проброса портов нам нужны фиксированные адреса.

Запустите виртуальные машины и войдите в систему через консоль VirtualBox.

> Предварительно на обеих машинах установите **sudo** и добавьте вашего пользователя в группу **sudo**

**Настройка Wazuh-Server (IP 192.168.250.10):**

Откроем файл конфигурации сети в текстовом редакторе:

`sudo nano /etc/network/interfaces`

Найдем секцию, отвечающую за сетевой интерфейс и заменим ее на следующую:

```
auto enp0s3
iface enp0s3 inet static
    address 192.168.250.10/24
    gateway 192.168.250.1
    dns-nameservers 8.8.8.8
```

> Название интерфейса может отличаться в зависимости от образа виртуальной машины. Перед настройкой выполните команду `ip a` и уточните его актуальное название.

Сохраним файл (нажмем Ctrl+O, Enter) и выйдем из редактора (Ctrl+X).

Применим изменения, перезапустив сетевую службу и перезагрузив виртуальную машину:

```
sudo systemctl restart networking
sudo reboot
```

**Настройка Wazuh-Agent (IP 192.168.250.11):**

Выполните аналогичные действия на второй виртуальной машине, но в файле **/etc/network/interfaces** укажите другой IP-адрес:

```
auto enp0s3
iface enp0s3 inet static
    address 192.168.250.11/24
    gateway 192.168.250.1
    dns-nameservers 8.8.8.8
```

Затем перезапустите сеть и перезагрузите:

```
sudo systemctl restart networking
sudo reboot
```

Для начала работы подключимся к каждой виртуальной машине по SSH. Допустим, что имя пользователя на вашей виртуальной машине: **pt-intern**. Команда **ssh** устанавливает защищенное соединение с удаленным сервером. Флаг **-p** указывает номер порта, а [**pt-intern@127.0.0.1**](mailto:pt-intern@127.0.0.1) - это имя пользователя и адрес хоста.

- Подключение к обеим виртуальным машинам:

```
ssh -p 2225 pt-intern@127.0.0.1
ssh -p 2226 pt-intern@127.0.0.1
```

Теперь у нас есть доступ к обеим виртуальным машинам. Для проверки корректности выполнения задания в конце практики необходимо скачать и подготовить чекер. Выполним следующие команды на **Wazuh-Server**:

```
sudo apt install wget -y
mkdir -p ~/checkers
wget "https://storage.ptsecurity.com/seafhttp/f/af11043a84e94544a6e9/?op=download" -O ~/checkers/checker_wazuh_vmp
chmod +x ~/checkers/checker_wazuh_vmp
ls -la ~/checkers/
```

В выводе должен отобразиться файл **checker_wazuh_vmp** с правами на выполнение (**x** в правах доступа). Теперь чекер готов к запуску в конце практики.

##### Подключение и настройка Wazuh

Переходим к настройке сервера мониторинга. Все следующие команды выполняются на Wazuh-Server (192.168.250.10).

Обновляем список пакетов и устанавливаем необходимые зависимости. Команда **sudo apt update** обновляет индекс пакетов, а **sudo apt upgrade** обновляет установленные пакеты:

```
sudo apt update && sudo apt upgrade -y
sudo apt install apt-transport-https lsb-release wget curl -y
```

Запустился процесс обновления.

Далее скачиваем и запускаем установочный скрипт. Команда **wget** с флагом **-qO -** загружает скрипт и передает его в bash для выполнения. Флаги **-a -i** означают установку всех компонентов в автоматическом режиме: `wget -qO - https://packages.wazuh.com/4.7/wazuh-install.sh | sudo bash -s -- -a -i`

Начинается процесс установки: загрузка пакетов, настройка Wazuh Indexer, Dashboard и Manager.

![](../../_images/4b8e6f907c61.webp)

После завершения видны логин **admin** и сгенерированный пароль администратора. **Сохраните этот пароль** - он понадобится для входа в веб-интерфейс.

После установки все пароли хранятся в архиве **wazuh-install-files.tar** в домашней директории. Рекомендуется сохранить их в надежное место. Для просмотра всех паролей выполните: `sudo tar -O -xf ~/wazuh-install-files.tar wazuh-install-files/wazuh-passwords.txt`

Теперь переходим к настройке агента. Все следующие команды выполняются на Wazuh-Agent (192.168.250.11). Обновим систему и установим пакеты:

```
sudo apt update && sudo apt upgrade -y
sudo apt install wget lsb-release -y
sudo apt install rsyslog -y
sudo systemctl enable rsyslog
sudo systemctl start rsyslog
```

Проверяем связь с сервером. Команда **ping** отправляет запросы и показывает время отклика: `ping -c 3 192.168.250.10`

![](../../_images/ce24cc6be189.webp)

На изображении виден успешный ответ от сервера: 3 пакета отправлено, 3 получено, 0% потерь. Это подтверждает, что сеть между ВМ настроена корректно.

Переходим к добавлению агента в Wazuh. Открываем в браузере [**https://127.0.0.1:8443**](https://127.0.0.1:8443) и авторизуемся (**admin** и пароль из шага установки сервера). Чтобы добавить агента перейдем на страницу: **Agents** -> **Deploy new agent**.

Если при входе в веб-интерфейс возникает ошибка **API version timeout** или **API connection No API available to connect**, необходимо увеличить таймаут в конфигурации Dashboard. Это актуально при работе на виртуальных машинах с ограниченными ресурсами. Для исправления отредактируйте конфигурационный файл через `sudo nano /usr/share/wazuh-dashboard/data/wazuh/config/wazuh.yml` и добавьте параметр **timeout** над секцией **hosts**: **timeout: 120000**

Сохраните файл (Ctrl+O, Enter) и выйдите (Ctrl+X). Затем перезапустите Dashboard:

```
sudo systemctl restart wazuh-dashboard
sleep 30
```

На главной странице будет предложено добавить агента, нажмём на кнопку **Add agent**.

![](../../_images/2481ab47c907.webp)

Также добавить агента можно в меню **Agents**. Откроем выпадающий список в хедере сервиса и выберем вкладку Agents

![](../../_images/7a76dad815e5.webp)

Далее заполняем параметры:

- **Operating system:** **Linux DEB**

![](../../_images/5f3497393c2d.webp)
- **Server address:** **192.168.250.10**

![](../../_images/89403f811414.webp)
- **Agent name:** **wazuh-agent-vm2**

![](../../_images/932f8b0f4bce.webp)

Копируем команду из пункта 4 страницы **Deploy new agent**

![](../../_images/0f0e5bd23d13.webp)

И вставляем скопированную команду в консоль Wazuh-Agent:

```
wget https://packages.wazuh.com/4.x/apt/pool/main/w/wazuh-agent/wazuh-agent_4.7.5-1_amd64.deb && sudo WAZUH_MANAGER='192.168.250.10' WAZUH_AGENT_NAME='wazuh-agent-vm2' dpkg -i ./wazuh-agent_4.7.5-1_amd64.deb 
```

![](../../_images/91f7b5163e9b.webp)

На изображении виден процесс установки: скачивание .deb-пакета, распаковка и настройка wazuh-agent.

Запускаем службу агента и включаем автозагрузку:

```
sudo systemctl daemon-reload
sudo systemctl enable wazuh-agent
sudo systemctl start wazuh-agent
```

Проверяем статус службы. Команда **systemctl status** показывает состояние сервиса: `sudo systemctl status wazuh-agent`

![](../../_images/bee2e13a1793.webp)

На изображении виден статус сервиса: зеленая точка и надпись "active (running)" означают, что агент работает. Отображаются также PID процесса и использование ресурсов. Ждем 2 минуты для завершения подключения агента к серверу.

Откроем веб-интерфейс и проверим статус агента. Для этого вренемся на страницу **Deploy new agent** и нажмем **Refresh**.

![](../../_images/b5103a3d66f5.webp)

На изображении виден список агентов: **wazuh-agent-vm2** со статусом **Active**, IP **192.168.250.11**, версия **v4.7.5**. Это подтверждает, что агент зарегистрирован и отправляет данные.

**FIM (File Integrity Monitoring)** - модуль контроля целостности файлов. При первом сканировании Wazuh сохраняет исходное состояние файлов в отслеживаемых директориях: их контрольные суммы и метаданные. К метаданным относятся размер файла, владелец, группа, права доступа, время изменения и другие атрибуты.

При последующих проверках FIM сравнивает текущее состояние файлов с сохранённым. Так Wazuh может обнаружить:

- создание нового файла;
- изменение содержимого файла;
- изменение его владельца, прав доступа и других атрибутов;
- удаление файла.

Если FIM обнаруживает изменение, агент передаёт информацию о нём на Wazuh Manager. Там событие обрабатывается правилами и при необходимости преобразуется в оповещение. Сам FIM не запрещает изменение и не восстанавливает файл – он обнаруживает и регистрирует произошедшее.

По умолчанию Wazuh отслеживает системные директории **/etc**, **/usr/bin**, **/usr/sbin**, **/bin** и **/sbin**. В рамках кейса мы добавим директорию **/tmp** в конфигурацию агента. Это позволит безопасно создавать, изменять и удалять тестовые файлы, не затрагивая критичные системные данные.

Открываем конфигурационный файл агента в редакторе **nano**: `sudo nano /var/ossec/etc/ossec.conf`

Находим секцию **&lt;syscheck>** и добавляем строку для мониторинга **/tmp**: **&lt;directories check_all="yes" realtime="yes">/tmp&lt;/directories>**

Параметры этой строки определяют режим мониторинга:

- `check_all="yes"` – Wazuh сохраняет и проверяет все поддерживаемые атрибуты файлов: контрольные суммы MD5, SHA-1 и SHA-256, размер, владельца, группу, права доступа, время изменения и inode;
- `realtime="yes"` – изменения в директории отслеживаются непрерывно. Благодаря этому создание, изменение или удаление файла будет обнаружено сразу, без ожидания следующей плановой проверки.

![](../../_images/81c1114f84d0.webp)

На изображении видно отредактированный файл: добавлена строка с директорией **/tmp** и параметрами **check_all** и **realtime**.

Прежде чем добавлять мониторинг **auth.log**, разберемся, как Wazuh обрабатывает сырые текстовые логи и извлекает из них структурированные данные для анализа. За это отвечают два компонента: **кодеры** на стороне агента и **декодеры** на стороне сервера.

Задача кодера - преобразовать сырые логи в формат, понятный для передачи на сервер. Когда агент читает строку из файла лога, кодер упаковывает её в специальный формат вместе с метаданными (временная метка, имя агента, тип лога) и отправляет в Wazuh Manager.

Декодер извлекает структурированные данные из полученных логов. Например, для лога SSH декодер извлечет IP-адрес источника, имя пользователя и тип события (успешный вход, неудачная попытка и т.д.). Эти структурированные данные затем могут использоваться правилами для анализа, которые определяют является ли событие инцидентом безопасности.

Для мониторинга входа по SSH в разделе `<!--Log analysis -->` добавим секцию **&lt;localfile>**:

```
  <localfile>
    <log_format>syslog</log_format>
    <location>/var/log/auth.log</location>
  </localfile>
```

![](../../_images/d3f8ba83a215.webp)

> Конфигурационный файл **может выглядеть иначе**: кейс был написан для конкретной версии Wazuh, а структура файла со временем может измениться. Расположение блока не принципиально, важнее корректно соблюсти синтаксис и отступы.

Сохраняем файл и выходим. Перезапускаем агента для применения изменений: `sudo systemctl restart wazuh-agent`

Теперь сгенерируем события безопасности для проверки работы Wazuh. Вместо ручного создания единичных событий будем использовать утилиту Hydra - специализированный инструмент для автоматизированного подбора паролей. Устанавливаем ее с помощью `sudo apt install hydra -y` и создаем список паролей. Необходимо более 8 попыток, чтобы сработали правила Wazuh на обнаружение брутфорса, сделаем 30:

```
echo -e "password\n123456\nadmin\nqwerty\nletmein\nwelcome\n12345678\n123456789\n1234567890\npassword1\nadmin123\nroot\ntest\nguest\nuser\n1234567\n12345\n1234\n111111\n000000\npassw0rd\nsecret\nsuperman\nbatman\nmichael\nfootball\nshadow\nprincess\nsunshine\ntrustno1" > /tmp/passwords.txt
```

Запускаем Hydra для подбора пароля по SSH. Это сгенерирует множественные неудачные попытки входа, которые зафиксируются в auth.log, впишем команду `hydra -l invalid_user -P /tmp/passwords.txt ssh://127.0.0.1 -t 1` в консоль.

![](../../_images/9f340e99c256.webp)

На изображении виден процесс работы Hydra: утилита последовательно перебирает пароли из списка, генерируя множественные неудачные попытки входа. Команда выполняется около 4 минут из-за защитных механизмов SSH-сервера.

> Hydra запускается с флагом **-t 1** (один поток), чтобы SSH-сервер успевал обрабатывать и логировать каждую попытку. Это гарантирует, что все события попадут в auth.log и будут корректно обработаны Wazuh.

Создаем файл в отслеживаемой директории: `echo "WAZUH FIM TEST $(date)" | sudo tee /tmp/wazuh_fim_test.txt`

![](../../_images/f8b6ac0d687c.webp)

На изображении видно создание файла с тестовым содержимым и подтверждение записи. Подождем 15-20 секунд для обработки событий сервером.

Посмотрим, появилось ли событие о подборе паролей в Wazuh. Перейдем в **Security events** и введем в фильтре **agent.ip: "192.168.250.11" AND rule.id: "5712"**. Временной диапазон: **Last 15 minutes**

![](../../_images/525121417aae.webp)

Нажимаем **Update**

![](../../_images/725c2d576e8d.webp)

На изображении видно событие брутфорса: Rule ID 5712. Это подтверждает, что Wazuh корректно детектирует атаки.

Проверим, заметил ли Wazuh добавление файла в директорию /tmp. Перейдем **Modules** -> **Integrity monitoring** и введем в фильтре **agent.ip: "192.168.250.11" AND syscheck.path: "/tmp/wazuh_fim_test.txt"**. Временной диапазон: **Last 15 minutes**.

![](../../_images/cc362018c378.webp)

Нажимаем **Update**

![](../../_images/52b7a9f2eef8.webp)

На изображении видно событие **FIM **типа **added **для созданного файла. Это означает, что агент корректно отследил создание файла и передал данные на сервер.

## Вопрос
*тип: open_answer, макс. баллов: 1, попыток: 3*
