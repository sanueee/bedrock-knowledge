## Что такое харденинг

**Харденинг (усиление защиты)** - это процесс повышения безопасности системы путем целенаправленного сокращения поверхности атаки и тонкой настройки механизмов защиты.

**Поверхность атаки** - это совокупность точек входа и уязвимых мест, через которые потенциально возможен несанкционированный доступ к системе или данным. Размер этой поверхности напрямую зависит от количества активных сервисов, открытых сетевых портов, объема выданных прав пользователям и наличия известных уязвимостей в используемом программном обеспечении.

Эти определения становятся более наглядными, если применить их к конкретной конфигурации. Сравним два состояния одного и того же веб-сервера.  
До начала работ по усилению защиты на узле могут быть активны: SSH с парольной аутентификацией и разрешённым входом под учетной записью root (порт 22), FTP (21/tcp), Telnet (23/tcp), база данных, слушающая все сетевые интерфейсы (3306/tcp), и почтовый агент SMTP (25/tcp).  
После проведения харденинга остаются лишь две необходимые точки входа: 443/tcp для работы веб-приложения и 22/tcp для SSH. При этом SSH использует строгую аутентификацию по ключам и принимает соединения исключительно с доверенных IP-адресов администраторов. В результате поверхность атаки сокращается как количественно (меньше точек входа), так и качественно (ужесточаются условия доступа к оставшимся).

> Основная цель харденинга состоит в разумном снижении вероятности компрометации системы за счет блокировки известных векторов атак и существенного усложнения процесса несанкционированного проникновения.

Ключевые задачи этого процесса включают:

- **Снижение рисков:** минимизация вероятности успешной атаки путем устранения уязвимостей и конфигурационных ошибок.
- **Ограничение потенциального ущерба:** локализация последствий в случае компрометации (за счет сетевой сегментации, принципа минимальных привилегий и изоляции процессов).
- **Соответствие стандартам:** выполнение требований отраслевых стандартов (например, CIS Benchmarks) и регуляторных норм (PCI DSS, HIPAA, GDPR, ФЗ-152).

Харденинг логично применять на нескольких уровнях, создавая эшелонированную оборону:

|Уровень|Описание|Примеры мер|
|---|---|---|
|**Физический**|Ограничение физического доступа к оборудованию|Контроль доступа в дата-центр, установка паролей на BIOS/UEFI, шифрование дисков|
|**Сетевой**|Фильтрация и контроль сетевого трафика|Межсетевые экраны, сегментация сети, VPN, системы обнаружения и предотвращения вторжений (IDS/IPS)|
|**Виртуализации и контейнеров**|Изоляция рабочих нагрузок|Настройка гипервизоров, ограничение прав контейнеров, использование стандартов безопасности подов (PSS) и приёмного контроля (PSA)|
|**Операционной системы**|Настройка ядра, служб и прав доступа|Отключение неиспользуемых служб, настройка SELinux/AppArmor, строгое управление учётными записями|
|**Прикладной**|Безопасная конфигурация приложений|Специфическая настройка веб-серверов и баз данных, отключение избыточного функционала|

В качестве примера комплексного применения рассмотрим условный учебный веб-портал. На физическом уровне здесь используются шифрование дисков (LUKS) и пароль на BIOS/UEFI. На сетевом уровне межсетевой экран пропускает только трафик на порту 443, а доступ администраторов осуществляется по SSH через выделенный транзитный узел (jump host). На уровне контейнеризации приложение работает без повышенных привилегий, с корневой файловой системой, смонтированной только для чтения. На уровне ОС служба запущена от изолированной учётной записи без возможности интерактивного входа, при этом включен принудительный контроль доступа. На прикладном уровне в веб-сервере отключён вывод списка файлов каталогов, а база данных принимает соединения исключительно с локального узла.

Уровни логично дополняют друг друга: многоуровневая защита усложняет задачу потенциального нарушителя, так как преодоление одного барьера не дает доступа ко всей системе.

Реализация мер безопасности на перечисленных уровнях осуществляется с применением различных методологий. Базовым и наиболее фундаментальным подходом остается ручное конфигурирование.

## Ручной харденинг

**Ручной харденинг** - это подход, при котором системный администратор или инженер по безопасности применяет чек-листы настроек на каждом сервере вручную, опираясь на авторитетные руководства (такие как CIS Benchmarks) и внутренние технические требования.

Такой метод позволяет добиться высокой точности настроек и гибко адаптировать параметры под уникальные задачи. Однако его применение требует пропорциональных временных затрат при масштабировании и в значительной степени зависит от квалификации и внимательности исполнителя.

Основные направления ручного усиления защиты:

|Направление|Описание|Примеры мер|
|---|---|---|
|**Управление доступом**|Контроль аутентификации и авторизации|Запрет прямого входа под root, обязательная аутентификация по SSH-ключам, настройка sudo с минимально необходимыми привилегиями, блокировка учётных записей после серии неудачных попыток входа|
|**Управление сервисами**|Минимизация запущенных служб|Отключение неиспользуемых демонов (FTP, telnet, почтовых агентов), настройка автозапуска только критически важных сервисов|
|**Сетевая безопасность**|Контроль сетевого трафика|Настройка nftables (или iptables) с политикой "запрещено всё, что не разрешено явно", ограничение исходящих соединений|
|**Защита файловой системы**|Контроль целостности и прав доступа|Установка строгих прав на системные файлы (**/etc/passwd**, **/etc/shadow**), использование ACL, настройка атрибута неизменяемости (immutable) для ключевых конфигураций|
|**Принудительный контроль (MAC)**|Mandatory Access Control|Настройка SELinux в режиме enforcing (семейства RHEL/Fedora) или AppArmor (Debian/Ubuntu/SUSE) с применением ограничивающих профилей для сервисов|
|**Криптография**|Шифрование и защита данных|Использование TLS 1.2+ для сетевых соединений, шифрование дисков (LUKS), отключение устаревших алгоритмов (MD5, SHA1, RC4)|
|**Аудит и логирование**|Сбор и защита журналов событий|Настройка **auditd**, централизованная отправка логов на защищенный сервер, предотвращение несанкционированного изменения журналов|
|**Управление уязвимостями**|Своевременное применение исправлений|Настройка автоматических обновлений безопасности, регулярный аудит установленных пакетов|

> В качестве практического ориентира по ручному усилению защиты часто используется репозиторий [How-To-Secure-A-Linux-Server](https://github.com/imthenachoman/How-To-Secure-A-Linux-Server). Этот ресурс представляет собой подробный пошаговый чек-лист, охватывающий различные уровни: от физической безопасности и разметки дисков до тонкой настройки параметров ядра и систем мониторинга.

Ручной харденинг оправдан в инфраструктурах с небольшим количеством узлов или в уникальных системах, требующих ювелирной настройки. В крупных и динамичных средах этот метод целесообразно автоматизировать, чтобы избежать чрезмерных временных затрат и риска рассинхронизации конфигураций.

## Автоматизированный харденинг

По мере роста инфраструктуры ручной подход становится трудоемким. Автоматизация необходима для предотвращения пропуска этапов настройки и минимизации риска конфигурационного дрейфа (ситуации, когда настройки серверов со временем начинают расходиться из-за ручных вмешательств, локальных обновлений или изменений в окружении).

Конфигурационный дрейф хорошо иллюстрирует типичная рабочая ситуация: инженер временно открыл порт 8080 на продуктивном узле для отладки и забыл отменить правило. Без автоматизации это правило может оставаться действующим месяцами, создавая скрытую уязвимость. При использовании средств управления конфигурациями правило, не описанное в коде, будет удалено при следующем плановом прогоне, а при включенном контроле целостности файлов любое несанкционированное изменение немедленно породит оповещение. Этот процесс - от накопления отклонений до возврата к эталону - схематично представлен ниже.

![](../../_images/d721dfdbb84e.webp)

Таким образом, средства управления конфигурациями не исключают сам факт ручного вмешательства, но позволяют своевременно выявлять подобные отклонения и возвращать систему к утвержденному эталонному состоянию.

Автоматизированный харденинг реализуется с помощью специализированных инструментов, которые условно можно разделить на две категории.

**1. Средства аудита и оценки соответствия**

Эти инструменты сканируют систему и сравнивают её текущую конфигурацию с эталонными профилями безопасности.

|Инструмент|Описание|Особенности|
|---|---|---|
|[**Lynis**](https://github.com/CISOfy/lynis)|Инструмент аудита безопасности для Unix-подобных систем|Анализирует параметры, выдаёт рекомендации с указанием приоритетов, рассчитывает индекс защищённости. Запускается локально, не требует постоянного агента|
|[**OpenSCAP**](https://github.com/OpenSCAP/openscap)|Инструмент проверки соответствия стандартам|Поддерживает профили SCAP, включая CIS Benchmarks, STIG, PCI-DSS. Генерирует подробные отчёты и способен автоматически исправлять часть несоответствий|
|[**CIS-CAT**](https://www.cisecurity.org/cybersecurity-tools/cis-cat-pro)|Сканер от Center for Internet Security|Сравнивает конфигурацию с эталонными CIS Benchmarks. Результаты часто используются для последующего исправления через средства управления конфигурациями|
|[**Wazuh**](https://github.com/wazuh/wazuh)|Платформа мониторинга безопасности|Агрегирует данные с агентов, проверяет соответствие стандартам, отслеживает целостность файлов (FIM) и помогает обнаруживать уязвимости|
|[**kernel-hardening-checker**](https://github.com/a13xp0p0v/kernel-hardening-checker)|Проверка параметров харденинга ядра Linux|Сравнивает опции Kconfig, параметры загрузки и sysctl с рекомендациями KSPP (Kernel Self Protection Project). Работает без агента|

**2. Средства управления конфигурациями**

Эти инструменты применяют и поддерживают заданное состояние системы, описанное в виде кода (концепция "Инфраструктура как код", IaC).

|Инструмент|Описание|Особенности|
|---|---|---|
|[**Ansible**](https://github.com/ansible/ansible)|Система управления на основе SSH|Использует декларативные сценарии (плэйбуки) на YAML. Имеет готовые роли для харденинга. Архитектура без агентов|
|[**Puppet**](https://github.com/puppetlabs/puppet)|Система с агент-серверной архитектурой|Использует собственный декларативный язык. Поддерживает модули для харденинга. Хорошо подходит для крупных инфраструктур|
|[**Chef**](https://github.com/chef/chef)|Система на основе Ruby|Использует модули конфигурирования, описанные на Ruby. Обладает богатой экосистемой готовых рецептов|
|[**SaltStack**](https://github.com/saltstack/salt)|Система управления и оркестрации|Написана на Python, поддерживает как агентную, так и безагентную архитектуры. Эффективна в больших и динамичных средах|

Взаимодействие управляющего узла с целевыми серверами может быть организовано двумя основными способами:

![](../../_images/a9214a382235.webp)

Схема без агентов упрощает первоначальное развертывание, так как на серверах не требуется устанавливать дополнительное ПО. Агент-серверная схема, в свою очередь, обеспечивает более надежное непрерывное поддержание состояния и чаще применяется в крупных корпоративных инфраструктурах.

Использование IaC позволяет тиражировать эталонную конфигурацию на каждый новый сервер. Если конфигурационные файлы были изменены вручную, инструмент управления при следующем запуске (или в режиме непрерывного применения) вернет их к заданному состоянию.

> Важно отметить, что перед применением автоматизированных профилей в продуктивной среде требуется их тщательное тестирование в изолированном окружении. Отдельные строгие правила (в частности, CIS Level 2) могут потенциально ограничить работу специфических приложений или усложнить легитимный доступ администраторов.

Для выбора оптимальной стратегии защиты необходимо учитывать характеристики обоих методов.

## Сравнение подходов

Выбор между ручным и автоматизированным подходами редко бывает однозначным и зависит от масштаба инфраструктуры, требований к безопасности и доступных ресурсов команды.

|Критерий|Ручной харденинг|Автоматизированный харденинг|
|---|---|---|
|**Скорость внедрения**|Относительно низкая: требует времени на настройку каждого сервера|Высокая: после отладки конвейера применяется ко всем серверам параллельно|
|**Вероятность человеческой ошибки**|Повышенная: возможны опечатки или пропущенные шаги|Сниженная: при условии предварительной проверки на стенде и поэтапного раската|
|**Масштабируемость**|Линейный рост временных затрат|Параллельное применение к сотням и тысячам серверов|
|**Контроль дрейфа конфигураций**|Требует дополнительных процедур и ручных проверок|Встроенный: инструменты помогают возвращать систему к эталону|
|**Порог входа**|Требует глубокого знания ОС и файлов конфигурации|Требует знания инструмента автоматизации и структуры профилей|
|**Гибкость**|Высокая: легко внести точечное исключение для конкретного сервера|Средняя: требует написания условий в коде или создания отдельных профилей|
|**Воспроизводимость**|Зависит от конкретного исполнителя|Код версионируется и может быть точно воспроизведён|
|**Стоимость владения**|Время инженера на рутинные операции|Время на разработку, поддержку кода и инфраструктуру автоматизации|

Следует учитывать, что ошибка в скрипте автоматизации может тиражироваться на весь парк серверов одновременно. Поэтому изменения раскатываются поэтапно: сначала на тестовом стенде, затем на небольшой группе узлов и только потом на всей инфраструктуре. Кроме того, автоматизация не отменяет необходимости фундаментального знания операционной системы: инженер должен четко понимать, какие именно изменения вносят применяемые профили.

На практике часто используется гибридная модель: базовый автоматизированный харденинг разворачивается на все серверы через Ansible или OpenSCAP, а специфические требования для отдельных ролей (например, для узлов баз данных или кластеров Kubernetes) настраиваются вручную, тестируются и затем интегрируются в общие автоматизированные конвейеры.

Процесс усиления защиты сервера - это не разовое мероприятие, а непрерывный цикл, который повторяется по мере изменения инфраструктуры и эволюции ландшафта угроз. Последовательность этапов представлена ниже.

![](../../_images/9048724d0653.webp)

Благодаря этапу возврата цикл не завершается на фазе внедрения: данные мониторинга и изменения в инфраструктуре закономерно запускают новый виток аудита и корректировки настроек.

Рассмотрим каждый этап подробнее.

**Этап 1: Оценка текущего состояния**

Перед внесением любых изменений проводится объективная оценка текущего уровня безопасности. Запускается сканирование системы с помощью Lynis, OpenSCAP или аналогичного инструмента. Анализатор изучает конфигурацию и формирует отчет с перечнем выявленных несоответствий и рекомендациями.

Типичные выявляемые несоответствия могут включать:

- Отсутствие настроенных автоматических обновлений безопасности.
- Использование устаревших протоколов и алгоритмов хеширования (TLS 1.0, MD5).
- Неоптимальные параметры конфигурации ядра.
- Открытые, но неиспользуемые порты (например, 21/FTP, 23/Telnet).
- Отсутствие ограничений на количество попыток ввода пароля.
- Избыточные права доступа к системным файлам (например, **/etc/shadow** доступен для чтения широкому кругу пользователей).
- Отключенные или работающие в разрешительном режиме SELinux/AppArmor.

**Этап 2: Формирование базового профиля**

На данном этапе настраиваются фундаментальные параметры безопасности:

- **SSH:** отключается парольная аутентификация, разрешается вход только по ключам, запрещается прямой вход для root, настраивается ограничение попыток входа (через fail2ban или механизмы PAM).
- **Межсетевой экран:** настраивается nftables (или iptables) с политикой "запрещено всё, что не разрешено явно", открываются только необходимые порты (например, 22/TCP для SSH с определенных IP, 80/443 для веб-сервера).
- **Обновления:** настраивается автоматическая установка патчей безопасности (например: unattended-upgrades для Debian/Ubuntu и dnf-automatic для RHEL/CentOS).
- **Учётные записи:** блокируются или удаляются неиспользуемые учётные записи, настраиваются политики сложности паролей через PAM.

**Этап 3: Применение отраслевых стандартов**

С помощью инструментов автоматизации применяется утвержденный профиль безопасности, например CIS Benchmark Level 1 или Level 2.

Инструмент проверяет и приводит к эталонному виду:

- Права на файлы в системных директориях (**/etc**, **/var**, **/usr**).
- Настройки ядра через sysctl (отключение пересылки IP-пакетов, включение SYN cookies, ограничение ICMP).
- Настройки PAM (модули аутентификации, ограничение сессий).
- Конфигурации SSH, FTP, SMTP и других сетевых сервисов.
- Правила аудита (auditd).

Создание резервных копий конфигурационных файлов перед внесением изменений остается обязательной практикой для обеспечения возможности быстрого отката.

**Этап 4: Верификация и непрерывный мониторинг**

После применения настроек сканирование запускается повторно для проверки роста индекса безопасности (в случае с Lynis) или сокращения количества несоответствий (для OpenSCAP).

Далее выстраивается система постоянного мониторинга:

- **Контроль целостности файлов (FIM):** система аудита (Wazuh, OSSEC, AIDE) отслеживает несанкционированные изменения в критически важных файлах.
- **Централизованное логирование:** журналы событий отправляются на выделенный защищенный сервер для долгосрочного хранения и анализа.
- **Обнаружение аномалий:** настройка правил для фиксации подозрительной активности (массовые неудачные попытки входа, запуск нестандартных процессов).
- **Регулярное сканирование:** автоматический запуск аудиторов по расписанию для выявления нового конфигурационного дрейфа.

Администратор получает оповещения об отклонениях от утвержденного эталона и может оперативно реагировать на потенциальные инциденты.

Харденинг формирует надежный фундамент безопасности, на который в дальнейшем интегрируются системы мониторинга, логирования и реагирования на инциденты. Грамотное сочетание ручных методов настройки и современных автоматизированных инструментов обеспечивает стабильное и защищенное функционирование IT-инфраструктуры. Для закрепления полученных знаний перейдем к практике.

Практика посвящена комплексному аудиту безопасности сервера и устранению найденных нарушений. Работа строится по циклу "аудит - исправление - верификация": сначала мы снимаем базовые показатели двумя независимыми инструментами, **Lynis** и **OpenSCAP**, затем устраняем нарушения и подтверждаем улучшения повторным сканированием.

Чтобы OpenSCAP мог проверять систему не "в целом", а по готовому эталону безопасности, сначала скачиваем актуальные SCAP-профили. Создаем рабочую директорию командой **mkdir -p** (флаг **-p** создает всю цепочку каталогов и не выдает ошибку, если они уже существуют), скачиваем архив SCAP Security Guide утилитой **wget -q** в тихом режиме, распаковываем его командой **tar -xzf** и проверяем результат командой **ls -lh**:

```bash
mkdir -p ~/scap-content && cd ~/scap-content
wget -q https://github.com/ComplianceAsCode/content/releases/download/v0.1.81/scap-security-guide-0.1.81.tar.gz
tar -xzf scap-security-guide-0.1.81.tar.gz
cd ~
ls -lh ~/scap-content/scap-security-guide-0.1.81/ssg-debian12-ds.xml
```

![](../../_images/ad2860355397.webp)

На изображении виден вывод **ls -lh**: файл **ssg-debian12-ds.xml** имеет размер около 15 МБ - это готовый профиль безопасности (datastream) для Debian 12, по которому OpenSCAP будет выполнять сканирование.

После Lynis запускаем второй независимый аудит - OpenSCAP. Это комплаенс-сканер, который проверяет систему по готовому SCAP-профилю, скачанному на нулевом этапе. Создаем директорию для отчетов и запускаем сканирование: флаг **--profile** выбирает стандартный профиль безопасности для Debian 12, **--results** сохраняет результаты в XML, а **--report** строит наглядный HTML-отчет:

mkdir -p ~/audit-reports
sudo oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_standard --results ~/audit-reports/openscap-baseline.xml --report ~/audit-reports/openscap-baseline.html ~/scap-content/scap-security-guide-0.1.81/ssg-debian12-ds.xml

ssh -L 8080:127.0.0.1:8080 -p 2222 pt-intern@127.0.0.1

python3 -m http.server 8080

Сначала восстанавливаем корректные права на /etc/shadow. Режим **640** означает: владелец (root) читает и пишет, группа shadow только читает, все остальные не имеют доступа вовсе:

```bash
sudo chmod 640 /etc/shadow
ls -l /etc/shadow
```

![](../../_images/249f64073fad.webp)

На изображении видны новые права **-rw-r----- root shadow** - доступ к хэшам паролей ограничен.

Устанавливаем rsyslog, чтобы системные логи снова писались на диск - это нужно и для расследования инцидентов, и для выполнения правил OpenSCAP. Команда **systemctl enable --now** сразу добавляет службу в автозагрузку и запускает ее:

```bash
sudo apt update
sudo apt install -y rsyslog
sudo systemctl enable --now rsyslog
sudo systemctl status rsyslog --no-pager
```

![](../../_images/a12257c12db2.webp)

На изображении виден статус службы **active (running)** и включенная автозагрузка.

Отключаем дампы памяти для setuid-программ: командой **sed -i** заменяем значение 1 на 0 прямо в файле конфигурации, а **sysctl --system** перечитывает все настройки sysctl:

```bash
sudo sed -i 's/fs.suid_dumpable = 1/fs.suid_dumpable = 0/' /etc/sysctl.d/99-custom.conf
sudo sysctl --system
sudo sysctl fs.suid_dumpable
```

![](../../_images/52e94a7fecfc.webp)

На изображении видно значение **fs.suid_dumpable = 0** - параметр приведен к безопасному значению.

Блокируем учетную запись тестового пользователя: **passwd -l** "запирает" хэш пароля восклицательным знаком, после чего вход становится невозможен, но сама учетная запись не удаляется:

```bash
sudo passwd -l user_practice
sudo getent shadow user_practice
```

![](../../_images/ed3cc311b7ae.webp)

На изображении видно, что в поле хэша появился префикс "!" - учетная запись заблокирована.

Дополнительно запрещаем вход по SSH с пустым паролем на уровне конфигурации: **sed** раскомментировал строку и выставил значение **no**, а **grep** наглядно показывает результат:

```bash
sudo sed -i 's/^#*PermitEmptyPasswords.*/PermitEmptyPasswords no/' /etc/ssh/sshd_config
grep -i "^PermitEmptyPasswords" /etc/ssh/sshd_config
```

![](../../_images/0267aa7b2dff.webp)

На изображении видна строка **PermitEmptyPasswords no** в конфигурации SSH.

Перезапускаем SSH-сервер, чтобы новая настройка вступила в силу, и убеждаемся, что служба корректно поднялась и мы не потеряли доступ к серверу:

```bash

sudo systemctl status ssh --no-pager
```

![](../../_images/3b048028a7b2.webp)

На изображении виден статус ssh **active (running)** - конфигурация применена, доступ сохранен.

Устраняем telnet: удаляем его строку из /etc/inetd.conf, перезапускаем inetd и полностью удаляем пакет telnet-сервера. Используем **apt purge** вместо remove, чтобы вместе с пакетом удалились и его конфигурационные файлы, а **autoremove** очищает ставшие ненужными зависимости. Контрольная команда **ss** должна показать, что порт 23 больше не слушается:

```bash
sudo sed -i '/telnet/d' /etc/inetd.conf
sudo systemctl restart inetutils-inetd
sudo apt purge -y inetutils-telnetd
sudo apt autoremove -y
ss -tulpn | grep :23
```

Последняя команда не выводит ничего - порт закрыт, telnet устранен из системы.

Устанавливаем средства активной защиты. **fail2ban** анализирует журналы входа и автоматически блокирует адреса, с которых поступает слишком много неудачных попыток, - это защита от перебора паролей:

```bash
sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban
sudo systemctl status fail2ban --no-pager
```

![](../../_images/beab917e52fb.webp)

На изображении виден статус fail2ban **active (running)**.

![](../../_images/72e9903fc66a.webp)

На изображении виден список jail: по умолчанию включен jail **sshd**, который отслеживает попытки входа по SSH.

Устанавливаем **auditd** - подсистему аудита уровня ядра, которая журналирует события, важные для безопасности (обращения к файлам, изменения учетных записей и т.д.):

![](../../_images/44511e9b3da1.webp)
