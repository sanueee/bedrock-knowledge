Когда вы дважды щёлкаете по ярлыку программы или запускаете исполняемый файл командой **./my_program**, в системе появляется работающая программа. До запуска **my_program** - это просто исполняемый файл на диске. Он не использует процессорное время, не имеет PID и не отображается в списке процессов. После запуска операционная система создаёт для него **процесс**, выделяет ресурсы и начинает выполнять инструкции программы.
Работающая программа может состоять далеко не из одной последовательности действий. Например, браузер одновременно загружает страницы, обрабатывает ввод с клавиатуры, воспроизводит видео и обновляет интерфейс. Для этого внутри одного процесса могут работать несколько потоков.

##### Процесс и поток

Процесс и поток тесно связаны между собой, но отвечают за разные вещи.

**Процесс** - это запущенная программа вместе с ресурсами, которые операционная система выделила для её работы. У процесса есть собственное адресное пространство, права доступа, открытые файлы, идентификатор и другие свойства.

**Поток** - это отдельная последовательность выполнения внутри процесса. Планировщик операционной системы выделяет процессорное время именно потокам, которые выполняют инструкции программы.

У каждого процесса есть хотя бы один поток. Он появляется вместе с процессом и обычно называется **главным потоком**. Если программе нужно выполнять несколько задач одновременно, она создаёт дополнительные потоки.
Например, программа может копировать большой файл. Один поток читает данные с диска, второй записывает их в новый файл, а третий обновляет индикатор выполнения. Все они относятся к одному процессу и работают с общими данными.

Потоки одного процесса используют общие ресурсы:

- код программы;
- виртуальное адресное пространство;
- глобальные переменные и данные в куче;
- открытые файлы;
- текущую директорию;
- права доступа процесса.

При этом у каждого потока есть собственные:

- стек с локальными переменными и историей вызовов функций;
- набор регистров процессора;
- состояние выполнения;
- идентификатор потока.

Получается, что процесс создаёт изолированную среду для программы, а потоки выполняют работу внутри этой среды. Разные процессы по умолчанию не могут обращаться к памяти друг друга. Поэтому ошибка в одной программе обычно не приводит к падению остальных. Потоки, напротив, используют общую память, поэтому должны аккуратно работать с общими данными.

Например, два потока одновременно увеличивают один счётчик. Оба могут прочитать старое значение, увеличить его на единицу и записать одинаковый результат. В итоге счётчик увеличится только один раз, хотя оба потока выполнили операцию. Такую ситуацию называют **состоянием гонки** или **race condition**. Для защиты общих данных разработчики используют механизмы синхронизации, например блокировки.

Состояние гонки - не просто неприятная ошибка, из-за которой программа может выдать неверный результат. В системах, от которых зависит безопасность людей, последствия могут быть намного серьёзнее.

> Один из известных примеров - аппарат лучевой терапии **Therac-25**. В 1985-1987 годах с ним произошло шесть известных аварий, связанных с передозировками радиации. Исследователи установили, что важную роль в происшествиях сыграли ошибки многозадачного кода, включая **состояния гонки** при работе с общей памятью. Из-за этого в некоторых случаях аппарат мог перейти в опасное состояние и выдать пациенту значительно большую дозу излучения, чем было назначено оператором.

##### Как запускается программа

После входа в систему в виртуальной машине уже работает командная оболочка **bash**. Она сама является процессом и ожидает команды пользователя. Выполним команду: `./my_program`. В этом случае **bash** обычно запускает отдельный дочерний процесс для программы **my_program**. Упрощённо запуск выглядит так:

1. Командная оболочка **bash** вызывает системный вызов **fork()** и создаёт дочерний процесс. Исходный процесс называют **родительским**, а созданный - **дочерним**.
2. Дочерний процесс получает собственный PID. Сначала он похож на копию родительского процесса **bash**.
3. Дочерний процесс вызывает системный вызов **execve()**. Его содержимое заменяется программой **my_program**, при этом PID процесса сохраняется.
4. Ядро добавляет процесс в планировщик. Главный поток программы начинает получать процессорное время и выполнять инструкции.

После завершения программа возвращает код завершения. Для обычной команды, запущенной без **&**, родительский процесс **bash** получает этот код с помощью **wait()**. Так отображается родительский и дочерний процесс в утилите **ps**, о которой мы поговорим позже.

![](../../_images/a241671f03d9.webp)

На этом этапе у процесса появляются основные свойства:

- **PID** - уникальный идентификатор процесса;
- **PPID** - идентификатор родительского процесса;
- владелец процесса, определяемый UID и GID;
- собственное виртуальное адресное пространство;
- один или несколько потоков;
- состояние, по которому ядро определяет, выполняется процесс или ожидает какое-либо событие.

Команда **./my_program** запускает отдельный процесс, потому что **my_program** - внешняя программа.
С некоторыми встроенными командами оболочки ситуация отличается. Например, команда **cd** изменяет текущую директорию самой оболочки **bash**. Если бы **cd** выполнялась в дочернем процессе, после его завершения оболочка осталась бы в прежней директории. Поэтому **bash** выполняет **cd** внутри собственного процесса.

##### Завершение процесса

Когда программа заканчивает работу, её процесс завершает выполнение. Память, открытые файлы и большинство других ресурсов освобождаются. При этом родительский процесс всё ещё должен получить код завершения дочернего процесса. Для этого используются системные вызовы **wait()** и **waitpid()**.

Иногда родительский процесс завершается раньше дочернего. Например, программа запустила фоновую задачу и завершилась, пока задача продолжает работать. Такой дочерний процесс называют **сиротским процессом** *(orphan process)*. Такой процесс не является ошибкой сам по себе. Операционная система назначает ему нового родителя. Обычно эту роль получает процесс с PID 1, которым в большинстве Linux-систем является **systemd**.
Другая ситуация возникает, когда дочерний процесс уже завершился, но родитель ещё не получил его код завершения. Такой процесс называют **зомби-процессом**.

Зомби-процесс больше не выполняет код и не использует память завершившейся программы. В таблице процессов остаётся только минимальная запись с PID и кодом завершения. Она нужна родительскому процессу, чтобы узнать результат работы дочернего процесса.
Зомби-процесс нельзя завершить сигналом, потому что он уже завершён. Чтобы запись исчезла, родительский процесс должен вызвать **wait()**. Если родительский процесс не делает этого, его обычно приходится исправлять, перезапускать или завершать.

##### Наблюдаем за процессами и потоками

Для просмотра процессов используется утилита **ps**. Она показывает снимок состояния системы на момент запуска команды. Начнём с команды: `ps aux`
Команда выводит список процессов всех пользователей и показывает расширенную информацию о них.
Ключи **aux** относятся к BSD-формату записи параметров:

- **a** - показать процессы всех пользователей, связанные с терминалами;
- **u** - вывести расширенный формат с пользователем, загрузкой CPU и памяти;
- **x** - также показать процессы, не связанные с терминалом.

Вместе ключи **aux** позволяют увидеть практически все процессы в системе. Пример вывода:

```
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
pt-intern   1234  0.0  0.1  12345  6789 pts/0    Ss   10:00   0:00 -bash
pt-intern   1456  0.3  1.2 456789 54321 pts/0    Sl   10:01   0:12 ./my_program

```

Наиболее важные столбцы:

- **USER** - пользователь, от имени которого запущен процесс;
- **PID** - идентификатор процесса;
- **%CPU** - текущая загрузка процессора;
- **%MEM** - использование оперативной памяти;
- **TTY** - терминал, с которым связан процесс;
- **STAT** - состояние процесса;
- **COMMAND** - полная команда запуска процесса.

Чтобы найти конкретный процесс, вывод **ps** можно передать команде **grep**: `ps aux | grep signal_case`. Команда **grep** тоже на короткое время появится в списке процессов. Поэтому в выводе часто можно увидеть строку с самой командой поиска.
Чтобы посмотреть процессы вместе с родительскими связями, используем команду: `ps -ef --forest`

Для просмотра потоков используется команда: `ps -eLf | grep firefox`

```
UID          PID  PPID   LWP  C NLWP STIME TTY          TIME CMD
user        1234     1  1234  0    3 10:00 ?        00:00:12 /usr/lib/firefox/firefox
user        1234     1  1235  0    3 10:00 ?        00:00:03 /usr/lib/firefox/firefox
user        1234     1  1236  0    3 10:00 ?        00:00:18 /usr/lib/firefox/firefox

```

Все три строки относятся к одному процессу, потому что у них совпадает PID. При этом значения LWP различаются: каждое значение соответствует отдельному потоку. В этом выводе:

- **PID** - идентификатор процесса;
- **PPID** - идентификатор родительского процесса;
- **LWP** - идентификатор отдельного потока;
- **NLWP** - общее количество потоков в процессе;
- **CMD** - команда, которой был запущен процесс.

У **ps** есть несколько полезных параметров:

- **-e** - показать процессы всех пользователей;
- **-L** - показать потоки;
- **-f** - вывести подробный формат;
- **--forest** - показать дерево родительских процессов.

##### Состояния процессов

Процесс не обязательно постоянно использует процессор. Большую часть времени программы ожидают ввод с клавиатуры, данные из сети, ответ от диска или срабатывание таймера. В выводе `ps aux` состояние процесса отображается в столбце **STAT**. В других форматах вывода этот столбец может отсутствовать.

Первая буква показывает основное состояние процесса:

| Обозначение | Состояние | Описание |
|---|---|---|
| R | Running | Процесс выполняется или готов получить процессорное время. |
| S | Sleeping | Процесс ожидает событие: ввод, сетевые данные, таймер или завершение другой операции. |
| D | Uninterruptible sleep | Процесс ожидает завершения операции ввода-вывода, например работы с диском. |
| T | Stopped | Процесс приостановлен сигналом SIGSTOP или SIGTSTP . |
| Z | Zombie | Процесс завершился, но родитель ещё не получил его код завершения. |

После основной буквы могут отображаться дополнительные символы:

- **s** - процесс является лидером сессии;
- **l** - процесс содержит несколько потоков;
- **+** - процесс относится к активной группе процессов терминала;
- **<** - процесс работает с повышенным приоритетом;
- **N** - процесс работает с пониженным приоритетом.
   Например, значение **Sl** означает, что процесс ожидает событие и содержит несколько потоков.

Состояние процесса может меняться очень быстро. Например, веб-сервер ожидает входящий запрос в состоянии **S**, затем получает данные, переходит в состояние **R**, обрабатывает запрос и снова начинает ожидание.

##### top

Утилита **ps** показывает состояние системы только в момент запуска команды. Это похоже на фотографию: она полезна, но не показывает, что изменится через секунду. Чтобы наблюдать за процессами в реальном времени, используется утилита **top**. Запустим её командой: `top`

![](../../_images/b61c003e1de7.webp)

В верхней части окна отображается общая информация о системе: количество процессов, загрузка процессора и использование памяти. Ниже находится список процессов, который постоянно обновляется. Основные клавиши для работы с **top**:

- **1** - показать загрузку каждого ядра CPU отдельно;
- **c** - показать полную строку запуска процесса;
- **V** - включить отображение дерева процессов;
- **H** - переключить отображение потоков вместо процессов;
- **k** - отправить сигнал процессу;
- **r** - изменить значение nice;
- **u** - отфильтровать процессы по пользователю;
- **q** - выйти из программы.
   Например, если в **top** включить отображение потоков клавишей **H**, многопоточный браузер или сервер будет представлен не одной строкой, а несколькими. Так можно увидеть, какие потоки используют процессорное время.

##### Управление процессами

Иногда процесс нужно не только найти, но и остановить, перезапустить или временно приостановить. Для этого в Linux используются сигналы. **Сигнал** - это короткое уведомление, которое операционная система или другой процесс отправляет программе. Программа может обработать некоторые сигналы самостоятельно: закрыть файлы, сохранить данные или завершить текущую операцию.

Для отправки сигнала используется утилита **kill**. Название может сбивать с толку: команда **kill** не всегда завершает процесс. На самом деле она отправляет указанному процессу сигнал.

Общий вид команды: **kill -SIG_NAME &lt;PID>. **Если не указать сигнал, команда отправит **SIGTERM**.

Наиболее распространённые сигналы:

| Сигнал | Номер | Назначение |
|---|---|---|
| SIGTERM | 15 | Запрос на корректное завершение процесса. |
| SIGKILL | 9 | Принудительное завершение процесса. Его нельзя перехватить или проигнорировать. |
| SIGINT | 2 | Прерывание процесса. Обычно отправляется сочетанием клавиш Ctrl+C. |
| SIGHUP | 1 | Исторически обозначает разрыв соединения. Некоторые серверы используют его для перечитывания конфигурации. |
| SIGSTOP | 19 | Приостановка процесса. Этот сигнал нельзя перехватить или проигнорировать. |
| SIGCONT | 18 | Возобновление работы ранее остановленного процесса. |

В командах удобнее использовать имена сигналов, а не их номера:

- **kill -TERM 1234** — отправить процессу с PID 1234 сигнал **SIGTERM**.
- **kill -KILL 1234** — принудительно завершить процесс.
- **kill -STOP 1235** — остановить процесс.
- **kill -CONT 1235** — продолжить выполнение остановленного процесса.

Обычно сначала отправляют **SIGTERM**, чтобы программа успела закрыть файлы, сохранить данные и корректно завершить работу. **SIGKILL** используют только в крайнем случае, когда процесс завис или игнорирует обычное завершение.

##### Приоритеты выполнения

В системе одновременно работают десятки и сотни процессов. Ядро постоянно распределяет между ними процессорное время. Если одна программа начинает активно использовать CPU, это не означает, что она получит его целиком: планировщик должен оставить время и другим задачам.

Значение **nice** влияет на относительный приоритет задачи. Чем меньше значение, тем выше приоритет. Диапазон значений **nice**:

- **-20** - наиболее высокий приоритет;
- **0** - стандартный приоритет;
- **19** - наиболее низкий приоритет.

Изменение приоритета не делает программу быстрее само по себе. Оно влияет только на то, как процессорное время будет распределяться между конкурирующими задачами. Обычный пользователь обычно может понижать приоритет собственных процессов, увеличивая значение **nice**. Для повышения приоритета, то есть установки меньшего значения, обычно требуются дополнительные права.
Посмотреть значение **nice** можно в **top**, в столбце **NI**, или с помощью команды: `ps -l`. Для запуска программы с пониженным приоритетом используется утилита **nice**. Для изменения приоритета уже запущенного процесса используется **renice**:

```
nice -n 10 ./heavy_task
renice -n 10 -p 1234
```
