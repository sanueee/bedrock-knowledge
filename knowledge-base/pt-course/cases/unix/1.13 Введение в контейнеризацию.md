В современном IT перенос приложения с одной машины на другую часто превращается в лотерею. На одной машине стоит одна версия библиотек, на другой - другая. Где-то не хватает системного пакета, где-то отличается конфигурация, где-то приложение вообще запускают на другой версии операционной системы. В итоге программа, которая работала у разработчика, может внезапно не запуститься на тестовом сервере или в продакшене.

Один из способов решить эту проблему - упаковать приложение вместе с окружением. Например, можно создать виртуальную машину: установить туда операционную систему, нужные пакеты, зависимости и само приложение. Такой подход рабочий, но не всегда удобный. Виртуальная машина тяжёлая, долго запускается и требует больше ресурсов, потому что внутри неё работает полноценная гостевая операционная система.

Контейнеры решают похожую задачу легче. Они позволяют упаковать приложение, его зависимости и настройки в единый образ, а затем запускать его в изолированной среде. При этом контейнер не содержит отдельное ядро операционной системы, а использует ядро хоста.

##### Что такое контейнеризация

**Контейнеризация** - это способ упаковки приложения и его окружения в единый стандартный блок, который можно запускать на подходящей системе с контейнерным движком.

Сам термин пришёл из логистики. Морской контейнер стандартизирован: неважно, что внутри - телевизоры, бананы или автомобили, его можно погрузить на корабль, поезд или грузовик. Так и программный контейнер: неважно, что внутри - веб-сервер, база данных или отдельный сервис, он запускается через одинаковый интерфейс.

Обычно контейнерный образ содержит:

- файлы приложения
- среду выполнения, например интерпретатор Python или JVM
- системные библиотеки и утилиты, необходимые приложению
- конфигурационные файлы
- переменные окружения

Контейнер не является полноценной виртуальной машиной. Он больше похож на изолированный процесс, который запускается в уже работающей операционной системе.

##### Виртуальные машины и контейнеры

Виртуальные машины и контейнеры решают похожую проблему, но делают это по-разному.

| Параметр | Виртуальная машина | Контейнер |
|---|---|---|
| Изоляция | На уровне виртуального железа | На уровне механизмов ядра ОС |
| Операционная система | У каждой ВМ своё ядро и своя гостевая ОС | Отдельного ядра нет, используется ядро хоста |
| Размер | Обычно гигабайты | Обычно меньше, потому что не нужна полная гостевая ОС |
| Запуск | Требует загрузки ОС | Обычно запускается быстрее, как отдельный процесс |
| Использование ресурсов | Больше накладных расходов | Меньше накладных расходов |

Это не значит, что контейнеры всегда лучше виртуальных машин. Виртуальные машины удобны, когда нужна полноценная отдельная система, сильная изоляция или другой тип операционной системы. Контейнеры удобны, когда нужно быстро и предсказуемо запускать приложения в одинаковом окружении.

##### Как работает изоляция под капотом

В Linux контейнеризация строится на механизмах ядра. Для вводного уровня достаточно понимать две основные идеи:

- **Namespaces** отвечают за то, что процесс видит. Например, контейнер может видеть свой список процессов, свою файловую систему и свою сеть.
- **Cgroups** отвечают за ограничения ресурсов. С их помощью можно ограничивать использование процессора, оперативной памяти и дискового ввода-вывода.

За счёт этих механизмов процесс внутри контейнера работает не напрямую со всей системой, а в ограниченном окружении. Docker и другие инструменты контейнеризации предоставляют удобный интерфейс для управления этими механизмами.

##### Образы и контейнеры

Контейнер создаётся из **образа**. Образ - это неизменяемый шаблон, в котором лежат файлы приложения, зависимости и инструкции запуска.

Если провести аналогию:

- **образ** - это шаблон или чертёж
- **контейнер** - это запущенный экземпляр, созданный по этому шаблону
   Из одного образа можно создать много контейнеров. Например, один и тот же образ веб-приложения можно запустить несколько раз, чтобы получить несколько одинаковых экземпляров сервиса.

##### Слои образа

Образы состоят из слоёв. Каждый слой хранит изменение файловой системы: добавление, изменение или удаление файлов. Слои дают несколько преимуществ:

- **Неизменяемость** - созданный слой не изменяется, поверх него создаются новые слои.
- **Переиспользование** - разные образы могут использовать общие базовые слои.
- **Кэширование** - при повторной сборке Docker может переиспользовать уже собранные слои, если соответствующие инструкции и файлы не изменились.
- **Copy-on-Write** - если контейнер меняет файл из образа, изменение записывается в отдельный доступный на запись слой контейнера.

Важно понимать: если какой-то слой изменился, Docker пересобирает его и следующие за ним слои. Поэтому порядок инструкций в **Dockerfile** влияет на скорость повторной сборки.

##### Реестры контейнеров

Готовые и кастомные образы хранятся в специальных хранилищах - **реестрах**. Самый известный публичный реестр - **Docker Hub**. Компании часто используют приватные реестры, например **GitLab Container Registry**, **AWS ECR** или **Harbor**.

Реестр можно сравнить с GitHub или App Store для контейнерных образов. Из него можно скачать готовый образ базы данных, веб-сервера или языка программирования, а затем использовать его как основу для своего приложения.

##### Хранение данных и тома

Контейнеры по своей природе временные. Если удалить контейнер, данные из его собственного доступного на запись слоя тоже исчезнут. Поэтому важные данные не хранят внутри контейнера напрямую.

Для постоянного хранения используют монтирования:

- **Volume** - хранилище, которым управляет Docker. Данные лежат на хосте в специальной директории Docker, но контейнер видит их как обычные файлы внутри своей файловой системы. Часто используется для баз данных и постоянных данных приложения.
- **Bind mount** - подключение конкретного файла или директории с хоста внутрь контейнера. Часто используется в разработке, когда код лежит на хосте, а приложение запускается в контейнере.
- **tmpfs mount** - хранение данных в оперативной памяти хоста. Такие данные не записываются на диск и исчезают после остановки контейнера.

Например, если контейнер с базой данных пересоздать, он может подключить тот же **volume** к тому же пути внутри контейнера. В этом случае данные останутся на месте.

##### Сети в контейнерах

У контейнера есть собственное сетевое окружение. Приложение внутри контейнера не становится автоматически доступным снаружи. Чтобы пользователь или другое приложение могли обратиться к сервису внутри контейнера, обычно используют проброс портов.

Например, команда `docker run -p 8080:80 nginx` связывает порт **8080** на хосте с портом **80** внутри контейнера. После этого запрос на порт **8080** хостовой машины будет перенаправлен в контейнер на порт **80**.

Для связи нескольких контейнеров между собой Docker может создавать контейнерные сети. Внутри такой сети контейнеры могут обращаться друг к другу по IP-адресам или именам контейнеров.

##### Инструменты контейнеризации

Для работы с контейнерами существуют разные инструменты.

**Docker** - самый распространённый инструмент для знакомства с контейнеризацией. Он предоставляет:

- CLI для работы с контейнерами и образами
- формат контейнерных образов
- **Dockerfile** для описания сборки образа
- встроенную работу с сетями и томами
- **Docker Compose** для запуска многокомпонентных приложений
- интеграцию с **Docker Hub**

**Podman** - альтернатива Docker. Он может запускать контейнеры без отдельного Docker-демона и часто используется там, где важен запуск контейнеров от имени обычного пользователя.

**containerd** - более низкоуровневая среда выполнения контейнеров. Она используется внутри Docker и Kubernetes.

**CRI-O** - контейнерная среда выполнения, ориентированная на Kubernetes.

**LXC** - Linux Containers. Это более системный вариант контейнеризации: он удобен, когда нужно запустить изолированную Linux-среду, похожую на отдельную систему, а не только один прикладной процесс. Например, такой подход часто встречается в инфраструктуре, где нужно быстро поднять отдельную среду под сервис без полноценной виртуальной машины.

Несмотря на разнообразие инструментов, для введения нам хватит функционала Docker. Поэтому дальше будем работать именно с ним.

##### Оркестрация: когда контейнеров становится много

Один контейнер можно запустить вручную. Но в реальной инфраструктуре приложение может состоять из нескольких контейнеров: фронтенд, бэкенд, база данных, кэш, брокер сообщений и другие сервисы. Когда контейнеров становится много, их нужно автоматически запускать, перезапускать при сбоях, обновлять, масштабировать и распределять по серверам. Для этого используют системы оркестрации.

Самый известный оркестратор - **Kubernetes**. Он позволяет описать желаемое состояние приложения: какие контейнеры должны работать, сколько экземпляров нужно запустить, какие ресурсы им выделить и как направлять к ним трафик. Kubernetes сам старается привести кластер к этому состоянию. Kubernetes умеет:

- перезапускать контейнеры при сбоях
- увеличивать или уменьшать количество экземпляров приложения
- распределять трафик между экземплярами приложения
- выполнять постепенные обновления
- передавать конфигурацию и секреты в контейнеры

Для небольших стендов иногда используют облегчённые варианты Kubernetes, например **k3s**.

#### Первое знакомство с Docker

Первое знакомство с Docker обычно начинается с запуска контейнера **hello-world**. Это специальный тестовый образ, который помогает проверить, что Docker Engine установлен и работает. Запустим контейнер: `docker run hello-world`

При выполнении этой команды Docker делает несколько действий:

1. Проверяет, есть ли образ **hello-world** в локальном хранилище образов.
2. Если образа нет, скачивает его из Docker Hub.
3. Создаёт контейнер на основе образа.
4. Запускает процесс внутри контейнера.
5. Выводит сообщение в терминал.
6. Завершает контейнер, потому что основной процесс внутри него закончил работу.

![](../../_images/002a6bb7e779.webp)

Сообщение **Hello from Docker!** подтверждает, что контейнер был успешно создан и выполнен. После вывода сообщения основной процесс завершается, поэтому контейнер останавливается.

Проверим список контейнеров: `docker ps -a`. Команда **docker ps** показывает контейнеры. Без флага **-a** она выводит только запущенные контейнеры. Флаг **-a** добавляет в вывод остановленные контейнеры.

![](../../_images/20ddec9cae82.webp)

Статус **Exited (0)** означает, что контейнер завершился успешно. Код **0** обычно означает завершение без ошибки.

Если при запуске контейнера не указать имя, Docker автоматически сгенерирует его сам.

#### Создание собственного образа

Теперь создадим простой образ на базе **Alpine Linux**. Alpine часто используют в контейнерах, потому что это небольшой Linux-дистрибутив. Создадим отдельную директорию для примера и перейдём в неё: `mkdir docker-example && cd docker-example`

Создадим файл **Dockerfile**: `nano Dockerfile` и добавим в него содержимое:

```
FROM alpine:latest
ENV APP_NAME="docker_example"
CMD echo "Application: ${APP_NAME}"
```

В этом **Dockerfile** используются три инструкции:

- **FROM** задаёт базовый образ, на основе которого будет собираться новый образ.
- **ENV** создаёт переменную окружения внутри образа.
- **CMD** задаёт команду по умолчанию, которая выполнится при запуске контейнера.

Соберём образ: `docker build -t example-image:latest .`

Здесь:

- **-t example-image:latest** задаёт имя образа и тег.
- **example-image** - имя образа.
- **latest** - тег образа. Это просто имя тега по умолчанию, а не гарантия, что образ действительно самый новый.
- **точка в конце** указывает на текущую директорию как на контекст сборки.

**Контекст сборки** - это набор файлов, которые Docker получает при сборке образа. В нашем случае в контекст попадает текущая директория с файлом **Dockerfile**.

![](../../_images/cd1832c344b1.webp)

В Docker-демон отправляется контекст сборки - файлы из текущей директории (за исключением указанных в **.dockerignore**, о котором будет написано чуть позже). Далее последовательно выполняются инструкции из Dockerfile. Как было описано ранее, на каждом из этапов Docker создает временный контейнер, в котором выполняет инструкции, а строка, идущая после `--->` это сокращённый идентификатор, который является первыми символами полного SHA256-хеша образа.

После сборки образ появится в локальном хранилище образов. Посмотрим список образов: `docker images`

![](../../_images/cce82aa29291.webp)

#### Просмотр метаданных образа

Образ содержит не только файловую систему, но и метаданные: команду запуска, переменные окружения, рабочую директорию, открытые порты, метки и другие параметры. Для просмотра подробной информации об образе используется команда **docker image inspect**: `docker image inspect example-image:latest`

Команда выводит большой JSON-документ. В нём можно найти настройки, которые Docker будет использовать при создании контейнера из этого образа. Например, переменные окружения хранятся в поле **Config.Env**.

##### Запуск интерактивной оболочки

Иногда нужно попасть внутрь контейнера и выполнить команды в его окружении. Например, можно запустить контейнер **Alpine** с интерактивной оболочкой **sh**: `docker run -it alpine sh`

В этой команде:

- **-i** оставляет стандартный ввод открытым.
- **-t** создаёт псевдотерминал.
- **alpine** - образ, из которого запускается контейнер.
- **sh** - команда, которая запускается внутри контейнера.

После запуска откроется интерактивная сессия внутри контейнера.

![](../../_images/dff47898bb59.webp)

Важно: команда **docker run** каждый раз создаёт новый контейнер. Если нужно выполнить команду внутри уже запущенного контейнера, чаще используют **docker exec**. Например, можно запустить оболочку внутри уже работающего контейнера: `docker exec -it alpine_container sh`

Или сразу выполнить конкретную команду без входа в интерактивную оболочку: `docker exec alpine_container echo 'hello'`. Команда **docker exec** запускает новую команду внутри уже работающего контейнера.

Наличие интерактивной оболочки внутри контейнера не гарантируется. Многие образы содержат **sh** или **bash**, но существуют **distroless-образы**, в которых нет оболочки, пакетного менеджера и большинства системных утилит. В таких образах приложение может быть единственным доступным процессом.

> Чтобы выйти из интерактивной оболочки, воспользуйтесь командой **exit**

##### Инструкция COPY и контекст сборки

При сборке образов часто используется инструкция **COPY**. Она копирует файлы и директории из контекста сборки в файловую систему образа. Общий вид инструкции: `COPY <источник> <назначение>`

Здесь:

- **источник** - файл или директория внутри контекста сборки.
- **назначение** - путь внутри образа, куда нужно поместить файл или директорию.

Например:

```
COPY app.py /app/app.py
```

Эта инструкция копирует файл **app.py** из контекста сборки в путь **/app/app.py** внутри образа. Файлы за пределами контекста сборки недоступны для **COPY**. Если сборка запускается из текущей директории командой `docker build -t example-image:latest .`, то контекстом будет текущая директория.

##### Файл .dockerignore

Иногда в директории проекта есть файлы, которые не должны попадать в контекст сборки: временные файлы, локальные настройки, кэш, зависимости, секреты. Для исключения таких файлов используется **.dockerignore**. Этот файл работает по похожей идее с **.gitignore**: в нём перечисляют файлы и директории, которые Docker не должен отправлять в контекст сборки.

Пример **.dockerignore**:

```
.git
*.log
.env
node_modules
```

Важно: **.dockerignore** помогает не отправлять лишние файлы в контекст сборки, но это не отменяет базовое правило - секреты не должны попадать в образ. Если секрет уже был скопирован в один из слоёв, последующее удаление файла не всегда спасает.

##### Удалённые файлы и слои образа

Docker-образ состоит из слоёв. Если на одном этапе сборки файл был добавлен в образ, а на следующем этапе удалён, итоговая файловая система может уже не показывать этот файл. Но слой, где файл ещё существовал, может остаться в истории образа. Для анализа образа можно сохранить его в tar-архив: `docker save some_image -o archive.tar`

Команда **docker save** сохраняет образ вместе со слоями и метаданными. Затем архив можно распаковать и изучить его содержимое:

```
mkdir archive
tar -xf archive.tar -C archive/
```

Внутри архива будут файлы с метаданными и слои образа. В разных версиях Docker структура архива может отличаться, но общий смысл один: каждый слой хранит изменения файловой системы на определённом этапе сборки.

## Вопрос №3
*тип: open_answer, макс. баллов: 1, попыток: 3*

При сборке образа **app_config** разработчик использовал инструкцию **COPY** и добавил в образ файл **config.ini**, а затем удалил его на одном из следующих этапов сборки. Изучите слои образа и найдите значение переменной **api_key**, которое находилось в удалённом файле. Какое содержание переменной **api_key** в файле **config.ini**? Пример: **pt_student_1feffa91**

> Архив, созданный с помощью **docker save**, содержит отдельные слои образа. После распаковки основного архива содержимое каждого слоя можно просмотреть командой `tar -tf <архив_слоя>`. Чтобы найти нужный файл среди выведенных путей, результат команды можно передать утилите **grep**.
