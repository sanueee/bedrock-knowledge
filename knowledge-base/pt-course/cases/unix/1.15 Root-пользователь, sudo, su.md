# Guided Case 1.15 — Root-пользователь, sudo, su

## Исходные данные

Для выполнения данного кейса необходимо скачать **OVA-образ** виртуальной машины, заготовленный Positive Technologies. В данном образе уже есть готовый набор программного обеспечения, загрузить его можно по [**данной ссылке**](https://storage.ptsecurity.com/seafhttp/f/498cc7331b524efb9c9a/?op=view).

К виртуальной машине можно подключиться с помощью графического интерфейса VirtualBox со следующими учетными данными:

- Login - **pt-intern**
- Password - **p7-1N73rn**

Переходим к выполнению практической работы по аудиту безопасности сервера веб-приложения. Начинаем с анализа учетной записи Alice, которая отвечает за мониторинг системных логов. Для переключения на эту учетную запись выполняем команду **su - alice** и вводим пароль: **password7164**.

Для начала изучим доступные логи и рабочее окружение, выполнив команду **ls -la /var/log/**, чтобы просмотреть список файлов в директории логов, и команду **cat /var/log/syslog**, чтобы прочитать содержимое системного журнала и понять, какие данные там хранятся.

Далее проверяем разрешенные sudo-команды с помощью команды **sudo -l**, которая выводит список действий, доступных текущему пользователю с повышенными привилегиями.

![](../../_images/ddee208cbe0e.webp)

На изображении видно, что Alice может выполнять команду /usr/bin/less /var/log/syslog от имени root без запроса пароля (флаг NOPASSWD). Это стандартная, но потенциально опасная практика, если не ограничены возможности самой программы less.

Запускаем разрешенную команду: **sudo /usr/bin/less /var/log/syslog**. Файл открывается в программе-пейджере less. Теперь пробуем эксплуатировать уязвимость shell-escape. В программе less можно выполнять команды оболочки, добавив восклицательный знак перед командой. Вводим **!/bin/bash** и нажимаем Enter, чтобы попытаться вызвать интерактивную оболочку.

Проверяем полученные привилегии командой **id**, которая отображает текущий идентификатор пользователя и группы.

![](../../_images/aa621617d7df.webp)

На изображении видно: uid=0(root) gid=0(root) groups=0(root). Мы получили полноценную оболочку root. Это сработало, потому что программа less без флага NOEXEC позволяет выполнять произвольные команды оболочки, а администратор не ограничил эту возможность.

Для продолжения работы выходим из оболочки root и программы less, последовательно выполнив команду **exit** дважды.

Переходим к учетной записи Bob, который отвечает за анализ логов приложения. Подключаемся командой **su - bob**, вводим пароль: **password3952**

Изучаем структуру логов приложения командами **ls -la /var/log/app/** для просмотра содержимого директории и **cat /var/log/app/application.log** для чтения файла с событиями веб-приложения. Проверяем sudo-права командой **sudo -l**

![](../../_images/6657d9bffe02.webp)

На изображении видно, что Bob может выполнять /usr/bin/find /var/log/app/ _с использованием символа подстановки (wildcard). Символ_ в правилах sudoers матчит любые символы, включая пробелы и дополнительные аргументы команд, что является классической ошибкой конфигурации.

Эксплуатируем эту уязвимость. Утилита find поддерживает ключ -exec, который позволяет выполнять произвольные команды для найденных файлов. Используем существующий файл application.log, выполнив команду: **sudo /usr/bin/find /var/log/app/ -name application.log -exec /bin/bash ;**. Эта команда заставит find запустить оболочку bash при обнаружении файла.

Проверяем привилегии командой **id**.

![](../../_images/1777a0b7a35e.webp)

На изображении отображается uid=0(root). Мы снова получили root-доступ. Wildcard позволил передать дополнительные аргументы (-exec /bin/bash ;), что дало возможность выполнить произвольную команду с правами суперпользователя.

Выходим из сессии, выполнив команду **exit** дважды.

Переходим к учетной записи Charlie, администратора веб-приложения. Подключаемся командой **su - charlie**, вводим пароль: **password9278**

Изучаем конфигурацию приложения командами **ls -la /var/www/webapp/config/** для просмотра директории и **cat /var/www/webapp/config/app.conf** для чтения файла с настройками подключения к базе данных. Опять проверяем sudo-права командой **sudo -l**

![](../../_images/51b815bfd55d.webp)

На изображении видно критическую ошибку: Charlie может выполнять /usr/bin/nano без указания конкретного файла. Это означает, что он может открыть для редактирования любой файл в системе, включая системные конфигурации.

Открываем системный файл sudoers для редактирования командой: **sudo /usr/bin/nano /etc/sudoers**

![](../../_images/858dcd9055cf.webp)

На изображении виден редактор nano с открытым файлом /etc/sudoers. Спускаемся в самый конец файла и добавляем строку: **charlie ALL=(ALL) NOPASSWD: ALL**. Сохраняем файл сочетанием клавиш Ctrl+O, подтверждаем Enter и выходим Ctrl+X.

Теперь у нас есть полные права на выполнение любых команд. Получаем интерактивную оболочку root командой **sudo -i** и проверяем привилегии командой **id**

![](../../_images/81adaa0a18e3.webp)

На изображении подтверждается uid=0(root). Charlie получил полный контроль над системой, так как разрешение запускать nano без указания конкретного файла позволило отредактировать /etc/sudoers и выдать себе полные права.

Выходим из сессии, выполнив команду **exit** дважды.

Переходим к учетной записи Diana, которая выполняет скрипты аудита системы. Подключаемся командой **su - diana**, вводим пароль **password2053**. Изучаем доступные скрипты командой **ls -la /opt/app/scripts/**. Проверяем sudo-права командой **sudo -l**

![](../../_images/751e23c185c8.webp)

На изображении видно две важные детали конфигурации. Во-первых, переменная окружения PATH сохраняется при выполнении через sudo (env_keep+=PATH). Во-вторых, Diana может выполнять скрипт /opt/app/scripts/check_status.sh.

Создаем вредоносный скрипт с именем одной из команд, используемых внутри check_status.sh (например, df), выполнив последовательно команды: **echo '#!/bin/bash' > /tmp/df**, затем **echo '/bin/bash' >> /tmp/df** и после **chmod +x /tmp/df**, чтобы сделать его исполняемым.

Подменяем переменную окружения PATH, чтобы наша директория /tmp искалась системой первой: **export PATH=/tmp:$PATH**

Запускаем легитимный скрипт аудита через sudo: **sudo /opt/app/scripts/check_status.sh**. Затем проверяем привилегии командой **id**

![](../../_images/591373d4c108.webp)

На изображении видно uid=0(root). Diana получила root через подмену переменной окружения. Когда скрипт попытался выполнить команду df, система нашла наш вредоносный /tmp/df вместо настоящего /usr/bin/df, потому что PATH был подменен, а директива env_keep позволила передать этот модифицированный PATH в среду root.

Теперь переходим к исправлению найденных уязвимостей. Все последующие команды выполняются из-под пользователя root.

Для исправления уязвимости Alice добавляем тег NOEXEC, который блокирует выполнение новых процессов из программы. Выполняем команды:

```bash
cat > /etc/sudoers.d/alice << 'EOF'
alice ALL=(root) NOPASSWD: NOEXEC: /usr/bin/less /var/log/syslog
EOF
```

Затем устанавливаем корректные права доступа к файлу командой **chmod 440 /etc/sudoers.d/alice** и проверяем синтаксис всех файлов sudoers командой **visudo -c**, чтобы избежать блокировки административного доступа.

Проверяем, что уязвимость закрыта. Переключаемся на alice командой **su - alice** и запускаем команду **sudo /usr/bin/less /var/log/syslog**. Пытаемся выполнить команду оболочки, введя **!/bin/bash**

![](../../_images/4bab48f580fc.webp)

На изображении видно сообщение об ошибке: shell is not available или !command disabled. Уязвимость закрыта, Alice по-прежнему может читать логи, но не может вызвать оболочку. Выходим командой **exit**.

Для исправления уязвимости Bob заменяем опасную утилиту find на безопасный grep, который не позволяет выполнить произвольный код. Выполняем:

```bash
cat > /etc/sudoers.d/bob << 'EOF'
bob ALL=(root) NOPASSWD: /usr/bin/grep * /var/log/app/*
EOF
```

Устанавливаем права командой **chmod 440 /etc/sudoers.d/bob** и проверяем синтаксис командой **visudo -c**

Проверяем функциональность. Переключаемся на bob командой **su - bob** и выполняем поиск: **sudo /usr/bin/grep -R "ERROR" /var/log/app/**

![](../../_images/a3d627bee8a7.webp)

На изображении виден результат поиска: найдена строка с ошибкой NullPointerException. Bob может выполнять свою работу. Теперь проверяем, что уязвимость закрыта, попытавшись использовать find: **sudo /usr/bin/find /var/log/app/ -name application.log -exec /bin/bash ;**

![](../../_images/631bfca3b654.webp)

На изображении отображается сообщение: Sorry, user bob is not allowed to execute... Find больше недоступен, уязвимость закрыта. Выходим командой **exit**

Для исправления уязвимости Charlie сначала удаляем строку, которую он добавил при атаке. Открываем основной файл sudoers командой **visudo**, находим в конце файла строку **charlie ALL=(ALL) NOPASSWD: ALL** и удаляем её.

![](../../_images/0bfe166d21ce.webp)

Сохраняем файл (Ctrl+O, Enter, Ctrl+X). Теперь ограничиваем charlie конкретным файлом конфигурации, выполнив:

```bash
cat > /etc/sudoers.d/charlie << 'EOF'
charlie ALL=(root) NOPASSWD: /usr/bin/nano /var/www/webapp/config/app.conf
EOF
```

Устанавливаем права командой **chmod 440 /etc/sudoers.d/charlie** и проверяем синтаксис командой **visudo -c**

Проверяем функциональность. Переключаемся на charlie и выполняем **sudo /usr/bin/nano /var/www/webapp/config/app.conf**

![](../../_images/b8dd34e7792d.webp)

На изображении файл app.conf успешно открылся, charlie может редактировать конфигурацию приложения. Проверяем закрытие уязвимости, попытавшись открыть системный файл: **sudo /usr/bin/nano /etc/sudoers**

![](../../_images/88dd29ed6abb.webp)

На изображении видно сообщение: Sorry, user charlie is not allowed to execute... Charlie больше не может редактировать системные файлы. Выходим командой **exit**

Для исправления уязвимости Diana убираем опасные директивы env_keep, оставляя только разрешение на запуск скрипта. Выполняем:

```bash
cat > /etc/sudoers.d/diana << 'EOF'
diana ALL=(root) NOPASSWD: /opt/app/scripts/check_status.sh
EOF
```

Устанавливаем права командой **chmod 440 /etc/sudoers.d/diana** и проверяем синтаксис командой **visudo -c**

Создаем тестовый вредоносный скрипт для проверки: **echo '#!/bin/bash' > /tmp/df**, затем **echo '/bin/bash' >> /tmp/df**, потом **chmod +x /tmp/df**. Подменяем PATH: **export PATH=/tmp:$PATH**

![](../../_images/6d45ef2e95ab.webp)

На изображении виден процесс создания вредоносного файла и подмены переменной окружения. Теперь, если diana попытается запустить скрипт с подмененным PATH, sudo автоматически сбросит PATH к безопасному значению secure_path, и атака не сработает. Сбрасываем PATH командой **unset PATH** и выходим командой **exit**
