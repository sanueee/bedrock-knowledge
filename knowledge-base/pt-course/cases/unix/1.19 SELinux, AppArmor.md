# Guided Case 1.19 — SELinux, AppArmor

> [!info] Путь в курсе
> Глава 1: UNIX-системы и их безопасность / Часть 3: Защита Linux-систем
>
> **Теория:** [3.03 Основные механизмы разграничения доступа](../../unix/3%20Защита%20Linux-систем/3.03%20Основные%20механизмы%20разграничения%20доступа.md)

## Исходные данные

Чтобы выполнить этот кейс, необходим базовый образ **Debian-12-Gold**. Клонируем исходный образ в VirtualBox и переименуем его в Guided Case 1.19 для удобства использования.

К виртуальной машине подключиться можно с помощью графического интерфейса VirtualBox с учётными данными, которые вы указывали при настройке.

Для доступа к виртуальной машине с хост-машины настроим проброс портов в VirtualBox. Для этого откроем настройки виртуальной машины: **Settings** -> **Network** -> **Adapter 1** -> **NAT** -> **Port Forwarding** и добавим правило:

|Name|Protocol|Host IP|Host Port|Guest IP|Guest Port|
|---|---|---|---|---|---|
|SSH|TCP|127.0.0.1|2222|10.0.2.15|22|

Запустите виртуальную машину и войдите в систему через консоль VirtualBox.

> Предварительно на машине установите **sudo** и добавьте пользователя **pt-intern** в группу **sudo**

Для начала работы подключимся к виртуальной машине по SSH.

- Подключение к виртуальной машине:

```bash
ssh -p 2222 pt-intern@127.0.0.1
```

Теперь у нас есть доступ к виртуальной машине, и мы можем переходить к подготовке лабораторной среды. Для проверки корректности выполнения задания в конце практики необходимо скачать и подготовить чекер. Выполним следующие команды:

```bash
sudo apt install wget -y
mkdir -p ~/checkers
wget "https://storage.ptsecurity.com/d/24947391f6994a6d8897/files/?p=%2Fchecker_apparmor_vmp&dl=1" -O ~/checkers/checker_apparmor_vmp
chmod +x ~/checkers/checker_apparmor_vmp
ls -la ~/checkers/
```

В выводе должен отобразиться файл **checker_apparmor_vmp** с правами на выполнение (**x** в правах доступа). Теперь чекер готов к запуску в конце практики.

Переходим к настройке веб-сервера с использованием мандатного контроля доступа. Все следующие команды выполняются на виртуальной машине с Debian. Мандатный контроль доступа добавляет дополнительный уровень защиты поверх стандартных прав Linux, ограничивая возможности скомпрометированных сервисов. В этой практике мы будем работать с AppArmor.

Обновляем список пакетов и устанавливаем необходимые зависимости: веб-сервер Nginx, интерпретатор PHP-FPM, утилиты для работы с AppArmor и curl для проверки доступности сервисов. Команда **sudo apt update** обновляет индекс пакетов, а **apt install** загружает и настраивает программное обеспечение:

```bash
sudo apt update
sudo apt install -y nginx php-fpm apparmor-utils apparmor-profiles curl
```

Запустился процесс загрузки и установки пакетов. После завершения все необходимые компоненты будут готовы к работе.

Далее создаем нестандартную директорию для нашего приложения и размещаем в ней тестовый PHP-скрипт. В реальных проектах приложения часто размещают в отдельных директориях, таких как **/opt**, для изоляции от системных файлов. Команда **mkdir -p** создает вложенные папки, а **tee** записывает вывод в файл:

```bash
sudo mkdir -p /opt/myapp/php
echo '<?php echo "Success! PHP Version: " . phpversion() . "\n"; ?>' | sudo tee /opt/myapp/php/index.php
```

Затем с помощью **chown** и **chmod** мы выставляем идеальные стандартные права доступа (DAC), назначая владельцем пользователя **www-data**, от которого работает веб-сервер, и выдавая права на чтение и выполнение:

```bash
sudo chown -R www-data:www-data /opt/myapp
sudo chmod -R 755 /opt/myapp
```

С точки зрения стандартных прав Linux, всё настроено абсолютно корректно, и веб-сервер должен иметь полный доступ к этим файлам.

Теперь настраиваем Nginx. Создаем конфигурационный файл, который будет слушать нестандартный порт **8082**, отдавать файлы из нашей директории **/opt/myapp/php** и передавать выполнение PHP-скриптов в Unix-сокет PHP-FPM. Использование heredoc (**cat << "EOF"**) позволяет удобно записать многострочный текст в файл одной командой:

```bash
sudo bash -c 'cat << "EOF" > /etc/nginx/sites-available/phpapp
server {
    listen 8082;
    server_name localhost;

    root /opt/myapp/php;
    index index.php;

    location / {
        try_files $uri $uri/ =404;
    }

    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/php8.2-fpm.sock;
    }
}
EOF'
```

Активируем новый сайт, создав символическую ссылку в директории **sites-enabled**, удаляем конфигурацию по умолчанию и перезапускаем Nginx для применения изменений:

```bash
sudo rm -f /etc/nginx/sites-enabled/default
sudo ln -sf /etc/nginx/sites-available/phpapp /etc/nginx/sites-enabled/
sudo systemctl restart nginx
```

Переходим к настройке мандатного контроля доступа. По умолчанию профиль AppArmor для PHP-FPM в Debian может находиться в щадящем режиме или быть не загруженным. Переводим его в режим принудительного блокирования (**enforce**) с помощью утилиты **aa-enforce**. В этом режиме ядро будет жестко пресекать любые действия процесса, которые явно не разрешены в профиле. После изменения режима обязательно перезапускаем сам сервис PHP-FPM:

```bash
sudo aa-enforce /etc/apparmor.d/php-fpm
sudo systemctl restart php8.2-fpm
```

Проверяем доступность нашего сайта. Команда **curl -I** отправляет HEAD-запрос и показывает только HTTP-заголовки ответа, что позволяет быстро проверить статус код без загрузки всего тела страницы: **curl -I http://localhost:8082/index.php | grep HTTP**

![](../../_images/9c76a508dbfe.webp)

На изображении виден ответ сервера с кодом **HTTP/1.1 403 Forbidden**. Несмотря на то, что стандартные права Linux (DAC) настроены корректно, доступ запрещен. Это классический пример конфликта DAC и MAC: стандартные права разрешают чтение, но мандатный контроль (AppArmor) блокирует процессу доступ к нестандартным путям, так как их нет в «белом списке» профиля.

Проведем расследование инцидента. Сначала посмотрим логи ядра Linux, отфильтровав их по слову **DENIED**. Команда **journalctl -k** выводит сообщения исключительно от ядра (kernel), где AppArmor регистрирует все блокировки: **sudo journalctl -k | grep DENIED | tail -n 10**

![](../../_images/5b47fc80a5e7.webp)

На изображении видна запись аудита: **apparmor="DENIED" operation="open" profile="php-fpm" name="/opt/myapp/php/index.php"**. Это прямое доказательство того, что ядро перехватило системный вызов открытия файла и заблокировало его. Параметр **requested_mask="r"** показывает, что процесс запрашивал права на чтение, но получил отказ.

Дополнительно проверим логи самого веб-сервера, чтобы увидеть, как эту ошибку интерпретирует Nginx: **sudo tail -n 20 /var/log/nginx/error.log**

![](../../_images/4b92bc2d412d.webp)

На изображении видна ошибка в error.log: **FastCGI sent in stderr: "Unable to open primary script... (Permission denied)"**. Это подтверждает, что Nginx успешно принял запрос и передал его в PHP-FPM, но интерпретатор PHP не смог прочитать файл из-за ограничений ядра.

Убедимся, что в текущих профилях AppArmor нет упоминаний нашей директории, выполнив рекурсивный поиск по конфигурациям: **sudo grep -r myapp /etc/apparmor.d/**

Поиск ничего не выдаст, что подтверждает отсутствие разрешений. Теперь добавим необходимое правило. В Debian системные профили лежат в **/etc/apparmor.d/**, но локальные изменения принято вносить в специальную директорию **local/**. Это хорошая практика: файлы в **local/** не перезаписываются пакетным менеджером при обновлении системы. Добавляем правило, разрешающее чтение (**r**) для всех файлов в директории и поддиректориях: `echo "/opt/myapp/php/** r," | sudo tee -a /etc/apparmor.d/local/php-fpm`

Обратите внимание на запятую в конце строки — это обязательное требование синтаксиса AppArmor.

Перезагружаем профиль в ядро с помощью **apparmor_parser**, перезапускаем PHP-FPM и проверяем работу сайта:

```bash
sudo apparmor_parser -r /etc/apparmor.d/php-fpm
sudo systemctl restart php8.2-fpm
curl -s http://localhost:8082/index.php
```

![](../../_images/a94832f6d345.webp)

На изображении виден успешный вывод функции **phpinfo()** с информацией о версии PHP и настройках. Сайт заработал, мандатный контроль успешно настроен вручную.

Теперь рассмотрим профессиональный подход с использованием автоматизации. В реальных условиях администраторы часто используют системные утилиты для разбора логов. Откатим наши ручные изменения, удалив добавленную строку из локального профиля с помощью **sed**, и перезапустим службы, чтобы снова получить ошибку:

```bash
sudo sed -i '/\/opt\/myapp/d' /etc/apparmor.d/local/php-fpm
sudo apparmor_parser -r /etc/apparmor.d/php-fpm
sudo systemctl restart php8.2-fpm
```

Сгенерируем новую ошибку доступа и сохраним сообщения ядра во временный файл. Утилита анализа логов требует, чтобы логи были в файле, поэтому мы перенаправляем вывод **dmesg** в **/tmp/aa_denied.log**:

```bash
curl -s http://localhost:8082/index.php > /dev/null
sudo dmesg | grep DENIED > /tmp/aa_denied.log
```

Запускаем утилиту **aa-logprof**, которая автоматически проанализирует логи и предложит готовые правила. Скармливаем ей наш файл с логами через флаг **-f**: **sudo aa-logprof -f /tmp/aa_denied.log**

![](../../_images/d5941773143e.webp)

На изображении видно интерактивное меню утилиты. Для настройки правила необходимо нажать **O** (снять привязку к владельцу файла), затем дважды нажать **G** (превратить путь в рекурсивный шаблон `/opt/myapp/php/**`), нажать **A** (Allow - разрешить) и в конце **S** (Save - сохранить изменения в профиль). Утилита сама сформирует правильный синтаксис и запишет его в нужные конфигурационные файлы.

Проверяем, как утилита записала сгенерированное правило в конфигурационные файлы AppArmor: **sudo grep -r myapp /etc/apparmor.d/**

![](../../_images/0cd5dbb73218.webp)

На изображении видно, что утилита самостоятельно добавила нужную строку с правами доступа в профиль, избавив нас от необходимости писать синтаксис вручную.

Применяем изменения, перезагружая профиль и перезапуская сервис:

```bash
sudo apparmor_parser -r /etc/apparmor.d/php-fpm
sudo systemctl restart php8.2-fpm
```

Выполняем финальную проверку с помощью **curl -s http://localhost:8082/index.php**

![](../../_images/a94832f6d345.webp)

На изображении виден успешный вывод **phpinfo()**. Мы успешно восстановили работу сервиса, используя инструменты автоматизации политик безопасности. Этот подход экономит время и снижает вероятность синтаксических ошибок при написании сложных профилей.
