# Guided Case 1.8 — Демоны, службы, автозапуск

> [!info] Путь в курсе

>

## Стенд / введение

- Для выполнения этого кейса не требуется определённый образ виртуальной машины. Можно использовать любой из образов, выданных ранее, или работать на виртуальной машине **Debian-12-Gold**, которую мы делали в [**начале блока**](http://pt.edtechlab.local/ru/mentor/modules/vvedenie-v-kiberbezopasnost/view/1210).

В Linux не все программы запускают вручную. Одни должны стартовать вместе с системой и работать в фоне, другие администратор добавляет в автозапуск сам.

Например:

- SSH-сервер должен принимать подключения после перезагрузки машины
- веб-сервер должен обслуживать запросы без открытого терминала
- сетевые службы должны работать ещё до входа пользователя в графическую оболочку
- агенты мониторинга должны постоянно собирать информацию о состоянии системы

Для таких задач в Linux используются демоны, службы и механизмы автозапуска. В этой статье разберём эти понятия на простом практическом примере. Создадим небольшой скрипт, оформим его как службу для **systemd**, запустим вручную, включим автозапуск и посмотрим логи.

#### Обычная программа и фоновый процесс

Когда пользователь запускает команду в терминале, она обычно привязана к текущей сессии. Например: `sleep 100`

![](../../_images/415fd72d28bf.webp)

Команда **sleep** просто ждёт 100 секунд. Пока она работает, терминал занят. Если открыть второй терминал, процесс можно увидеть с помощью команды `ps aux | grep sleep`. Это обычный процесс. Он был запущен пользователем вручную и работает до завершения команды. Можно запустить команду как фоновый процесс: `sleep 100 &`

![](../../_images/05c83d5b3977.webp)

Символ **&** сообщает оболочке, что команду нужно выполнить как фоновую задачу. После запуска терминал сразу возвращает приглашение для ввода новых команд. В выводе также можно увидеть **[1]**. Это номер задачи, привязанной к текущей сессии оболочки. Список задач можно просмотреть с помощью команды `jobs`

![](../../_images/a2a2cfc63ec3.webp)

Знак **+** указывает на текущую задачу. Это задача, с которой оболочка будет взаимодействовать по умолчанию, если выполнить команду управления задачами без указания номера. Чтобы вернуть задачу на передний план, используйте команду **fg**. Например, для задачи с номером **1** выполните `fg 1`

![](../../_images/1b1cf8a3c8cb.webp)

Но такой процесс всё ещё не является полноценной службой. Он связан с пользовательской сессией, им неудобно управлять, он не запускается автоматически после перезагрузки и не имеет отдельного описания для системы. Для простых одноразовых задач этого достаточно. Для системных фоновых процессов – нет.

#### Демоны и службы

Многие системные процессы должны работать постоянно независимо от того, вошёл ли пользователь в систему. Такие процессы называют демонами. **Демон** – это процесс, который работает в фоновом режиме и выполняет служебные задачи без прямого взаимодействия с пользователем.

Примеры демонов:

- **cron** запускает задачи по расписанию
- **systemd-journald** собирает системные логи
- **sshd** принимает SSH-подключения
- **NetworkManager** управляет сетевыми подключениями

Однако операционной системе также нужен способ управлять этими процессами: запускать их при загрузке, останавливать, перезапускать после сбоев и отслеживать их состояние. Для этого используются службы.

**Служба** – это описание того, как система должна запускать и контролировать программу: какую команду выполнять, когда её запускать, какие зависимости учитывать и что делать после завершения или сбоя. Во многих современных дистрибутивах Linux службами управляет **systemd** - система инициализации и менеджер служб. При загрузке системы он запускается одним из первых процессов и управляет службами, зависимостями между юнитами и другими системными компонентами. Журналы в составе **systemd** собирает отдельная служба **systemd-journald**.

> Кроме **systemd**, в Linux существуют и другие системы инициализации и управления службами, например **SysVinit**, **OpenRC** и **runit**. Однако **systemd** используется во многих современных дистрибутивах Linux.

Для управления службами используется утилита **systemctl**. Например, узнаем статус службы SSH с помощью команды `systemctl status ssh`

![](../../_images/0c74f3b4a989.webp)

#### Чем служба отличается от автозапуска в shell

Иногда автозапуск пытаются настраивать через **.bashrc**, **.profile** и другие файлы shell, но это не то же самое, что systemd-служба.

Файл **.bashrc** выполняется при запуске интерактивной Bash-сессии, например при открытии терминала. Если добавить в него запуск серверного процесса, новая копия процесса будет создаваться при каждом запуске такой сессии. Кроме того, программа не запустится вместе с системой без входа пользователя в shell.

Есть и другие механизмы запуска задач:

- **cron** – подходит для периодических задач по расписанию
- **systemd timers** – запускают задачи по расписанию или через заданные интервалы и интегрированы с **systemd**
- **Desktop autostart** – подходит для программ графической сессии пользователя
- **Shell startup files** – подходят для настройки shell-окружения
- **systemd services** – подходят для долгоживущих фоновых процессов и системных служб

#### Создаём свою службу

Создадим простую учебную службу **heartbeat-demo**, которая будет раз в 5 минут делать бэкап директории **/etc**. Сначала создадим обычный shell-скрипт: `sudo nano /usr/local/bin/heartbeat-demo.sh`

Добавим в него содержимое:

```
#!/bin/bash

BACKUP_DIR="/var/backups/demo"
SOURCE_DIR="/etc"

mkdir -p "$BACKUP_DIR"

while true; do
    tar -czf "$BACKUP_DIR/etc-backup.tar.gz" "$SOURCE_DIR"
    sleep 300
done
```

Этот скрипт делает следующее:

- задаёт директорию, в которой будет храниться бэкап
- задаёт директорию, содержимое которой нужно сохранить
- создаёт директорию для бэкапа, если её ещё нет
- создаёт архив сразу после запуска, а затем перезаписывает его каждые 5 минут

Сохраним файл и сделаем его исполняемым: `sudo chmod +x /usr/local/bin/heartbeat-demo.sh`

Теперь скрипт можно запустить вручную: `sudo /usr/local/bin/heartbeat-demo.sh`

Скрипт будет выполняться на переднем плане и займёт текущий терминал до остановки. Остановить его можно сочетанием клавиш **Ctrl+C**. После этого перейдём в директорию, куда сохраняется бэкап. В ней появится созданный архив:

![](../../_images/2e3faa7e3081.webp)

Пока это обычный скрипт. Он работает только тогда, когда пользователь сам его запустил, и не стартует автоматически после перезагрузки. Чтобы **systemd** мог запускать и контролировать этот скрипт, создадим для него юнит.

**Юнит** – это объект, которым управляет **systemd**. Для запуска программ используют юниты типа **.service**. Их описывают в юнит-файлах: в таком файле указывают, какую команду нужно запустить и как **systemd** должен управлять процессом. Для нашей службы создадим юнит-файл **heartbeat-demo.service** в каталоге **/etc/systemd/system/**.

##### Типы юнитов

К основным типам юнитов относят:

- **.service** – описывает службу и процесс, который нужно запустить
- **.socket** – описывает сокет, через который служба может принимать подключения
- **.timer** – запускает другой юнит по расписанию или через заданные интервалы
- **.mount** – описывает точку монтирования
- **.path** – запускает юнит при изменении файла или каталога
- **.target** – объединяет несколько юнитов и обозначает определённое состояние системы

Для нашей задачи нужен юнит типа **.service**, так как он будет запускать созданный ранее скрипт и контролировать его работу. Собственные юниты администратор обычно описывает в юнит-файлах. Локальные юнит-файлы размещают в каталоге **/etc/systemd/system/**.

Создадим в этом каталоге юнит-файл **heartbeat-demo.service**: `sudo nano /etc/systemd/system/heartbeat-demo.service`

Добавим в него содержимое:

```
[Unit]
Description=Simple heartbeat demo service
After=network.target

[Service]
ExecStart=/usr/local/bin/heartbeat-demo.sh
Restart=always

[Install]
WantedBy=multi-user.target
```

Юнит-файл состоит из секций:

- **[Unit]** – общая информация о службе и её зависимостях
- **[Service]** – параметры запуска процесса
- **[Install]** – настройки подключения службы к автозагрузке

Разберём этот файл по частям. Блок **[Unit]** содержит общее описание службы и информацию о порядке запуска:

```
[Unit]
Description=Simple heartbeat demo service
After=network.target
```

Строка **Description=Simple heartbeat demo service** используется только для отображения и описания юнита в выводе **systemd**, что помогает понять назначение службы.

Строка **After=network.target** задаёт порядок запуска: если оба юнита запускаются в рамках одной операции, **heartbeat-demo.service** будет запущен после **network.target**. Эта директива не создаёт зависимость и не гарантирует, что сеть уже полностью готова к работе. В нашем примере она добавлена только для знакомства с порядком запуска юнитов. В реальных службах директивы порядка запуска указывают только тогда, когда такой порядок действительно важен.

> **network.target** – специальный **target**-юнит. Он обозначает, что системные компоненты сети уже запущены, но не гарантирует, что сетевое подключение уже готово к работе.

Дальше идёт блок **[Service]**, который описывает, как запускать службу:

```
[Service]
ExecStart=/usr/local/bin/heartbeat-demo.sh
Restart=always
```

Директива **ExecStart=/usr/local/bin/heartbeat-demo.sh** указывает команду, которую **systemd** должен запустить.

Директива **Restart=always** говорит **systemd** перезапускать службу после завершения её процесса, кроме случая, когда службу явно останавливают командой **systemctl stop**.

## Вопрос №1
*тип: open_answer, макс. баллов: 1, попыток: 3*

Какая директива определяет порядок запуска юнитов? Пример: **Type**

Следующий блок – **[Install]**, который описывает, как служба подключается к автозагрузке:

```
[Install]
WantedBy=multi-user.target
```

**multi-user.target** – это target-юнит многопользовательского режима системы. Он используется для служб, которые должны запускаться при обычной загрузке системы без привязки к графической сессии пользователя.

Когда мы включим службу в автозапуск, **systemd** создаст связь между нашей службой и этим target-юнитом. После создания или изменения юнит-файла нужно сказать **systemd** перечитать конфигурацию с помощью команды `sudo systemctl daemon-reload`. Эта команда не запускает службу, а только обновляет представление **systemd** о доступных юнит-файлах. Если забыть выполнить **daemon-reload**, **systemd** может не увидеть новый юнит-файл или продолжить использовать старую версию конфигурации.

После этого можно запустить службу: `sudo systemctl start heartbeat-demo.service`

Проверим её состояние командой `systemctl status heartbeat-demo.service`

![](../../_images/c14e2700adb7.webp)

Главное в выводе – строка **Active: active (running)**. Она означает, что служба запущена и её процесс работает. Также обратите внимание на слово **disabled**. Оно означает, что служба пока не включена в автозапуск. Она работает сейчас, но после перезагрузки не будет запущена автоматически.

Это происходит потому, что команда **systemctl start** запускает службу только сейчас, но не добавляет её в автозапуск. Чтобы включить автозапуск, выполните команду `sudo systemctl enable heartbeat-demo.service`
Для выключения автозапуска используется аналогичная команда `sudo systemctl disable heartbeat-demo.service`

![](../../_images/eb777bfac1ed.webp)

## Вопрос №2
*тип: open_answer, макс. баллов: 1, попыток: 3*

Какую подкоманду утилиты **systemctl** нужно выполнить, чтобы **systemd** перечитал изменённые юнит-файлы? Пример: **status**

После того как служба перестала быть нужна, её можно остановить с помощью команды `sudo systemctl stop heartbeat-demo.service`. В результате в выводе состояния службы увидим строку **Active: inactive (dead)**.

![](../../_images/cc768db887dc.webp)

Помимо остановки, службу можно перезапустить, например если она зависла, или мы внесли в неё коррективы. Для этого используется команда `sudo systemctl restart heartbeat-demo.service`. Она сначала останавливает службу, а затем запускает её снова.

![](../../_images/4611c5bdd575.webp)

Команда **systemctl reload** применяется только к службам, которые умеют перечитывать собственную конфигурацию без перезапуска. Она не останавливает и не запускает процесс заново. Наша учебная служба не поддерживает **reload**, поэтому для неё используется **restart**.

Чтобы посмотреть установленные юнит-файлы типа **.service** и состояние их включения в автозапуск, используйте команду: `systemctl list-unit-files --type=service`

![](../../_images/99873d1b70c7.webp)

Столбец **STATE** показывает состояние юнит-файла, например **enabled**, **disabled** или **static**. Столбец **PRESET** показывает состояние, рекомендуемое политикой дистрибутива или организации.

Чтобы посмотреть загруженные в **systemd** юниты типа **.service**, используйте команду: `systemctl list-units --type=service --all`. А чтобы отфильтровать список по названию службы, можно воспользоваться утилитой **grep**: `systemctl list-unit-files --type=service | grep networking`

![](../../_images/497c36367975.webp)
