#### SID и почему он не меняется

**Security Identifier** (**SID**) - это уникальный идентификатор, который Windows присваивает каждой учётной записи и группе при создании. Имя пользователя - это лишь "вывеска"; на уровне ядра все права привязаны именно к **SID**. Для того чтобы вывести **SID** всех пользователей: `Get-LocalUser | Select-Object Name, Enabled, SID`

![](../../_images/bf0469411833.webp)

В выводе у **petya** и **vasya** будут разные **SID** вида **S-1-5-21-...-1003** и **S-1-5-21-...-1004**. Запомните **RID** пользователя **vasya** - он понадобится позже.

Чтобы убедиться, что **SID** не зависит от имени, переименуйте **vasya** в **vasiliy **и обратно:

```
Rename-LocalUser -Name "vasya" -NewName "vasiliy"
Get-LocalUser -Name "vasiliy" | Select-Object Name, SID
Rename-LocalUser -Name "vasiliy" -NewName "vasya"
Get-LocalUser -Name "vasya" | Select-Object Name, SID
```

![](../../_images/c3e585824530.webp)

**SID** в обоих случаях одинаковый. Это значит, что любая ссылка на пользователя в **NTFS ACL**, в членстве групп или в реестре после переименования продолжает работать без перенастройки.

#### Наследование и его разрыв

По умолчанию все права из корня **LabShare** наследуются подпапкой **Restricted** - именно поэтому мы можем не настраивать каждую подпапку отдельно. Займемся отключением наследования папок. Для этого откройте свойства **C:\LabShare\Restricted** -> **Security** -> **Advanced**

![](../../_images/bac1f8348bd0.webp)

Нажмите **Change permissions**

После нажатия **Change permissions**, станет доступна кнопка **Disable inheritance**, нажмём на нее

Выберите **Convert** - так мы сохраняем доступ для **SYSTEM**, **Administrators** и владельца, но получим возможность точечно править эти правила на самом объекте

**Deny сильнее Allow**

На подкаталоге **Restricted** разыграйте классический сценарий, который сбивает с толку начинающих администраторов. Пользователь **petya** входит в группу **LabAuditors**; группа получит **Full Control** на **Restricted**, но самому **petya** мы явно запретили чтение. По правилам Windows явный **Deny** перекрывает любой **Allow** - и даже как член группы с полным доступом **petya** не сможет открыть папку.

```
icacls "C:\LabShare\Restricted" /grant "LabAuditors:(OI)(CI)F"
icacls "C:\LabShare\Restricted" /deny "petya:(OI)(CI)R"
```

![](../../_images/e4885dc49542.webp)

Проверьте получившийся ACL:

```
(Get-Acl "C:\LabShare\Restricted").Access |
    Select-Object IdentityReference, AccessControlType, FileSystemRights
```

![](../../_images/2be81901a636.webp)

В выводе должны быть две дополнительных колонки: **AccessControlType = Allow** для **LabAuditors** с **FullControl** и **AccessControlType = Deny** для **petya** с **Read, Synchronize**. Чтобы практически почувствовать механику, запустите **File Explorer** под **petya** и попробуйте открыть папку **Restricted**

![](../../_images/ae46c516d72e.jpg)

#### Сетевые vs NTFS-права

Самое распространённое заблуждение администратора - смешивать **Share permissions** (права на сетевой ресурс) и **NTFS permissions** (права файловой системы). Это два **разных** уровня контроля, и при сетевом доступе итоговое право пользователя - это **пересечение** того, что разрешают оба уровня. Что запрещает один, второй не разблокирует.

Создайте на каталоге **C:\LabShare** общий сетевой ресурс. Сначала через **GUI**: нажмём правой кнопкой по папке **LabShare** -> **Properties** -> **Sharing** -> **Advanced Sharing**

![](../../_images/e150447dc9ee.webp)

![](../../_images/18a86dadd822.webp)

По умолчанию **Everyone** получает **Read** - оставьте это значение. Нажмём **OK** дважды и **Close**

![](../../_images/0f23c59daa0e.webp)

```

New-SmbShare -Name "LabShare" -Path "C:\LabShare" -FullAccess "Administrators" -ReadAccess "Everyone"
```

![](../../_images/1f51dad6a6b8.webp)

Командлет **New-SmbShare** входит в модуль **SmbShare**. Параметр **-ReadAccess** выдаёт **Share-уровень Read** для группы **Everyone**, **-FullAccess** - **Share-уровень Full** для администраторов (чтобы мы могли управлять сетевой папкой по сети).

По правилу пересечения: при доступе по сети **vasya** получит **минимум** из (**Share = Read**, **NTFS = Modify**) - то есть **Read**, без записи. А при локальном доступе сетевой слой не применяется, и **vasya** получит **Modify**.

#### RID Hijacking

Во второй части мы разыграли роль атакующего, который уже получил права администратора на машине и хочет закрепиться - но так, чтобы при беглом аудите его учётка не выделялась. Стандартное добавление в группу **Administrators** легко детектируется простой командой **Get-LocalGroupMember Administrators**. **RID Hijacking** обходит эту проверку: учётка остаётся обычным пользователем по списку группы, но при логине ядро присваивает её токену права администратора.

Принцип атаки следующий. Windows хранит данные локальных учёток в кусте реестра **HKLM\SAM**. У каждой учётной записи есть подключ вида **HKLM\SAM\SAM\Domains\Account\Users&lt;RID_hex>**, внутри которого лежит бинарное значение **F** - дескриптор учётной записи

![](../../_images/2fed666cda93.jpg)

На смещении **0x30** в этом значении записаны четыре байта **RID** в формате **little-endian**. Если в этих четырёх байтах вместо родного **RID** жертвы записать **F4 01 00 00** (что соответствует **0x1F4** = десятичное **500**, **RID** встроенного администратора), то при следующем входе подсистема **Local Security Authority Subsystem Service** (**LSASS**) построит токен жертвы с привилегиями администратора. При этом запись в группе **Administrators** не меняется - в этом и есть скрытность техники. Атака описана **Sebastián Castro** из CSL в 2017 году и каталогизирована **MITRE ATT&CK** как часть **T1098** (Account Manipulation).

> **Предупреждение.** Дальнейшие действия модифицируют куст **SAM**. Ошибочное изменение байтов на другом смещении или повреждение значения **F** может привести к невозможности входа в систему. Перед началом **повторно** сделаем снапшот ВМ.

#### Получение SYSTEM-контекста

Куст **HKLM\SAM** защищён **ACL** так, что даже из-под учётной записи **Administrator** прямое чтение его подключей запрещено - **regedit** под админом покажет ветку, но без содержимого. Доступ к содержимому имеет только встроенный контекст **NT AUTHORITY\SYSTEM**. Самый чистый способ запустить **regedit** под **SYSTEM** - утилита **PsExec** из набора **Sysinternals**.

Скачайте архив [**PsExec**](https://learn.microsoft.com/ru-ru/sysinternals/downloads/psexec) с официального сайта microsoft и и разархивируйте его по пути **C:\PSTools** Откройте **PowerShell** от имени администратора, перейдите в каталог с **PsExec.exe** и выполним:

```
cd C:\PSTools
.\PsExec.exe -accepteula -s -i regedit.exe
```

![](../../_images/a12c93cff903.webp)

Разбор флагов:

- **-accepteula** - один раз принять лицензионное соглашение **Sysinternals**, чтобы окно EULA больше не появлялось
- **-s** - запустить процесс под учётной записью **NT AUTHORITY\SYSTEM**
- **-i** - запустить в интерактивной сессии текущего пользователя, чтобы окно **regedit** появилось на рабочем столе

На рабочем столе откроется **Registry Editor**. Чтобы убедиться, что он действительно работает под **SYSTEM**, в отдельном окне запустите аналогичную команду для **cmd**: `.\PsExec.exe -s -i cmd.exe`

В появившемся окне **Command Prompt** выполним **whoami** - в выводе появится **nt authority\system**. Это и есть контекст, в котором сейчас работает **regedit**.

![](../../_images/04f86df1eeed.webp)

#### Поиск RID жертвы

В **regedit**, запущенном под **SYSTEM**, развернём ветку **HKEY_LOCAL_MACHINE\SAM\SAM\Domains\Account\Users**. Под обычным администратором эта ветка пуста - под **SYSTEM** Вы увидим список подключей с шестнадцатеричными именами вида **000001F4** (это RID 500, встроенный администратор), **000001F5** (RID 501, гость) и далее - по одному подключу на каждую локальную учётную запись.

Чтобы определить **RID** именно **vasya**, перейдите в подключ **Names** внутри **Users**: **HKLM\SAM\SAM\Domains\Account\Users\Names**. Внутри Вы увидим список имён всех локальных учёток

![](../../_images/16d3cf8cdeda.jpg)

Нажмите по подключу **vasya** - в правой панели **regedit** в строке **(Default)** в колонке **Type** будет указано значение вида **REG_&lt;RID_в_hex>**, например **0x3ec (1004)**. Это и есть **RID** пользователя **vasya** в hex - именно по этому имени называется его подключ в **Users**

![](../../_images/a26c6625e80c.jpg)

Запомните это число - оно понадобится буквально через минуту.

#### Резервная копия ветки жертвы

> **Предупреждение.** Прежде чем менять байты значения **F**, экспортируйте подключ жертвы. Это запасной слой защиты сверх снапшота ВМ: если что-то пойдёт не так, ветку можно будет восстановить точечно, не откатывая весь снимок.

В **regedit** развернём **HKLM\SAM\SAM\Domains\Account\Users&lt;RID_hex>** (для примера выше - **000003EC**). Нажмём правой кнопкой по этому подключу, выберите **Export**

![](../../_images/345eb68795c1.jpg)

В открывшемся окне укажите путь сохранения, например **C:\Lab\vasya_backup.reg**, и нажмём **Save**. Файл с расширением **.reg** будет содержать полное дерево значений жертвы и при необходимости импортируется обратно через **regedit** -> **Import**

![](../../_images/efca99c40862.jpg)

#### Модификация поля F

Войдите в подключ жертвы (например, **HKLM\SAM\SAM\Domains\Account\Users\000003EС**). В правой панели **regedit** найдите значение **F** типа **REG_BINARY**. Нажмём по нему дважды - откроется окно **Edit Binary Value**, где видна сырая бинарная структура значения.

![](../../_images/be0d539f04bd.jpg)

> **Предупреждение.** Изменяйте **строго четыре байта** на смещении **0x30**. Адрес смещения отображается в левой колонке окна **Edit Binary Value**. Соседнее смещение **0x38** содержит флаг **enabled / disabled** - его трогать **нельзя**, иначе учётка может оказаться отключённой или повреждённой.

Для **vasya** с **RID 0x3EС** там лежит последовательность **EС 03 00 00**. Аккуратно замените эти четыре байта на **F4 01 00 00** - это **0x1F4** = **500**, **RID** встроенного администратора в **little-endian**. Все остальные байты значения **F** не трогайте. Нажмём **OK**.

Закройте **regedit** (запущенный под **SYSTEM**) и окно **cmd** под **SYSTEM** - они больше не нужны.

#### Проверка эффекта атаки

После изменения байтов в **SAM** атака уже сработала на уровне реестра: при любом построении токена для **vasya** подсистема **LSASS** теперь будет подставлять **RID 500**. Чтобы это увидеть, не нужно выходить из текущей сессии и заходить под **vasya** - достаточно запустить процесс **от имени vasya** прямо из текущего окна командой **runas**, которая создаёт новый токен с учётными данными указанного пользователя.

> **Предупреждение.** На **Windows 11** полноценный вход (**Sign out** -> вход на экране **Welcome**) под учётной записью, у которой подменён **RID**, приводит к рассинхрону между токеном (где **RID 500**) и записью **ProfileList** в реестре (где привязка к нативному **SID** жертвы). Подсистема построения профиля не понимает, чей профиль грузить, и сессия зависает на сером экране, либо создаётся временный профиль. Это **известное побочное явление** **RID Hijacking** на современных Windows, поэтому ниже Вы будете проверять эффект атаки через **runas** - так создаётся только токен, без пересборки профиля, и проблема не возникает.

Откройте **PowerShell от имени администратора** (та же сессия, в которой Вы работали) и выполним: `runas /user:vasya "powershell.exe -NoExit -Command whoami /user; whoami /groups; New-Item -Path C:\Windows\System32\rid_hijack_proof.txt -ItemType File -Force"`

![](../../_images/a0388d9a3003.webp)

В окне запроса пароля введите **P@ssword123**. Откроется новое окно **PowerShell**, в заголовке которого будет указано **running as <имя_компьютера>\vasya**. В этом окне автоматически выполнятся три команды

![](../../_images/3783728cb6c1.jpg)
- **Первая команда** - **whoami /user** - покажет **SID** текущего токена. И это и есть главное доказательство атаки: в **SID** последнее число (**RID**) будет **500**, а не нативный **1004** для **vasya**. То есть подсистема **LSASS** при создании токена прочитала из **SAM** поле **F** на смещении **0x30**, обнаружила там **F4 01 00 00**, интерпретировала как **RID 500** и построила токен встроенного администратора, хотя имя пользователя при этом - **vasya**
- **Вторая команда** - **whoami /groups** - выведет список групп токена. В нём появится строка **BUILTIN\Administrators** со статусом **Enabled by default, Enabled group**. **Vasya** на уровне токена теперь является администратором
- **Третья команда** - **New-Item C:\Windows\System32\rid_hijack_proof.txt** - создаст файл в защищённом системном каталоге. Каталог **C:\Windows\System32** требует прав администратора для записи; для обычного пользователя такая команда вернула бы ошибку доступа. Здесь файл создаётся без ошибки - последнее доказательство, что **vasya** работает в контексте администратора

Окно **PowerShell от имени vasya** можно теперь закрыть.

#### Парадокс скрытности

Самое интересное в этой технике - её незаметность для стандартных средств аудита. В Вашей основной сессии **PowerShell от имени администратора** выполним: `Get-LocalGroupMember -Group "Administrators"`

![](../../_images/11b0fd347bc0.webp)

В выводе Вы **не увидите** **vasya**. Группа **Administrators** содержит только тех, кого туда добавили явно через **Add-LocalGroupMember** или **GUI**, - сам факт подмены **RID** не отражается в членстве групп, потому что атака меняет не списки членов, а внутреннюю структуру учётной записи в **SAM**. На уровне обычного аудита это абсолютно скрытная техника: учётка по всем спискам - обычный пользователь, а по реальным правам - администратор.

Сверить это можно и через **Computer Management**: откройте **compmgmt.msc**, развернём **Local Users and Groups** -> **Groups**, дважды нажмём по **Administrators** - в окне **Members** **vasya** также не будет. Графическая оснастка опирается на те же данные о членстве групп, что и **Get-LocalGroupMember**, и тоже не показывает атаку

![](../../_images/a6cf02158cd0.jpg)

Способ обнаружения атаки тоже виден в этом противоречии: если у пользователя, которого нет в группе **Administrators**, при анализе токена через **whoami /user** или через инвентаризацию активных процессов внезапно обнаруживается **RID 500** или членство в **BUILTIN\Administrators** - это и есть аномалия, на которую должен реагировать аудит. Этот же подход - сверка не списка членов группы, а фактического содержимого токенов - разбирается в блоке защиты ниже.

#### Как защититься

Несколько практических мер, которые закрывают или хотя бы детектируют **RID Hijacking**:

- **Аудит изменений ключей в HKLM\SAM**. Любая модификация подключей внутри **HKLM\SAM\SAM\Domains\Account\Users** - подозрительное событие, требующее расследования. Это можно ловить штатным аудитом реестра через **Event ID 4657** в журнале **Security** или через **Sysmon**; детальный разбор работы журналов и **Sysmon** - тема другой статьи, здесь достаточно понимать, что сама ветка должна быть включена в политику аудита
- **Регулярный аудит локальных учёток с проверкой реального токена**. Стандартная сверка **Get-LocalGroupMember** Administrators не поймает подменённый **RID**. Однако сверить можно фактический **SID-RID** в токенах активных сеансов. Если в выводе **Get-WmiObject Win32_LoggedOnUser** или при анализе процессов explorer.exe для разных учёток обнаруживается, что у обычного пользователя процесс работает с **SID**, заканчивающимся на **-500**, - это и есть та самая аномалия
- **Контроль доступа к PsExec** и аналогичным инструментам повышения привилегий. Сам факт запуска **PsExec -s** на пользовательской машине без производственной необходимости - повод для разбора
