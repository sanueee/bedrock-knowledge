### Работа с драйверами

Начнём с базовой проверки: что загружено в ядро, откуда и подписано ли. Без этого невозможно отличить легитимный драйвер от **BYOVD**.

Тестовые драйвера, который мы будем рассматривать, подписаны самоподписанным сертификатом - не доверенным Microsoft. По умолчанию Windows запрещает загрузку таких драйверов через механизм **DSE (Driver Signature Enforcement)** Для обхода включим **режим тестовой подписи** - официальный режим Windows для разработчиков драйверов.

> **Важно:** Test Mode используется только в изолированной лабораторной VM. В реальной атаке BYOVD атакующий **не включает** этот режим - он использует уже подписанный легитимный драйвер с уязвимостью. Именно поэтому BYOVD так опасен: никаких специальных режимов не требуется.

В **системе** выключаем **Secure boot**

![](../../_images/385003258925.webp)

Запускаем VM и открываем **Powershell** от имени администратора:

```
Get-CimInstance -ClassName Win32_DeviceGuard `

Select-Object VirtualizationBasedSecurityStatus, `

Разбор команды:

- **Get-CimInstance** - обращается к **WMI**/**CIM** для получения системной информации
- **-ClassName Win32_DeviceGuard** - класс который содержит данные о состоянии **VBS** и **HVCI**
- **-Namespace root\Microsoft\Windows\DeviceGuard** - пространство имён где находится этот класс

![](../../_images/90ee4bfa4079.webp)

Посмотрим результат: Import-Csv C:\Labs\hvci_status.csv

![](../../_images/c9e7c5be552b.webp)

> Расшифровка значений **VirtualizationBasedSecurityStatus**: **0** - VBS отключён **1** - VBS включён но не активен **2** -VBS активен, защита работает
> 
> 
> 
> Если значение не равно **2** - система уязвима к **BYOVD** в полной мере.

Сохраним список всех загруженных драйверов - это базовая точка отсчёта, с которой мы сравним состояние системы после загрузки тестового драйвера:

```
driverquery /v /fo csv | ConvertFrom-Csv |
Select-Object "Module Name", "Start Mode", "State", "Path" |
Export-Csv C:\Labs\drivers_list.csv -NoTypeInformation
```

Разбор команды:

- **driverquery /v /fo csv** - выводит подробный список всех загруженных драйверов в формате CSV
- **ConvertFrom-Csv** - преобразует **CSV**-текст в объекты **PowerShell** для удобной фильтрации
- **Select-Object** - выбирает только нужные колонки
- **Export-Csv** - сохраняет результат в файл. Флаг **-NoTypeInformation** убирает служебную строку из начала **CSV**

![](../../_images/47a2e86977c9.webp)

Посмотрим результат: `Import-Csv C:\Labs\drivers_list.csv | Format-Table -AutoSize`

![](../../_images/9ae17bd118f8.webp)

> Обратим внимание на колонку **Path**. Все легитимные системные драйверы находятся в **C:\Windows\System32\drivers**. Любой драйвер из другого места - повод для проверки

Теперь отфильтруем только те драйверы, которые загружены не из системных папок - именно так выглядит аномалия при реальной атаке:

```
driverquery /v /fo csv | ConvertFrom-Csv |
Where-Object {
$_."Path" -notlike "*\Windows\System32\*" -and
$_."Path" -notlike "*\Windows\SysWOW64\*" -and
$_."Path" -ne ""
} |
Select-Object "Module Name", "Start Mode", "State", "Path" |
Export-Csv C:\Labs\nonstandard_drivers.csv -NoTypeInformation

```

Разбор команды:

- **Where-Object** - фильтрует объекты по условию
- **-notlike "*\Windows\System32\*"** - исключает пути содержащие системную папку. Символ ***** означает любой набор символов
- **-and** - оба условия должны выполняться одновременно
- **-ne ""** - исключает пустые значения пути

![](../../_images/071b270c9df5.webp)

Посмотрим результат: `Import-Csv C:\Labs\nonstandard_drivers.csv`

![](../../_images/f6f334fca052.webp)

> Легитимные системные драйверы загружаются из **C:\Windows\System32\drivers**. Драйвер загруженный атакующим через **sc.exe** будет находиться в другом месте - это и есть аномалия.

Загрузим тестовый драйвер:

```
sc.exe create LabTestDrv type= kernel binPath= C:\Temp\labtest.sys
sc.exe start LabTestDrv
```

Разбор команды:

- **sc.exe** - утилита управления службами и драйверами Windows
- **create LabTestDrv** - создаёт новый сервис с именем **LabTestDrv**
- **type= kernel **- указывает что это драйвер режима ядра, а не обычная служба
- **binPath= C:\Temp\labtest.sys** - путь к файлу драйвера
- **start LabTestDrv** - запускает зарегистрированный драйвер

![](../../_images/3183ccdaa3b6.webp)

Теперь снова поищем драйвера вне системных папок:

```
driverquery /v /fo csv | ConvertFrom-Csv |
Where-Object {
$_."Path" -notlike "*\Windows\System32\*" -and
$_."Path" -notlike "*\Windows\SysWOW64\*" -and
$_."Path" -ne ""
} |
Select-Object "Module Name", "Start Mode", "State", "Path" |
Export-Csv C:\Labs\nonstandard_drivers.csv -NoTypeInformation
Import-Csv C:\Labs\nonstandard_drivers.csv
```

![](../../_images/8864903030a4.webp)

Проверим подпись драйвера:

```
Get-AuthenticodeSignature C:\Temp\labtest.sys |
Select-Object Path, Status, SignerCertificate |
Export-Csv C:\Labs\driver_signature.csv -NoTypeInformation
Import-Csv C:\Labs\driver_signature.csv
```

![](../../_images/e591ab25735e.webp)

> **Get-AuthenticodeSignature** проверяет цифровую подпись файла и возвращает информацию о сертификате и статусе подписи. Возможные статусы: **Valid** - подпись валидна, **NotSigned** - файл не подписан, **UnknownError** - подпись есть но сертификат не доверенный (Именно такие сертификаты у нас используется в практике)

Выгрузим тестовый драйвер:

- Остановим работающий драйвер: `sc.exe stop LabTestDrv`
- Удалим регистрацию сервиса из системы: `sc.exe delete LabTestDrv`

### Атака DLL Hijacking

В этой части мы будем использовать **legitimate.exe** - приложение, которое при запуске ищет **vuln.dll** по стандартному порядку поиска Windows. **vuln.dll** - вредоносная библиотека: при загрузке она устанавливает обратное соединение с машиной атакующего.

> Перед началом убедимся что IP-адрес нашей **Debian** машины - **192.168.0.108**. Если адрес другой - меняем его в настройках сети перед выполнением атак.

Перед тем как подкладывать **DLL**, нужно понять какие именно библиотеки ищет приложение и не находит. Для этого используем **Process Monitor** инструмент **Sysinternals**, который в реальном времени показывает все файловые операции процессов

Откроем **Process Monitor** - файл **C:\Tools\Procmon.exe**

![](../../_images/5dbd2f8c5ac5.webp)

Настроим фильтры: Перейдем в **filter** нажав **Ctrl + L**

![](../../_images/dd5ab7d7fb2e.webp)

Выбираем **Process Name** - **is** - `legitimate.exe` - **Include** и нажимаем **Add**

![](../../_images/70bb905f5321.webp)

Также делаем с остальными:

- **Result** - **is** - `NAME NOT FOUND` - **Include**
- **Path** - **ends with** - `.dll` - **Include**

> Эти три фильтра вместе показывают только те **DLL** которые приложение ищет и не находит - именно это нужно атакующему для выбора цели.

![](../../_images/35c35c6a30dd.webp)

Запускаем **legitimate.exe** чтобы **Process Monitor** перехватил его файловые операции и показал какие **DLL** приложение ищет и не находит - именно эти имена станут целью для подмены: `Start-Process C:\Labs\DLLHijack\app\legitimate.exe`

![](../../_images/4daf8dc73163.webp)

Мы убедились какие **DLL** ищет приложение. Теперь разберём три способа подложить вредоносную библиотеку - каждый эксплуатирует свою точку в порядке поиска.

#### Hijacking через папку приложения

Когда приложение вызывает **LoadLibrary("vuln.dll")** Windows ищет файл по фиксированному порядку. Первое место в этом порядке - папка из которой запущено само приложение. Если атакующий может записать файл в эту папку - он кладёт туда **DLL** с нужным именем и при следующем запуске приложения его код выполняется автоматически.

**Цепочка атаки злоумышленника:**

1. Атакующий кладёт **vuln.dll** в папку приложения
2. Пользователь запускает **legitimate.exe**
3. Windows находит **DLL** в папке приложения первой
4. Вредоносный код выполняется в контексте процесса

Никаких эксплойтов, никаких уязвимостей в коде приложения - только неправильные права на папку или ошибка в порядке поиска DLL. Именно поэтому этот сценарий так распространён: он работает против легитимных приложений которые просто не нашли нужную **DLL** в системе.

Скопируем вредоносную DLL в папку приложения: `Copy-Item C:\Labs\DLLHijack\payload\vuln.dll C:\Labs\DLLHijack\app\vuln.dll`

![](../../_images/746900aca0c1.webp)

На **Debian** запустим **netcat** в режиме прослушивания на порту **4444**: `nc -lvp 4444`

![](../../_images/5b9c057d84eb.webp)

На windows машине запустим приложение: `Start-Process C:\Labs\DLLHijack\app\legitimate.exe`

![](../../_images/4daf8dc73163.webp)

На **Debian** появится входящее соединение - это означает что вредоносная **DLL** загрузилась и выполнилась. Чтобы убедиться от чьего имени работает наш код введём: `whoami`

![](../../_images/f3ff2288435e.webp)

Для следующего сценария удалим **C:\Labs\DLLHijack\app\vuln.dll: **`Remove-Item C:\Labs\DLLHijack\app\vuln.dll -ErrorAction SilentlyContinue`

#### Hijacking через PATH

Переменная окружения **PATH** содержит список папок в которых Windows ищет исполняемые файлы и библиотеки. Когда приложение запрашивает **DLL** и не находит её в системных папках - Windows перебирает папки из **PATH** по порядку.

Уязвимость возникает когда в **PATH** попадает папка с правами записи для обычных пользователей. Это частая ошибка администраторов: добавили папку для удобства запуска скриптов, но не ограничили права. В результате любой пользователь может положить туда файл с нужным именем и он загрузится вместо легитимной **DLL**.

**Цепочка атаки злоумышленника:**

1. Находит папку в **PATH** с правами записи
2. Определяет через **Process Monitor** какую **DLL** ищет целевое приложение
3. Кладёт вредоносную **DLL** в эту папку под нужным именем

Смоделируем ошибку администратора - добавим **C:\Tools** в **PATH** с правами записи для пользователей:

```
$currentPath = [Environment]::GetEnvironmentVariable("PATH", "Machine")
[Environment]::SetEnvironmentVariable("PATH", "$currentPath;C:\Tools", "Machine")
icacls "C:\Tools" /grant "BUILTIN\Users:(OI)(CI)W" /T 
```

Разбор команды:

- **[Environment]::GetEnvironmentVariable("PATH", "Machine")** - читает системную переменную **PATH**
- **SetEnvironmentVariable** - устанавливает новое значение. **"Machine"** означает системный уровень
- **icacls /grant "BUILTIN\Users:(OI)(CI)W"** - выдаёт группе **Users** права записи. **OI** и **CI** означают что права распространяются на файлы и вложенные папки
- **/T** - применяет рекурсивно

![](../../_images/74e38ae02d59.webp)

Проверим какие папки из **Path** доступны для записи. Перейдём в пользователя **Student**, откроем **PowerShell** и выполним скрипт:

```
$env:PATH -split ';' | Where-Object { $_ -ne "" } | ForEach-Object {
if (Test-Path $_) {
$acl = Get-Acl $_ -ErrorAction SilentlyContinue
$writable = $acl.Access | Where-Object {
$_.FileSystemRights -match 'Write|FullControl' -and
$_.IdentityReference -notmatch 'SYSTEM|Administrators|TrustedInstaller'
}
if ($writable) {
[PSCustomObject]@{ Path = $_; Writable = $true }
}
}
} | Export-Csv C:\Labs\path_writable.csv -NoTypeInformation
Import-Csv C:\Labs\path_writable.csv

```

Разбор команды:

- **$env:PATH -split ';'** - разбивает строку **PATH** на массив папок по разделителю **;**
- **ForEach-Object** - выполняет блок кода для каждого элемента массива
- **Get-Acl** - читает список контроля доступа (**ACL**) для папки
- **$_.FileSystemRights -match 'Write|FullControl'** - проверяет наличие прав записи
- **$_.IdentityReference -notmatch 'SYSTEM|Administrators|TrustedInstaller'** - исключает системные учётные записи
- **[PSCustomObject]@{}** - создаёт объект с нужными полями для вывода

![](../../_images/5efe46f07c84.webp)

Мы видим **C:\Tools** - папка с правами записи есть в **PATH**. Скопируем **DLL** туда:

`Copy-Item C:\Labs\DLLHijack\payload\vuln.dll "C:\Tools\vuln.dll"`

#### DLL Side-Loading

**DLL Side-Loading** - техника при которой легитимное **подписанное** приложение используется как носитель для вредоносной DLL. Приложение загружает DLL по относительному пути без проверки её подписи. Атакующий кладёт свою **DLL** рядом с легитимным **.exe** - и при запуске приложения вредоносный код выполняется автоматически.

Ключевое отличие от других сценариев: здесь запускается **подписанный легитимный файл**. Это позволяет обходить контроль по имени процесса и пути запуска.

**Цепочка атаки злоумышленника:**

1. Атакующий копирует **legitimate.exe** и **vuln.dll** в новую папку
2. Запускает **exe**
3. Windows загружает **DLL** из той же директории
4. Код выполняется.

Возвращаемся в пользователя **Admin**

Скопируем приложение в новую директорию:

- Cоздадим папку для записи файлов: `New-Item -ItemType Directory -Path C:\Labs\DLLHijack\attack -Force`
- Перенесём туда наш **легитимный файл: **`Copy-Item C:\Labs\DLLHijack\app\legitimate.exe C:\Labs\DLLHijack\attack\legitimate.exe`

![](../../_images/14ce6e9a12a7.webp)

Select-Object Path, Status
```

![](../../_images/04dca317371c.webp)

> **UnknownError** здесь не ошибка в привычном смысле - это статус подписи: файл подписан, но сертификат не доверенный. Для нашего тестового драйвера это ожидаемый результат.

Скопируем вредоносную **DLL**: `Copy-Item C:\Labs\DLLHijack\payload\vuln.dll C:\Labs\DLLHijack\attack\vuln.dll`

![](../../_images/c077b09419a4.webp)
