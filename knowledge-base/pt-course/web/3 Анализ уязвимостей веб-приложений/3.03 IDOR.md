# IDOR

### Что такое IDOR

**IDOR** (Insecure Direct Object Reference) - уязвимость, возникающая, когда веб-приложение использует вводимые пользователем данные (ID из URL) для прямого доступа к объекту, **не проверяя**, имеет ли текущий пользователь право на доступ к этому объекту.

## 

![](../../_images/2173ccbdb5a1.webp)

### В чём заключается уязвимость

Причина IDOR - **отсутствие проверки прав доступа **на стороне сервера. Приложение доверяет идентификатору, который приходит от пользователя, и не проверяет принадлежность данных текущему пользователю. Вы заходите в личный кабинет интернет-банка **https://bank.ru/account?user_id=1001** меняете **1001 **на **1002** - и видите чужой счёт. Это банальный пример** IDOR**.

#### Виды IDOR

| Вид | Описание |
|---|---|
| Прямой IDOR | Пользователь меняет идентификатор в запросе и получает доступ к чужому объекту |
| IDOR второго порядка | Идентификатор сначала сохраняется, а затем используется для доступа. Проверка прав есть на первом шаге, но отсутствует на втором |

#### Прямой IDOR

В компании используется CRM-система для менеджеров по продажам. Каждый менеджер видит только своих клиентов. Доступ осуществляется через параметр **manager_id** в URL. Суть уязвимости заключается в том, что система доверяет параметру **manager_id **из URL и не проверяет, принадлежит ли этот **ID** текущему пользователю.

Рассмотрим уязвимость на примере.

![](../../_images/72296a72cd8d.webp)

Менеджер (ID 201) входит в CRM под своими учётными данными. На странице отображаются клиенты, номера телефонов, email, суммы контрактов и внутренние комментарии.

![](../../_images/1b9cdc95d93f.webp)

Что будет, если менеджер изменит GET-параметр **manager_id** на другое значение? Например изменим **manager_id** с **201 **на **202** в **URL **`http://127.0.0.1:5000/clients?manager_id=202` cистема без каких-либо проверок отобразит клиентов другого менеджера:

![](../../_images/abf78d58fa68.webp)

В результате менеджер без каких-либо прав получает доступ к коммерческой информации другого отдела, контактным данным клиентов, внутренним комментариям. Уязвимость возникает из-за отсутствия проверки прав доступа к объекту. Сервер использует **manager_id** из запроса, но не сверяет его с идентификатором текущего пользователя из сессии. **/clients?manager_id=202** должен возвращать клиентов только если **session.user_id == 202**.

#### IDOR второго порядка

В HR-системе руководители могут формировать отчёты по зарплатам своих сотрудников. Процесс двухэтапный:

1. Руководитель заказывает отчёт. Система создаёт задание и запоминает, кто его создал.
2. Через некоторое время отчёт становится доступен для скачивания по ссылке с **report_id**.

Руководитель отдела продаж **(ID 301**) заказывает отчёт по своему отделу. Через несколько минут он скачивает его по ссылке. Затем он пробует подставить другой **report_id** - и получает отчёт по зарплатам другого отдела. Система проверяет пользователя при создании отчёта, но не проверяет при скачивании. Проверка авторизации есть на первом шаге, но отсутствует на втором. Так Руководитель отдела продаж (ID 301) входит в HR-систему.

![](../../_images/b96020b03856.webp)

Руководитель нажимает **Order a report** для своего отдела. Система создаёт задание и генерирует уникальный идентификатор отчёта.

![](../../_images/589ac9448f0f.webp)

Переадресация на скачивание отчёта под данным **URL** `http://127.0.0.1:5000/download_report?report_id=RPT-ae7e9`

![](../../_images/c0fc9b24d7f6.webp)

Подробнее разберем суть уязвимости.На сервере хранится соответствие:

```
{
  "report_id": "RPT-a1b2c",
  "owner_id": 301,
  "data": "..."
}
```

При скачивании сервер не проверяет, что **owner_id** совпадает с текущим пользователем:

```
report = reports.get(report_id)
return report.data
```

После того как руководитель отдела продаж получил ссылку на свой отчёт, он обращает внимание на структуру **URL**. В адресной строке браузера отображается `http://127.0.0.1:5000/download_report?report_id=RPT-ae7e9`. Руководитель знает, что идентификаторы отчётов других отделов выглядят похожим образом, поэтому он изменяет параметр **report_id**, подставляя другой идентификатор `http://127.0.0.1:5000/download_report?report_id=RPT-eaa99` система, не выполняя никакой проверки прав доступа, принимает запрос и возвращает отчёт, связанный с этим идентификатором. В результате руководитель отдела продаж получает доступ к отчёту, сформированному для другого подразделения. Видим, что руководитель без каких-либо на то прав получает доступ к конфиденциальной информации другого отдела.

![](../../_images/5369b36dabbe.webp)

**IDOR второго порядка **возникает, когда проверка авторизации выполняется на этапе создания объекта, но отсутствует при его последующем скачивании, специалисту по анализу защищенности достаточно знать или подобрать **report_id**, чтобы получить доступ к чужим данным. Успешная эксплуатация такой уязвимости может привести к утечки конфиденциальной информации, повышения привилегий и несанкционированного доступа к административным функциям.

### Инструменты, используемые атакующими для обнаружения и последующей эксплуатации Insecure Direct Object References

- [**Burp Suite**](https://portswigger.net/burp) - это популярный набор инструментов для тестирования безопасности веб-приложений, который включает функции для обнаружения IDOR-уязвимостей. В **Burp Suite** есть расширения, такие как **Burp Scanner** и **Burp Intruder**, которые помогают обнаруживать IDOR путем модификации HTTP-запросов и тестирования различных GET- и POST-параметров.
- [**IDOR detect tool**](https://github.com/y1nglamore/IDOR_detect_tool) - путем замены аутентификационной информации и повторного воспроизведения запроса, а также сравнения результатов пакета определяется, существует ли в интерфейсе уязвимость IDOR.
- [**XRCross**](https://github.com/pikpikcu/xrcross) - инструмент для поиска и анализа уязвимостей, в том числе IDOR.
- [**IDOR-Forge**](https://github.com/errorfiathck/IDOR-Forge) - мощный и универсальный инструмент, предназначенный для обнаружения уязвимостей IDOR
