# Механизмы аутентификации: Cookie-based, JWT

> [!info] Путь в курсе
> Глава 4: Веб-приложения и безопасность веб-приложений / Часть 1: Основы веб-приложения

#### Что такое аутентификация и авторизация

Прежде чем рассматривать механизмы, важно разграничить два понятия:

- **Аутентификация** - подтверждение личности пользователя. Система проверяет, тот ли это человек, за кого себя выдаёт. Например: ввод логина и пароля, сканирование отпечатка пальца, вход через Google.
- **Авторизация** - предоставление прав и определение, к каким ресурсам пользователь может получить доступ. Например, после входа в систему пользователь получает возможность просматривать собственный профиль, однако доступ к административной панели для него остаётся закрытым.

Аутентификация происходит один раз (в момент входа). Авторизация проверяется при каждом обращении к защищённому ресурсу.

##### Cookie-based-аутентификация

Это классический механизм аутентификации, используемый на большинстве традиционных веб-сайтов. Он основан на сессиях и cookies.

##### Как это работает

1. Пользователь отправляет на сервер логин и пароль.
2. Сервер проверяет учётные данные. Если они верны, создаёт **сессию** - запись в своём хранилище, где сохраняет информацию о пользователе (ID, роль, время входа).
3. Сервер генерирует уникальный идентификатор сессии - **Session ID** и отправляет его браузеру в **cookie** с помощью HTTP-заголовка **Set-Cookie**.
4. Браузер сохраняет эту cookie и теперь автоматически прикладывает её к каждому последующему запросу к этому сайту.
5. При получении запроса сервер смотрит на **Session ID** в cookie, находит по нему сессию в своём хранилище и таким образом узнаёт пользователя.

Сервер **хранит состояние** (все активные сессии в БД или кэше). Это называется **stateful**-подход.

**Плюсы и минусы**

| Плюсы | Минусы |
|---|---|
| Простота реализации | Нагрузка на сервер - при каждом запросе нужно искать сессию в хранилище |
| Возможность мгновенно завершить сессию | Проблемы с масштабированием - при нескольких серверах нужно общее хранилище сессий. |
| Использование HttpOnly cookie защищает от некоторых уязвимостей (токен недоступен JavaScript) | При росте числа пользователей растёт и хранилище сессий |

##### JWT (JSON Web Token)

Это современный механизм, широко применяемый в API, микросервисах и SPA (одностраничных приложениях). **JWT** - это самодостаточный токен, содержащий всю информацию о пользователе внутри себя.

**Как это работает**

1. Пользователь отправляет на сервер логин и пароль.
2. Сервер проверяет учётные данные. Если они верны, генерирует **JWT** - закодированную строку, внутри которой зашита информация о пользователе (его ID, роль) и время жизни токена.
3. Сервер отправляет этот JWT обратно клиенту (обычно в теле ответа или в cookie).
4. Клиент сохраняет токен (например, в **localStorage**, **sessionStorage** или в памяти) и при каждом запросе к API добавляет его в заголовке **Authorization: Bearer &lt;token>**.
5. Сервер, получив запрос, проверяет подпись JWT и срок его действия (поле **exp**). Если проверка пройдена, сервер доверяет информации, содержащейся в токене. Обращение к базе данных для верификации пользователя не требуется.

![](../../_images/09a088cfdefc.webp)

**Ключевые свойства JWT:**

- **Самодостаточность.** Токен содержит всю необходимую информацию о пользователе и его правах, что позволяет серверу не обращаться к базе данных для валидации.
- **Безопасность.** Подпись токена гарантирует его целостность и подлинность.
- **Ограниченное время жизни.** Каждый токен имеет поле **exp**, определяющее момент его истечения.

**Типы JWT в системах авторизации:**

| Тип | Назначение | Срок жизни | Характеристика |
|---|---|---|---|
| Access Token | Используется для доступа к защищённым ресурсам API | Короткий | Многоразовый, передаётся с каждым запросом |
| Refresh Token | Используется для получения новой пары токенов после истечения access token | Длительный | Одноразовый, хранится в защищённом хранилище на клиенте |

**Структура JWT:** Токен состоит из трёх частей, разделённых символом точки (**.**):

![](../../_images/9e82c99be1a2.webp)

| Часть | Назначение | Пример содержимого |
|---|---|---|
| Header | Содержит метаинформацию о токене: тип токена и алгоритм формирования подписи | {"alg": "HS256", "typ": "JWT"} |
| Payload | Содержит набор утверждений - данные, передаваемые токеном | {"sub": "user123", "exp": 1743000000, "role": "admin"} |
| Signature | Представляет собой результат криптографического преобразования (header + payload) с использованием секретного ключа | Результат подписания |

**Стандартные утверждения:**

| Поле | Название | Назначение |
|---|---|---|
| iss | Издатель | Идентификатор приложения, выпустившего токен |
| sub | Субъект | Идентификатор пользователя, которому выдан токен |
| aud | Получатель | Массив URL серверов, для которых предназначен токен |
| exp | Время истечения | UNIX-временная метка, после которой токен считается недействительным |
| nbf | Не ранее | Временная метка, до которой токен недействителен |
| iat | Время выдачи | UNIX-временная метка создания токена |
| jti | Идентификатор токена | Уникальный идентификатор токена (предотвращает повторное использование) |

**Процедура валидации JWT на сервере:**

1. Извлечь JWT из заголовка HTTP-запроса.
2. Определить алгоритм подписи из поля **alg** заголовка.
3. Вычислить сигнатуру для комбинации **header + "." + payload** с использованием того же алгоритма и секретного ключа.
4. Сравнить вычисленную сигнатуру с переданной **signature**. При несовпадении вернуть HTTP-статус **401 Unauthorized**.
5. Проверить срок действия токена: значение **exp** должно быть больше текущего времени. При истечении срока вернуть **401 Unauthorized**.
6. Проверить дополнительные утверждения: **iss**, **aud**, **nbf**.
7. При успешном прохождении всех проверок обработать запрос, используя данные из payload.

![](../../_images/24e666872608.webp)

**Способы передачи JWT:**

| Направление | Способ передачи | Пример |
|---|---|---|
| От сервера к клиенту | В теле HTTP-ответа | {"access_token": "&lt;jwt>"} |
| От сервера к клиенту | В заголовке Set-Cookie | Set-Cookie: accessToken=&lt;jwt>; HttpOnly; Secure |
| От клиента к серверу | В заголовке Authorization | Authorization: Bearer &lt;jwt> |
| От клиента к серверу | В заголовке Cookie | Cookie: accessToken=&lt;jwt> |

А сейчас подробнее рассмотрим выдачу JWT на примере ранее используемой **CMS Directus**. Для запуска необходимо добавить переменную окружения **SECRET="random_secret_456"**. Данная переменная будет использоваться для подписи JWT. В итоге контейнер будет запускаться командой: `sudo docker run -d --name my-directus -p 8055:8055 -e ADMIN_EMAIL="pt_student@example.com" -e ADMIN_PASSWORD="strong_password" -e SECRET="random_secret_456" directus/directus`

Как было упомянуто ранее, JWT состоит из 3 частей, закодированных в base64 и разделенными точкой. Декодированные части мы можем видеть в правой части сайта. Для данного токена:

3. **1dv6aos6hfcvjWGhZoUdQQQ3xWhPDJYTt_J8xaYJ5Rs** - signature;

##### Header

**Header** содержит поле **alg**, которое является обязательным. Оно содержит алгоритм подписи. Для обеспечения целостности JWT применяются различные алгоритмы цифровой подписи. Они делятся на две основные категории: симметричные и асимметричные.

К симметричным алгоритмам относится семейство HMAC, например **HS256**, **HS384** и **HS512**. В таких алгоритмах для создания подписи и для её проверки используется один и тот же ключ.

Асимметричные алгоритмы используют пару ключей: закрытый ключ применяется для подписи токена, а открытый для проверки подписи. Наиболее распространёнными являются алгоритмы **RS256**, **RS384**, **RS512**, основанные на RSA, а также **ES256**, **ES384**, **ES512**, использующие криптографию на эллиптических кривых.

> Также поле **alg** может содержать значение **none**. В таком случае криптографическая подпись не применяется, а целостность токена не обеспечивается средствами асимметричной или симметричной криптографии.

Поле **typ** используется для указания типа содержимого токена. Наиболее распространённым значением является **typ: "JWT"**, которое сообщает получателю, что данный объект следует интерпретировать как JSON Web Token. Данное поле носит информационный характер и не является обязательным. Он предназначен для упрощения обработки токена различными системами и библиотеками. Его наличие позволяет явно определить формат передаваемых данных, особенно в случаях, когда приложение работает одновременно с несколькими типами объектов или токенов.

##### Payload

Данная часть содержит набор утверждений о пользователе. Это вспомогательные данные необходимые для приложения.

```
{
  "id": "3de6e428b-7d45-4bfc-b0b8-a334316b0083",
  "admin_access": false,
  "iat": 1779056664,
  "name": "ptsecurity"
}
```

В данном примере токен содержит следующие данные:

- **id** - уникальный идентификатор пользователя;
- **admin_access** - флаг наличия/отсутствия административных прав;
- **name** - имя пользователя;
- **iat** - время выдачи токена в формате Unix time.

##### Signature

Часть **Signature** в JWT используется для обеспечения целостности и подлинности токена. Она гарантирует, что содержимое **header** и **payload** не было изменено после выпуска токена. Подпись необходима для защиты от подделки данных. Если кто-то изменит payload, как в случае токена из примера, **admin_access: false** на **true**, подпись станет недействительной. Также подпись необходима для подтверждения, что токен был выпущен доверенным сервером авторизации.
