# Веб-серверы, прокси, CDN

## Что такое веб-сервер

**Веб-сервер** - это программное обеспечение, которое принимает HTTP-запросы от клиентов (например, браузеров) и отправляет им ответы. Он управляет сетевыми соединениями, раздает статический контент (HTML, CSS, изображения) и может передавать динамические запросы веб-приложениям.

![](../../_images/61579006ef08.webp)

Веб-сервер выполняет следующие функции:

1. **Управление сетевыми соединениями** - прослушивание определённого порта (обычно 80 для HTTP и 443 для HTTPS), принятие входящих соединений, их обслуживание и закрытие.
2. **Обслуживание статического контента** - при получении запроса к статическому файлу (HTML, CSS, JavaScript, изображения, видео) веб-сервер считывает этот файл с диска и отправляет его клиенту без какой-либо дополнительной обработки.
3. **Проксирование динамических запросов** - если запрос требует выполнения программной логики, веб-сервер передаёт этот запрос специализированному веб-приложению, а полученный от приложения результат возвращает клиенту.

> **Проксирование** - технология, в которой сервер позволяет клиентам выполнять косвенные запросы к другим сетевым службам.

### Популярные веб-серверы

| Сервер | Ключевые особенности |
|---|---|
| Nginx | Асинхронный, событийно-ориентированный. Высокая производительность, эффективное потребление ресурсов. |
| Apache | Модульный веб-сервер, поддерживающий PHP, Python, Perl и другие языки. Ранее был самым популярным решением, но сейчас всё чаще уступает Nginx и Caddy из-за более низкой производительности при высоких нагрузках. |
| Microsoft IIS | Веб-сервер для Windows, тесно интегрирован с технологиями Microsoft. |
| Caddy | Отличается простотой настройки, высокой производительностью, автоматическим получением и обновлением SSL/TLS-сертификатов. |
| Traefik | Динамический reverse-proxy для микросервисных архитектур. Поддерживает автоматическое обнаружение сервисов, обновление маршрутизации без перезагрузки и интеграцию с Let's Encrypt для выдачи TLS-сертификатов. |

### Как веб-сервер передает данные веб-приложению

Веб-сервер сам по себе не выполняет программную логику (например, не ходит в базу данных и не генерирует динамические страницы). Для этого он передаёт управление веб-приложению - отдельной программе. Для взаимодействия веб-сервера и веб-приложения используются специальные протоколы взаимодействия веб-серверов.

![](../../_images/980a5eff90cb.webp)

**Основные протоколы:**

| Протокол | Описание |
|---|---|
| CGI (Common Gateway Interface) | Классический стандарт, при котором веб-сервер запускает новый процесс для каждого запроса |
| FastCGI | Усовершенствованная версия CGI, использующая постоянные процессы-обработчики |
| WSGI (Web Server Gateway Interface) | Стандарт для языка Python |

### Пример конфигурации Nginx

Рассмотрим пример конфигурации, иллюстрирующий работу веб-сервера Nginx:

```
server {
    listen       80 default_server;
    server_name  localhost;
    
    location /api {
        proxy_pass http://api_server;
    }
    
    location / {
        try_files $uri $uri/ =404;
        root   /var/www/html;
        index  index.html index.htm;
    }
}
```

**Что делает эта конфигурация:**

| Директива | Назначение |
|---|---|
| listen 80 default_server; | Nginx прослушивает порт 80 (стандартный порт HTTP) и является сервером по умолчанию для этого порта. |
| server_name localhost; | Определяет, для какого доменного имени работает этот сервер. |
| location /api { ... } | Все запросы, начинающиеся с /api , обрабатываются этим блоком. Директива proxy_pass перенаправляет их на внутренний сервер приложений. |
| location / { ... } | Все остальные запросы обрабатываются этим блоком. Директива root указывает корневой каталог, откуда отдаются статические файлы ( /var/www/html ). Директива index задаёт файл, который отдаётся при обращении к каталогу (например, index.html ). |

### Прокси-серверы

**Прокси-сервер** - это промежуточное звено между клиентом и сервером. Все запросы клиента сначала попадают на прокси-сервер, который затем перенаправляет их целевому серверу. Ответ от сервера также идёт через прокси-сервер обратно клиенту.

![](../../_images/ae55052be5d0.webp)

Существует два основных типа прокси-серверов: **forward proxy** и **reverse proxy**. Они различаются тем, с какой стороны от прокси находятся клиент и сервер, а также целями использования.

**Forward Proxy**

**Forward proxy** располагается **перед клиентом** и действует от его имени. Клиент явно настраивает своё приложение на использование этого прокси-сервера. Когда клиент отправляет запрос, он направляет его не напрямую целевому серверу, а на прокси. Прокси, в свою очередь, перенаправляет запрос целевому серверу от своего имени. Целевой сервер видит только IP-адрес прокси-сервера и ничего не знает о реальном клиенте.

![](../../_images/a7b6fce29c7d.webp)

Основные цели Forward Proxy:

- **Обход блокировок:** доступ к ресурсам, которые могут быть недоступны с IP-адреса клиента.
- **Анонимность:** сокрытие реального IP-адреса клиента.
- **Контроль доступа:** ограничение доступа к внешним ресурсам внутри корпоративной сети.

Пример конфигурации Nginx как forward proxy:

```
server {
    listen 8888; # Порт, на котором будет слушать прокси
    location / {
        resolver 8.8.8.8; # DNS-сервер для разрешения имен
        proxy_pass http://$http_host$uri$is_args$args; # Передача запроса
    }
}
```

Разберем, что делает конфигурация:

**listen 8888** - Nginx слушает порт 8888.

**location /** - Обрабатывает все запросы независимо от пути.

**resolver 8.8.8.8** - Использует Google DNS для разрешения доменных имён в реальном времени.

**proxy_pass http://$http_host$uri$is_args$args** - Динамическая переадресация запроса.

**Reverse Proxy**

Располагается **перед сервером** и действует от его имени. Клиент ничего не знает о существовании обратного прокси - для него он сам является сервером. Прокси принимает запрос от клиента и перенаправляет его к одному из внутренних серверов.

![](../../_images/c954fdf30070.webp)

Основные цели Reverse Proxy:

- **Балансировка нагрузки:** распределение входящих запросов между несколькими серверами приложений для обеспечения отказоустойчивости и высокой производительности.
- **Защита и скрытие внутренней инфраструктуры:** сокрытие данных IP-адресов и архитектуры внутренних серверов от внешнего мира.
- **Терминация SSL/TLS:** снятие нагрузки на расшифровку HTTPS-трафика с серверов приложений.
- **Кэширование:** кэширование ответов от серверов приложений для ускорения ответа клиентам и снижения нагрузки.

Пример конфигурации Nginx как reverse proxy:

```
server {
    listen 80;
    server_name example.com;
    location / {
        proxy_pass http://localhost:5000; # Перенаправляем запросы на приложение
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**Что делает конфигурация:**

1. **listen 80** - Nginx слушает порт 80 (стандартный HTTP)
2. **server_name example.com** - Отвечает на запросы к домену example.com
3. **proxy_pass http://localhost:5000** - Перенаправляет все запросы на приложение, работающее на порту 5000
4. **proxy_set_header** - Передаёт реальную информацию о клиенте (IP, протокол).

### CDN (Content Delivery Network)

**CDN** (Content Delivery Network) - это географически распределённая сетевая инфраструктура, которая обеспечивает быструю доставку контента пользователям. Серверы CDN располагаются в разных точках мира, и запросы пользователя направляются на ближайший к нему сервер.

![](../../_images/9c1ebbf90ab2.webp)

### Основные термины

| Термин | Описание |
|---|---|
| origin | Исходный сервер, на котором хранятся оригинальные файлы сайта. CDN забирает контент именно с него. |
| PoP / Edge Server | Точка присутствия CDN - кэширующий сервер, расположенный в определённой географической локации. |
| Статический контент | Неизменяемые файлы, например, изображения, видео, CSS, JavaScript. Именно их раздача через CDN даёт максимальный эффект. |
| Динамический контент | Генерируется на сервере под каждого пользователя. CDN помогает и с ним, но по-другому - сокращая сетевой маршрут. |

**Зачем нужны CDN**

Основная причина - **скорость загрузки**. При стандартной схеме все запросы от пользователей направляются на один центральный сервер, который может находиться на другом континенте, что приводит к значительным задержкам из-за физической удалённости. CDN решает эту проблему за счёт географического распределения серверов, когда копии статического контента размещаются на множестве серверов в разных точках мира, и пользователь автоматически перенаправляется на ближайший к нему сервер.

Другие задачи CDN:

- **Снижение нагрузки на origin** - большую часть статики отдают edge-серверы.
- **Устойчивость к пиковым нагрузкам** - CDN распределяет трафик между множеством серверов.
- **Отказоустойчивость** - если origin упал, статика с CDN продолжает отдаваться.
- **Экономия трафика** - контент кэшируется, и повторные запросы не идут на origin.

**Как работает CDN**

Общий принцип:

1. Пользователь заходит на сайт **example.com**. Браузер получает HTML-страницу с origin.
2. Все ссылки на статику ведут не на origin, а на CDN-домен.
3. DNS-запрос к **cdn.example.com** возвращает IP-адрес ближайшего к пользователю edge-сервера.
4. Если на этом сервере есть кэшированная копия файла - он отдаётся мгновенно. Если нет - сервер забирает файл с origin, сохраняет у себя и отдаёт пользователю.

### Как CDN определяет ближайший сервер

Используются две основные технологии:

| Технология | Принцип работы |
|---|---|
| GeoDNS | Доменное имя привязано к нескольким IP-адресам. DNS-сервер смотрит на географию пользователя (по его IP) и возвращает адрес ближайшей точки присутствия. |
| Anycast | Один и тот же IP-адрес используется на множестве серверов по всему миру. Маршрутизаторы интернет-провайдера сами направляют пользователя на ближайший сервер с этим адресом. |

**Как кэшируется контент**

Самый простой вариант - кэширование по первому обращению:

1. Первый пользователь из региона запрашивает файл. Edge-сервер забирает его с origin и сохраняет у себя.
2. Все последующие пользователи из того же региона получают файл уже из кэша edge-сервера. Для ускорения заполнения кэша в новых регионах используется региональное извлечение - соседние edge-серверы делятся контентом друг с другом, а не ходят каждый раз на origin.

**Как подключить CDN (на примере статики)**

Процесс подключения выглядит так:

1. Вынести статику сайта на отдельный домен (например, **static.example.com**) - это будет origin.
2. Создать домен для CDN-раздачи (например, **cdn.example.com**).
3. Подключиться к CDN-провайдеру, указав ему домен origin (**static.example.com**) и домен для раздачи (**cdn.example.com**).
4. В DNS-настройках добавить CNAME-запись: **cdn.example.com** -> выделенный провайдером домен (например, **xxxx.selcdn.net**).
5. На сайте заменить ссылки на статику с **static.example.com** на **cdn.example.com**.

После этого пользователи получают HTML с основного сервера, а картинки, стили и скрипты - с ближайшего edge-сервера CDN.

### Кому нужны CDN

- **Проектам с международной или федеральной аудиторией** - ускорение доступа из удалённых регионов.
- **Сайтам с большим количеством статики** - интернет-магазины, новостные порталы, галереи.
- **Стриминговым сервисам** - потоковое видео и аудио.

- Caddy

```
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https
```

Проверим установку необходимых утилит:

![](../../_images/8ca83fbc3915.webp)

Для практической части создадим простейший веб-сайт, чтобы настроить и в дальнейшем проверить работу веб-сервера.

Создадим отдельную директорию для проекта и перейдем в неё `mkdir ~/node-app && cd ~/node-app`

Далее инициализируем Node.js-приложение `npm init -y`

Эта команда создает файл **package.json** с настройками проекта. Параметр **-y** указывает, что все предлагаемые значения принимаются по умолчанию. После этого установим веб-фреймворк **Express**, который предоставляет минимальный функционал для создания веб-приложений на Node.js: `npm install express`

![](../../_images/1084efb47d90.webp)

Теперь нам нужно создать простейшее веб-приложение, которое будет обрабатывать GET-запрос и возвращать HTML-страницу. Важно уточнить, что само приложение работает по HTTP, то есть без какого-либо шифрования. Задача защищенного соединения будет обеспечивать веб-сервер на Caddy

```
cat > app.js << 'EOF'
const express = require('express');
const app = express();

app.get('/', (req, res) => {
  res.send(`
    <!DOCTYPE html>
    <html>
    <head>
        <title>Node.js App</title>
        <style>
            body { font-family: Arial; text-align: center; padding: 50px; background: #f0f0f0; }
            h1 { color: #333; }
            .info { background: white; padding: 20px; border-radius: 8px; display: inline-block; }
        </style>
    </head>
    <body>
        <div class="info">
            <h1>The Node.js application is running!</h1>
            <p>Port: 3000</p>
        </div>
    </body>
    </html>
  `);
});

const PORT = 3000;
app.listen(PORT, '0.0.0.0', () => {
  console.log('Сервер запущен на порту ' + PORT);
});
EOF
```

Команда `cat > app.js << 'EOF'` создаёт файл **app.js** и записывает в него код до строки **EOF**.

Созданное веб-приложение на **Express** запускает сервер на порту 3000. При переходе на главную страницу (**/**) оно возвращает HTML-блок с заголовком «The Node.js application is running!» и указанием порта. В итоге мы имеем простейшее веб-приложение, теперь нужно обеспечить защищенное соединение. Как мы изучали ранее, для этого нам нужен TLS-сертификат.

Создадим директорию, где будут храниться файлы сертификата `sudo mkdir -p /etc/caddy/certs`

Далее генерируем самоподписанный сертификат и закрытый ключ `sudo openssl req -x509 -newkey rsa:2048 -keyout /etc/caddy/certs/key.pem -out /etc/caddy/certs/cert.pem -days 365 -nodes -subj "/CN=192.168.206.191"`

Важно, в поле CN указывается IP-адрес машины, поскольку доменное имя в данной среде отсутствует (CN=Your IP). В результате появились два файла: **cert.pem** (наш TLS-сертификат) и **key.pm** (закрытый ключ). Теперь нужно передать права на эти файлы пользователю **caddy**, от имени которого будет работать наш веб-сервер `sudo chown -R caddy:caddy /etc/caddy/certs/`

Вот мы и подготовили TLS-сертификат, теперь нужно настроить Caddy. Конфигурация Caddy задается в файле **/etc/caddy/Caddyfile**. Давайте перезапишем его следующим содержимым:

```
sudo bash -c 'cat > /etc/caddy/Caddyfile << EOF
:443 {
    tls /etc/caddy/certs/cert.pem /etc/caddy/certs/key.pem
    reverse_proxy localhost:3000
}
EOF'
```

Разберем конфигурацию. Блок **443** указывает Caddy слушать входящие соединения на порту 443(стандартный порт для HTTPS). С использованием директивы **tls** задаем пути к файлам сертификата и закрытого ключа, которые Caddy будет использовать при TLS-рукопожатии с клиентом. Директива **reverse_proxy** перенаправляет все входящие запросы к локально работающему Node.js-приложению на 3000 порту.

Что мы получаем в итоге? Простейшую структуру с использованием веб-сервера, как reverse proxy.

Давайте рассмотрим схему взаимодействия: браузер устанавливает зашифрованное HTTPS-соединение с Caddy, который в свою очередь передает расшифрованный запрос приложению по обычному HTTP. Приложение формирует ответ и возвращает его обратно через Caddy. Давайте проверим работу нашего веб-приложения. Для этого запустим **app.js** в фоновом режиме с помощью символа **&**: `cd ~/node-app && node app.js &`

```
sudo systemctl restart caddy
sudo systemctl enable caddy

```

Во-первых, обратим внимание, что соединение не защищено. Во-вторых, стоит отметить, что у нас получилось зайти на страницу, только потому, что при ее создании мы указали, что подключиться можно с любого IP. Видим, предупреждение браузера о **самоподписанном** сертификате. Даже при этом, общение между браузером пользователя и Caddy, происходит в зашифрованном виде.
