# Управление состоянием: сессии и cookies

> [!info] Путь в курсе
> Глава 4: Веб-приложения и безопасность веб-приложений / Часть 1: Основы веб-приложения

Протокол HTTP относится к протоколам без сохранения состояния. Каждый HTTP-запрос обрабатывается сервером независимо от предыдущих и последующих запросов. Сервер не имеет встроенных механизмов для определения принадлежности нескольких запросов одному клиенту или пользователю.

Данная архитектурная особенность HTTP создаёт ограничения для реализации прикладных функций, требующих поддержки контекста взаимодействия, таких как аутентификация, хранение пользовательских настроек, ведение истории действий. Для преодоления этого ограничения были разработаны механизмы управления состоянием: cookies, сессии и токены.

## Cookies

**Cookie** - это фрагмент данных, передаваемый веб-сервером браузеру в заголовке HTTP-ответа. Браузер сохраняет полученные данные и при каждом последующем запросе к тому же серверу автоматически включает их в заголовок **Cookie**. Cookies используются для хранения на клиентской стороне информации, необходимой для идентификации пользователя или сохранения его настроек.

### Порядок работы с cookies

1. Сервер включает в HTTP-ответ заголовок **Set-Cookie**.
2. Браузер интерпретирует данный заголовок как команду на сохранение указанных данных в локальном хранилище.
3. При формировании каждого последующего запроса к тому же домену браузер проверяет наличие сохранённых cookies и при их наличии добавляет заголовок **Cookie** с соответствующими данными.

![](../../_images/fcab974126e0.webp)

**Функциональное назначение cookies:**

| Функция | Пример реализации |
|---|---|
| Хранение пользовательских предпочтений | Сохранение выбранного языка интерфейса (cookie lang=en ) и темы оформления |
| Идентификация сессии | Передача идентификатора сессии (например, sessionid=xyjaez1081lze23 ) |
| Отслеживание поведения пользователя | Сбор статистики посещений, анализ пути по сайту |

### Атрибуты cookie

Каждый cookie может иметь набор атрибутов, определяющих условия его передачи, срок действия и уровень безопасности. Формат заголовка **Set-Cookie** включает следующие параметры: `Set-Cookie: name=значение; expires=дата; path=путь; domain=домен; secure; HttpOnly; SameSite=значение`

### Описание атрибутов

| Атрибут | Назначение |
|---|---|
| Domain | Определяет домен, для которого действует cookie. При отсутствии атрибута cookie привязывается только к домену, установившему его. |
| Path | Определяет URL-путь, для которого cookie передаётся. |
| Expires / Max-Age | Устанавливает абсолютную дату истечения срока действия или максимальное время жизни в секундах. При отсутствии этих атрибутов cookie считается сессионным и удаляется после закрытия браузера. |
| Secure | При наличии данного атрибута cookie передаётся только по защищённому соединению HTTPS. Передача по HTTP блокируется. |
| HttpOnly | При наличии данного атрибута cookie недоступен для чтения и изменения через DOM API. |
| SameSite | Контролирует отправку cookie при межсайтовых запросах. |
| SameSite=Strict | Cookie не передаётся при любых переходах с другого сайта. |
| SameSite=Lax | Cookie передаётся при переходе по гиперссылке, но не передаётся при отправке форм или запросах из JavaScript. |
| SameSite=None | Cookie передаётся при любых запросах. |

**HttpOnly**

Флаг **HttpOnly** предназначен для ограничения доступа к cookie из JavaScript-кода. Если специалисту по анализу защищенности удастся внедрить и выполнить произвольный скрипт на странице, этот скрипт не сможет прочитать содержимое cookie через объект **document.cookie**. Рекомендуется устанавливать HttpOnly для всех cookie, которые содержат чувствительную информацию, например идентификаторы сессий, токены доступа, данные авторизации.

**Secure**

Флаг **Secure** обеспечивает передачу cookie только по защищённому соединению HTTPS. Если cookie помечена этим флагом, браузер никогда не отправит её по незашифрованному HTTP-каналу. Флаг **Secure** следует устанавливать для всех cookie, передающих конфиденциальные данные. Без этого флага cookie может быть отправлена по незащищённому соединению и перехвачена.

**SameSite**

Флаг **SameSite** определяет условия, при которых браузер отправляет cookie при переходе на сайт с других ресурсов. Это снижает риск несанкционированных действий от имени пользователя.

Возможны три значения. если значение атрибута выставлено **Strict**, браузеры не будут отправлять его в межсайтовых запросах. Это идеально подходит для критически важных данных, таких как банковские операции или доступ к личному кабинету. Однако он может негативно сказаться на удобстве, так как пользователи, пришедшие по внешним ссылкам, будут вынуждены заново проходить авторизацию.

При настройке SameSite=**Lax** браузеры отправляют куки в межсайтовых запросах, но только при одновременном выполнении двух условий. Во-первых, запрос должен использовать метод GET. Во-вторых, запрос должен возникнуть в результате перехода пользователя по ссылке, то есть когда он сам кликнул и перешел на другой сайт.

Режим **None** полностью отключает любые ограничения SameSite, разрешая браузеру отправлять куки абсолютно во всех запросах, даже если они были инициированы совершенно посторонними сайтами. Такой вариант используется только тогда, когда кросс-доменная работа жизненно необходима, например, для функционирования сторонних виджетов, кнопок социальных сетей или систем сквозной авторизации между разными доменами. Поскольку это наименее безопасный подход, он требует обязательного использования дополнительного флага Secure и внедрения других механизмов защиты, чтобы предотвратить злонамеренное использование сессии пользователя.

### Сессии

**Сессия** - это механизм сохранения состояния, при котором данные о пользователе хранятся на серверной стороне, а клиенту передаётся только уникальный идентификатор сессии. **Алгоритм работы сессий:**

1. При первом обращении пользователя сервер генерирует уникальный идентификатор сессии - **session ID**.
2. Идентификатор передаётся браузеру в виде cookie.
3. Данные, ассоциированные с сессией (пользовательские настройки, состояние корзины, флаг аутентификации), сохраняются на сервере в выбранном хранилище: реляционной базе данных, системе кэширования, файловой системе.
4. При каждом последующем запросе браузер возвращает **session ID** в cookie. Сервер по этому идентификатору извлекает соответствующие данные и восстанавливает контекст взаимодействия.

![](../../_images/4514297a28ed.webp)

**Управление временем жизни сессии**

Сессия не может существовать бесконечно. Для обеспечения безопасности устанавливаются ограничения на время её жизни:

| Тип таймаута | Описание |
|---|---|
| Idle Timeout | Сессия завершается, если пользователь не совершал действий в течение указанного времени |
| Absolute Timeout | Сессия завершается через фиксированное время после входа, независимо от активности пользователя |

**Хранение сессий на сервере**

Данные сессии могут храниться в разных местах, и от этого зависят безопасность и производительность:

| Способ хранения | Особенности |
|---|---|
| Память приложения | Самый быстрый, но при перезапуске сервера или масштабировании данные теряются |
| Файловая система | Простота реализации, но возможны проблемы с блокировками при высокой нагрузке |
| База данных | Надёжно, поддерживает репликацию, но создаёт дополнительную нагрузку на БД |
| Кэш-система (Redis, Memcached) | Высокая скорость, поддержка распределённых систем, автоматическое удаление устаревших данных |

**Безопасная передача идентификатора сессии**

Идентификатор сессии - **session ID** - передаётся между клиентом и сервером, как правило, в cookie. Для обеспечения безопасности необходимо правильно настроить атрибуты этой cookie:

| Атрибут | Значение | Назначение |
|---|---|---|
| HttpOnly | true | Запрещает доступ к session ID из JavaScript, что ограничивает возможность несанкционированного доступа к данным через клиентские скрипты |
| Secure | true | Передаёт session ID только по защищённому соединению HTTPS, предотвращая перехват данных при передаче через незащищённые сети |
| SameSite | Lax или Strict | Ограничивает отправку session ID при переходах с других сайтов, снижая риск выполнения несанкционированных действий от имени пользователя |

Теперь на практическом примере рассмотрим механизм сессий на основе **cookies**. Для этого воспользуемся веб-приложением **flaskr**. Необходимо выполнить команды

```
python -m venv venv        # Создает виртуальное окружение
source venv/bin/activate   # Linux/Mac
venv\Scripts\activate      # Windows

pip install flask          # Установка flask
```

Далее необходимо клонировать репозиторий с **github** и локальную установку

```
git clone https://github.com/pallets/flask.git
cd flask/examples/tutorial
pip install .
```

Далее необходимо инициализировать базу данных `flask --app flaskr init-db`

После чего запустить веб-приложение `flask --app flaskr run`

Также перед выполнением последующих действий необходимо использовать** Burp Suite** для перехвата запросов и последующего анализа запросов. Зарегистрируемся и пройдем аутентификацию

![](../../_images/157d62024bde.webp)

При просмотре запроса для аутентификации, увидим, что после отправки учетных данных, сервер возвращает ответ с заголовком **Set-Cookie**.

![](../../_images/05025f4d3e1e.webp)

При дальнейших запросах браузер добавляет заголовок Cookie со значением, которое было в **Set-Cookie**

![](../../_images/ec8640301399.webp)

Далее разберем механизм формирования cookie. При сохранении данных в объекте **session** Flask сериализует эти данные, подписывает их с использованием **SECRET_KEY** и помещает результат в cookie, которое отправляется браузеру пользователя. В основе механизма сессий Flask лежит библиотека itsdangerous, которая сохраняет данные сессии и формирует строку вида: **base64(data).timestamp.signature**

**timestamp** содержит временную метку создания или обновления cookie. Она используется для контроля срока действия данных и позволяет серверу определять актуальность сессии.

**signature** является криптографической подписью, вычисляемой на основе содержимого cookie и секретного ключа приложения. При получении запроса Flask повторно вычисляет подпись и сравнивает ее с переданной. Если значения не совпадают, cookie считается подделанным или поврежденным и данные сессии отклоняются.

**Кража сеанса**

Важно, чтобы секретный ключ таковым и оставался, а также обладал достаточной криптографической стойкостью и не был предсказуемым. В противном случае возникает возможность сформировать произвольное содержимое cookie, подписать его тем же ключом и выдать за легитимное. Рассмотрим на примере данного веб-приложения. Если декодировать первую часть cookie, то можно увидеть, что session-cookie содержит данные о user_id пользователя: **{"user_id":3}**

Для дальнейших действий создадим еще одного пользователя. Теперь можем предположить, что сессия определяется идентификатором из cookie. При попытке просто изменить идентификатор, ожидаемого результата достигнуть не удастся. После модификации данных криптографическая подпись перестанет соответствовать содержимому cookie. Однако если известен ключ, который использовали для подписи, можно будет изменить user_id и подписать заново.

Для этого воспользуемся утилитой flask-unsign. Для установки необходимо выполнить команды `pip3 install flask-unsign flask-unsign[wordlist]`

Далее необходимо выполнить команду `flask-unsign --unsign --cookie "your_token"`

Данная команда расшифрует данные закодированные в base64, а также попытается подобрать ключ для подписи cookie. В данном учебном варианте используется стандартный ключ 'dev', который утилита нашла:

![](../../_images/9dba0c7e3eae.webp)

После данные можно изменить и подписать тем же ключом. Для этого необходимо выполнить команду, в которой вместо **user_id: 3** необходимо использовать user_id нового пользователя которого создали ранее:

![](../../_images/19d2225555ed.webp)

В результате получим корректно подписанный session-cookie. Теперь снова зайдем под старым пользователем, и вставим вместо старого значения cookie новое, и перезагрузим страницу. В результате увидим загруженную сессию второго пользователя:

![](../../_images/938a3207070c.webp)

Сервер должен следить за тем, кто использует сессию. Если контекст резко меняется, сессия может быть скомпрометирована. Так например, если геолокация пользователя резко меняется, сессию можно приостановить. Также можно проверять **User-Agent**. Если сессия была создана в Chrome на Windows, а запрос пришел от Safari на iPhone, это явный признак кражи токена. Сервер должен отклонить такой запрос.

Помимо этого, в браузерах существуют дополнительные меры безопасности от кражи сессий. Так например, в Google Chrome есть функция безопасности - Device Bound Session Credentials, которая связывает файлы cookie с конкретным устройством пользователя. Процесс аутентификации связан с конкретной парой открытых/закрытых ключей, созданной с использованием чипа доверенного платформенного модуля (TPM) устройства.
