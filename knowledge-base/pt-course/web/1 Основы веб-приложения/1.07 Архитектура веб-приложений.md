# Архитектура веб-приложений

> [!info] Путь в курсе
> Глава 4: Веб-приложения и безопасность веб-приложений / Часть 1: Основы веб-приложения

Архитектура веб-приложения определяет, как взаимодействуют его компоненты: клиентская часть, серверная логика и данные. Понимание этих подходов необходимо для выбора правильной структуры проекта, обеспечения его масштабируемости и надежности.

## Клиент-серверная модель

Это фундаментальная модель, лежащая в основе работы любого веб-приложения. Взаимодействие строится по принципу "запрос-ответ":

1. **Клиент** инициирует соединение и отправляет HTTP-запрос.
2. **Сервер** принимает запрос, выполняет необходимую обработку (например, обращается к базе данных, выполняет бизнес-логику) и формирует ответ.
3. **Сервер** отправляет ответ клиенту, после чего соединение может быть закрыто.

### Трехуровневая архитектура

Трехуровневая архитектура - это наиболее распространенная модель, которая разделяет приложение на три логических уровня:

- **Уровень представления** - взаимодействие с пользователем: отображение интерфейса, валидация ввода, отправка запросов на сервер. Не содержит бизнес-логики и не обращается к базе данных напрямую.
- **Уровень бизнес-логики** - обработка данных по правилам приложения: вычисления, авторизация, проверка прав доступа, формирование ответов для клиента.
- **Уровень данных** - хранение и управление данными: базы данных, файловые хранилища, кэши.

**Почему выделяют уровень данных?**

1. **Производительность.** Базы данных требуют значительных вычислительных ресурсов. Вынос их на отдельный сервер позволяет эффективнее распределять нагрузку.
2. **Масштабируемость.** Уровень бизнес-логики можно легко дублировать (запустить 10 копий сервера), в то время как база данных долгое время остается единым компонентом.
3. **Развитие технологий хранения.** Появились NoSQL-решения, кэширующие СУБД, шардирование и кластеризация, что требует выделенного слоя для управления этими сложными системами.

> **Шардирование** - распределение данных по нескольким независимым серверам для увеличения объёма хранимой информации и пропускной способности.

> **Кластеризация** - объединение нескольких серверов в единую систему, обеспечивающую высокую доступность, так как при отказе одного узла его нагрузку берут на себя другие.

### Современная структура веб-приложений

На практике современное веб-приложение выходит за рамки простой трехуровневой модели и включает дополнительные компоненты, обеспечивающие высокую производительность, отказоустойчивость и безопасность.

![](../../_images/b1848568e228.webp)

**Основные компоненты современной архитектуры:**

1. **CDN **(Content Delivery Network) - сеть доставки контента. Это географически распределенные серверы, которые кэшируют статический контент (изображения, CSS, JavaScript, видео) и отдают его пользователю с ближайшей точки присутствия. Это ускоряет загрузку страниц и снижает нагрузку на основной сервер.
2. **Балансировщик нагрузки** - распределяет входящие запросы между несколькими экземплярами сервера приложений. Обеспечивает отказоустойчивость (если один сервер упал, запросы идут на другие) и горизонтальное масштабирование.
3. **Веб-сервер** - принимает запросы от клиентов, может отдавать статический контент напрямую, выступать в роли reverse-proxy, кэшировать ответы и балансировать нагрузку между серверами приложений.
4. **Сервер приложений** - выполняет бизнес-логику приложения. Может быть реализован на любом языке программирования.
5. **Кэширующий сервис** - хранит часто запрашиваемые данные в оперативной памяти. Это позволяет получать данные в миллисекунды без обращения к основной базе данных.
6. **База данных** - основное хранилище данных.

**Цикл жизни запроса в современной архитектуре:**

1. Пользователь вводит адрес сайта в браузере.
2. DNS преобразует доменное имя в IP-адрес балансировщика нагрузки.
3. Браузер отправляет HTTPS-запрос на балансировщик (или напрямую на веб-сервер).
4. Балансировщик/веб-сервер принимает запрос:
   
   - Если запрошен статический файл (CSS, изображение), сервер отдаёт его напрямую или из CDN.
   - Если запрос требует выполнения логики, он передаёт его одному из серверов приложений.
5. Сервер приложений обрабатывает запрос:
   
   - При необходимости сначала обращается к кэшу для быстрого получения данных.
   - Если данных в кэше нет, выполняет запрос к базе данных.
   - Полученные данные могут быть сохранены в кэш для следующих запросов.
6. Сервер приложений формирует ответ (HTML) и возвращает его веб-серверу.
7. Веб-сервер отправляет ответ клиенту.
8. Браузер отображает страницу.

### Монолитная архитектура

**Что это:** приложение построено как единое целое. Вся бизнес-логика, обработка запросов, доступ к данным - всё находится внутри одного процесса. Приложение собирается в один исполняемый файл или разворачивается как единый сервис.

**Как выглядит:** один сервер приложений, одна база данных (или кластер базы данных под ним). Все модули тесно связаны между собой.

![](../../_images/1c425a8939da.webp)

**Плюсы:**

- Простота разработки.
- Удобство развёртывания (один файл/контейнер).
- Более простая отладка и тестирование.

**Минусы:**

- Сложность масштабирования - приходится масштабировать всё приложение целиком, даже если нагружен только один модуль.
- Нерациональное использование ресурсов сервера.
- Низкая отказоустойчивость - ошибка в одном модуле может остановить работу всего приложения. Основная проблема - сложность масштабирования. Монолитную архитектуру можно масштабировать только вертикально, горизонтальное масштабирование практически невозможно. Вертикальное масштабирование:

### Микросервисная архитектура

**Что это:** подход, при котором приложение разбивается на множество небольших, независимо разворачиваемых сервисов. Каждый сервис отвечает за свою узкую бизнес-функцию (например, сервис авторизации, сервис новостей, сервис комментариев). Сервисы общаются между собой по сети (через API).

**Как выглядит:** несколько независимых серверов приложений, каждый - со своей базой данных (или общей). Сервисы могут быть написаны на разных языках программирования.

![](../../_images/35c4046f9a30.webp)

**Плюсы:**

- Гибкость масштабирования - можно масштабировать только те сервисы, которые испытывают высокую нагрузку.
- Независимость разработки и развёртывания - разные команды могут работать над разными сервисами параллельно.
- Отказоустойчивость - выход из строя одного сервиса не останавливает всё приложение.

**Минусы:**

- Сложность разработки и эксплуатации - требуется управление множеством сервисов и сетевых взаимодействий.
- Сложность тестирования - нужно тестировать не только отдельные сервисы, но и их взаимодействие. Пример горизонтального масштабирования для процесса с высокой нагрузкой, например "Авторизация".
