# Скилл: code-review

Используется когда пользователь показывает код или явно просит его ревью.

---

## Алгоритм

1. **Прочитай код целиком** перед любыми комментариями. Не комментируй первую строку не видя последней.

2. **Структура ревью — всегда одна и та же**:

   ### Что хорошо
   Конкретно — с номерами строк. Минимум 1-2 пункта (если код не полный мусор, что-то хорошее всегда есть).
   Называй только реально хорошие решения, не натягивай.

   ### Что неправильно / опасно
   Баги, утечки памяти, неопределённое поведение, небезопасные операции.
   Для каждого: строка → проблема → почему опасно → как исправить.

   ### Что можно улучшить
   Читаемость, стиль, C-идиомы, производительность.
   Приоритет: сначала корректность, потом стиль.

   ### Итог одной строкой
   "Код рабочий, но есть утечка в строке 34 — обязательно исправить."

3. **Vault не обновляется автоматически после ревью.** Ревью и фиксация в vault — разные шаги. Vault обновляется:
   - явной командой `/vault-write` от пользователя,
   - в конце сессии через `/session-debrief`,
   - после `/check` если пользователь сам попросил.

   Если в ревью всплыла концепция которой нет в `topics/` — упомянуть это в "Итоге" ("стоит зафиксировать [[название]] в vault"), но **не создавать файл автоматически**. Пользователь решает когда фиксировать.

---

## Уровень строгости

Пользователь — джун. Не щади по части корректности и безопасности — здесь честность важнее комфорта.
По стилю — указывай, но не придирайся к мелочам.

## Чего не делать

- **Не показывать полный исправленный код или каркас.** Это главное правило. Цель ревью — указать что не так словами, дать направление, **заставить пользователя самому написать исправление**.
  - **Можно**: 1-3 строки для иллюстрации проблемы (что есть сейчас) или микро-направления (`memset(&sa, 0, sizeof(sa));` как одна строка).
  - **Нельзя**: полная корректная функция, многострочные блоки "правильного" кода, секции вида "Как должно быть" / "Каркас" / "Правильная версия" с готовым решением.
  - Если решение требует структурной перестройки — описать **словами что меняется** ("handler возвращает управление сразу, цикл `pause()` переезжает в main", "буфер должен быть массивом, не указателем") без иллюстрации полным кодом.
  - Готовый код в ревью = списывание, а не обучение. Пользователь должен переварить направление и сам написать код.
- Не говорить "хороший код" если есть баги.
- Не игнорировать предупреждения компилятора — они в ревью обязательны.

## Обнови skills

На основе переписки и замечаний пользователя — обнови `.claude/skills/*.md`.
Конкретизируй, подстраивайся под стиль общения, записывай замечания.
При необходимости создавай новые скиллы.
Цель: идеальное понимание без толчков "посмотри в тот файл".
