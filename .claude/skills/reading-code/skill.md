# Скилл: reading-code

Используется для целенаправленного чтения чужого кода — open-source проектов и Linux kernel.
Цель — научиться **читать** код, а не только писать его. Разработчик СЗИ читает в 5 раз больше, чем пишет.

---

## Триггеры

Счётчиков **нет**. Reading-code инициируется одним из двух способов:

**1. По запросу пользователя:** "дай почитать код", "хочу разобрать чужой код", "reading-задание".

**2. По решению Claude в естественных моментах:**
- **После интеграционного задания** (позиции 5/10/15/20 блока) — пользователь только что синтезировал 4 темы в своём коде, идеальный момент посмотреть как это сделано в production. Claude предлагает: "ты только что собрал X на своих руках — хочешь увидеть как похожую интеграцию делают в \<проект\>?"
- **Как компонент мок-собеса** — если в ходе вопросов всплывает тема где разбор реального модуля даст больше чем абстрактный ответ.
- **При переходе на новую технологию / новый блок** — перед стартом блока полезно прочитать чужой код по теме (для блока H — eBPF — это особенно показано).

Не предлагать reading-code если только что была reading-сессия или если пользователь в режиме интенсивного писания (3+ writing подряд без передышки — само по себе не повод, но если есть выбор между reading и атомарным — лучше reading).

## Алгоритм

### 1. Прочитай контекст

Прочитай `knowledge-base/self-study/roadmap/00-roadmap.md` → "Текущая позиция":
- Активный блок (A / B / C / ...) и его статус.
- "Выполненные темы блока X" — все пройденные блоки — в `roadmap/archive.md`.

Также `roadmap/journal.md` → "Reading-сессии" — журнал предыдущих разборов, чтобы не дублировать модуль.

Не давать задание по теме которую пользователь ещё не проходил.

### 2. Подбери модуль (не одну функцию)

Главное правило: **маленький модуль с внутренними зависимостями**, не отдельная функция.
Цель — понять как связаны 2-5 функций между собой, как они передают состояние, как обрабатывают ошибки.

Объём: **150–400 строк** реального кода. Меньше — слишком узко (не видно архитектуры). Больше — не хватит сессии.

#### Источники по блокам

| Блок / тема | Источники |
|-------------|-----------|
| A — Linux internals | Linux kernel: `kernel/fork.c`, `kernel/signal/`, `fs/proc/`, `kernel/pipe.c`. musl libc для пользовательского side. |
| B — Networking | musl libc `src/network/`, ClamAV `libclamav/`, Suricata, простые части OpenSSH client (`channels.c`). |
| C — Rust | Rust std small modules: `std::sync::Mutex`, `std::fs`. Crates: `tokio::sync::oneshot`, маленькие части `nix` crate. |
| D-E — Crypto / async | `chacha20poly1305` crate (auth/encrypt пара функций), `tokio::net::TcpListener` accept loop. |
| F — VPN | `boringtun` (WireGuard на Rust), модуль handshake. |
| G — Sandbox | `bubblewrap` (~1500 строк всего, читать модулями), runc `libcontainer/seccomp/`, Firejail отдельные `src/firejail/`. |
| H — eBPF | `bcc/libbpf-tools/*.bpf.c` — каждый tool ~200-400 строк, идеальный размер. |
| I — LLM-security | NVIDIA `nemo-guardrails` отдельные rails, `llm-guard` отдельные сканеры, `garak` пробы. |

При сомнении — спросить пользователя "что больше зайдёт: ядро, прикладной C или прикладной Rust?".

### 3. Сформулируй задание чётко

```
Файл: <путь к файлу или ссылка на upstream>
Объём: <строки> (например, lines 120-310)
Цель: <что именно понять — не "что делает", а конкретный вопрос>
Время: 60–90 минут
```

**Цель формулируется как вопрос**, не как "прочитай и пойми". Примеры хороших целей:
- "Как `do_fork()` синхронизирует родителя и ребёнка до возврата из сисколла?"
- "Почему в `bcc/tools/execsnoop.bpf.c` события идут через ring buffer, а не через perf buffer?"
- "Как `bubblewrap` дропает privileges в правильном порядке, чтобы не открыть race?"

Плохая цель: "прочитай fork.c" — слишком расплывчато.

### 4. Создай файл задания

Создай `self-practice/<domain>/reading-NN/reading-NN.md` (папка задачи по тематике домена, например `self-practice/networking/reading-03/reading-03.md` для разбора сетевого модуля) с шаблоном:

```markdown
---
task: reading-NN
title: <модуль> — <короткая цель>
status: in-progress
date: YYYY-MM-DD
type: reading
---

## Источник
- Проект: <название>
- Файл: <путь>
- Версия / commit: <если важно>

## Цель чтения
<вопрос из шага 3>

## Что прочитать
<конкретные функции / диапазон строк>

---

## Что понял
*(заполняется после)*

## Что осталось непонятным
*(заполняется после — это важнее, чем "что понял")*

## Интересные приёмы
*(идиомы, неожиданные решения, defensive programming)*

## Связанные темы
*(заполняется после)*
```

### 5. Подожди отчёта

После того как пользователь прочитал — провести разбор:
- Сначала пользователь рассказывает что понял (своими словами).
- Потом задавай 2-3 уточняющих вопроса по самым нетривиальным местам кода.
- Только после этого — закрепить через `vault-write`: запись в `topics/reading/<имя>.md` с архитектурными выводами.

**Подача в разборе — использовать паттерны из `explain-code/skill.md` раздел 3.0:**
- Actors-with-letters (P/C1/C2 для процессов, T1/T2 для тредов, и т.д.).
- Numbered steps для последовательностей.
- Один вопрос пользователя — один ответ. Не вводить сбоку 5 новых концепций.
- Если ответ требует > 3 новых терминов — остановиться, предложить `/theory` сессию.

### 6. Обнови журнал

После завершения reading-сессии:
- В `knowledge-base/self-study/roadmap/journal.md` → "Reading-сессии" — добавить строку с датой, источником, целью и `[[wikilink]]` на конспект в `topics/reading/`.
- В `roadmap/archive.md` → "Темы — Reading" — добавить `[[wikilink]]` на конспект.

## Чего не делать

- Не давать "прочитай весь Linux kernel" — это убьёт мотивацию. Один модуль за сессию.
- Не давать функцию-вакуум без вызывающего кода — теряется контекст использования.
- Не пропускать шаг 5 — без разбора чтение проходит "мимо".
- Не выбирать модули с тяжёлыми внешними зависимостями (RCU, lockdep), пока пользователь не готов к ним.
- Не экзаменовать пользователя — это не контроль, это совместный разбор.
