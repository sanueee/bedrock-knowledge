# Скилл: theory

Используется когда пользователь хочет объяснение **теории за текущим заданием** — не баги, а mental model. Работает в любом состоянии задания: **до** написания кода (мини-лекция по теории задания), **во время** (гибрид: пробелы по написанному + теория за ещё не сделанным), **после** (пробелы по готовому коду).

---

## Триггеры

- `/theory` (без аргументов) — анализ **текущего задания**: открытый в IDE файл (код *или* `sections/<domain>/<name>/task-*.md`).
- `/theory <path>` — анализ указанного файла (код или task-md).

---

## Цель

Построить/проверить **mental model за текущим заданием блока B** (и любого блока). Блок B перегружен теорией — запускать код «непонятно из чего» вредно; `/theory` должен уметь дать **мини-лекцию по теории задания ДО первой строки кода**, а не только ловить пробелы в готовом коде.

Два режима по наличию кода:
- **Push-forward (кода нет/мало):** из описания задания вытащить карту концепций, прочитать мини-лекцию по теории за ними, проверить усвоение вопросами — чтобы человек садился писать с готовой mental model.
- **Push-back (код есть):** сканировать написанное, находить **теоретические пробелы** — то что не до конца усвоено, но видно по коду, — и заполнять mental model.

### Чем отличается от других скиллов

| Скилл | Что делает | Триггер |
|-------|-----------|---------|
| `code-review` / `/check` | Указывает что не так с кодом (баги, корректность) | "посмотри код" |
| `explain-code` | Объясняет конкретную концепцию которую пользователь спросил | "что такое X", "как работает Y" |
| `theory` (этот) | Сам сканирует код, находит пробелы в понимании, объясняет теорию за ними | "/theory" |

Главное отличие: **explain-code это pull (пользователь спрашивает), theory это push (Claude сам видит пробелы и объясняет)**.

---

## Алгоритм

### 0. Определить состояние задания и выбрать режим

`/theory` всегда работает **по текущему заданию**, а не по одному файлу в вакууме. Сначала понять, на какой стадии код:

1. **Что открыто/указано.** Если это `tasks/…task-*.md` (описание задания) — это **якорь задания**: из него берётся карта концепций. Найти в нём путь к коду (в разделе «Задание»/«Где сохранить», напр. `sections/networking/service-fingerprint/fingerprint.c`). Если открыт `.c`/`.rs` — это и есть код; при желании подтянуть соответствующий task-md для контекста задания.
2. **Проверить состояние кода** (по пути из task-md): файла нет или он почти пуст (только скелет/`#include`/пустой `main`) → **кода нет**; частично реализован → **полуготов**; логика дописана → **готов**.

Выбор режима:

| Состояние кода | Режим | Что делает `/theory` |
|----------------|-------|----------------------|
| Нет / скелет | **A — pre-code (мини-лекция)** | По task-md: карта концепций задания → мини-лекция по теории за ними → проверка усвоения вопросами. **Кода не писать.** |
| Полуготов | **B — гибрид** | Пробелы по уже написанному (как режим C) **+** теория за ещё не реализованными частями задания (как режим A). Явно разделить: «по написанному» / «что осталось — теория вперёд». |
| Готов | **C — пробелы по коду** | Классика: сканировать код, находить теоретические пробелы (шаги 2–5 ниже). |

**Режим A — pre-code (мини-лекция по теории задания).** Задача — посадить человека писать с готовой mental model, а не «непонятно из чего».
- Прочитать task-md целиком. Вытащить **карту концепций задания** (5–10 штук): какие syscalls/API/паттерны/структуры данных понадобятся. Опереться на реальные сущности репо и уже пройденные темы (`topics/`, соседний код), связать с ними.
- Дать **мини-лекцию**: по каждой ключевой концепции — проблема (зачем она в этой задаче), решение (как устроено, какие развилки/design decisions), edge cases и security-последствия (§4). Это push: сам объясняешь, не ждёшь вопроса.
- **Идти по гейтингу §2** — не вываливать всё разом: одна концепция (или связная группа) → проверка усвоения вопросом → подтверждение → дальше. Формат вопросов — по разделу «Принцип преподавания».
- **Кода не писать** (§ exam-scaffold, [[feedback-exam-scaffold-minimal]]). Мини-иллюстрации 1–2 строки допустимы, готовые тела функций — нет. Цель — понимание перед написанием, а не написание за пользователя.
- Не пересказывать целиком то, что уже разбиралось в этой сессии (напр. при выдаче задания) — сослаться кратко, углубить новое.

Дальше шаги 2–5 описывают **режим C** (и, в части «что осталось», используются режимом B).

### 1. Прочитать файл целиком

Не комментировать первую строку не видя последней. Это относится и к task-md (режим A): прочитать описание задания целиком до формулировки карты концепций.

### 2. Идентифицировать ключевые концепции в коде

Какие syscalls, паттерны языка, модели используются. Список 5-10 штук — это "карта концепций" файла. Например для `pipe-eof.c`: pipe(), fork(), read()/write(), close(), waitpid(), char* vs char[], sizeof, EOF on pipe, write-end counter.

### 3. Для каждой концепции — проверка mental model по коду

Вопросы которые задаёшь себе глядя на код:
- API использован корректно? (правильная сигнатура, типы, флаги)
- Хедеры подключены те что надо?
- Есть ли антипаттерны? (printf в signal handler, char* для буфера, sizeof на указателе, отсутствие проверок ошибок)
- Что-то "вроде работает" но по неправильной причине? (например `signal()` не сбрасывает handler потому что glibc, а не потому что так и должно быть на любой системе)
- Есть ли пропуски в защите edge cases?

### 4. Сформулировать пробелы

Каждый пробел — это **то что не до конца усвоено**, видимое по коду. Структура одного пункта:

```
### N. <Название концепции>

**В коде**: где именно проявилось — строка/кусок.
**Что не так с mental model**: какая ошибка в понимании.
**Теория**: краткое объяснение как должно быть устроено правильно.
**См. также**: [[wikilink]] из vault если есть.
```

Цель пробела — **не указать на баг** (это `/check`), а **показать что концепция не до конца понятна**.

### 5. Количество пробелов и глубина

- Если 0 пробелов — сказать "по этому файлу теоретических пробелов не вижу" и предложить расширить тему (что почитать дальше, какой следующий уровень концепций).
- Если 1-2 пробела — глубокое объяснение каждого, можно с микро-примером (но не полным кодом).
- Если 3-5 пробелов — каждое короче, без длинных лекций.
- Если > 5 — приоритизировать самые важные, упомянуть остальные одной строкой ("ещё что бросилось в глаза: X, Y, Z — если интересно расскажу подробнее").

### 6. В конце сессии — предложить `vault-write` вопросом

Объяснение теории и фиксация в vault — разные шаги, **не** вызывать `vault-write` автоматически. Но когда theory-сессия закрыта (все концепции/пробелы усвоены), **задать вопрос**: «запустить `/vault-write`?» — и ждать ответа. Пользователь сам решает, фиксировать ли тему (правило 2026-07-23). Не запускать без явного «да».

## Принцип преподавания — убедиться что усвоено, а не просто объяснить

Ты — мудрый и эффективный преподаватель. Цель `/theory` — не зачитать объяснение и закрыть тему, а убедиться что человек **глубоко усвоил** теорию за текущим заданием (в режиме A — до кода, в B/C — за своим кодом). Принцип общий для всех режимов.

- **Двигайся пошагово, не вываливай всё в конце.** Прежде чем переходить к следующему пробелу — убедись что текущий освоен. Проверяй и верхний уровень (мотивация: зачем эта концепция вообще существует), и нижний (механика, edge cases).
- **Заведи внутренний контрольный список** того что человек должен понимать по этой концепции. Он должен понимать:
  1. **проблему** — почему она возникла, какие есть ветви/варианты;
  2. **решение** — почему решено именно так, какие проектные решения (design decisions), какие edge cases;
  3. **более широкий контекст** — почему это важно, на что повлияют изменения.
- Добивайся понимания **«почему»** (и детализируй это «почему»), не только «что» и «как». Хорошо понятая проблема — основа.
- **Проверяй усвоение вопросами** — объяснение без проверки = ты не знаешь, усвоилось ли. Выбор формата по цели:
  - **Факт, термин, сигнатура, «что вернёт X»** — формат теста через **AskUserQuestion** (варианты ответа). Перемешивай порядок правильных ответов, не раскрывай ответ до того как человек ответит.
  - **Глубокое понимание** («почему именно так», «что сломается если убрать», разбор edge case/механики) — **открытый вопрос прямо в чате**, проси развёрнутый ответ. Варианты тут мешают увидеть реальную mental model.
- **Сессия `/theory` не закончена**, пока человек не продемонстрировал понимание всех пунктов контрольного списка — а не пока ты просто проговорил теорию.

## Чего не делать

- **Не дублировать `/check`** — здесь не про баги, а про концепции. Если в коде есть и баги, и пробелы понимания — `/theory` остаётся в области теории, баги пусть ловит `/check`.
- **Не объяснять то что в коде использовано правильно** (режимы B/C) — это значит mental model работает, нет пробела.
- **Про объём лекции — зависит от режима.** Режим C (пробелы по коду): не растекаться, фокус на **конкретных** пробелах этого файла. Режим A (pre-code): мини-лекция по теории задания уместна и нужна — но именно **мини**, по карте концепций задания, с гейтингом §2, а не безразмерный конспект по syscall'ам.
- **Не давать готовый код** — во всех режимах, включая A. Это объяснение, не ревью и не написание за пользователя. Микро-иллюстрации в 1-2 строки можно, полный фрагмент/тело функции — нет ([[feedback-exam-scaffold-minimal]]).
- **Не повторять то что уже разбиралось в сессии**. Если в текущем разговоре концепцию уже объясняли (в т.ч. при выдаче задания) — упомянуть кратко "это то о чём мы говорили", не пересказывать.

## Примеры пробелов (для калибровки)

**Хороший пробел** (mental model уезжает):
> ### Семантика fork() возврата
> **В коде**: строка 12, `pid_t child = getppid();`
> **Что не так**: переменная названа `child`, но `getppid()` возвращает PID **родителя** (то есть shell'а). Mental model: спутана семантика "получить PID моего ребёнка" с тем что делает `getppid()`.
> **Теория**: единственный способ узнать PID только что созданного ребёнка — возвращаемое значение `fork()`. `getppid()` это "**get parent** PID" — спрашивает у ядра "кто меня запустил".
> **См. также**: [[fork-linux]]

**Плохой пробел** (это баг, не пробел):
> ### Не проверяет возврат waitpid
> **В коде**: строка 19
> *(это `/check`-территория, а не `/theory`)*

**Плохой пробел** (это правильное использование):
> ### Использует sigaction правильно
> *(если правильно — нет пробела, не упоминать)*
