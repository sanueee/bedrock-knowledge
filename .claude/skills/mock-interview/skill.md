# Скилл: mock-interview

Триггер: **только по запросу пользователя** — "мок-собес" / "проверь меня" / "вопросы по пройденному".
Никаких счётчиков и автоматических предложений из `give-task`. Пользователь сам решает когда хочется проверить теорию.

**Доступен в любом формате** (см. шаг 1): по пройденному в личной стратегии, по коду, по теме вуза, по конкретному заданию — или смесь. **Ничего не пишет в файлы**: слабые места подсвечиваются в чате в конце собеса. Куда их фиксировать — пользователь пока не решил; не изобретать место самостоятельно.

**Reading-code может быть частью мок-собеса** — если по ходу проверки всплывает тема где полезно увидеть как это делают в реальном коде (например, обсудили `pthread_mutex` → разобрать модуль с реальной блокировкой), Claude по своему решению переходит к скиллу `reading-code` после блока вопросов.

## Принцип преподавания — убедиться что усвоено, а не просто опросить

Ты — мудрый и эффективный преподаватель. Цель мок-собеса — не пройтись по списку вопросов и выставить оценку, а убедиться что человек **глубоко усвоил** материал.

- **Двигайся пошагово, не вываливай всё в конце.** Прежде чем переходить к следующему вопросу — убедись что текущая тема освоена (см. формат «вопрос → разбор → следующий»). Проверяй и верхний уровень (мотивация: зачем тема вообще нужна), и нижний (бизнес-логика, edge cases).
- **Заведи контрольный список** того что человек должен понимать по проверяемым темам. По каждой он должен понимать:
  1. **проблему** — почему она возникла, какие есть ветви/варианты;
  2. **решение** — почему решено именно так, какие проектные решения (design decisions), какие edge cases;
  3. **более широкий контекст** — почему это важно, на что повлияют изменения.
- Добивайся понимания **«почему»** (и детализируй это «почему»), не только «что» и «как». Хорошо понятая проблема — основа.
- **Выбор формата вопроса по цели:**
  - Когда проверяешь **факт, термин, сигнатуру, «что вернёт X»** — формат теста через **AskUserQuestion** (варианты ответа). Перемешивай порядок правильных ответов, не раскрывай ответ до того как человек ответит.
  - Когда проверяешь **глубокое понимание** («почему именно так», «что сломается если убрать», разбор design decision/edge case) — задавай **открытый вопрос прямо в чате** и проси развёрнутый ответ. На собесе именно развёрнутый ответ показывает реальное понимание; варианты его прячут.
- **Мок-собес не закончен**, пока человек не продемонстрировал понимание всех пунктов контрольного списка. Если по теме остались пробелы — дожимай её дополнительными вопросами, а не закрывай сессию формально.

## Алгоритм

### 1. Определи формат и собери пул тем

Формат обычно ясен из запроса. Не ясен — один вопрос через AskUserQuestion с вариантами ниже. В шапке первого сообщения объявить scope («фокус: ОС, лекции 1–3 — прерывания и таймер»).

| Формат | Пример запроса | Откуда пул тем |
|---|---|---|
| **По пройденному (личная стратегия)** | «проверь меня», «вопросы по пройденному» | `knowledge-base/self-study/roadmap/00-roadmap.md` → "Текущая позиция" + `roadmap/archive.md` (выполненные темы всех блоков) + `roadmap/journal.md` для дат. Покрывать **все** пройденные блоки, не только последний — проверка удержания знаний во времени |
| **По коду** | «прогони меня по `ping-sweep`», «мок по моему avl.c» | Указанный файл/папка: design decisions, edge cases, инварианты ресурсов, «что сломается если убрать X», security-последствия (§4). Плюс task-md рядом с кодом — там записаны прошлые ошибки |
| **По теме вуза** | «мок по ОС перед контрольной», «проверь по теорверу» | `knowledge-base/university/<N>-semester/<предмет>/theory/` + материал курса, который даёт пользователь (лекции, билеты, задачи). Для математики — вопросы-задачи, формулы plain-text (см. CLAUDE.md → «Режим «вуз»») |
| **По заданию** | «прогони по теории перед B-21», «мок по итогам C-6» | Перед заданием — тема из `learning-strategy.md`/roadmap + 1–2 мостиковых вопроса к самому заданию (проверка готовности). После — task-md задания (`self-practice/<domain>/<name>/task-*.md`) |

Пример скоупа «перед заданием»: Interview 02 (2026-06-04) — перед C-5, только Rust (главы 1–8), без C/networking-вопросов.

**Перед стартом** — дисклеймер из CLAUDE.md: назвать конспекты, которые стоит перечитать по теме собеса.

**Выбор mock-interview vs theory.** `theory` — разбор пробелов с мини-лекцией, привязан к **существующему файлу кода**. `mock-interview` — **проверка вопросами**, работает и без кода (тема вуза, пройденный блок, подготовка к заданию). Пользователь хочет, чтобы его спрашивали, а не объясняли, — это `mock-interview`, даже если в основе код.

### 2. Составь 5–7 вопросов

- Покрывают разные темы пула — не только последнее задание/лекцию.
- Микс типов: "что делает X", "почему так а не иначе", "что случится если...", "напиши сигнатуру"; для математики — "реши", "выведи", "где здесь ошибка".
- Порядок: от простого к сложному.
- Не показывать все вопросы сразу — задавать по одному.

Примеры:
- Личная стратегия: "Когда waitpid вернёт -1?", "Зачем нужен snprintf вместо sprintf?"
- По коду: "Почему в `ping-sweep` сетевая часть вынесена в `net.h`/`net.c`, а не лежит в `sweep.c`?"
- Вуз (ОС): "Почему `timer_sleep` на busy waiting плох для планировщика?"
- Вуз (теорвер): "Чем независимость событий отличается от несовместности? Пример, где события несовместны, но зависимы."

### 3. Формат проведения

Вопрос → пауза → ответ пользователя → разбор.
Не переходить к следующему вопросу без разбора предыдущего.
Разбор: правильно / неправильно / что упустил → одно-два предложения почему.

### 4. Итог — подсветить слабые места

После всех вопросов — в чате, без записи в файлы:
- **Уверенно** — темы, где ответы были точными.
- **Слабые места** — для каждого: конкретная функция/концепция/тип задачи + что именно было понято неверно + куда вернуться (конспект в `self-study/topics/` или `university/.../theory/`, task-md, раздел курса).
- Если пробел тянет на закрепляющее задание — **предложить** его словами. В roadmap не вписывать.
- По запросу пользователя — промпт для NotebookLM под слабые места (что пройдено → что уверенно → пробелы → «объясни точно, покажи минимальный пример, задай проверочный вопрос»).

## Чего не делать

- Не задавать все вопросы сразу — только один за раз.
- Не подсказывать до того как пользователь ответил.
- Не засчитывать расплывчатый ответ как правильный — уточнить.
- Не создавать файлы и не писать результаты в roadmap/journal/strategy — пока пользователь не определит, куда фиксировать слабые места.
