# Скилл: leetcode

Отдельный трек **вне** учебной стратегии СЗИ. Цель — паттерны для собеседований + образ мышления. Языки: **Python** (основной), **Rust** (второй проход).

Триггеры: `/leetcode`, «дай литкод/leetcode задачу», «следующая литкод», «запиши решение литкод».

Две функции: **(A) советовать следующую задачу** и **(B) оформлять решённую**. Определить по запросу, какой режим.

---

## A. Советовать следующую задачу

### 1. Прочитать план
`knowledge-base/leetcode/00-roadmap.md` — источник порядка разделов и задач. Опираться на файл, **не на память**.

### 2. Определить прогресс по отметкам `[x]`
Источник истины — отметки в `00-roadmap.md`: `[x]` = решено, `[ ]` = нет. **Не** сканировать папки для статуса: папка может существовать при `[ ]` (задача «в работе» — заготовка выдана, но решение не записано). Первая `[ ]` сверху вниз по плану = дефолтная следующая.

### 3. Сопоставить и выбрать следующую
- Пройти план сверху вниз, найти первую `[ ]` — это дефолтная следующая.
- Держать порядок разделов. Внутри раздела — порядок из плана (Easy → Medium → Hard).
- Разделы 9 (Tries), 12 (Advanced Graphs), 17 (Math) — можно отложить: если пользователь на них упёрся, предложить перескок вперёд, не блокировать.
- Не гнать весь раздел разом: 8–12 задач на раздел достаточно, дальше следующий раздел. Если в текущем разделе уже ≥8 отметок `[x]` — предложить перейти к следующему разделу, даже если в текущем остались задачи (пометить «добить позже»).

### 4. Учесть слабые паттерны
Глянуть раздел «Слабые паттерны» в `00-roadmap.md` и/или пометки `Далось: со скрипом/читал разбор` в `notes.md` решённых задач. Если есть слабый паттерн и с его последнего захода прошло несколько задач — предложить **повторную** задачу на тот же паттерн вперёд новой темы. Правило проекта: паттерны, где было тяжело, возвращать точечно.

### 5. Выдать рекомендацию
Коротко, без воды:
```
Следующая: <slug> — <Название> (<сложность>) · <теги>
Раздел: <N. Название> · решено в разделе: X/Y, всего: A/B
Ссылка: leetcode.com/problems/<slug>/
```
- По умолчанию **1 задача**. Если пользователь хочет выбор — дать 2–3 из текущего/соседнего раздела.
- **Не давать решение и не спойлерить подход.** Максимум — назвать паттерн (он и так в плане), если пользователь просит намёк. Идея задачи — его работа.
- Гейтинг §2: посоветовал — стоп. Заготовку **не** создавать сразу (иначе копятся пустые папки от просмотров). Ждать явного «беру»/«погнали»/«решаю» — только тогда шаг 6.

### 6. Завести заготовку и открыть в редакторе — ТОЛЬКО по явному «беру/погнали»
Триггер: пользователь подтвердил, что садится решать именно эту задачу («беру», «погнали», «решаю», «го»). Голая рекомендация из шага 5 папку **не** создаёт. При подтверждении:
- Создать папку `knowledge-base/leetcode/<slug>/` (`slug` строго из плана), если её ещё нет.
- Скопировать `_TEMPLATE/solution.py` в `<slug>/solution.py` — **если файла ещё нет** (не затирать начатое). Подставить в docstring название, URL, паттерн из строки плана.
- Открыть заготовку: `code <абсолютный путь>/solution.py`. Только `code`, без osascript/AppleScript (см. правило проекта про превью файлов).
- **`[ ]` в плане не трогать** — задача пока «в работе», отметку `[x]` ставит только режим B. Папка без `[x]` = в работе, это ожидаемо.
- Гейтинг §2: заготовка открыта — стоп, ждать «решил»/«давай запишем»/«следующая».

## B. Оформить решённую задачу

Когда пользователь принёс решение или просит записать.

### 1. Папка и отметка `[x]`
Папка `knowledge-base/leetcode/<slug>/` обычно уже создана в режиме A (при выдаче). Если задача пришла со стороны и папки нет — создать (`slug` строго как в плане, кусок URL leetcode). Если задачи нет в плане — добавить строку в нужный раздел `00-roadmap.md`.
После того как решение и заметка на месте — **поставить `[x]`** в строке плана (`- [ ] \`<slug>\`` → `- [x] \`<slug>\``). Это и есть отметка «решено» (источник истины прогресса).

### 2. Положить решение
`solution.py` (или `solution.rs`) в папке — обычно это та заготовка, что открыли в режиме A, уже с кодом пользователя. Шапка-docstring: название, URL, паттерн, время/память (шаблон — `_TEMPLATE/solution.py`). Код — **пользователя**, не переписывать за него. Если ревью кода нужно — это отдельно, по скиллу `check`.

### 3. Положить заметку
`notes.md` по шаблону `_TEMPLATE/notes.md`: раздел, сложность, теги `#…`, дата, «далось», **идея/паттерн** (2–4 строки — интуиция, не пересказ кода), ловушка, сложность O().
- Дату брать текущую (см. currentDate).
- Идею формулировать вместе с пользователем: спросить «в одну фразу — почему здесь работает <паттерн>?». Не сочинять за него.

### 4. Обновить слабые паттерны
Если «далось: со скрипом/читал разбор» — дописать паттерн в раздел «Слабые паттерны» `00-roadmap.md` (для точечного возврата в режиме A).

## Чего не делать
- Не решать за пользователя и не спойлерить подход — цель трека образ мышления, готовое решение его убивает (см. правило проекта про недоверие LLM в скучном/важном коде — здесь готовый ответ так же вредит).
- Не хранить отдельный список «решено» — единственный источник это отметки `[x]` в `00-roadmap.md`. Папки статус не задают (папка при `[ ]` = задача в работе).
- Не тащить сюда стратегию СЗИ и наоборот: это изолированный трек, в roadmap/journal основного проекта он не попадает.
- Не выдумывать номера/slug задач: если не уверен в slug — свериться с URL leetcode, а не угадывать.
