# Скилл: explain-code

Используется когда пользователь просит объяснить код, функцию, концепцию или системный вызов.

---

## Алгоритм

### 1. Проверь vault перед объяснением

Поищи тему в `knowledge-base/topics/` (Glob или Grep по названию концепции).

**Если файл найден:**
Первый ответ — только путь:
"Тема уже в vault: `knowledge-base/topics/linux/opendir.md`"
Подожди. Если пользователь просит объяснить — переходи к шагу 2.

**Если файла нет:**
Переходи к шагу 2 сразу.

### 2. Прочитай код

Найди нужный файл в тематических папках (`linux/`, `networking/` и т.д.) или попроси путь.

### 3. Объясняй в три слоя

- **Что делает** — одно предложение, без терминов.
- **Как работает** — пошагово, с конкретными строками кода. Называй номера строк.
- **Почему так** — зачем именно этот подход, какие альтернативы существуют и почему они хуже/лучше.

### 4. Используй аналогии

Только из того что пользователь уже знает:
- Знает C: используй аналогии с указателями, файловыми дескрипторами.
- Знает Linux: сравнивай с командами (`ls`, `cat /proc/...`).
- Не знает тему: объясни через бытовой пример, потом перейди к техническому.

### 5. Паттерны подачи материала

Эти приёмы существенно облегчают понимание. Использовать **по умолчанию**, а не "когда захочется".

**(а) Actors-with-letters — обозначай участников буквами и опиши их явно**

Когда в объяснении больше одного процесса/потока/узла — давай им короткие имена и заводи "сетап" в начале:

> Сетап: P — родитель. C1 — первый ребёнок. C2 — второй ребёнок.
> P создал pipe `[rfd, wfd]`. Договорённость: C1 пишет в `wfd`, P читает из `rfd`.

Дальше в тексте используй только эти буквы (`P`, `C1`, `wfd`) — это резко снижает когнитивную нагрузку (cognitive load). Без этого читатель каждый раз вспоминает "о ком сейчас речь".

Применять для: процессов, потоков, сокетов, нод сети, пользователей в threat model, любых множественных сущностей.

**(б) Numbered steps — пошагово, а не сплошным текстом**

Когда описываешь **последовательность** (что происходит во время syscall, как разворачивается баг, как идёт handshake) — формат "1. ... 2. ... 3. ..." всегда лучше сплошного абзаца. Даже если шагов всего три. Каждый шаг — одно действие, одна строка.

Плохо: "Ядро дублирует task_struct, потом копирует mm_struct с COW, потом копирует fd-таблицу инкрементируя refcount каждого file, потом..."
Хорошо:
```
1. Ядро дублирует task_struct.
2. Копирует mm_struct (страницы помечаются copy-on-write).
3. Копирует fd-таблицу — refcount каждого file++.
4. Возвращается дважды: у родителя ret=pid_ребёнка, у ребёнка ret=0.
```

**(в) Таблицы для классификации**

Когда есть N вариантов / N сценариев / N техник — таблица. Колонки: вариант, что делает, когда применять.

**(г) Один вопрос — один ответ**

Если пользователь спросил про X — отвечай **только про X**. Не упоминать сбоку Y и Z которые "тоже относятся к теме". Это перегружает.

Жёсткое правило: **если в ответе на простой вопрос появляется ≥3 новых терминов которых пользователь не знает — стоп**. Сократить ответ до главного, остальное предложить отдельной theory-сессией.

### 6. Английские термины — обязательно

Уровень пользователя: B2 (читает и смотрит свободно, говорить тяжело).
Цель — выстроить рабочий технический словарь на английском.

- Каждый ключевой технический термин даём **на английском с русским переводом в скобках при первом упоминании**:
  "процесс-зомби (zombie process)", "захват блокировки (lock acquisition)", "состояние гонки (race condition)".
- При повторных упоминаниях в той же сессии — можно использовать только английский термин, если он уже введён.
- Названия системных вызовов, функций, флагов — **только английский** (никогда не переводить `fork()`, `EAGAIN`, `O_NONBLOCK`).
- Идиомы которые имеют устоявшийся английский термин (ownership, lifetime, borrow checker, syscall, kernel space) — давать на английском, не калькировать на русский.

### 7. Задай уточняющие вопросы

2–3 вопроса для проверки понимания. Не "всё понял?", а конкретные:
- "Что вернёт readlink если симлинк битый?"
- "Чем opendir отличается от open?"

Задавать по одному. Не переходить к следующему без ответа на предыдущий.

Если пользователь правильно ответил на 2–3 вопроса подряд и не путался —
это сигнал для `session-debrief`: тема усвоена.

### 8. Предложи добавить в vault

Если концепция новая или объяснялась с деталями которых нет в `knowledge-base/topics/`:
"Добавить в vault?" → используй скилл `vault-write`.

---

## Чего не делать

- Не объяснять всё сразу одним блоком текста.
- Не использовать термины без расшифровки если тема новая.
- Не хвалить за вопрос ("отличный вопрос!") — сразу к сути.
- Не переходить к следующему вопросу пока не получен ответ на предыдущий.
- Не предлагать создать файл в vault если он уже существует.
