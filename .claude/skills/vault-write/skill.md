# Скилл: vault-write

Триггеры:
- прямая просьба: "добавь в vault", "запиши тему", "обнови knowledge-base"
- вызов из `session-debrief` (шаги 2–3)
- вызов из `explain-code` после объяснения новой концепции
- вызов из `code-review` после обнаружения концепции которой нет в topics/

---

## Алгоритм

### 1. Задай один вопрос

Перед записью — всегда спрашивать:
"Что было сложным, непонятным или интересным?"

Один вопрос. Подождать ответа. Ответ определяет что именно
и насколько подробно расписывать.

**Исключение**: если вызов из `session-debrief` и вопрос там уже задавался —
не повторять, использовать уже полученный ответ.

### 2. Определи тип записи

| Ситуация | Куда |
|----------|------|
| Концепция языка C | `knowledge-base/topics/c/` |
| Концепция Linux internals | `knowledge-base/topics/linux/` |
| Сети, сокеты, протоколы | `knowledge-base/topics/networking/` |
| Разбор чужого open-source кода | `knowledge-base/topics/reading/` |
| LLM-security (этапы Z/I/J) | `knowledge-base/topics/llm-sec/` |
| Web/CTF/общая безопасность | `knowledge-base/topics/security/` |
| Концепция Rust | `knowledge-base/topics/rust/` (создать при первом C-task'е) |
| Структура данных (часть закрытого блока A) | `knowledge-base/topics/ds/` (хаб: `00-index.md`) |
| Выполненное задание | `knowledge-base/tasks/block-X-<name>/task-<блок><NN>-<name>.md` (нумерация внутри блока с буквенным префиксом, например `block-b-networking/task-b04-getaddrinfo.md`) |
| Reading-сессия | `knowledge-base/tasks/block-X-<name>/reading-NN.md` (в папке тематического блока) + конспект в `topics/reading/` |
| Мок-собес | `knowledge-base/interviews/interview-NN.md` |
| CTF writeup | `knowledge-base/ctf/<platform>/<category>/<task>.md` |
| Обновление существующей записи | найти файл → дополнить (не создавать дубликат) |

Перед созданием нового файла — проверить что он не существует (`Glob` или `Grep`).

### 3. Структура topics/ файла

**Frontmatter обязателен.** Obsidian рендерит его как табличку "Свойства" в начале страницы — это быстрый снимок темы без чтения текста.

```
---
тема: <развёрнутое название: русское + английский термин, как в заголовке>
блок: <A — Linux syscalls | B — Сетевой стек | C — Rust | D — Rust intermediate | E — Crypto | F — VPN | G — Sandbox | H — eBPF | I — LLM-sec | J — LLM-sec | Z — Python bonus | DS — Структуры данных (экзамен) | Фундамент (theory) | Reading | Security/CTF | Курс — Архитектура Linux>
дата: YYYY-MM-DD
связано:
  - "[[wikilink1]]"
  - "[[wikilink2]]"
---

# <Название концепции на русском> / <English term>

## Что это
Одно предложение. Английский термин в скобках при первом упоминании если он не вынесен в заголовок.

## Ключевые термины (English)
- term 1 — короткое определение
- term 2 — короткое определение
*(этот раздел обязателен — это словарь, который растёт)*

## Как работает
Механика. Без воды. Последовательно.

## Пример
<только реальный код из сессии — не generic>

## Подводные камни
Что может пойти не так: NULL, errno, неинициализированная переменная, edge cases.

## Связанные темы
[[wikilink]] [[wikilink]]
```

Для новых тем — писать подробно: с антипримерами, объяснением "почему так а не иначе".

**Правила frontmatter:**
- `тема:` — то же что и H1, человекочитаемо. Не filename.
- `блок:` — к какому учебному блоку относится. Берётся из текущего активного блока (см. `roadmap/00-roadmap.md` → "Текущая позиция") или указывается явно для специальных типов (Reading, CTF, курс).
- `дата:` — день создания записи. Никогда не обновлять при правках — это исторический маркер.
- `связано:` — YAML-список. Каждый `[[wikilink]]` — **в кавычках** на отдельной строке с отступом `  - `. Без кавычек Obsidian парсит `[[...]]` как невалидный YAML и выкидывает frontmatter с ошибкой "Недопустимые свойства". Минимум одна ссылка если в vault есть смежные темы; пусто (`связано:` без элементов) — только для первого файла в новой категории.

**Английские термины в записях (обязательно):**
- Заголовок темы: русское название + английский термин через слэш (`Состояние гонки / Race condition`).
- Раздел `## Ключевые термины (English)` — глоссарий ключевых слов темы на английском с короткими определениями. Это резюме-словарь для будущих собеседований и чтения мануалов.
- В тексте — английский термин в скобках при первом упоминании.
- Названия функций/сисколлов/флагов — всегда английский, никогда не транслитерировать.

**Правила для задач:**
- Секции до `---` — описание задания (что дано). Секции после — опыт (что сделал).
- Для in-progress задач: секции после `---` оставить `*(заполняется после выполнения)*`.
- `## Связанные темы` — обязательно, это граф. Минимум 2 `[[wikilink]]`.
- После создания задания — проверить что `roadmap/journal.md` содержит ссылку `[[task-<блок><NN>-name]]` в таблице нужного блока (таблицы «Задачи — writing» разбиты по блокам A/B/C/...).

---

## Чего не делать

- Не писать generic примеры — только код из реальной сессии.
- Не создавать новый файл если тема уже есть — сначала проверить.
- Не дублировать: tasks/ про опыт, topics/ про концепцию.
- Не пропускать шаг 1 (если вопрос ещё не задавался в этой сессии).
- Не начинать с длинного введения — сразу к сути.
