# Скилл: give-task

Используется когда пользователь говорит "у меня есть N часов/минут" или "дай задание".

---

## Алгоритм

Шаг 1 — это **проверка перед выдачей задания**: незакрытые закрепляющие задания приоритетнее главного трека. Только если чисто — к шагу 2.

### 1. Проверь незакрытые закрепляющие задания после мок-собесов

Прочитай `knowledge-base/00-roadmap.md` → "Текущая позиция" → "Невыполненные закрепляющие задания". Это primary source — если там пусто, идём дальше. Если что-то есть — они приоритетнее главного трека.

Если есть невыполненные закрепляющие задания — **они приоритетнее следующей темы по плану**. Предложить их первым же сообщением: "После Interview NN остались закрепляющие задания (перечислить), их нужно закрыть до перехода к <следующая тема>". Без этого пробелы из мок-собеса остаются непроработанными.

Детали по слабым местам конкретного Interview NN — в `strategy/learning-strategy.md` → раздел `#### Interview NN`.

Оформление: одним сшитым task'ом `task-NN-interviewMM-reinforce.md` (несколько микро-программ внутри одного файла) — это дешевле для vault и нагляднее как блок работы над пробелами.

Если чисто — продолжай к шагу 2.

### 2. Прочитай контекст

**Primary source (статус):** `knowledge-base/00-roadmap.md` → "Текущая позиция". Там:
- Активный блок и его статус.
- **Позиция в блоке**: сколько атомарных уже выполнено, какое следующее по счёту, нужна ли интеграционная (на позициях 5/10/15/20), близок ли магнум опус.
- Выполненные темы блока (по всем блокам).
- Последний выполненный task.
- "Следующий шаг" — следующий пункт главного трека.
- "Параллельные блоки/треки доступны сейчас" — это критично, см. шаг 3.

**Plan source (детали):** `strategy/learning-strategy.md`:
- Раздел "## Структура блока" — определение 16+4+1 и гейта закрытия. Перечитывать всегда.
- Раздел активного блока (например `### Блок B`) — карта тем, описания пунктов.
- Раздел параллельного блока (например `### Блок C — Rust`) — детали для альтернативы.

Стратегия **не содержит** меток статуса `[ТЕКУЩИЙ]` / `[✅]` — это план без сиюминутного состояния. Статус живёт только в roadmap.

### 3. Определи тип следующего задания

По позиции в блоке выбери один из трёх типов:

**(а) Атомарное задание** (большинство случаев): следующая по карте тем тема блока. Одна тема — одна задача.

**(б) Интеграционное задание** (после каждых 4 атомарных — позиции 5, 10, 15, 20): синтез последних 4 атомарных тем в одном проекте. **Не вводить новой теории.** Цель — совместить пройденное. Формулировать так, чтобы реально использовались все 4 темы (если естественно не сочетаются — переосмыслить набор, а не натягивать).

**(в) Магнум опус** (21-е, финал блока): заранее определённый проект блока. Перед стартом — короткий чек: "вот что входит в магнум опус, всё ли пройдено в атомарных". Если темы недостаточно — добавить их перед опусом.

Тип задания пишется в начале сообщения пользователю: "Это **атомарное B-N** (тема Y)" или "Это **интеграционное B-5** — синтез B1-B4".

**Исключение — учебник-driven блоки (Rust по The Book, блок C).** Они идут **линейно по главам** (одна глава = одно задание) и под структуру «4 атомарных + интеграционное + опус» не подведены — намеренно, переработки не будет. Правило «каждое 5-е интеграционное» к ним **не применяется**: `C-N` = «N-е задание по главам», не «позиция N в карте». Все задания такого блока — атомарные по новой главе. Если пользователь спросит «почему C-5 не интеграционное» — объяснить это, не натягивать интеграцию. Детали — `strategy/learning-strategy.md` → "## Структура блока" → исключение для учебник-driven блоков.

**НЕ затаскивать в задание материал из ещё не прочитанных глав.** В учебник-driven блоке задание ограничено главами, которые пользователь уже прошёл. Пример провала (C-5, эта сессия): в задание по гл.7–8 я вписал `.iter().filter().count()` — это гл.13 (итераторы/замыкания), пользователь её не читал, пришлось объяснять на ходу и давать `for`-альтернативу. Перед выдачей — свериться с картой блока (`learning-strategy.md` → "### Блок C"): какие главы пройдены, и формулировать **только** в их рамках. Если естественное решение требует более поздней главы — переформулировать задачу под текущие знания (тут: подсчёт через `for` + счётчик, а не итераторный конвейер), а позднюю тему оставить её главе.

### 4. Спроси про параллельный трек, если он доступен

В `00-roadmap.md` → "Текущая позиция" есть раздел "**Параллельные блоки/треки доступны сейчас**". Если там перечислены доступные блоки (C, B0, и т.д.) — **не выдавать сразу следующую задачу из главного трека**. Прежде всего предложить пользователю выбор:

```
Сейчас доступны параллельные блоки помимо главного:
- Главный трек: <тип задания> — <тема>
- Параллельно: <блок> — <тема>
- Параллельно: <блок> — <тема>

Что сегодня?
```

Это **обязательно** при наличии параллельных треков. Чёткое правило: писать N подряд задач из главного трека без перехода на параллельный — нездорово (теряется Rust и т.д.).

**Зафиксированный ритм 3:1 (B : C) — действует на время совместного прохождения блоков B и C** (договорённость 2026-06-04). На каждые **3 задания из B** (главный трек, сетевой фундамент) — **1 из C** (Rust, параллельный). Механика:
- При предложении выбора (блок выше) — **по умолчанию рекомендовать B**, и переключать на C только когда с момента последней C-задачи прошло 3 B-задачи. Считать по журналу writing в `00-roadmap.md` (даты/номера B и C).
- Текущий перекос (на старте договорённости: C=5, B=3) **выправляется плавно** — ближайшие задания идут из B, пока пропорция прохождения блоков не сравняется (ориентир ~B=8/26). **Не** загонять пользователя в 12 B подряд ради строгого соотношения — это убивает параллельный Rust. 3:1 — это **ритм вперёд**, а не ретро-долг.
- Пользователь всегда может перебить («хочу C сегодня» / «давай ещё B») — ритм это дефолт, не жёсткое ограничение.
- Когда один из блоков закроется (B-26 или конец карты C) — ритм снимается, пересмотреть в этом файле.

Если пользователь явно сказал "дай B-N" или "продолжаем главный трек" — без вопроса, сразу к шагу 5.

CTF и мок-собес здесь не предлагаются как альтернативы — они приходят по запросу пользователя или по решению Claude (reading-code), см. соответствующие скиллы.

### 5. Определи масштаб по времени

| Время | Тип задачи |
|-------|------------|
| 30–60 мин | Задача на одну конкретную функцию или системный вызов. Подходит для атомарных. |
| 1–2 часа | Мини-утилита с полным циклом. Атомарное "посерьёзнее" или короткое интеграционное. |
| 2+ часов | Интеграционное задание или сегмент магнум опуса. Задание → код → ревью → vault. |

### 6. Сформулируй задание

Конкретно:
- **Тип** (атомарное N / интеграционное N / магнум опус) и позиция в блоке.
- Что написать (название, что принимает, что выводит).
- Какие функции/системные вызовы использовать.
- **Какие хедеры подключать.** Для каждой функции/типа из задания указать `#include` явно. Не "разберётся по man" — список хедеров в задании. Это снимает класс ошибок "implicit declaration", "забыл `<errno.h>`", "не знал что `pthread_*` в `<pthread.h>`" и формирует привычку держать соответствие функция→хедер в голове. Для часто используемых функций мок-собеса — особенно строго (`errno` → `<errno.h>`, `pthread_*` → `<pthread.h>`, `O_*` флаги → `<fcntl.h>`).
- Для интеграционного — **явно перечислить какие 4 атомарных темы синтезируются** и где каждая используется в задаче.
- На каком механизме тренироваться.
- Где сохранить код (`linux/proc/`, `networking/` и т.д.).
- Что создать в vault: `knowledge-base/tasks/block-X-<name>/task-<блок><NN>-<name>.md`, где `block-X-<name>` — папка активного блока (`block-a-linux-internals`, `block-b-networking`, `block-c-rust`, и т.д. — название в kebab-case на английском). **Нумерация — внутри блока, с буквенным префиксом** (`task-b04-getaddrinfo`, `task-c05-...`). NN — двузначный (`01`, `02`, ...), равен позиции в блоке. Префикс блока в имени файла обязателен (иначе wikilink-имена конфликтуют между папками: `[[task-04]]` неоднозначен).

**Домен задачи определяется активным блоком** в "Текущей позиции" стратегии. Не предлагать темы из других блоков (Python, Rust, eBPF...) без явного запроса пользователя.

Сводка по доменам блоков (для быстрой ориентации, не источник истины):
- Блок A — C + Linux syscalls (закрыт по старой схеме, возврат в G).
- Блок B — C + сетевой стек.
- Блок C — Rust базовый.
- Блок D — Rust intermediate (tokio, serde, nix).
- Блок E — Криптография на Rust.
- Блок F — VPN на Rust.
- Блок G — C + Linux изоляция + углубление тем блока A.
- Блок H — eBPF (C + опционально Go).
- Блок I/J — Python + LLM-security.
- Блок Z — Python (prompt injection detector, bonus конца этапа 1).

### 7. Создай файл задания

Создай файл сразу — с заполненным разделом "Задание". Путь: `knowledge-base/tasks/block-X-<name>/task-<блок><NN>-<name>.md` (нумерация внутри блока с буквенным префиксом — `task-b04-getaddrinfo`), где `block-X-<name>` — папка активного блока. Текущие папки: `block-a-linux-internals`, `block-b-networking`, `block-c-rust`. Если активный блок ещё не имеет папки (D, E, F, G, H, I, J, Z) — создать её по той же конвенции (`block-X-<short-name-en>`, kebab-case, lowercase). Reading-сессии (`reading-NN.md`) — отдельная сквозная последовательность (не per-block), кладутся в папку блока по тематике.

В заголовке/frontmatter указать тип: `type: atomic | integration | magnum-opus` и позицию в блоке (`block-position: B-5`).
Остальные разделы оставить пустыми — заполнит `vault-write` по итогам.

### 8. Открой файл задания в VSCode

Сразу после создания файла открыть его — **только** командой:

code <abs_path>

**Никаких `osascript` / AppleScript / попыток автоматом поднять markdown preview** (Cmd+Shift+V и т.п.). Пробовали — хрупко, требует лишних разрешений, пугает пользователя. Превью пользователь включит сам. Это разрешено в allow-list ровно как `code <path>` и не должно обрастать ничем. (Подтверждено пользователем 2026-06-05.)

## Чего не делать

- Не давать задание без чтения стратегии — иначе задания будут хаотичными.
- Не давать задание которое уже выполнено (проверить "Выполненные темы блока X" в `00-roadmap.md` → "Текущая позиция").
- Не давать две темы сразу в атомарном задании — одна задача, один навык. **В интеграционном — наоборот**, обязан синтезировать минимум 4 темы.
- Не придумывать задачи "из головы" — только по стратегии.
- Не пропускать интеграционное задание на позициях 5/10/15/20 — это сердце новой структуры. Если темы не сочетаются естественно — это сигнал что карта тем плохо разложена, а не повод скипнуть.

## Обнови skills

На основе переписки и замечаний пользователя — обнови `.claude/skills/*.md`.
Конкретизируй, подстраивайся под стиль общения, записывай замечания.
При необходимости создавай новые скиллы.
Цель: идеальное понимание без толчков "посмотри в тот файл".
