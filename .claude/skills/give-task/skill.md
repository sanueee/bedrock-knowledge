# Скилл: give-task

Используется когда пользователь говорит "у меня есть N часов/минут" или "дай задание".

---

## Алгоритм

Шаги 1–2 — это **проверки перед выдачей задания**. Каждая может перенаправить пользователя на другой скилл или другую задачу. Только если обе чистые — переходить к шагу 3.

### 1. Проверь счётчики

Прочитай `knowledge-base/00-roadmap.md` → "Текущая позиция" → "Счётчики". Там три счётчика:

**Счётчик reading-code (≥ 4) — приоритет 1, обязательный:**
"Ты выполнил 4 writing-задачи с последнего reading. Перед следующей writing — нужна reading-сессия по чужому коду."
Не делать опциональным — это часть стратегии. Сразу → скилл `reading-code`.

**Счётчик мок-собеса (≥ 8) — приоритет 2, мягкий:**
"Ты выполнил 8 задач с последнего мок-собеса. Хочешь сначала проверить знания?"
Если согласен → скилл `mock-interview`.

**Счётчик CTF (≥ 5) — приоритет 3, мягкий:**
"Ты выполнил 5 задач с последнего CTF. Хочешь сначала CTF-сессию на picoCTF? Или продолжим с writing?"
Если согласен → скилл `ctf`.

Если сработали несколько счётчиков — порядок: сначала reading-code (обязательный), затем мок-собес следующей сессией, CTF — третьим. Не запускать всё в одну сессию.

### 2. Проверь незакрытые закрепляющие задания после мок-собесов

Прочитай `knowledge-base/00-roadmap.md` → "Текущая позиция" → "Невыполненные закрепляющие задания". Это primary source — если там пусто, идём дальше. Если что-то есть — они приоритетнее главного трека.

Если есть невыполненные закрепляющие задания — **они приоритетнее следующей темы по плану**. Предложить их первым же сообщением: "После Interview NN остались закрепляющие задания (перечислить), их нужно закрыть до перехода к <следующая тема>". Без этого пробелы из мок-собеса остаются непроработанными.

Детали по слабым местам конкретного Interview NN — в `strategy/learning-strategy.md` → раздел `#### Interview NN`.

Оформление: одним сшитым task'ом `task-NN-interviewMM-reinforce.md` (несколько микро-программ внутри одного файла) — это дешевле для vault и нагляднее как блок работы над пробелами.

Если обе проверки чистые — продолжай к шагу 3.

### 3. Прочитай контекст

**Primary source (статус):** `knowledge-base/00-roadmap.md` → "Текущая позиция". Там:
- Активный блок и его статус.
- Выполненные темы блока A / блока B / Фундамент (theory).
- Последний выполненный task.
- "Следующий шаг" — следующий пункт главного трека с функциями/путями.
- "Параллельные блоки/треки доступны сейчас" — это критично, см. шаг 4.
- Счётчики, невыполненные reinforce.

**Plan source (детали):** `strategy/learning-strategy.md`:
- Раздел активного блока (например `### Блок B — Сетевой стек`) — детальные описания всех пунктов блока (B0...B6) с функциями, библиотеками, путями. Сюда заходишь чтобы узнать "что именно в B2".
- Раздел параллельного блока (например `### Блок C — Rust`) — детали для альтернативы.

Стратегия **не содержит** меток статуса `[ТЕКУЩИЙ]` / `[✅]` — это план без сиюминутного состояния. Статус живёт только в roadmap.

### 4. Спроси про параллельный трек, если он доступен

В `00-roadmap.md` → "Текущая позиция" есть раздел "**Параллельные блоки/треки доступны сейчас**". Если там перечислены доступные блоки (C, B0, и т.д.) — **не выдавать сразу следующую writing-задачу из главного трека**. Прежде всего предложить пользователю выбор:

```
Сейчас доступны параллельные блоки помимо главного (B2 → libpcap):
- Главный трек: B2 — libpcap, разбор пакетов (C, ~2-3 часа)
- Параллельно: C1 — Rust The Book главы 1-4 (чтение с вопросами, ~1-2 часа)
- Параллельно: B0 — OWASP Top 10 web (теория + DVWA, ~1-2 часа)

Что сегодня?
```

Это **обязательно** при наличии параллельных треков. Без вопроса пользователь не знает что у него есть выбор — стратегия предполагает чередование. Чёткое правило: писать N подряд writing-задач из главного трека без перехода на параллельный — нездорово (теряется Rust, OWASP, и т.д.).

Если пользователь явно сказал "дай B2" или "продолжаем главный трек" — без вопроса, сразу к шагу 5.

CTF и reading-code управляются **счётчиками** (шаг 1), не предлагаются здесь как альтернативы. Они приходят автоматически когда счётчик достигнут.

### 5. Определи масштаб по времени

| Время | Тип задачи |
|-------|------------|
| < 30 мин | Концептуальная задача или чтение с вопросом. Без написания кода. |
| 30–60 мин | Задача на одну конкретную функцию или системный вызов. |
| 1–2 часа | Мини-утилита с полным циклом: написать → собрать → протестировать. |
| 2+ часов | Новый task: задание → код → ревью → документация в vault. |

### 6. Сформулируй задание

Конкретно:
- Что написать (название, что принимает, что выводит).
- Какие функции/системные вызовы использовать — брать из "Следующая задача" в стратегии.
- **Какие хедеры подключать.** Для каждой функции/типа из задания указать `#include` явно. Не "разберётся по man" — список хедеров в задании. Это снимает класс ошибок "implicit declaration", "забыл `<errno.h>`", "не знал что `pthread_*` в `<pthread.h>`" и формирует привычку держать соответствие функция→хедер в голове. Для часто используемых функций мок-собеса — особенно строго (`errno` → `<errno.h>`, `pthread_*` → `<pthread.h>`, `O_*` флаги → `<fcntl.h>`).
- На каком Linux-механизме тренироваться.
- Где сохранить код (`linux/proc/`, `linux/fd/` и т.д.).
- Что создать в vault (`knowledge-base/tasks/task-NN.md`).

**Домен задачи определяется активным блоком** в "Текущей позиции" стратегии. Не предлагать темы из других блоков (Python, Rust, eBPF...) без явного запроса пользователя.

Сводка по доменам блоков (для быстрой ориентации, не источник истины):
- Блок A — C + Linux syscalls.
- Блок B — C + сетевой стек (sockets, libpcap, DNS, TLS).
- Блок C — Rust базовый (rewrite of A).
- Блок D — Rust intermediate (tokio, serde, nix).
- Блок E — Криптография на Rust.
- Блок F — VPN на Rust.
- Блок G — C + Linux изоляция (namespaces, seccomp, cgroups).
- Блок H — eBPF (C + опционально Go).
- Блок I/J — Python + LLM-security.
- Блок Z — Python (prompt injection detector, bonus конца этапа 1).

### 7. Создай файл задания

Создай `knowledge-base/tasks/task-NN.md` сразу — с заполненным разделом "Задание".
Остальные разделы оставить пустыми — заполнит `vault-write` по итогам.

## Чего не делать

- Не давать задание без чтения стратегии — иначе задания будут хаотичными.
- Не давать задание которое уже выполнено (проверить "Выполненные темы блока X" в `00-roadmap.md` → "Текущая позиция").
- Не давать две темы сразу — одна задача, один навык.
- Не придумывать задачи "из головы" — только по стратегии.
