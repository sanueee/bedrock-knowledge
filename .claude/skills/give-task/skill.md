# Скилл: give-task

Используется когда пользователь говорит "у меня есть N часов/минут" или "дай задание".

---

## Алгоритм

Шаг 1 — это **проверка перед выдачей задания**: незакрытые закрепляющие задания приоритетнее главного трека. Только если чисто — к шагу 2.

### 1. Проверь незакрытые закрепляющие задания после мок-собесов

Прочитай `knowledge-base/roadmap/00-roadmap.md` → "Текущая позиция" → "Невыполненные закрепляющие задания". Это primary source — если там пусто, идём дальше. Если что-то есть — они приоритетнее главного трека.

Если есть невыполненные закрепляющие задания — **они приоритетнее следующей темы по плану**. Предложить их первым же сообщением: "После Interview NN остались закрепляющие задания (перечислить), их нужно закрыть до перехода к <следующая тема>". Без этого пробелы из мок-собеса остаются непроработанными.

Детали по слабым местам конкретного Interview NN — в `knowledge-base/interviews/interview-NN.md` (полная запись) и `roadmap/journal.md` → "Мок-собесы" (сводка). В стратегии их нет — она хранит только план.

Оформление: одним сшитым task'ом `task-NN-interviewMM-reinforce.md` (несколько микро-программ внутри одного файла) — это дешевле для vault и нагляднее как блок работы над пробелами.

Если чисто — продолжай к шагу 2.

### 2. Прочитай контекст

**Primary source (статус):** `knowledge-base/roadmap/00-roadmap.md` → "Текущая позиция". Там:
- Активный блок и его статус.
- **Позиция в блоке**: сколько атомарных уже выполнено, какое следующее по счёту, нужна ли интеграционная (каждое 5-е задание — точные позиции для активного блока в roadmap), близок ли магнум опус.
- Выполненные темы блока (по всем блокам).
- Последний выполненный task.
- "Следующий шаг" — следующий пункт главного трека.
- "Параллельные блоки/треки доступны сейчас" — это критично, см. шаг 3.

**Plan source (детали):** `knowledge-base/strategy/learning-strategy.md`:
- Раздел активного блока (например `### Блок B`) — карта тем, описания пунктов.
- Раздел параллельного блока (например `### Блок C — Rust`) — детали для альтернативы.

Структура блока (16+4+1, позиции интеграционных, гейт закрытия) — в скилле `plan-block`. Если активный блок ещё не расписан по заданиям (только проза) — сначала `plan-block`, потом выдача.

Стратегия **не содержит** меток статуса `[ТЕКУЩИЙ]` / `[✅]` — это план без сиюминутного состояния. Статус живёт только в roadmap.

### 3. Определи тип следующего задания

По позиции в блоке выбери один из трёх типов:

**(а) Атомарное задание** (большинство случаев): следующая по карте тем тема блока. Одна тема — одна задача.

**(б) Интеграционное задание** (каждое 5-е — позиции 5/10/15/20[/25…] по размеру блока): синтез последних 4 атомарных тем в одном проекте. **Не вводить новой теории.** Цель — совместить пройденное. Формулировать так, чтобы реально использовались все 4 темы (если естественно не сочетаются — переосмыслить набор, а не натягивать).

**(в) Магнум опус** (последнее задание блока, финал): заранее определённый проект блока. Перед стартом — короткий чек: "вот что входит в магнум опус, всё ли пройдено в атомарных". Если темы недостаточно — добавить их перед опусом.

Тип задания пишется в начале сообщения пользователю: "Это **атомарное B-N** (тема Y)" или "Это **интеграционное B-5** — синтез B1-B4".

**Исключение — учебник-driven блоки (Rust по The Book, блок C).** Они идут **линейно по главам** (одна глава = одно задание) и под структуру «4 атомарных + интеграционное + опус» не подведены — намеренно, переработки не будет. Правило «каждое 5-е интеграционное» к ним **не применяется**: `C-N` = «N-е задание по главам», не «позиция N в карте». Все задания такого блока — атомарные по новой главе. Если пользователь спросит «почему C-5 не интеграционное» — объяснить это, не натягивать интеграцию. Детали — скилл `plan-block` → исключение для учебник-driven блоков.

**НЕ затаскивать в задание материал из ещё не прочитанных глав.** В учебник-driven блоке задание ограничено главами, которые пользователь уже прошёл. Пример провала (C-5, эта сессия): в задание по гл.7–8 я вписал `.iter().filter().count()` — это гл.13 (итераторы/замыкания), пользователь её не читал, пришлось объяснять на ходу и давать `for`-альтернативу. Перед выдачей — свериться: какие главы **пройдены** (роадмап → "Текущая позиция", блок C) и какая **следующая** по оставшейся карте (`learning-strategy.md` → "### Блок C" — там только ещё не сделанные задания). Формулировать **только** в рамках уже пройденных глав. Если естественное решение требует более поздней главы — переформулировать задачу под текущие знания (тут: подсчёт через `for` + счётчик, а не итераторный конвейер), а позднюю тему оставить её главе.

### 4. Спроси про параллельный трек, если он доступен

В `roadmap/00-roadmap.md` → "Текущая позиция" есть раздел "**Параллельные блоки/треки доступны сейчас**". Если там перечислены доступные блоки (C, B0, и т.д.) — **не выдавать сразу следующую задачу из главного трека**. Прежде всего предложить пользователю выбор:

```
Сейчас доступны параллельные блоки помимо главного:
- Главный трек: <тип задания> — <тема>
- Параллельно: <блок> — <тема>
- Параллельно: <блок> — <тема>

Что сегодня?
```

Это **обязательно** при наличии параллельных треков. Чёткое правило: писать N подряд задач из главного трека без перехода на параллельный — нездорово (теряется Rust и т.д.).

**Зафиксированный ритм 3:1 (B : C) — действует на время совместного прохождения блоков B и C** (договорённость 2026-06-04). На каждые **3 задания из B** (главный трек, сетевой фундамент) — **1 из C** (Rust, параллельный). Механика:
- При предложении выбора (блок выше) — **по умолчанию рекомендовать B**, и переключать на C только когда с момента последней C-задачи прошло 3 B-задачи. Считать по журналу writing в `roadmap/journal.md` (даты/номера B и C).
- Если на старте перекос (C опередил B) — **выправлять плавно**: рекомендовать B, пока пропорция прохождения не сравняется. Текущий счёт B/C — по журналу writing, не хардкодить здесь. **Не** загонять в 12 B подряд ради строгого соотношения — это убивает параллельный Rust. 3:1 — это **ритм вперёд**, а не ретро-долг.
- Пользователь всегда может перебить («хочу C сегодня» / «давай ещё B») — ритм это дефолт, не жёсткое ограничение.
- Когда один из блоков закроется (B-26 или конец карты C) — ритм снимается, пересмотреть в этом файле.

Если пользователь явно сказал "дай B-N" или "продолжаем главный трек" — без вопроса, сразу к шагу 5.

CTF и мок-собес здесь не предлагаются как альтернативы — они приходят по запросу пользователя или по решению Claude (reading-code), см. соответствующие скиллы.

### 5. Определи масштаб по времени

| Время | Тип задачи |
|-------|------------|
| 30–60 мин | Задача на одну конкретную функцию или системный вызов. Подходит для атомарных. |
| 1–2 часа | Мини-утилита с полным циклом. Атомарное "посерьёзнее" или короткое интеграционное. |
| 2+ часов | Интеграционное задание или сегмент магнум опуса. Задание → код → ревью → vault. |

### 6. Сформулируй задание

Конкретно:
- **Тип** (атомарное N / интеграционное N / магнум опус) и позиция в блоке.
- Что написать (название, что принимает, что выводит).
- Какие функции/системные вызовы использовать.
- **В пошаговом разборе «что делает программа» — у каждого пункта указывать конкретные функции в виде `name()`** (правило пользователя 2026-07-05). Не описывать шаг абстрактным глаголом («отправить запрос», «прочитать ответ») без привязки к вызову — пользователь должен сразу видеть, чем шаг делается. Формат: функцию `name()` ставить **рядом с глаголом** (`отправить запрос через send()`) **или** в конце пункта перечислением (`… — send(), затем recv() в цикле`). Пример:
  ```
  1. Резолвит host → connect: getaddrinfo() + socket() + connect().
  2. Собирает текст запроса в буфер: snprintf().
  3. Отправляет запрос в цикле: send().
  4. Читает ответ до закрытия: recv() в цикле до 0.
  5. Находит границу заголовки/тело: memmem()/strstr() по "\r\n\r\n".
  ```
  Это устраняет разрыв «понял что делать, но не знаю чем» на новой теме.
- **Какие хедеры подключать.** Для каждой функции/типа из задания указать `#include` явно. Не "разберётся по man" — список хедеров в задании. Это снимает класс ошибок "implicit declaration", "забыл `<errno.h>`", "не знал что `pthread_*` в `<pthread.h>`" и формирует привычку держать соответствие функция→хедер в голове. Для часто используемых функций мок-собеса — особенно строго (`errno` → `<errno.h>`, `pthread_*` → `<pthread.h>`, `O_*` флаги → `<fcntl.h>`).
  - **Формат выдачи хедеров — готовый к copy-paste блок кода `#include`, НЕ таблица** (правило пользователя 2026-07-05). Дать один C-code-fence со списком `#include <...>` — так, чтобы пользователь скопировал целиком в начало файла. Соответствие функция→хедер выносить в **комментарий в той же строке** (`#include <netdb.h>   // getaddrinfo, gai_strerror`), а не в отдельную колонку. Пример:
    ```c
    #include <stdio.h>      // printf, fprintf, snprintf
    #include <string.h>     // strstr, strncmp, memcpy
    #include <strings.h>    // strcasecmp, strncasecmp
    #include <netdb.h>      // getaddrinfo, freeaddrinfo, gai_strerror
    #include <sys/socket.h> // socket, connect, recv, send
    #include <unistd.h>     // close
    #include <errno.h>      // errno
    ```
- Для интеграционного — **явно перечислить какие 4 атомарных темы синтезируются** и где каждая используется в задаче.
- На каком механизме тренироваться.
- Где сохранить: **папка задачи** `sections/<domain>/<name>/` — код и task-md лежат **вместе** (см. шаг 7).

**Домен задачи определяется активным блоком** ("Текущая позиция" в roadmap). Не предлагать темы из других блоков (Python, Rust, eBPF...) без явного запроса. Домены блоков — в `knowledge-base/strategy/learning-strategy.md` (разделы блоков), не дублировать здесь.

### 7. Создай папку задачи — task-md И код-файл вместе

**Структура: `sections/<domain>/<name>/`** — код и задание живут в одной папке (как `sections/leetcode/<problem>/`).

- **`<domain>`** — доменная папка по активному блоку: `ds`, `linux`, `networking`, `rust`, `crypto` (новый домен → новая папка `sections/<domain>/`, kebab-case, lowercase). Домен определяется активным блоком ("Текущая позиция"), не смешивать.
- **`<name>`** — имя задачи в kebab-case **без** блок-префикса (`service-fingerprint`, `getaddrinfo`, `rust-ch9-error-handling`). Совпадает с хвостом имени task-файла.

Создать в папке **сразу оба файла**:
1. **task-md** `task-<блок><NN>-<name>.md` — **имя сохраняет блок-префикс** (`task-b14-tls`, `task-c06-...`), иначе wikilink-имена `[[task-...]]` конфликтуют между папками. NN — двузначный, равен позиции в блоке.
2. **код-файл(ы)** с правильным именем и расширением (`fingerprint.c`, для Rust — `cargo new <proj>` внутри папки задачи). Файл — минимальный скелет: `#include`-блок из шага 6 + пустой `main`/сигнатуры (по [[feedback-exam-scaffold-minimal]] — тела пишет пользователь). Задача без кода (observational/reading/теория) — код-файл не создавать, только task-md.

### 8. Открой ОБА файла в VSCode

Сразу после создания открыть **и task-md, и код-файл** — **только** командой `code`:

code <abs_path_task_md> <abs_path_code>

(один вызов с двумя путями либо два вызова `code`). Для задачи без кода — открыть только task-md.

**Никаких `osascript` / AppleScript / попыток автоматом поднять markdown preview** (Cmd+Shift+V и т.п.). Пробовали — хрупко, требует лишних разрешений, пугает пользователя. Превью пользователь включит сам. Это разрешено в allow-list ровно как `code <path>` и не должно обрастать ничем. (Подтверждено пользователем 2026-06-05.)

## Чего не делать

- Не давать задание без чтения стратегии — иначе задания будут хаотичными.
- Не давать задание которое уже выполнено (проверить "Выполненные темы блока X" в `roadmap/archive.md`).
- Не давать две темы сразу в атомарном задании — одна задача, один навык. **В интеграционном — наоборот**, обязан синтезировать минимум 4 темы.
- Не придумывать задачи "из головы" — только по стратегии.
- Не пропускать интеграционное задание на позициях 5/10/15/20 — это сердце новой структуры. Если темы не сочетаются естественно — это сигнал что карта тем плохо разложена, а не повод скипнуть.
