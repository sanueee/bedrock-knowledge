# Скилл: exam

Триггер: пользователь вызывает `/exam` (с аргументом или без) либо пишет про
подготовку к экзамену по **структурам данных**.

Это **временный учебный блок** (дедлайн ~2026-06-20), ортогональный карьерному
вектору (сети/Rust/eBPF). Он живёт отдельно от `give-task`/основного roadmap,
чтобы не смешивать. Свой primary source — **`knowledge-base/topics/ds/00-index.md`**.

---

## Primary source (читать ВСЕГДА в начале)

`knowledge-base/topics/ds/00-index.md` — хаб подготовки:
- **Карта тем** со статусами (⬜ не пройдено / 🟡 конспект есть / ✅ уверенно / ⚠️ слабое).
- **Слабые места** — пробелы, вскрытые пробниками. Приоритетнее непройденного.
- **Журнал пробных экзаменов**.
- **Дедлайн** и план на оставшиеся дни.

Конспекты по темам — отдельные файлы `topics/ds/NN-<name>.md`. Код — `ds/` (корень репо).

**Контекст пользователя (из CLAUDE.md):** C — на уровне уверенного джуна (writing на C
идёт легко, это **builder** — любит реализовывать). Rust — старт (главы 1–8). Python —
школьный базис. Это важно: реализации структур давать на C как основные, а Python/Rust —
как параллели «как это выглядит на знакомом языке».

## Дисклеймер по статусам

«🟡 конспект есть» ≠ «знает». Знания выветриваются. Перед пробным экзаменом или
повторным разбором темы — **перечитать конспект** `topics/ds/NN-<name>.md` и сверить,
что в голове, а не только на бумаге. Если конспекта нет — пометить и создать после сессии.

## Подача формул (критично)

Любую математику — **plain-text/Unicode, НЕ LaTeX**. `$$...$$`, `\frac`, `\sum`, `\cdot`
в чате Claude Code не рендерятся (выводится сырой код) — пользователю это нечитаемо, и он
прямо просил так не делать (2026-06-10, [[feedback-formula-plaintext]]). Правила:
- степени `2^32` или `n²`; умножение `·`; суммы `Σ(i=1..n) …`; дроби `(n+1)/2`; Big-O `O(n log n)`; `≤ ≥ ≈ ∞ √`;
- многошаговые выводы — в ``` code-блоках ``` (моноширинный, ничего не ломается);
- единообразно в чате и в конспектах.

## Режимы (по аргументу)

`/exam` маршрутизирует по аргументу. Если аргумент неоднозначен — уточнить одним вопросом.

### Режим A — `/exam` (без аргумента): анализ и маршрутизация

Это **диспетчер**. Алгоритм:

1. Прочитать `00-index.md`: посчитать покрытие (сколько ⬜ / 🟡 / ✅ / ⚠️), достать слабые места, дедлайн, сколько дней осталось.
2. Если карта тем всё ещё помечена «предварительная» / пользователь не подтверждал syllabus — **спросить**: «Список тем пока предварительный. Скинь, что было на лекциях за семестр, или сверим с тем, что уже в карте?» Не блокироваться намертво — если пользователь говорит «работаем по текущей карте», продолжать.
3. Вывести сжатую сводку: `осталось N дней`, `покрытие: X/Y тем с конспектами`, `слабые места: ...`, `следующее по плану: <тема>`.
4. Предложить выбор (через обычный текст или AskUserQuestion):
   - **Разобрать тему** (по плану следующая, или слабое место в приоритете) → Режим B.
   - **Пробный экзамен** (тест) → Режим C.
   - **Билет** (классический устный) → Режим D.
   - **Повторить слабое** → Режим B по теме из «Слабые места».
5. Приоритет рекомендации: **слабое место (⚠️) > следующее непройденное (⬜) > повторение (🟡)**. «Следующее непройденное» = первый ⬜ по разделу **«Очередь изучения»** в `00-index.md` (канонический порядок). Ближе к дедлайну — толкать к пробным экзаменам.

### Режим B — `/exam <тема>`: разбор темы (теория, «интересно»)

Главный режим. **Каркас — шаблон препода (7 пунктов)**, потому что именно по нему
строится экзамен. Поверх — обогащение «чтобы блеснуть» (Python/Rust, реальные системы).
Не сухой пересказ: давать зацепки для памяти, «почему так, а не иначе».

Семь пунктов по каждой структуре (этот порядок — в `00-index.md` → «Шаблон разбора»):

1. **Определение** — что это абстрактно (ADT).
2. **Пример** — на C (основной язык пользователя), при пользе — Pascal как у препода. Показать объявление/устройство.
3. **Особенности** — нюансы, инварианты, детали реализации.
4. **Плюсы и недостатки**.
5. **Где применяется** — + **реальные системы** (это его ИБ/системный вектор, цепляет сильнее всего):
   - **Красно-чёрные деревья** — ядро Linux: `epoll` хранит отслеживаемые fd в rbtree; CFS-планировщик; VMA. Прямая связь с его блоком B.
   - **Хеш-таблицы** — таблицы процессов/инодов в ядре, символьные таблицы компиляторов, кеши, dedup.
   - **Trie / бор** — IP-роутинг (longest prefix match); **Aho-Corasick** (trie+автомат) — сигнатурный матчинг в IDS (Snort/Suricata) и антивирусах.
   - **B-/B+-деревья** — индексы PostgreSQL/SQLite, ФС (ext4 htree, NTFS, Btrfs).
   - **Куча (heap)** — таймеры ядра, приоритетные очереди, Дейкстра.
   - **Связные списки** — intrusive-списки ядра (`list_head`).
   - **Стек** — call stack, вычисление выражений, DFS; **stack-based overflow** (связь с его CTF/безопасностью).
   - **Union / type punning** — регистры процессора, парсинг бинарных форматов, сетевые заголовки.
6. **Операции** — от банальных (инициализация, индексация, присваивание, сравнение) до специфичных (для деревьев — **повороты, обновление высот, баланс-фактор**; для хеша — рехеширование; для динамических — выделение/освобождение). Для каждой — что делает и как.
7. **Сложность** — **таблица Big-O** по операциям (доступ/поиск/вставка/удаление), средний/худший случай. Где препод считает **вероятностный средний случай или амортизацию** — показать вывод, не только итог. Это корона его экзамена.

**Обязательно подключать сквозные темы** (см. `00-index.md` → «Сквозные темы»), если
структура их касается:
- **Мощность (#)** и **размер (sizeof)** — формулы (массив/запись/union), padding/выравнивание.
- **Представление в памяти** — машинное слово, упакованные/неупакованные, row/column-major.
- **Проблемы памяти** — для динамических структур: **фрагментация (внутр./внешн.),
  висячие указатели (dangling pointer), use-after-free**, утечки. Препод их спрашивает прицельно.

**Обогащение для устного** (поверх 7 пунктов):
- **Параллели Python/Rust** — как структура называется/выглядит: Python (`list`/`dict`/`set`/`collections.deque`/`heapq`), Rust (`Vec`/`HashMap`/`BTreeMap`/`VecDeque`/`BinaryHeap`). Что из коробки, что руками.
- **Аналоги и trade-offs** — массив vs список; BST vs хеш (порядок vs O(1)); chaining vs open addressing. Экзамен любит «почему X, а не Y».

**Длина ответа на уточнение (обратная связь 2026-06-15).** Развёрнутый разбор по 7 пунктам — для
**первого** прохода новой структуры. Когда пользователь внутри темы задаёт **уточняющий вопрос
или вопрос по предыдущему ответу** (особенно по ходу написания кода / прожарки) — отвечать
**коротко, 1–2 абзаца, строго по сути**. Не вываливать смежные ветки, расширения, полные
рефакторинги. Он путается, не разобравшись в предыдущем. Сомневаешься — короче. См. CLAUDE.md →
«Длина ответа на уточняющий вопрос».

**Со структуры «массив» и далее — формат «код + прожарка»** (просьба пользователя 2026-06-10).
Темы 0–4 очереди (классификация → сложность) — концептуальные, без кода. Начиная с массива:
1. Сначала теория по 7 пунктам (как выше).
2. Дать **небольшую практическую задачу**, которая естественно решается этой структурой
   → код в `ds/<name>.c` (указать `#include`, как в `give-task`). Задача — «легко решается
   именно этой структурой», builder её пишет сам.

   **УРОВЕНЬ СКЕЛЕТА (жёсткое правило — обратная связь 2026-06-14, [[feedback-exam-scaffold-minimal]]).**
   Дефолт, выбранный пользователем: `#include` + `struct` + boilerplate (`node_new`/malloc/free
   обвязка) + **`main` с тестами** (это мишень) + **сигнатуры функций с ОДНОЙ строкой-контрактом**
   «что делает». **Тела пишет пользователь — ВСЕ, включая повороты/перецепки указателей.**
   Категорически НЕ делать: расписывать алгоритм по шагам в комментариях; писать «образец —
   половину функции, вторую зеркаль сам»; давать готовые rotate/insert/splay/delete. Это
   убивает весь смысл (он builder, рекурсию/деревья закрываем именно письмом руками). Механику,
   диаграммы, «почему так» — объяснять в чате словами/ASCII, **не кодом**. Готовый код
   показывать **только** если застрял и сам попросил, или на прожарке после его попытки. Даже
   совсем новую идиому — объяснить словами/картинкой, дать написать самому.
3. Когда пользователь написал код — **прожарить (drill)**, по одному вопросу за раз:
   - пройтись по его коду (что делает строка, почему так, что сломается если убрать/поменять);
   - теория по структуре (из 7 пунктов);
   - **гипотетические сценарии** («а если вход пустой / с дубликатами / переполнение / N огромное?»);
   - **сложность по случаям: лучший / худший / средний** (для среднего — вероятностный вывод, если уместно).
   Это мини мок-собес по только что написанному коду: теория + практика + активное припоминание.
   Код — сначала, прожарка — потом, не вперемешку.

**Задания «найди ошибку в голом коде»** (просьба пользователя, пробник №1 2026-06-12).
Регулярно давать фрагменты чужого кода с багами на поиск — пробник вскрыл, что писать свой
код с краевыми случаями пользователь умеет, а **находить** те же баги в готовом коде — слабее
(чтение ≠ письмо). Особенно: краевые случаи с двумя указателями (dequeue без проверки пустой /
dangling tail), выравнивание, путаница total vs amortized. Это и тренаж к тесту («какие ошибки
в данном фрагменте?» — вопросы 39/41 реального теста).

После разбора — **создать/обновить конспект** `topics/ds/NN-<name>.md` через `vault-write`
(структура topics/, блок `DS — Структуры данных (экзамен)`), и **обновить статус** темы в
`00-index.md` (⬜ → 🟡, проставить ссылки на конспект и код). Открыть конспект: `code <abs_path>`.

**Чекпойнт перед следующей темой (обязательно — см. CLAUDE.md → «Чекпойнт перед переходом»).**
Закрыв тему (разбор + прожарка + конспект), **не начинать следующий пункт очереди молча**.
Остановиться и спросить: «есть вопросы по этой теме? идём дальше?» Можно *предложить/
порекомендовать* следующее, но стартовать его только после подтверждения пользователя
(«да»/«дальше»/«жги» = подтверждение, отдельно не переспрашивать). Темп задаёт пользователь.

### Режим C — `/exam тест` / `/exam mock` / «пробный экзамен»: тест

Эмуляция реального теста по правилам препода. **Перед стартом** — перечитать конспекты
тем, попадающих в выборку (дисклеймер выше).

Правила, которые воспроизводим точно:
- **~60 минут**, обратный отсчёт. Зафиксировать время старта в сообщении (`старт: HH:MM, дедлайн: HH:MM`). Следить за wall clock, предупредить на середине и за ~10 мин. По истечении — «время вышло, тест закрыт», ответы засчитываются как есть.
- **Можно короткий вариант** по запросу (~30 мин / 12–15 вопросов) — спросить в начале: полный (~25 вопросов) или короткий.
- **Вопросы разной стоимости** — у каждого подписать `[N балл(а/ов)]` (1 — факт/термин, 2 — применение/сложность, 3 — разбор/«почему»).
- **Последовательно, без возврата** — задавать **строго по одному**, не показывать следующий до ответа, **не давать переигрывать** ответ (как в реальном тесте). Это дисциплинирует.
- **Случайная выборка** — мешать темы и порядок, не идти подряд по модулям. Покрывать разные модули из пройденного (а на генеральной — всё).
- **Микс форматов под реальный тест:**
  - **варианты ответа** → через `AskUserQuestion` (перемешивать позицию правильного, не подсвечивать его).
  - **поле для ввода** → открытый вопрос прямо в чате (вписать термин, сложность, результат обхода дерева, что выведет код). Это ближе к «полю для ввода ответа» и честнее проверяет.
- **Под этого препода** — щедро включать его любимое (см. `00-index.md` → «Сквозные темы»): посчитать **мощность/размер** структуры (`sizeof(union)`, `#array`, размер `struct` с padding), **вывести сложность** (в т.ч. амортизацию/вероятностный средний случай), доступ к `A[i][j]` при row/column-major, «что не так с этим кодом» (dangling pointer / use-after-free / сравнение массивов через `==`), упакованные vs неупакованные. Это даёт больше баллов, чем чистые определения.
- **Без разбора по ходу** (в отличие от мок-собеса) — это экзамен, не урок. Разбор — в конце, чтобы не сбивать таймер и режим «без возврата».

В конце:
1. **Подсчёт баллов** — набрано / максимум, процент, грубая оценка (по 5-балльной шкале как ориентир).
2. **Разбор каждого вопроса** — правильно / неправильно / что упустил, коротко почему.
3. **Два списка** — уверенно / провалено.
4. **Зафиксировать**: строка в «Журнал пробных экзаменов» (`00-index.md`), проставить ⚠️ слабым темам и дописать конкретику в «Слабые места».

### Режим D — `/exam билет` / «устный»: классический экзамен

Эмуляция «тянешь билет → готовишься → отвечаешь».
1. Сгенерировать **билет** — 2–3 вопроса разной глубины из пройденного (например: 1 теоретический термин + 1 структура с разбором + 1 на сложность/сравнение). Показать билет целиком.
2. Дать **время на подготовку** (5–10 мин по запросу) — пользователь пишет развёрнутый ответ (можно тезисами).
3. Слушать ответ как преподаватель: что верно, где плывёт, добивающие вопросы («а почему именно так?», «а что если...»).
4. **«Блеснуть»** — после ответа подсказать 1–2 эффектных факта/связи по теме билета (где в реальных системах, неожиданная аналогия), которые поднимают ответ выше среднего.
5. Зафиксировать слабые места в `00-index.md`, как в режиме C.

## Чего не делать

- Не вести DS-статус в основном `00-roadmap.md` и не давать DS-задачи через `give-task` — это отдельный временный блок со своим хабом.
- В режиме C/D **не разбирать по ходу** и не давать переигрывать ответ — это ломает эмуляцию «без возврата».
- Не выдавать сухой пересказ в режиме B — обязательны все пять слоёв, особенно «где применяется» и Big-O.
- Не задавать все вопросы пробника сразу — строго по одному.
- Не засчитывать расплывчатый ответ как верный.
- Не игнорировать слабые места — они приоритетнее непройденного по плану.
