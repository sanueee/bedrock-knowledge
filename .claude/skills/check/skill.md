# Скилл: check

`/check` — быстрое **приоритизированное** ревью одного файла. Цель не «список замечаний», а чтобы человек **усвоил урок кода**. Держать компактно, не раздувать.

---

## ГЛАВНОЕ (нарушение = провал скилла)

- **НЕ ДАВАТЬ полных блоков исправленного кода** — ни «правильной версии», ни «каркаса как надо». Максимум **1–3 строки** на пункт для иллюстрации. Структурную правку — **словами**. Человек пишет сам.
- **ПРИОРИТИЗИРОВАТЬ**: критичные баги → edge cases → косметика. Косметику опускать, если файл функционально сырой.
- **ПУНКТЫ КОРОТКИЕ**: суть + `file:line`. Указать на ошибку, **не разжёвывать** — без лекций на три абзаца.
- **КЛАССИФИЦИРОВАТЬ ПРИРОДУ каждой ошибки** перед тем как писать пункт — от неё зависит объём (см. «Природа ошибки»). Опечатка ≠ незнание, и подача должна отличаться радикально.
- **КАЖДЫЙ ПУНКТ ЗАКАНЧИВАЕТСЯ НАПРАВЛЕНИЕМ ФИКСА** — куда смотреть / что поменять, одной фразой. Не «разберись сам», не ждать, пока пользователь допросит. Готовый код по-прежнему не даём, но направление обязано быть.
- **НЕ вызывать `vault-write`** автоматически — это отдельная команда `/vault-write`.

---

## ШАГИ

1. **ОПРЕДЕЛИТЬ файл** — путь из команды; нет пути → спросить какой смотреть.
2. **ПРОЧИТАТЬ файл целиком** до любых комментариев.
3. **ВЫДАТЬ ответ** по разделу «Структура вывода».
4. **СПРОСИТЬ на понимание** — только если среди найденного есть **логическая/архитектурная** ошибка (см. «Природа ошибки»). Вопрос по ней, ждать ответа. Файл, где одни опечатки и механические промахи, вопросом не завершать — просто список с фиксами.

---

## Структура вывода

Три секции по убыванию важности, **нумерация несквозная** (внутри каждой своя). Пустую секцию пропускать — не выдумывать пункты ради заполнения.

1. **Критичные баги** — корректность/безопасность: падение, UB, утечка ресурса, неверный результат, потеря данных, дыра.
2. **Менее значимые** — edge cases, редкие входы, устойчивость: непроверенный возврат сисколла, граничное значение, рассинхрон на нетипичном пути.
3. **Косметика** — стиль, именование, микро-упрощения.

**Расхождения с [`CODESTYLE.md`](../../CODESTYLE.md) — отдельная четвёртая секция, не в «косметике».** Прочитать CODESTYLE **до** ревью. Причина разделения (обратная связь 2026-08-09): стиль — это то, что пользователь сознательно приводит к единому виду ради снижения нагрузки на проектирование, и такие пункты он хочет видеть списком «привести к конвенции», а не вперемешку с багами. Формат — короткая строка «что не по стилю → какой пункт CODESTYLE», без объяснений. Расхождений нет — секцию пропустить молча.

Без секции «Что хорошо» и без «Итога» с водой. Всё чисто → коротко «критичных нет» и к тестированию.

**Формат вопроса в конце** (шаг 4): открытый вопрос в чате — для «почему так / что сломается если убрать»; **AskUserQuestion** — для факта/сигнатуры/«что вернёт X» (перемешивать порядок ответов, не раскрывать заранее).

## Итеративные сессии (один файл несколько раз подряд)

- **ПОВТОР бага подсвечивать явно — ТОЛЬКО для критичных.** Замечен в прошлой итерации и не исправлен → "**Баг X НЕ исправлен** (N-я итерация). Перечитай эту строку посимвольно". Глаз пропускает «тот же текст» — нужен сигнал, что это **рецидив**, а не новое замечание.
- **«Менее значимые» и «косметика» рецидивом НЕ помечать** (обратная связь 2026-08-01). Пользователь сознательно забивает на часть мелких пунктов — это его право, а не пропущенная ошибка. Механика: назвал минорный пункт один раз → в следующих итерациях он либо не упоминается вовсе, либо идёт обычной строкой без «рецидив»/«N-я итерация». Давить повторами на мелочи = шум, из-за которого теряются критичные пункты.
- **Счётчик остатка считает только незакрытые критичные** + минорные, названные впервые. Осознанно пропущенные не накапливать.
- **СЧЁТЧИК остатка** в конце: сколько невыполненных пунктов. Дошло до 0 → явно «файл готов, время тестировать» + конкретные тесты (запуск, end-to-end сценарий).
- **НЕ дублировать объяснения** между итерациями: концепцию объяснил раз → дальше «см. прошлое объяснение», без повтора. Иначе ревью раздувается.
- **ПЕРЕЧИТАТЬ строку в ТЕКУЩЕЙ версии перед заявлением о рецидиве или ссылкой на `file:line`.** Не полагаться на память прошлой итерации и не называть номер строки/«рецидив», если этот участок не перечитан в текущем файле. При чтении через `offset` — не утверждать ничего про части файла, которые в этой итерации не видел. (Провал 2026-07-18: подсветил `count_port` как рецидив по памяти — а его уже удалили; читал фрагментами и не перепроверил. Выдумывать строку и гадать «почему компилятор не ругнулся» — нарушение §1 честности.)

**Прогон Linux-only кода (epoll / `sys/epoll.h` и т.п.) на macOS — через Docker:**
- демон лежит → `open -a Docker`, дождаться `docker info`;
- вход в gcc-контейнер: `docker run --rm -it -v "$PWD":/work -w /work gcc:latest bash`;
- внутри — `gcc file.c -o a.out` + прогон; слушатель для тестов (`nc -l PORT` / `python3 -m http.server PORT`) поднимать в том же контейнере.

## Природа ошибки — определить ДО того, как писать пункт (обратная связь 2026-08-01)

Провал сессии B-19: баг `while (sent = sendto(...) && errno == EINTR)` — банальная невнимательность со скобками — разбирался объёмной трассировкой на 5 шагов, четыре итерации подряд задавались наводящие вопросы вместо прямого «здесь `&&` связывает сильнее `=`». Пользователь: «если бы сказал сразу, сомнений бы не осталось». Объём ответа должен определяться **природой** ошибки, а не её критичностью.

Перед каждым пунктом ответить себе: **почему** этот код такой?

| Природа | Признаки | Как подавать | Объём |
|---------|----------|--------------|-------|
| **Опечатка / невнимательность** | имя переменной, `&` vs `&&`, порядок строк, забытая `;`, скобки, приоритет операторов, копипаст-рассинхрон | **Сказать прямо, что не так и как правильно.** Никаких наводящих вопросов и трассировок — пользователь это знает, просто не увидел | 1–2 строки |
| **Механический промах рефакторинга** | сигнатура↔вызов, индекс `[i]` vs `[j]`, инкремент потерялся при переносе ветки, дубль объявления | Прямо + указать **класс** («правка сигнатуры = правка всех вызовов»), т.к. класс подтверждён с B-13/B-15 | 2–3 строки |
| **Незнание факта/контракта** | не знает что возвращает syscall, поведение флага, формат протокола, что `SO_RCVTIMEO` перезапускается | Объяснить факт, дать опору (man/RFC/`topics/`) — здесь развёрнутость уместна | абзац |
| **Логическая / архитектурная** | неверная модель («чужой пакет = тайм-аут»), не та структура цикла, не тот контракт функции | Полный разбор в три слоя + вопрос на понимание — **только здесь** уместен сократический режим | развёрнуто |

**Правила поверх таблицы:**
- **Рецидив опечатки — сразу прямое указание, без вопросов.** Если пункт назван 2+ раза и не исправлен — гипотеза «не понимает» ложна, значит **не видит**. Показать символ/скобку, назвать правильный вариант словами.
- **Наводящий вопрос вместо ответа — только для логических ошибок.** На опечатке он воспринимается как допрос и жжёт время.
- **Не смешивать в одном пункте**: сначала «что не так» (одна фраза), потом «куда смотреть/что менять» (одна фраза), и только для логических — «почему».

## Как разбирать и объяснять баг

Применять к **логическим/архитектурным** ошибкам (см. таблицу выше); для опечаток — не применять, там три слоя избыточны.

Каждый баг разбирать **в три слоя**:
- **Что** — одно предложение, без терминов.
- **Как** — пошагово, с конкретными строками (`file:line`), номера называть.
- **Почему** — зачем именно так, какие альтернативы и чем они хуже/лучше.

**Аналогии** — только из того, что пользователь уже знает (C: указатели, fd; Linux: команды `ls`, `cat /proc/...`). Незнакомую тему — сначала бытовой пример, потом технический.

**ОБЯЗАТЕЛЬНО: перед разбором ПРОЧИТАТЬ [`explain-code/skill.md`](../explain-code/skill.md) и применить его приёмы.** Это не «по желанию» — приёмы подачи и проверки понимания живут только там, `check` их не дублирует. Каждый разбор бага и каждый вопрос строятся по этим приёмам: actors-with-letters (именовать участников буквами), numbered steps (последовательность — списком, не прозой), таблицы для классификации, «один вопрос — один ответ», follow-up ≤2 абзаца, английские термины EN+RU при первом упоминании, формат уточняющих вопросов. Пропустить чтение explain-code = нарушение скилла.

## Принцип преподавания

Цель `/check` — не выкатить замечания и уйти, а убедиться что человек **глубоко усвоил** урок этого кода.

- **Пошагово, не вываливать всё сразу.** Следующее замечание — только после того как текущее освоено. Проверять и верх (зачем паттерн/проверка нужны), и низ (бизнес-логика, edge cases).
- **Внутренний чек-лист** — человек должен понимать: (1) **проблему** — почему возникла, какие ветви/варианты; (2) **решение** — почему именно так, какие design decisions и edge cases; (3) **контекст** — почему важно, на что повлияют изменения.
- Добиваться **«почему»** (и детализировать его), не только «что» и «как». Хорошо понятая проблема — основа.
- **Сессия не закончена**, пока человек не продемонстрировал понимание всех пунктов чек-листа — а не пока ты просто перечислил замечания.

## Исключение: C++-хедеры в C-файлах — ИГНОРИРОВАТЬ

`#include <cerrno>`/`<cstdio>`/`<cstdlib>`/`<cstring>`/`<csignal>` и прочие `c*`-хедеры без `.h` в `.c`-файле — это **автоподстановка VS Code** при Tab-переключении, не ошибка пользователя. Он убирает их сам перед сборкой. Не выносить в замечания, не считать за баг, не подсвечивать как рецидив — даже если из-за них не компилируется. Игнорировать этот класс полностью.
