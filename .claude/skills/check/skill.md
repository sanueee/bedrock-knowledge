# Скилл: check

`/check` — быстрое **приоритизированное** ревью одного файла. Цель не «список замечаний», а чтобы человек **усвоил урок кода**. Держать компактно, не раздувать.

---

## ГЛАВНОЕ (нарушение = провал скилла)

- **НЕ ДАВАТЬ полных блоков исправленного кода** — ни «правильной версии», ни «каркаса как надо». Максимум **1–3 строки** на пункт для иллюстрации. Структурную правку — **словами**. Человек пишет сам.
- **ПРИОРИТИЗИРОВАТЬ**: критичные баги → edge cases → косметика. Косметику опускать, если файл функционально сырой.
- **ПУНКТЫ КОРОТКИЕ**: суть + `file:line`. Указать на ошибку, **не разжёвывать** — без лекций на три абзаца.
- **НЕ ОБЪЯСНЯТЬ сразу** — после списка спросить «почему это баг / где выстрел в ногу» и ждать ответа.
- **НЕ вызывать `vault-write`** автоматически — это отдельная команда `/vault-write`.

---

## ШАГИ

1. **ОПРЕДЕЛИТЬ файл** — путь из команды; нет пути → спросить какой смотреть.
2. **ПРОЧИТАТЬ файл целиком** до любых комментариев.
3. **ВЫДАТЬ ответ** по разделу «Структура вывода».
4. **СПРОСИТЬ на понимание** — 1–2 ключевых бага, вопрос «почему / сценарий выстрела в ногу», ждать ответа.

---

## Структура вывода

Три секции по убыванию важности, **нумерация несквозная** (внутри каждой своя). Пустую секцию пропускать — не выдумывать пункты ради заполнения.

1. **Критичные баги** — корректность/безопасность: падение, UB, утечка ресурса, неверный результат, потеря данных, дыра.
2. **Менее значимые** — edge cases, редкие входы, устойчивость: непроверенный возврат сисколла, граничное значение, рассинхрон на нетипичном пути.
3. **Косметика** — стиль, именование, микро-упрощения.

Без секции «Что хорошо» и без «Итога» с водой. Всё чисто → коротко «критичных нет» и к тестированию.

**Формат вопроса в конце** (шаг 4): открытый вопрос в чате — для «почему так / что сломается если убрать»; **AskUserQuestion** — для факта/сигнатуры/«что вернёт X» (перемешивать порядок ответов, не раскрывать заранее).

---

## Итеративные сессии (один файл несколько раз подряд)

- **ПОВТОР бага подсвечивать явно.** Замечен в прошлой итерации и не исправлен → "**Баг X НЕ исправлен** (N-я итерация). Перечитай эту строку посимвольно". Глаз пропускает «тот же текст» — нужен сигнал, что это **рецидив**, а не новое замечание.
- **СЧЁТЧИК остатка** в конце: сколько невыполненных пунктов. Дошло до 0 → явно «файл готов, время тестировать» + конкретные тесты (запуск, end-to-end сценарий).
- **НЕ дублировать объяснения** между итерациями: концепцию объяснил раз → дальше «см. прошлое объяснение», без повтора. Иначе ревью раздувается.

**Прогон Linux-only кода (epoll / `sys/epoll.h` и т.п.) на macOS — через Docker:**
- демон лежит → `open -a Docker`, дождаться `docker info`;
- вход в gcc-контейнер: `docker run --rm -it -v "$PWD":/work -w /work gcc:latest bash`;
- внутри — `gcc file.c -o a.out` + прогон; слушатель для тестов (`nc -l PORT` / `python3 -m http.server PORT`) поднимать в том же контейнере.

## Как разбирать и объяснять баг

Каждый баг разбирать **в три слоя**:
- **Что** — одно предложение, без терминов.
- **Как** — пошагово, с конкретными строками (`file:line`), номера называть.
- **Почему** — зачем именно так, какие альтернативы и чем они хуже/лучше.

**Аналогии** — только из того, что пользователь уже знает (C: указатели, fd; Linux: команды `ls`, `cat /proc/...`). Незнакомую тему — сначала бытовой пример, потом технический.

**ОБЯЗАТЕЛЬНО: перед разбором ПРОЧИТАТЬ [`explain-code/skill.md`](../explain-code/skill.md) и применить его приёмы.** Это не «по желанию» — приёмы подачи и проверки понимания живут только там, `check` их не дублирует. Каждый разбор бага и каждый вопрос строятся по этим приёмам: actors-with-letters (именовать участников буквами), numbered steps (последовательность — списком, не прозой), таблицы для классификации, «один вопрос — один ответ», follow-up ≤2 абзаца, английские термины EN+RU при первом упоминании, формат уточняющих вопросов. Пропустить чтение explain-code = нарушение скилла.

## Принцип преподавания

Цель `/check` — не выкатить замечания и уйти, а убедиться что человек **глубоко усвоил** урок этого кода.

- **Пошагово, не вываливать всё сразу.** Следующее замечание — только после того как текущее освоено. Проверять и верх (зачем паттерн/проверка нужны), и низ (бизнес-логика, edge cases).
- **Внутренний чек-лист** — человек должен понимать: (1) **проблему** — почему возникла, какие ветви/варианты; (2) **решение** — почему именно так, какие design decisions и edge cases; (3) **контекст** — почему важно, на что повлияют изменения.
- Добиваться **«почему»** (и детализировать его), не только «что» и «как». Хорошо понятая проблема — основа.
- **Сессия не закончена**, пока человек не продемонстрировал понимание всех пунктов чек-листа — а не пока ты просто перечислил замечания.

## Исключение: C++-хедеры в C-файлах — ИГНОРИРОВАТЬ

`#include <cerrno>`/`<cstdio>`/`<cstdlib>`/`<cstring>`/`<csignal>` и прочие `c*`-хедеры без `.h` в `.c`-файле — это **автоподстановка VS Code** при Tab-переключении, не ошибка пользователя. Он убирает их сам перед сборкой. Не выносить в замечания, не считать за баг, не подсвечивать как рецидив — даже если из-за них не компилируется. Игнорировать этот класс полностью.
