# Скилл: debug

Триггеры: "не компилируется", "segfault", "ошибка", "не работает",
пользователь вставляет вывод gcc / make / valgrind / gdb.

---

## Алгоритм

### 1. Собери контекст

Если пользователь не вставил текст ошибки — попроси:
"Вставь вывод gcc / вывод программы."

Если код не виден — прочитай файл сам (спроси путь если неизвестен).
Не гадай по описанию — нужен реальный текст ошибки.

### 2. Классифицируй ошибку

| Тип | Признак |
|-----|---------|
| Ошибка компиляции | gcc/clang вывел `error:` |
| Предупреждение | gcc вывел `warning:` — не игнорировать, разбирать как ошибку |
| Segfault | `Segmentation fault`, `SIGSEGV` |
| Логическая ошибка | программа работает, вывод неправильный |
| Утечка памяти | `valgrind: definitely lost` / `still reachable` |

### 3. Дай hint — не решение

- Укажи файл и строку где проблема.
- Объясни что именно не так и почему это ошибка.
- Задай направляющий вопрос: "Что возвращает readdir когда каталог кончился?"
- Подожди — пусть пользователь попробует сам.

### 4. Если hint не помог

- Покажи минимальный пример где ошибка воспроизводится.
- Объясни инструмент: как читать вывод valgrind, как запустить gdb,
  как поставить breakpoint и напечатать переменную.
- Только если пользователь совсем застрял → показывай исправление
  с объяснением почему именно так.

### 5. Зафиксируй

Если ошибка типичная (off-by-one, не проверил NULL, забыл free,
не инициализировал переменную) — предложи добавить в vault:
"Добавить в vault как типичную ошибку?" → используй скилл `vault-write`.

---

## Чего не делать

- Не давать исправленный код сразу — сначала hint.
- Не игнорировать `warning:` — объяснять как ошибку.
- Не называть инструменты (gdb, valgrind) без объяснения что они делают.
- Не чинить несколько проблем за раз — одна ошибка → один hint.
- Не переписывать функцию целиком чтобы "починить" — только точечное указание.
