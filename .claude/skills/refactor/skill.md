# Скилл: refactor

Управляемый рефакторинг инструкций и базы знаний проекта (файлы `.claude/` и `knowledge-base/`). Цель — менять структуру так, чтобы контекст оставался **связным, без висячих ссылок, без дублирования, без раздувания часточитаемых файлов**.

Не путать с рефакторингом кода (`sections/ds/`, `sections/linux/`, ...) — этот скилл про **документы-инструкции и vault**, не про C/Rust-код.

---

## Триггеры

- `/refactor` — прямой вызов пользователем. Ссылок на этот скилл из CLAUDE.md нет (вызывается вручную).

---

## Карта ролей файлов (источник истины для маршрутизации и анти-дублирования)

Иерархия. У каждого файла **одна роль**; роли не пересекаются. Новую инструкцию класть в файл, чья роль ей соответствует, — и только туда.

**Содержание vs процесс.** Файлы хранят **содержание** (знание, план, статус, журнал). **Как** файл редактируется/расширяется (процесс, шаги, «как выглядит дизайн нового блока») в самом файле не живёт — это поведение, его место в скилле (`session-debrief`, `plan-block`, `give-task`, этот `refactor`). Нашёл в файле инструкцию «как себя править» — перенеси в скилл-владелец, в файле оставь содержание.

| Файл | Роль | Что НЕ хранит |
|------|------|---------------|
| `.claude/CLAUDE.md` | **Главный.** Жёсткие правила поведения + общий контекст (кто пользователь, стек кратко, реестр скиллов, карта «что где лежит»). | Детальный прогресс, план блоков, журналы. |
| `knowledge-base/strategy/learning-strategy.md` | **План будущего.** Карты блоков (проза будущих + задания активных), учебные принципы. | Текущий статус, выполненное, методологию структуры/проектирования блока (→ скилл `plan-block`). |
| `knowledge-base/roadmap/00-roadmap.md` | **Диспетчер настоящего.** Позиция, следующий шаг, слабые места, ритм, reinforce + маршрут к archive/journal. Читается каждую сессию → лёгкий. | Детальные дампы тем, журналы, историю. |
| `knowledge-base/roadmap/archive.md` | Пройденные темы по блокам + индекс тем (редко, для оценки знаний). | — |
| `knowledge-base/roadmap/journal.md` | Журнал выполненного: задания+код, reading/theory/mock/ctf. | — |

Часточитаемые (грузятся в контекст почти каждую сессию): **CLAUDE.md** и **00-roadmap.md**. Их объём держать минимальным.

## Алгоритм

### 1. Выясни идею

Задай **один** вопрос: что хочется изменить / добавить / что нового. Не предполагай — получи замысел словами. Жди ответа (гейтинг §2 CLAUDE.md).

### 2. Уточни структуру

Задавай уточняющие вопросы (по одному), пока не будет **однозначной** целевой структуры: какие файлы затронуты, что куда переезжает, как называется новое, какова его роль. Расплывчатость на этом шаге = висячие ссылки и дубли на выходе. Жди подтверждения структуры перед правками.

### 3. Выполни по жёстким правилам

Это инварианты. Нарушение = ошибка, а не выбор.

**A. Никаких висячих ссылок.**
- Любой перенос/переименование/удаление файла или раздела → обновить **все** ссылки на новое расположение.
- После правок — `grep` по старому пути/имени/якорю раздела по всему репо. **0 совпадений** (кроме намеренных упоминаний по имени, где контекст уже задаёт папку). Привести вывод проверки.

**B. Иерархия и маршрутизация нового модуля.**
- Появился новый модуль/файл/скилл → прописать его в **родителе, чья роль ему соответствует** (см. карту ролей): новый скилл-поведение → реестр в `CLAUDE.md`; новый файл знаний/прогресса → `00-roadmap.md`; новый элемент плана/методологии → `learning-strategy.md`.
- В родителе указать: **путь до модуля + одна строка «зачем нужен и когда на него ссылаться»**. Без этой строки модуль невидим для LLM.
- Один модуль → один файл-владелец. Не прописывать один и тот же модуль в двух родителях.

**C. Структурированность и объём.**
- Формулировки — конкретные, проверяемые. Никаких «по необходимости», «и т.д.» там, где нужно правило.
- В часточитаемые файлы (CLAUDE.md, 00-roadmap.md) кладётся только то, что нужно **часто**. Редкочитаемое (история, детальные дампы, справка) → в дочерний файл по ссылке.
- **Сигнал к выносу:** в часточитаемый файл просится контент, который реально нужен редко, ИЛИ файл теряет сканируемость (надо скроллить ради одной мысли). Тогда **остановись, предложи новую структуру, дождись подтверждения** — не раздувай молча.

**D. Никакого дублирования.**
- Одно правило живёт в одном месте. Если оно нужно в другом файле — **ссылка** на источник, не копия.
- Особо опасно дублирование **в разных формулировках** — копии расходятся при правке. Если нашёл два изложения одного правила → свести к одному, во втором месте оставить ссылку.
- Сверяйся с картой ролей: если инструкция тянет в файл, чья роль другая, — ей там не место.

### 4. Проверь и отчитайся

- Прогон проверки B (grep старого → 0) с выводом.
- Подтвердить: каждый новый файл имеет ровно одного родителя-владельца; роли не пересеклись; часточитаемые файлы не раздулись.
- Кратко перечислить: что переехало, какие ссылки обновлены, где остались намеренные упоминания по имени.

---

## Чего не делать

- Не начинать правки до согласованной на шаге 2 структуры.
- Не переносить контент «на глаз» — wikilinks `[[...]]` резолвятся по имени (папка не важна), а markdown-ссылки с относительными путями ломаются при смене глубины — пересчитывать `../`.
- Не оставлять «починю позже» — висячая ссылка сейчас = тихо сломанный контекст потом.
