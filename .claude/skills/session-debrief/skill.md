# Скилл: session-debrief

Триггеры:
- пользователь пишет "на этом все" / "на этом всё" / "заканчиваем"
- пользователь пишет "прочитай CLAUDE.md" В КОНЦЕ сессии (после выполнения задания)
- пользователь правильно ответил на 2–3 уточняющих вопроса из `explain-code` подряд
  и не путался в ответах → предложить: "Кажется разобрались. Закончим сессию?"
  Дождаться подтверждения перед запуском дебрифа.

Это сигнал: сессия завершена, нужно зафиксировать результаты и обновить файлы.

---

## Алгоритм

### 1. Задай один вопрос

Спроси что было сложным или непонятным в этой сессии.
Один вопрос, кратко. Не список. Подожди ответа.

Пример: "Что вызвало затруднение — сам системный вызов или логика обработки ошибок?"

### 2. Зафиксируй в vault

Используй скилл `vault-write`.
Передай ответ из Шага 1 — повторно не спрашивай.

**Сессия по вузу** (CLAUDE.md → «Режим «вуз»») — обновить только папку предмета `knowledge-base/university/<N>-semester/<предмет>/` (`theory/` — конспекты, `practice/` — лабы/задачи). Шаги 3–4 (roadmap, стратегия) **пропустить**: они только про личную стратегию. Дальше — сразу Шаг 5–6.

**Мок-собес** — в файлы ничего не пишется (см. `mock-interview`). Если сессия была только мок-собесом — vault и roadmap не трогать.

Что обновить (личная стратегия):
- `self-practice/<domain>/<name>/task-<блок>NN-<name>.md` — моё решение, ошибки, рефлексия (файл уже создан скиллом `give-task` в папке задачи рядом с кодом)
- `knowledge-base/self-study/topics/` — каждая концепция которая всплыла в сессии

### 3. Обнови roadmap (диспетчер + journal + archive)

Roadmap разбит на 3 файла в `knowledge-base/self-study/roadmap/` — обновлять по статусу нужный:
- **`00-roadmap.md` (диспетчер)** — позиция, следующий шаг, слабые места, ритм, reinforce. Читается каждую сессию → держать лёгким.
- **`journal.md`** — журналы: «Задачи — writing», «Reading-сессии», «Theory-сессии», «CTF». («Мок-собесы» — исторический раздел, новые строки не добавлять.)
- **`archive.md`** — детальные «Выполненные темы блока X» + «Фундамент» + индекс тем («Темы — Linux/Rust/...»). Сюда же уезжает дамп блока при его закрытии.

Стратегия (план) и CLAUDE.md (контекст) трогаются редко (см. Шаг 4).

**Обновить дату в frontmatter `00-roadmap.md`** (`обновлено: YYYY-MM-DD`) — всегда.

**`00-roadmap.md` → "Текущая позиция"** — обновить все строки которые изменились:
1. "Блоки" / "Активный блок" — если сменился (весь B завершён → C/D). При закрытии блока — перенести его детальный дамп «Выполненные темы» из `archive.md` в архивную форму (блок закрыт), а в диспетчере оставить только статус ✅.
2. "Позиция" — обновить счётчик `N/26`. Если только что было задание — N+1. Отметить если следующее будет интеграционным (позиции 5/10/15/20/25) или магнум опусом (26).
3. "Следующий шаг" — следующий пункт главного трека с функциями/путями (из стратегии → раздел блока). Для интеграционного — указать какие 4 атомарных синтезируются.
4. "Слабые места" (блоки B/C) — обновить, если проработали/выявили.
5. "Параллельные блоки/треки доступны сейчас" — пересмотреть. Если параллельный блок стал доступен после завершения текущего task'а — добавить. Если завершён или больше не релевантен — убрать. `give-task` читает эту секцию для предложения выбора.
6. "Невыполненные закрепляющие задания" — добавлять только если пользователь сам попросил завести reinforce. Если пользователь только что закрыл reinforce — удалить.

**`archive.md` → "Выполненные темы блока X"** — дописать **что именно** усвоено (не "task-N выполнен", а концепции — например "EPIPE/ECONNRESET, partial read, sigaction(SIGPIPE, SIG_IGN)"). Если завершилась /theory-сессия — обновить "Фундамент" там же.

**Счётчики мок-собеса / reading / CTF — больше не ведём.** Эти треки управляются скиллами по запросу пользователя / решению Claude.

**`journal.md` → разделы журналов** — добавить строку:
- "Задачи — writing" — для обычных task'ов.
- "Reading-сессии" — для reading-NN.
- "Theory-сессии" — для /theory сессий.
- "CTF" — для CTF-тасков (по таску, не сессии).

**`archive.md` → разделы тем** — если в задаче всплыли новые темы, добавить `[[wikilink]]` в "Темы — Linux/Networking/C/Reading/...".

### 4. Обнови CLAUDE.md (редко) и стратегию (очень редко)

**CLAUDE.md** — обновлять только если поменялось что-то в "Кто я" (возраст, курс, тип) или в реестре скиллов. Снимок уровня по стеку живёт **не здесь**, а в `00-roadmap.md` → "Снимок уровня по стеку" — его правка идёт в Шаге 3 (при смене языка/уровня обновить ту строку).

**Стратегия (`learning-strategy.md`)** — это **план будущего**. Правила правки:
- **Завершено задание текущего блока → удалить его пункт из стратегии.** Выполненные задания в стратегии не живут — только оставшиеся. Детали усвоенного уезжают в `archive.md` (Шаг 3), пункт из соответствующего блока стратегии **удаляется**. Это основная регулярная правка стратегии после обычного task'а.
- Появилась новая тема которую стоит добавить в план **будущего** блока — добавить (новый пункт).
- Изменился приоритет или вектор — обсудить с пользователем перед правкой "Ближайший план".

Стратегия **не содержит**: меток статуса `[✅]`/`[ТЕКУЩИЙ]`/"Текущая позиция" (статус — только в roadmap); архива выполненных заданий (он в `roadmap/`); результатов мок-собесов (они нигде не фиксируются). Будущие блоки в стратегии описаны прозой — НЕ расписывать их по заданиям заранее, подробная карта проектируется при старте блока.

### 5. Обнови skills

На основе переписки и замечаний пользователя — обнови .claude/skills/*.md.
Конкретизируй, подстраивайся под стиль общения, записывай замечания.
При необходимости создавай новые скиллы.
Цель: идеальное понимание без толчков "посмотри в тот файл".

### 6. Закоммить и запушь (ОБЯЗАТЕЛЬНО)

После всех правок (Шаги 2–5) — **один коммит на сессию** и `git push` в `origin`.
Пользователь явно попросил это делать в дебрифе (2026-07-03). Коммитим и пушим
**прямо в `main`** — это личный учебный vault, линейная история на `main` намеренна;
дефолтное «сначала ветку» здесь **не** применяем (явное разрешение пользователя).

**Конвенция сообщений (постоянная, универсальная):**

```
<type>(<id>): <краткое описание на русском>

- <что сделано: буллеты по код+vault>
```

- `type` — один из: `task | reading | theory | mock | ctf | uni | vault | refactor | chore`.
  - `task` — обычное задание блока (writing); `reading` — reading-сессия;
    `theory` — /theory; `mock` — мок-собес (только если были правки файлов); `ctf` — CTF-writeup;
    `uni` — вузовский предмет (конспект, лаба, задача);
    `vault` — правки только в knowledge-base без кода; `refactor` — /refactor;
    `chore` — настройки/скиллы/прочее.
- `id` — позиция/идентификатор: `B-9`, `C-6`, `reading-02`, `ctf-<task>`; для `uni` — предмет: `os`, `ds`, `prog-langs`, `probability`.
  Нет id → без скобок: `chore: ...`.
- subject — на русском, ≤ ~72 символов, **без точки** в конце, именной/повелительный.
- body — буллеты что сделано (код + конспекты + roadmap), кратко.
- **БЕЗ trailer'а `Co-Authored-By`** — коммиты идут только от имени пользователя
  (явное указание 2026-07-03). Дефолт окружения «дописывать Co-Authored-By» здесь снят.

Пример (эта сессия):
```
task(B-9): UDP echo — recvfrom/sendto, границы датаграмм, потеря пакета

- self-practice/networking/udp-echo/udp_echo.c: server/client, SO_RCVTIMEO, grateful shutdown
- vault: topics/networking/udp-sockets.md + дозаполнен task-b09
- roadmap: позиция 9/26, след. шаг B-10, слабое место «подсчёт байт»
```

**ДО `git add` — удалить собранные бинарники** из папки задания (`sweep`, `a.out`, `*_san` и т.п.). Пользователь: «исполняемые файлы лучше удалять» (2026-08-09) — то есть **удалять**, а не заносить в `.gitignore`: они пересобираются одной командой, а правило в `.gitignore` под каждое имя только копит мусор. Проверка перед коммитом: `git status --short` не должен показывать ничего исполняемого, в папке задания остаются только `*.c`/`*.h`/`task-*.md`.

**Механика:** `git add -A` → `git commit -F <файл-сообщения или heredoc>` → `git push`.
Сообщение с многострочным телом передавать через `-F` (файл во scratchpad) или несколько
`-m`, не одной строкой. После push — сообщить пользователю хэш и что запушено.
Если push отклонён (non-fast-forward и т.п.) — **не** форсить, показать ошибку пользователю.

---

## Чего не делать

- Не пропускать Шаг 1 — ответ важен для честной фиксации трудностей.
- Не писать "всё прошло отлично" — если были трудности, фиксировать их.
- Не запускать дебриф если пользователь просто читает CLAUDE.md не в конце сессии.
