## Задание 9.1 — `opendir-errors.c`

**Что делает:**
1. Вызывает `opendir("/no/such/path")` — несуществующий путь.
2. Проверяет что вернулся `NULL`, печатает ошибку через `perror("opendir")` (или вручную через `errno` + `strerror()`).
3. Затем открывает `/tmp` (или любой существующий путь), итерирует через `readdir()` в цикле `while ((entry = readdir(dp)) != NULL)`, печатает имя каждого entry.
4. Закрывает через `closedir()`.

**Что должен увидеть:**
- При несуществующем пути: `opendir: No such file or directory` (errno = `ENOENT`).
- В рабочем цикле: список файлов в `/tmp`. Цикл завершается естественно — `readdir()` возвращает `NULL` когда entries закончились (а **не** при ошибке). Это и есть пойнт мок-собеса: `opendir()` возвращает `NULL` при ошибке, `readdir()` — при конце директории (или ошибке, но это редкий кейс — отличают через `errno = 0` перед вызовом).

**Функции:** `opendir()`, `readdir()`, `closedir()`, `perror()`, `errno`.

## Задание 9.2 — `zombie.c`

**Что делает:**
1. `fork()`. Дочерний процесс сразу `exit(0)` — ничего не делает.
2. Родитель печатает свой `getpid()` и `getppid()` дочернего (через `fork()` возвращает PID), затем `sleep(15)` **без** `waitpid()`.
3. После `sleep()` вызывает `waitpid(child, &status, 0)`, печатает что собрал статус.
4. Перед `waitpid()` процесс ещё спит — это окно для проверки.

**Как наблюдать:**
- В одном терминале — запустить `./zombie`, увидеть выведенный PID дочернего.
- Во втором терминале — `ps aux | grep Z` или `ps -ef --forest` — увидеть запись `<defunct>` или статус `Z` для дочернего PID.
- После `sleep` истечёт и родитель вызовет `waitpid()` — снова `ps`, запись исчезла.

**Что должен увидеть и зафиксировать в vault:**
- Зомби — это **запись в таблице процессов** которая держит PID, exit status, информацию о ресурсах. **Не** дескрипторы, не память (память освобождена при `exit()`). Утечка — это PID-slot, и при массовом форке без `wait` система упирается в лимит PIDов.

**Функции:** `fork()`, `exit()`, `sleep()`, `waitpid()`, `getpid()`.

## Задание 9.3 — `signal-vs-sigaction.c`

**Две программы или одна с флагом `--mode signal | --mode sigaction`** — на твой выбор. Удобнее как два файла: `sig-old.c` и `sig-new.c`.

**Версия `signal()`:**
1. `signal(SIGINT, handler)` где `handler` печатает `"got SIGINT, count=N"` и инкрементирует счётчик.
2. Цикл `while(1) pause();`.
3. Запустить, нажать `Ctrl+C` дважды.

**Что должен увидеть:** на System V семантике (то что даёт стандартный `signal()` на Linux в некоторых конфигурациях — но в glibc по умолчанию работает BSD-семантика с автоматической переустановкой). **Если** обработчик сбросился — второй `Ctrl+C` убивает процесс с дефолтным действием. Если нет — оба раза печатает.

**Важно:** на современном Linux (glibc) `signal()` обычно работает как BSD-вариант (не сбрасывает). Чтобы **гарантированно** увидеть сброс — использовать `sysv_signal()` или собрать с `-D_BSD_SOURCE=0`. Если на твоей системе обработчик не сбрасывается — это и есть ответ: **`signal()` не определяет поведение однозначно, оно зависит от libc и флагов компиляции. Поэтому в production используют `sigaction()`.**

**Версия `sigaction()`:**
1. `struct sigaction sa = {0}; sa.sa_handler = handler; sigemptyset(&sa.sa_mask); sa.sa_flags = SA_RESTART;`
2. `sigaction(SIGINT, &sa, NULL);`
3. Тот же цикл `while(1) pause();`.
4. `Ctrl+C` сколько угодно раз — обработчик не сбрасывается, поведение детерминированное.

**Что зафиксировать в vault:**
- `signal()` — древний API, поведение зависит от libc. Не использовать в новом коде.
- `sigaction()` даёт явный контроль: `sa_mask` — какие сигналы блокировать на время выполнения handler'а; `sa_flags` (`SA_RESTART`, `SA_SIGINFO`, `SA_NODEFER` и др.) — как именно обрабатывать.

**Функции:** `signal()`, `sigaction()`, `sigemptyset()`, `pause()`.

## Задание 9.4 — `pipe-eof.c`

**Что делает:**
1. `pipe(fd)` → массив `[read_end, write_end]`.
2. `fork()`. Дочерний пишет в `fd[1]` строку `"hello"` и сразу `exit(0)` — но **не закрывает `fd[1]` родителя** (родительская копия write-end остаётся открытой!).
3. Родитель в цикле `read(fd[0], buf, sizeof(buf))` — читает что прислал ребёнок, потом ждёт `read()` снова.
4. Запустить — увидеть что после первой `read` (которая прочитала `"hello"`) **вторая `read()` виснет**, EOF не приходит.
5. Прервать через `Ctrl+C`. Затем модифицировать: после `fork()` родитель **сам закрывает `fd[1]`** (`close(fd[1])` — это закрывает родительскую копию write-end; ядро видит что больше никто не пишет, отдаёт EOF). Перезапустить — `read()` возвращает 0, программа корректно завершается.

**Что должен увидеть и зафиксировать:**
- EOF на pipe приходит когда **закрыты все** копии write-end. После `fork()` дескрипторы дублируются — у дочернего своя копия `fd[1]`, у родителя — своя. Ребёнок может сделать `close(fd[1])` и `exit()`, но если родитель не закрыл свою копию — pipe остаётся "пишущим", ядро ждёт.
- Правило: **после `fork()` каждая сторона закрывает ненужный конец pipe немедленно.**

**Функции:** `pipe()`, `fork()`, `read()`, `write()`, `close()`.

- Пойнт мок-собеса 2026-04-28 закрыт: я перепутал какой из них что значит. Теперь устаканено через цикл вживую.

### Ошибки и трудности

- Не проверил `d2 == NULL` после второго `opendir()`. Программа на `/tmp` работала, но если бы пути не было — был бы segfault в `readdir(NULL)`. Урок: **тот же паттерн `if (NULL) { perror; return 1; }` — везде где есть `opendir`**, не только при экспериментальной первой проверке.

## 9.2 — zombie

### Моё решение (после исправлений)

```c
pid_t p = fork();
if (p < 0) { perror("fork"); exit(1); }
if (p == 0) { exit(0); }                  // child
printf("parent %d: child - %d\n", getpid(), p);
sleep(15);
int status;
if (waitpid(p, &status, 0) == -1) { perror("waitpid"); exit(1); }
if (WIFEXITED(status))
    printf("child %d exited normally, code = %d\n", p, WEXITSTATUS(status));
```

В двух панелях `tmux`: в одной `./a.out`, в другой — `ps aux | grep Z` подряд несколько раз.

### Что наблюдал

- Пока родитель спит — `ps` стабильно показывает зомби: `PID Z+ tty6 [a.out] <defunct>`. Состояние `Z+` = zombie + foreground process group.
- Сразу после того как родитель напечатает `child ... exited normally` (то есть `waitpid` отработал) — следующая `ps aux | grep Z` зомби не находит. Запись из таблицы процессов ушла, PID-slot можно переиспользовать.
- Сравнение PID: ребёнок > родитель (например parent=2599, child=2600). Это нормальное поведение `fork()` — следующий свободный PID идёт после текущего.

### Ключевые выводы

1. **`fork()` возвращает разные значения двум процессам.** Это и есть единственный способ их различить:
   - в родителе — PID ребёнка (>0)
   - в ребёнке — `0`
   - при ошибке (например исчерпан `pid_max`) — `-1` в родителе, ребёнка не создалось
   Это норма, не "wtf API" — без этого нельзя было бы написать ветку "если я ребёнок, делай X".

2. **`getppid()` ≠ "PID моего ребёнка".** Это "**get parent** PID" — PID **родителя текущего процесса**. Для ребёнка `getppid()` = PID родителя (то что дал `fork`). Для родителя `getppid()` = PID **shell'а**, который запустил `./a.out`. Никогда не путать "child" в своей переменной с тем что вернул `getppid()`.

3. **`waitpid` возвращает status в bit-packed виде.** Читать только через макросы:
   - `WIFEXITED(status)` — true если ребёнок завершился через `exit()` (нормально)
   - `WEXITSTATUS(status)` — достать код выхода (то что ребёнок передал в `exit()`)
   - `WIFSIGNALED(status)` / `WTERMSIG(status)` — true и сигнал, если убит сигналом
   Прямое чтение `status` как `int` даёт мусор.

4. **Зомби — это запись в таблице процессов**, держит PID + exit code + ресурсы (`rusage`). Не дескрипторы, не память. Утечка зомби = утечка PID-slot'ов. Реап:
   - явно — `waitpid()` родителя
   - неявно — если родитель умер раньше ребёнка, осиротевшего реапит init/systemd (PID 1)

5. **stdout буферизация по умолчанию line-buffered на терминале.** `printf` без `\n` сидит в буфере процесса и не вылезает на экран, пока:
   - не появится `\n` в буфере, или
   - буфер не переполнится, или
   - не вызвать `fflush(stdout)`, или
   - не произойдёт `exit()`/`return из main` (тогда libc сам флашит).
   На pipe/file stdout fully-buffered — даже `\n` не помогает, нужен `fflush`. Привычка: после каждого диагностического `printf` либо `\n`, либо `fflush(stdout)`.

### Ошибки и трудности

- **Главный баг**: написал `pid_t child = getppid();` думая что это "PID моего ребёнка". На самом деле это PID моего родителя (bash). Поэтому `printf` показывал `child - 2408` где 2408 — PID shell'а. Параллельно `waitpid(child, ...)` ждал bash, возвращал `-1` с `errno = ECHILD`, `status` оставался неинициализированным мусором.
- Не проверял возврат `waitpid`. Если бы проверял — увидел бы `waitpid: No child processes` сразу и не запутался. **Правило: проверять возврат каждого syscall.**
- `printf` без `\n` в первой версии — не видел вывод пока родитель спал, путался какой PID искать в `ps`. Появился `\n` → всё пришло на экран сразу.
- Сначала пытался ловить вывод и `ps` в одной панели — не получалось, потому что родитель блокирует терминал на время `sleep`. Решение: две панели tmux. И обнаружил что **родитель и ребёнок наследуют один и тот же controlling tty** — поэтому printf ребёнка и родителя идёт в один и тот же терминал.

## 9.3 — signal-vs-sigaction

### Моё решение

Один файл `signal-vs-sigaction.c` с CLI `--mode {signal|sigaction}`. Парсинг через ручной `strcmp` (для одного аргумента `getopt` избыточен). Handler инкрементирует `volatile sig_atomic_t count` и пишет статичную строку через `write(STDOUT_FILENO, ...)`. Главный цикл в main: `pause()` → когда просыпается, печатает `count=N` для всех новых срабатываний (через `last_seen` и догон в `while (last_seen < count)`).

```c
static volatile sig_atomic_t count = 0;

void handler(int sig) {
    count++;
    const char msg[] = "got SIGINT\n";
    write(STDOUT_FILENO, msg, sizeof(msg) - 1);
}

int main(...) {
    /* установка через signal(SIGINT, handler) или sigaction с SA_RESTART */
    sig_atomic_t last_seen = 0;
    while (1) {
        pause();
        while (last_seen < count) {
            last_seen++;
            printf("count=%d\n", last_seen);
        }
    }
}
```

### Что наблюдал

Запускал оба режима, нажимал `Ctrl+C` несколько раз. На моей системе (Ubuntu Server, glibc):
- **`--mode sigaction`**: каждый Ctrl+C → handler срабатывает, `count=1`, `count=2`, `count=3`, ... — поведение детерминированное, обработчик не сбрасывается.
- **`--mode signal`**: то же самое поведение. **Сброса handler'а нет** — `signal()` на современном glibc ведёт себя как BSD-вариант, не как System V.

То есть на этой конкретной системе разница между `signal()` и `sigaction()` **не видна на глаз**. Это и есть пойнт упражнения: **поведение `signal()` не определено стандартом однозначно**, оно зависит от libc и флагов компиляции. Поэтому в production используют `sigaction()` с явными флагами — там поведение зафиксировано POSIX'ом.

### Ключевые выводы

1. **Модель сигналов = программный interrupt.** Handler срабатывает в любой момент между инструкциями главного потока. Это не отдельный поток — главный поток замораживается, регистры пушатся на стек, выполняется handler, стек разворачивается, главный поток продолжает.

2. **Handler устанавливается один раз — действует всё время жизни процесса** (при `sigaction`, или при `signal` на современном glibc). Сразу после `sigaction(SIGINT, ...)` любой Ctrl+C в любом месте программы вызовет handler. Не нужно "подписываться заново".

3. **Pending signals не очередь — это бит.** Три Ctrl+C подряд пока handler работает = handler позовётся **один раз** после возврата, не три. Realtime-сигналы (SIGRTMIN..SIGRTMAX) — исключение, они queueable.

4. **Async-signal-safety — главное правило написания handler'ов.** В handler'е можно вызывать только функции из списка POSIX async-signal-safe (`man 7 signal-safety`). `printf`, `malloc`, `fprintf`, `strerror` — **нельзя**. Они используют внутренние мьютексы и static state — handler может прервать main в середине их работы и устроить deadlock или corruption. **Можно**: `write`, `read`, `_exit`, `kill`, `getpid`, `signal`, `sigaction`. Базовый паттерн: handler делает только syscalls и обновляет флаги, всё остальное — в main loop.

5. **Идиома `static volatile sig_atomic_t flag` для общения handler ↔ main.**
   - `sig_atomic_t` — атомарное чтение/запись (одна инструкция, не разорвётся при прерывании сигналом)
   - `volatile` — запрет компилятору кешировать в регистре. Без него цикл `while (flag == 0)` может быть оптимизирован в бесконечный
   - `static` — internal linkage, не утечёт в другие файлы

6. **`signal()` vs `sigaction()`** — два API. `signal()` исторически на System V автоматически сбрасывал handler после первого срабатывания (классическая гонка). На современном glibc/BSD не сбрасывает. Поведение зависит от libc → в production используют **только** `sigaction()` где всё детерминированно. `sigaction()` плюс даёт `sa_mask` (доп. блокировка сигналов на время handler'а), `sa_flags` (`SA_RESTART`, `SA_SIGINFO` и др.), `siginfo_t` (расширенная информация — кто отправил, откуда).

7. **`SA_RESTART`** — флаг автоматического перезапуска прерванных syscalls. Без него `read`/`accept`/`connect` после сигнала возвращают `-1` с `errno = EINTR`, и нужно перезапускать вручную в цикле. С `SA_RESTART` ядро делает это само. **Не действует** на `pause`, `sleep`, `select`, `poll` — они и должны возвращаться по сигналу.

8. **`struct sigaction sa = {0};`** — обязательная инициализация. Структура содержит implementation-specific поля (`sa_restorer` на Linux), без обнуления там мусор.

### Ошибки и трудности

- **`signal(SIGINT, &sa);`** — передал указатель на `struct sigaction` вместо указателя на функцию-обработчик. Compile error из-за несовместимых типов. `signal()` принимает `void (*)(int)`, `sigaction()` — `struct sigaction *`. Это разные API, не путать.
- **Главный цикл `while(1) pause()` поставил внутри handler'а**, а не в main. После первого Ctrl+C программа застряла бы внутри handler'а навсегда. Канонический паттерн: handler делает минимум и быстро возвращается, цикл — в main.
- **`printf` в handler** — async-signal-unsafe. Заменил на `write(STDOUT_FILENO, ...)` со статической строкой.
- **Пробовал форматировать число в handler через `printf("%d", count)`** — нет async-signal-safe способа сделать это безопасно. Решение: handler только инкрементит счётчик, форматирование и печать — в main.
- **Забыл `SA_RESTART` в первой версии** — в данной программе с `pause()` визуально не виден, но для зачёта концепции — добавил.
- **Не инициализировал `struct sigaction sa;`** — добавил `= {0}` после комментария.
- **Не проверял возврат `signal()` / `sigaction()`** — добавил проверки на `SIG_ERR` / `-1`.
- **Оставил dead variable `got_signal`** в коде после рефакторинга на `count` — заметил, удалил.

## 9.4 — pipe-eof

### Моё решение

```c
int fd[2];
if (pipe(fd) == -1) { perror("pipe"); exit(1); }

pid_t p = fork();
if (p == 0) {
    close(fd[0]);                  // ребёнок не читает
    char *msg = "hello";
    write(fd[1], msg, strlen(msg));
    exit(0);
}
// родитель
close(fd[1]);                      // ← ключевая строка эксперимента
char buf[256]; ssize_t n;
while ((n = read(fd[0], buf, sizeof(buf) - 1)) > 0) {
    buf[n] = '\0';
    printf("parent received: %s\n", buf);
}
close(fd[0]);
waitpid(p, NULL, 0);
```

Запускал две версии — с `close(fd[1])` и без (закомментированной).

### Что наблюдал

- **С `close(fd[1])`**: программа печатает `parent received: hello`, потом `read()` возвращает `0` (EOF), цикл выходит, `waitpid` отрабатывает, процесс корректно завершается.
- **Без `close(fd[1])`** (закомментировал): `parent received: hello` печатается, потом программа **виснет на втором `read()`**. В соседней панели tmux `ps aux | grep a.out` показывает родителя в `S` (sleep, ждёт I/O — read на пустом pipe), ребёнка в `Z+` (зомби — родитель не вызвал `waitpid`, потому что застрял в read'е). Прерываю Ctrl+C — оба процесса умирают.

### Ключевые выводы

1. **EOF на pipe приходит когда ВСЕ копии write-end закрыты**, не одна из них. Ядро ведёт счётчик `nrwriters` — сколько процессов держат открытый write-end. `read()` возвращает `0` (EOF) только когда `nrwriters == 0`. Пока счётчик > 0 — `read()` либо отдаёт данные, либо блокируется ожидая их.

2. **После `fork()` дескрипторы дублируются**. Если у родителя после `fork()` есть `fd[1]` и у ребёнка тоже есть `fd[1]` — это **две разные копии одного pipe-end**, обе считаются в `nrwriters`. Закрытие одной копии не закрывает другую. Это и есть смысл правила "после `fork()` каждая сторона немедленно закрывает ненужный конец": если родитель только читает, его `fd[1]` нужно явно закрыть, иначе после смерти ребёнка `nrwriters` останется = 1 (родительская копия), и EOF никогда не придёт.

3. **`char *` и `char[]` — принципиально разные вещи в C.** `char *buf;` — это переменная-указатель (8 байт на стеке), значение — мусор, никакого буфера не выделено. Передача такого `buf` в `read()` — UB, запись по мусорному адресу, segfault. `char buf[256];` — массив на 256 байт, реальная память на стеке, корректный буфер. На уровне семантики:
   - `sizeof(char *)` = 8 (размер указателя)
   - `sizeof(char[256])` = 256 (размер массива)
   - В функции массив-параметр **распадается в указатель**, `sizeof` внутри = 8 — поэтому если функция должна знать размер, его передают явным аргументом

4. **SIGPIPE — симметричный случай.** Если все read-ends закрыты, `write()` приводит к SIGPIPE (default — terminate) или возврату `-1` с `errno = EPIPE` если SIGPIPE игнорируется. В сетевых программах SIGPIPE обычно игнорируют и проверяют `EPIPE`, иначе закрытие соединения партнёром убивает процесс.

5. **Гигиена fork+pipe**: правильный паттерн — каждая сторона немедленно закрывает ненужные концы:
   - ребёнок: `close(fd[0])` если только пишет, `close(fd[1])` если только читает
   - родитель: симметрично
   В простой одно-pipe программе на финальный результат не всегда влияет, но в цепочках типа `cmd1 | cmd2 | cmd3` (когда `dup2` подменяет stdin/stdout пайпами) забытый close ломает весь пайплайн — команды не получают EOF.

### Ошибки и трудности

- **Главный баг**: написал `char *buf;` (неинициализированный указатель) и передавал его в `read()`. Программа падала бы с segfault до того как я увижу pipe-эксперимент. Дополнительно — `sizeof(buf)` на этом `char *` = 8, а не размер буфера. Урок: `char *` ≠ `char[]`, `sizeof` на указателе = размер указателя.
- Забыл `<sys/wait.h>` для `waitpid()`. На glibc это пролезло с warning'ом implicit declaration, но формально UB. Привычка: каждая функция → явный хедер.
- Ребёнок не закрывал `fd[0]` (свой read-end). На результат этой задачи не влияло (EOF определяется write-ends), но это нарушение правила "закрывай ненужное немедленно". Добавил.
- Сначала делал только версию которая работает (с `close(fd[1])`). Не увидел зависание — а это и есть главное наблюдение упражнения. Закомментировал `close(fd[1])` отдельным запуском, поймал зависание в `ps`, увидел пару `S`/`Z+`.
