# B-18 — Internet checksum (RFC 1071)

**Тип:** атомарное (позиция 18/26, Фаза 4 — Raw sockets + L2/L3).
**Синтез опоры:** endianness и byte order (B-16 `interface-enumeration` — `htons`/`htonl`, представление данных в памяти vs на проводе); работа с сырыми байтами буфера (B-15 byte-exact парсинг). Право на raw socket из B-17 здесь **не нужно** — ничего не отправляем.

## Задание

Написать `sections/networking/internet-checksum/checksum.c` — программа строит **IP-заголовок** и **TCP-заголовок** в памяти для заданных src/dst адресов, считает для каждого Internet checksum по RFC 1071 и **верифицирует** результат (пересчёт по заголовку с уже вставленным checksum обязан дать 0).

```
usage: ./checksum <src-ip> <dst-ip>

$ ./checksum 192.168.1.10 192.168.1.20
IP header (20 bytes):
  45 00 00 28 00 00 40 00 40 06 00 00 c0 a8 01 0a
  c0 a8 01 14
  computed checksum: 0xXXXX
  verify (recompute over header incl. checksum): 0x0000  OK

TCP header (20 bytes) + pseudo-header:
  pseudo: src=192.168.1.10 dst=192.168.1.20 proto=6 tcp_len=20
  TCP bytes: 30 39 00 50 00 00 00 00 00 00 00 00 50 02 20 00
             00 00 00 00
  computed checksum: 0xXXXX
  verify: 0x0000  OK
```

(hex-байты заголовка выше реальны для этих полей; `0xXXXX` для checksum — плейсхолдер, посчитаешь сам.)

### Центральная идея — one's complement sum + end-around carry

Алгоритм из RFC 1071 в трёх шагах, и он один и тот же для IP, TCP, ICMP:

1. Разбить данные на **16-битные слова**, сложить их в аккумулятор пошире (`uint32_t`).
2. Пока в старших 16 битах аккумулятора остаётся перенос (carry) — свернуть его обратно в младшие 16 (**end-around carry**): `sum = (sum & 0xFFFF) + (sum >> 16)`, повторять пока `sum >> 16` не станет 0.
3. Взять **побитовое дополнение** (one's complement, `~`) младших 16 бит — это и есть checksum.

Два инварианта, вокруг которых крутится всё:
- **Поле checksum на момент расчёта = 0.** Считаешь сумму по заголовку, где это поле обнулено, потом кладёшь результат в него.
- **Свойство верификации:** если посчитать сумму по заголовку, где checksum **уже вставлен** (не обнулён), получится `0x0000`. Это твой тест на корректность — не нужно сверяться с внешним эталоном.

### Pseudo-header (только для TCP)

TCP checksum считается не по одному TCP-заголовку, а по конкатенации **pseudo-header + TCP-заголовок (+ данные, у нас данных нет)**. Pseudo-header — 12 байт, которые **не отправляются в пакете**, но участвуют в сумме:

```
  0                   1                   2                   3
  +--------+--------+--------+--------+
  |          Source IP (4)            |
  +--------+--------+--------+--------+
  |        Destination IP (4)         |
  +--------+--------+--------+--------+
  |  zero  | proto  |   TCP length    |   proto=6 (IPPROTO_TCP), TCP length = длина TCP-заголовка+данных
  +--------+--------+--------+--------+
```

Смысл: связать TCP-сегмент с IP-адресами, чтобы пакет, доставленный не тому хосту, был отбракован. Классическая ошибка — забыть pseudo-header и посчитать checksum только по TCP-заголовку.

### Алгоритм (пошагово)

1. Проверить `argc == 3`, иначе usage. Распарсить оба IP: `inet_pton(AF_INET, argv[i], &addr)` → `struct in_addr` (network order уже).
2. Построить IP-заголовок в буфере: заполнить `struct iphdr` (version=4, ihl=5, tot_len, ttl, protocol=IPPROTO_TCP, saddr/daddr), поле `check` **обнулить**. Многобайтовые поля — через `htons`/`htonl`.
3. Посчитать IP checksum по заголовку с `check=0`, положить результат в `iph->check`.
4. Верификация IP: пересчитать checksum по заголовку с уже вставленным `check` — сравнить с 0. Вывести OK/FAIL.
5. Построить pseudo-header (12 байт: saddr, daddr, 0, proto=6, htons(tcp_len)) + TCP-заголовок (`struct tcphdr`: source, dest, seq, doff=5, syn=1, window), поле `check` **обнулить** — в один сплошной буфер.
6. Посчитать TCP checksum по этому буферу, положить в `tcph->check`.
7. Верификация TCP аналогично шагу 4.
8. Вывести hex-дампы заголовков и вычисленные значения: `printf("%02x ", byte)` в цикле.

## Примеры для теста

- **Тест 1** — базовый прогон, оба verify = OK — `./checksum 192.168.1.10 192.168.1.20`
- **Тест 2** — другие адреса, checksum должен отличаться, verify по-прежнему OK — `./checksum 10.0.0.1 8.8.8.8`
- **Тест 3** — нечётная длина: временно добавь 1 байт данных к TCP (payload), проверь что последний одиночный байт обработан и verify = OK. Либо unit-тест checksum на известном векторе из RFC 1071 §3 (последовательность байт → известная сумма).
- **Тест 4** — негативный: намеренно испорти один байт заголовка ПОСЛЕ вставки checksum → verify обязан дать не-ноль (FAIL). Доказывает, что проверка работает.

## Разбор /check

Файл дошёл до чистой сборки (`-Wall -Wextra`, 0 предупреждений) за несколько итераций `/check`. Баги по классам:

| Итерация | Найдено | Класс |
|----------|---------|-------|
| ранняя | `compute_checksum` не двигал `data` (`data += 2` забыт) → цикл читал одно и то же первое слово | логика цикла |
| ранняя | нечётная `len`: хвостовой байт терялся (`while (len>1)` останавливался на 1) → добавлена ветка `if (len==1) sum += *data<<8` (padding нулём **справа**) | edge case |
| ранняя | бессмысленные проверки `data+1 != NULL` (не bounds check, а проверка указателя; `p+1==NULL` практически недостижимо + UB заграничного указателя) → одна проверка `data==NULL` на входе | ложная защита |
| `inet_pton` | проверка `== -1` пропускала невалидный IP: `inet_pton` возвращает `0` на битой строке, `-1` только на неизвестном address family → битый `argv` шёл дальше с мусором в `addr` | недоверенный вход (§4) |
| sentinel | `uint32_t valid_addr(...)` возвращал `-1` как ошибку — коллизия: адрес занимает весь `2^32`, `0xFFFFFFFF` = валидный broadcast → разделил статус (`int` return) и данные (out-param) | контракт функции |
| проброс | `main` игнорировал возврат `build_*`; `build_tcp` игнорировал `build_pseudo` → протянул `-1` до `main`, где печать + `exit(FAILURE)` | error propagation |
| рецидив | `build_pseudo_header` не в прототипах (implicit declaration) + `valid_addr(dst_ip)` вызван с одним аргументом (`daddr` получал адрес src) | механический промах при рефакторинге |
| byte order | `hdr->check = compute(...)` без `htons` → на LE checksum ложилась в память перевёрнутой; **подтверждено численно** на эталонном заголовке (Wikipedia, wire `b8 61`): функция вернула `0xb861`, raw-store дал `61 b8` → фикс `htons(compute(...))` в обоих местах | byte order на границе функции |
| косметика | порты `source`/`dest` перепутаны по смыслу (source=80, dest=54321 для SYN к серверу) — на checksum не влияет | семантика |

**Security-заметки (§4):** `*data << 8` — UB нет (`uint8_t` → integer promotion до `int`, max `0xFF00` ≪ `INT_MAX`); `compute_checksum` слепо доверяет паре `(data, len)` — короче реального буфера `len` = OOB-read, ответственность вызывающего; `pseudo_header` без padding (`sizeof == 12`) — иначе `buffer[32]` переполнится, размер выражен через `sizeof(pseudo) + sizeof(*header)`, не литералом.

## Session-debrief / итог

**Что усвоено:** алгоритм RFC 1071 (folding = end-around carry, `~sum`, инвариант «поле `check`=0 при расчёте»), сборка IP/TCP-заголовков из `struct iphdr`/`struct tcphdr` с byte order по полям (`htons`/`htonl`, адреса из `inet_pton` уже network), pseudo-header для TCP checksum (12 байт, не отправляется, защита от misdelivery), сборка буфера pseudo+tcp через `memcpy` для единого прохода checksum, верификация через свойство «пересчёт по заголовку с вставленным check = 0».

**Главные уроки сессии:**
1. **Byte order живёт на границе функции.** Свёртка суммы byte-order-независима (one's complement коммутирует с byteswap), но результат forced-BE чтения нужно класть в поле через `htons` — иначе host-order запись переворачивает байты. Поймано не self-verify (использует ту же функцию → согласованная ошибка), а **независимым расчётом** против эталона.
2. **Sentinel-коллизия.** Тип, покрывающий весь диапазон возврата (IPv4 = `2^32`), не оставляет значения под ошибку → статус и данные разделять (out-param), как `inet_pton`.

**Слабое место (сам сформулировал):** «работа с байтами остаётся сложной» — сборка слов из байт, byte order при чтении/записи, ручная раскладка буфера. Концепции усваиваются, но байтовый уровень требует проговаривания по шагам, не автоматизм (продолжение линии B-12/B-15/B-16 — endianness и byte-exact парсинг).

**Что бы сделал иначе:** держать в голове чек-лист «каждое многобайтовое поле → нужен ли ему свой byte order при записи», включая поле `check`; при переходе на новую сигнатуру функции сразу править все вызовы (рецидив `valid_addr(dst_ip)` — механический промах на рефакторинге, класс подтверждён с B-13/B-15).

### Ключевые термины (English)
- **one's complement sum** — сумма 16-битных слов с end-around carry; основа internet checksum.
- **end-around carry / folding** — перенос за 16-й бит заворачивается обратно в младшие 16 (`(sum & 0xFFFF) + (sum >> 16)`).
- **pseudo-header** — 12 байт из L3-контекста (src/dst IP, proto, TCP length), суммируются в TCP checksum, не отправляются.
- **byte order independence** — свойство one's complement sum: byte-swapped вход → byte-swapped выход, тот же checksum (RFC 1071 §2).
- **sentinel value** — зарезервированное значение под «ошибку/пусто»; невозможно, если тип покрывает весь диапазон данных.
- **out-parameter** — возврат данных через переданный указатель, статус — через `return` (контракт `inet_pton`).
- **implicit declaration** — вызов функции без прототипа в C; компилятор угадывает сигнатуру → рассинхрон типов.
